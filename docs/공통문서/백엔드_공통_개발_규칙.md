# ABC 백엔드 공통 개발 규칙

> 프로젝트: Acorn Book Cloud(ABC)
> 목적: 팀원별 API 구현 방식 차이를 줄이기 위한 최소 공통 규칙

---

## 1. API 기본 규칙

- API prefix는 `/api/v1`로 통일한다.
- URL은 복수형 명사를 사용한다.
- Controller는 Entity를 직접 반환하지 않고 Response DTO를 반환한다.
- Request Body는 반드시 Request DTO로 받는다.
- 생성 성공은 `201 Created`, 일반 조회/수정/삭제 성공은 `200 OK`를 사용한다.

예시:

```text
POST   /api/v1/auth/register
POST   /api/v1/auth/login
GET    /api/v1/books
GET    /api/v1/books/{bookId}
POST   /api/v1/books/{bookId}/favorites
DELETE /api/v1/books/{bookId}/favorites
GET    /api/v1/members/me
```

## 2. 공통 성공 응답

모든 API 성공 응답은 아래 형식을 기본으로 한다.

```json
{
  "success": true,
  "code": "OK",
  "message": "요청이 성공했습니다.",
  "data": {}
}
```

생성 성공 예시:

```json
{
  "success": true,
  "code": "CREATED",
  "message": "생성되었습니다.",
  "data": {
    "id": 1
  }
}
```

데이터가 없는 성공 응답은 `data`를 `null`로 내려준다.

```json
{
  "success": true,
  "code": "OK",
  "message": "처리되었습니다.",
  "data": null
}
```

## 3. 페이징 응답

목록 API는 Spring Page 객체를 그대로 반환하지 않고 아래 구조로 변환한다.

```json
{
  "success": true,
  "code": "OK",
  "message": "조회되었습니다.",
  "data": {
    "content": [],
    "page": 0,
    "size": 10,
    "totalElements": 135,
    "totalPages": 7,
    "last": false
  }
}
```

기본 페이징 파라미터:

```text
page=0
size=10
sort=createdAt,desc
```

## 4. 공통 에러 응답

예외 발생 시 응답 형식은 아래로 통일한다.

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해주세요.",
  "errors": [
    {
      "field": "email",
      "message": "이메일 형식이 올바르지 않습니다."
    }
  ]
}
```

일반 비즈니스 예외는 `errors`를 빈 배열로 내려준다.

```json
{
  "success": false,
  "code": "MEMBER_EMAIL_DUPLICATED",
  "message": "이미 사용 중인 이메일입니다.",
  "errors": []
}
```

## 5. HTTP Status 기준

| 상황 | HTTP Status |
|---|---:|
| 조회/수정/삭제 성공 | 200 OK |
| 생성 성공 | 201 Created |
| 입력값 오류, 잘못된 요청 | 400 Bad Request |
| 로그인 실패, 토큰 없음, 토큰 만료 | 401 Unauthorized |
| 권한 없음 | 403 Forbidden |
| 리소스 없음 | 404 Not Found |
| 중복, 이미 처리된 요청 | 409 Conflict |
| 서버 내부 오류 | 500 Internal Server Error |

예시:

| 상황 | Status | Error Code |
|---|---:|---|
| 이메일 중복 | 409 | MEMBER_EMAIL_DUPLICATED |
| 로그인 실패 | 401 | AUTH_LOGIN_FAILED |
| 없는 도서 조회 | 404 | BOOK_NOT_FOUND |
| 이미 대여 중인 도서 | 409 | RENTAL_ALREADY_EXISTS |
| Validation 실패 | 400 | VALIDATION_ERROR |

## 6. ErrorCode 규칙

에러 코드는 `도메인_상황` 형식의 대문자 스네이크 케이스를 사용한다.

```text
COMMON_NOT_FOUND
VALIDATION_ERROR
AUTH_LOGIN_FAILED
AUTH_TOKEN_EXPIRED
AUTH_ACCESS_DENIED
MEMBER_EMAIL_DUPLICATED
MEMBER_NOT_FOUND
BOOK_NOT_FOUND
RENTAL_ALREADY_EXISTS
PAYMENT_FAILED
```

팀원이 새 예외를 추가할 때는 반드시 `ErrorCode enum`에 먼저 추가한다.
서비스 계층에서는 아래 방식으로 예외를 던진다.

```java
throw new BusinessException(ErrorCode.MEMBER_EMAIL_DUPLICATED);
```

## 7. Validation 규칙

- 입력 검증은 Request DTO에서 처리한다.
- Controller 파라미터에는 `@Valid`를 붙인다.
- Entity에는 화면/API 입력 검증용 어노테이션을 남발하지 않는다.
- Validation 메시지는 한글로 작성한다.
- Validation 실패는 항상 `400 Bad Request + VALIDATION_ERROR`로 응답한다.

예시:

```java
public record RegisterRequest(
    @NotBlank(message = "아이디는 필수입니다.")
    @Size(min = 5, max = 20, message = "아이디는 5~20자로 입력해주세요.")
    @Pattern(regexp = "^[a-zA-Z0-9]+$", message = "아이디는 영문과 숫자만 사용할 수 있습니다.")
    String loginId,

    @NotBlank(message = "이메일은 필수입니다.")
    @Email(message = "이메일 형식이 올바르지 않습니다.")
    String email,

    @NotBlank(message = "비밀번호는 필수입니다.")
    @Pattern(
        regexp = "^(?=.*[A-Za-z])(?=.*\\d)(?=.*[^A-Za-z0-9]).{8,20}$",
        message = "비밀번호는 영문, 숫자, 특수문자를 포함해 8~20자로 입력해주세요."
    )
    String password
) {}
```

## 8. DTO 네이밍 규칙

| 구분 | 규칙 | 예시 |
|---|---|---|
| 요청 DTO | `기능명Request` | `RegisterRequest`, `BookCreateRequest` |
| 응답 DTO | `기능명Response` | `LoginResponse`, `BookDetailResponse` |
| 목록 항목 DTO | `기능명SummaryResponse` | `BookSummaryResponse` |
| 내부 조건 DTO | `기능명Command`, `기능명Criteria` | `RegisterCommand`, `BookSearchCriteria` |

DTO는 기능 패키지의 `dto` 하위에 둔다.

```text
auth/dto/RegisterRequest.java
auth/dto/LoginResponse.java
book/dto/BookSummaryResponse.java
book/dto/BookDetailResponse.java
```

## 9. 패키지 구조

기능별 패키지 구조를 기본으로 한다.

```text
com.acorn.abc
  common
    config
    exception
    response
    security
  auth
    controller
    service
    dto
    domain
    repository
  member
    controller
    service
    dto
    domain
    repository
  book
    controller
    service
    dto
    domain
    repository
```

공통 규칙:

- Controller: 요청/응답 DTO 처리, HTTP 상태 결정
- Service: 비즈니스 로직, 트랜잭션 처리
- Repository: DB 접근
- Domain/Entity: 핵심 데이터 모델
- DTO: API 입출력 전용 객체

## 10. BaseEntity 규칙

모든 Entity는 `BaseEntity`를 상속받아 공통 필드를 사용한다.

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

Entity 예시:

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Member extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // ...
}
```

- `createdAt`, `updatedAt`은 모든 Entity에 BaseEntity로만 추가한다. 직접 선언하지 않는다.
- `@EnableJpaAuditing`은 메인 클래스 또는 별도 Config에 선언한다.

## 11. 날짜/시간 규칙

- 서버 기준 시간대는 `Asia/Seoul`로 한다.
- 날짜는 `yyyy-MM-dd` 형식을 사용한다.
- 날짜시간은 `yyyy-MM-dd'T'HH:mm:ss` 형식을 사용한다.

예시:

```json
{
  "birthDate": "2000-01-01",
  "createdAt": "2026-07-01T14:30:00"
}
```

## 12. Swagger 작성 규칙

Controller에는 `@Tag`, API 메서드에는 `@Operation`을 작성한다.
Request/Response DTO에는 필요한 경우 `@Schema`를 작성한다.

```java
@Tag(name = "Auth", description = "인증 API")
@RestController
@RequestMapping("/api/v1/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthService authService;

    @Operation(summary = "회원가입", description = "신규 회원을 등록합니다.")
    @PostMapping("/register")
    public ResponseEntity<ApiResponse<Long>> register(@Valid @RequestBody RegisterRequest request) {
        Long memberId = authService.register(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.created(memberId));
    }
}
```

## 13. Git 협업 규칙

브랜치:

```text
main       운영/최종 제출 브랜치
feature/*  기능 개발 브랜치
```

예시:

```text
feature/auth
feature/book
feature/rental
feature/admin-member
```

커밋 메시지:

```text
feat: 회원가입 API 추가
fix: 로그인 실패 응답 코드 수정
docs: 공통 응답 문서 추가
refactor: 도서 조회 서비스 분리
test: 회원가입 validation 테스트 추가
chore: swagger 의존성 추가
```

PR 규칙:

- `feature/*`에서 작업 후 `main`으로 PR을 생성한다.
- PR 전 최소한 로컬에서 빌드 또는 테스트를 실행한다.
- 공통 응답, 예외 응답, URL 규칙이 맞는지 확인한다.

## 14. 초기 구현 우선순위

DB가 확정되기 전에도 아래 공통 코드는 먼저 맞춘다.

1. `BaseEntity`
2. `ApiResponse`
3. `PageResponse`
4. `ErrorResponse`
5. `ErrorCode`
6. `BusinessException`
7. `GlobalExceptionHandler`
8. Validation 실패 처리
9. Swagger 기본 설정
10. Security 기본 설정

이 문서의 규칙이 바뀌면 팀원에게 공유하고, 관련 공통 코드도 같이 수정한다.
