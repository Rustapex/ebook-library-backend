## 3. 실제 후속 작업

### 3.1 감사 로그 enum DB CHECK 제약 추가

대상:

- 테이블: `admin_audit_log`
- 컬럼:
  - `action_type`
  - `target_type`

이유:

- Java enum은 애플리케이션 정상 경로에서 허용되지 않은 값을 막는다.
- 하지만 DB 직접 INSERT/UPDATE, 운영 보정 SQL, 외부 import, 우회성 버그 경로는 Java enum을 거치지 않을 수 있다.
- 현재 DB 컬럼은 `VARCHAR(50)`라서 DB 차원에서는 enum 외 문자열을 막지 못한다.
- 따라서 CHECK 제약은 DB 무결성의 마지막 방어선으로 추가하는 것이 맞다.

작성된 후속 문서:

- `docs/작업현황/2026-07-14_PR46_감사로그_DB_CHECK제약_후속계획.md`
- `docs/작업현황/2026-07-14_PR46_admin_audit_log_check_constraints.sql`

적용 방향:

1. SQL로 현재 DB의 invalid `action_type`/`target_type` 데이터를 먼저 조회한다.
2. invalid 데이터가 없을 때만 CHECK 제약을 추가한다.
3. CHECK 제약 추가 후 `information_schema.check_constraints`로 적용 여부를 확인한다.
4. 기존 감사 로그 조회 API `GET /api/v1/admin/audit-logs?page=0&size=10`을 1회 호출해 회귀를 확인한다.

`schema.sql` 반영 여부:

- 최종적으로 fresh DB까지 같은 무결성을 보장하려면 `src/main/resources/schema.sql`에도 같은 CHECK 제약을 반영하는 것이 가장 깔끔하다.
- 다만 이번 사용자가 요청한 범위는 `docs/작업현황` 하위 계획 및 수동 적용 SQL 작성이므로, 실제 `schema.sql` 수정은 별도 코드 변경 지시가 있을 때 진행한다.

## 4. 코드 수정이 아닌 항목

### 4.1 PR 본문 최신화

최신 comment 기준으로 PR 본문에 남아 있을 수 있는 “Swagger/Postman 미실행” 문구는 실제 테스트 완료 상태와 맞지 않는다.

하지만 이것은 GitHub PR 본문 정리 작업이다. 저장소 소스 코드나 계획 문서의 구현 작업으로 분류하지 않는다.

### 4.2 `idx_reading_progress_last_read_at`

결정:

- `idx_reading_progress_last_read_at`는 `schema.sql`에 넣지 않는다.
- 성능 인덱스 sidecar SQL로 유지한다.
- 사용자 로컬 DB에는 이미 적용 완료.
- 팀원에게 공유 예정.

따라서 현재 계획 문서에서 추가 구현 작업으로 잡지 않는다.

### 4.3 `TOTAL + baseDate`

결정:

- 기존 설계대로 유지한다.
- `TOTAL`은 전체 기간/오늘 기준 KPI 집계 의미를 유지한다.
- trend bucket은 `baseDate` 기준 최근 12개월 계산 구조를 유지한다.
- 최신 comment에서도 blocker가 아니라 문서/계약 이해를 위한 watch 항목으로 언급됐다.

따라서 소스 수정 계획에는 넣지 않는다. 필요하면 PR 본문 또는 API 설명 문서에서 의미를 명확히 쓰는 정도로 충분하다.
