## 1. 구현 목표

### 1.1 `API-AUTH-001` 회원가입 아이디/이메일 중복 검증 JSON 응답

API:

- `API-AUTH-001`
- `POST /api/v1/auth/signup`
- 인증: 비회원

목표:

- 회원가입 요청의 `loginId`가 이미 `member.login_id`에 존재하면 회원가입을 막는다.
- 회원가입 요청의 `email`이 이미 `member.email`에 존재하면 회원가입을 막는다.
- 단순 차단에서 끝내지 않고, 백엔드 공통 규칙에 맞는 JSON 에러 응답을 내려준다.
- 중복이 없으면 `201 Created`와 공통 성공 응답 JSON으로 회원가입 성공 정보를 반환한다.

기대 에러 응답:

```json
{
  "success": false,
  "code": "MEMBER_LOGIN_ID_DUPLICATED",
  "message": "이미 사용 중인 아이디입니다.",
  "errors": []
}
```

이메일 중복도 같은 구조로 `code=MEMBER_EMAIL_DUPLICATED`, `errors=[]`를 반환한다.

구현 판단:

- `AuthService.signup()`의 중복 차단 로직은 이미 있다.
- 실제 확인해야 할 부분은 전역 예외 처리 결과가 공통 에러 JSON 형식으로 내려가는지다.
- 부족하면 `GlobalExceptionHandler` 또는 관련 예외 응답 처리를 공통 규칙에 맞춘다.
- `AuthServiceTest`/`AuthControllerTest` 중 하나 이상에서 중복 아이디 JSON 응답까지 확인한다.

### 1.2 `API-ME-001` 회원정보 수정 전 기존 정보 채우기

API:

- `API-ME-001`
- `GET /api/v1/me`
- 인증: 회원 A JWT

목표:

- `U-015 /me/profile` 진입 시 프론트가 먼저 `GET /api/v1/me`를 호출한다.
- 응답에는 회원정보 수정 화면에 필요한 기존 정보가 모두 들어 있어야 한다.
- 성공 응답은 공통 성공 JSON 형식으로 내려준다.

기대 성공 응답 구조:

```json
{
  "success": true,
  "code": "OK",
  "message": "요청이 성공했습니다.",
  "data": {
    "memberId": 1,
    "loginId": "member0714a",
    "name": "회원A",
    "email": "member0714a@example.com",
    "phone": "010-0714-0001",
    "birthDate": "1995-07-14",
    "gender": "MALE",
    "role": "USER",
    "status": "JOINED"
  }
}
```

구현 방향:

- `MeController`에 `@GetMapping` 추가
- `MemberService.getMyInfo(memberId)` 추가
- `MeInfoResponse` 또는 `MemberMeResponse` DTO 추가
- 인증 사용자는 `@AuthenticationPrincipal CustomUserDetails`에서 `memberId`를 얻는다.
- 다른 회원 ID를 요청 파라미터로 받지 않는다.

### 1.3 `API-ME-002` 회원정보 수정

API:

- `API-ME-002`
- `PATCH /api/v1/me`
- 인증: 회원 A JWT

목표:

- 로그인한 회원 본인의 수정 가능한 정보만 수정한다.
- 수정 가능한 필드:
  - `name`
  - `email`
  - `phone`
  - `gender`
- 수정 불가 필드:
  - `loginId`
  - `birthDate`
  - `role`
  - `status`
  - `memberId`
  - `gradeId`
  - `pointBalance`
- 이메일 변경 시 자기 자신을 제외한 다른 회원의 이메일과 중복되면 `409 + MEMBER_EMAIL_DUPLICATED` JSON 응답을 반환한다.
- 성공 응답은 수정된 회원정보를 공통 성공 JSON으로 반환한다.

구현 방향:

- `MeController`에 `@PatchMapping` 추가
- `MemberUpdateRequest` DTO 추가
- `MeInfoResponse` 또는 `MemberUpdateResponse` DTO 추가
- `MemberService.updateMyInfo(memberId, request)` 추가
- `Member` 엔티티에 `updateProfile(name, email, phone, gender)` 같은 명시적 변경 메서드 추가
- `MemberRepository`에 이메일 중복 검증 메서드 추가
  - 예: `boolean existsByEmailAndMemberIdNot(String email, Long memberId)`

## 4. 상세 구현 계획

### 4.1 회원가입 중복 검증 JSON 응답 확인/보강

현재 확인된 중복 차단 로직:

```java
if (memberRepository.existsByLoginId(request.loginId())) {
    throw new BusinessException(ErrorCode.MEMBER_LOGIN_ID_DUPLICATED);
}
```

작업 계획:

1. 기존 중복 차단 로직은 유지한다.
2. `MEMBER_LOGIN_ID_DUPLICATED`, `MEMBER_EMAIL_DUPLICATED`가 공통 에러 응답 JSON으로 내려가는지 확인한다.
3. 응답이 공통 규칙과 다르면 전역 예외 처리 응답 형식을 맞춘다.
4. 테스트 기대값은 아래처럼 고정한다.

```json
{
  "success": false,
  "code": "MEMBER_LOGIN_ID_DUPLICATED",
  "message": "이미 사용 중인 아이디입니다.",
  "errors": []
}
```

### 4.3 회원정보 수정 API 구현

수정 파일 후보:

- `src/main/java/com/acorn/abc/member/controller/MeController.java`
- `src/main/java/com/acorn/abc/member/service/MemberService.java`
- `src/main/java/com/acorn/abc/member/domain/Member.java`
- `src/main/java/com/acorn/abc/member/repository/MemberRepository.java`
- `src/main/java/com/acorn/abc/member/dto/MemberUpdateRequest.java`
- `src/main/java/com/acorn/abc/member/dto/MeInfoResponse.java`

요청 DTO 후보:

```json
{
  "name": "회원A수정",
  "email": "member0714a-updated@example.com",
  "phone": "010-0714-9999",
  "gender": "FEMALE"
}
```

검증 정책:

- `PATCH /api/v1/me`는 부분 수정 API로 확정한다.
- request body에서 누락된 필드는 기존값을 유지한다.
- `null`도 이번 구현에서는 기존값 유지로 처리한다. 선택값을 실제로 비우는 기능은 별도 요구가 생기면 후속 API/정책으로 분리한다.
- `name`: 값이 있으면 blank 불가. 누락/null이면 기존값 유지.
- `email`: 값이 있으면 blank 불가, 이메일 형식 검증, 자기 자신 제외 중복 검증. 누락/null이면 기존값 유지.
- `phone`: 선택값. 누락/null이면 기존값 유지, 빈 문자열은 `null`로 정규화해 전화번호 제거로 처리한다.
- `gender`: 이번 범위에서는 DB/Entity enum 전환 없이 `String` 컬럼을 유지하고, 요청 DTO 검증에서 `MALE`, `FEMALE`, `NONE`만 허용한다. 누락/null이면 기존값을 유지하고, `NONE`을 명시하면 DB에는 `null`로 저장해 성별 선택을 제거한다.
- request body에 `loginId`, `birthDate`, `role`, `status`가 들어오지 않도록 DTO에 필드를 만들지 않는다.

## 7. 확정된 구현 정책과 남은 확인사항

### 7.1 이번 구현에서 확정한 정책

1. `API-ME-001` 응답 범위
   - 회원정보 수정 화면 진입 시 기존 값을 채우기 위한 기본 정보만 반환한다.
   - 반환 대상은 `memberId`, `loginId`, `name`, `email`, `phone`, `birthDate`, `gender`, `role`, `status`로 잡는다.
   - API 명세의 마이페이지 요약 카운트는 필요하지 않으므로 이번 범위와 후속 작업 항목에서 제외한다.

2. 마이페이지 요약 카운트의 의미
   - API 명세의 `API-ME-001`에는 회원 기본정보 외에 포인트, 쿠폰 수, 대여 수, 완독 수, 즐겨찾기 수, 미읽은 알림 수가 함께 적혀 있다.
   - 이 값들은 `U-014` 마이페이지 요약 카드/배지용 정보에 가깝고, `U-015` 회원정보 수정 화면의 기존값 채우기에는 필수값이 아니다.
   - 이번 작업의 `API-ME-001`은 `U-015` 회원정보 수정 화면의 기존 정보 조회 용도로 확정하며, 요약 카운트는 구현하지 않는다.

3. `PATCH /api/v1/me` 누락/null 처리
   - `PATCH`는 부분 수정으로 처리한다.
   - 누락된 필드는 기존값 유지로 확정한다.
   - `null`도 기존값 유지로 확정한다.
   - 필수 성격의 수정 필드인 `name`, `email`은 값이 들어온 경우 blank를 허용하지 않는다.
   - 선택 필드인 `phone`은 빈 문자열이 들어오면 `null`로 정규화해 전화번호 제거로 처리한다.

4. `gender` 처리
   - 이번 범위에서는 DB 컬럼과 Entity 타입을 enum으로 바꾸지 않는다.
   - 현재 `MEMBER.gender`는 `VARCHAR(20)`, `Member.gender`는 `String`이므로 enum 전환은 Entity, DTO, 기존 데이터, schema/data, 테스트까지 영향이 생긴다.
   - 대신 요청 DTO 단계에서 허용값을 `MALE`, `FEMALE`, `NONE`으로 제한한다.
   - 누락/null이면 기존값을 유지한다.
   - 요청값이 `NONE`이면 성별 선택 제거로 해석하고 DB에는 `null`로 저장한다.

### 7.2 추가 결정 필요 없음

1. `phone` 제거는 요청의 빈 문자열을 `null`로 정규화하는 방식으로 확정했다.
2. `gender=NONE`은 성별 선택 제거로 해석하고 DB에는 `null`로 저장하는 방식으로 확정했다.
3. `API-ME-001`은 `U-015` 회원정보 수정 화면에 필요한 기본 정보만 반환하며, 마이페이지 요약 카운트는 구현하지 않는 것으로 확정했다.
