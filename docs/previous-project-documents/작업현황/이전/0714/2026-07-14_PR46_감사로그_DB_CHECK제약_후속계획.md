# PR #46 감사 로그 DB CHECK 제약 후속 계획

대상 PR 코멘트: https://github.com/shangpa/AcornProject/pull/46#issuecomment-4964890621
대상 항목: 3. 감사 로그 enum의 DB 제약은 아직 없음
범위: `schema.sql`은 수정하지 않고, 분리 SQL 파일과 설계문서 하위 근거 문서를 작성한다. 실제 DB 적용은 별도 실행한다.

## 0. targeted-file-reading 확인 근거

- PR #46 최신 재검토 코멘트(`#4964890621`)는 API 구현 100% 기준 blocker는 없다고 판단했다.
- 같은 코멘트에서 `admin_audit_log.action_type`, `target_type`은 Java/Swagger/test 레벨에서는 enum 동기화가 잡혔지만 DB에서는 `VARCHAR`이고 `CHECK` 제약이 없다고 watch 항목으로 남겼다.
- 기존 계획 문서에는 `schema.sql` 반영을 최종 권장안으로 열어둔 내용이 있었으나, 이번 결정은 `schema.sql`과 분리한 별도 SQL 파일로 진행하는 것이다.
- 이미 정리된 enum 기준값은 다음 Java enum을 source of truth로 삼는다.
  - `AdminAuditLogActionType`: `MEMBER_POINT_ADJUST`, `COUPON_CREATE`, `COUPON_ISSUE`, `BOOK_CREATE`, `CHALLENGE_UPDATE`, `MEMBER_UPDATE`, `BOOK_UPDATE`, `REPORT_PROCESS`, `NOTICE_WRITE`
  - `AdminAuditLogTargetType`: `MEMBER`, `COUPON`, `BOOK`, `CHALLENGE`, `BOOK_REPORT`, `REVIEW_REPORT`, `REVIEW`, `NOTICE`, `SANCTION_HISTORY`

## 1. 질문에 대한 판단

Java enum을 쓰면 애플리케이션의 정상 감사 로그 기록 경로에서는 enum에 없는 값이 들어가기 어렵다. `AdminAuditLogWriter`가 enum 타입을 받고, 조회 필터도 enum 파싱으로 검증하기 때문이다.

하지만 DB CHECK가 없으면 아래 경로는 여전히 열려 있다.

- 수동 SQL INSERT/UPDATE
- 운영/공유 DB 직접 보정
- 외부 배치나 import 스크립트
- 향후 다른 코드가 enum을 거치지 않고 문자열 저장 경로를 만들 가능성
- 기존 DB에 잘못된 값이 이미 들어가거나, 직접 입력으로 들어가는 경우

따라서 리뷰 3번의 핵심은 “Java enum만으로 애플리케이션 계층은 방어됐지만, DB 자체의 데이터 무결성은 아직 방어되지 않는다”는 뜻이다. DB CHECK는 마지막 방어선이다.

## 2. 확정 방향

이번 후속 작업은 아래 방향으로 확정한다.

1. `src/main/resources/schema.sql`은 수정하지 않는다.
2. `docs/작업현황` 하위에 감사 로그 CHECK 제약 전용 SQL 파일을 별도로 둔다.
3. 해당 SQL은 운영/공유/로컬 DB에 수동 적용하는 sidecar SQL로 취급한다.
4. 별도 SQL을 만든 이유와 적용 정책은 `docs/작업현황/설계문서` 하위의 근거 문서로 나중에 따로 남긴다.
5. 이 작업은 API 동작 변경이 아니라 DB 무결성 보강이다.

## 3. 별도 SQL 파일 작성 계획

작성 예정 파일:

- `docs/작업현황/2026-07-14_PR46_admin_audit_log_check_constraints.sql`

포함해야 할 내용:

1. 목적 주석
   - PR #46 최신 리뷰의 3번 watch 항목 대응임을 명시한다.
   - `schema.sql` 자동 초기화 대상이 아니라 수동 적용 SQL임을 명시한다.

2. 적용 전 데이터 점검
   - `admin_audit_log.action_type`이 Java enum 목록 밖인 행을 조회한다.
   - `admin_audit_log.target_type`이 Java enum 목록 밖인 행을 조회한다.
   - 두 조회 결과가 0건이어야 CHECK 제약 추가를 진행할 수 있다고 주석에 명시한다.

3. 기존 제약 중복 방지
   - 같은 이름의 CHECK 제약이 이미 있으면 제거하거나, 재실행 시 충돌하지 않도록 처리한다.
   - 제약명은 아래처럼 고정한다.
     - `chk_admin_audit_log_action_type`
     - `chk_admin_audit_log_target_type`

4. CHECK 제약 추가
   - `action_type IN (...)`
   - `target_type IN (...)`
   - 허용값은 Java enum 기준값과 동일해야 한다.

5. 적용 후 확인
   - `information_schema.check_constraints`에서 두 CHECK 제약이 등록됐는지 조회한다.

6. 선택적 실패 테스트
   - invalid `action_type` 또는 invalid `target_type` INSERT 예시는 주석 처리로만 둔다.
   - 실제 실행은 롤백 가능한 로컬 환경에서만 하도록 명시한다.

7. 회귀 확인 안내
   - SQL 적용 후 `GET /api/v1/admin/audit-logs?page=0&size=10`을 1회 호출해 기존 조회 API가 정상 동작하는지 확인한다.

## 4. `schema.sql`과 분리하는 이유

이번 작업에서는 `schema.sql`에 바로 CHECK 제약을 넣지 않는다.

이유:

- PR #46 최신 comment 기준으로 이 항목은 merge blocker가 아니라 운영/계약 watch 항목이다.
- 기존/공유 DB에 이미 생성된 테이블에는 `schema.sql` 수정만으로 제약이 자동 적용되지 않는다.
- 지금 필요한 것은 “현재 DB에 실제로 적용할 수 있는 수동 SQL”이다.
- `schema.sql`을 수정하면 fresh DB 초기화 정책까지 바뀌므로 별도 코드/스키마 변경 범위가 된다.
- 현재 결정은 `idx_reading_progress_last_read_at`처럼 런타임 스키마 자동 초기화와 분리해 수동 적용 대상으로 관리하는 것이다.

영향:

- 기존 DB: 별도 SQL을 실행해야 CHECK 제약이 생긴다.
- fresh DB: `schema.sql`에는 반영하지 않으므로 새로 초기화한 DB에는 CHECK 제약이 자동 생성되지 않는다.
- 팀 공유: SQL 파일과 적용 이유를 함께 공유해야 한다.
- 추후 정책 변경: fresh DB까지 동일하게 보호해야 한다고 결정하면 그때 `schema.sql` 반영 PR을 별도로 잡는다.

## 5. 설계문서 하위 근거 문서 작성 계획

이번 작업에서 아래 근거 문서를 작성한다. 이 문서는 설계문서 원문을 바로 수정하지 않고, 나중에 일괄 반영할 근거를 남기는 문서다.

작성 예정 파일:

- `docs/작업현황/설계문서/2026-07-14_PR46_감사로그_DB_CHECK제약_분리SQL_근거.md`

문서 목적:

- 왜 `schema.sql`이 아니라 별도 SQL 파일로 CHECK 제약을 적용하는지 설명한다.
- Java enum이 있는데도 DB CHECK가 필요한 이유를 설명한다.
- SQL 파일을 어떤 DB에, 어떤 순서로, 어떤 검증과 함께 적용해야 하는지 기록한다.
- 나중에 설계문서 원문을 일괄 반영할 때 참고할 근거를 남긴다.

문서에 포함할 내용:

1. 배경
   - PR #46 최신 리뷰에서 감사 로그 enum DB 제약 부재가 watch 항목으로 남았다.
   - API 구현 blocker는 아니지만 DB 무결성 보강 대상이다.

2. DB CHECK가 필요한 이유
   - Java enum은 애플리케이션 정상 경로를 막는다.
   - DB 직접 입력, 운영 보정, 외부 import, 우회성 코드 경로는 Java enum을 거치지 않을 수 있다.
   - 따라서 DB 자체에서 허용값을 제한해야 데이터 품질을 보장할 수 있다.

3. `schema.sql`과 분리하는 이유
   - 기존 DB에 즉시 적용 가능한 수동 SQL이 필요하다.
   - `schema.sql` 수정은 fresh DB 초기화 정책 변경이므로 이번 후속 범위와 분리한다.
   - 수동 적용 SQL은 적용 여부를 DB별로 확인하고 공유하기 쉽다.

4. 적용 대상
   - `admin_audit_log.action_type`
   - `admin_audit_log.target_type`

5. 적용 절차
   - invalid 데이터 사전 조회
   - 필요 시 데이터 정리
   - CHECK 제약 추가
   - `information_schema.check_constraints` 확인
   - 감사 로그 조회 API 회귀 확인

6. 한계와 후속 결정
   - fresh DB에는 자동 반영되지 않는다.
   - 추후 모든 초기화 DB에도 같은 제약이 필요하다고 결정되면 `schema.sql` 반영을 별도 작업으로 잡는다.

## 6. 구현/적용 순서

1. 이 계획 문서 내용을 기준으로 별도 SQL 파일을 작성 또는 보완한다.
2. 설계문서 하위 근거 문서는 실제 SQL 적용 전에 작성한다.
3. SQL §1로 현재 DB의 잘못된 `action_type`/`target_type` 값을 먼저 조회한다.
4. invalid 값이 1건이라도 있으면 CHECK 추가 전에 데이터를 먼저 정리한다.
5. SQL로 `action_type`, `target_type` CHECK 제약을 추가한다.
6. `information_schema.check_constraints`에서 제약 적용 여부를 확인한다.
7. 롤백 가능한 환경에서만 invalid INSERT 실패 테스트를 선택적으로 수행한다.
8. 기존 감사 로그 조회 API `GET /api/v1/admin/audit-logs?page=0&size=10`를 1회 호출해 정상 조회를 확인한다.
9. 팀원에게 SQL 파일, 적용 이유, 적용 여부 확인 방법을 공유한다.

## 7. 검증 계획

수동 DB 확인:

```sql
SELECT CONSTRAINT_NAME, CHECK_CLAUSE
FROM information_schema.check_constraints
WHERE CONSTRAINT_SCHEMA = DATABASE()
  AND CONSTRAINT_NAME IN ('chk_admin_audit_log_action_type', 'chk_admin_audit_log_target_type');
```

API 회귀 확인:

- `GET /api/v1/admin/audit-logs?page=0&size=10`
- 기대: `200`, `success=true`, 기존 감사 로그 목록 조회 가능

자동 테스트:

- 이번 분리 SQL 적용은 Java 코드 변경이 아니므로 자동 테스트 필수 범위는 아니다.
- 다만 이후 `schema.sql`까지 반영하는 별도 작업으로 확장하면 `./gradlew.bat build --console=plain`을 실행한다.
