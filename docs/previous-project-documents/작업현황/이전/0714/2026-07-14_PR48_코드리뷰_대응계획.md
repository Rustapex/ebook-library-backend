## 1. 목적

PR #48 마지막 코드리뷰에서 확인된 아래 세 항목을 반영해 최종 API 명세 충족도를 100%로 올린 뒤 병합 가능한 상태로 만든다.

1. `API-ME-001 GET /api/v1/me` 응답을 최종 API 명세대로 확장한다.
2. `API-ME-002 PATCH /api/v1/me` 요청 DTO의 문자열 길이 검증을 런타임 DB 제약과 일치시킨다.
3. 이메일 중복 사전 조회 이후 발생할 수 있는 DB UNIQUE 동시성 충돌도 `409 MEMBER_EMAIL_DUPLICATED`로 변환한다.

PR 본문에 기록된 Swagger/Postman 미실행 상태도 해소하고, 자동 테스트와 수동 API 테스트를 모두 완료한 뒤 병합한다.

## 2. targeted-file-reading 확인 근거

- 마지막 댓글의 최종 판단은 `수정 후 병합`이다.
- PR 본문에서 주장한 기존 범위의 구현 일치율은 100%지만, 최종 API 명세 충족도는 75%로 판정됐다.

- 현재 PR에는 Swagger/Postman 수동 검증 결과가 없다.

### 2.2 최종 API 명세와 화면 요구

- `docs/API 명세/api-spec(final).md:169`: `API-ME-001` 관련 Entity는 `MEMBER`, `MEMBER_GRADE`, `USER_READING_STATISTICS`, `MEMBER_COUPON`, `BOOK_RENTAL`, `FAVORITE_BOOK`이다.

### 2.3 런타임 DB와 현재 Repository

- `MEMBER.name`은 `VARCHAR(50)`, `MEMBER.email`은 `VARCHAR(255)`, `MEMBER.phone`은 `VARCHAR(20)`이다.
- `MEMBER.email`에는 `uk_member_email` UNIQUE 제약이 있다.
- 현재 회원의 포인트 잔액은 `MEMBER.point_balance`에 저장된다.
- 현재 등급은 `MEMBER.grade_id`와 `MEMBER_GRADE`로 확인할 수 있다.
- 등급 산정 시작일은 `MEMBER.grade_payment_started_at`에 저장되고, 등급 변경 시 결제 누적액을 다시 계산하는 기준이다.

- `ReadingProgressRepository.countCompletedByMemberAndPeriod()`는 기간을 `null`로 전달하면 회원의 전체 완독 수를 계산할 수 있다.
- 쿠폰 수, 회원 전체 대여 수, 미읽은 알림 수, 회원별 등급 산정 결제액에는 필요한 전용 집계 메서드가 아직 없다.

## 3. 확정된 결정

### 3.1 `API-ME-001`은 최종 명세대로 확장

리뷰에서 제시한 선택지 중 A안을 확정한다.

- 최종 API 명세를 기본정보 전용으로 축소하지 않는다.
- `GET /api/v1/me` 한 번으로 U-014 마이페이지 요약과 U-015 수정 화면 초기값을 모두 제공한다.
- 기존 기본정보 필드는 유지하고 등급/포인트/집계 필드를 추가한다.
- U-015는 확장된 응답 중 기본정보 필드만 사용하면 된다.

### 3.2 최종 응답 필드

`MeInfoResponse`는 아래 구조로 확장한다.

```json
{
  "memberId": 1,
  "loginId": "member0714a",
  "name": "회원A",
  "email": "member0714a@example.com",
  "phone": "010-0714-0001",
  "birthDate": "1995-07-14",
  "gender": "MALE",
  "role": "USER",
  "status": "JOINED",
  "grade": {
    "gradeId": 1,
    "gradeName": "씨앗",
    "gradeLevel": 1,
    "nextGradeId": 2,
    "nextGradeName": "새싹",
    "currentPaymentAmount": 10000,
    "targetPaymentAmount": 20000,
    "progressRate": 50.0
  },
  "pointBalance": 3000,
  "couponCount": 2,
  "rentalCount": 5,
  "completedBookCount": 3,
  "favoriteCount": 4,
  "unreadNotificationCount": 1
}
```

필드 타입과 의미:

| 필드 | 타입 | 계산 기준 |
|---|---|---|
| `grade` | object | 현재 등급, 다음 등급, 결제 달성률 요약 |
| `pointBalance` | int | `MEMBER.point_balance` 현재값 |
| `couponCount` | long | 현재 시점에 `ISSUED`이고 만료되지 않은 사용 가능 쿠폰 수 |
| `rentalCount` | long | 해당 회원의 전체 `BOOK_RENTAL` 행 수 |
| `completedBookCount` | long | 해당 회원의 `READING_PROGRESS.completed_yn=true` 전체 수 |
| `favoriteCount` | long | 현재 `FAVORITE_BOOK` 행 수 |
| `unreadNotificationCount` | long | 해당 회원의 `NOTIFICATION.read_yn=false` 수 |

### 3.3 등급 달성률 계산 정책

- 현재 등급보다 `gradeLevel`이 한 단계 높은 등급을 다음 목표 등급으로 조회한다.
- `currentPaymentAmount`는 현재 회원의 `PAID` 결제 중 등급 산정 시작일 이후 `PAYMENT.amount` 합계다.
- `gradePaymentStartedAt`이 `null`이면 회원 가입일을 결제 집계 시작일로 사용한다.
- `targetPaymentAmount`는 다음 등급의 `minPaymentAmount`다.
- `progressRate = min(100, currentPaymentAmount / targetPaymentAmount * 100)`으로 계산하고 소수 둘째 자리까지 반환한다.
- 이미 최고 등급이면 `nextGradeId`, `nextGradeName`, `targetPaymentAmount`는 `null`, `progressRate`는 `100.0`으로 반환한다.
- 이번 작업은 달성률 조회만 구현한다. 실제 자동 승급/하락 처리와 스케줄러는 범위에서 제외한다.

### 3.4 U-014의 리뷰 수 표기 불일치

- 화면흐름도 U-014 요약 카드에는 리뷰 수가 적혀 있지만 최종 API 명세 `API-ME-001` 응답 항목에는 리뷰 수가 없다.
- 문서 우선순위와 사용자의 결정에 따라 이번 구현은 최종 API 명세를 기준으로 하며 `reviewCount`는 추가하지 않는다.
- 구현 완료 후 `docs/작업현황/설계문서`의 반영 예정 문서에 이 불일치와 정리 필요성을 기록한다. 실제 화면흐름도 원문은 이번 코드리뷰 대응에서 직접 수정하지 않는다.

### 3.5 PATCH 기존 정책 유지

- 누락 또는 `null` 필드는 기존값을 유지한다.
- `phone=""` 또는 공백 문자열은 `null`로 정규화한다.
- `gender=NONE`은 DB에 `null`로 저장한다.
- `loginId`, `birthDate`, `role`, `status`는 수정 DTO에 넣지 않는다.

## 4. 상세 구현 계획

### 4.1 `API-ME-001` 응답 DTO 확장

대상:

- `src/main/java/com/acorn/abc/member/dto/MeInfoResponse.java`
- 신규 `src/main/java/com/acorn/abc/member/dto/MemberGradeSummaryResponse.java`

작업:

1. 기존 기본정보 필드는 유지한다.
2. 등급 정보는 중첩 DTO로 분리한다.
3. `pointBalance`, `couponCount`, `rentalCount`, `completedBookCount`, `favoriteCount`, `unreadNotificationCount`를 추가한다.
4. 기존 `MeInfoResponse.from(Member)`만으로 집계값을 만들 수 없으므로, 기본정보와 계산 결과를 명시적으로 받는 팩토리 메서드 또는 생성 흐름으로 변경한다.
5. Controller의 반환 형식은 기존대로 `ApiResponse<MeInfoResponse>`를 유지한다.

### 4.2 집계 Repository 메서드 추가/재사용

대상과 계획:

| Repository | 작업 |
|---|---|
| `MemberGradeRepository` | 현재 등급보다 높은 첫 등급 조회 메서드 추가 |
| `PaymentRepository` | 회원 ID, `PAID`, 등급 산정 시작일 기준 `SUM(amount)` 메서드 추가 |
| `MemberCouponRepository` | 회원 ID, `ISSUED`, 현재 시각 이전 미만료 조건의 사용 가능 쿠폰 수 메서드 추가 |
| `BookRentalRepository` | `countByMember_MemberId(memberId)` 추가 |
| `ReadingProgressRepository` | 기존 `countCompletedByMemberAndPeriod(memberId, null, null)` 재사용 |
| `FavoriteBookRepository` | 기존 `countByMember_MemberId(memberId)` 재사용 |
| `NotificationRepository` | `countByMember_MemberIdAndReadYnFalse(memberId)` 추가 |

집계는 한 회원의 마이페이지 조회 시 수행되는 단순 COUNT/SUM 쿼리다. 이번 범위에서는 복잡한 단일 native query나 별도 통계 스냅샷을 도입하지 않고, 기존 인덱스를 사용하는 명시적 Repository 집계로 구현한다.

### 4.3 GET 전용 집계 서비스 분리

`MemberService`에 다수의 조회 Repository 의존성을 추가하지 않도록 GET 전용 서비스를 분리한다.

- 신규 클래스: `member/service/MeInfoService`
- 책임: 회원 기본정보 조회, 현재/다음 등급 조회, 결제 달성률 계산, 요약 카운트 조합
- `MeController.getMe()`는 `MeInfoService.getMe(memberId)`를 호출한다.
- `MemberService`는 비밀번호 변경과 `PATCH /api/v1/me` 수정 책임을 유지한다.

서비스 조회 메서드는 `@Transactional(readOnly = true)`를 적용한다. 모든 집계 쿼리에는 인증 principal의 `memberId`를 그대로 전달하고 외부 회원 ID 입력은 받지 않는다.

### 4.4 PATCH DTO 길이 검증 보강

대상:

- `src/main/java/com/acorn/abc/member/dto/MemberUpdateRequest.java`

추가 검증:

| 필드 | 검증 |
|---|---|
| `name` | `@Size(max = 50)` |
| `email` | 기존 `@Email` 유지 + `@Size(max = 255)` |
| `phone` | `@Size(max = 20)` |
| `gender` | 기존 `@Pattern(MALE|FEMALE|NONE)` 유지 |

`@Size`는 `null`을 허용하므로 부분 수정의 누락/null 기존값 유지 정책과 충돌하지 않는다. 값이 전달된 경우에만 최대 길이를 검증하고, 초과 입력은 DB 접근 전에 `400 VALIDATION_ERROR`로 차단한다.

### 4.5 이메일 UNIQUE 동시성 충돌 변환

기존 `existsByEmailAndMemberIdNot()` 사전 조회는 빠른 사용자 피드백을 위해 유지한다. DB의 `uk_member_email` UNIQUE 제약도 최종 방어선으로 유지한다.

구현 흐름:

1. 사전 조회가 중복이면 기존대로 `MEMBER_EMAIL_DUPLICATED`를 던진다.
2. 사전 조회 이후 회원 이메일을 변경한다.
3. 트랜잭션 종료 이후가 아니라 서비스 내부에서 DB 제약 위반을 확인할 수 있도록 변경 직후 `memberRepository.flush()`를 수행한다.
4. `DataIntegrityViolationException`의 원인이 `uk_member_email`이면 `BusinessException(ErrorCode.MEMBER_EMAIL_DUPLICATED)`로 변환한다.
5. 다른 DB 제약 위반은 이메일 중복으로 오인하지 않고 원래 예외를 다시 던진다.
6. 기존 `MEMBER_EMAIL_DUPLICATED` ErrorCode를 재사용하므로 신규 ErrorCode 승인 요청은 필요 없다.

이 처리는 `MemberService.updateMyInfo()` 범위에 한정한다. 모든 `DataIntegrityViolationException`을 전역에서 이메일 중복으로 바꾸는 방식은 사용하지 않는다.

## 5. 자동 테스트 계획

### 5.1 `MeInfoServiceTest`

1. 기본정보와 모든 요약 카운트를 응답에 조합한다.
2. 포인트는 `Member.pointBalance` 현재값을 반환한다.
3. 사용 가능 쿠폰 수만 반환한다.
4. 대여/완독/즐겨찾기/미읽은 알림 수를 회원 ID 기준으로 조회한다.
5. 현재 등급과 다음 등급을 반환한다.
6. 등급 결제 누적액과 달성률을 계산한다.
7. 달성률이 100을 넘으면 100으로 제한한다.
8. 최고 등급이면 다음 등급/목표 금액은 `null`, 달성률은 `100.0`이다.
9. 회원이 없으면 `MEMBER_NOT_FOUND`를 반환한다.

### 5.2 `MeControllerTest`

1. `GET /api/v1/me` 정상 응답에 기존 기본정보가 유지된다.
2. 응답에 `grade`, `pointBalance`, `couponCount`, `rentalCount`, `completedBookCount`, `favoriteCount`, `unreadNotificationCount`가 포함된다.
3. `name` 51자 입력은 `400 VALIDATION_ERROR`다.
4. `email` 256자 입력은 `400 VALIDATION_ERROR`다.
5. `phone` 21자 입력은 `400 VALIDATION_ERROR`다.
6. 각 길이 검증 실패 응답의 `errors`에 대상 필드가 포함된다.

### 5.3 `MemberServiceTest`

1. 기존 이메일 중복 사전 조회의 `409` 변환을 유지한다.
2. 사전 조회에서는 중복이 없었지만 `flush()`에서 `uk_member_email` 충돌이 발생하면 `MEMBER_EMAIL_DUPLICATED`로 변환한다.
3. 이메일 외의 예상하지 못한 DB 무결성 예외는 그대로 다시 던진다.
4. 누락/null, phone blank, gender `NONE` 기존 정책의 회귀 테스트를 유지한다.

### 5.4 Repository 테스트

1. 회원별 사용 가능 쿠폰 수가 `ISSUED`와 만료 시각을 모두 반영한다.
2. 회원별 전체 대여 수를 정확히 집계한다.
3. 회원별 미읽은 알림 수에서 읽은 알림과 다른 회원 알림을 제외한다.
4. 회원별 `PAID` 결제액 집계에서 산정 시작일 이전 결제와 다른 회원 결제를 제외한다.
5. 현재 등급보다 바로 높은 다음 등급을 조회하고 최고 등급에서는 빈 결과를 반환한다.

기존 산출물을 구현 완료 후 갱신하고 실행한다. 이 계획 작성 단계에서는 해당 파일을 수정하지 않는다.

- `api-test-results/회원/0714 회원가입 정보 수정/회원가입_정보수정_Swagger_Postman_체크리스트.md`

체크리스트 추가 항목:

1. `API-ME-001 GET /api/v1/me` 정상 응답의 모든 확장 필드 확인
2. 등급 달성률과 DB `PAYMENT.amount` 합계 비교
3. 사용 가능 쿠폰/전체 대여/전체 완독/즐겨찾기/미읽은 알림 수와 DB 확인 쿼리 결과 비교
