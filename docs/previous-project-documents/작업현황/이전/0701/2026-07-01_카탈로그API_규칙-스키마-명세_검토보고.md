## 1. 완전하게 구현된 부분

- **API prefix/URL**: `/api/v1/books`, `/api/v1/categories`, `/api/v1/collections` — 복수형 명사, prefix 규칙 100% 준수 (`BookController.java:22`, `CategoryController.java:19`, `CollectionController.java:20`)
- **Controller는 Entity 미반환**: 전부 `~Response`/`PageResponse<T>`만 반환
- **공통 성공 응답**: `ResponseEntity.ok(ApiResponse.ok(...))` 일관 사용
- **예외 처리**: `BusinessException`+`ErrorCode`만 사용(`BOOK_NOT_FOUND`, `COMMON_NOT_FOUND`, `VALIDATION_ERROR`) — 규칙.md 6절 정확히 준수
- **DTO 네이밍**: `~Response`, `~Criteria` 규칙 100% 준수
- **Repository = JPA**: raw JDBC/`DatabaseConnectionProvider` 완전 제거, `JpaRepository`+`JpaSpecificationExecutor`+`@Query`로 전환 완료 — 규칙.md가 전제하는 JPA 기반 데이터 접근 확립
- **BookCard 공통 스키마(api-spec 2.1)**: `bookId/title/coverImageUrl/authors/publisherName/rentalType/rentalPrice/averageRating/reviewCount/favoriteYn` 필드가 `BookCardResponse`와 정확히 1:1 일치
- **User 노출 정책(구현 메모 #3)**: `BOOK.status=AVAILABLE`, `CATEGORY.status=ACTIVE`만 노출하도록 정확히 구현
- **`gradlew build`**: 컴파일/테스트/빌드 전부 성공(H2 기반)

## 2. 알맞게 구성된 부분 (대체로 맞으나 100%는 아님)

- API-BOOK-001/002/003/005, API-CATEGORY-001, API-COLLECTION-001/002 — URL·HTTP verb·요청 파라미터 매핑은 api-spec 3절 표와 정확히 일치
- 목록 필터링(카테고리/상위카테고리/컬렉션/이벤트섹션/대여유형) 정책 구현 — API-BOOK-001 정책("카드에는 표지/제목/저자/출판사/무료유료/가격/즐겨찾기 여부") 충족
- Swagger `@Tag`/`@Operation` 부착됨(다만 `@Schema`는 DTO에 없음 — 규칙 12절엔 "필요한 경우"라 필수는 아님)
- 컬렉션 미리보기(previewSize) — "대표 도서 5~6개 미리보기"라는 정책 문구를 강제 고정값이 아니라 클라이언트가 조절 가능한 파라미터로 구현. 스펙 의도와 방향은 맞으나 "5~6개"라는 구체적 숫자를 강제하진 않음

## 3. 부족한 부분

- **[P2] `API-LIBRARY-001`** (`GET /api/v1/books/{bookId}/libraries`) — 미구현. 이번 브랜치(catalog-user-api) 스코프에 아예 없음
- **[P1] `myRentalState`, `myFavoriteYn`, `favoriteYn`** — 인증이 없어 항상 `null`/`false` 고정 (`BookService.java`의 `currentMemberIdOrNull()` 자리에 해당 로직이 없음 — 회원 인증 붙기 전까지는 의도된 제한이지만 명세상 "로그인 회원 기준" 요구사항은 아직 미충족)
- **[P0] BaseEntity 미상속 및 직접 선언** — `BaseEntity` 클래스 자체가 프로젝트 전체에 아직 존재하지 않음(`common/entity` 패키지 없음, `rg "class BaseEntity"` 결과 소스 0건). 세부적으로:
  - `Book`, `Collection`은 스키마(`schema.sql`)에 `created_at`/`updated_at` 컬럼이 **모두 존재**함에도 `BaseEntity` 없이 필드를 직접 선언(`Book.java:71-75`, `Collection.java:57-61`) — 규칙 10절("createdAt/updatedAt 직접 선언 금지") **이미 위반된 상태**.
  - `Publisher/Author/BookKeyword/CollectionBook`은 `created_at` 컬럼은 있으나 `updated_at`이 없어, `BaseEntity` 적용 전 스키마에 `updated_at` 컬럼 추가가 먼저 필요.
  - `Category`만 `created_at`/`updated_at` 둘 다 없어 스키마 변경 없이는 `BaseEntity` 적용 자체가 불가.
- **[P2] Category 패키지 위치** — `book.domain.Category`로 남아있어 규칙 9절(기능별 패키지 구조) 미준수 (엔티티 무수정 방침에 따라 유지)
- **[P1] `archTest` 게이트 부재** — CLAUDE.md/규칙 문서가 요구하는 완료 조건(`archTest` 실행)을 자동 검증할 수단 자체가 프로젝트에 없음

## 4. 이상한 점 / 확인이 필요한 부분

1. **[P0] 페이징 응답 포맷이 두 기준 문서에서 서로 다름 (가장 중요)**
   - `백엔드_공통_개발_규칙.md` 3절: `content/page(0부터)/size/totalElements/totalPages/last`, 기본 `size=10`
   - `api-spec(final).md` 1.4절: `items/page(1부터)/size/totalElements/totalPages/hasNext`, 기본 `size=20`
   - 현재 `PageResponse.java`는 규칙.md의 필드 구조(`content`/0-base/`last`)를 따르면서 기본값만 api-spec 값(`size=20`)을 섞어 씀 → **두 문서 자체가 충돌하고, 구현은 어느 한쪽과도 완전히 일치하지 않는 혼합 상태**입니다.
   - 특히 `page` 0-base vs 1-base 차이는 단순 포맷이 아니라 **실제 동작 버그 리스크**입니다. 프론트가 api-spec을 보고 `page=1`을 "첫 페이지"로 요청하면, 현재 서버는 이를 "두 번째 페이지"로 해석합니다. → **어느 문서를 기준으로 통일할지 팀 확인이 꼭 필요합니다.**
2. **[P1]** `API-BOOK-001`에 명세(4.2절)에 없는 **`collectionId` 쿼리 파라미터**가 추가돼 있음 — 구현 편의상 확장한 것으로 보이나, 명세와 다르다는 점을 리뷰어가 인지해야 함
3. **[P2]** `docs/데이터베이스/ddl/schema.sql`과 실제 `src/main/resources/schema.sql`의 **컬럼명 표기 방식 자체가 다름**(예: `category_status` vs `status`). 코드는 후자를 정확히 따르고 있어 동작엔 문제없지만, 문서 간 불일치가 팀 전체 혼란 요인이 될 수 있음
4. **[P1]** `sort` 파라미터 허용값(`latest/title/popular`)이 api-spec 어디에도 명시적 enum으로 정의돼 있지 않음(스펙엔 `sort?`로만 표기) — 프론트와 실제 값 이름이 맞는지 확인 필요, 코드(`BookListCriteria.sort`)도 순수 `String`이라 검증 로직 없음
5. **[P0] `Book`/`Collection`이 `created_at`/`updated_at`을 `BaseEntity` 없이 직접 선언 — 이미 발생한 규칙 위반 사례** — 두 엔티티 모두 스키마에 두 컬럼이 이미 존재하는데도 `BaseEntity` 상속 없이 필드를 직접 선언함(`Book.java:71-75`, `Collection.java:57-61`). 3절의 다른 항목(`Category` 등)은 "아직 안 한 일"이지만, 이 항목은 규칙 10절을 어긴 코드가 **이미 병합되어 `main`에 들어간 상태**라는 점에서 시급도가 더 높음
