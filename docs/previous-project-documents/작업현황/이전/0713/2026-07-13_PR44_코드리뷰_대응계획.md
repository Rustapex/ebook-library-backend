## 3. 상수-allowlist 수동 연결 — parameterized test로 누락 방지

- **리뷰 지적**: `AdminAuditLogActionType`/`AdminAuditLogTargetType`이 실제 Java enum이 아니라 `public static final String` 상수 + 별도 `Set.of(...)`(`VALUES`)로 수동 연결돼 있어, 나중에 상수를 추가하고 `VALUES`에 반영을 빠뜨릴 위험이 있다.
- **대상 파일(안)**: `src/test/java/com/acorn/abc/statistic/domain/AdminAuditLogActionTypeTest.java`, `AdminAuditLogTargetTypeTest.java` (신규 2개 테스트 클래스)
- **변경 범위**: 테스트 코드만. 프로덕션 코드(상수 클래스 자체를 enum으로 바꾸는 등)는 이번 범위에 포함하지 않는다 — 리뷰도 "enum화 검토"는 별도 후속으로 언급했지 이번에 하라는 요구는 아니었다.
- **구현 방식(중요한 설계 판단)**: 리뷰가 원하는 건 "상수를 추가했는데 `VALUES`에 넣는 걸 깜빡했을 때 테스트가 실패하는 것"이다. `@ParameterizedTest`에 값을 수동으로 나열하면(`"MEMBER_POINT_ADJUST", "COUPON_CREATE", ...`) 새 상수를 추가해도 그 목록에 안 넣으면 테스트도 통과해버려서 리뷰가 원하는 효과가 안 난다. 그래서 **리플렉션으로 클래스에 선언된 모든 `public static final String` 필드를 순회**하면서 각 값이 `isValid()`를 통과하는지 확인하는 방식으로 구현해야, 상수 선언과 `VALUES` 등록 사이의 누락을 실제로 잡아낸다.
- **결정 필요 사항**: 리플렉션 기반 테스트 방식에 동의하는지 확인 필요(위 이유로 이 방식을 권장하지만, 프로젝트에 리플렉션 기반 테스트 전례가 있는지는 별도 확인 안 함).

## 4. Swagger 문서에 허용 actionType/targetType 목록 노출

- **리뷰 지적**: Swagger/OpenAPI 문서에 허용 가능한 `actionType`/`targetType` 값 목록이 안 드러나 있어 프론트/API 사용자가 헷갈릴 수 있다.
- **대상 파일**: `src/main/java/com/acorn/abc/admin/statistic/controller/AdminAuditLogController.java`의 `actionType`/`targetType` 파라미터
- **변경 범위**: `AdminStatisticController`의 `baseDate` 파라미터처럼 `@Parameter(description = ...)`를 추가해, 허용값을 설명 문구에 나열한다. 예:
  > `actionType`: 관리자 작업 유형 필터입니다. 생략 가능. 허용값: `MEMBER_POINT_ADJUST`, `COUPON_CREATE`, `COUPON_ISSUE`, `BOOK_CREATE`, `CHALLENGE_UPDATE`, `MEMBER_UPDATE`, `BOOK_UPDATE`, `REPORT_PROCESS`, `NOTICE_WRITE`
- **주의**: `@Pattern`처럼 정규식으로 고정하는 게 아니라 설명 문구일 뿐이라, 3절과 마찬가지로 상수가 늘어나면 이 설명 문구도 별도로 손으로 갱신해야 한다는 한계가 있다. 이 한계 자체는 이번 범위에서 해결하지 않고(예: 문구를 상수 목록에서 자동 생성하는 것은 과설계로 판단), 설명에만 반영한다.

### 체크리스트 문서 — 2곳 갱신 필요

- **§5 감사 로그 검증 표에 Swagger UI 확인 항목 추가 필요**: 4절(Swagger `@Parameter` 설명 추가)은 API 응답을 바꾸지는 않지만 Swagger UI에 노출되는 내용을 바꾸는 유일한 변경이다. 지금 체크리스트에는 이 부분을 눈으로 확인하는 항목이 없다. `GET /api/v1/admin/audit-logs` Swagger 페이지에서 `actionType`/`targetType` 파라미터 설명에 허용값 목록이 정상적으로 나오는지 확인하는 케이스 1개를 §5에 추가해야 한다.
- **"PR 반영 문구" 절의 테스트 개수 갱신 필요**: 현재 문구는 "230 tests, 0 failures"로 고정돼 있다. 2·3절 반영 후 테스트가 늘어나므로(컨트롤러 테스트는 기존 메서드에 assertion만 추가라 개수 불변, 3절 리플렉션 테스트 신규 클래스 2개 × 1개 메서드 = +2), 실제 빌드 결과에 맞춰 숫자를 다시 채워야 한다. 지금 미리 확정 숫자를 적지 않고, 구현 완료 후 실제 `./gradlew.bat build` 결과로 갱신하는 것으로 계획해둔다.

이 두 갱신은 실제 코드(2~4절) 반영이 끝난 뒤, 체크리스트 파일에 직접 반영한다(지금은 계획 문서에만 기록).

## Swagger/Postman 테스트 시점 — 지금 할지, 코드리뷰 반영 후 할지

**코드리뷰 3개 항목을 먼저 반영한 뒤 한 번에 테스트하는 것을 권장한다.**

- 2절(테스트 body 검증)과 3절(리플렉션 테스트)은 전부 **자동화 테스트 코드**만 추가하는 변경이라 Swagger/Postman으로 확인할 대상 자체가 없다 — `./gradlew.bat build` 결과가 검증의 전부다.
- 4절(Swagger 설명 추가)은 **Swagger UI에 보이는 내용 자체를 바꾼다.** 지금 Swagger/Postman 테스트를 먼저 하면, 4절 반영 후 Swagger UI 문구가 바뀐 걸 확인하려고 또 한 번 Swagger를 열어봐야 한다. 반대로 3개 항목을 먼저 반영하고 나서 테스트하면, 최종 상태(설명 문구 포함)를 한 번에 확인할 수 있어 중복 작업이 없다.
- API 응답 자체(`400`/`VALIDATION_ERROR` 등)는 이미 지난 라운드 코드에서 결정된 것이고 이번 3개 항목으로 안 바뀌므로, "지금 먼저 테스트해도 되는 부분"과 "나중에 반영 후 테스트해야 더 효율적인 부분"이 섞여 있지만, 어차피 API 응답 관련 항목(§5 감사 로그 검증)은 아직 한 번도 Swagger/Postman으로 확인 안 된 상태이므로 코드 변경(4절)까지 다 끝난 뒤 §5를 포함해서 한 번에 진행하는 게 가장 효율적이다.
