## 2. [MEDIUM] memberId 전달 검증 테스트 보강

- **리뷰 지적**: `UserStatisticControllerTest`의 "본인 memberId로 조회" 테스트가 이름만 그렇고 실제로는 `anyLong()`으로 느슨하게 스텁해서 어떤 memberId가 전달됐는지 검증하지 않는다. `UserStatisticServiceTest`도 repository 호출 인자에 memberId 검증이 없다.
- **왜 중요한가**: 회원 통계는 "본인 데이터만 조회"가 핵심 계약이라, 인증 principal의 memberId가 그대로 전달되는지를 테스트가 직접 보장해야 회귀(예: 실수로 다른 값을 하드코딩하거나 파라미터 순서를 바꾸는 버그)를 잡을 수 있다.
- **대상 파일**:
  - `UserStatisticControllerTest.java` — `getMyStatistics_정상_요청은_200을_반환하고_본인_memberId로_조회한다()`에 `verify(userStatisticService).getStatistics(eq(1L), eq("TOTAL"), isNull())` 추가(현재 `CustomUserDetails(1L, "USER")`를 principal로 쓰고 있으므로 `1L` 고정 검증 가능).
  - `UserStatisticServiceTest.java` — 최소 1개 이상의 repository 호출에 `eq(MEMBER_ID)` 검증 추가(예: `verify(bookRentalRepository).countByMemberAndPeriod(eq(MEMBER_ID), any(), any())`).
- **변경 범위**: 테스트 코드만. 프로덕션 코드 변경 없음.
- **결정 필요 사항**: 없음(리뷰 제안 그대로 적용 가능, 별도 설계 선택지 없음).

## 3. [LOW/WATCH] 기간·추이 계산 로직 중복

- **리뷰 지적**: `UserStatisticService`의 `resolvePeriodRange`/`resolveTrendBuckets`가 `AdminStatisticService`와 거의 같은 규칙을 별도로 들고 있다. 향후 기간 규칙이 바뀌면 관리자/회원 통계가 서로 달라질 위험이 있다.
- **현황**: 구현 당시(`2026-07-13_회원용독서통계_구현계획.md` §5.3)에 이미 이 중복을 인지했고, "관리자 쪽 로직이 아직 안정화 초기 단계라 무리하게 공통화하면 양쪽 다 건드리는 변경이 잦아질 수 있다"는 이유로 의도적으로 복붙을 선택했다.
- **결정 필요 사항(안 A/B)**:
  - **안 A — 공통 컴포넌트로 추출**: `StatisticPeriodResolver`/`TrendBucketCalculator` 같은 공통 클래스를 새로 만들고, `AdminStatisticService`와 `UserStatisticService` 양쪽 다 이걸 쓰도록 리팩터링한다.
    - 장점: 기간 규칙이 바뀔 때 한 곳만 고치면 됨. 리뷰가 지적한 위험 완전 해소.
    - 단점: 이미 merge된 `AdminStatisticService`(PR41/42/44에서 여러 차례 리뷰받은 안정적인 코드)를 다시 건드려야 함. 리팩터링 자체의 회귀 위험이 있고, 관련 테스트(`AdminStatisticServiceTest`)도 영향받을 수 있음.
  - **안 B(권장) — 현행 유지, 문서화만 보강**: 코드는 그대로 두고, 두 서비스 클래스 상단 주석에 "이 로직은 X 서비스와 동일한 규칙을 따로 유지 중이며, 기간 규칙 변경 시 두 곳을 함께 수정해야 한다"는 상호 참조 주석을 추가한다.
    - 장점: 이미 검증된 코드를 안 건드림. 리스크 최소화.
    - 단점: 실제로 규칙이 바뀔 때 한쪽을 빠뜨릴 위험은 여전히 남음(문서화로 완화만 함).
  - **권장 근거**: 리뷰도 "LOW/WATCH"(merge blocker 아님, 관찰 대상)로만 분류했고, 구현 당시 판단(무리한 공통화 지양)이 여전히 유효하다고 본다. **안 B를 권장**하되, 최종 확정은 사용자 몫이다.

## 4. [LOW] 실시간 집계 성능/인덱스 후속 검토

- **리뷰 지적**: 회원 통계 API가 한 요청에서 여러 aggregate query를 실행한다. 현재 규모에서는 문제 아니지만, 데이터가 늘면 `memberId + 기간` 집계 경로에 대한 composite index를 MySQL `EXPLAIN` 기준으로 검토하는 게 좋다.
- **현황**: `src/main/resources/관리자통계_성능인덱스.sql`(PR42에서 작성)가 `book_rental.created_at`, `reading_progress.completed_at`, `review(status, created_at)`에 대한 인덱스를 이미 담고 있으나, 아직 로컬/공유 DB 어디에도 적용 안 됨(`docs/작업현황/설계문서/2026-07-13_관리자통계_성능인덱스_적용현황.md` 확인, 두 행 모두 `[ ] 미적용`).
- **분석(`schema.sql` 직접 확인 완료)**:
  - `book_rental.member_id` — `fk_book_rental_member` FK 제약이 있어 InnoDB가 자동으로 인덱스를 만든다(610행). 이미 인덱스 있음.
  - `review.member_id`, `favorite_book.member_id` — 둘 다 `UNIQUE (member_id, book_id)` 복합 제약이 있다(332행, 320행). 왼쪽 접두(leftmost prefix) 규칙상 `member_id` 단독 조회도 이 인덱스를 탄다. 이미 인덱스 있음.
  - `reading_progress` — `rental_id`에 `UNIQUE` 제약이 있어(296행) `book_rental` 조인 경로 자체는 인덱스를 탄다. `book_rental.member_id`도 위에서 확인했듯 인덱스 있음.
  - 결론: **`memberId` 기준 조회 경로 자체는 이미 전부 인덱스가 있다.** 신규로 걱정해야 할 부분은 아니다.
  - 다만 기간 필터 컬럼 중 `reading_progress.last_read_at`(이번 PR45의 `sumReadPageCountByMemberAndPeriod`가 사용)은 기존 `관리자통계_성능인덱스.sql`(PR42)이 커버하는 목록(`book_rental.created_at`, `reading_progress.completed_at`, `review(status, created_at)`)에 없다. `completed_at`은 있는데 `last_read_at`은 빠져 있다.
- **대상 파일(안)**: 기존 `관리자통계_성능인덱스.sql`에 `reading_progress.last_read_at` 인덱스 한 줄만 추가.
- **결정 필요 사항**: `memberId` 조회 경로는 이미 인덱스가 있다는 게 확인됐으므로 이 항목 자체의 시급성은 낮다. `last_read_at` 인덱스를 지금 추가할지, 아니면 리뷰가 말한 대로 "사용량이 늘면" 시점까지 미룰지만 결정하면 된다.
