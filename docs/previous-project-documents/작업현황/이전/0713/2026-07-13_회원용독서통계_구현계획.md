## 1. 배경

PR #44는 사용자가 직접 merge할 예정이다(이 문서는 그 이후를 대비한 계획이며, merge 작업 자체는 이 문서의 범위가 아니다). PR #44 merge로 "관리자 API(대시보드/통계/감사로그)" 3개 endpoint는 spec 기준 100% 구현 완료 상태가 된다.

사용자의 담당 도메인은 "관리자 API(대시보드/통계/감사로그 등) + 회원 통계"이며, 담당 도메인 전체를 100% 구현하는 것이 목표다. 남은 마지막 조각이 회원용 독서 통계(`API-STAT-001`, `GET /api/v1/me/statistics`, 화면 `U-026`)다. 이 문서는 그 구현계획이다.

**PR #44 재검토 코멘트 반영**: 위 코멘트에서 PR #44는 "COMMENT / merge 가능"(blocker 없음)으로 재확인됐고, 별도로 "회원 통계 후속 작업 진행 방향" 절에서 이 문서와 동일한 방향(별도 PR로 분리, 실시간 집계 검토, `memberId`는 인증 사용자 기준, 서비스/repository 테스트 분리, Swagger 수동 검증)을 리뷰어도 독립적으로 권장했다. 이 문서의 기존 설계 방향(2절 별도 브랜치, 4.1절 실시간 집계 권장, 5.4절 인증 기반 memberId)과 일치하는 외부 확인으로 반영했다. 리뷰 코멘트 중 PR #44(감사 로그) 자체에 대한 비차단 후속 권장 2건(`@Schema(allowableValues=...)` 보강, action/target vocabulary enum·registry화 검토)은 회원 통계와 무관한 별개 사안이라 이 문서에는 반영하지 않는다.

이 문서는 계획 문서다. 실제 소스/스키마 파일은 이 문서 작성 단계에서 건드리지 않는다.

## 3. API 요구사항 정리

- **API**: `API-STAT-001`, `GET /api/v1/me/statistics`, 회원 인증 필요(본인 데이터만 조회, 다른 회원 통계 조회 불가)
- **Query**: `periodType`(필수, `WEEKLY`/`MONTHLY`/`YEARLY`/`TOTAL`), `baseDate`(선택)
- **Response 지표**(화면 U-026 + api-spec 320행 기준): 대여 수, 완독 수, 읽은 페이지, 리뷰 수, 즐겨찾기 수, 탄소 절약량(완독 수×2kg), 나무 보호량(완독 수×0.04그루), 기간별 독서량 그래프
- **주의**: `ageBand` 파라미터는 없다(본인 조회이므로 나이대 필터 불필요) — 관리자 API와 파라미터 구성이 다르다.
- **관련 테이블**: `USER_READING_STATISTIC`(화면설계 문서 언급) — 다만 9절 조사에서 이미 확인했듯 이 테이블은 비어 있고 채우는 배치도 없다. 4.1절에서 정리했듯 이 테이블은 쓰지 않고 실시간 집계로 확정했다.

## 4. 설계 선택지 정리 (실시간 집계는 확정, 나머지는 기본값 적용)

### 4.1 실시간 집계 vs `user_reading_statistic` 배치 적재 — **확정(재확인 불필요)**

**결론: 안 A(실시간 집계)로 확정한다.** 이번 문서에서 새로 정하는 게 아니라, 이미 세 단계에 걸쳐 같은 방향으로 확정된 정책을 회원 통계에 그대로 적용하는 것이다.

- `docs/작업현황/2026-07-12_관리자-통계-확장_구현계획.md` §3.6: "`admin_statistic` 테이블 사용 여부 — 이번 범위에서는 직접 저장/재도입을 보류한다"를 이미 확정 사항으로 명시(표에 "이번 구현은 추가 결정 대기 없이 아래 기준으로 진행한다"라고 못박음).
- 같은 문서 §3.7: 선택지 A/B/C를 비교한 뒤 **"선택지 C(하이브리드, 실시간 집계 중심)를 기본 권장"**으로 확정했고, 그 근거로 "PR #37에서 배치 경합 때문에 실시간 집계로 전환한 결정과 충돌하지 않는다"는 더 이전의 프로젝트 전역 결정(PR #37)까지 인용하고 있다. 즉 이 정책은 관리자 통계 한정이 아니라 PR #37부터 이어지는 프로젝트 공통 방향이다.
- `docs/작업현황/2026-07-12_관리자API후속작업_구현계획.md` §9도 "관리자 통계(PR41/PR42)에서 이미 검증된 '실시간 집계' 패턴 ... 관리자 쪽 `AdminStatistic` 테이블도 있었는데 실사용은 실시간 집계로 대체했던 전례가 있다(PR41/PR42 확정 정책)"고 동일하게 정리해뒀다.
- `user_reading_statistic` 테이블이 이미 존재하는 것은 `admin_statistic`과 똑같은 상황(테이블은 있지만 실사용은 실시간 집계로 대체)이라, 다른 결론을 낼 근거가 없다.

**따라서 이 항목은 더 이상 "확정 필요 사항"이 아니다.** `user_reading_statistic` 테이블/스케줄러는 쓰지 않고, `BookRentalRepository`/`ReadingProgressRepository`/`ReviewRepository`/`FavoriteBookRepository`를 회원 ID + 기간 조건으로 직접 집계하는 방식으로 바로 구현을 진행한다.

### 4.2 "읽은 페이지" 지표 계산 방식 — **확정: B1(`last_read_at` 기간 필터)**

**결론: `last_read_at`이 조회 기간 안에 있는 `reading_progress` 행들의 `read_page_count`를 합산한다.** 다른 지표(대여 수/완독 수/리뷰 수)와 마찬가지로 `periodType`에 따라 값이 달라지는 기간 지표로 확정한다. 이전 초안의 "안 A(현재 상태, 기간 무관)"는 기각한다.

- **기각 이유**: `docs/기획문서들/멘토링전기획문서/ERD-정책-확정-필요사항 수정후.md` §3.6(284-329행)의 회의 확정 문구 — `[회의] 사용자 통계 - 주간/월간/연간/전체 별) - 대여 수, 완독 수, 읽은 페이지 수` — 읽은 페이지 수도 명시적으로 기간별 지표로 요구돼 있어, "기간 무관" 안 A는 이 회의 결정과 정면으로 충돌한다.
- **B1(채택) 구현 규모가 작은 이유**: `ViewerService.moveToPage()`(페이지 조회/진행상황 저장 시 호출)가 페이지를 넘길 때마다 `last_read_at`을 갱신하는 것을 코드로 확인했다. 이 컬럼은 이미 `findRecentByMemberId()`에서 정렬 기준으로 쓰는 기존 컬럼이라, 신규 스키마 변경 없이 대여수/리뷰수와 동일한 쿼리 패턴(`WHERE last_read_at BETWEEN :from AND :to`)만 추가하면 된다. "진짜 정확한" 페이지 조회 이벤트 로그 방식(신규 테이블 + `ViewerService`에 기록 로직 추가)은 이번 범위에서 채택하지 않는다 — B1로도 회의에서 요구한 "기간별로 값이 달라진다"는 요구사항 자체는 충족되기 때문이다.
- **알려진 한계(구현 규모와 무관, 데이터 모델 자체의 한계)**: `read_page_count`는 "지금까지 도달한 최대 페이지"(`Math.max(기존값, pageNo)` 누적값)이지 "그 기간에 읽은 페이지 수"가 아니다. 예: 6월에 940페이지까지 읽고 7월에 1페이지만 더 넘기면, 7월 통계에 950페이지 전부가 잡힌다. 정확한 값을 내려면 페이지 조회 이벤트 로그(신규 테이블)가 필요한데 이번 범위에서는 도입하지 않는다 — 이 한계는 구현 시 코드 주석/Swagger 설명에 명시하고, 아래 4.2.1의 ERD 정책 문서 반영예정에도 남긴다.

### 4.2.1 ERD 정책 문서 반영예정 계획 (문서 계획만, 지금 수정 안 함)

`docs/기획문서들/멘토링전기획문서/ERD-정책-확정-필요사항 수정후.md`는 기획팀이 관리하는 문서라 이 작업 담당자가 직접 수정하지 않는다 — 8절(프론트 설계문서 처리)과 같은 원칙: 담당자가 아닌 문서는 직접 고치지 않고 반영예정 문서만 남기고, 실제 반영은 문서 담당자에게 넘긴다.

- **작성 위치(착수 시점에 실제 생성)**: `docs/작업현황/설계문서/2026-07-13_ERD정책문서_읽은페이지지표_반영예정.md`(신규)
- **담을 내용(계획)**:
  - 원본 위치: ERD 정책 문서 §3.6(284-329행), `[회의] 사용자 통계 - 주간/월간/연간/전체 별 - 읽은 페이지 수` 문구
  - 반영 제안: "읽은 페이지 수"의 계산 기준을 "해당 기간 내 `last_read_at`을 가진 진행상황의 `read_page_count`(누적 도달 페이지) 합"으로 구체화하고, "정확한 순수 독서량이 아니라 근사치"라는 한계를 각주로 남기도록 제안.
  - 반영 이유: 현재 정책 문서에는 "읽은 페이지 수"라고만 적혀 있고 계산 기준이 없어서, 나중에 다른 개발자가 다시 볼 때 B1(근사치) 방식이라는 걸 모르고 "정확한 값"으로 오해할 수 있다.
  - 처리 방식: 위 신규 문서에 기록만 해두고, 실제 ERD 정책 문서 수정은 기획팀/문서 담당자에게 넘긴다. 이번 문서(회원용독서통계_구현계획.md)에는 이 계획만 적고, 실제 파일 생성은 8절 작업순서 단계에서 진행한다.

### 4.3 그래프(기간별 독서량) — **형식은 확정된 패턴 재사용, 기준 지표는 기본값 적용**

- **형식(확정, 재확인 불필요)**: 관리자 통계 확장 §3.4에서 이미 `{label, periodStartDate, periodEndDate, count}` 형태와 `WEEKLY=7일/MONTHLY=해당월 일별/YEARLY=12개월/TOTAL=최근 12개월` bucket 기준을 확정해뒀다. 회원 통계도 같은 형식을 그대로 쓴다.
- **기준 지표(기본값 적용)**: "독서량"의 기준을 관리자 통계의 `completedReadTrend`와 동일하게 **완독 수 기준**으로 채택한다. 이 프로젝트에 이미 존재하는 유일한 "독서량 추이" 개념이 `completedReadTrend`이므로, 새 지표를 만들지 않고 그대로 재사용하는 것이 가장 근거가 명확하다. 이견 있으면 구현 전에 알려달라.

### 4.4 즐겨찾기 수 — **확정(사용자 결정)**

**결론: 기간 필터 개념 없음. 현재 즐겨찾기 도서 개수만 반환한다.** `periodType`이 `WEEKLY`/`MONTHLY`/`YEARLY`/`TOTAL` 무엇이든 이 필드 값은 항상 동일하다.

## 5. 구현 계획

### 5.1 DTO

- `UserReadingStatisticResponse`(신규, `~Response` 네이밍 규칙): `periodType`, `periodStartDate`, `periodEndDate`, `rentalCount`, `readBookCount`, `readPageCount`, `reviewCount`, `favoriteCount`, `carbonSavedKg`, `treeSavedCount`, `readingTrend`(4.3절 확정대로 완독 수 기준 trend 포함) — `AdminStatisticResponse`와 필드 성격은 겹치지만 나이대/전체회원 KPI 없이 본인 값만 담는다.

### 5.2 Repository 신규 쿼리 (회원 단위 + 기간 조건)

- `BookRentalRepository`: 회원 ID + 기간으로 대여 수를 세는 메서드 신규(기존 `countByStatisticConditions`는 나이대 조건 기반이라 회원 단위로는 못 씀).
- `ReadingProgressRepository`: 회원 ID + 기간으로 완독 수를 세는 메서드, 4.2절 확정(B1)대로 `last_read_at`이 기간 안에 있는 행의 `read_page_count`를 합산하는 메서드.
- `ReviewRepository`: 회원 ID + 기간으로 리뷰 수를 세는 메서드.
- `FavoriteBookRepository`: 4.4절 확정대로 회원 ID 기준 "현재 즐겨찾기 수"(기간 조건 없음)를 세는 메서드.

### 5.3 Service

- `UserStatisticService`(가칭) 신설. `AdminStatisticService.resolvePeriodRange()`와 사실상 동일한 기간 계산 로직이 필요 — 코드 중복을 피하려면 공통 유틸(`PeriodRangeCalculator` 등)로 추출하는 것도 검토 대상이나, 과설계 방지 차원에서 최초 구현은 복붙 후 필요 시 리팩터링하는 것을 권장(관리자 쪽 로직도 아직 안정화 초기 단계라 무리하게 공통화하면 양쪽 다 건드리는 변경이 잦아질 수 있음).
- `PeriodType`은 `TOTAL`/`WEEKLY`/`MONTHLY`/`YEARLY` 4종(ageBand 없음).

### 5.4 Controller

- `UserStatisticController`(가칭), `GET /api/v1/me/statistics`. `MeController` 패턴을 따라 `@AuthenticationPrincipal CustomUserDetails userDetails`로 `memberId`를 얻는다. PR #44 재검토 코멘트도 "`memberId`는 인증 사용자 기준으로 받는 구조가 안전하다"고 명시해, 이 설계가 리뷰 기준과 일치함을 확인했다.
- `periodType`은 관리자 API와 동일하게 `@Pattern(regexp = "WEEKLY|MONTHLY|YEARLY|TOTAL")`로 컨트롤러 단에서 fail-fast(PR42/PR44에서 확립된 정책과 동일).

### 5.5 테스트

- Repository 테스트(baseline-delta 패턴, 실제 공유 MySQL 기준) — 신규 쿼리마다. PR #44 재검토 코멘트도 "서비스 단위 테스트와 repository 집계 테스트를 분리"하도록 권장해 이 구성과 일치한다.
- Service 테스트 — 기간 계산, 잘못된 periodType fail-fast.
- Controller 테스트 — **인증 누락 시 401**(또는 프로젝트의 기존 인증 실패 처리 방식 확인 필요, PR #44 재검토 코멘트에서 명시적으로 언급된 케이스), 정상 200, 잘못된 periodType 400.

## 6. Swagger/Postman 검증 계획

- 경로(제안): `api-test-results/회원 통계/` 신규 폴더(관리자 API 폴더와 구분).
- 케이스: `TOTAL`/`WEEKLY`/`MONTHLY`/`YEARLY` 각 조회, 잘못된 periodType 400, **인증 누락(토큰 없이 호출) 케이스**(PR #44 재검토 코멘트에서 명시적으로 언급 — 기존 §5.5 초안에는 있었으나 이 절의 수동 검증 케이스 목록에는 빠져 있었음, 이번에 보강), 다른 회원 데이터가 안 섞이는지(2명 이상 회원으로 교차 확인), 탄소/나무 계산값 검증.
- 착수 시점에 별도 체크리스트/SQL 문서로 구체화한다(이번 문서 범위 아님).

## 7. 위험/가정

- `review`/`favorite` 도메인은 이번 세션에서 깊게 조사하지 않았다 — 5.2절 신규 쿼리 설계 전에 `Review`/`FavoriteBook` 엔티티의 정확한 컬럼(특히 생성일시 컬럼명)을 다시 확인해야 한다.
- 다른 회원의 통계가 절대 섞이지 않아야 한다는 요구사항(보안)은 모든 신규 쿼리에 회원 ID 조건이 반드시 들어가야 한다는 뜻이다 — 관리자 통계 코드를 복붙할 때 이 조건을 빠뜨리지 않도록 특히 주의해야 한다(리뷰에서 지적될 가능성이 높은 지점).
- 4.2절에서 채택한 "읽은 페이지" B1 방식은 근사치다(누적 최대 도달 페이지 기준이라 기간 경계에서 과다 집계될 수 있음). 코드 주석/Swagger 설명에 이 한계를 명시해야 하고, 정확한 값이 필요해지면 별도 이벤트 로그 테이블 도입을 후속 검토해야 한다(4.2절 참고).
