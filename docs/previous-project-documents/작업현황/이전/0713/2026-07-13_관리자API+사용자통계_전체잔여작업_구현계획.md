## 1. 배경 — 현재 도메인 상태

담당 도메인은 "관리자 API(대시보드/통계/감사로그 등) + 사용자 통계"다. API 명세 기준 핵심 endpoint 4개(API-ADMIN-DASHBOARD-001, API-ADMIN-STAT-001, API-ADMIN-AUDIT-001, API-STAT-001)는 전부 구현 완료됐다.

- API-ADMIN-DASHBOARD-001/STAT-001/AUDIT-001: PR41/PR42/PR44로 구현 완료, `main`에 merge됨.
- API-STAT-001(회원 통계): PR45로 구현 완료, 현재 `main`으로 가는 PR #45가 OPEN 상태(리뷰 COMMENT/merge 가능 판정, 별도 대응계획 §3.1 참고).

**따라서 "endpoint가 존재하고 spec대로 동작하는가" 기준으로는 이미 100%다.** 남은 작업은 전부 (a) 코드리뷰에서 나온 견고성/품질 보강, (b) 이전에 미루거나 잘못 범위 제외했던 항목, (c) 코드가 아니라 문서/운영 작업이다. 이 문서는 이 세 가지를 전부 모아 정리한다.

### 3.2 감사 로그 `@Schema(allowableValues=...)` 보강

- **이전 판단 정정**: 회원용독서통계 계획 문서 작성 당시 "회원 통계와 무관한 별개 사안"이라며 반영하지 않았으나, 사용자가 "범위 밖은 없다"고 명시적으로 정정함. 이번 문서에 정식으로 포함한다.
- **리뷰 지적**(PR44 재검토): `actionType`/`targetType`의 허용값이 현재는 `@Parameter.description`의 설명 문장으로만 들어가 있어 OpenAPI schema 관점에서는 여전히 일반 문자열이다. generated client나 계약 도구까지 고려하면 `@Schema(allowableValues = {...})`를 붙이는 게 더 좋다.
- **대상 파일**: `src/main/java/com/acorn/abc/admin/statistic/controller/AdminAuditLogController.java`의 `actionType`/`targetType` 파라미터.
- **변경 범위**: `@Parameter` 옆에 `@Schema(allowableValues = {"MEMBER_POINT_ADJUST", "COUPON_CREATE", ...})`를 추가. 순수 Swagger/OpenAPI 문서화용 애너테이션이라 런타임 검증 로직(안 B, 서비스단 상수 대조)에는 영향 없음.
- **결정 필요 사항**: 없음. 값 목록은 `AdminAuditLogActionType`/`TargetType`의 상수를 그대로 나열하면 되므로 설계 선택지가 갈리지 않는다. 다만 §3.3에서 "값 목록을 한 곳에서 가져오는 방식"이 정해지면 이 애너테이션도 그 방식을 따라야 한다(중복 하드코딩 방지) — 그래서 3.3을 먼저 결정하고 이 항목을 진행하는 순서를 권장한다.

### 3.3 감사 로그 action/target vocabulary — enum 전환 **확정(안 A로 진행)**

- **이전 판단 정정**: 위와 동일하게, 이전에 "범위 밖"으로 뺐던 걸 정식 포함한다.
- **리뷰 지적**(PR44 재검토): action/target vocabulary가 현재 writer 호출부, 서비스 검증 allowlist, Swagger 설명 사이에 수동 동기화 지점이 여러 곳(3곳)에 있다. 리플렉션 테스트로 실수 가능성은 낮아졌지만, 값이 계속 늘어날 예정이면 enum 또는 중앙 registry 구조를 검토하는 게 좋다.
- **현황 확인**(`rg` 기준): `AdminAuditLogActionType`/`TargetType`을 직접 참조하는 곳은 `AdminAuditLogService`(검증) 외에 프로덕션 코드 4곳(`BookApprovalService`, `CouponService`, `PointService`, `ChallengeService`)과 그 테스트 4곳, 총 8개 파일이다.
- **결론(확정)**: **안 A(실제 Java enum으로 전환)로 진행한다.** `AdminAuditLogActionType`/`TargetType`을 `enum`으로 바꾸고, `AdminAuditLogWriter.record()`의 파라미터 타입도 `String` → enum으로 바꾼다. DB 컬럼(`action_type`/`target_type`)은 계속 `VARCHAR`이므로 저장 시 `.name()`으로 변환하고, 기존 상수 이름을 enum 상수 이름으로 그대로 재사용해 기존 저장 데이터와 호환한다.
- **확정 근거(사용자 확인)**:
  - 이 리팩터링이 건드리는 4개 서비스(`BookApprovalService`=도서/카테고리/컬렉션, `CouponService`/`PointService`/`ChallengeService`=챌린지/출석/포인트/쿠폰)는 전부 이 작업 담당자 소관 도메인이라, 다른 팀원 코드와 겹치지 않는다.
  - `docs/작업현황/2026-07-13_front-back-api-connection_검토보고.md`(§3 해당 도메인 섹션) 대조 결과, `GET /api/v1/admin/audit-logs`/`POST·PUT /api/v1/admin/coupons·challenges`/`POST /api/v1/admin/members/{id}/points`는 이미 프론트와 연결돼 있지만, 이 리팩터링은 각 API의 요청/응답 바디를 바꾸지 않는다(감사 로그 기록은 내부 부수효과, `AdminAuditLogSummaryResponse.actionType`/`targetType`도 이미 `String` 필드라 JSON 응답은 변화 없음). `BookApprovalService`가 쓰는 ISBN 임시등록 API는 오히려 §5에서 "아직 Front 연결 안 됨"으로 확인돼 노출도가 더 낮다.
  - 현재 다른 팀원이 이 4개 서비스 파일을 동시에 건드리고 있지 않음을 확인함(사용자 확인) — merge conflict 위험 없음.
- **위험성(사용자 확인 완료, 그래도 진행)**:
  - **테스트 재검증 범위 확대**: 프로덕션 4개 + 테스트 4개, 총 8개 파일을 고쳐야 해서 회귀 테스트 범위가 넓어진다. 리팩터링 후 `./gradlew.bat build` 전체 재실행으로 검증한다.
  - **조회 API의 `valueOf()` 예외 처리 누락 위험**: `GET /admin/audit-logs`의 `actionType`/`targetType` 쿼리 파라미터를 enum으로 변환할 때 `ActionType.valueOf(input)`이 잘못된 값에 대해 `IllegalArgumentException`(unchecked)을 던진다. 이걸 `catch`해서 `BusinessException(ErrorCode.VALIDATION_ERROR)`로 변환하지 않으면 400 대신 500이 나가는 회귀가 생긴다 — 구현 시 반드시 처리.
  - **enum 상수 이름 불일치 위험**: enum 상수 이름이 기존에 DB에 저장된 문자열 값과 정확히 일치해야 한다(대소문자/언더스코어 포함). 기존 상수 이름(`MEMBER_POINT_ADJUST` 등)을 그대로 재사용하면 문제 없음.
  - 위 세 가지 외에 DB 스키마 변경이나 API 계약 변경으로 인한 위험은 없음을 확인함(이번 대화에서 직접 코드/문서 대조로 검증 완료).

  - 즉 회원 상태 변경(일반), 도서 수정(일반 PUT), 신고 처리, 공지 작성, 컬렉션 관리자 API 등은 **현재 `main` 기준으로도 여전히 구현되지 않았다.** 이전 결론(프론트 문서 기반)과 결과가 동일하다 — stale 정보가 아니라 지금 코드로 다시 확인해도 같은 결론이다.
- **결론(재확정)**: 이 항목은 "관리자 API(대시보드/통계/감사로그)" 도메인 자체의 작업이 아니라 회원/도서/신고/공지 등 **다른 도메인**의 write API가 먼저 구현돼야 하는 항목이라, 이번 담당 범위에서 여전히 착수 불가다. Scope-out 유지(현재 코드 기준으로 재확인됨).
