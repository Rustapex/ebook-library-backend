## 3. 확정 정책

### 3.1 기간 계산

- `TOTAL`: 전체 기간. `baseDate`가 있어도 집계 기간에는 영향을 주지 않는다.
- `WEEKLY`: `baseDate`가 속한 ISO 주간, 월요일 00:00:00 이상부터 다음 월요일 00:00:00 미만까지.
- `MONTHLY`: `baseDate`가 속한 월의 1일 00:00:00 이상부터 다음 달 1일 00:00:00 미만까지.
- `YEARLY`: `baseDate`가 속한 연도의 1월 1일 00:00:00 이상부터 다음 해 1월 1일 00:00:00 미만까지.
- `baseDate`가 없으면 `LocalDate.now()`를 기본값으로 쓴다. `TOTAL` 응답의 `periodEndDate`도 요청 시점의 오늘 날짜로 둔다.
- 기간 조건은 `start <= timestamp < endExclusive` 방식으로 통일한다.

### 3.2 나이대 계산

- `ageBand=ALL` 또는 미지정이면 나이대 필터를 적용하지 않는다.
- `10S`, `20S`, `30S`, `40S`, `50_PLUS`는 `member.birthDate` 기준 만 나이로 계산한다.
- 기준일은 `baseDate`가 있으면 `baseDate`, 없으면 `LocalDate.now()`다. `TOTAL`도 ageBand가 지정되면 같은 기준일로 만 나이를 계산한다.
- 생일이 아직 지나지 않았으면 1살을 빼는 국제 통용 만 나이 기준을 적용한다.

### 3.3 집계 기준 컬럼

| 지표 | 기준 |
|---|---|
| 전체 회원 수 | 기간 조건 없이 현재 `member` 전체 수. ageBand가 있으면 해당 나이대 회원 수 |
| 제재 회원 수 | 현재 `member.status = SANCTIONED`. ageBand가 있으면 해당 나이대 회원만 |
| 이용 가능 도서 수 | 현재 `book.status = AVAILABLE`. 기간/나이대와 무관 |
| 전체 대여 수 | `book_rental.created_at`이 기간에 포함되는 건수 |
| 무료/유료 대여 수 | `book_rental.created_at` 기간 + `book.rental_type` 기준 |
| 완독 수 | `reading_progress.completed_yn = true`이고 `completed_at`이 기간에 포함되는 건수 |
| 결제 합계 | `payment.payment_status = PAID`이고 `paid_at`이 기간에 포함되는 `amount` 합계 |
| 리뷰 수 | `review.status = ACTIVE`이고 `created_at`이 기간에 포함되는 건수 |
| 신고 수 | `book_report.created_at` + `review_report.created_at` 기간 포함 건수 합계 |

나이대 필터가 필요한 대여/완독/결제/리뷰/신고 지표는 각 row의 회원과 `member.birth_date`를 조인해서 계산한다.

### 3.4 추이 응답

추이 응답은 DTO 필드를 추가한다.

권장 구조:

```text
rentalTrend: [{ label, periodStartDate, periodEndDate, count }]
paymentTrend: [{ label, periodStartDate, periodEndDate, amount }]
completedReadTrend: [{ label, periodStartDate, periodEndDate, count }]
```

bucket 기준:

- `WEEKLY`: 7개 일별 bucket
- `MONTHLY`: 해당 월의 일별 bucket
- `YEARLY`: 12개 월별 bucket
- `TOTAL`: 최근 12개월 월별 bucket

추이도 `ageBand` 필터를 동일하게 적용한다.

### 3.5 탄소/나무 계산값

- 탄소 절약량 = 완독 수 x 2kg
- 나무 보호량 = 완독 수 x 0.04그루
- DB에 저장하지 않고 응답 시 계산한다.
- 기준 완독 수는 현재 응답의 `totalReadBookCount`와 동일한 기간/나이대 조건을 적용한 값이다.
- 응답 필드명은 구현 시 DTO에 `carbonSavedKg`, `treeSavedCount`로 추가한다.

### 3.7 그래프/스케줄러 선택지와 영향도

#### 선택지 A - 전부 실시간 집계

내용:

- API 요청 때마다 원본 테이블에서 KPI와 추이 bucket을 계산한다.
- `admin_statistic` 저장/스케줄러를 사용하지 않는다.

장점:

- 구현이 가장 단순하고 기존 PR #37의 “배치 폐기, 실시간 집계 전환” 결정과 일관된다.
- 스케줄러, 동시 실행, upsert 경합, 스냅샷 원복 문제가 없다.
- Swagger/Postman 테스트에서 SQL 기대값과 응답값을 바로 비교하기 쉽다.

단점/영향:

- 막대그래프 요청 때 bucket별 count/sum 쿼리가 늘어난다.
- 회원 수, 제재 회원 수, 이용 가능 도서 수 같은 현재 상태 지표는 과거 시점 값을 복원하지 못한다.
- 데이터가 늘면 관리자 통계 API 응답이 느려질 수 있다.

적합한 경우:

- 프로젝트 규모가 작고 관리자 통계 호출이 많지 않은 경우.
- 그래프가 대여/결제/완독처럼 원본 이벤트 시간 컬럼으로 재계산 가능한 지표 중심인 경우.

#### 선택지 B - 스케줄러 스냅샷 중심

내용:

- `@Scheduled` 작업이 주기적으로 통계를 계산해 저장하고, API는 저장된 스냅샷을 조회한다.
- 기간/나이대별 KPI뿐 아니라 그래프용 bucket도 저장 대상으로 본다.

장점:

- 프론트 막대그래프 응답이 빠르고 안정적이다.
- 과거 시점의 상태 지표를 보존할 수 있다.
- 운영 데이터가 많아져도 API 요청 부하가 낮다.

단점/영향:

- 스케줄러, 중복 실행 방지, upsert, 재집계, 실패 재시도 정책이 필요하다.
- 다중 인스턴스 환경에서는 같은 기간 row 생성 경합을 다시 다뤄야 한다.
- 기존 `admin_statistic` 테이블은 KPI 스냅샷에는 맞지만 그래프 bucket 저장에는 부족하다. 일별/월별 bucket 저장이 필요하면 `admin_statistic_trend` 같은 별도 테이블 또는 스키마 변경이 필요하다.
- 테스트도 “스케줄러 실행 전/후”와 “저장된 스냅샷 조회”까지 포함돼 커진다.

적합한 경우:

- 프론트에서 과거 시점 상태값까지 정확한 막대그래프를 요구하는 경우.
- 운영 데이터가 많고 관리자 통계 조회 성능을 보장해야 하는 경우.

#### 선택지 C - 하이브리드

내용:

- 이번 PR에서는 KPI와 대여/결제/완독 추이를 원본 이벤트 테이블 기준 실시간 계산으로 구현한다.
- 과거 상태 복원이 필요한 지표 또는 성능 문제가 확인되는 지표만 후속으로 스케줄러 스냅샷을 도입한다.
- 문서에는 “현재 그래프는 이벤트 기준 실시간 추이이며, 스냅샷 기반 과거 상태 그래프는 후속 확장”이라고 명시한다.

장점:

- 이번 범위의 구현량을 통제하면서 프론트 그래프에 필요한 기본 배열은 제공할 수 있다.
- PR #37에서 배치 경합 때문에 실시간 집계로 전환한 결정과 충돌하지 않는다.
- 나중에 성능/정확도 요구가 생겼을 때 필요한 지표만 스냅샷으로 전환할 수 있다.

단점/영향:

- 프론트가 기대하는 “과거 상태 스냅샷 그래프”와는 의미가 다를 수 있으므로 Swagger/체크리스트에 그래프 의미를 명확히 써야 한다.
- 완전한 스냅샷 기반 통계 시스템은 이번 작업 이후에도 남는다.

권장:

- **선택지 C를 기본 권장**한다.
- 이유: 현재 A-016 그래프 요구는 대여/결제/완독 추이이며, 이 셋은 원본 이벤트 시간 컬럼으로 재계산 가능하다. 반면 스케줄러를 지금 넣으면 `admin_statistic` 구조 한계와 동시 실행 정책까지 같이 풀어야 해서 PR 범위가 커진다.
- 단, 사용자가 “막대그래프는 반드시 저장된 일/월 단위 스냅샷 기준이어야 한다”고 결정하면 선택지 B로 바꾼다.

## 4. 구현 계획

### 4.1 DTO 확장

- `AdminStatisticResponse`에 환경 지표와 추이 필드를 추가한다.
- 추이 항목 전용 record를 둔다.
  - `AdminStatisticTrendResponse` 또는 `AdminStatisticResponse.TrendPoint`
- 기존 KPI 필드는 유지해서 대시보드가 사용하는 `getTotalStatisticForDashboard()` 영향이 최소화되게 한다.

### 4.2 기간/나이대 계산 유틸

- `AdminStatisticService` 내부 private 메서드 또는 작은 helper 클래스로 시작한다.
- `PeriodRange(periodStartDate, periodEndDate, startDateTime, endDateTimeExclusive)` 형태를 사용한다.
- `AgeBandRange(minAgeInclusive, maxAgeInclusive)` 형태로 변환하되, SQL/JPA에서는 birthDate 범위로 바꿔 조회한다.
- 만 나이 기준 birthDate 범위:
  - 최소 나이 `min`, 최대 나이 `max`
  - `birthDate <= 기준일.minusYears(min)`
  - `birthDate > 기준일.minusYears(max + 1)`

### 4.3 Repository 쿼리 추가

기존 단순 count 메서드는 유지하고, 관리자 통계 전용 조건부 쿼리를 추가한다.

대상:

- `MemberRepository`
- `BookRentalRepository`
- `ReadingProgressRepository`
- `PaymentRepository`
- `ReviewRepository`
- `BookReportRepository`
- `ReviewReportRepository`

원칙:

- `from`/`to` 기간 파라미터는 `TOTAL`일 때 null 허용 또는 서비스에서 전체 기간으로 변환한다.
- ageBand 필터는 `birthDateFrom`, `birthDateTo` 파라미터를 nullable로 둔다.
- MySQL 함수 의존 쿼리보다 JPQL 조건 조합을 우선 사용한다.
- 선택지 C 확정 시 추이 bucket 집계는 처음 구현에서 서비스가 bucket별 조건을 만들고 repository count/sum을 호출하는 방식으로 시작한다. 성능 문제가 보이면 native group by 또는 스케줄러 스냅샷으로 후속 최적화한다.
- 선택지 B 확정 시 이번 섹션은 스케줄러 저장/조회 구조로 재작성해야 하며, 기존 `admin_statistic`만으로 그래프 bucket 저장이 가능한지 먼저 검토한다.

### 4.4 Service 흐름 변경

1. `periodType`, `baseDate`, `ageBand`를 정규화한다.
2. `PeriodRange`와 `AgeBandRange`를 계산한다.
3. KPI count/sum을 조건부 repository 메서드로 조회한다.
4. 완독 수 기준으로 `carbonSavedKg`, `treeSavedCount`를 계산한다.
5. `rentalTrend`, `paymentTrend`, `completedReadTrend`를 bucket 기준으로 계산한다.
6. `AdminStatisticResponse`를 반환한다.

`getTotalStatisticForDashboard()`는 기존처럼 `TOTAL + ALL`을 호출하되, 대시보드 응답에 불필요한 추이 필드가 포함되는 것이 문제인지 확인한다. 공통 DTO를 그대로 쓰면 응답은 커지지만 동작은 단순하다. 대시보드 응답을 가볍게 유지해야 하면 대시보드용 KPI DTO 분리를 후속으로 검토한다.

### 4.5 Controller/Swagger 갱신

- `@Operation` 설명에서 “현재는 TOTAL+ALL만 지원” 문구를 제거한다.
- `baseDate` 설명을 실제 기준일 설명으로 변경한다.
- `periodType`, `ageBand` 허용값 설명에 정상 지원 범위를 명시한다.
- 잘못된 enum 값은 기존처럼 `400 VALIDATION_ERROR`로 둔다.

## 6. 위험과 후속 검토

- 실시간 집계 방식은 구현이 단순하지만 데이터가 늘면 관리자 통계 응답이 느려질 수 있다. 이 경우 `admin_statistic` 또는 별도 그래프 스냅샷 테이블을 다시 사용하는 최적화 PR을 검토한다.
- `admin_statistic` 엔티티는 현재 `int` count와 오래된 review/report 주석을 갖고 있어, 이번 실시간 집계에서 계속 쓰지 않을 경우 직접 수정하지 않는다. 스냅샷 저장을 재도입할 때 함께 정리한다.
- 추이 bucket을 repository 반복 호출로 구현하면 쿼리 수가 늘어난다. 선택지 C에서는 정확성과 구현 범위를 우선하고, 성능 최적화는 측정 후 결정한다.
- 선택지 B를 택하면 스케줄러 테스트, 스냅샷 중복 생성 방지, 실패 시 재시도, 데이터 원복 SQL까지 검증 범위에 포함해야 한다.
- 나이대 필터를 리뷰/신고에 적용할 때 “작성자/신고자 기준”으로 볼지 “대상자 기준”으로 볼지 혼동될 수 있다. 이번 통계는 운영 사용자 분포 기준이므로 리뷰 작성자, 신고자는 reporter 기준으로 잡는다.
