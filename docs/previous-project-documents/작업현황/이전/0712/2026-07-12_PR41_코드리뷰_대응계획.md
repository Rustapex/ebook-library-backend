## 1. 감사 로그 summary 문자열을 직접 이어붙이는 방식 — 안전성 문제

- 위치: `CouponService.java:92`, `ChallengeService.java:198,215`, `BookApprovalService.java:112`
- 문제: `"{\"couponName\":\"" + name + "\"}"` 식으로 문자열을 직접 조립. 쿠폰명/챌린지명/도서명에 `"`, `\`, 줄바꿈이 들어오면 `beforeSummary`/`afterSummary`가 깨진 JSON으로 저장됨. 관리자가 나중에 감사 로그를 조회/추적할 때 근거 자료가 깨지는 셈이라 지적이 타당함.
- 수정 방안:
  - **안 A(권장)**: `com.fasterxml.jackson.databind.ObjectMapper`로 작은 `Map<String, Object>` 또는 record를 직렬화해서 저장. `AdminAuditLogWriter`에 `ObjectMapper` 주입하고, 호출부는 `Map.of("couponName", name, "couponType", type)` 같은 형태로 넘기면 이스케이프를 신경 쓸 필요가 없음.
  - 안 B: JSON 모양을 포기하고 `"couponName=" + name + ", couponType=" + type` 같은 plain 포맷으로 고정. 파싱은 못 하지만 이스케이프 문제 자체가 없음.
- 확정: **안 A**. 이미 `AdminAuditLogSummaryResponse`가 `beforeSummary`/`afterSummary`를 그대로 문자열로 내려주는 구조라, 저장 시점에 유효한 JSON으로 만들어두면 나중에 프론트에서 파싱해서 예쁘게 보여줄 여지도 남는다.
- 구현 방향: `AdminAuditLogWriter`에 `ObjectMapper`를 주입하고, 호출부는 `Map<String, Object>` 또는 작은 record를 넘긴다. Writer 내부에서 `writeValueAsString(...)`으로 JSON 문자열을 만든 뒤 기존 `AdminAuditLog.create(...)`에는 문자열을 저장한다.
- 장점: 호출부의 하드코딩 문자열 조립을 제거하고, 따옴표/역슬래시/줄바꿈 이스케이프를 Jackson에 맡긴다.

## 2. `AdminStatisticResponse.reviewCount`/`reportCount` 0 고정

- 위치: `AdminStatisticService.java:21,75,76`, `AdminStatisticServiceTest.java:65`
- 리뷰어 의견: 이번 PR에서 신고 Repository(`BookReportRepository`/`ReviewReportRepository`)가 이미 들어왔으니, "최근 위젯 추가"를 넘어 "대시보드 KPI까지 명세 일치"가 목표라면 이 김에 count까지 연결하는 게 맞다는 제안.
- 확인: `docs/작업현황/2026-07-10_관리자-대시보드-통계-감사로그API_구현계획.md` §4-4에서 review_count/report_count를 "review 패키지 Repository 부재"를 이유로 0 고정하기로 이미 확정했었는데, 이번 PR(§6.2)에서 그 Repository가 실제로 생겼으므로 그 전제가 더 이상 유효하지 않음.
- 수정 방안:
  - **안 A**: `AdminStatisticService`에 `bookReportRepository.count()` + `reviewReportRepository.count()`를 더해 `reportCount`로, `Review`는 아직 Repository는 있지만(다른 PR에서 추가됨) 이번 범위에 포함할지 확인 필요 — `reviewCount`는 `ReviewRepository.count()`로 채움.
  - 안 B: 이번 PR 범위를 "최근 위젯"으로 명확히 남기고, PR 본문/Swagger 설명에 "reviewCount/reportCount는 후속 PR" 명시만 하고 코드는 그대로 둠.
- 확정: **안 A**.
- 상세 결정:
  - `reportCount`는 `BookReportRepository.count()` + `ReviewReportRepository.count()` 합계로 채운다.
  - `reviewCount`는 `ReviewRepository.count()`로 채운다.
  - API 명세에서 `reviewCount`는 활성 리뷰 수로 설명되어 있으므로, 구현 시 `ReviewRepository.countByStatus("ACTIVE")` 같은 명시적 메서드가 더 적합한지 확인한다. 현재 단순 `count()`만 쓰면 `HIDDEN`/`DELETED`까지 포함될 수 있으므로, 구현 시 테스트 기대값과 함께 확정한다.
- 이유: PR #37 당시 0 고정의 전제였던 "review/report Repository 부재"가 이번 PR에서 해소됐다. 대시보드 KPI가 명세의 리뷰/신고 KPI를 포함하므로 이번 범위에서 연결하는 편이 맞다.

## 3. `AdminRecentReportResponse.reportId`가 targetType별로 겹칠 수 있음

- 위치: `AdminRecentReportResponse.java:9`, `AdminDashboardService.java:60-67`
- 문제: `reportId`는 `book_report_id` 또는 `review_report_id`를 그대로 쓰므로, BOOK 신고 1건과 REVIEW 신고 1건이 둘 다 `reportId=1`일 수 있음. 현재 `targetType`이 같이 내려가므로 조합하면 구분 가능하지만, 프론트가 `reportId` 단독을 React key 등으로 쓰면 충돌 위험.
- 수정 방안:
  - **안 A(권장)**: 코드 변경 없이, PR 본문/Swagger 설명에 "reportId는 targetType과 함께 조합해서 사용해야 하는 값(단독 유니크 아님)"이라고 명시만 한다.
  - 안 B: `AdminRecentReportResponse`에 `reportKey`(예: `"BOOK:1"`) 필드를 추가로 내려준다. 프론트 계약이 하나 더 늘어남.
- 확정: **안 A**. 이번 PR에서 프론트 연동이 아직 없고, 필드 추가는 나중에 실제 프론트 요구가 생기면 그때 넣어도 늦지 않음.
- 반영 내용: Swagger description과 PR 본문에 "`reportId`는 `targetType`과 함께 조합해서 식별해야 하며, 단독 전역 유니크 값이 아니다"라고 명시한다.
- `targetType` 고정 여부: 코드에 `AdminAuditLogTargetType` 같은 상수 클래스가 이미 있으므로 enum-like 상수로 고정하는 방식은 가능하다. 다만 이 항목의 핵심은 `reportId` 단독 사용 오해 방지이고, DTO 필드 타입을 enum으로 바꾸면 API 계약 변경이 커진다. 이번 PR에서는 설명 보강만 하고, 실제 프론트에서 타입 안정성이 필요해지면 별도 후속으로 `ReportTargetType` 상수/enum 적용을 검토한다.

### 5.2 PR41 구현 후 추가할 검증 항목

1. 감사 로그 summary JSON 안전성
   - 기존 감사 로그 발생 API 중 하나 이상에 따옴표(`"`), 역슬래시(`\\`), 줄바꿈이 포함된 입력값을 사용하도록 체크리스트와 SQL 안내를 보강한다.
   - 예: 쿠폰명, 포인트 지급 설명, 챌린지 수정값, 도서 승인 대상 문자열에 특수문자를 포함한다.
   - Swagger/Postman 기대값: API 호출은 성공하고, `admin_audit_log.before_summary`/`after_summary`는 JSON 파싱 가능한 문자열이어야 한다.
   - DB 확인은 가능하면 `JSON_VALID(before_summary)`/`JSON_VALID(after_summary)`를 사용하고, MySQL 버전 또는 컬럼 값 특성상 곤란하면 조회 결과를 체크리스트에서 직접 JSON 파싱 확인하도록 명시한다.

2. `reviewCount`/`reportCount` 실제 집계
   - 통계 API `GET /api/v1/admin/statistics?periodType=TOTAL` 검증에 다음 기대값 계산을 추가한다.
   - `reportCount` 기대값: `book_report` 전체 건수 + `review_report` 전체 건수
   - `reviewCount` 기대값: 구현에서 확정한 기준에 맞춘 리뷰 건수. 현재 계획은 API 명세의 “활성 리뷰 수”에 맞춰 `ACTIVE` 리뷰 기준을 우선 검토한다.
   - SQL 파일에는 Swagger 호출 전후로 기대 count를 직접 조회하는 SELECT를 추가해, SQL 파일만 봐도 통계 응답과 비교할 수 있게 한다.
   - 체크리스트에는 응답 필드 `data.reviewCount`, `data.reportCount`가 어떤 SQL 결과와 일치해야 하는지 API 번호/Method/URL 옆에 명시한다.

3. `AdminRecentReportResponse.reportId` 식별 규칙
   - 대시보드 API `GET /api/v1/admin/dashboard` 검증에서 `recentReports[*].reportId`는 단독 전역 유니크 값이 아니라 `targetType + reportId` 조합으로 식별하는 값임을 확인 항목으로 둔다.
   - Swagger description과 PR 본문에도 같은 설명을 반영한다.
   - 이번 범위에서는 DTO 필드 타입 변경 없이 설명 보강만 한다.
