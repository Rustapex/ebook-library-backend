## 1. 배경

PR #42 코드리뷰 재검토 코멘트(https://github.com/shangpa/AcornProject/pull/42#issuecomment-4951557223, 작성자 `Rustapex`, 2026-07-12T14:35:29Z)에서 **COMMENT / merge 가능** 판정과 함께, merge blocker는 아니지만 후속으로 추적하면 좋은 항목 4개를 남겼다(3~6절).

사용자 요청에 따라 이번 회차에서는 이 4개 항목에 더해 관리자 대시보드/통계/감사로그 도메인 전체를 다시 조사해 추가로 구현할 부분을 찾았다. 그 결과:

- 항목 7(감사 로그 `actionType`/`targetType` 미검증)을 새로 발견했다.
- 항목 8(프론트 설계문서 stale 서술 2건)을 발견했다. 단, 프론트 저장소(`abc-proj-win-FRONT`) 파일은 이 작업 담당자 소관이 아니므로 직접 수정하지 않고 수정요청 문서만 작성한다(8절 참고).
- 사용자 확인에 따라, 회원용 독서 통계(API-STAT-001, `/api/v1/me/statistics`)도 "통계" 담당 도메인에 포함되는 항목으로 재확인됐다. 원래 이 항목을 관리자 API가 아니라는 이유로 scope-out했던 판단은 도메인 담당 범위를 잘못 이해한 것이었다. 다만 신규 API 하나를 통째로 추가하는 규모라 **이번 브랜치(`feature/admin-dashboard-statistics-audit-followups`)에는 포함하지 않고 별도 브랜치로 분리하기로 확정**했다(9절).
- 프론트엔드와 백엔드는 개별적으로 개발 중이며, 백엔드 개발은 프론트 구현 완료 여부와 무관하게 진행한다(프론트-백엔드 연결은 프론트 완성 후 별도로 진행). 따라서 이 계획의 항목들은 프론트 미구현을 이유로 미루지 않는다.

이 문서는 계획 문서다. 실제 소스/스키마/설정 파일은 이 문서 작성 단계에서 건드리지 않는다.

## 7. 감사 로그 `actionType`/`targetType` 미검증 (신규 발견)

- **현황 확인**(`rg` 기준):
  - `AdminAuditLogController.getAuditLogs()`는 `actionType`/`targetType`을 `@RequestParam(required = false) String`으로만 받고 `@Pattern` 등 형식 검증이 없음(`page`/`size`만 `@Min` 검증됨).
  - `AdminAuditLogRepository.search()`의 JPQL은 `(:actionType IS NULL OR a.actionType = :actionType)` 형태 — `AdminAuditLog.actionType`/`targetType`은 enum이 아니라 순수 `String` 컬럼(`AdminAuditLog.java` 35/38행).
  - `AdminAuditLogActionType`/`AdminAuditLogTargetType`은 실제 Java enum이 아니라 `public static final String` 상수 모음 클래스(`private` 생성자로 인스턴스화만 막음) — 즉 컨트롤러/서비스 어디에도 "이 값이 알려진 상수 목록에 속하는지" 검증하는 코드가 없다.
  - `AdminAuditLogServiceTest`/`AdminAuditLogControllerTest` 모두 `page`/`size` 경계값 테스트만 있고, 잘못된 `actionType`/`targetType` 케이스 테스트가 없다.
- **영향**: `actionType=GARBAGE` 같은 값을 보내도 400이 아니라 200 + 빈 목록으로 응답한다. PR42에서 통계 API의 `periodType`/`ageBand`에 대해 정확히 같은 패턴("잘못된 값이 조용히 정상 응답으로 처리됨")을 지적받아 fail-fast로 고쳤는데, 감사 로그 API에는 아직 대칭 처리가 안 돼 있다.
- **PR42 사례와의 차이(심각도 판단 근거)**: 통계 API는 잘못된 값이 *다른 정상 값으로 오인*되어 그럴듯하지만 틀린 데이터를 돌려줬다(예: 잘못된 periodType이 조용히 TOTAL로 처리됨). 감사 로그는 잘못된 값이 매칭되는 로그가 없어 그냥 "빈 목록"이 되므로, 데이터가 틀리게 보이진 않는다. 다만 관리자가 오타를 냈을 때 "결과 없음"과 "필터값 오류"를 구분하지 못하는 문제는 동일하게 남는다.
- **대상 파일(안)**: `AdminAuditLogController.java`(`@Pattern` 추가 여부 또는 서비스단 검증), `AdminAuditLogService.java`, 필요 시 `AdminAuditLogActionType`/`TargetType`에 상수 목록을 노출하는 정적 메서드(예: `values()` 유사) 추가, `AdminAuditLogControllerTest`/`AdminAuditLogServiceTest`에 잘못된 값 케이스 추가.
- **결정 필요 사항(안 A/B, 미확정)**:
  - **안 A**: `periodType`/`ageBand`처럼 컨트롤러 `@Pattern(regexp = "...")`으로 고정 목록 검증. 장점: 기존 통계 API와 패턴 일관. 단점: `AdminAuditLogActionType`/`TargetType`에 §9 후속 작업으로 값이 계속 추가될 예정(12절)이라 `@Pattern` 정규식을 매번 같이 고쳐야 함.
  - **안 B**: 서비스단에서 상수 클래스의 값 목록(reflection 또는 명시적 `Set`)과 대조해 `BusinessException(ErrorCode.VALIDATION_ERROR)`. 장점: 상수 클래스 한 곳만 고치면 됨. 단점: 컨트롤러 계층 검증(현재 프로젝트 관례)과 다른 계층에서 검증하게 됨.
  - 신규 `ErrorCode` 추가는 이번에도 하지 않고 기존 `VALIDATION_ERROR` 재사용을 기본안으로 제안(통계 항목1과 동일 정책).
  - **확정**: 안 B(서비스단에서 상수 클래스 값 목록과 대조해 `BusinessException(ErrorCode.VALIDATION_ERROR)`). `periodType`/`ageBand`는 6개 이하 값으로 거의 안 늘어나는 고정 목록이라 `@Pattern`이 적합했지만, `actionType`/`targetType`은 12절 scope-out에 적어둔 대로 다른 admin 도메인(회원/도서/신고/공지 등) write API가 생길 때마다 상수가 계속 늘어날 예정(§9 후속 작업)이다. `@Pattern` 정규식(안 A)을 택하면 상수 추가 때마다 컨트롤러 정규식도 같이 고쳐야 해서 리뷰가 지적한 "여러 파일 동기화 필요" 문제를 스스로 만드는 셈이라 안 B로 확정했다. 컨트롤러 계층 검증이라는 기존 관례와 다른 계층(서비스)에서 검증하게 되는 점은 의도적 예외로 남긴다.
  - **이번 브랜치 포함 확정**: 심각도(7절 "PR42 사례와의 차이" 참고 — 잘못된 값이 틀린 데이터가 아니라 빈 목록을 반환하므로 PR42 통계 버그보다 위험도는 낮음)는 낮지만, 변경 자체가 작아(서비스 메서드 1개 + 테스트) 이번 브랜치에 포함하기로 확정.

- 성능 인덱스(3절) 실제 DB 적용(로컬/공유) 자체 — 추적 문서 작성까지만, 적용 행위는 제외.

(참고: 이전 초안에서 §9-4 `user_reading_statistic`을 "회원용 API라 관리자 API 범위 밖"이라는 이유로 scope-out했으나, 사용자 확인에 따라 이는 담당 도메인 이해 오류였음이 확인됐다. 도메인 범위 자체는 scope-out 대상이 아니고, 9절의 신규 구현 항목으로 남는다. 다만 규모 때문에 **이번 브랜치의 scope-out**(별도 브랜치로 분리)이라는 점은 위 표에 확정 사항으로 반영했다.)

## 작업 순서(안 — 일부 미확정 항목은 사용자 확정 후 진행)

1. 브랜치 생성(`feature/admin-dashboard-statistics-audit-followups`, 사용자 실행 또는 명시적 지시 후 진행)
2. 항목 7(감사 로그 검증, 안 B 확정) 코드+테스트 구현 → 빌드/테스트 검증
3. 항목 6(ReadingProgressRepository 일별/월별 테스트 둘 다) 추가 → 빌드/테스트 검증
4. 항목 4(TOTAL 기준일 불일치, 안 A 확정) 반영예정 문서 갱신
5. 항목 5(trend label 포맷 문서화), 항목 8.1(프론트 수정요청 문서) 작성
6. 항목 3(성능 인덱스 적용 추적 문서) 작성 — 실제 DB 적용은 범위 제외
7. 10절 초경량 이해메모 + 반영예정/수정요청 문서 작성
8. 11절 `api-test-results` 0713 체크리스트(PR42 4개 항목 + 감사 로그 검증)/SQL 작성 → 사용자가 Swagger/Postman 실행

(9절 회원용 독서 통계는 별도 브랜치로 분리 확정 — 이 작업 순서에서 제외, 착수 시점에 별도 계획 문서로 다시 다룬다.)
