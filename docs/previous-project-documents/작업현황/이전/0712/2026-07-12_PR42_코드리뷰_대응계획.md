## 1. 잘못된 `periodType`/`ageBand`가 조용히 정상 응답으로 처리됨

- 위치: `src/main/java/com/acorn/abc/statistic/service/AdminStatisticService.java:136-154`(`resolvePeriodRange`), `156-174`(`resolveAgeBandRange`)
- 코드 확인 결과 리뷰 주장이 정확함:
  - `resolvePeriodRange`는 `WEEKLY`/`MONTHLY`/`YEARLY`가 아니면 전부 `TOTAL`로 처리(153행 `return new PeriodRange(TOTAL_PERIOD_START_DATE, LocalDate.now(), null, null);`).
  - `resolveAgeBandRange`는 `10S`/`20S`/`30S`/`40S`/`50_PLUS`가 아니면 전부 `new AgeBandRange(null, null)`(=필터 없음=`ALL`과 동일)로 처리(173행).
- 위험: `AdminStatisticController`의 `@Pattern` 검증은 HTTP 경로에서만 동작한다. `AdminStatisticService#getStatistics()`는 `public` 메서드라 서비스 직접 호출(다른 서비스/배치/테스트)이나 향후 재사용 경로에서는 이 검증을 거치지 않고, 오타나 잘못된 값이 조용히 `TOTAL`/`ALL`로 둔갑해 잘못된 통계를 정상 응답처럼 돌려줄 수 있다.
- 수정 방안:
  - **안 A(확정)**: `resolvePeriodRange`/`resolveAgeBandRange`에서 `TOTAL`/`ALL`(또는 `null`→`ALL`)을 명시 분기로 처리하고, 그 외 인식 불가 값은 `BusinessException(ErrorCode.VALIDATION_ERROR)`로 fail-fast.
  - 안 B: 지금 구조를 유지하고 Controller `@Pattern`만 신뢰한다. 리뷰가 REQUEST CHANGES 사유로 명시했으므로 채택 안 함.
- 테스트 보강: `AdminStatisticServiceTest`에 `getStatistics("DAILY", ...)`, `getStatistics("TOTAL", ..., "TEENAGER")` 같은 invalid 값이 `VALIDATION_ERROR`를 던지는지 확인하는 케이스 추가.
- **확정(2026-07-12): 안 A, 신규 `ErrorCode` 추가 없음.**
  - `docs/공통문서/백엔드_공통_개발_규칙.md` §7 "Validation 규칙"에 "Validation 실패는 항상 `400 Bad Request + VALIDATION_ERROR`로 응답한다"는 규칙이 이미 있고, `ErrorCode` enum에도 `VALIDATION_ERROR`(400)가 이미 존재한다(§6 예시 목록). Controller의 `@Pattern` 검증 실패와 서비스 레벨의 값 검증 실패가 같은 성격(입력값 검증)이므로 같은 코드를 재사용하는 것이 규칙과 일치한다.
  - `docs/작업현황/0706/2026-07-06_ErrorCode_신규추가_승인요청.md`(챌린지/출석/포인트/쿠폰 API용 신규 ErrorCode 6개 추가 사례)를 참고 삼아 대조한 결과, 그 문서는 "기존 ErrorCode로 표현 안 되는 새로운 실패 시나리오"에만 신규 코드를 추가했다. 이번 건은 이미 있는 `VALIDATION_ERROR`의 적용 범위(입력값 검증 실패)에 정확히 들어맞으므로 같은 기준으로도 신규 코드 추가 사유가 아니다.
  - 따라서 `ErrorCode enum`에 항목을 추가하는 절차(CLAUDE.md의 "새 ErrorCode가 필요하면 코드 작성 전에 승인 요청 문서를 먼저 만든다")는 이번 건에는 해당하지 않는다 — 신규 코드가 없기 때문이다.

## 2. 추이 집계가 bucket마다 3개 aggregate query를 반복 호출함

- 위치: `AdminStatisticService.java:91-110`(bucket 루프), `184-216`(`resolveTrendBuckets`)
- 코드 확인 결과 리뷰 주장이 정확함: 기본 KPI 집계 후 `buckets` 각각에 대해 `bookRentalRepository`/`paymentRepository`/`readingProgressRepository` 3개 쿼리를 매번 새로 호출한다. `MONTHLY`는 최대 31개 bucket이라 추이만 최대 93회 aggregate query가 발생한다(리뷰 추정치와 일치).
- 이 구조 자체는 구현계획 §3.6/§3.7에서 "선택지 C(하이브리드, 스케줄러 없이 실시간 집계)"로 이미 사용자 확정을 받은 사항이다. 리뷰도 이 결정 자체를 문제 삼지 않고, "그 안에서 쿼리 수를 줄일 여지가 있다"는 최적화 지적이다.
- 수정 방안:
  - **안 A(확정)**: `GROUP BY DATE(created_at)`(WEEKLY/MONTHLY) 또는 `GROUP BY DATE_FORMAT(created_at, '%Y-%m')`(YEARLY/TOTAL) 형태의 grouped aggregate 쿼리 1회로 기간 내 전체 bucket 값을 한 번에 가져오고, 결과에 없는 bucket(데이터가 0건인 날짜)은 서비스에서 메모리상 0으로 채운다. `rentalTrend`/`paymentTrend`/`completedReadTrend` 각각 1회씩, 총 3회 쿼리로 줄어든다(기존 최대 93회 → 3회).
  - 안 B: 지금 구조를 유지하되 후속 성능 검증 기준만 문서화. 채택 안 함.
- **확정(2026-07-12): 안 A(grouped query 전환).**
  - Repository에 `WEEKLY`/`MONTHLY`용 `GROUP BY DATE(...)`, `YEARLY`/`TOTAL`용 `GROUP BY DATE_FORMAT(..., '%Y-%m')` 쿼리를 추가해야 한다(대여/결제/완독 3개 × bucket 단위 2가지 = 최대 6개 신규 쿼리, 또는 파라미터로 일별/월별을 분기하는 방식도 검토).
  - 서비스는 grouped 결과(예: `Map<LocalDate, Long>` 또는 `Map<String, Long>`)를 먼저 조회한 뒤, `resolveTrendBuckets()`가 만든 bucket 목록을 순회하며 매칭되는 값이 없으면 0으로 채우는 방식으로 변경한다(쿼리 자체는 3회로 줄지만 bucket 매칭 로직은 새로 필요).
  - 변경 범위가 항목 1보다 크므로, 구현 단계에서 Repository/Service 구조 변경을 먼저 별도로 조사·설계한 뒤 진행한다.

- 반복 bucket query(항목 2)와 결합되면 인덱스 없는 range scan 비용이 커질 수 있다는 리뷰 지적이 타당하다.
- 수정 방안:
  - **안 A**: `idx_book_rental_created_at`, `idx_reading_progress_completed_at`, `idx_review_status_created_at`(복합 — 기존 `review.status` 단독 인덱스를 복합으로 바꾸거나 추가) 인덱스를 추가.
  - 안 B: 지금은 추가하지 않고, 실제 데이터 규모 기준으로 `EXPLAIN` 실행계획을 먼저 확인한 뒤 필요할 때 추가한다.
- **확정(2026-07-12, 경로 재확정): 안 A로 인덱스는 추가하되, `src/main/resources/schema.sql`에는 반영하지 않는다. 별도 스크립트는 `docs/데이터베이스/`가 아니라 `src/main/resources/` 경로에 둔다(사용자 지정).**
  - 이유: 이 프로젝트는 팀원 각자 개별 MySQL DB를 쓰고 있고, `schema.sql`은 `spring.sql.init.mode=always`로 부팅 시 전원 자동 반영된다. `schema.sql`을 직접 고치면 각자 DB에 어떤 인덱스가 실제로 적용됐는지, 누가 언제 반영했는지 추적하기 어렵다.
  - 대신 별도 SQL 파일 `src/main/resources/관리자통계_성능인덱스.sql`을 신규 작성해서 아래 3개 `CREATE INDEX` 문을 담는다.
    ```sql
    CREATE INDEX idx_book_rental_created_at ON book_rental (created_at);
    CREATE INDEX idx_reading_progress_completed_at ON reading_progress (completed_at);
    CREATE INDEX idx_review_status_created_at ON review (status, created_at);
    ```
  - 자동 실행 안 됨 확인: `src/main/resources/application.properties`에 `spring.sql.init.schema-locations=classpath:schema.sql`, `spring.sql.init.data-locations=classpath:data.sql`이 파일명까지 명시적으로 고정돼 있다. 즉 부팅 시 자동으로 실행되는 대상은 정확히 `schema.sql`/`data.sql` 이 두 파일뿐이고, 같은 폴더에 다른 이름의 `.sql` 파일을 추가로 둬도 Spring Boot가 자동으로 찾아서 실행하지 않는다(직접 확인함). 그래서 `schema.sql`과 물리적으로 같은 폴더에 둬도 "각자 DB에 조용히 자동 반영되는 문제"는 생기지 않는다.
  - 파일 상단에 "이 스크립트는 `schema.sql`/`data.sql`과 달리 자동 초기화 대상이 아니며, 관리자 통계 확장(PR #42) 성능 개선을 위해 각자 로컬/공유 DB에 수동으로 실행한다"는 안내 주석을 남긴다. 기존 `review.status` 단독 인덱스(`idx_review_status`)와 신규 복합 인덱스(`status, created_at`)가 공존하는 게 맞는지는 구현 단계에서 다시 확인한다(중복 인덱스로 판단되면 기존 인덱스 교체 여부도 함께 검토).
  - `docs/데이터베이스/ddl/schema.sql`(설계 단계 DDL, `문서 우선순위`상 런타임 `schema.sql`보다 우선순위 낮음)에도 반영할지는 이번 범위에서 결정하지 않고, 실제 인덱스 스크립트 작성 시점에 별도 확인한다.

## Watchlist (선택 — blocking 아님)

### W1. `TOTAL`의 기준일 불일치

- `TOTAL`의 `periodStartDate`/`periodEndDate`는 `LocalDate.now()` 기준(153행)인데, `TOTAL`의 추이 bucket과 `ageBand` 계산은 `resolvedBaseDate`(`baseDate` 파라미터 또는 `LocalDate.now()`) 기준이다(68, 91행).
