## 3. 현재 구현 상태 요약

- `GET /api/v1/admin/dashboard` 컨트롤러/서비스/DTO 1차 구현

### 3.2 부분 완료된 것

- 최근 결제 목록은 있으나 `paymentStatus = PAID` 필터가 없다.

- 실시간 집계는 단순하고 안전하지만, 데이터 증가 시 성능 기준과 스냅샷 전환 기준이 아직 없다.

### 3.3 미완료된 것

- 대시보드 최근 신고 목록

### 6.2 2순위 - 대시보드 최근 신고 구현

목표:

- A-001 대시보드 운영 목록에 최근 신고를 포함한다.

선택지:

| 선택지 | 장점 | 단점/영향 |
|---|---|---|
| 통합 DTO `recentReports[]` | 대시보드의 "최근 신고" 목록을 시간순으로 한 번에 보여주기 쉽다. 책 신고/리뷰 신고가 같은 운영 큐로 보인다. 프론트는 하나의 리스트 컴포넌트만 만들면 된다. | `targetType=BOOK/REVIEW`, `targetId`, `targetTitle`처럼 타입 구분 필드가 필요하다. 상세 이동 시 targetType별 라우팅 분기가 필요하다. |
| 분리 DTO `recentBookReports[]`, `recentReviewReports[]` | 각 타입별 필드 차이를 명확히 둘 수 있다. 타입별 섹션을 따로 보여주는 화면에는 단순하다. | A-001의 "최근 신고"를 하나의 최신순 목록으로 보여주려면 프론트가 두 배열을 다시 합쳐야 한다. 전체 최근순 제한 기준이 백엔드/프론트에 중복될 수 있다. |

결정:

- 대시보드용 DTO는 `AdminRecentReportResponse`로 통합한다.
- 이유: A-001 화면은 "최근 신고" 운영 목록이며, 책 신고와 리뷰 신고를 별도 표로 관리하는 화면이 아니라 최신순 운영 큐로 보는 성격이 강하다.
- 필드는 `reportId`, `targetType`, `targetId`, `targetTitle`, `reportType`, `reportStatus`, `reporterName`, `createdAt` 수준으로 제한한다.
- Repository는 책 신고/리뷰 신고 각각 최근 N건 조회 후 서비스에서 합쳐 최신순으로 제한한다.
- 상세 처리와 상태 변경은 `API-ADMIN-REPORT-*` 작업 범위로 분리한다.

### 6.3 3순위 - 대시보드 최근 희망도서 구현

목표:

- A-001 대시보드 운영 목록에 최근 희망도서 후보를 포함한다.

결정:

- 대시보드 최근 희망도서는 사용자별 신청 row가 아니라 `BookRequestCandidate` 후보 단위로 반환한다.
- 이유: 관리자는 같은 도서를 몇 명이 신청했는지 보고 승인/반려 판단을 해야 하며, 사용자 단위 목록은 대시보드에서 불필요하게 많고 운영성이 낮다.
- 런타임 스키마 기준 후보 상태는 `REQUESTED`, `IN_REVIEW`, `APPROVED`, `REJECTED`이고, 개별 신청 상태는 `REQUESTED`, `APPROVED`, `REJECTED`다.
- 승인 시 같은 후보에 연결된 모든 사용자 신청 row를 승인 처리하고 `BOOK_REQUEST` 알림을 생성한다.
- 반려 시 같은 후보에 연결된 모든 사용자 신청 row를 반려 처리하고 `BOOK_REQUEST` 알림을 생성한다.
- 도서 등록/연결이 필요한 경우 `approvedBookId`를 연결한다.

권장 방향:

- 대시보드에는 후보 단위 `AdminRecentBookRequestResponse`를 반환한다.
- 필드는 `candidateId`, `title`, `author`, `publisher`, `requestCount`, `candidateStatus`, `firstRequestedAt` 수준으로 제한한다.
- 개별 신청자 목록은 A-011 희망도서 관리 API 범위로 둔다.

### 6.4 4순위 - 통계 기간/나이대 확장

목표:

- `API-ADMIN-STAT-001`의 `periodType`, `baseDate`, `ageBand`가 실제로 의미 있게 동작하게 한다.

작업:

1. 지원 범위는 최종 목표 기준 `TOTAL`, `WEEKLY`, `MONTHLY`, `YEARLY`로 둔다.
2. `baseDate` 기준 기간 시작/종료 계산 유틸 작성
3. `ageBand`가 `ALL`이 아니면 회원 `birthDate` 기준 **만 나이(국제 통용 나이)**로 `10S`, `20S`, `30S`, `40S`, `50_PLUS`를 계산한다.
4. 대여/결제/완독/리뷰/신고 count 쿼리에 기간 조건 반영
5. 지원하지 않는 조합은 명확한 에러 또는 빈 결과 정책 결정

주의:

- 현재 실시간 집계는 과거 스냅샷 값이 아니라 현재 DB 기준 기간 집계다.
- 기간별 추이를 정확히 보존하려면 `admin_statistic` 스냅샷 저장이 다시 필요할 수 있다.
- 이번 브랜치에서 구현량이 커지면 `TOTAL/ALL` 안정화와 대시보드 운영 목록을 먼저 끝내고, 통계 확장은 별도 PR로 분리한다.

### 6.5 5순위 - 통계 추이/탄소·나무 계산값

목표:

- A-016 통계 화면의 그래프 영역과 API 명세의 탄소/나무 계산값을 맞춘다.

작업:

1. 응답 DTO에 추이 목록 추가 여부 결정
2. `rentalTrend`, `paymentTrend`, `completedReadTrend` 형태 검토
3. 기간 단위별 bucket 계산 정책 결정
4. 탄소/나무 계산값은 이번 통계 확장 범위에 포함한다.
5. 계산식은 API 명세의 사용자 통계 계산식과 맞춰 `탄소 절약량 = 완독 수 × 2kg`, `나무 보호량 = 완독 수 × 0.04그루`로 둔다. 계산값은 DB에 저장하지 않고 응답 시 계산한다.
6. 테스트 데이터 기준 기대값 작성

주의:

- 관리자 통계에서도 사용자 통계와 같은 계산식을 사용한다.
- 계산값은 표시용 파생값이므로 저장 스키마를 늘리지 않는다.

### 6.6 6순위 - 감사 로그 기록 연동

목표:

- 감사 로그 조회 API가 실제 관리자 변경 이력을 조회할 수 있도록 변경성 관리자 API에서 로그를 남긴다.

의미:

- 감사 로그 기록은 관리자가 어떤 변경 API를 실행했는지 `admin_audit_log` 테이블에 남기는 것이다.
- 예: 관리자가 회원 상태를 `ACTIVE -> SANCTIONED`로 바꾸면 `actionType=MEMBER_STATUS_CHANGE`, `targetType=MEMBER`, `targetId=회원ID`, `beforeSummary=변경 전 요약`, `afterSummary=변경 후 요약`, `adminMemberId=작업 관리자`, `createdAt=작업 시각`을 저장한다.
- 감사 로그 조회 API(`GET /api/v1/admin/audit-logs`)는 이 기록을 필터링해서 보여주는 조회 전용 API다. 로그 자체를 수정/삭제하는 API는 만들지 않는다.

대상 후보:

- 도서 등록/수정/상태 변경
- 카테고리 등록/수정
- 회원 상태 변경
- 회원 포인트 조정
- 신고 처리
- 희망도서 승인/반려
- 공지 등록/수정/숨김
- 쿠폰 등록/발급
- 챌린지 등록/수정
- 도서관 등록/수정/보유 도서 변경
- 컬렉션 등록/수정/도서 추가/정렬/상태 변경

권장 방향:

- `AdminAuditLogWriter` 또는 `AdminAuditLogRecordService`를 만든다.
- action type과 target type은 문자열 난립을 막기 위해 상수 또는 enum-like class로 표준화한다. `actionType`은 수행한 행위이고, `targetType`은 행위 대상 도메인이다.
- 1차 표준값은 ERD 예시를 그대로 따른다.
  - `actionType`: `MEMBER_UPDATE`, `BOOK_UPDATE`, `REPORT_PROCESS`, `NOTICE_WRITE`, `COUPON_ISSUE`
  - `targetType`: `MEMBER`, `BOOK`, `BOOK_REPORT`, `REVIEW_REPORT`, `REVIEW`, `NOTICE`, `COUPON`, `SANCTION_HISTORY`
- 쿠폰은 ERD상 감사 로그 대상이므로 표준값에서는 제외하지 않는다. 다만 구현 순서는 후순위로 둘 수 있다.
- 리뷰 신고는 회원 대상 신고 테이블로 바꾸지 않는다. 신고 자체는 `REVIEW_REPORT`이고, 신고 처리 결과 회원 제재가 발생하면 `MEMBER` 또는 `SANCTION_HISTORY`를 별도 대상 후보로 기록한다.
- `beforeSummary`, `afterSummary`는 민감정보를 제외하고 핵심 변경값만 저장한다.
- 로그 기록 실패 정책은 기본적으로 **본 작업도 롤백**으로 둔다. 관리자 변경 이력은 운영 추적의 일부이므로, 변경은 성공했는데 감사 로그만 빠지는 상태를 만들지 않는 편이 안전하다.
- 단, 알림 발송처럼 외부 부수 효과까지 포함된 복합 작업에서는 트랜잭션 경계를 별도 검토한다.

초기 적용 순서:

1. 회원 상태 변경 / 포인트 조정
2. 쿠폰 등록 / 발급
3. 공지 등록 / 수정
4. 도서 등록 / 수정 / 상태 변경
5. 신고 처리 / 희망도서 처리
6. 나머지 관리자 변경 API

남은 작업:

1. `AdminAuditLogActionType`, `AdminAuditLogTargetType` 상수 또는 enum-like class 작성.
2. `AdminAuditLogWriter` 또는 `AdminAuditLogRecordService` 작성.
3. 1차 적용 대상 관리자 변경 API에 감사 로그 저장 호출 추가.
4. `beforeSummary`/`afterSummary`에 저장할 필드 범위 확정: 비밀번호, 토큰, 개인정보 원문은 제외하고 상태/제목/식별자/처리 결과 중심으로 요약.
5. 신고 처리에서 리뷰 숨김/회원 제재가 함께 발생하는 경우, `REPORT_PROCESS` 로그의 summary에 포함할지 별도 `MEMBER_UPDATE` 로그를 추가할지 구현 시점에 테스트 가능한 방식으로 고정.
6. 감사 로그 조회 필터 테스트: `actionType`, `targetType`, `targetId`, 페이징.

## 7. 문서 정리 계획

### 7.1 설계문서 직접 수정은 후순위

이번 구현 PR에서 `docs/API 명세/api-spec(final).md`, `docs/화면흐름도/03-Admin-상세화면설계도.md`, ERD/DDL 문서를 바로 최신화하지 않는다.

대신 구현 과정에서 실제 코드와 문서 사이에 생긴 차이를 별도 반영 예정 문서로 먼저 남긴다. 이후 설계문서 정합성 작업에서 해당 문서를 근거로 원본 설계문서를 일괄 수정한다.

### 7.2 설계문서 반영 예정 문서 작성

아래 경로에 Markdown 문서를 만든다.

```text
docs/작업현황/설계문서에 반영 예정/YYYY-MM-DD_관리자-API-설계문서-반영예정.md
```

문서에는 최소한 아래 항목을 표로 작성한다.

| 항목 | 내용 |
|---|---|
| 대상 설계문서 | `api-spec(final).md`, 관리자 화면설계, ERD/DDL 등 실제로 바꿔야 하는 파일 |
| 위치 | API ID, 화면 ID, 섹션명, 테이블명, 컬럼명 등 찾을 수 있는 기준 |
| 변경 전 | 현재 문서가 설명하는 내용 |
| 변경 후 | 구현 후 맞춰야 하는 내용 |
| 변경 이유 | 이번 구현에서 정책/응답/테이블 사용 방식이 바뀐 이유 |
| 영향 범위 | 프론트, Swagger, Postman, DB seed/test data, 후속 PR 영향 |
| 반영 상태 | 예정/반영 완료/보류 |

반영 예정 문서에 반드시 포함할 후보:

- `API-ADMIN-DASHBOARD-001`: 최근 신고, 최근 희망도서 후보, 최근 결제 응답 범위.
- `API-ADMIN-STAT-001`: `TOTAL/WEEKLY/MONTHLY/YEARLY`, `baseDate`, `ageBand`, 추이, 탄소/나무 계산값.
- `API-ADMIN-AUDIT-001`: 조회 전용 유지, 로그 생성은 변경성 관리자 API의 부수 효과임을 명시.
- 관리자 화면설계 A-001/A-016/A-017: 실제 응답 필드와 화면 위젯의 구현 단계 정리.
- 감사 로그 표준값: `actionType`, `targetType` 1차 표준값과 후속 확장 가능성.

### 7.3 Swagger 설명 갱신 계획

구현 범위가 확장되면 Swagger description에서 “1차 구현” 표현을 줄이고 실제 응답 필드 기준으로 갱신한다.

아직 미구현인 항목은 Swagger에서 완성된 것처럼 보이지 않게 한다. Swagger 문구 변경 사항도 `설계문서에 반영 예정` 문서에 같이 기록한다.

### 8.3 Swagger/Postman 수동 검증 산출물


두 파일은 서로를 보완하되, 각각 단독으로 봐도 테스트를 수행할 수 있게 작성한다.

#### 체크리스트 Markdown 작성 규칙

체크리스트 문서에는 각 API별로 아래 정보를 반드시 포함한다.

| 항목 | 필수 내용 |
|---|---|
| API ID | 예: `API-ADMIN-DASHBOARD-001` |
| HTTP Method | `GET`, `POST`, `PUT`, `PATCH` 등 |
| URL | Swagger/Postman에서 호출할 정확한 URL과 query string 예시 |
| 인증/권한 | 관리자 토큰 필요 여부 |
| 사전 SQL | 어떤 SQL 블록을 먼저 실행해야 하는지 |
| Request Body | body가 필요한 경우 JSON 예시와 각 필드 의미 |
| 기대 응답 | HTTP status, 공통 응답 코드, 주요 data 필드 |
| 확인 포인트 | DB 변경, 감사 로그 생성, 알림 생성, 응답 정렬/페이징 등 |
| 원복 SQL | 테스트 종료 후 어떤 SQL 블록으로 원복하는지 |

체크리스트에는 최소한 아래 호출을 포함한다.

- `API-ADMIN-DASHBOARD-001` `GET /api/v1/admin/dashboard`
- `API-ADMIN-STAT-001` `GET /api/v1/admin/statistics?periodType=TOTAL`
- `API-ADMIN-STAT-001` `GET /api/v1/admin/statistics?periodType=MONTHLY&baseDate=YYYY-MM-DD&ageBand=ALL`
- `API-ADMIN-STAT-001` `GET /api/v1/admin/statistics?periodType=MONTHLY&baseDate=YYYY-MM-DD&ageBand=20S`
- `API-ADMIN-AUDIT-001` `GET /api/v1/admin/audit-logs`
- 감사 로그 기록 대상 관리자 변경 API 최소 2개 이상: 예를 들어 회원 상태 변경, 신고 처리, 공지 작성, 쿠폰 발급, 도서 상태 변경 중 구현된 항목.

#### SQL 파일 작성 규칙

SQL 파일은 단순 insert 모음이 아니라, 주석만 보고도 테스트 순서를 알 수 있게 작성한다.

SQL 파일에는 최소한 아래 블록을 둔다.

```sql
-- 0. 목적/주의사항
-- 1. 현재 DB 상태 확인 SELECT
-- 2. 테스트 데이터 INSERT/UPDATE
-- 3. Swagger/Postman 호출 순서 안내
-- 4. 각 호출 후 DB 검증 SELECT
-- 5. 원복 DELETE/UPDATE
-- 6. 원복 확인 SELECT
```

SQL 파일 안의 `3. Swagger/Postman 호출 순서 안내`에는 체크리스트 문서와 같은 API ID, Method, URL, 필요한 body 요약을 주석으로 적는다.

예시 형식:

```sql
-- [API-ADMIN-REPORT-002] PATCH /api/v1/admin/reports/{targetType}/{reportId}/status
-- Body 예시: { "status": "DONE", "processResult": "관리자 처리 완료", "hideReviewYn": true }
-- 이 호출 후 아래 SELECT로 REVIEW_REPORT 상태와 ADMIN_AUDIT_LOG 생성을 확인한다.
```

체크리스트 Markdown도 SQL 파일명을 명시하고, SQL 파일도 체크리스트 Markdown 파일명을 명시한다. 이렇게 해서 둘 중 하나만 열어도 어떤 데이터로 어떤 API를 어떤 순서로 검증하는지 알 수 있게 한다.
