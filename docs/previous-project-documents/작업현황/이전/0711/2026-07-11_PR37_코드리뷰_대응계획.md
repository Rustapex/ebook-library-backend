## 1. 코멘트별 확인 및 대응 방안

### 1-1. `AdminStatisticService`의 API 표면이 실제 구현보다 넓음

- 리뷰 원문 요약: `baseDate`를 파라미터로 받지만 서비스가 실제로 쓰지 않는다. `TOTAL+ALL` 외 조합은 전부 `COMMON_NOT_FOUND`다. API 명세/컨트롤러 파라미터만 보면 `WEEKLY`/`MONTHLY`/`YEARLY`, `ageBand`, `baseDate`까지 다 지원하는 것처럼 보인다.
- 코드 확인: `AdminStatisticService.getStatistics(periodType, baseDate, ageBand)` — `baseDate`는 메서드 시그니처에만 있고 내부 로직(`findStatistic()`)은 `periodType`/`ageBand`만 참조한다. 정확한 지적.
- 원인: 구현계획 §4-1에서 1단계 범위(`TOTAL`+`ALL`만)를 확정하면서, `baseDate`는 2단계(WEEKLY 등)를 위해 시그니처만 남겨뒀는데 그 사실을 Swagger Operation 설명에 명시하지 않았다.
- 수정 방안:
  - **안 A(권장)**: 컨트롤러 파라미터에 `@Parameter(description=...)`로 "현재 미사용, 2단계에서 사용 예정"을 명시하고 `@Operation` summary/description도 "1단계: TOTAL+ALL만 지원"으로 보강한다. `baseDate` 파라미터 자체는 API 명세와의 계약 유지를 위해 남긴다.
  - 안 B: `baseDate` 파라미터를 이번 PR에서 제거하고 2단계 착수 시 다시 추가한다. API 명세(`baseDate?`가 이미 문서화됨)와 불일치가 생겨 비권장.
- 권장: **안 A**.

### 1-2. Dashboard 응답이 명세의 전체 위젯 중 일부만 구현

- 리뷰 원문 요약: 현재 응답은 통계+최근 결제뿐. 최근 신고/최근 희망도서는 계획 문서상 제외가 확인되지만, API 명세/화면 설계에는 포함돼 있어 클라이언트가 완성 응답으로 오해할 수 있다.
- 코드 확인: `AdminDashboardController.getDashboard()`의 `@Operation(description = "KPI 통계와 최근 결제 목록을 반환합니다.")` — "이게 대시보드 응답의 일부일 뿐"이라는 사실이 설명에 없다.
- 수정 방안:
  - **안 A(권장)**: Operation description에 "1차 구현: 최근 결제만 포함. 최근 신고/희망도서는 `review`/`request` Repository 추가 후 후속 작업으로 추가 예정(구현계획 §9)"을 명시한다.
  - 안 B: `AdminDashboardResponse`에 신고/희망도서 필드를 미리 추가하고 빈 배열로 채운다. `review`/`request` Repository가 없어 실제 값을 못 채우고, 빈 배열이 "0건"인지 "미구현"인지 클라이언트가 구분 못 해 오히려 혼란을 키운다. 비권장.
- 권장: **안 A**.

### 1-3. `AdminStatisticBatchService`의 startup/schedule 갱신은 단일 인스턴스 전제 필요 — **정정 확정(2026-07-11): 배치 폐기, 실시간 집계로 전환**

- 리뷰 원문 요약: `@PostConstruct`와 `@Scheduled`가 같은 `TOTAL/ALL` row를 read-then-create/save로 다룬다. `admin_statistic`에 `(period_type, period_start_date, age_band)` UNIQUE 제약이 있어, 다중 인스턴스 기동 시 첫 insert 경합 가능성이 있다.
- 코드 확인: `AdminStatisticBatchService.refreshTotalStatistics()` — `findByPeriodTypeAndPeriodStartDateAndAgeBand()` 조회 후 없으면 `create()`+`save()`. 두 인스턴스가 동시에 "없음"을 보고 각자 insert하면 실제로 경합 가능. 이전 Swagger 검증 체크리스트(§2)에서 이미 "알려진 리스크"로 남겨둔 사안과 동일.
- 1차 확정(같은 날 앞서 논의): 인스턴스는 하나만 띄우기로 하고 주석만 추가하는 방향으로 확정했었음.
- **재논의 후 최종 확정**: TOTAL/ALL 통계를 배치(`@PostConstruct`+`@Scheduled`)로 사전 집계해두는 대신, API 요청 시점에 원본 테이블을 직접 집계하는 **실시간 집계 방식으로 전환**한다(구현계획 §4-1에서 이미 검토했던 안 B와 동일한 방향으로 재선택). 이 프로젝트 규모(관리자 전용, 저트래픽, 소규모 데이터)에서는 실시간 집계도 성능 문제가 없다고 판단함.
  - 이 결정으로 §1-3이 지적한 "다중 인스턴스 upsert 경합" 문제 자체가 **원천 해소**된다 — 더 이상 `admin_statistic`에 쓰기(insert/update)를 하는 배치가 없으므로 경합할 대상이 없어짐.
  - 단, `WEEKLY`/`MONTHLY`/`YEARLY` 추이 그래프(A-016, 후속 작업)는 실시간 집계만으로는 과거 시점 값을 재현할 수 없어서, 그래프 기능 착수 시점에 주기적 스냅샷 저장 방식이 다시 필요해질 수 있다는 점은 별도로 남겨둔다(§3 후속 작업 참고).
  - 실제 구현(배치/스케줄링 코드 제거, 서비스 로직을 실시간 집계로 재작성)은 이번 문서에서 착수하지 않는다 — 작업은 추후 진행하고, 완료 후 PR #37에 반영 코멘트를 남기기로 함(사용자 확인).

### 1-4. 감사 로그 조회 `size` 상한 없음 — **확정(2026-07-11)**

- 리뷰 원문 요약: `page`/`size`에 최솟값 검증(`@Min`)은 있지만 `size` 최댓값이 없다. 감사 로그는 커질 가능성이 큰 테이블이라 상한이 안전하다.
- 코드 확인 결과 정정: 처음에 제안했던 `@Max(100)` 애노테이션은 **이 프로젝트에 전례가 없는 방식**이다. 실제로 확인해보니 `AdminChallengeController`/`AdminCouponController`/`PointController`/`CouponController`까지 이 프로젝트의 모든 목록 조회 API가 `size`에 `@Min(1)`만 두고 상한 애노테이션은 아예 안 쓴다. 대신 `BookService`/`CollectionService`에 이미 있는 패턴은 `private static final int MAX_SIZE = 100;` 상수를 두고 서비스 메서드 안에서 `Math.min(size, MAX_SIZE)`로 **조용히 잘라서** 쓰는 방식이다(400으로 막는 게 아니라 100건으로 캡).
- 확정된 수정 방안: `@Max` 애노테이션 대신, `AdminAuditLogService`에 `BookService`/`CollectionService`와 동일하게 `MAX_SIZE = 100` 상수 + `Math.min(size, MAX_SIZE)` 클램프를 추가한다. 이렇게 하면 이 프로젝트의 기존 관례와 일치하고, `size`가 커도 400 에러 대신 100건으로 잘려서 조회된다.

### 1-5. `BaseEntity` 규칙과 `AdminStatistic` — **확정(2026-07-11): 이번 범위 제외**

- 리뷰 원문 요약: 공통 규칙상 Entity는 `BaseEntity` 상속이 원칙인데 `AdminStatistic`은 직접 `updatedAt`을 가진다. 리뷰어 스스로도 "이 PR만의 문제로 보기 어렵다"고 인정(기존 코드에도 유사 사례 있음).
- 코드 확인: `docs/공통문서/백엔드_공통_개발_규칙.md` 10절 위반이지만, 챌린지/출석/포인트 도메인 등 기존에도 `BaseEntity` 미상속 사례가 있고 이미 별도 후속 정리 대상으로 이월되어 온 사안(`CLAUDE.local.md` 이력 참고). `AdminStatistic`도 같은 부류다.
- 확정: 이번 PR에서는 손대지 않는다. 기존 "BaseEntity 미상속 정리" 후속 작업 목록에 `AdminStatistic`을 추가만 해둔다.

## 2. 병합 여부 — 안 A(같은 브랜치에서 수정 후 병합) vs 안 B(지금 병합 후 새 브랜치)

### 안 A. 지금 브랜치(`feature/admin-dashboard-statistics-audit-log`)에서 §1-1~1-4 반영 후 병합

- 장점: §1-1/1-2는 `@Operation`/`@Parameter` 설명 보강, §1-4는 `MAX_SIZE` 상수+`Math.min()` 클램프(기존 `BookService`/`CollectionService`와 동일 패턴) 추가로 전부 저위험·저비용 수정이다. "공개 계약과 구현 범위 간극"이라는 리뷰 지적을 병합 전에 없애서, 리뷰어가 우려한 "리뷰/프론트 연동 단계 오해"를 원천 차단한다.
- 참고: §1-3은 애초 예상(주석 한 줄)보다 범위가 커졌다 — 배치/스케줄링 코드를 제거하고 실시간 집계로 재작성하는 실질적인 코드 변경이다(§1-3 정정 확정 참고). 그래도 API 응답 계약은 그대로라 병합 시점 판단(안 A/B) 자체에는 영향 없음.
- 단점: 병합이 그만큼 늦어진다(다만 위 항목들은 몇 시간 내 끝날 분량).
- PR #37에 커밋을 추가로 쌓고, 리뷰어에게 재확인 요청(코멘트) 후 병합.

### 안 B. 지금 상태로 병합하고 별도 브랜치에서 후속 작업

- 장점: 병합이 빠르다.
- 단점: 리뷰어가 이미 "REQUEST CHANGES 권장"이라고 명시한 상태로 병합하는 셈이라, 리뷰 프로세스와 어긋난다. §1-1/1-2가 지적한 "완성된 API처럼 보이는 계약"이 `main`에 그대로 들어가 프론트 연동 시 실제로 오해를 유발할 위험이 실현될 수 있다.

### 권장: **안 A**

이유: §1-1/1-2/1-4는 실제 코드/문서 수정량이 매우 작고(리스크 낮음), §1-3도 주석 추가뿐이라 병합을 늦출 만큼 큰 작업이 아니다. blocking bug는 없다는 리뷰어 결론과 별개로, "리뷰가 요청한 변경을 반영하지 않고 병합"하는 것은 이 프로젝트의 PR 리뷰 관례(코드리뷰 대응 후 병합)와도 맞지 않는다. §1-5(BaseEntity)만 기존 관례대로 이번 범위에서 제외하고 진행한다.
