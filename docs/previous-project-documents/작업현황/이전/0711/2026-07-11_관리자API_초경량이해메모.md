# 관리자 API §6.1~§6.3, §6.6 — 초경량 이해 메모

작성일: 2026-07-11 (형식: `docs/작업현황/설계문서/2026-07-11_초경량-이해-메모-규칙.md` 기준)

---

- API: API-ADMIN-DASHBOARD-001 GET /api/v1/admin/dashboard, API-ADMIN-STAT-001 GET /api/v1/admin/statistics
- 목적: 최근 결제 목록에 PAID 아닌 결제가 섞이는 문제 방지, 통계 count가 int overflow 위험 없이 long으로 나가게 정리(§6.1)
- 흐름: PaymentRepository.findRecentPayments에 WHERE paymentStatus='PAID' 추가 → AdminStatisticService의 (int) 캐스팅 제거, AdminStatisticResponse 필드 long 전환
- DB: 스키마 변경 없음, payment.payment_status 컬럼으로 필터링만 함
- 주의: findRecentPayments를 다른 곳에서도 쓰게 되면 "PAID만 나온다"는 전제가 깨지지 않는지 확인할 것

---

- API: API-ADMIN-DASHBOARD-001 GET /api/v1/admin/dashboard
- 목적: 대시보드 운영 목록에 최근 신고(책+리뷰 통합), 최근 희망도서 후보를 추가(§6.2, §6.3)
- 흐름: 신규 BookReportRepository/ReviewReportRepository(각각 최근 N건) → AdminDashboardService에서 합쳐 최신순 재정렬. 신규 BookRequestCandidateRepository → 후보 단위 그대로 반환
- DB: book_report/review_report/book_request_candidate 조회만, 스키마 변경 없음. 세 테이블 모두 이번에 Repository를 처음 추가함
- 주의: reportId는 book_report_id/review_report_id를 그대로 쓰므로 BOOK/REVIEW 타입 간에 값이 겹칠 수 있음(targetType으로 구분해야 함)

---

- API: 관리자 변경성 API 5종(포인트조정/쿠폰등록/쿠폰발급/도서ISBN승인/챌린지수정)
- 목적: 관리자 감사 로그(admin_audit_log)에 실제 변경 이력을 남기기 시작(§6.6)
- 흐름: 각 컨트롤러에 `@AuthenticationPrincipal CustomUserDetails` 추가 → adminMemberId를 서비스로 전달 → AdminAuditLogWriter.record(...)를 같은 트랜잭션 안에서 호출(별도 트랜잭션 안 엶 — 실패 시 본 작업도 함께 롤백)
- DB: admin_audit_log에 INSERT만 추가. 대상 테이블(member/coupon/book/challenge) 자체 스키마는 안 건드림
- 주의: 회원상태변경/공지/신고처리/희망도서처리 API는 아직 존재하지 않아 감사 로그 대상에서 빠져 있음(생기면 §9 후속 작업으로 추가)
