# REST API 작업 규칙 / 세션 운영 규칙 정리 (2026-07-10 기준)

> 목적: 지금까지의 작업 세션(`docs/작업현황/*`, `CLAUDE.local.md`, `.claude/` 설정, auto-memory)에서 실제로 어떻게 일해왔는지를 근거 기반으로 정리한 문서. 다른 세션에서 `/init`으로 `CLAUDE.md`를 다시 만들 때 참고 자료로 쓰기 위한 것이며, 규범(이렇게 해야 한다)이 아니라 **관측된 사실**(실제로 이렇게 해왔다) 중심으로 작성했다.
> 근거 문서는 각 항목 옆에 표기했다. 전체 파일을 통독하지 않고 각 문서의 목차(heading)와 관련 절만 확인했다.

---

## 0. 프로젝트 개요

- Spring Boot(4.x) 기반 REST API 백엔드 프로젝트(`com.acorn.abc`, `build.gradle`)이며 Java 17 + Gradle을 사용한다.
- Controller / Service / Repository / DTO / Domain(Entity) 계층을 기능(도메인) 단위 패키지로 분리한다 (`docs/공통문서/백엔드_공통_개발_규칙.md` 9절).
- 데이터 접근은 Spring Data JPA(`ddl-auto=validate`, 스키마는 `schema.sql`/`data.sql`로 부팅 시 자동 반영).
- **운영 DB와 테스트 DB가 분리되어 있지 않다 — 둘 다 실제 MySQL 8.x를 사용한다.** H2/Testcontainers 등 인메모리·격리 DB는 도입되어 있지 않으며, 이 때문에 실제로 테스트 격리 문제가 발생해 별도 대응 문서(`0707/2026-07-07_실DB테스트격리이슈_수정계획.md`, `0707/2026-07-07_mysql-shared-db-test-guide.md`, `0707/2026-07-07_gradle-test_카테고리_DB_임시정리_계획.md`)가 만들어졌다. 팀 공유 MySQL(한 대의 PC를 DB 서버로 삼아 LAN으로 공유)로 전환하는 방향이 확정된 상태다.
- 프런트엔드(`abc-front/`)는 React + Vite + TypeScript로 별도 구성되어 있으며 백엔드 규칙과는 독립적으로 관리된다.
- API 컨벤션(요청/응답 포맷, 에러코드, DTO 네이밍 등)은 `docs/공통문서/백엔드_공통_개발_규칙.md` 한 문서로 통일되어 있고, 이 문서가 실질적인 "헌법" 역할을 한다. ArchUnit 같은 자동화된 컨벤션 검증 테스트는 **검토만 되었고 아직 도입되지 않았다**(`0702/2026-07-02_archTest_ArchUnit의존성_추가_분석.md`) — 현재 컨벤션 준수 확인은 코드 리뷰 + `.\gradlew.bat build` 수동 확인으로 이루어진다.

## 1. REST API 작업 시작 규칙

새 API/기능 작업은 곧바로 코드를 건드리지 않고 아래 순서로 시작하는 패턴이 반복적으로 관측된다.

1. **기존 산출물 대조 검토부터 한다.** API 명세(`docs/API 명세/api-spec(final).md`), 스키마(`schema.sql`, `docs/데이터베이스/ddl/schema.sql`), 화면흐름도(`docs/화면흐름도/`)를 서로 대조해 "완전히 구현된 부분 / 대체로 맞는 부분 / 부족한 부분 / 확인이 필요한 부분"으로 나눈 **검토 보고 문서**를 먼저 만든다.
   - 근거: `0701/2026-07-01_카탈로그API_규칙-스키마-명세_검토보고.md`, `0702/2026-07-02_화면흐름도-API명세_4.2_대조검토.md`, `0702/2026-07-02_DB문서-실제DB_불일치_발견.md`.
2. **구현 착수 전 "구현계획" 문서를 별도로 작성한다.** 대상 파일, 변경 범위, 결정이 필요한 지점을 먼저 정리하고, 실제 코드 수정은 이 문서가 사용자 확인을 받은 뒤 시작한다.
   - 근거: `0706/2026-07-06_챌린지-출석-포인트-쿠폰API_구현계획.md`, `2026-07-09_쿠폰실제지급로직_구현계획.md`, `2026-07-09_fix-challenge-coupon-reward-guard_구현계획.md`.
3. **설계 선택지가 갈리는 지점은 "안 A / 안 B" 형태로 문서에 나열하고, 사용자가 확정한 뒤에만 진행한다.** 즉흥적으로 하나를 골라 구현하지 않는다.
   - 근거: `2026-07-09_PR33_5차리뷰_및_후속작업_대응계획.md`(§1-4, §6 "결정 사항, 전부 확정"), `CLAUDE.local.md`의 "구현 중 확정된 중요한 정책/결정" 절(응답 필드 안 A/B 채택 기록).
4. **새 `ErrorCode`가 필요하면 코드 작성 전에 별도의 "승인 요청" 문서를 만든다.** 구조는 "왜 필요한가 → 신규 코드 목록(표) → 추가했을 때 영향 → 승인 요청 사항" 순서로 고정되어 있다. `ErrorCode.java` 자체의 클래스 주석에도 "새로운 예외가 필요할 때는 반드시 팀장에게 보고 후 승인 받고 추가한다"고 명시되어 있다.
   - 근거: `0706/2026-07-06_ErrorCode_신규추가_승인요청.md`, `docs/작업현황/ErrorCode_신규추가_완료.md`, `src/main/java/com/acorn/abc/common/exception/ErrorCode.java` 상단 주석.
5. **조사 범위는 사용자가 지정하거나 명시적으로 언급한 파일로 제한한다.** "관련되어 보인다"는 이유로 임의로 다른 문서(예: 낡은 ERD 문서)까지 확장해서 읽지 않는다 — 실제로 이 확장 때문에 지적받은 사례가 있다.
   - 근거: auto-memory `feedback_plan_only_no_file_edits`.

## 2. 구현 규칙

- **`docs/공통문서/백엔드_공통_개발_규칙.md`을 벗어나지 않는다.** `/api/v1` prefix, 복수형 URL, Controller의 Entity 직접 반환 금지, Request DTO(`@Valid`), `ApiResponse`/`ErrorResponse` 공통 포맷, `BusinessException` + `ErrorCode`, `BaseEntity` 상속, `~Request`/`~Response`/`~SummaryResponse` 네이밍, 기능별 패키지 분리(`controller/service/dto/domain/repository`) — 이 규칙들은 `.claude/rules/backend-convention.md`와 `abc-backend-convention` 스킬에도 요약되어 실제 작업에 상시 적용된다.
- **"계획"과 "구현"은 명확히 분리된 별개의 승인 단계다.** "계획 세워줘"라는 요청은 조사와 문서 작성까지만을 의미하며, 조사 중 버그나 개선점을 발견해도 실제 소스/스키마 파일은 고치지 않는다. "진행해"와 같은 짧은 승인도 직전에 제안한 단일 단계에 대한 승인으로 좁게 해석하고, 그다음 단계(실제 코드 작성)까지 자동으로 포함한다고 확대 해석하지 않는다.
  - 근거: auto-memory `feedback_plan_only_no_file_edits` (schema.sql을 계획 단계에서 직접 수정했다가 지적받은 실제 사례 포함).
- **회귀 방어용 코드는 "도달 불가능해 보여도" 남겨두는 결정이 실제로 있었다.** 예: `claimReward()`의 `else` 분기(`CHALLENGE_REWARD_TYPE_NOT_SUPPORTED`)는 schema CHECK 제약상 실사용 도달이 불가능하지만 회귀 방어용으로 유지하기로 확정, 테스트도 가상 타입(`"UNKNOWN"`)으로 유지.
  - 근거: `CLAUDE.local.md` "구현 중 확정된 중요한 정책/결정" 절.
- **기존 서비스의 패턴을 그대로 따르고 임의로 검증을 추가하지 않는다.** 예: coupon 지급 시 재고/유효기간 추가 검증은 하지 않고 기존 `CouponService.issueCoupon()`과 동일한 패턴을 유지하기로 확정.
  - 근거: `CLAUDE.local.md` 동일 절.
- **범위 제외(scope-out) 결정은 문서에 명시적으로 남긴다.** 예: BaseEntity 미상속 정리는 이번 라운드에서 의도적으로 제외하고 별도 진행하기로 확정 — "잘 몰라서 빠뜨림"이 아니라 "알고 있고 의도적으로 미룸"임을 구분해서 기록한다.
- **병합 충돌은 파일별로 "중복인지 아닌지"부터 분석 문서로 정리한 뒤 처리 방식을 확정한다.** (유지/합치기/이름 통일 등) 실행은 사용자 확정 후에만 한다.
  - 근거: `0707/2026-07-07_병합충돌_해결계획.md`.

## 3. 검증 규칙

- **백엔드 코드를 수정하면 완료 보고 전에 `.\gradlew.bat build`를 실행해 위반 0건을 확인하는 것이 고정 규칙이다.** 여러 작업현황 문서와 `.claude/rules/backend-convention.md`에 동일하게 명시되어 있다.
- **테스트는 목/스텁이 아니라 실제 로컬(또는 팀 공유) MySQL DB에 대해 실행된다.** 이로 인해 실제로 "실DB 테스트 격리 이슈"가 발생했고, 원인 분석 → 옵션 A(테스트 전용 스키마 분리)/B(테스트 코드 격리 패턴 통일)/C(팀 공유 MySQL 전환) 비교 → 결정(C+B 병행, A 보류) 순서로 대응했다.
  - 근거: `0707/2026-07-07_실DB테스트격리이슈_수정계획.md`.
- **DB 상태에 의존하는 임시 테스트(예: 카테고리 데이터)는 실행 전 백업, 실행 후 원복 SQL을 준비해 실행 순서를 문서로 고정한다.** "테스트 전 현재 상태 확인 → 백업 테이블 생성 → 임시 비활성화 → 테스트 실행 → 원복" 순서.
  - 근거: `0707/2026-07-07_gradle-test_카테고리_DB_임시정리_계획.md`.
- **API 기능 검증은 케이스별 Swagger 수동 테스트 체크리스트 문서를 먼저 만들고 하나씩 실행해 PASS/FAIL을 기록한다.** 각 케이스는 "요청 → 기대 응답 → 실제 결과"를 남기고, 실행 전/후 DB 정리(사전 준비 SQL, 원복 SQL)를 함께 기록한다.
  - 근거: `2026-07-09_쿠폰실제지급_Swagger검증_체크리스트.md`, `2026-07-09_ChallengeRewardFailFast_검증_체크리스트.md`, `2026-07-08_AdminChallengeUpdate_검증_체크리스트.md`, `0707/2026-07-07_챌린지출석포인트쿠폰API_Swagger검증_코드수정계획.md`.
- **동시성이 관련된 기능은 Postman을 이용한 별도의 동시성 검증 계획을 세운다.**
  - 근거: `0707/2026-07-07_챌린지출석포인트쿠폰API_Postman_동시성검증_계획.md`.
- **PR 코드리뷰 대응은 "N차 코드리뷰 대응계획" 문서를 차수마다 새로 만든다.** 구조는 고정되어 있다: 리뷰 원문 요약 → 코드 확인 결과(rg로 직접 확인) → 왜 문제인지/리스크 → 수정 방안(안 A/B) → 권장 → (여러 지적사항 반복) → 결정 사항(전부 확정) → 진행 순서. 이전 차수에서 "문제 아님"으로 정정된 항목도 삭제하지 않고 "정정: 문제 아님, 확인 완료"로 이력을 남긴다.
  - 근거: `0707/2026-07-07_PR33_코드리뷰_대응계획.md` ~ `2026-07-09_PR33_5차리뷰_및_후속작업_대응계획.md` (총 5차), `0703/2026-07-03_PR22_리뷰반영_수정계획.md`.
- **컨벤션 자동 검증(ArchUnit 등)은 아직 실체가 없다.** 검토 문서는 있지만(`0702/2026-07-02_archTest_ArchUnit의존성_추가_분석.md`) `build.gradle`에 반영되지 않았으므로, "archTest"라는 표현이 다른 문서/스킬에 등장해도 실제로는 수동 검증(코드 리뷰 + 빌드)을 가리킨다.

## 4. 세션 운영 규칙

- **작업현황 문서는 날짜 기반으로 계속 누적한다.** 파일명 규칙은 `YYYY-MM-DD_주제_문서유형.md`이며, 문서유형 접미사가 사실상 표준화되어 있다: `_검토보고`, `_구현계획`, `_수정계획`, `_승인요청`, `_체크리스트`, `_대응계획`, `_원인결과검증`. 초기(0701~0707)에는 날짜 하위 폴더(`docs/작업현황/0701/` 등)를 썼고, 이후(0708~)에는 `docs/작업현황/` 바로 아래 날짜-prefix 파일로 정리되는 추세다.
- **작업 도중 결정이 바뀌거나 새 사실이 확인돼도 기존 작업현황 문서를 즉시 고치지 않는다.** 변경사항은 현재 진행 중인 계획 문서에만 반영하고, 관련 기존 문서 전체 정리는 구현이 다 끝난 뒤 한 번에 반영한다. 사용자가 "지금 바로 문서 고쳐줘"라고 명시한 경우만 예외.
  - 근거: auto-memory `feedback_doc_update_batching` (같은 지시가 최소 두 번 반복됐다고 기록됨).
- **세션 인수인계는 `CLAUDE.local.md`(로컬 전용, `.git/info/exclude`로 관리되어 git 미추적)에 남긴다.** 형식은 고정되어 있다: 작성일 / 현재 브랜치 / 현재 작업 목표 / 지금까지 완료한 작업 / 아직 완료하지 못한 작업 / 수정한 주요 파일 / 실행한 테스트와 결과 / 발견했지만 수정하지 않은 문제 / 다음 세션에서 가장 먼저 할 작업 / 구현 중 확정된 중요한 정책·결정 / 현재 git status·주의사항. **이 문서는 현재 상태의 스냅샷이며 과거 이력을 계속 쌓는 문서가 아니다** — 매 세션 최신 상태로 다시 쓴다.
- **커밋/PR 메시지는 type은 영어(feat/fix/docs/refactor/test/chore), 설명 문장은 한국어로 고정한다.** 실제 생성은 `git-message-standardizer` 스킬로 초안만 만들고, `git commit`/`gh pr create` 자체는 사용자 승인 후 별도 단계로 실행한다 — 초안 작성과 실제 게시(예: `gh pr comment`)가 분리된 별개의 완료 조건으로 취급된다(초안만 쓰고 게시를 잊는 경우가 실제로 있었음, `CLAUDE.local.md` "아직 완료하지 못한 작업" 참고).
- **브랜치 전략은 `main`(운영/최종) + `feature/*`(기능별) + PR이다.** PR 전에는 최소한 로컬 빌드/테스트를 실행하고, 공통 응답/에러 응답/URL 규칙 준수 여부를 확인한다. Merge는 PR을 통해서만 이루어진다(직접 push 금지가 관측됨 — 커밋 로그가 전부 "Merge pull request #N" 형태).
- **사전 확인 없이 자동 실행하지 않는 액션이 명확히 구분되어 있다:** 파일/폴더 삭제, `git clean`/`git reset --hard`/force push, `git commit`/`push`/`gh pr create`/merge/approve, 의존성·빌드 설정 변경, secret/.env/토큰 원문 열람(존재 여부·경로·키 이름만 보고). 반대로 조사성 명령(`rg`, `git status`, `git diff`), 테스트/빌드 실행은 매번 허락을 구하지 않고 자동 진행한다.
  - 근거: `.claude/settings.local.json`의 허용 패턴 목록(테스트/빌드/rg/git status 계열은 폭넓게 허용, `git commit -m '`/`git push`/`gh api` 등은 개별 승인 흔적).
- **범위가 애매하면 넓게 추측해서 고치지 않고 "범위확인필요"로 먼저 보고한다.**

## 참고: 이 문서 자체의 위치

이 문서는 과거 작업현황 문서·`CLAUDE.local.md`·`.claude/` 설정·auto-memory를 종합해 만든 "프로세스 회고" 문서이며, 특정 기능 구현 계획서가 아니다. 향후 `/init`으로 `CLAUDE.md`를 재생성할 때 "이 프로젝트에서 실제로 통용되는 작업 프로세스"를 넣는 근거 자료로 사용하되, 여기 적힌 내용도 시간이 지나면 바뀔 수 있으므로 재사용 시점의 `docs/작업현황/` 최신 문서와 대조 확인할 것.
