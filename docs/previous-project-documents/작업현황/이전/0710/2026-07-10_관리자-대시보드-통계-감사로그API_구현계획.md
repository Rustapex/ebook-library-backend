# 관리자 대시보드 / 통계 관리 / 감사 로그 API 구현계획 (2026-07-10)

> 범위: 관리자 API 중 대시보드(A-001), 통계 관리(A-016), 관리자 감사 로그(A-017) 3개 화면과 그에 연동되는 API-ADMIN-DASHBOARD-001 / API-ADMIN-STAT-001 / API-ADMIN-AUDIT-001 3개 API.
> 이 문서는 계획 문서다. 조사만 했고 실제 소스/스키마 파일은 수정하지 않았다. §4의 결정 사항은 2026-07-10에 전부 확정됐다(안 A 단계적 적용/최근 결제만 N=5/`@Validated`+`@Pattern`/`review`·`request` 도메인 제외) — 실제 코드 작성은 §6 작업 순서대로 진행하며, 확정 과정에서 새로 생긴 후속 과제는 §9에 정리했다.
> 사전 확인: 현재 브랜치 `main`, `git status --short --branch` 결과 미커밋 변경 없음(clean).

## 2. 관련 테이블 (런타임 스키마 확인 결과)

- `admin_statistic` — 기간/나이대별 사전 집계 KPI. `UNIQUE(period_type, period_start_date, age_band)`, `CHECK period_type IN (WEEKLY, MONTHLY, YEARLY, TOTAL)`, `CHECK age_band IN (ALL, 10S, 20S, 30S, 40S, 50_PLUS)`.
- `admin_audit_log` — 조회 전용 로그. `admin_member_id` FK, `action_type`/`target_type`/`target_id`/`created_at` 인덱스가 이미 존재(조회 성능 고려된 상태).
- `user_reading_statistic` — 개인별 독서 통계(`API-STAT-001`, "내 독서 통계 조회"용). 이번 admin 범위는 아니지만 `admin_statistic`과 구조가 같고 같은 미해결 이슈(§3)를 공유해 참고로 기록.
- 대시보드는 위 표 외에 `member`, `book`, `book_rental`, `payment`, `review`, `book_report`, `review_report`, `book_request` 원본 테이블도 직접 참조.
- `docs/데이터베이스/ddl/schema.sql`(설계 문서)과 `src/main/resources/schema.sql`(런타임)을 대조한 결과 세 테이블 모두 컬럼/제약조건이 일치— 불일치 없음.

## 3. 현재 구현 상태 조사 결과

- `com.acorn.abc.statistic` 패키지에는 `domain`만 있다(`AdminAuditLog`, `AdminStatistic`, `UserReadingStatistic`) — `repository`/`service`/`controller`가 전혀 없다.
- `com.acorn.abc.admin` 패키지는 `book`/`challenge`/`coupon`/`member`만 있고 통계·대시보드·감사로그용 하위 패키지가 없다.
- 기존 admin API 패턴(`AdminChallengeController` 확인 결과): 별도 `AdminXxxService`를 만들지 않고 기존 도메인 서비스(`ChallengeService`)에 관리자용 메서드를 추가해 재사용한다. `statistic` 도메인은 재사용할 기존 서비스가 없으므로 이번엔 신규 서비스를 만들어야 한다.
- **대시보드가 참조하는 `review`(`BookReport`, `ReviewReport`) / `request`(`BookRequest`) 도메인은 Entity만 있고 Repository조차 없다.** "최근 신고", "최근 희망도서" 목록을 만들려면 이 엔티티들의 최소 Repository부터 추가해야 한다 — 이번 조사에서 새로 확인된 선행 의존성이다.
- `SecurityConfig`에 `/api/v1/admin/**` → `hasRole("ADMIN")` 전역 규칙이 이미 있어(다른 admin 컨트롤러와 동일), 컨트롤러에 별도 `@PreAuthorize`는 필요 없다.
- `ErrorCode.java`에 통계/감사로그/대시보드 전용 코드가 없다. 셋 다 조회 전용 GET API라 새 `ErrorCode`가 필요 없어 보이지만, 잘못된 `periodType`/`ageBand` 처리 방식은 §4-3에서 확정이 필요하다.
- **`admin_statistic`/`user_reading_statistic`을 채우는 배치·스케줄러가 현재 전혀 없다.** `batch` 패키지는 도서 ISBN 승인 전용이라 무관하다. 즉 두 통계 테이블은 스키마만 있고 아무도 쓰지 않는 상태다.

## 4. 결정이 필요한 사항 (구현 착수 전 확정 필요)

### 4-1. `admin_statistic`을 채우는 방식 — **확정(2026-07-10): 안 A(배치), 단계적으로 진행**

- **1단계(이번 범위)**: 배치는 `TOTAL` + `ALL`(전체 기간·전체 나이대) 딱 한 조합만 채운다. 대시보드(A-001)의 KPI 카드는 이 한 줄로 충분히 채울 수 있다.
- **2단계(후속, 이번 범위 아님)**: `WEEKLY`/`MONTHLY`/`YEARLY`와 나이대별(`10S`~`50_PLUS`) 조합을 추가한다. A-016 통계 관리 화면(그래프, 나이대별 통계)에 필요하며, A-001 대시보드에는 필수가 아니다.
- 이 프로젝트에 `@Scheduled`/`@EnableScheduling`이 전혀 없다는 것을 확인했다(grep 결과 0건) — 이번 작업이 이 코드베이스 최초의 스케줄링 컴포넌트가 된다.
- **미확정 항목(구현 시점에 재논의)**: 2단계 데이터가 아직 없는 상태에서 A-016이 `WEEKLY` 등 아직 채워지지 않은 조합을 조회하면 "해당 조합 행 없음" 상황이 생긴다. 이때 응답을 빈 통계(0으로 채운 응답)로 줄지 404로 줄지는 아직 정하지 않았다 — §9(남은 작업) 참고.

### 4-2. 대시보드 "최근 N건" 목록 — **확정(2026-07-10)**

- 이번 범위에서는 "최근 결제"만 구현한다. "최근 신고"/"최근 희망도서"는 §4-4에 따라 `review`/`request` 도메인 Repository가 없어 이번 범위에서 제외한다.
- 정렬: `ORDER BY paid_at DESC`(`Payment.paidAt` 기준, 실제 결제 발생 시각).
- 개수: 고정 N=5, 페이징 파라미터 없이 `PageRequest.of(0, 5)`로 상위 5건만 조회(`ReadingProgressRepository.findRecentByMemberId`/`BookService`의 `PageRequest.of(0, limit)` 상위 N건 조회 패턴과 동일한 스타일 재사용).

### 4-3. `periodType`/`ageBand` 잘못된 값 처리 — **확정(2026-07-10): 안 2**

- `String @RequestParam` + 컨트롤러 클래스 레벨 `@Validated` + 파라미터에 `@Pattern(regexp = "WEEKLY|MONTHLY|YEARLY|TOTAL", ...)` / `@Pattern(regexp = "ALL|10S|20S|30S|40S|50_PLUS", ...)`.
- `AdminChallengeController`가 `page`/`size`에 이미 쓰는 `@Validated` + 제약 애노테이션 스타일을 그대로 재사용한다. 위반 시 `ConstraintViolationException` → 기존 `GlobalExceptionHandler`가 이미 400 + `VALIDATION_ERROR`로 처리(신규 `ErrorCode` 불필요).
- 참고(기존 한계, 이번 범위에서 고치지 않음): `ConstraintViolationException` 핸들러는 필드별 메시지를 응답 body에 담지 않고 `"입력값을 확인해주세요."`만 내려준다.

### 4-4. Repository 없는 선행 도메인 처리 범위 — **확정(2026-07-10): 이번 범위 제외**

`BookReport`/`ReviewReport`/`BookRequest`의 Repository 추가는 이번 작업 범위에서 제외하고 별도 작업으로 진행하기로 확정했다. 이번 라운드의 대시보드(API-ADMIN-DASHBOARD-001) 구현에서는 "최근 신고", "최근 희망도서" 목록을 이 세 엔티티에 의존하지 않는 범위로 좁히거나, 해당 위젯을 이번 구현 대상에서 제외한다(§5 구현 대상 파일에서 이 제약을 반영해 조정).

## 5. 구현 대상 파일 (§4 확정 반영)

- 신규: `admin/statistic/controller/` 하위 컨트롤러 (대시보드/통계/감사로그 3개 API)
- 신규: `statistic/repository/AdminStatisticRepository.java`, `AdminAuditLogRepository.java`
- 신규: `statistic/service/` 하위 서비스 — 통계 배치용 집계 로직(1단계: `TOTAL`+`ALL`만) 포함
- 신규: 배치 컴포넌트 — `admin_statistic`의 `TOTAL`+`ALL` 행을 채우는 `@Scheduled` 잡(이 코드베이스 최초의 스케줄링 컴포넌트, `@EnableScheduling` 설정 추가 필요)
- 신규: `PaymentRepository`에 최근 결제 조회 메서드 추가 — `ORDER BY paid_at DESC` + `Pageable`(`findRecentBy...` 스타일)
- 신규 DTO: 대시보드 응답(최근 결제 포함), 통계 응답, 감사 로그 목록 응답 등 (`~Response`/`~SummaryResponse` 네이밍 규칙 적용)
- 이번 범위 제외(§4-4): `review/repository/BookReportRepository.java`, `ReviewReportRepository.java`, `request/repository/BookRequestRepository.java`, 그리고 대시보드의 "최근 신고"/"최근 희망도서" 위젯

## 6. 작업 순서

1. 배치 컴포넌트(`admin_statistic`의 `TOTAL`+`ALL` 집계, `@EnableScheduling` 추가) 구현.
2. 감사 로그(API-ADMIN-AUDIT-001) — 조회 전용이고 인덱스가 이미 있어 셋 중 가장 단순, 먼저 구현.
3. 통계 관리(API-ADMIN-STAT-001) — 1단계 배치가 채운 `TOTAL`+`ALL` 조회 기준으로 구현. `periodType`/`ageBand`는 §4-3(안 2)에 따라 `@Validated`+`@Pattern`으로 검증.
4. 대시보드(API-ADMIN-DASHBOARD-001) — `admin_statistic`(`TOTAL`+`ALL`) 조회 + `PaymentRepository`의 "최근 결제 5건" 조합.
5. 단위 테스트 작성, `.\gradlew.bat build`로 위반 0건 확인.
6. Swagger 수동 검증 체크리스트를 별도 문서로 작성한 뒤 실행.

## 7. 테스트/검증 계획 (착수 시 별도 체크리스트 문서로 구체화)

- 정상 조회(200), 잘못된 `periodType`/`ageBand`(§4-3: `@Pattern` 위반 → 400 VALIDATION_ERROR) 케이스.
- `TOTAL`+`ALL` 외 조합(예: `WEEKLY`) 조회 시 현재 동작 확인 — 배치가 아직 안 채운 조합이므로 §9의 미확정 응답 정책과 연결되는 케이스임을 인지하고 기록.
- 관리자 권한 없이 호출 시 403 확인(`SecurityConfig`의 `hasRole(ADMIN)` 규칙에 의존).
- 감사 로그는 조회 전용이므로 수정/삭제 API가 실제로 없는지 테스트로도 확인.
- 대시보드 "최근 결제" 5건이 `paid_at` 내림차순으로 오는지 확인.

## 8. 위험/가정

- 1단계 배치가 `TOTAL`+`ALL`만 채우므로, A-016 통계 관리 화면에서 `WEEKLY`/`MONTHLY`/`YEARLY`나 나이대별 조회를 시도하면 데이터가 없다 — 화면 자체는 이번 범위가 아니지만 API를 먼저 붙이는 프런트가 있다면 혼선이 생길 수 있다.
- `review`/`request` 도메인에 Repository가 전혀 없다는 사실은 이번 조사에서 새로 확인된 것이며, 대시보드의 "최근 신고"/"최근 희망도서" 위젯은 이번 범위에서 아예 빠진다(§4-4).

## 9. 남은 작업 (후속 작업, 이번 범위 아님)

이번 라운드(§5, §6) 구현이 끝난 뒤에도 남는 작업들이다. 별도 계획 문서로 착수 시점에 다시 다룬다.

1. **통계 배치 2단계**: `admin_statistic`에 `WEEKLY`/`MONTHLY`/`YEARLY` 기간과 `10S`~`50_PLUS` 나이대별 조합을 채우는 배치 확장(§4-1 2단계). A-016 통계 관리 화면(그래프, 나이대별 통계, 환경 지표)이 이 데이터를 필요로 한다.
2. **미채워진 통계 조합 조회 시 응답 정책 확정**: 배치가 아직 안 채운 `(periodType, ageBand)` 조합을 API-ADMIN-STAT-001로 조회했을 때 빈 통계(0으로 채운 응답)를 줄지 404를 줄지 — §4-1에서 미확정으로 남긴 항목, 2단계 배치 착수 전(또는 착수와 함께) 확정 필요.
3. **`review`/`request` 도메인 Repository 추가**: `BookReportRepository`, `ReviewReportRepository`, `BookRequestRepository`(§4-4). 이게 끝나야 대시보드의 "최근 신고", "최근 희망도서" 위젯을 API-ADMIN-DASHBOARD-001에 추가할 수 있다.
4. **`user_reading_statistic`(개인별 독서 통계, API-STAT-001) 처리 방식**: 이번 계획은 관리자용 `admin_statistic`만 다뤘다. 회원용 `user_reading_statistic`을 배치로 채울지, 언제 채울지는 이번 범위에서 다루지 않았고 별도로 정해야 한다.
