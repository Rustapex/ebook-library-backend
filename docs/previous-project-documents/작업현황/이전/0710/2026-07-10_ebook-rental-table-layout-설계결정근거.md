# ebook-rental-table-layout 설계 결정 근거

## 문서 목적

이 문서는 `ebook-rental-table-layout-feedback-reflected.xlsx`를 만들 때 적용한 주요 ERD/DB 설계 결정의 근거를 정리한 문서이다.

## 기준 자료

| 구분 | 확인 내용 | 반영 방향 |
|---|---|---|
| 멘토 피드백 | 전체 대문자, 정수형 PK 제외, 회원 식별자 단일화, 상태명 축약, 날짜/일시 명칭 정리 | 검토용 ERD 스프레드시트의 물리명과 자료형에 반영 |
| 기존 계획서 | 42개 테이블 유지, 원본 시트 구조 유지, 다음 단계 xlsx는 복제본 생성 | 원본 파일은 보존하고 반영본 xlsx를 새 파일로 생성 |
| DDL/DML/API/화면설계 | 기존 명칭, 상태값, 회원/쿠폰/비밀번호 재설정 정책 확인 | xlsx 반영 시 영향 항목을 식별하는 참고 자료로 사용 |
| RFC 9562 UUID | UUID는 128비트 식별자이며 문자열 표현은 하이픈 포함 36자 형태가 일반적임 | PK/FK 검토안은 `CHAR(36)` UUID 문자열로 통일 |
| Jakarta Persistence/Hibernate | UUID 식별자와 `GenerationType.UUID`를 지원함 | UUID 생성 주체는 애플리케이션 또는 JPA로 둠 |
| MySQL 문자/바이너리 타입 | `CHAR`, `VARCHAR`, `BINARY`는 저장 방식과 길이 특성이 다름 | 가독성과 멘토 피드백 반영을 우선하여 `CHAR(36)` 선택 |
| MySQL InnoDB 인덱스 | 클러스터형 PK와 보조 인덱스는 PK 크기와 삽입 패턴의 영향을 받음 | UUID의 저장 공간/인덱스 단점은 근거에 명시 |
| MySQL UUID 함수 | `UUID_TO_BIN`, `BIN_TO_UUID`로 UUID를 `BINARY(16)`에 저장할 수 있음 | 운영 효율 대안은 인정하되 이번 반영본은 `CHAR(36)` 유지 |
| RFC 5321 이메일 길이 | 이메일 주소는 실무적으로 254자 한도가 널리 사용됨 | `EMAIL VARCHAR(254)`로 계획 |
| Google OpenID Connect | Google 계정의 안정 식별자는 이메일이 아니라 `sub`임 | 회원 테이블에 `GOOGLE_SUB`만 추가하고 별도 인증 테이블은 만들지 않음 |
| OWASP Password Storage | 원문 비밀번호 저장 금지, 안전한 단방향 해시 저장 필요 | 논리명은 `회원 비밀번호`, 물리명은 `MEMBER_PW`, 실제 저장값은 해시라는 정책을 비고에 기록 |
| MySQL 날짜/숫자 타입 | 날짜는 `DATE`, 날짜시간은 `DATETIME`, 금액/비율은 적절한 숫자 타입 사용 | `_DT`, `_DTTM`, `_AMT`, `_RATE`, `_CNT` 기준 적용 |
| ISBN 자료 | ISBN-13은 13자리 식별자이며 산술 계산 대상이 아님 | `ISBN CHAR(13)` 및 `UNIQUE` 적용 |

## 주요 설계 결정

| 결정 항목        | 결정                                         | 근거                                                     | 단점/주의                                                  |
| ------------ | ------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------ |
| PK/FK        | 모든 단일 PK와 UUID FK를 `CHAR(36)`으로 변경         | 정수형 PK 제외 피드백, UUID 지원, 외부 추측 어려움                      | `BIGINT`보다 저장 공간과 인덱스 크기가 큼                            |
| 복합 PK        | N:M 매핑 테이블은 복합키 유지, 구성 FK만 `CHAR(36)`      | 관계 테이블의 자연스러운 중복 방지 구조 유지                              | FK 컬럼 길이가 커짐                                           |
| `LOGIN_ID`   | 삭제                                         | 회원 식별자 단일화 피드백                                         | 기존 아이디 로그인/아이디 찾기 개념은 계정 확인 정책으로 재해석 필요                |
| 로그인 식별자      | 일반 로그인은 `EMAIL` 사용                         | `LOGIN_ID` 삭제 후 사용자가 입력할 식별자 필요                        | 이메일 변경 불가 정책 및 검증 정책 필요                                |
| 계정 확인        | 기존 아이디 찾기는 계정 확인으로 정리                      | `LOGIN_ID`가 없으면 조회할 아이디가 없으므로 이메일 인증 기반 계정 확인이 더 자연스러움 | 화면 문구와 API 명칭은 별도 단계에서 정리 필요                           |
| 이메일 정규화      | `EMAIL_NORM` 컬럼은 두지 않음                     | 테이블 속성 과다 증가 방지, 검토 ERD 단순화                            | 대소문자 비교 정책은 애플리케이션 검증/비고로 관리해야 함                       |
| Google 로그인   | `GOOGLE_SUB` 하나만 둠                         | Google OIDC의 안정 식별자는 `sub`                             | 여러 OAuth 제공자를 지원하려면 별도 인증 테이블 또는 provider 컬럼이 필요할 수 있음 |
| 회원 비밀번호      | `MEMBER_PW VARCHAR(255)`                   | 업무 논리명은 회원 비밀번호가 명확함                                   | 실제 저장값은 원문이 아니라 안전한 해시여야 함                             |
| 상태 suffix    | 상태 컬럼은 `_ST`로 통일                           | 멘토의 축약 요구와 내부 표준단어 사전 반영                               | 국제 표준 강제 약어는 아니므로 문서 내부 일관성이 중요                        |
| 날짜/일시 suffix | 날짜는 `_DT`, 날짜시간은 `_DTTM`                   | 시간 포함 여부를 물리명에서 구분                                     | 기존 `_AT`, `_DATE`와 명칭 차이가 생김                           |
| 관리자 여부       | `ADMIN_YN CHAR(1)`                         | 단순 관리자 구분은 Y/N으로 충분                                    | 다중 역할/권한 체계가 필요하면 별도 역할 설계 필요                          |
| 성별 코드        | `GENDER_CD CHAR(1)` nullable, 허용값 `M`, `F` | 사용자가 결정한 허용값과 비필수 정책 반영                                | 기타/미응답을 코드로 구분하지 않고 NULL로 표현                           |
| 회원 물리 삭제     | 하지 않음                                      | 탈퇴 상태와 비식별화 일시로 관리                                     | 개인정보 처리 정책은 별도 검토 필요                                   |
| 비밀번호 재설정 코드  | 기존 시트 유지                                   | 피드백 대상이며 기존 구조가 있으므로 삭제하지 않음                           | final API 범위와 다를 수 있어 비고 처리 필요                         |
| 쿠폰 만료        | 쿠폰 자체는 유지, 만료 정책 컬럼만 제거                    | 사용자가 쿠폰 삭제가 아니라 쿠폰 만료 없음으로 결정                          | 만료 정책이 생기면 쿠폰/회원쿠폰 구조 재검토 필요                           |
| ISBN         | `ISBN CHAR(13)`                            | ISBN은 계산용 숫자가 아닌 고정 길이 식별자                             | ISBN-10 또는 외부 API의 다른 형식은 별도 변환 필요                     |

## xlsx 반영 기준

- 원본 workbook은 덮어쓰지 않는다.
- 반영본 파일명은 `ebook-rental-table-layout-feedback-reflected.xlsx`이다.
- 42개 시트, 시트명, 시트 순서, 레이아웃은 유지한다.
- 추가 시트를 만들지 않는다.
- 근거는 이 markdown 문서에만 남긴다.
- 비밀번호 재설정 코드는 기존 시트 하나를 수정한다.
- 컬럼명은 `UPPER_SNAKE_CASE`를 사용한다.
- PK/FK의 `AUTO_INCREMENT`, `UNSIGNED`, 정수형 PK/FK는 제거한다.
- CHECK 제약조건은 변경 후 컬럼명을 참조하도록 작성한다.
- 쿠폰은 유지하되 쿠폰 만료 관련 컬럼은 제외한다.

## 향후 설명이 필요한 질문

1. 왜 `BIGINT` 대신 UUID를 사용하는가?
2. 왜 `CHAR(36)`을 사용하고 `BINARY(16)`을 사용하지 않았는가?
3. UUID PK의 인덱스 단점은 무엇인가?
4. `LOGIN_ID` 삭제 후 사용자는 무엇으로 로그인하는가?
5. 기존 아이디 찾기를 왜 계정 확인으로 바꾸는가?
6. 왜 `EMAIL_NORM`을 실제 컬럼으로 두지 않았는가?
7. Google 로그인에 왜 `GOOGLE_SUB`만 두었는가?
8. `MEMBER_PW`라는 명칭이 원문 저장으로 오해되지 않게 하려면 무엇을 설명해야 하는가?
9. 왜 `STATUS` 대신 `_ST`를 사용하는가?
10. 왜 쿠폰은 유지하면서 만료 정책만 제거했는가?
