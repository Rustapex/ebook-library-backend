# CLAUDE.md 재작성용 참고자료 — 기준 문서 / 작업 규칙 정리 (2026-07-10)

> 이 문서의 절 구성(프로젝트 개요 / 기준 문서 / 문서 우선순위 / REST API 작업 시작 규칙 / 구현 규칙 / 검증 규칙 / 세션 운영 규칙)은 별도로 제공된 초안 파일의 목차 구조만 참고했다. **그 초안 파일의 본문 내용은 사용하지 않았다** — 각 절의 실제 내용은 이 프로젝트의 `docs/작업현황/*`, `CLAUDE.local.md`, `.claude/` 설정, auto-memory를 다시 근거로 확인해 채운 것이다. 근거가 확인되지 않은 일반론(예: 초안에 있던 "테스트에서는 H2 사용 가능")은 이 프로젝트의 실제 사실과 다르므로 넣지 않았다.
> 목적: 다른 세션에서 `/init`으로 `CLAUDE.md`를 다시 만들 때, "이 프로젝트가 실제로 참고하는 문서가 무엇이고 어떤 순서로 일해왔는가"를 근거와 함께 보여주는 자료로 쓴다.

## 프로젝트 개요

- Spring Boot(4.x) 기반 REST API 프로젝트(`com.acorn.abc`), Java 17 + Gradle(`build.gradle`).
- Controller / Service / Repository / DTO / Domain(Entity)을 도메인 패키지 단위로 분리(`docs/공통문서/백엔드_공통_개발_규칙.md` 9절 — 실제 `src/main/java/com/acorn/abc/*` 구조와 일치).
- 데이터 접근은 Spring Data JPA, 스키마는 `src/main/resources/schema.sql`/`data.sql`을 부팅 시 자동 반영(`spring.jpa.hibernate.ddl-auto=validate`).
- **운영 DB와 테스트 DB가 분리돼 있지 않다 — 둘 다 실제 MySQL 8.x다.** H2/Testcontainers는 쓰지 않는다. 이 구성 때문에 실제로 테스트 격리 문제가 발생했고(`docs/작업현황/0707/2026-07-07_실DB테스트격리이슈_수정계획.md`), 한 대의 PC를 DB 서버로 삼아 팀이 공유하는 방식(`docs/작업현황/0707/2026-07-07_mysql-shared-db-test-guide.md`)으로 대응 중이다.
- 프런트엔드(`abc-front/`)는 React + Vite + TypeScript로 별도 관리되며 백엔드 규칙과 독립적이다.
- 컨벤션 자동 검증(ArchUnit 등)은 검토만 됐고 아직 미도입(`docs/작업현황/0702/2026-07-02_archTest_ArchUnit의존성_추가_분석.md`) — 현재는 코드 리뷰 + `.\gradlew.bat build` 수동 확인으로 대체.

## 문서 우선순위

충돌이 실제로 발생했던 사례를 근거로 정리한 우선순위다.

- **런타임 DB 제약조건(`src/main/resources/schema.sql`)이 설계 문서(`docs/데이터베이스/ddl/schema.sql`, ERD)보다 우선한다.** 다만 둘이 다르면 조용히 런타임 쪽으로 넘기지 않고 불일치 자체를 별도 문서로 먼저 보고한다.
  - 근거: `docs/작업현황/0702/2026-07-02_DB문서-실제DB_불일치_발견.md`.
- **공통 구현 규칙은 `docs/공통문서/백엔드_공통_개발_규칙.md`가 원본이고, `.claude/rules/backend-convention.md`는 요약본이다.** 두 문서가 어긋나면 원본이 기준이라고 `.claude/rules/backend-convention.md` 자체에 명시돼 있다.
- **API URL/Method/요청·응답/상태코드는 `docs/API 명세/api-spec(final).md`를 기준으로 실제 구현과 대조 검토한다.** 명세와 구현이 다르면 임의로 구현에 맞춰 정리하지 않고 차이를 먼저 보고한다(예: 카탈로그 API 검토보고의 "이상한 점/확인이 필요한 부분" 절).
- **문서 간 충돌은 하나를 임의로 골라 진행하지 않는다.** 영향 범위를 먼저 정리해 사용자에게 보고하고, 결정이 난 뒤에만 진행한다 — ErrorCode 승인 요청, PR 코드리뷰 대응계획, 병합 충돌 분석 문서가 모두 이 패턴(원인 분석 → 안 A/B → 사용자 확정 → 실행)을 반복적으로 따른다.

## REST API 작업 시작 규칙

실제로 관측되는 시작 순서다.

1. `CLAUDE.local.md`의 `Current handoff`(현재 브랜치, 현재 작업 목표, 완료/미완료 작업)를 먼저 확인한다 — 이 파일은 매 세션 갱신되는 스냅샷이라 과거 이력이 아니라 "지금" 기준으로 읽어야 한다.
2. 이번 작업과 관련된 화면흐름도/API 명세/스키마를 대조해 "이미 구현된 부분 / 대체로 맞는 부분 / 부족한 부분 / 확인 필요한 부분"으로 나눈 검토 문서를 먼저 만든다.
   - 근거: `docs/작업현황/0701/2026-07-01_카탈로그API_규칙-스키마-명세_검토보고.md`, `docs/작업현황/0702/2026-07-02_화면흐름도-API명세_4.2_대조검토.md`.
3. 구현 착수 전에 "구현계획" 문서로 대상 파일, 변경 범위, 결정 필요 사항을 먼저 정리한다. 이 단계에서는 실제 소스/스키마 파일을 건드리지 않는다.
   - 근거: `docs/작업현황/2026-07-09_쿠폰실제지급로직_구현계획.md`, auto-memory `feedback_plan_only_no_file_edits`.
4. 설계 선택지가 갈리면 "안 A/안 B"로 문서에 나열하고 사용자 확정 후에만 진행한다.
5. 새 `ErrorCode`가 필요하면 코드 작성 전에 "왜 필요한가 → 신규 코드 목록 → 영향 → 승인 요청 사항" 구조의 승인 요청 문서를 먼저 만든다(`ErrorCode.java` 클래스 주석에도 동일하게 명시).
   - 근거: `docs/작업현황/0706/2026-07-06_ErrorCode_신규추가_승인요청.md`.
6. 조사 범위는 사용자가 지정했거나 명시적으로 언급한 파일로 제한하고, 관련돼 보인다는 이유로 임의로 다른 문서(특히 오래된 설계 문서)까지 확장해서 읽지 않는다.
7. 대용량 문서는 통째로 읽지 않고 `rg`로 API ID/화면 ID/URL/테이블명 등 키워드를 먼저 찾아 필요한 범위만 읽는다(`targeted-file-reading` 스킬).

## 구현 규칙

- `docs/공통문서/백엔드_공통_개발_규칙.md`를 벗어나지 않는다: `/api/v1` prefix, 복수형 URL, Controller는 Entity 대신 Response DTO 반환, Request DTO(`@Valid`), `ApiResponse`/`ErrorResponse` 공통 포맷, `BusinessException`+`ErrorCode`, `BaseEntity` 상속, `~Request`/`~Response`/`~SummaryResponse` 네이밍.
- "계획"과 "구현"은 별개의 승인 단계다. "계획 세워줘"라는 요청에는 조사·문서 작성까지만 하고, 조사 중 발견한 버그·개선점이 있어도 실제 파일은 고치지 않는다. 짧은 승인("진행해")도 직전 제안 범위로 좁게 해석한다.
  - 근거: auto-memory `feedback_plan_only_no_file_edits`(schema.sql을 계획 단계에서 직접 고쳤다가 지적받은 실제 사례 포함).
- Enum/상태값이 DB `CHECK` 제약조건과 연동돼 있으면, 그 제약이 애플리케이션 코드의 방어 로직 도달 가능성을 바꾼다는 점을 실제로 확인하고 반영한다. 예: `claimReward()`의 `else` 분기(`CHALLENGE_REWARD_TYPE_NOT_SUPPORTED`)는 schema `CHECK` 제약상 실사용으로는 도달 불가능하지만, 회귀 방어용으로 남기고 테스트도 가상 타입(`"UNKNOWN"`)으로 유지하기로 확정했다.
  - 근거: `CLAUDE.local.md` "구현 중 확정된 중요한 정책/결정" 절, `docs/작업현황/2026-07-09_PR33_5차리뷰_및_후속작업_대응계획.md` §3.
- 동시 요청으로 인한 중복 지급/중복 생성 가능성은 실제로 별도 검증 대상이었다(출석/포인트/쿠폰 도메인의 Postman 동시성 검증).
  - 근거: `docs/작업현황/0707/2026-07-07_챌린지출석포인트쿠폰API_Postman_동시성검증_계획.md`.
- 범위 제외(scope-out) 결정은 "몰라서 빠뜨림"과 구분되도록 문서에 명시적으로 남긴다. 예: BaseEntity 미상속 정리는 이번 라운드에서 의도적으로 제외하고 별도 진행하기로 확정.
- 병합 충돌은 파일별로 "중복인지 아닌지"부터 분석 문서로 정리하고, 처리 방식(유지/합치기/이름 통일)을 사용자 확정 후 실행한다.
  - 근거: `docs/작업현황/0707/2026-07-07_병합충돌_해결계획.md`.
- 현재 작업 범위와 무관한 파일/코드는 손대지 않는다(위 "계획 세워줘" 사례와 동일 원칙).

## 검증 규칙

- 백엔드 코드를 수정하면 완료 보고 전 `.\gradlew.bat build`로 위반 0건을 확인하는 것이 고정 규칙이다.
- 테스트는 실제(로컬 또는 팀 공유) MySQL DB에 대해 실행되며, 목/스텁 DB가 아니다. 이 때문에 실제 테스트 격리 문제가 발생했고, 원인 분석 → 옵션 비교(전용 스키마 분리 / 테스트 코드 격리 패턴 통일 / 팀 공유 MySQL 전환) → 결정까지 문서로 남겼다.
  - 근거: `docs/작업현황/0707/2026-07-07_실DB테스트격리이슈_수정계획.md`.
- DB 상태에 의존하는 임시 테스트는 "현재 상태 확인 → 백업 → 임시 조작 → 테스트 실행 → 원복" 순서를 SQL로 고정해 문서화한다.
  - 근거: `docs/작업현황/0707/2026-07-07_gradle-test_카테고리_DB_임시정리_계획.md`.
- 신규/변경 API 기능은 케이스별 Swagger 수동 테스트 체크리스트를 먼저 작성하고(정상 응답/잘못된 요청/존재하지 않는 리소스/이미 처리된 요청 등 케이스 구분), 하나씩 실행해 PASS/FAIL과 실제 결과(응답 JSON, DB 조회 결과)를 남긴다. 실행 전/후 DB 정리용 SQL도 함께 준비한다.
  - 근거: `docs/작업현황/2026-07-09_쿠폰실제지급_Swagger검증_체크리스트.md`, `docs/작업현황/2026-07-09_ChallengeRewardFailFast_검증_체크리스트.md`.
- 동시성이 걸린 기능은 Postman으로 별도 동시 요청 검증 계획을 세운다.
- PR 코드리뷰 대응은 차수별 문서(리뷰 원문 요약 → 코드 확인 → 원인/리스크 → 수정 방안 안 A/B → 권장 → 결정 사항 → 진행 순서)로 처리하며, 이전 차수에서 "문제 아님"으로 정정된 항목도 지우지 않고 "정정: 문제 아님, 확인 완료"로 이력을 남긴다.
  - 근거: `docs/작업현황/0707/2026-07-07_PR33_코드리뷰_대응계획.md` ~ `docs/작업현황/2026-07-09_PR33_5차리뷰_및_후속작업_대응계획.md`(5차분).
- 컨벤션 자동 검증(ArchUnit)은 미도입 상태이므로, "검증했다"고 보고할 때 자동 검증과 수동 검증(리뷰+빌드)을 구분해서 표현한다.
- 실행하지 못한 테스트는 실행한 것처럼 보고하지 않는다 — 실행 못 한 이유와 수동으로 확인해야 할 항목을 분리해서 보고하는 방식이 검증 체크리스트 문서들에서 일관되게 관측된다.

## 세션 운영 규칙

- 작업현황 문서는 `docs/작업현황/YYYY-MM-DD_주제_문서유형.md` 형식으로 날짜 기반 누적한다(문서유형: `_검토보고`/`_구현계획`/`_수정계획`/`_승인요청`/`_체크리스트`/`_대응계획`/`_원인결과검증`).
- 작업 도중 결정이 바뀌거나 새 사실이 확인돼도 기존 작업현황 문서를 바로 고치지 않는다. 변경사항은 지금 작성 중인 계획 문서에만 반영하고, 관련 기존 문서 정리는 구현이 끝난 뒤 한 번에 반영한다(사용자가 "지금 바로 고쳐줘"라고 명시한 경우만 예외).
  - 근거: auto-memory `feedback_doc_update_batching`(같은 지시가 최소 두 번 반복됐다고 기록).
- 세션 인수인계는 `CLAUDE.local.md`(로컬 전용, `.git/info/exclude`로 관리되어 git 미추적)에 고정 형식으로 남긴다: 작성일 / 현재 브랜치 / 현재 작업 목표 / 완료한 작업 / 미완료 작업 / 수정한 주요 파일 / 실행한 테스트와 결과 / 발견했지만 미수정 문제 / 다음 세션 최우선 작업 / 확정된 정책·결정 / git status·주의사항. 이 문서는 현재 상태 스냅샷이며 과거 이력을 계속 쌓지 않는다 — 매 세션 최신 상태로 다시 쓴다.
- 커밋/PR 메시지는 type 영어(feat/fix/docs/refactor/test/chore) + 설명 한국어로 고정하며, `git-message-standardizer` 스킬로 초안만 작성한다. 초안 작성과 실제 게시(`git commit`/`gh pr create`/`gh pr comment`)는 분리된 별개 완료 조건으로 취급된다 — 초안만 쓰고 게시를 잊는 경우가 실제로 있었다.
- 브랜치 전략은 `main`(운영/최종) + `feature/*`(기능별) + PR이며, merge는 PR을 통해서만 한다(커밋 로그가 전부 "Merge pull request #N" 형태로 확인됨). PR 전 최소 로컬 빌드/테스트를 실행한다.
- 사전 확인 없이 자동 실행하지 않는 액션: 파일/폴더 삭제, `git clean`/`git reset --hard`/force push, `git commit`/`push`/`gh pr create`/merge/approve, 의존성·빌드 설정 변경, secret/.env/토큰 원문 열람. 반대로 조사성 명령(`rg`, `git status`, `git diff`)과 테스트/빌드 실행은 매번 허락을 구하지 않는다.
  - 근거: `.claude/settings.local.json` 허용 패턴 목록.
- 범위가 애매하면 넓게 추측해서 고치지 않고 "범위확인필요"로 먼저 보고한다.
