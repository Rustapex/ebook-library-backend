# 2026-07-20 PR #52 관리자 도서 API 코드리뷰 대응 계획

## 0. 목적과 범위

- PR #52의 리뷰 4건을 반영해 관리자 도서 API 계약·구현·검증 자료를 보완한다.
- 관리자 도서 API는 기존 `API-ADMIN-BOOK-001`~`004`와 신규 `005`만 대상이다.
- 프런트엔드 코드는 수정하지 않는다. 신규 `005` 계약은 A-006 수정 화면 연결 대상으로 전달만 한다.
- 관리자 도서관 API, 지도 API, 외부 연동 키, 관리자 카테고리 API는 생성·수정·테스트하지 않는다.
- 현재 Swagger/Postman 수동 검증은 실행하지 않았다. 이 계획도 수동 테스트 성공을 주장하지 않는다.

## 1. 리뷰 결론과 원인

| 리뷰 항목 | 판단 | 대응 |
|---|---|---|
| 관리자 도서 상세 조회 부재 | 기존 공식 명세·현황은 001~004만 정의했지만, A-006이 기존 안내성 상세 값을 안전하게 채울 계약이 없었다. | `API-ADMIN-BOOK-005`를 추가한다. |
| 상태 변경이 콘텐츠 확인 정책 우회 | 실제 상태 변경에 사유 검증·no-op 규칙이 없었다. | Service 조건부 사유 검증과 no-op 규칙을 추가한다. |
| 동일 상태도 감사 로그 기록 | 실제 변경과 no-op을 구분하지 않았다. | 동일 상태는 상태·`updatedAt`·감사 로그를 바꾸지 않는다. |
| 5초 session timeout 복원 실패 무시 | JDBC connection session 값이 pool에 남을 위험이 있다. | 5초 session 조작을 제거하고 DB 기본 lock timeout을 사용한다. |

## 2. 확정 정책

### 2.1 API-ADMIN-BOOK-005 — 관리자 도서 상세 조회

- `GET /api/v1/admin/books/{bookId}`
- ADMIN 전용이며 `AVAILABLE`, `HIDDEN`, `INACTIVE` 도서를 모두 조회한다.
- 존재하지 않으면 `BOOK_NOT_FOUND(404)`를 반환한다.
- 반환 범위는 수정 가능한 메타정보, 출판사, 작가, 카테고리, 안내성 상세 정보, 상태, 생성·수정 시각이다.
- 반환하지 않는 보호 데이터는 `BookPage`, `detailContent`, 키워드·키워드 매핑, 파일, `totalPages`, 대여·평점·리뷰 집계값이다.
- read-only API이므로 감사 로그를 남기지 않는다.
- 작가는 `authorOrder ASC, authorId ASC`, 카테고리는 `categoryId ASC`으로 안정적으로 정렬한다.
- 관리자 상세에서는 현재 연결된 작가·카테고리가 `INACTIVE`여도 현재 연결 관계와 status를 함께 반환한다. 이는 수정 화면의 현재 상태 확인용이며, 003 재저장 시에는 기존 정책대로 `ACTIVE` 카테고리만 새로 연결할 수 있다.

### 2.2 API-ADMIN-BOOK-004 — 상태 변경

- `AVAILABLE`, `HIDDEN`, `INACTIVE`의 서로 다른 상태 간 전환은 모두 허용한다.
- 현재 상태와 요청 상태가 같으면 사유가 없어도 200 no-op으로 반환한다. 상태, `updatedAt`, 감사 로그는 변경하지 않는다.
- 실제 상태 변경일 때만 사유를 trim한다. trim 뒤 빈 값이면 `VALIDATION_ERROR(400)`으로 거부한다.
- 실제 변경은 이전 상태, 이후 상태, 사유, 관리자 ID를 포함한 `BOOK_UPDATE` 감사 로그와 같은 transaction으로 저장한다.
- 콘텐츠 완료 여부를 검증하는 DB 컬럼·제약조건은 이번 시연 범위에서 추가하지 않는다. `INACTIVE -> AVAILABLE`도 사유 기록을 통한 관리자 수동 확인으로 처리한다.
- DTO의 `reason`에는 고정 `@NotBlank`를 적용하지 않는다. no-op에 사유가 없어도 200이어야 하므로 Service에서만 조건부로 검증한다.

### 2.3 잠금과 transaction

- 수정(003)·상태 변경(004)의 `findByIdForUpdate(PESSIMISTIC_WRITE)` 행 잠금은 유지한다.
- `BookLockTimeoutSupport`, Service 주입·호출, 5초 `SET SESSION innodb_lock_wait_timeout` 조작과 복원 로직은 제거한다.
- DB 기본 lock timeout과 deadlock에서 발생하는 `PessimisticLockingFailureException -> CONCURRENT_UPDATE(409)` 공통 처리는 유지한다.
- 두 관리자가 같은 도서를 동시에 수정하면 뒤 요청은 앞 transaction의 commit 또는 rollback까지 DB 기본 timeout 범위에서 대기한다. 앞 요청이 끝나면 뒤 요청은 이어서 처리될 수 있으며, 오래된 화면의 마지막 저장 문제는 이번 시연 범위에서 제외한다.

## 4. 구현 변경 계획

1. 관리자 전용 상세 Response DTO와 `GET /{bookId}` Controller·Service 경로를 추가한다.
2. 005는 `Book`, `BookDetail`, `BookAuthor`, `BookCategory`만 조립하며 보호 데이터 Repository를 호출하지 않는다.
3. 004 Service에서 같은 상태를 먼저 판별하고 no-op을 반환한다. 실제 변경일 때만 사유를 검증·상태 변경·감사 로그 기록한다.
4. `BookLockTimeoutSupport` 파일과 관련 주입·호출·mock 테스트를 제거한다. write-lock Repository와 공통 409 예외 처리는 보존한다.
5. 005 테스트, 상태 변경 사유/no-op 테스트, session SQL 미사용 회귀 테스트를 추가한다.

## 6. Swagger/Postman 체크리스트·SQL 최신화 판단

### 6.1 판단: 최신화가 필요하다

현재 `api-test-results/관리자 도서 API`의 두 파일은 001~004만 전제로 한다. 005가 없고, 동일 상태 요청에서 감사 로그가 추가된다는 기존 기대가 남아 있으며, 5초 timeout에 따른 409 동시 수정 시나리오가 포함되어 있다. 확정 정책과 일치하지 않으므로 수동 테스트를 시작하기 전에 최신화해야 한다.

현재 수동 검증은 미실행이므로 기존 체크리스트·SQL의 PASS/FAIL 기록이나 실제 DB 데이터는 수정하지 않는다. 구현 코드와 계약 문서가 반영된 뒤, 수동 테스트 직전에 두 자료의 내용만 동기화한다.

### 6.2 체크리스트 최신화 계획

대상: `api-test-results/관리자 도서 API/관리자-도서API_체크리스트.md`

- 제목·범위를 001~005로 변경한다.
- 005 정상 조회, `HIDDEN`·`INACTIVE` 조회, 404, 401/403, 보호 데이터 미노출, 작가·카테고리 정렬·비활성 연관 데이터 노출 시나리오를 추가한다.
- 004 실제 상태 변경의 빈/공백 사유 400, 실제 변경 감사 로그, 동일 상태 사유 없음 200 no-op과 감사 로그 건수·`updatedAt` 불변 시나리오를 추가한다.
- 기존 004 동일 상태 시나리오의 “감사 로그가 매번 추가” 기대를 “감사 로그 추가 없음”으로 변경한다.
- 5초 409을 전제로 한 Postman 동시 수정 시나리오는 제거한다. 기본 DB timeout은 수동 테스트의 고정 성공 기준으로 삼지 않는다.
- 모든 신규 시나리오에 API ID, Method/URL, 인증, path/query/body, 기대 응답, 확인 SQL 절 번호, 다음 단계와 cleanup 순서를 기록한다.

### 6.3 SQL 최신화 계획

대상: `api-test-results/관리자 도서 API/관리자-도서API_테스트데이터_및_정리.sql`

- 005 결과 검증 SELECT를 추가한다. 안내성 상세·작가·카테고리·상태를 확인하되 `book_page`, 키워드, 파일, `detail_content`, 집계값을 조회·변경 대상으로 추가하지 않는다.
- 004 실제 변경 전후 감사 로그 건수와 `after_summary.reason`을 확인하는 SELECT를 유지·명확화한다.
- 동일 상태 no-op 전후에는 book `updated_at`과 `BOOK_UPDATE` 감사 로그 건수가 같음을 비교하는 SELECT를 추가한다.
- 5초 session timeout 설정·복원 및 그에 따른 409 기대를 위한 SQL/주석은 제거한다.
- 기존 INSERT·검증·cleanup은 `ADMIN_BOOK_TEST_` prefix와 정확한 ID, `NOT EXISTS`, `ROW_COUNT()` 증거 원칙을 유지한다.

## 7. 테스트와 검증 순서

1. 단위 테스트는 DB에 연결하지 않고 005 조립, 004 조건부 사유, no-op, 감사 로그 호출 여부를 검증한다.
2. Controller·보안 테스트는 005의 ADMIN 200, USER 403, 미인증 401, 없는 도서 404를 검증한다.
3. Repository·통합 테스트는 `schema.sql`과 `data.sql`만 적용한 독립 테스트 DB를 전제로 하며, 개발자 개인 DB 데이터·ID에 의존하지 않는다.
4. 코드와 기준 문서가 확정된 뒤 체크리스트·SQL을 최신화한다.
5. 최신화된 자료로 Swagger/Postman 수동 검증을 수행하고, 실패·미실행 항목은 PASS가 아닌 FAIL 또는 BLOCKED로 기록한다.
6. 마지막에 cleanup SQL과 `ROW_COUNT()`·remaining count로 테스트 데이터를 정리한다.

## 8. 범위 제외와 완료 기준

- 관리자 도서관 API·지도 API·외부 키·관리자 카테고리 API에는 Controller, Service, DTO, Repository, SQL, 체크리스트를 추가하거나 수정하지 않는다.
- 출판사·작가의 동시 관리자 등록과 ISBN DB UNIQUE 충돌의 동시성 보완은 기존 “동시 관리자 등록 없음” 전제에 따라 이번 대응 범위에서 제외한다.
- 005, 004 no-op/사유 정책, session timeout 제거, 기준 문서 정정, 체크리스트·SQL 최신화 계획이 모두 반영되고 관련 테스트·수동 검증이 구분 기록되어야 대응 완료로 판단한다.
