# 백엔드 O·화면 O·프론트 연결 X API 연결 계획

- 작성일: 2026-07-20
- 기준 현황: `docs/프로젝트현황/API-ID별_백엔드구현_프론트연결_현황.md`
- 백엔드 저장소: `C:\Github\abc-proj-win`
- 프론트 저장소: `C:\Github\abc-proj-win-FRONT\abc_front`
- 목적: 기존 화면의 디자인·구조는 유지한 채, 백엔드 응답이 기존 화면의 데이터 영역에 실제로 표시되도록 백엔드 → 프론트 데이터 흐름만 연결·정리한다.

## 1. 결론

- 이번 범위는 백엔드 신규 API 구현이나 프론트 화면 신규 개발이 아니라 기존 API와 기존 화면의 데이터 연결 작업이다.
- 새로운 기능 정책이나 도메인 규칙을 결정할 필요는 없다.
- 백엔드 URL·HTTP Method·인증·요청/응답 계약은 현재 백엔드 `main` 구현과 API 명세를 기준으로 프론트를 맞춘다.
- 정적 조사 결과 관리자 도서 5개, 관리자 컬렉션 4개, 관리자 회원 3개는 이미 wrapper와 화면 호출이 있다. 이 12개는 현황표의 기존 `프론트 연결 X`와 달리 정적 기준에서는 `O`이다. 다만 백엔드 DTO와 다른 타입·필드, fallback·로컬 성공 처리가 있어 실제 데이터 표시를 보장하지 못하므로 데이터 계약 정렬이 필요하다.
- 원칙적으로 백엔드는 수정하지 않는다. 올바른 요청을 보냈는데도 Controller 매핑, 응답 DTO, 권한, CORS 문제로 실패한다는 근거가 확인될 때만 백엔드 수정 여부를 별도로 판단한다.
- 프론트 수정은 API 호출·타입·응답 변환·기존 상태값 갱신·기존 오류 상태 처리로만 한정한다. 디자인, 화면 구조, 배치, CSS, CSS module, 인라인 `style`, 클래스명, 디자인 컴포넌트는 절대 수정하지 않는다.

### 범위 제외

- `API-ADMIN-COLLECTION-005`, `API-ADMIN-COLLECTION-006`: 백엔드는 구현되어 있으나 현재 현황표에서 화면 ID와 화면 구현이 `-`이므로 이번 조건에서 제외한다.
- EPUB 업로드 API: 관리자 도서 5개 API ID 범위와 별도 기능이므로 이번 연결 계획에 포함하지 않는다.
- 백엔드 또는 화면 구현이 `X`인 API: 이번 작업의 전제에 맞지 않으므로 제외한다.
- 현황표의 `프론트 연결 X`이지만 백엔드 Controller가 없는 API: 프론트 wrapper·화면 호출이 이미 있어도 실제 연결은 불가능하므로 이번 작업에서 상태를 `O`로 바꾸지 않는다. 이 경우는 `프론트 호출 구현 O / 백엔드 구현 X / 연결 X`로 별도 관리한다.
- 신규 카드, 표, 모달, 탭, 섹션, 버튼, 화면, route, 페이지 이동 흐름의 생성·삭제·재배치: 범위 제외다.
- CSS, CSS module, Sass, 인라인 `style`, 클래스명, 디자인 토큰, 여백·색상·폰트·반응형 등 시각 요소의 변경: 범위 제외다.

## 3. 현재 상태 해석

### 3.1 사용자 컬렉션 2개

- 백엔드는 `GET /api/v1/collections`, `GET /api/v1/collections/{collectionId}`를 제공한다.
- 프론트 `src/api`와 `src/types/api.ts`에는 사용자 컬렉션 전용 호출 함수와 타입이 없다.
- `U-001`은 추천·신간·베스트 도서만 호출하고 있고, `U-006`도 `collectionId`를 이용한 컬렉션 상세 조회가 없다.
- 따라서 이 2개는 실제 프론트 연결 코드를 추가해야 한다.

### 3.2 관리자 API 12개

- 관리자 도서, 관리자 컬렉션, 관리자 회원 API는 프론트 wrapper와 화면 호출 코드가 이미 존재한다.
- 현황표의 `프론트 연결 X`는 현재 소스보다 오래된 판정이다. 현황표가 정의한 정적 기준(백엔드 `O` + wrapper + 화면 사용)으로는 이 12개를 `O`로 최신화할 수 있다.
- 현재 화면은 조회 실패 시 임시 데이터를 표시하거나, 변경 요청이 실패해도 화면에서만 성공한 것처럼 상태를 바꾸는 구간이 있다.
- 따라서 이 12개는 wrapper 신규 작성이 아니라 백엔드 DTO를 기존 화면의 데이터 상태로 변환하고, 실패를 숨기는 fallback·로컬 성공 처리를 제거하는 작업이 핵심이다.

### 3.3 현황표 최신화 기준

- 정적 존재 기준으로 즉시 `프론트 연결 O`로 변경할 항목: 관리자 컬렉션 4개, 관리자 도서 5개, 관리자 회원 3개. 전체 프론트 연결 `O` 집계는 `46 → 58`이 된다.
- `API-COLLECTION-001`, `API-COLLECTION-002`는 실제 wrapper·화면 호출이 없으므로 `X`를 유지한다.
- 백엔드 `X`이나 프론트 wrapper·화면 호출이 확인된 20개 API는 연결 `X`를 유지한다. 대상은 `API-REPORT-004`, `API-NOTICE-001`, `API-NOTI-001`~`002`, `API-REQUEST-001`~`002`, `API-ADMIN-CATEGORY-001`~`002`, `API-ADMIN-RENTAL-001`, `API-ADMIN-PAYMENT-001`, `API-ADMIN-REPORT-001`~`002`, `API-ADMIN-REQUEST-001`~`002`, `API-ADMIN-NOTICE-001`~`003`, `API-ADMIN-LIBRARY-001`~`003`이다. 이 20개는 별도 열 `프론트 호출 구현`을 추가할 때만 `O`로 기록한다.
- 현황표에서 `프론트 연결 O`인데 wrapper 또는 화면 사용이 없는 항목은 이번 존재 조사에서 확인되지 않았다.

## 4. 저장소별 수정 계획

### 4.1 백엔드 저장소

예상 수정 없음.

- 기존 Controller 경로와 DTO를 프론트 연결 기준으로 사용한다.
- 프론트에서 전송하는 필드가 백엔드 DTO와 다르면 프론트를 수정한다.
- 연동 확인 중 다음 증거가 발생한 경우에만 백엔드 이슈로 분리한다.
  - 명세·구현에 존재해야 하는 Controller 경로가 실제로 404를 반환함
  - 올바른 관리자 토큰을 사용했는데 Security 설정 때문에 401/403이 발생함
  - 허용해야 하는 프론트 origin에서 CORS 차단이 발생함
  - 백엔드 응답 자체가 현재 DTO 또는 합의된 명세와 다름

### 4.2 프론트 저장소 공통

대상 경로:

- `src/api/apiClient.ts`
- `src/types/api.ts`
- 도메인별 `src/api/*Api.ts`
- 대상 화면 `U-001`, `U-006`, `A-002`, `A-003`, `A-004`, `A-005`, `A-006`, `A-018`

공통 처리:

1. `apiClient`의 `VITE_API_BASE_URL`과 Bearer 토큰 사용 방식은 유지한다.
2. 백엔드 `ApiResponse<T>`와 `PageResponse<T>` 봉투 구조를 그대로 사용한다.
3. API별 요청·응답 타입을 백엔드 DTO에 맞춘다.
4. 조회 실패 시 임시 데이터를 정상 데이터처럼 표시하지 않는다.
5. 변경 API 실패 시 로컬 상태를 성공 상태로 변경하지 않는다.
6. 변경 성공 후 응답값을 반영하거나 서버 데이터를 다시 조회한다.
7. 400·401·403·404·409·500 오류는 기존 공통 오류 표시 방식으로 사용자에게 보여준다.

### 4.3 프론트 변경 절대 금지 범위

다음 항목은 이번 연결 작업에서 절대 수정하지 않는다.

- 화면 디자인, 화면 구조, 컴포넌트 배치, JSX 마크업 계층
- CSS, CSS module, Sass, 인라인 `style`, `className`, 색상·폰트·여백·크기·반응형
- 새 화면·새 route·새 컴포넌트·새 버튼·새 모달·새 표·새 탭·새 카드 생성
- 기존 버튼·문구·섹션의 위치 변경, 삭제, 추가

허용되는 프론트 수정은 기존 API wrapper와 TypeScript 타입, 기존 state의 데이터 대입, 기존 `useEffect`·이벤트 핸들러의 API 호출, 응답 변환 adapter, 기존 오류 상태에 서버 오류를 대입하는 코드뿐이다. 기존 화면에 컬렉션 데이터를 표시할 데이터 영역이 전혀 없다면 UI를 새로 만들지 않고 `범위확인필요`로 보고한다.

## 5. 도메인별 실행 순서

### 5.1 사용자 컬렉션 연결

대상: `API-COLLECTION-001`, `API-COLLECTION-002`

1. `src/types/api.ts`에 컬렉션 목록·상세·쿼리 타입을 추가한다.
2. `src/api/collectionApi.ts`를 만들고 목록·상세 GET wrapper를 추가한다.
3. `U-001`, `U-006`의 기존 데이터 표시 영역과 상태값이 있는 범위에서만 목록·상세 응답을 대입한다.
4. 기존 route, 화면 이동, JSX 구조를 변경하지 않고 현재 조회 분기 안에서 컬렉션 요청이 다른 목록 데이터를 덮어쓰지 않게 한다.
5. 컬렉션 API 실패 시 기존 임시 데이터로 조용히 대체하지 않고, 이미 존재하는 오류 상태를 사용한다.
6. 기존 화면에 컬렉션 응답을 받을 상태값이나 표시 영역이 없으면 UI를 추가하지 않고 해당 항목을 `범위확인필요`로 남긴다.

### 5.2 관리자 도서 연결 안정화

대상: `API-ADMIN-BOOK-001`~`005`

1. `AdminBookSummary`, `AdminBookDetail`, 저장 요청 타입을 백엔드 DTO 구조에 맞춘다.
2. 목록의 `authorNames`와 카테고리 배열을 기존 `A-004` 표 데이터 형식으로만 매핑한다.
3. 등록·수정 요청에서 `keywords`, `status`를 제거하고 상세 설명 필드는 `detail`에만 넣는다.
4. 상태 변경은 반드시 `API-ADMIN-BOOK-004`로만 호출한다.
5. `API-ADMIN-BOOK-005` 응답의 저자·카테고리 객체와 `detail`을 기존 `A-006` 폼 상태값으로만 변환한다.
6. `A-004`, `A-006`의 도서 fallback 표시를 제거하고 실패 상태를 명시한다.
7. 등록·수정·상태 변경 성공 후 목록 또는 상세를 다시 조회해 서버 저장값을 기준으로 화면을 갱신한다.

### 5.3 관리자 컬렉션 연결 안정화

대상: `API-ADMIN-COLLECTION-001`~`004`

1. 목록 응답의 `name`, `mappedCount`를 기준으로 프론트 타입과 기존 화면 상태값을 정렬한다.
2. 수정 요청은 `collectionName` 대신 `name`을 사용하고 백엔드 DTO에 없는 `displayOrder`를 보내지 않는다.
3. 도서 저장 요청의 `books[{bookId, displayOrder}]` 구조를 유지하고 성공 후 목록을 재조회한다.
4. 상태 변경·도서 제외 요청은 `removeBookIds[]`를 사용한다.
5. API 실패 시 `finally`에서 로컬 데이터를 변경하거나 성공 메시지를 표시하는 로직을 제거한다.
6. `A-018`의 임시 컬렉션 fallback을 제거하고 로딩·빈 결과·오류 상태를 구분한다.

### 5.4 관리자 회원 연결 안정화

대상: `API-ADMIN-MEMBER-001`~`003`

1. 목록 응답의 마스킹 필드와 `activeSanctions[]`를 기존 표 데이터 타입에 맞춘다.
2. `A-002`의 임시 회원 목록 fallback을 제거한다.
3. 상세 응답의 `profile`, `usageSummary` 중첩 구조를 `A-003` 표시 구조에 맞춘다.
4. 상세 API가 반환하지 않는 이력 탭 배열을 기본 상세 응답에 포함된 것으로 가정하지 않는다.
5. 상태 변경 실패 시 `A-003`에서 로컬 회원 상태를 변경하는 처리를 제거한다.
6. 상태 변경 성공 후 목록·상세를 다시 조회해 현재 제재 상태를 서버 기준으로 표시한다.

## 6. 검증 계획

### 6.1 정적 검증

- 14개 API ID마다 프론트 wrapper가 존재하는지 확인한다.
- wrapper가 대상 화면 또는 화면에서 사용하는 hook/service에서 실제 호출되는지 확인한다.
- Method, URL, query, path, body가 백엔드 Controller·DTO와 일치하는지 확인한다.
- 실패 경로에서 fallback 데이터나 로컬 성공 상태가 적용되지 않는지 확인한다.
- TypeScript 타입이 실제 응답 필드와 일치하는지 확인한다.

### 6.2 프론트 검증

- `npm run lint`
- `npm run build`
- 현재 별도 프론트 테스트 러너가 없으므로 자동 단위 테스트는 범위에 포함하지 않는다.

### 6.3 연동 스모크 확인

각 API는 다음 최소 조건으로 확인한다.

- 조회 API: 정상 데이터 또는 정상 빈 결과가 화면에 표시됨
- 생성·수정·상태 변경 API: 성공 응답 후 서버 재조회 결과가 화면에 반영됨
- 인증 API: 비로그인 또는 일반 사용자로 관리자 API 호출 시 권한 오류가 정상 표시됨
- 잘못된 ID: 404가 임시 데이터로 대체되지 않고 오류로 표시됨
- 잘못된 요청: 400 검증 메시지가 성공 메시지로 바뀌지 않음

## 8. 작업 권장 순서

3. 관리자 컬렉션 4개: 실패를 성공처럼 처리하는 로직을 먼저 제거한다.
4. 관리자 회원 3개: 목록·상세 응답 구조를 정렬하고 상태 변경 실패 처리를 수정한다.

## 9. 작업 위치와 권한

- 현재 Codex 작업 위치는 백엔드 저장소 `C:\Github\abc-proj-win`이고, 이 저장소 안의 계획 문서는 바로 생성·수정할 수 있다.
- 프론트 저장소 `C:\Github\abc-proj-win-FRONT\abc_front`는 현재 작업공간의 쓰기 허용 범위 밖이다.
- 프론트 파일은 읽어서 분석할 수 있지만, 실제 수정·생성 시에는 해당 경로 쓰기 승인이 필요하다.
- 사용자가 프론트 저장소 수정 권한을 보유한 것과 Codex 실행환경의 파일 쓰기 허용 범위는 별개다. 구현 단계에서는 프론트 저장소를 작업공간으로 열거나, 해당 경로 쓰기 승인을 받아 수정한다.

## 10. 신규 결정 필요 여부

현재 14개 연결 범위에서는 신규 기능 결정이 필요하지 않다. 다음 기준을 그대로 적용한다.

- 화면 동작: 기존 화면 설계·디자인·구조·배치 유지, 데이터만 실제 서버 응답으로 교체
- API 동작: 현재 백엔드 구현과 명세 유지
- 인증: 기존 access token과 관리자 권한 사용
- 오류 처리: 실패를 임시 성공으로 숨기지 않음
- 데이터 표시: 서버 응답을 단일 기준으로 사용

데이터를 표시하려면 새로운 디자인 요소나 화면 구조가 필요하다는 판단이 나오면, 그 변경은 이번 범위에 포함하지 않는다. 기존 영역에 연결할 수 없는 이유와 필요한 UI 변경만 보고하고 사용자의 별도 지시를 받는다.

구현 중 명세와 현재 백엔드 DTO가 서로 다르면 새로운 기능 결정을 요청하는 것이 아니라, 먼저 불일치 항목과 영향을 기록하고 현재 `main`의 실제 계약을 기준으로 프론트를 정렬한다. 사용자 판단이 필요한 경우는 화면 요구 자체를 바꾸거나 API 계약을 새로 확장해야 할 때뿐이다.
