## 3. 발견한 이슈 (구현 전에 알아야 할 것)

### 3-1. api-spec이 언급한 `BOOK_FILE` 테이블이 실제 DB에 없음

- api-spec URL 요약표(`api-spec(final).md:186`)에 `API-VIEWER-001` 관련 테이블로 `BOOK_RENTAL, BOOK_PAGE, BOOK_FILE, READING_PROGRESS, BOOKMARK`가 적혀 있음.
- `src/main/resources/schema.sql`에 `book_file` 테이블 자체가 없음(rg로 확인, 매치 0건).
- **1순위/2순위 원칙 적용**: 규칙.md엔 이 이슈에 대한 언급이 없어 원칙으로 자동 해결은 안 되지만, 실제 DB(schema.sql)가 사실상의 최종 기준이므로 **`BOOK_FILE` 관련 로직 없이 `book_page.page_content`만으로 뷰어 페이지 본문을 구현**하는 쪽으로 판단. api-spec 쪽의 오기(誤記)로 보임.

### 3-2. `API-RENTAL-001`(대여 생성)/`API-RENTAL-003`(내 대여 목록) — (결정 완료) 이번 범위에서 만들지 않음

- 대여 생성/조회는 추후 별도로 개발 예정이라, 이번 뷰어/북마크/진행 API 개발은 "대여는 이미 존재한다"고 가정하고 진행한다.
- Repository 테스트는 지금까지와 동일하게 네이티브 INSERT로 `book_rental`을 직접 시드해서 검증한다(`Library`/`Favorite` 때와 동일 방식) — 대여 생성 API가 없어도 뷰어 쪽 구현·검증에는 지장 없음.

### 3-3. 신규 `ErrorCode` 3개 — 별도 승인 요청 자료 작성 완료

- `ErrorCode.java:10`이 "새로운 예외가 필요할때는 반드시 팀장에게 보고후 승인 받고 추가한다"고 명시하고 있어, 이유/위치/영향을 정리한 별도 문서를 만들어뒀다: `2026-07-02_ErrorCode_신규추가_승인요청.md`.
- 신규 코드 3개(`RENTAL_NOT_FOUND`, `BOOKMARK_NOT_FOUND`, `BOOKMARK_ALREADY_EXISTS`)는 그대로 진행. `ErrorCode.java` 수정 시점에 위 문서로 보고하면 됨(코드 작성 자체를 막을 필요는 없음, 승인은 별도 트랙으로 처리).

### 3-4. `API-READING-001`의 컨트롤러 위치 — (결정 완료) `rental` 패키지에 별도 컨트롤러

- `rental` 패키지에 `ReadingController`를 신설해 `/api/v1/me/recent-books`를 매핑한다. `MeController`(4.1 담당자 소유)는 건드리지 않는다.
- `book`/`library` 컨트롤러가 이미 `/api/v1/books` prefix를 나눠 쓰는 선례와 동일한 방식.

### 3-5. `API-READING-001` 응답에 `coverImageUrl` — (결정 완료) 추가

- api-spec(`:284`)엔 "최근 읽은 책"이라고만 있어 필드가 불명확했지만, `02-User-상세화면설계도.md:646`(U-028)이 "표지, 제목, 현재/전체 페이지, 진행률, 마지막 읽은 시각"을 요구함을 확인해 응답 DTO에 `coverImageUrl`을 포함하기로 결정.
- `Book.coverImageUrl`이 직접 필드라 추가 조회 비용 없음.

### 3-6. "완독" 판정 규칙(결정 완료) / 통계 테이블 쓰기(결정 완료: 이번 범위 제외)

- **완독 판정**: `currentPage`가 도서의 마지막 페이지(`Book.totalPages`)에 도달하면 완독으로 판정한다(`reading_progress.completed_yn=true`, `completed_at` 저장). api-spec 4.3절 "마지막 페이지 도달 시 최초 1회 완독 처리"와 일치 — `completedYn`이 이미 `true`면 다시 처리하지 않음(최초 1회 보장).
- **통계 테이블(`USER_READING_STATISTICS`/`ADMIN_STATISTICS`) 쓰기**: 이번 범위에서 제외한다. 두 테이블 다 `period_start_date`/`period_end_date` 기반 기간 집계 테이블(`schema.sql:531-556`)이라 요청 1건마다 갱신하는 구조가 아니라고 판단했고, api-spec에 이 테이블들이 언급돼 있다는 이유만으로 구현을 막지 않는다(문서는 2순위, 이후 통계 담당자가 별도로 배치/집계 로직을 만들 때 `reading_progress`를 소스로 쓰면 됨).
