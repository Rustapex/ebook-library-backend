# DB 관련 문서와 실제 DB 파일 간 불일치 발견 (2026-07-02)

목적: `myRentalState`/`favoriteYn` 구현 과정에서 `docs/데이터베이스/erd/ebook-rental-erd.md`, `docs/데이터베이스/ddl/schema.sql`과 실제 앱이 로드하는 `src/main/resources/schema.sql`/`data.sql`을 대조하다가 발견한 문제를 기록한다.

---

## 1. `docs/데이터베이스/ddl/schema.sql`이 실제 runtime 스키마와 다름 (기존에 이미 발견, 재확인)

- `library` 테이블 컬럼명이 서로 다름:
  - `docs/데이터베이스/ddl/schema.sql`: `library_name`, `library_address`, `library_latitude`, `library_longitude`, `library_status`
  - `src/main/resources/schema.sql`(실제 앱이 로드): `library_name`, `address`, `latitude`, `longitude`, `status`
  - `Library.java` 엔티티는 `src/main/resources/schema.sql` 기준(짧은 이름)으로 이미 작성돼 있어, 앱은 정상 동작한다. 문제는 `docs/데이터베이스/ddl/schema.sql` 쪽이 실제와 안 맞는 것.
- **영향**: DB 관련 판단(컬럼명, 제약조건)을 `docs/데이터베이스/` 문서만 보고 내리면 틀릴 수 있다. 이번 `API-LIBRARY-001` 구현 때 이 불일치를 미리 발견해서 실제 `src/main/resources/schema.sql` 기준으로 작업해 문제는 없었지만, 문서 자체는 여전히 안 고쳐진 상태다.
- **제안**: `docs/데이터베이스/ddl/schema.sql`을 `src/main/resources/schema.sql` 기준으로 동기화(계획 문서 3절에 이미 "문서 정리 성격, 시간 날 때 진행"으로 등록돼 있음 — 우선순위 낮음 유지, 이번에 새로 만든 항목 아님).

## 2. `book_rental`에는 `(member_id, book_id)` UNIQUE 제약이 없음 (이번에 새로 발견)

- `favorite_book`(`schema.sql:305-312`)은 `UNIQUE(member_id, book_id)`가 있어 회원+도서당 행이 최대 1개로 보장된다.
- `book_rental`(`schema.sql:272-282`)은 이런 제약이 **없다.** ERD의 BR-41("대여 기간 종료 후 `READY` 상태로 돌아가며 다시 대여할 수 있다")이 "같은 행의 상태만 바뀐다"는 뜻인지 "새 행이 또 생긴다"는 뜻인지 스키마만으로는 확정할 수 없고, 유니크 제약이 없다는 건 최소한 "여러 행이 쌓일 수 있는 구조"라는 뜻이다.
- **영향**: `myRentalState`를 구현할 때 `findByMemberIdAndBookId`(단건 가정)로 짜면, 과거에 같은 책을 재대여한 이력이 있는 회원의 경우 `NonUniqueResultException`이 나거나(단건 강제 조회 시) 어떤 행이 반환될지 예측 불가능해질 위험이 있었다.
- **조치**: `BookRentalRepository.findFirstByMember_MemberIdAndBook_BookIdOrderByCreatedAtDesc`로 "최신 1건만" 가져오도록 구현(`src/main/java/com/acorn/abc/rental/repository/BookRentalRepository.java`). 이걸로 이번 구현 범위(도서 상세의 `myRentalState` 표시)는 문제없지만, 실제로 "재대여 시 새 행이 생기는지 vs 기존 행을 재사용하는지"는 4.3(대여) 담당자가 대여 생성 로직을 만들 때 확정해야 하는 사항이라 이 문서에서 결론내리지 않는다.

## 3. 결론

- 코드 구현에는 지장 없었음(둘 다 `src/main/resources/schema.sql` 기준으로 안전하게 처리함).
- `docs/데이터베이스/ddl/schema.sql` 동기화는 여전히 낮은 우선순위 잔여 항목.
- `book_rental`의 재대여 시 행 생성 정책은 4.3(대여) 담당자 확인이 필요한 별도 항목으로 남겨둠(이번 구현과는 무관하게 대여 도메인 자체의 결정 사항).
