목적: `docs/화면흐름도`(회원/비회원 화면 설계)와 `docs/API 명세/api-spec(final).md` 4.2절을 대조해서, 지금까지 구현한 `API-BOOK-001/002/003/005`, `API-CATEGORY-001`, `API-COLLECTION-001/002`, `API-LIBRARY-001`에 코드 변경이 필요한 부분이 있는지 확인한다. 우선순위: `docs/공통문서/백엔드_공통_개발_규칙.md`가 1순위. 화면흐름도는 `api-spec(final).md`와 충돌하는 경우 api-spec이 우선(`01-공통-화면설계기준.md:8`)이지만, 이번에 발견한 항목은 "충돌"이 아니라 api-spec이 명시하지 않은 세부사항(응답 필드)을 화면흐름도가 구체화한 경우라 화면흐름도 내용을 반영하는 게 맞다고 판단.

조사 방법: `targeted-file-reading`(rg로 헤딩/키워드 검색 후 해당 구간만 읽음). 읽은 파일: `docs/화면흐름도/01-공통-화면설계기준.md`(전체, 작아서 처음부터 읽음), `02-User-상세화면설계도.md`(U-001/006/007/008/024 구간), `04-전체-화면이동흐름.md`(1~3절 흐름도), `docs/API 명세/api-spec(final).md`(4.2절, 이전 조사에서 이미 확보).

### 4-1. `myRentalState` 값 정의 (ERD 확인 → 실제 runtime DB 파일로 재검증 완료)

- **1차 출처(ERD)**: `docs/데이터베이스/erd/ebook-rental-erd.md:129`(BR-40) — "대여 상태는 `READY`, `READING`, `OWNED`만 사용한다." / `:1076` — `book_rental.rental_status` `CHECK(... IN ('READY','READING','OWNED'))`.
- **재검증(2026-07-02, 실제 앱이 로드하는 파일)**: `src/main/resources/schema.sql:272-282`(`book_rental` 테이블 실제 DDL), `src/main/resources/data.sql`(17줄, `member_grade` seed만 있고 `book_rental`/`favorite_book`/`library` seed 없음)을 직접 다시 읽음. 결과: `rental_status VARCHAR(20) NOT NULL, CHECK (rental_status IN ('READY', 'READING', 'OWNED'))` — **ERD와 완전히 일치, 불일치 없음.** (참고: `docs/데이터베이스/ddl/schema.sql`은 이전에 `library` 테이블 컬럼명이 실제 runtime `schema.sql`과 달랐던 전례가 있어 이번에도 재확인이 필요했음 — 이번엔 문제없었지만, 앞으로도 DB 관련 결정은 `docs/데이터베이스/`가 아니라 `src/main/resources/schema.sql`을 최종 기준으로 재확인할 것)
- `api-spec(final).md`의 `API-RENTAL-003`(4.3절) "내 서재는 `READY`, `READING`, `OWNED`만 표시"와도 값이 일치함(3중 교차 확인).
- **구현 시 refinement(신규 발견)**: `favorite_book`은 `UNIQUE(member_id, book_id)` 제약이 있어 `(memberId, bookId)`당 행이 최대 1개지만, `book_rental`(`schema.sql:272-282`)은 **`(member_id, book_id)`에 UNIQUE 제약이 없음** — 즉 같은 회원이 같은 책을 과거에 대여했다가 끝나고 다시 대여하면 행이 여러 개 쌓일 수 있는 구조. 따라서 `BookRentalRepository`는 `findByMemberIdAndBookId`(단건 가정) 대신 **가장 최근 행 1개만 가져오는 조회**(`findTopByMemberIdAndBookIdOrderByCreatedAtDesc` 등)로 구현해야 함.
- **결론**: 상태값 정의는 재검증 완료, 결정 불필요하고 바로 구현 가능. 다만 Repository 메서드는 "최신 1건" 조회로 설계해야 함(단순 `findBy`가 아님).

### 4-2. 추천 개인화("회원은 관심 카테고리 중심") 근거 출처

- **유일한 출처**: `docs/화면흐름도/02-User-상세화면설계도.md:47` — U-001(메인/홈) "화면 구성" 표의 "추천 도서" 행: `"추천 도서 | 회원은 관심 카테고리 중심, 비회원은 공통 추천 도서"`.
- 추가로 확인한 곳(정의 없음, 확인만 함):
  - `02-User-상세화면설계도.md:592-607`(U-025 추천 도서 화면) — 탭 기준이 "같은 작가/같은 카테고리/같은 키워드"로만 돼 있고, 이건 `baseBookId` 기준 추천(이미 구현된 `AUTHOR`/`CATEGORY`/`KEYWORD` 타입)이라 U-001의 "관심 카테고리 중심"과는 다른 케이스. 여기도 "관심 카테고리"를 정의하지 않음.

- **결론**: "관심 카테고리"는 화면흐름도 한 곳(`02-User-상세화면설계도.md:47`)에만 텍스트로 존재하고, 이를 어떤 데이터로 계산할지(즐겨찾기 기준? 최근 대여 기준?) 정의한 문서가 전혀 없음 — 여전히 별도 결정 필요.

### 위험/미해결

- 추천 개인화("관심 카테고리")는 "관심 카테고리"를 어떻게 정의할지(즐겨찾기한 책의 카테고리? 최근 대여한 책의 카테고리?) 결정하는 사람이 있어야 함 — api-spec/화면흐름도/ERD 어디에도 정의가 없어 이 문서만으로는 해결 불가.

## 6. 실행 순서 (개정)

1. `LibrarySummaryResponse`/`LibraryService`에 `coverImageUrl` 추가(2-1) — 바로 착수 가능, 스키마/의존성 변경 없음, 다른 항목과 무관하게 독립적으로 먼저 처리 가능
