# Git 협업 가이드 HTML 개편 계획

## 1. 작업 목표

- 기존 `GIT 협업 가이드.html`을 Fork + Sourcetree 설치 중심 문서에서 팀 저장소 기반 브랜치 PR 협업 문서로 개편한다.
- 새 HTML은 작업자가 팀 저장소를 기준으로 자기 작업 브랜치를 만들고, PR을 올린 뒤, 팀장이 `main`에 merge한 내용을 다시 받아서 다음 작업을 이어가는 흐름을 설명한다.
- `git-message-standardizer` 기준을 반영해서 브랜치명, commit 메시지, PR 제목, PR 본문 작성 규칙을 표 중심으로 추가한다.

## 2. 확인한 기존 문서 근거

대상 파일:

- `C:\Github\abc-proj-win\docs\작업현황\GIT 협업 가이드.html`

확인한 구간:

- 문서 제목: `Git Fork + Sourcetree 협업 공지 가이드`
- 부제: `Windows / Mac + Sourcetree + GitHub Fork PR 협업 기준`
- 목차: Sourcetree 설치, GitHub 계정 추가, Fork와 클론, upstream 등록이 초반 핵심 흐름으로 구성되어 있음
- 역할 설명: 작업자는 Fork 저장소에서 개발하고 PR을 올리는 기준으로 설명되어 있음
- 기존 브랜치 규칙: `분류/작업내용`, 예시 `feature/member-login`, `fix/login-error`, `docs/git-guide`
- 기존 반복 흐름: PR 병합 후 `main` 최신화와 작업 브랜치에 최신 `main` 병합 필요성을 설명하고 있음

## 3. 새 HTML 파일 제안

| 항목 | 계획 |
|---|---|
| 새 파일명 | `GIT_브랜치_PR_협업_가이드.html` |
| 생성 위치 | `C:\Github\abc-proj-win\docs\작업현황` |
| 기존 파일 처리 | 기존 `GIT 협업 가이드.html`은 삭제하지 않고 보존 |
| 문서 기준 | Fork 없이 팀 저장소의 개인 작업 브랜치에서 작업 |
| 핵심 독자 | 팀원, 팀장, Git 초보 개발자 |
| 주요 목표 | 브랜치 생성, commit, push, PR 작성, 팀장 merge 이후 동기화 흐름을 실수 없이 반복하게 함 |

## 4. 제거하거나 축소할 기존 내용

| 기존 내용 | 처리 방향 | 이유 |
|---|---|---|
| Sourcetree 설치 | 제거 | 새 문서는 도구 설치 문서가 아니라 협업 절차 문서로 작성 |
| Sourcetree에서 GitHub 계정 추가 | 제거 | 계정 연결 절차보다 브랜치/PR 규칙이 핵심 |
| Fork 생성 | 제거 | Fork 협업이 아니라 팀 저장소의 개인 브랜치 협업으로 변경 |
| 내 Fork 저장소 클론 | 제거 | 팀 저장소 clone 기준으로 변경 |
| upstream 등록 | 제거 | Fork 구조가 아니므로 `upstream` 개념을 기본 흐름에서 제외 |
| `origin`을 내 Fork로 설명하는 내용 | 수정 | `origin`은 팀 저장소 원격 주소로 설명 |
| `upstream/main = local main = origin/main` 설명 | 수정 | `origin/main = local main` 최신화 기준으로 단순화 |
| Sourcetree 설치/계정 연결 화면 중심 설명 | 제거 | 새 문서는 도구 설치 문서가 아니라 협업 절차 문서로 작성 |
| Sourcetree 협업 작업 화면 설명 | 유지 후 재작성 | 설치 설명은 제거하되, branch 생성, pull, merge, push, stash 같은 실제 협업 절차는 Sourcetree GUI 방식과 터미널 방식으로 각각 안내 |

| 단계 | 작업자 행동 | 기준 브랜치 | 결과 |
|---|---|---|---|
| 1 | `main`으로 이동 | `main` | 기준 브랜치 확인 |
| 2 | 최신 `main` pull | `main` | 팀장이 merge한 최신 코드 반영 |
| 3 | 작업 브랜치 생성 | `feature/...`, `fix/...` 등 | 내 작업 공간 분리 |
| 4 | 코드/문서 수정 | 작업 브랜치 | 변경 내용 작성 |
| 5 | 로컬 검증 | 작업 브랜치 | 실행/테스트/빌드 확인 |
| 6 | commit 작성 | 작업 브랜치 | 변경 이력 저장 |
| 7 | push | 작업 브랜치 | GitHub에 작업 브랜치 업로드 |
| 8 | PR 생성 | 작업 브랜치 -> `main` | 팀장에게 merge 요청 |
| 9 | 팀장 리뷰/merge | `main` | 팀 저장소 `main`에 반영 |
| 10 | 작업자 `main` pull | `main` | merge된 최신 내용 로컬 반영 |
| 11 | 계속 작업 중인 브랜치에 `main` 병합 | 작업 브랜치 | 다음 PR 충돌 가능성 감소 |
| 12 | 병합 결과를 작업 브랜치에 push | 작업 브랜치 | 원격 작업 브랜치도 최신 `main` 반영 상태로 맞춤 |

## 7. 브랜치 명명 규칙

브랜치명 기본 형식:

```text
type/작업-내용
```

| 작업 내용 | 브랜치 type | 브랜치명 예시 | 사용 기준 |
|---|---|---|---|
| 새 기능 추가 | `feature` | `feature/member-login` | 회원가입, 로그인, 검색, 관리자 기능 등 새 기능 |
| 버그 수정 | `fix` | `fix/reservation-seat-duplicate` | 오류, 검증 실패, 잘못된 응답 수정 |
| 문서 수정 | `docs` | `docs/git-guide` | README, API 문서, ERD, 협업 가이드 수정 |
| 코드 구조 개선 | `refactor` | `refactor/movie-service` | 동작은 유지하고 서비스 분리, 중복 제거 |
| 테스트 추가/수정 | `test` | `test/member-validation` | 단위 테스트, 통합 테스트, 테스트 데이터 |
| 설정/환경 정리 | `chore` | `chore/gitignore-cleanup` | `.gitignore`, Gradle, 설정 파일, 폴더 정리 |
| 화면 스타일만 수정 | `style` | `style/reservation-page` | 기능 변화 없는 CSS, 공백, 정렬 수정 |

브랜치명 작성 규칙:

| 규칙 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 영어 소문자 사용 | `feature/member-login` | `Feature/MemberLogin` |
| 단어 구분은 하이픈 사용 | `fix/login-error-message` | `fix/login_error_message` |
| 한글, 공백 지양 | `docs/git-guide` | `문서/git 가이드` |
| 작업 범위를 드러냄 | `feat/member-signup` | `feat/work` |
| `main`에서 직접 작업 금지 | `feature/review-create` | `main`에 직접 commit |

## 8. commit 메시지 규칙

이 섹션은 이전 파일과 `git-message-standardizer` 기준을 참고한 초안이다. 실제 HTML 작성 전에는 commit type, scope, summary 규칙을 다시 조사하고 팀 규칙에 맞게 확정한다.

commit 제목 기본 형식:

```text
type(scope): 한국어 요약
```

scope가 애매하면 생략한다.

```text
type: 한국어 요약
```

| type | 의미 | 사용 상황 | commit 예시 |
|---|---|---|---|
| `feat` | 새 기능 추가 | 회원가입, 로그인, 검색 등 기능 추가 | `feat(member): 로그인 검증 로직 추가` |
| `fix` | 버그 수정 | 오류, 검증 실패, 잘못된 응답 수정 | `fix(reservation): 좌석 중복 예매 검증 오류 수정` |
| `docs` | 문서 수정 | README, API 문서, 가이드 수정 | `docs(git): 브랜치 PR 협업 가이드 추가` |
| `style` | 기능 변화 없는 포맷 수정 | 공백, 정렬, CSS 스타일만 수정 | `style(view): 예매 화면 버튼 간격 조정` |
| `refactor` | 구조 개선 | 동작 유지, 중복 제거, 서비스 분리 | `refactor(movie): 검색 서비스 흐름 단순화` |
| `test` | 테스트 코드 수정 | 단위/통합 테스트 추가 | `test(member): 회원가입 검증 테스트 추가` |
| `chore` | 설정/기타 작업 | `.gitignore`, Gradle, 폴더 정리 | `chore(config): 로컬 설정 파일 추적 제외` |

summary 작성 규칙:

| 규칙 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 한국어로 작성 | `fix: 예매 좌석 중복 확인 오류 수정` | `fix: correct reservation error` |
| 마침표 생략 | `docs: Git 협업 가이드 보완` | `docs: Git 협업 가이드 보완.` |
| 모호한 표현 금지 | `feat: 회원가입 입력값 검증 추가` | `feat: 작업함` |
| 변경 내용을 드러냄 | `refactor: 영화 검색 서비스 흐름 단순화` | `refactor: 수정` |

## 9. PR 제목 작성 규칙

PR 제목 기본 형식:

```text
type(scope): 한국어 요약
```

| PR 내용 | PR 제목 type | PR 제목 예시 |
|---|---|---|
| 새 기능 중심 | `feat` | `feat(member): 회원가입 입력값 검증 추가` |
| 버그 수정 중심 | `fix` | `fix(reservation): 좌석 중복 예매 검증 오류 수정` |
| 문서만 수정 | `docs` | `docs(git): 브랜치 PR 협업 가이드 추가` |
| 구조 개선 중심 | `refactor` | `refactor(movie): 검색 서비스 책임 분리` |
| 테스트 중심 | `test` | `test(review): 리뷰 작성 검증 테스트 추가` |
| 설정/환경 중심 | `chore` | `chore(git): 로컬 설정 파일 추적 제외` |
| 스타일만 수정 | `style` | `style(view): 예약 화면 레이아웃 정리` |

PR 제목 선택 규칙:

| 상황 | 선택 기준 |
|---|---|
| 여러 작업이 섞임 | 가장 중요한 변경을 PR 제목 type으로 사용 |
| 기능 추가 + 문서 수정 | `feat` 사용, 문서 수정은 PR 본문에 작성 |
| 버그 수정 + 테스트 추가 | `fix` 사용, 테스트 추가는 PR 본문에 작성 |
| 구조 개선 + 테스트 수정 | `refactor` 사용, 테스트 수정은 PR 본문에 작성 |

## 10. PR 본문 작성 규칙

이 섹션은 이전 파일과 `git-message-standardizer` 기준을 참고한 초안이다. 실제 HTML 작성 전에는 GitHub PR 템플릿 관례, 팀 리뷰 방식, 테스트 증빙 방식까지 다시 조사한 뒤 확정한다.

PR 본문은 아래 항목을 기본 후보로 작성한다. 단, 실제 문서 작성 시에는 조사 결과에 따라 항목명과 순서를 조정할 수 있다.

```markdown
### 1. 작업 내용

- 

### 2. 변경 이유

- 

### 3. 주요 변경 파일/영역

| 파일/영역 | 변경 내용 |
|---|---|

### 4. 테스트/검증

- [ ] 로컬 실행 확인
- [ ] 단위 테스트 확인
- [ ] 빌드 확인
- [ ] 직접 화면/기능 확인

### 5. 리뷰어 확인 요청

- 

### 6. 남은 문제/주의점

- 
```

PR 본문 작성 기준:

| 항목 | 작성 내용 | 예시 |
|---|---|---|
| 작업 내용 | 무엇을 바꿨는지 | 회원가입 입력값 검증 로직을 추가했습니다. |
| 변경 이유 | 왜 바꿨는지 | 잘못된 회원 정보가 저장 로직까지 전달되는 문제를 막기 위해 변경했습니다. |
| 주요 변경 파일/영역 | 어떤 파일/모듈이 영향을 받는지 | `member`, `reservation`, `docs`, `view` |
| 테스트/검증 | 실제 확인한 항목만 체크 | `[x] 빌드 확인` |
| 리뷰어 확인 요청 | 팀장이 특히 봐야 할 부분 | 예매 실패 시 오류 메시지가 적절한지 확인 부탁드립니다. |
| 남은 문제/주의점 | 이번 PR에 포함하지 않은 범위 | 비밀번호 정책 강화는 별도 작업으로 분리합니다. |

## 11. PR 전 체크리스트

| 체크 항목 | 확인 기준 |
|---|---|
| 현재 브랜치 확인 | `main`이 아니라 작업 브랜치인지 확인 |
| 변경 파일 확인 | 의도하지 않은 파일이 포함되지 않았는지 확인 |
| secret 파일 제외 | `.env`, token, auth 파일 원문이 포함되지 않았는지 확인 |
| commit 메시지 확인 | `type(scope): 한국어 요약` 형식인지 확인 |
| 최신 `main` 반영 | PR 전 작업 브랜치에 최신 `main`을 병합 |
| 테스트/빌드 확인 | 실제 수행한 검증만 PR 본문에 체크 |
| PR 제목 확인 | PR 전체 변경 범위를 대표하는 제목인지 확인 |
| PR 본문 확인 | 작업 내용, 변경 이유, 주요 파일, 테스트, 리뷰 요청, 주의점 포함 |

## 12. 팀장 merge 이후 작업자 동기화 절차

| 순서 | 작업 | 목적 |
|---:|---|---|
| 1 | PR이 merge되었는지 확인 | 팀 저장소 `main` 반영 여부 확인 |
| 2 | 현재 작업 브랜치의 미완료 변경 확인 | 다른 팀원의 merge 내용을 받기 전에 내 변경 상태 확인 |
| 3 | 미완료 변경을 `stash`에 넣거나 임시 commit할지 판단 | pull/merge 전 작업물 손실과 충돌 위험 관리 |
| 4 | 로컬에서 `main`으로 이동 | 최신 기준 브랜치로 이동 |
| 5 | `main` pull | 팀장이 merge한 내용 받기 |
| 6 | 완료된 작업 브랜치 정리 | 더 이상 필요 없는 브랜치 삭제 |
| 7 | 계속 작업 중인 브랜치로 이동 | 다음 작업 또는 이어지는 작업 진행 |
| 8 | 작업 브랜치에 최신 `main` 병합 | 다음 PR 충돌 가능성 감소 |
| 9 | `stash`를 사용했다면 복원 후 충돌 확인 | 임시 보관한 내 변경을 최신 코드 위에 다시 적용 |
| 10 | 충돌 발생 시 해결 후 재테스트 | 병합 후 동작 확인 |
| 11 | 병합/복원 결과 commit 필요 여부 확인 | 충돌 해결 또는 동기화 결과를 이력으로 남길지 판단 |
| 12 | 작업 브랜치 push | 원격 작업 브랜치도 최신 `main` 반영 상태로 업데이트 |

추가 조사 필요:

| 조사 항목 | 조사 이유 | HTML 반영 방향 |
|---|---|---|
| commit 메시지 작성 규칙 | `type`, `scope`, 한국어 summary, 본문 포함 여부를 팀 기준으로 확정해야 함 | commit 규칙 섹션에 좋은 예/나쁜 예, 작업별 type 선택 표, Sourcetree commit 창 작성 예시와 터미널 `git commit -m` 예시를 함께 작성 |

| PR 본문 작성 규칙 | 리뷰어가 확인해야 할 정보와 테스트 증빙 형식을 확정해야 함 | PR 본문 템플릿 후보를 조사한 뒤 작업 내용, 변경 이유, 주요 파일/영역, 테스트/검증, 리뷰 요청, 남은 문제 항목을 확정 |
| 작업별 branch 이름 작성 규칙 | 기능, 버그, 문서, 리팩터링 등 작업 종류에 따라 branch prefix와 이름을 통일해야 함 | `feature/...`, `fix/...`, `docs/...`, `refactor/...`, `test/...`, `chore/...` 같은 후보를 조사해 표로 작성 |
| 여러 작업이 있을 때 branch 분리 기준 | 1번 작업과 2번 작업을 한 branch에 묶을지, 별도 branch와 PR로 나눌지 판단 기준이 필요함 | 관련 없는 작업은 branch/PR 분리, 같은 목표의 작은 하위 작업은 한 branch 허용 같은 기준을 조사 후 체크리스트로 작성 |
| `stash` 사용이 적절한 상황 | 미완료 변경을 commit하지 않고 임시 보관할 때의 장단점 확인 | "다른 팀원 PR merge 전달을 받았을 때" 절차에 우선 후보로 설명 |
| 임시 commit 사용이 적절한 상황 | WIP commit이 충돌 해결과 이력 관리에 어떤 영향을 주는지 확인 | stash와 비교 표로 정리하고 팀 규칙에 따라 권장/비권장 표시 |
| 변경 파일이 있는 상태에서 pull/merge할 때의 위험 | 작업 중인 파일과 최신 `main` 변경이 겹칠 때 실패하거나 충돌이 날 수 있음 | pull 전 상태 확인 체크리스트에 추가 |
| `stash pop`과 `stash apply` 차이 | 복원 중 충돌이 날 때 어떤 방식이 더 안전한지 확인 | 명령어 예시는 조사 후 하나만 기본 절차로 채택 |
| 작업 브랜치에 `main` 병합 후 push 필요성 | 로컬 브랜치만 최신화하면 원격 PR 브랜치가 뒤처질 수 있음 | 6번 흐름과 12번 동기화 절차에 모두 반영 |

## 13. HTML 제작 방식

| 영역 | 제작 방향 |
|---|---|
| 디자인 | 기존 HTML의 가독성 있는 카드/표 스타일은 유지하되 설치 캡처 중심 구성은 제거 |
| 첫 화면 | “팀 저장소 브랜치 PR 협업 가이드” 제목과 핵심 원칙 3개 표시 |
| 표 | 브랜치명, commit type, PR 제목, PR 본문 규칙을 핵심 표로 배치 |
| 절차 설명 방식 | 같은 작업을 Sourcetree GUI 환경에서 하는 방법과 터미널에서 하는 방법으로 각각 안내 |
| 코드 블록 | 터미널 절차에는 꼭 필요한 Git 명령만 짧게 제공 |
| GUI 안내 | Sourcetree 절차에는 메뉴명, 버튼명, 현재 브랜치 확인 위치, push/pull/merge/stash 클릭 흐름을 짧게 제공 |
| 경고 박스 | `main` 직접 commit 금지, secret 파일 push 금지, PR 후 main pull 누락 금지 강조 |
| 반복 흐름 | PR merge 이후 `main pull`과 작업 브랜치 최신화까지 순환 구조로 시각화 |

## 15. 이번 계획에서 정한 가정

- 새 문서는 기존 파일을 덮어쓰지 않고 별도 HTML로 만든다.
- 팀원은 이미 Git과 GitHub를 사용할 수 있는 상태라고 가정한다.
- Fork를 쓰지 않고 팀 저장소에 개인 작업 브랜치를 push하는 방식으로 작성한다.
- commit 메시지와 PR 본문 규칙은 현재 초안이며, 실제 HTML 작성 전에 다시 조사해서 확정한다.
- PR 제목 규칙, branch 명명 규칙, 여러 작업의 branch 분리 기준도 실제 HTML 작성 전에 다시 조사해서 확정한다.
- 새 HTML은 Sourcetree GUI 환경에서의 방법과 터미널에서의 방법을 각각 제공하는 형태로 작성한다.
- 타 팀원의 PR merge 전달을 받은 상황에서는 pull/merge 전 `stash`와 임시 commit 중 무엇을 권장할지 조사 후 확정한다.
- 실제 commit, push, PR 생성, merge는 문서에 설명만 하고 수행하지 않는다.
- `git-message-standardizer`의 메시지 기준은 문서 규칙으로 반영하되, 실제 Git 메시지 작성 작업은 하지 않는다.
