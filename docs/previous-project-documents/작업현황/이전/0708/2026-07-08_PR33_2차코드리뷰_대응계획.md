## 1. 수정 필요 항목 (코드 확인 결과 포함)

### 1) `rewards` 배열의 `null` 원소 → NPE → 500

- 리뷰 지적 위치: `AdminChallengeUpdateRequest.java:26`, `ChallengeService.java:157`
- **코드 확인**: `AdminChallengeUpdateRequest`의 `rewards` 필드는 `@NotEmpty @Valid List<AdminChallengeRewardItemRequest> rewards`(10-28행). `@Valid`는 리스트의 **non-null 원소만** cascade 검증하고, 원소 자체가 `null`인 경우(`"rewards": [null]`)는 막지 못한다. `ChallengeService.validateRewardItems()`(157-163행)에서 `item.rewardType()`을 바로 호출하는데 `item`이 `null`이면 `NullPointerException` → `BusinessException`이 아니므로 `GlobalExceptionHandler`의 catch-all(500)로 떨어진다.
- **대응 방향**: `List<@NotNull(message = "...") AdminChallengeRewardItemRequest> rewards`처럼 원소 레벨 `@NotNull`을 추가해 `MethodArgumentNotValidException`(400)으로 먼저 걸러지게 한다. 서비스단 `validateRewardItems()`에도 `item == null` 방어를 추가하는 걸 함께 권장(DTO 검증이 우회되는 경로가 생기더라도 안전하게).

### 2) `rewardPoint` 음수/0 허용 → 보상 수령 시 포인트가 오히려 차감됨

- 리뷰 지적 위치: `AdminChallengeRewardItemRequest.java:12`, `ChallengeService.java:87-90`
- **코드 확인**: `rewardPoint`는 `Integer`이고 별도 애노테이션이 없다(12행). `ChallengeService.validateRewardItems()`(159행)는 `item.rewardPoint() == null` 여부만 검사하고 값의 부호는 확인하지 않는다. `claimReward()`(87-90행)에서 `int amount = reward.getRewardPoint() * reward.getRewardQuantity();`를 그대로 `pointService.grantOrAdjustPoint(memberId, amount, ...)`에 넘기므로, 관리자가 `rewardPoint=-100`으로 등록하면 사용자가 보상을 "수령"할 때 실제로는 포인트가 100 **차감**된다.
- **대응 방향**: `AdminChallengeRewardItemRequest.rewardPoint`에 `@Min(value = 1, message = "보상 포인트는 1 이상이어야 합니다.")` 추가. `rewardPoint`가 nullable(`Integer`)이라 `@Min`은 `null`을 통과시키므로 `null` 체크(기존 서비스 로직)와 `@Min`을 같이 둬야 한다. `validateRewardItems()`에도 `item.rewardPoint() <= 0`일 때 `VALIDATION_ERROR`를 던지는 방어를 추가하는 걸 권장(DTO만으로 충분할지, 서비스단 이중 방어까지 할지는 §4 결정 필요 참고).

### 3) `memberIds` 리스트 원소 `null` → `findById(null)` → 500

- 리뷰 지적 위치: `AdminCouponIssueRequest.java:9`, `CouponService.java:92-94`
- **코드 확인**: `AdminCouponIssueRequest.memberIds`는 `@NotEmpty List<Long> memberIds`(9행) — 리스트 자체가 비어있는지만 검사하고 원소 `null`은 막지 않는다. `CouponService.issueCoupon()`에서 각 `memberId`로 `memberRepository.findById(memberId)`를 호출하는데, `memberId`가 `null`이면 Spring Data JPA가 `InvalidDataAccessApiUsageException`을 던진다. 이건 `BusinessException`이 아니므로 catch-all(500)로 떨어진다.
- **대응 방향**: `List<@NotNull(message = "...") Long> memberIds`로 원소 레벨 `@NotNull` 추가.

### 4) `page`/`size` 미검증 → `IllegalArgumentException` → 500

- 리뷰 지적 위치: `CouponController.java:31-32`, `PointController.java:29-30`, `AdminCouponController.java:38-39`
- **코드 확인**: 리뷰가 지적한 3개 컨트롤러 전부 `@RequestParam(defaultValue = "0") int page`, `@RequestParam(defaultValue = "10") int size`만 있고 범위 검증이 없다. **추가 확인**: 같은 패턴이 `AdminChallengeController.java:35-36`에도 동일하게 있음(리뷰 코멘트가 언급하지 않은 4번째 지점) — 아래 결정에 따라 이번 라운드에 같이 포함한다. `PageRequest.of(page, size, ...)`는 `page < 0` 또는 `size < 1`일 때 `IllegalArgumentException`을 던지는데, `GlobalExceptionHandler`의 4개 핸들러(`BusinessException`/`MethodArgumentNotValidException`/타입불일치·파라미터누락/catch-all) 중 이걸 잡는 핸들러가 없어 catch-all(500)로 떨어진다.
- **대응 방향 — 확정**: **옵션 A.** 4개 컨트롤러(`CouponController`/`PointController`/`AdminCouponController`/`AdminChallengeController`) 클래스에 `@Validated` 추가 + `@RequestParam @Min(0) int page`, `@RequestParam @Min(1) int size`로 파라미터 레벨 검증. 이 경우 발생하는 예외는 `MethodArgumentNotValidException`이 아니라 `ConstraintViolationException`이라 `GlobalExceptionHandler`에 이 예외를 처리하는 핸들러를 신설한다.
- **응답 형태 — 확정**: `ConstraintViolationException`은 `ErrorCode`를 새로 추가하거나 전역 동작을 바꾸는 게 아니라, 검증 실패 시 스프링이 `throw`하는 예외를 잡아서 기존 `VALIDATION_ERROR` 코드로 변환만 하는 것이므로 **단순 응답**으로 처리한다: `ErrorResponse.of(ErrorCode.VALIDATION_ERROR)`(필드별 상세 없이 `errors: []`). 오늘 이미 추가한 `MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException` 핸들러(`handleBindingException`)와 완전히 같은 패턴이라 일관성도 맞는다.

## 2. 확인 권장 항목 (수정 필수는 아님, 팀 결정 필요)

### 5) 내 쿠폰 목록 조회 N+1 (`CouponService.java:45-52`)

- **코드 확인**: `getMyCoupons()`가 `MemberCoupon` 페이지를 조회한 뒤 `toResponse()`에서 `mc.getCoupon()`을 호출한다(51행). `MemberCoupon.coupon`은 `@ManyToOne(fetch = FetchType.LAZY)`라, 페이지 사이즈만큼 쿠폰 조회 쿼리가 추가로 발생할 수 있다.
- 참고: 1차 코드리뷰 대응계획(`2026-07-07_PR33_코드리뷰_대응계획.md` MEDIUM-4)에서 이미 고친 관리자 목록(`CouponService.getAdminCoupons`, `ChallengeService.getAdminChallenges`)과는 **다른 위치**(회원용 `getMyCoupons`)라 아직 반영되지 않았다.
- **대응 방향**: `MemberCouponRepository`의 조회 메서드에 `@EntityGraph(attributePaths = "coupon")`를 추가하거나 fetch join 쿼리로 전환.

**@EntityGraph vs fetch join 비용 비교(조사 결과)**: `MemberCoupon.coupon`은 `@ManyToOne`(단일 참조, `*-to-one`) 관계다. 이런 관계에서는 `@EntityGraph(attributePaths = "coupon")`와 JPQL의 `LEFT JOIN FETCH mc.coupon`이 **Hibernate 내부적으로 동일한 실행 계획(쿼리 1번, JOIN 1개)으로 컴파일된다** — 즉 쿼리 비용(DB 왕복 횟수, 생성되는 SQL)에는 차이가 없다.

차이는 비용이 아니라 코드량에 있다:
- `@EntityGraph`: `MemberCouponRepository`의 기존 파생 쿼리 메서드 2개(`findByMember_MemberId`, `findByMember_MemberIdAndCouponStatus`, 18/20행)에 애노테이션만 추가하면 된다. 메서드 시그니처·이름 변경 없음.
- fetch join(`@Query` + `JOIN FETCH`): 2개 메서드를 전부 커스텀 JPQL로 다시 써야 해서 코드량이 더 많고, 조건(상태 필터 유무)마다 쿼리를 따로 관리해야 한다.

**결론**: 이번 케이스는 비용 차이가 없으므로 코드가 더 간단한 `@EntityGraph` 쪽을 권장한다. (참고: `*-to-many`(컬렉션) 관계에 fetch join + `Pageable`을 같이 쓰면 Hibernate가 메모리 페이징으로 전환되는 성능 문제가 있는데, `coupon`은 컬렉션이 아니라 단일 참조라 이 문제는 해당 없음.)

### 6) 챌린지 보상 수정 타이밍 정책 (`ChallengeService.java:85`, `142-153`)

- **코드 확인**: 이미 달성했지만 아직 수령하지 않은 진행도가 있는 상태에서 관리자가 `updateChallenge()`로 보상을 바꾸면(149-153행에서 기존 `challenge_reward`를 전부 지우고 새로 저장), `claimReward()`는 수령 시점에 다시 조회한 **최신** 보상을 지급한다(스냅샷 없음, 85행).
- 이건 버그가 아니라 **정책 결정 사항** — **결정: 옵션 A(현행 유지)로 확정.** "보상은 항상 수령 시점 기준"이라는 정책을 코드 주석 + 서비스 테스트 1개로 고정한다(§5-2 참고). 옵션 B(스냅샷 방식)는 채택하지 않는다.

**"진행도가 초기화되냐"는 질문에 대한 답**: 아니다. `challenge_progress`(`current_count`/`achieved_yn`/`achieved_at`)는 이 이슈와 전혀 무관하다. 관리자가 보상을 바꿔도 진행도는 초기화되지 않고 "달성" 상태를 그대로 유지한다.

문제는 순수하게 **"수령 시 실제로 받는 보상의 양(포인트 개수 등)이 언제 기준이냐"**다. 예시:

1. 월요일: 회원 A가 챌린지를 달성(`achieved_yn=true`). 이때 보상은 `rewardPoint=100`으로 설정돼 있었지만 A는 아직 "수령"을 안 함(`reward_claimed_at=NULL`).
2. 화요일: 관리자가 이 챌린지 보상을 100 → 50으로 수정(`updateChallenge()`).
3. 수요일: A가 그제서야 보상을 수령(`claimReward()`). 이 시점에 `ChallengeReward`를 다시 조회하므로, A는 월요일 달성 당시 약속됐던 100이 아니라 화요일에 바뀐 50을 받는다.

즉 "진행도 초기화 여부"가 아니라 **"달성 시점에 약속된 보상 vs 수령 시점의 최신 보상, 어느 쪽을 지급하느냐"**의 문제다. 옵션 A(현행 유지)는 "항상 수령 시점 기준"으로 그대로 두는 것이고, 옵션 B(스냅샷)는 "달성한 시점에 이미 확정된 보상을 나중에 그대로 지급한다(관리자가 나중에 바꿔도 이미 달성한 사람에겐 영향 없음)"는 뜻이다.

### 3-1. 범위 밖 항목을 실제로 구현한다면 (설계 스케치, 지금 구현하지 않음)

#### A. 챌린지 `rewardType=coupon` 지급 연동

현재 `validateRewardItems()`(`ChallengeService.java:159`)가 `rewardType=coupon` 등록 자체를 막고 있다(1차 코드리뷰 대응계획 HIGH-1 옵션 A로 이미 적용됨). 구현하려면 이 차단부터 풀어야 한다.

필요한 변경(전부 신규 코드, 지금 안 함):
1. `validateRewardItems()`를 "`rewardType=coupon`이면 `couponId`가 채워져 있어야 한다"로 완화(1차 문서의 원래 옵션 B 방향).
2. `ChallengeService.claimReward()`의 87-93행 반복문에 `else if ("coupon".equals(reward.getRewardType()) && reward.getCouponId() != null)` 분기를 추가해 `CouponRepository.findById(couponId)`로 쿠폰을 조회하고 `reward.getRewardQuantity()`만큼 `MemberCoupon.create(member, coupon)`을 저장. 기존 `CouponService.issueCoupon()`(관리자 다건 발급용)의 발급 로직을 회원 1명 발급용으로 재사용하거나 별도 메서드로 분리 필요.
3. `ChallengeRewardClaimResponse`(현재 `rewardClaimedAt`/`grantedPoint`만 있음)에 발급된 쿠폰 정보(`issuedCoupons`)를 추가해야 응답에서 확인 가능. `AttendanceCheckResponse`가 이미 같은 패턴의 `issuedCoupons` 필드를 갖고 있어 참고 가능.
4. 포인트 지급과 쿠폰 발급이 같은 트랜잭션에서 실행돼야 하는데, `claimReward()` 전체가 이미 `@Transactional`이라 이 부분은 추가 작업 없이 만족됨.

2. `AttendanceService.checkIn()`의 `calculateConsecutiveDays()` 이후 `consecutiveDays == 7` 또는 `== 30`일 때 위 설정을 조회해서 `MemberCoupon` 발급.
3. `AttendanceCheckResponse.issuedCoupons`(현재 항상 빈 리스트)를 실제 발급 결과로 채움.
4. 멱등성 검증 필요: `checkIn()`은 하루 1번만 성공하도록 이미 막혀 있어 중복 발급 위험은 낮지만, "7일째 발급 도중 트랜잭션이 실패해서 재시도할 때 중복 발급되지 않는지"는 별도 확인 필요.

**결론**: A(쿠폰 보상)는 기존 코드 구조 안에서 상대적으로 작은 변경으로 가능하지만, B(연속 출석 쿠폰)는 스키마 설계 결정이 선행돼야 하는 더 큰 작업이다.

## 4. 결정 사항 (전부 확정)

1. **1~4번(수정 필요)**: 이번 라운드에 처리한다.
2. **2번(`rewardPoint` 검증)**: **이중 방어로 확정.** DTO `AdminChallengeRewardItemRequest.rewardPoint`에 `@Min(1)` 추가 + 서비스단 `ChallengeService.validateRewardItems()`에도 `item.rewardPoint() <= 0` 방어를 같이 넣는다.
3. **4번(`page`/`size` 검증)**: **옵션 A로 확정.** 4개 컨트롤러(`CouponController`/`PointController`/`AdminCouponController`/`AdminChallengeController`, 리뷰 코멘트가 지적한 3개 + 같은 패턴인 `AdminChallengeController` 포함)에 `@Validated` + `@Min(0) page`/`@Min(1) size` 추가, `GlobalExceptionHandler`에 `ConstraintViolationException` 핸들러 신설. 응답은 필드별 상세 없이 `ErrorResponse.of(ErrorCode.VALIDATION_ERROR)` 단순 응답으로 확정(새 `ErrorCode` 추가나 전역 동작 변경이 아니라 기존 `VALIDATION_ERROR`로 변환만 하는 것). **이 핸들러는 전역(`@RestControllerAdvice`)에서 쓰이므로, 실제 구현 시 별도 markdown 문서를 `docs/작업현황`에 남긴다 — 아래 §5 참고.**
4. **6번(보상 수정 타이밍 정책)**: **옵션 A(현행 유지)로 확정.** `ChallengeService.claimReward()`/`updateChallenge()` 근처에 "보상은 항상 수령 시점 기준"이라는 코드 주석을 남기고, **`ChallengeServiceTest`에 이 정책을 고정하는 서비스 테스트 1개를 추가한다**(§5-2 참고). 별도 markdown 문서는 지금 만들지 않고, 정책이 나중에 실제로 바뀌어야 할 필요가 생기면 그때 만든다.
5. **5번(N+1)**: **이번 라운드에 같이 구현한다.** `MemberCouponRepository`의 `findByMember_MemberId`/`findByMember_MemberIdAndCouponStatus`에 `@EntityGraph(attributePaths = "coupon")` 추가(§2-5절 비용 비교 근거).
6. **3-1절(범위 밖 A/B 구현)**: **이번 라운드 대상 아님, 나중에 별도 라운드로 진행.** 특히 B(연속 출석 쿠폰)는 스키마 결정이 선행돼야 해서 별도 계획 문서가 먼저 필요하다.

## 5. 이번 라운드 실행 시 남겨야 할 추가 문서

### 5-1. `GlobalExceptionHandler`에 `ConstraintViolationException` 핸들러 추가 시 (4번 관련)

`GlobalExceptionHandler`는 `@RestControllerAdvice`로 프로젝트 전체에 전역 적용되는 클래스다. 이번처럼 여기에 핸들러를 새로 추가할 때마다(오늘까지 이미 2번째 추가 — `MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException`에 이어), **팀장 공유용으로 별도 markdown 문서를 `docs/작업현황`에 남긴다.** 이전에 만든 `2026-07-07_GlobalExceptionHandler_수정_원인결과검증.md`와 같은 형식을 따르되, 이번 변경 기준으로 아래 3가지를 반드시 포함한다.

1. **수정 이유**: `page`/`size`에 `@Min` 검증을 추가하면서 발생하는 `ConstraintViolationException`이 현재 어떤 핸들러에도 안 걸려 500으로 응답되는 문제를 400으로 바로잡기 위함(리뷰 코멘트 근거, 실제 재현 증거 포함).
2. **기존 코드에 대한 영향**: `@RestControllerAdvice`가 전역이므로 이 예외 타입이 발생하는 다른 모든 API(이번 챌린지/출석/포인트/쿠폰 API 이외의 API 포함)에도 영향을 준다는 점을 명시. 기존 3~4개 핸들러(`BusinessException`/`MethodArgumentNotValidException`/타입불일치·파라미터누락/catch-all)의 동작이 바뀌지 않는지 재확인한 근거(예: 관련 키워드로 기존 테스트 전수 검색한 결과)를 남긴다.
3. **기존 코드 + 새로운 코드인지, 기존 코드 수정 + 추가인지 명시**: 이번 변경은 **기존 핸들러 3~4개를 한 줄도 안 건드리고 `@ExceptionHandler(ConstraintViolationException.class)` 메서드 1개만 새로 추가하는 것**이므로 "기존 코드 + 새로운 코드 추가"에 해당한다는 걸 명확히 적는다(기존 코드를 고쳐서 동작을 바꾸는 게 아님).

### 5-2. 보상 수정 타이밍 정책 — 코드 주석 + 서비스 테스트 (6번 관련)

`ChallengeService.claimReward()`(87행 근처)와 `updateChallenge()`(142행 근처)에 아래 취지의 주석을 남긴다(실행 시 정확한 문구는 코드 컨벤션에 맞춰 조정).

```java
// 정책: 챌린지 보상은 "달성 시점"이 아니라 "수령 시점"에 조회한 최신 challenge_reward를 지급한다.
// 즉 달성 후 미수령 상태에서 관리자가 보상을 변경하면, 이후 수령 시 변경된 보상이 지급된다(의도된 동작).
// 이 정책을 스냅샷 방식으로 바꿔야 한다면 별도 계획 문서 작성 후 진행할 것.
```

추가로 `ChallengeServiceTest`에 이 정책을 고정하는 서비스 테스트를 1개 추가한다(테스트명 예시: `claimReward_달성후_보상변경되면_수령시점_최신보상을_지급한다`). 시나리오: ① 챌린지 보상을 A로 설정 → ② 회원 진행도를 달성+미수령 상태로 세팅 → ③ 보상을 B로 변경(`updateChallenge()` 또는 리포지토리 직접 조작) → ④ `claimReward()` 호출 → ⑤ 지급된 포인트가 B 기준인지 검증. 이 테스트가 실패하면 정책이 코드에서 실제로 깨졌다는 뜻이므로 회귀를 잡아준다. 별도 markdown 문서는 지금 만들지 않는다.

## 6. 회귀 테스트 계획 (외부 검토 반영 — 이번 라운드 필수 항목)

이 계획을 그대로 구현해도 테스트로 고정하지 않으면 "PR 코멘트에 대응했다"고 안전하게 말하기 어렵다는 지적을 반영해, 1~6번 항목마다 최소 테스트를 아래처럼 정한다. 코드 수정과 같은 라운드에서 전부 추가한다.

| 항목 | 테스트 대상 | 테스트 케이스(최소) |
|---|---|---|
| 1) `rewards` null 원소 | `AdminChallengeUpdateRequest` 검증(Bean Validation 단위 테스트) 또는 `AdminChallengeController` 통합 테스트 | `rewards: [null]` 요청 시 500이 아니라 400 `VALIDATION_ERROR`로 응답 |
| 2) `rewardPoint` 음수/0 | `AdminChallengeRewardItemRequestTest`(DTO) + `ChallengeServiceTest`(서비스) | DTO: `rewardPoint=0`/`rewardPoint=-1`이 `@Min` 위반으로 걸러지는지. 서비스: DTO 검증을 우회한 값이 들어와도 `validateRewardItems()`가 막는지(이중 방어 확인) |
| 3) `memberIds` null 원소 | `AdminCouponIssueRequestTest`(신규 또는 기존 파일에 추가) | `memberIds: [null]` 요청 시 500이 아니라 400 `VALIDATION_ERROR`로 응답 |
| 4) `page`/`size` 검증 | 4개 컨트롤러 각각(최소 슬라이스/통합 테스트 1개씩, 또는 공통 테스트 유틸로 파라미터화) | `page=-1` 또는 `size=0` 요청 시 500이 아니라 400 `VALIDATION_ERROR`로 응답 |
| 5) 내 쿠폰 목록 N+1 | `MemberCouponRepositoryTest` 또는 `CouponServiceTest` | `@EntityGraph` 적용 후 `getMyCoupons()` 호출 시 쿠폰 정보가 정상적으로 채워지는지(값 검증). 쿼리 횟수 자체를 자동 테스트로 고정하긴 어려우니(Hibernate Statistics 별도 설정 필요) 최소한 "정상 동작"은 테스트로 커버하고, 쿼리 횟수 감소는 로컬에서 SQL 로그로 1회 수동 확인하는 것으로 충분 |
| 6) 보상 수정 타이밍 정책 | `ChallengeServiceTest` | §5-2에 적은 시나리오(보상 변경 후 수령 시 최신 보상 지급 확인) |

이 표의 각 행을 이번 라운드의 완료 조건에 포함한다. 코드만 고치고 테스트 없이 "빌드 통과"만으로 완료 보고하지 않는다.
