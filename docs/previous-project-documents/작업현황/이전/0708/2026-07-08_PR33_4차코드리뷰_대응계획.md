## 3. LOW-2: page/size 회귀 테스트가 실제 400 흐름을 검증하지 않음

### 3-1. 현재 코드 확인 결과

`AdminChallengeControllerTest.java`(및 동일 패턴의 `CouponControllerTest.java`, `AdminCouponControllerTest.java`, `PointControllerTest.java`) 확인:

- `MockMvcBuilders.standaloneSetup(new XxxController(...))`로 컨트롤러 인스턴스를 직접 생성해서 MockMvc를 구성.
- `page`/`size` 음수·0 케이스는 `validator.forExecutables().validateParameters(...)`로 **Bean Validation 제약이 파라미터에 붙어 있는지만** 직접 확인(리플렉션 기반).
- 실제 HTTP 요청(`GET .../api/v1/...?page=-1`)을 보내 컨트롤러 계층에서 400이 나오는지는 테스트하지 않음.
- 원인(이전 세션에서 확인됨): `standaloneSetup()`은 스프링 컨테이너 없이 컨트롤러 인스턴스를 그대로 사용하므로, `@Validated`가 실제로 동작하려면 필요한 AOP 프록시(`MethodValidationInterceptor`)가 걸리지 않음. 즉 순수 `standaloneSetup()`로는 `page=-1` 요청을 보내도 400이 아니라 정상 처리(또는 다른 예외)로 흐른다.

### 3-2. 수정 방안

컨텍스트 로딩 없이 가장 가벼운 방식으로 실제 AOP 검증 경로를 재현:

- `MethodValidationPostProcessor`를 테스트에서 직접 생성해 `afterPropertiesSet()` 호출 후, 컨트롤러 인스턴스를 `postProcessAfterInitialization(...)`으로 감싸 **실제 검증 프록시**를 만들고, 그 프록시를 `standaloneSetup()`에 전달.
- 이 프록시에 대해 `mockMvc.perform(get(...).param("page","-1"))` / `param("size","0")`을 실제로 호출해서 `.andExpect(status().isBadRequest())`로 검증하는 테스트를 4개 컨트롤러 테스트 파일에 각각 추가.
- 기존 `validateParameters()` 기반 테스트(제약이 붙어 있는지 확인)는 그대로 두거나, 새 MVC 레벨 테스트로 대체 — **대체보다는 추가를 권장**(제약 존재 여부 확인과 실제 HTTP 400 확인은 서로 다른 것을 검증하므로 둘 다 남기는 게 회귀 방어에 유리).
- `@WebMvcTest`/`@SpringBootTest` 방식은 `SecurityConfig`(`common/config/SecurityConfig.java`)가 존재해서 시큐리티 필터/인증 목킹까지 추가로 필요해지므로 **채택하지 않음**(더 무거움, 이번 프로젝트 테스트 스타일과도 어긋남).

### 3-2-1. (외부 리뷰로 추가 발견) 4개 파일의 `standaloneSetup()` 구성이 서로 다름 — 공통 헬퍼 필요

`rg`로 4개 테스트 파일의 `setUp()`을 직접 대조한 결과, **4개 파일이 동일하지 않음**:

- 이유: `CouponController`/`PointController`는 메서드 파라미터에 `@AuthenticationPrincipal CustomUserDetails userDetails`를 받음(각 컨트롤러 코드 확인 완료). Admin 쪽 2개 컨트롤러는 이 파라미터가 없음.
- **MethodValidationPostProcessor 프록시를 4개 파일에 그대로 복붙하면 위 차이를 놓치기 쉬움**(외부 리뷰 지적대로 "깨지기 쉬움"). Coupon/Point 테스트에서 프록시로 감싼 컨트롤러 인스턴스를 `standaloneSetup()`에 넘길 때 기존 `.setCustomArgumentResolvers(new AuthenticationPrincipalArgumentResolver())`를 빠뜨리면 `@AuthenticationPrincipal` 파라미터 바인딩이 깨져 400이 아니라 다른 예외/에러로 테스트가 실패함.
- **적용 방침**: 4개 파일에 동일한 프록시 생성 로직(`MethodValidationPostProcessor` 부분)만 공통되고, `setCustomArgumentResolvers`는 파일별 기존 설정을 그대로 유지 — 즉 "prox로 감싼 컨트롤러 인스턴스를 넘기는 것" 외에는 각 파일의 기존 `standaloneSetup()` 체인(`.setControllerAdvice(...)`, Coupon/Point는 `.setCustomArgumentResolvers(...)`까지)을 그대로 보존.
- **공통 유틸 클래스로 뽑지 않고, 4개 파일에 각각 짧은 private 메서드로 중복 허용(§5 결정 사항 8번 확정)**: `src/test/java/com/acorn/abc/common/` 폴더가 현재 프로젝트에 존재하지 않음(확인 완료) — 즉 테스트 간 공유 유틸 자체가 지금까지 하나도 없던 프로젝트에 이번 4개 파일만을 위해 새로 만드는 건 시기상조(재사용처가 이번 PR 범위 밖으로 확장될 근거 없음). 새 유틸을 만들면 그 자체가 "다른 도메인 테스트도 가져다 쓸 수 있는 새 전역 테스트 인프라"가 되어 이번 PR 범위를 넘는 영향이 생기므로, 대신 각 파일에 `MethodValidationPostProcessor` 프록시 생성 코드(5줄 안팎)를 그대로 복붙한다.

### 3-3. 영향받는 파일

- `src/test/java/com/acorn/abc/admin/challenge/controller/AdminChallengeControllerTest.java` — 프록시 + `GlobalExceptionHandler`만
- `src/test/java/com/acorn/abc/coupon/controller/CouponControllerTest.java` — 프록시 + `GlobalExceptionHandler` + `AuthenticationPrincipalArgumentResolver` 유지
- `src/test/java/com/acorn/abc/admin/coupon/controller/AdminCouponControllerTest.java` — 프록시 + `GlobalExceptionHandler`만
- `src/test/java/com/acorn/abc/member/controller/PointControllerTest.java` — 프록시 + `GlobalExceptionHandler` + `AuthenticationPrincipalArgumentResolver` 유지

각 파일에 `page=-1`, `size=0` 케이스 2개씩(컨트롤러당 최소 2개, 총 8개) 실제 400 검증 테스트 추가.

## 4. Swagger/Postman 수동 테스트 필요 여부 (명시)

이전 라운드(2~3차)와 달리 이번 계획에는 Swagger/Postman 절차를 별도로 만들지 않았다. **"계획이 없어서 안 쓴 것"이 아니라, 항목별로 필요 여부를 판단한 결과 "이번 3건은 전부 수동 API 테스트 없이 자동화 테스트(단위/MVC)만으로 충분하다"고 판단해서 의도적으로 뺀 것**이다. 근거는 항목별로 다음과 같다.

| 항목 | Swagger/Postman 필요 여부 | 이유 |
|---|---|---|
| MEDIUM-1 (progress N+1) | **불필요(권장)** | API 요청/응답 스키마(`ChallengeResponse` 필드 구성)가 전혀 바뀌지 않음. 바뀌는 건 내부 쿼리 횟수뿐이라 겉으로 드러나는 응답 값으로는 검증할 수 없고, 오직 "쿼리가 몇 번 호출됐는지"만 확인하면 되므로 `verify(challengeProgressRepository).findByMember_...In(...)` 같은 Mockito 단위 테스트가 Swagger보다 더 정확한 검증 수단임. 다만 회귀 확인 차원에서 로컬 실행 중 `GET /api/v1/challenges` 한 번 정도 눈으로 확인하는 것은 선택적으로 해볼 수 있음(§5 결정 사항 4번 참고). |
| LOW-1 (PR 본문 §8) | **해당 없음** | 코드 변경이 아니라 PR 본문 텍스트 수정이므로 API 테스트 대상 자체가 아님. |
| LOW-2 (page/size 400 테스트) | **불필요** | 이 항목 자체가 "Swagger로 수동 확인하던 것을 자동화된 MVC 테스트로 대체"하는 게 목적. `MethodValidationPostProcessor` 기반 테스트가 통과하면 `page=-1`/`size=0` → 400 흐름이 실제로 검증되므로, 같은 걸 Swagger로 또 눌러볼 필요가 없음. |

2~3차 때 Swagger 계획을 만들었던 이유는 그때 항목들(쿠폰 보상 검증, `challengeType`/`status` `@Pattern`)이 **DTO 검증 실패 시 응답 코드/메시지가 실제로 400으로 내려오는지**를 API 계약 관점에서 확인해야 했기 때문이다(응답 스키마·상태 코드가 바뀌는 변경). 이번 3건은 그 성격이 아니므로 계획을 세우지 않았다.

## 5. 결정 사항

아래는 계획 문서 작성자(나)가 임의로 정하지 않고 사용자가 확정해야 할 사항이다.

1. **MEDIUM-1의 `toResponse()` 시그니처 변경 방식 — 확정, 이대로 진행.**

   **`memberId` 제거 영향 분석(사용자 질문 답변):**
   - `toResponse()`는 `private` 메서드이고, 정의부(190행)와 호출부(61행) **단 2곳뿐** — 둘 다 `ChallengeService.java` 안에 있고, 둘 다 이번 MEDIUM-1 작업에서 어차피 같이 수정하는 지점임.
   - `rg -n "toResponse\("`로 `ChallengeService.java`/`ChallengeServiceTest.java` 전체를 검색한 결과 다른 호출부·다른 클래스의 참조·리플렉션 기반 테스트 없음.
   - §1-3에서 이미 확인했듯 `getChallenges()`(따라서 `toResponse()`도 간접적으로) 를 직접 테스트하는 기존 테스트가 0개라, "시그니처가 바뀌어서 깨지는 기존 테스트"도 없음.
   - **결론: 영향 범위가 이 파일 안, 이번에 수정할 2줄로 완전히 닫혀 있어 제거해도 안전함.** 다른 파일/다른 기능에 미치는 영향 없음.

2. **batch 조회 메서드 — 확정, 2개 분리안으로 진행.** (`...ChallengeIdInAndProgressDate(...)` DAILY용 + `...ChallengeIdIn(...)` TOTAL용)
3. **`ChallengeServiceTest`의 `challenge()` 헬퍼 — 확정, ①오버로드 추가 방식으로 진행.** (`challenge(id, name, challengeType)` 신규 오버로드, 기존 `challenge(id, name)`은 내부에서 `"DAILY"`를 넘기도록 위임 — 기존 테스트 5개 무영향)
4. **MEDIUM-1 로컬 Swagger 회귀 확인 — 확정, 하지 않음.** 단위 테스트(Mockito `verify`)로만 검증.
5. **LOW-2 기존 `validateParameters()` 테스트 처리 — 확정, 기존 테스트 유지 + MVC 400 테스트 신규 추가.**
6. **작업 순서 — 아래 §6대로 재배치(의존성 분석 반영).** 순서 자체는 결과에 영향 없다는 전제 하에, "한 번 한 작업이 다음 작업 때문에 다시 손대야 하는" 상황이 없도록 재배열함. 근거는 §6 상단 설명 참고.
7. **(외부 리뷰 반영, 스코프 조정 후 확정) TOTAL 그룹 중복 progress row 처리 — "정교한 병합 규칙"이 아니라 "최소 방어"로 확정.** `ChallengeProgress.create(...)` 호출부가 코드베이스 전체에 1곳뿐이고 항상 기존 row 존재 여부를 먼저 확인하므로, 앱 코드 경로로는 TOTAL 챌린지에 회원당 row가 2개 이상 생기는 상황이 실제로 발생하지 않음(재확인 완료). 발생하지 않는 상황을 위한 "최신 progressDate 우선" 같은 비즈니스 규칙은 만들지 않고, `Collectors.toMap(..., ..., (a, b) -> a)`로 병합 함수만 채워 `IllegalStateException` 크래시만 방지한다(§1-2, §1-4 반영 완료).
8. **(외부 리뷰 반영, 확정) LOW-2 공통 로직 분리 — 유틸 클래스 신설 안 함, 4개 파일에 중복 허용.** `src/test/java/com/acorn/abc/common/` 폴더가 프로젝트에 아예 없어(테스트 공유 유틸 전례 없음) 이번 4개 파일만을 위해 새 유틸을 만드는 건 시기상조로 판단. 신설하면 다른 도메인 테스트도 가져다 쓸 수 있는 새 전역 테스트 인프라가 생겨 이번 PR 범위를 넘는 영향이 발생하므로, `MethodValidationPostProcessor` 프록시 생성 코드(5줄 안팎)를 4개 파일에 각각 복붙하는 쪽으로 확정(§3-2-1 반영 완료).

이 문서는 계획 문서이며, 위 결정 사항 1~8번이 모두 확정됐으므로 다음 지시 시 바로 §6 순서대로 구현을 시작한다.

## 6. 진행 순서 (승인 시, 의존성 분석 기반 재배치)

**의존성 분석**: 3개 작업이 건드리는 파일이 서로 겹치는지 확인한 결과:

| 작업 | 건드리는 파일 | 다른 작업과 파일 겹침 |
|---|---|---|
| LOW-1 | PR 본문(GitHub, `gh pr edit`) | 없음 — 코드 파일과 완전히 무관 |
| MEDIUM-1 | `ChallengeProgressRepository.java`, `ChallengeService.java`, `ChallengeServiceTest.java` | 없음 |
| LOW-2 | `AdminChallengeControllerTest.java`, `CouponControllerTest.java`, `AdminCouponControllerTest.java`, `PointControllerTest.java` | 없음 |

세 작업 모두 파일이 완전히 분리돼 있어 **어떤 순서로 해도 서로 다시 손댈 일이 없음**. 다만 "먼저 해도 이후 작업 때문에 무효화되지 않는 것"을 기준으로 우선순위를 매기면:

- **LOW-1이 가장 안전**: 지금 §8에 있는 깨진 문장을 정리하는 것뿐이라, 이후 MEDIUM-1/LOW-2 코드 작업 결과와 무관하게 먼저 끝내도 됨. (단, 이번 4차 리뷰 대응 자체를 PR 본문에 새 섹션으로 기록하는 건 이 문서 범위 밖 — §8 정리만 지금 하고, "4차 리뷰 대응 §9 기록"은 전체 코드 작업이 끝난 뒤 별도로 필요할 수 있음. 이 경우 §8 정리를 지금 하든 나중에 §9와 같이 하든 결과는 같으므로 무효화 아님.)
- MEDIUM-1과 LOW-2는 파일이 겹치지 않으므로 순서 무관.

**최종 순서:**

1. LOW-1: PR 본문 §8 재작성 초안 최종 확정 → 사용자 승인 후 `gh pr edit` (다른 작업과 무관, 먼저 끝내도 이후 재작업 없음)
2. MEDIUM-1 구현: `ChallengeProgressRepository` batch 메서드 2개 추가 → `ChallengeProgressRepositoryTest`에 batch 메서드 테스트 추가(필수, §1-4) → `ChallengeService.getChallenges()`/`toResponse()` 리팩터(`memberId` 제거, DAILY/TOTAL 그룹별 빈 리스트 가드, `Collectors.toMap`에 `(a, b) -> a` 최소 병합 함수 적용) → `ChallengeServiceTest`에 신규 테스트 추가(`challenge()` 헬퍼 오버로드 포함)
3. LOW-2 구현: 4개 컨트롤러 테스트 파일 각각에 `MethodValidationPostProcessor` 프록시 생성 코드 추가(유틸 클래스 신설 없음) → 실제 400 MVC 테스트 추가(Coupon/Point는 기존 `AuthenticationPrincipalArgumentResolver` 유지, 기존 `validateParameters()` 테스트도 유지)
4. `.\gradlew.bat test` 실행해서 회귀 확인(기존 `CategoryRepositoryTest` 1건 실패는 무관 이슈로 계속 별개 취급)
5. 전체 diff 확인 후 커밋 메시지 초안 작성(git-message-standardizer) → 사용자 승인 후 커밋/푸시
