## 1. MEDIUM — 수정 필요 (1건)

### `AdminChallengeUpdateRequest.challengeType`/`status` 허용값 검증 누락

- 리뷰 지적 위치: `AdminChallengeUpdateRequest.java:15-25`
- **코드 확인**: 현재 `challengeType`(16행), `status`(25행) 둘 다 `@NotBlank`만 있고 허용값 검증이 없다.
  ```java
  @NotBlank(message = "챌린지 유형은 필수입니다.")
  String challengeType,
  ...
  @NotBlank(message = "상태는 필수입니다.")
  String status,
  ```
- schema.sql 115-116행 CHECK 제약: `chk_challenge_challenge_type CHECK (challenge_type IN ('DAILY', 'TOTAL'))`, `chk_challenge_status CHECK (status IN ('ACTIVE', 'INACTIVE'))`.
- **리스크**: `challengeType="INVALID"`처럼 잘못된 값이 DTO 검증을 통과하면 `ChallengeService.updateChallenge()`의 `challenge.update(...)`까지 진행된 뒤 flush/commit 시점에 DB CHECK 제약 위반(`DataIntegrityViolationException`)으로 떨어진다. 현재 `GlobalExceptionHandler`에는 이 예외 전용 핸들러가 없어 catch-all(500)로 응답된다. 2차 리뷰 대응 때 다른 DTO들(`AdminCouponCreateRequest`, `AdminChallengeRewardItemRequest`)에는 이미 이런 허용값 검증을 넣었는데 이 두 필드만 빠져 있었다.
- **대응 방향**: 기존에 이미 쓰고 있는 패턴과 동일하게 `@Pattern` 추가.
  ```java
  @NotBlank(message = "챌린지 유형은 필수입니다.")
  @Pattern(regexp = "DAILY|TOTAL", message = "챌린지 유형은 DAILY 또는 TOTAL만 허용됩니다.")
  String challengeType,
  ...
  @NotBlank(message = "상태는 필수입니다.")
  @Pattern(regexp = "ACTIVE|INACTIVE", message = "상태는 ACTIVE 또는 INACTIVE만 허용됩니다.")
  String status,
  ```
- **테스트**: `AdminChallengeUpdateRequestTest`(2차 리뷰 대응 때 이미 만든 파일)에 `challengeType`/`status`가 허용값 밖이면 거부되는 케이스 추가.

## 3. `CategoryRepositoryTest` 실DB 테스트 격리 이슈 — 참고 기록 (수정 범위 아님)

**이 절은 실제 수정 계획이 아니라 원인 분석 참고 기록이다.** `CategoryRepositoryTest`/`CollectionRepositoryTest`/`BookRepositoryTest`는 `book`/`category`/`collection` 도메인 소속 파일로, 챌린지/출석/포인트/쿠폰 담당 범위 밖이다. PR #31은 "같은 종류의 실DB 테스트 격리 문제를 다른 팀원이 어떻게 고쳤는지" 참고하기 위해 확인한 것이지, 그 기법을 이 파일들에 직접 적용하겠다는 뜻이 아니다. **이번 PR #33 범위에서 이 파일들을 수정하지 않는다.**

### 3-1. PR #31에서 배운 것 (참고)

PR #31(`test(book): BookApprovalServiceTest 실DB 잔여 데이터 flaky 실패 수정`)의 원인/해결 요약:

| 항목 | 내용 |
|---|---|
| 원인 1 | `AladinCategoryUpsertService.createOrGet()`이 `REQUIRES_NEW`라서, 테스트 트랜잭션이 롤백돼도 그 안에서 생성된 category row는 이미 커밋돼 남음 |
| 원인 2 | 테스트 fixture의 `aladin_category_id="2724"`가 실제 알라딘 category id와 겹쳐서, 실제 book이 그 category를 참조하면 재실행마다 실패 |
| 원인 3 | ISBN fixture도 이전 실행 잔여가 남아 UNIQUE 충돌 |
| 해결 1 | `@BeforeEach`에서 독립 트랜잭션(`REQUIRES_NEW`)으로 **이 테스트의 fixture만** 먼저 삭제 후 시작 |
| 해결 2 | fixture 값을 실제 값과 절대 안 겹치는 테스트 전용 값(`TEST-2724`)으로 교체 |

핵심 철학: **"실제/다른 테스트 데이터와 충돌할 수 있는 지점을 전부 테스트 전용 식별자로 격리한다."**

### 3-2. `CategoryRepositoryTest`가 실패하는 이유 (참고, PR #33 본문에 이미 원인만 기록된 상태 — 재확인)

`CategoryRepositoryTest.java` 현재 코드(36-41행):

```java
@Test
void findsOnlyActiveCategoriesOrderedByDisplayOrder() {
    List<Category> categories = categoryRepository.findByStatusOrderByDisplayOrderAscCategoryIdAsc("ACTIVE");

    assertThat(categories).extracting(Category::getCategoryName).containsExactly("Essay", "Novel");
    assertThat(categories).extracting(Category::getStatus).allMatch("ACTIVE"::equals);
}
```

- 이 테스트는 PR #31의 `REQUIRES_NEW` 문제와는 원인이 다르다. `@DataJpaTest`는 기본적으로 테스트마다 트랜잭션을 롤백하므로 "이 테스트 자신이 만든 잔여 데이터"가 남는 문제가 아니다.
- **진짜 원인**: `findByStatusOrderByDisplayOrderAscCategoryIdAsc("ACTIVE")`가 테이블 전체에서 ACTIVE 카테고리를 전부 가져오는데, `containsExactly("Essay", "Novel")`는 "정확히 이 2건만 있어야 통과"라고 요구한다. 공유 실DB에 이 테스트가 만들지 않은 다른 ACTIVE 카테고리 데이터가 하나라도 있으면 무조건 실패한다.
- PR #31의 "실제 값과 안 겹치는 fixture" 철학은 참고할 만하지만(fixture 이름 `"Novel"`/`"Essay"`가 실제 카테고리명과 겹칠 법함), **적용 여부와 방식은 이 파일을 담당하는 팀원이 결정할 사항**이다.

이 내용은 PR #33 본문에 "1건 실패, 기존에 이미 원인 분석된 이슈"로만 언급하는 근거 자료로 남긴다. 실제 수정은 이번 PR 범위 밖이다.

## 4. Swagger 테스트 계획 (1번 MEDIUM 항목용)

이번 수정은 단건 검증 실패 케이스라 Postman 동시성 도구 없이 **Swagger만으로 충분**하다(2차 리뷰 대응 때 `rewardType=coupon` 차단을 검증한 것과 같은 성격).

| 순서 | 요청 | 기대 결과 |
|---|---|---|
| 1 | `PUT /api/v1/admin/challenges/{challengeId}` — `challengeType="WEEKLY"`(DAILY/TOTAL 외 값) | 400 `VALIDATION_ERROR`(500 아님) |
| 2 | `PUT /api/v1/admin/challenges/{challengeId}` — `status="DELETED"`(ACTIVE/INACTIVE 외 값) | 400 `VALIDATION_ERROR`(500 아님) |
| 3 | `PUT /api/v1/admin/challenges/{challengeId}` — `challengeType="TOTAL"`, `status="INACTIVE"`(정상값, 회귀 확인) | 200 `OK`, 기존과 동일하게 정상 반영 |

상세 절차(Swagger 요청 본문, 기대 응답, 다르게 나올 때 확인 위치)는 별도 체크리스트 문서로 분리했다:

- 체크리스트: `docs/작업현황/2026-07-08_AdminChallengeUpdate_검증_체크리스트.md`
- 실행 SQL: `api-test-results/챌린지출석포인트쿠폰 API/0708/2026-07-08_AdminChallengeUpdate_검증_실행.sql`

### 4-1. DB 준비 방식 — 이번엔 "백업 → 비움 → 삽입 → 원복" 방식을 쓴다

이전 라운드들(2026-07-07/2026-07-07 Postman 계획 등)은 "DDL+data.sql만 있고 관련 테이블은 원래 비어 있다"고 가정하고, 기존 데이터를 건드리지 않은 채 새 이름의 테스트 전용 행만 추가하는 방식이었다. 이번엔 다르게 진행한다:

1. 이 테스트가 건드리는 `challenge`/`challenge_reward` 테이블의 **현재 있는 내용을 통째로 백업 테이블로 복제**한다.
2. 원본 `challenge`/`challenge_reward`를 **비운다**(DDL+data.sql만 적용한 직후 상태와 동일하게 — `data.sql`은 `member_grade`만 시드하고 이 두 테이블은 시드하지 않으므로, "비운 상태"가 곧 그 상태와 같다).
3. 이 테스트에 필요한 **최소한의 새 데이터만** 삽입해서 Swagger 테스트를 진행한다.
4. 테스트가 끝나면 비운 테이블에 **백업해둔 원래 내용을 그대로 다시 채워 넣어 원복**한다.

이유: 이 테스트는 실제 DB에 이미 있는 챌린지 데이터를 건드릴 위험이 있는 `PUT`(수정) API를 대상으로 하기 때문에, 기존 데이터와 섞이지 않도록 아예 테이블을 통째로 비웠다가 되돌리는 쪽이 더 안전하다고 판단했다. 상세 SQL(백업/비움/삽입/원복 4단계 + 세션 끊겼을 때 예비 복구)은 위 SQL 파일에 있다.
