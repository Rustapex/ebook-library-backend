# 관리자 컬렉션 API 구현계획

작성일: 2026-07-16  
대상: 기존 `API-ADMIN-COLLECTION-001`~`004` + 확정 보완 `API-ADMIN-COLLECTION-005` 생성·`006` 상세  
화면: `A-018 컬렉션 관리`  
권장 작업 브랜치: `feature/admin-collection-api`

## 1. 목적

`docs/작업현황/2026-07-15_API-ID별_백엔드구현_프론트연결_현황.md`의 도서/카테고리/컬렉션 구간에서 백엔드 구현 `X`로 확인된 관리자 컬렉션 API 4개와, 확정 결정 D-02·D-03에서 필요한 것으로 확정된 생성·상세 API 2개를 구현하기 위한 실행계획이다.

이번 작업에서는 이 계획 Markdown 한 파일만 작성한다. Java, SQL, API 명세, ERD, 정책 문서, 프론트 문서는 수정하지 않고 테스트도 실행하지 않는다.

구현 단계의 목표는 다음과 같다.

1. 관리자 컬렉션 목록·저장·도서 구성·상태 변경 API 구현
2. `COLLECTION`, `COLLECTION_BOOK`, `ADMIN_AUDIT_LOG` 기반 트랜잭션 구현
3. 공개 컬렉션 API와 관리자 API의 조회 정책 분리
4. Controller·Service·Repository 자동 테스트와 전체 build 검증
5. Swagger·Postman·DB 수동 검증 문서와 재현·원복 SQL 작성
6. 이해메모와 설계 문서 반영예정 문서 작성

### 3.1 확인된 문서 불일치

1. 멘토링 전 정책 문서는 `EVENT`, `EVENT_BOOK` 신규 테이블을 요구하지만 실제 SQL인 `src/main/resources/schema.sql`은 `COLLECTION`, `COLLECTION_BOOK + collectionType=EVENT` 통합 모델이다.
2. 설계 ERD/DDL은 컬럼명을 `collection_name`, `collection_description`, `collection_status`로 적었지만 실제 SQL은 `name`, `description`, `status`를 사용한다. 구현은 실제 SQL만 따른다.
3. API-ADMIN-COLLECTION-002는 자동증가 ID를 path로 받는 `PUT` 하나로 “등록/수정”을 모두 표현해 신규 생성 방법이 정의되지 않았다.
4. A-018은 기존 컬렉션의 전체 정보와 등록 도서를 편집해야 하지만 관리자 상세 조회 API가 정의되지 않았다.
5. A-018의 도서 검색은 문서상 미확정이었으나 D-14 확정안에 따라 `API-ADMIN-BOOK-001`을 별도 선행 의존성으로 사용한다.
6. 기존 `2026-07-15_도서-카테고리-컬렉션API_코드리뷰대응_구현계획.md` D-04는 EVENT에도 displayOrder 사용을 권고하지만 A-018 문서는 SERIES에만 displayOrder 사용을 명시하고 실제 SQL은 displayOrder를 NULL 허용한다.

`src/main/resources/schema.sql`이 실제 동작과 구현의 최종 기준이다. ERD·설계 DDL·정책 문서는 참고만 하며, 불일치는 설계 문서 반영예정 문서에 기록한다.

## 5. 구현 구조

### 5.1 패키지 분리

공개 API와 관리자 변경 로직의 정책이 다르므로 기존 `CollectionService`에 관리자 CRUD를 섞지 않는다.

```text
com.acorn.abc.admin.collection
├── controller/AdminCollectionController.java
└── dto/

com.acorn.abc.collection
├── domain/Collection.java
├── domain/CollectionBook.java
├── repository/CollectionRepository.java
├── repository/CollectionBookRepository.java
└── service/AdminCollectionService.java
```

- Controller·관리자 입출력 DTO는 `admin.collection`에 둔다.
- 핵심 컬렉션 transaction은 컬렉션 도메인의 `AdminCollectionService`에 둔다.
- 공개 `CollectionService`의 ACTIVE/AVAILABLE 노출 규칙은 변경하지 않는다.

### 5.2 예상 신규 DTO

| DTO | 주요 필드 |
|---|---|
| `AdminCollectionSummaryResponse` | collectionId, name, collectionType, discountRate, startDate, endDate, status, mappedCount, createdAt, updatedAt |
| `AdminCollectionDetailResponse` | 기본 필드 + description + createdBy + `books[]` |
| `AdminCollectionBookResponse` | collectionBookId, bookId, title, status, displayOrder |
| `AdminCollectionSaveRequest` | name, collectionType, discountRate?, description?, startDate?, endDate?, status |
| `AdminCollectionSaveResponse` | collectionId, status, createdAt/updatedAt |
| `AdminCollectionBooksUpdateRequest` | `books[{bookId, displayOrder?}]` |
| `AdminCollectionBooksUpdateResponse` | collectionId, mappedCount |
| `AdminCollectionPatchRequest` | status?, removeBookIds[]? |
| `AdminCollectionPatchResponse` | collectionId, status, mappedCount |

DTO 이름과 생성·수정 분리는 D-02 확정 결과에 따라 `CreateRequest`와 `UpdateRequest`로 더 명확히 나눌 수 있다.

### 5.3 Domain 변경

#### `Collection`

- `BaseEntity` 상속으로 createdAt/updatedAt을 공통 Auditing에 위임한다.
- `create(...)`, `updateBasicInfo(...)`, `changeStatus(...)` 도메인 메서드를 추가한다.
- name trim, 허용 type/status, 할인율, 날짜, 유형별 필드 조합은 Service/Request 검증 후 Domain에서 한 번 더 방어한다.
- createdBy는 생성 시 관리자만 기록하고 수정 시 바꾸지 않는다.

#### `CollectionBook`

- `create(collection, book, displayOrder)` factory와 `changeDisplayOrder(...)`를 추가한다.
- `collection_book`에는 updatedAt이 없으므로 mapping 순서 변경 시 별도 수정시각을 저장하지 않는다.
- 같은 컬렉션·도서 중복은 요청 검증과 DB UNIQUE를 함께 사용해 방어한다.

### 5.4 Repository 변경

#### `CollectionRepository`

- 관리자용 type/status optional filter와 `Pageable` 조회를 추가한다.
- 관리자 조회는 ACTIVE로 강제하지 않고 `ACTIVE/HIDDEN/ENDED` 전체를 조회할 수 있게 한다.
- write API용 `findByIdForUpdate`에 `PESSIMISTIC_WRITE` lock을 적용한다.
- 기본 정렬은 `createdAt DESC, collectionId DESC`로 고정한다.

#### 신규 `CollectionBookRepository`

- collectionId별 mapping·book fetch 조회
- collectionId 목록별 mapped count batch 조회
- collectionId + bookId 목록 조회
- collectionId별 mapping 존재 여부
- 지정 bookId mapping 삭제와 삭제 개수 반환
- 전체 mapping 수 조회

목록 1페이지마다 컬렉션별 count query가 반복되지 않도록 count는 collection ID 목록 단위 한 번에 조회한다.

### 5.5 Service transaction

권장 메서드:

```text
getAdminCollections(criteria)
getAdminCollectionDetail(collectionId)
createAdminCollection(request, adminMemberId)
updateAdminCollection(collectionId, request, adminMemberId)
upsertCollectionBooks(collectionId, request, adminMemberId)
patchCollection(collectionId, request, adminMemberId)
```

- 조회는 `@Transactional(readOnly = true)`를 사용한다.
- 변경은 collection 변경, mapping 변경, 감사 로그 기록을 하나의 transaction으로 처리한다.
- `AdminAuditLogWriter`에 전달하는 before/after summary는 ID, type, status, mappedCount, 변경 bookId만 포함하고 전체 description이나 불필요한 개인정보를 기록하지 않는다.

## 6. API별 구현 계획

### 6.1 API-ADMIN-COLLECTION-001 — 목록 조회

1. `collectionType?`, `status?`, `page?`, `size?`를 받는다.
2. type은 `SERIES/EVENT`, status는 `ACTIVE/HIDDEN/ENDED`만 허용한다.
3. `page>=0`, `1<=size<=100`, 기본 `page=0`, `size=10`으로 검증한다.
4. 목록 필드와 등록 도서 수를 반환한다.
5. count를 batch 조회해 N+1을 방지한다.
6. 관리자만 접근 가능하며 비회원 401, 일반회원 403을 공통 Security handler로 처리한다.

### 6.2 API-ADMIN-COLLECTION-002·005 — 수정·생성

D-02 확정안 기준:

- API-ADMIN-COLLECTION-005 생성: `POST /api/v1/admin/collections`, 성공 201
- API-ADMIN-COLLECTION-002 수정: `PUT /api/v1/admin/collections/{collectionId}`, 성공 200

Validation:

- name 필수, trim 후 1~100자
- collectionType은 SERIES/EVENT
- status는 ACTIVE/HIDDEN/ENDED
- discountRate는 EVENT에서만 null 또는 0~100
- startDate/endDate는 EVENT에서만 사용하며 둘 다 있으면 startDate<=endDate
- SERIES는 discountRate/startDate/endDate를 null로 제한
- mapping이 존재하는 컬렉션의 type 변경은 400
- 없는 수정 대상은 `COMMON_NOT_FOUND` 404

생성 시 authenticated admin memberId를 `created_by`로 저장한다. 생성·수정 각각 감사 로그를 남긴다.

### 6.3 API-ADMIN-COLLECTION-006 — 관리자 상세 조회

`GET /api/v1/admin/collections/{collectionId}`에서 HIDDEN/ENDED 컬렉션과 HIDDEN/INACTIVE 도서 mapping도 관리자에게 반환한다.

- SERIES: displayOrder ASC, collectionBookId ASC
- EVENT: createdAt ASC, collectionBookId ASC
- 없는 컬렉션: `COMMON_NOT_FOUND` 404
- Entity 직접 반환 금지

이 API는 신규 `API-ADMIN-COLLECTION-006`으로 설계 문서 반영예정 문서에 기록한다.

### 6.4 API-ADMIN-COLLECTION-003 — 도서 추가·정렬

1. 컬렉션 row를 write lock으로 조회한다.
2. request 내부 bookId 중복을 400으로 거부한다.
3. 전달 bookId 전체를 한 번에 조회하고 누락 ID가 하나라도 있으면 `BOOK_NOT_FOUND` 404로 전체 rollback한다.
4. 기존 mapping이면 displayOrder만 갱신하고, 신규면 CollectionBook을 생성한다.
5. SERIES는 양수 displayOrder 필수이며 컬렉션 전체에서 중복되지 않게 검증한다.
6. EVENT는 displayOrder를 null로 제한한다.
7. 미포함 기존 mapping은 유지한다.
8. 변경 후 전체 mappedCount를 반환하고 감사 로그를 기록한다.

### 6.5 API-ADMIN-COLLECTION-004 — 도서 제외·상태 변경

1. status와 removeBookIds 중 하나 이상 존재하도록 class-level validation 또는 Service 방어를 둔다.
2. removeBookIds 내부 중복은 400으로 처리한다.
3. 컬렉션 row를 write lock으로 조회한다.
4. 지정 mapping만 삭제하고 BOOK row는 절대 삭제하지 않는다.
5. 이미 제거된 bookId 재요청은 idempotent하게 무시한다.
6. 같은 status 재요청도 성공 처리한다.
7. status 변경과 제거가 같이 오면 한 transaction으로 처리한다.
8. 변경 후 status와 mappedCount를 반환하고 before/after 감사 로그를 기록한다.
