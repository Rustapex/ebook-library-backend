# 2026-07-16 관리자 회원 API 구현 계획

## 0. 목적·범위·이번 문서의 한계

- 관리자 회원 관리 화면을 위한 백엔드 API를 구현한다. 기준 API 명세의 대상은 **기존 4개 endpoint**이며, 상세 화면의 탭은 `API-ADMIN-MEMBER-002`의 query parameter로 처리한다. endpoint를 추가하지 않는다.
- 대상: `API-ADMIN-MEMBER-001`~`004`.
- 이번 세션에서 실제로 생성·수정하는 산출물은 **이 구현 계획 문서 1개뿐**이다. Java, SQL, API 명세, 설계 문서, 체크리스트, 테스트 데이터 SQL은 구현 단계에서 작성한다.
- 구현 브랜치 권장안: `feature/admin-member-api`.

| API ID | Method / URL | 구현 범위 |
|---|---|---|
| `API-ADMIN-MEMBER-001` | `GET /api/v1/admin/members` | 회원 목록·검색·필터·마스킹 |
| `API-ADMIN-MEMBER-002` | `GET /api/v1/admin/members/{memberId}` | 기본 상세 및 탭별 이력 조회 |
| `API-ADMIN-MEMBER-003` | `PATCH /api/v1/admin/members/{memberId}/status` | 상태/제재 변경 및 계정 정지 만료 복구 배치 |
| `API-ADMIN-MEMBER-004` | `POST /api/v1/admin/members/{memberId}/points` | 멱등 포인트 조정 |

### 0.1 기준과 현재 상태

| 기준 | 확인 내용 | 계획 반영 |
|---|---|---|

## 1. 확정 계약

### 1.1 공통 권한과 대상 보호

1. 네 API 모두 관리자 권한이 필요하다.
2. 대상 회원의 `role=ADMIN`이면 요청자가 누구든 **조회만 허용**하고 상태·제재·포인트 변경은 거부한다.
3. 위 보호 검사는 Controller에서 빠른 차단을 할 수 있으나, 우회 호출을 막기 위해 **Service에도 반드시 둔다**. Service 검사가 최종 기준이다.
4. `WITHDRAWN`, `DEACTIVATED` 회원은 목록/상세 조회는 허용하되 상태·제재 변경은 거부한다.
5. 비밀번호는 어떤 응답에도 포함하지 않으며 변경 범위에도 넣지 않는다.
6. 거부된 요청(ADMIN 대상, 탈퇴/비활성 대상, 잔액 부족, 멱등 키 충돌 등)은 별도 보안 감사 로그를 남기지 않는다. 성공적으로 커밋된 상태 변경만 `ADMIN_AUDIT_LOG`에 남긴다.

### 1.2 001 목록: 개인정보 최소화

- query: `q?`, `status?`, `role?`, `gradeId?`, `page?`, `size?`를 기준 API 명세대로 지원한다.
- `q`는 이름·로그인 아이디·이메일을 대상으로 하되, 응답 DTO에는 이메일과 전화번호를 마스킹해 반환한다.
- 목록 DTO에는 `birthDate`, `gender` 필드를 **아예 선언하지 않는다**. `null` 또는 빈 문자열로 반환하지 않는다.
- page는 0-based, 기본 `0`; size 기본 `20`, 최대 `100`; 범위 밖 page/size와 허용하지 않은 enum 필터는 HTTP 400 `VALIDATION_ERROR`로 처리한다.
- 정렬 기본값은 회원 생성일 내림차순, 동률은 `memberId` 내림차순으로 고정한다.
- 응답에는 현재 유효 제재 요약만 최소 정보로 포함한다. 만료된 제재·상세 사유·원문 개인정보는 목록에 포함하지 않는다.

### 1.3 002 상세: 기본 상세와 탭 응답 분리

| 요청 | 응답 계약 |
|---|---|
| `tab` 미지정 또는 `DEFAULT` | 프로필, 원문 `email`/`phone`, `birthDate`, `gender`, 이용 요약을 반환한다. |
| `RENTALS` | 대여 이력 전용 `PageResponse`를 반환한다. |
| `PAYMENTS` | 결제 이력 전용 `PageResponse`를 반환한다. |
| `REPORTS` | 신고 이력 전용 `PageResponse`를 반환한다. |
| `POINTS` | 포인트 이력 전용 `PageResponse`를 반환한다. |
| `SANCTIONS` | 제재 이력 전용 `PageResponse`를 반환한다. |

- 탭 응답은 기본 상세 DTO를 재사용하지 않고 **탭별 전용 DTO**를 만든다. 따라서 `profile` 필드는 `null`이 아니라 **응답 구조에 존재하지 않는다**.
- 탭 응답은 `memberId`와 해당 탭의 데이터만 반환하며 원문 PII를 포함하지 않는다.
- `DEFAULT`는 page/size를 사용하지 않는다. 이력 탭은 `page=0`, `size=20`을 기본으로 하고 size 최대 100을 적용한다.
- 각 탭은 발생 일시 내림차순, PK 내림차순을 공통 tie-breaker로 적용한다. `SANCTIONS`는 `startedAt DESC, sanctionHistoryId DESC`를 사용한다.
- 허용값 이외의 `tab`, 음수 page, 1 미만 또는 100 초과 size는 HTTP 400이다.

### 1.4 003 상태·제재 규칙

1. `ACCOUNT_SUSPENSION`만 회원 상태를 `SANCTIONED`로 바꾸며 로그인 차단 효과를 가진다.
2. `RENTAL_BAN`, `REVIEW_BAN`은 `SANCTION_HISTORY`만 생성한다. 회원 상태는 `JOINED`로 유지되며 각각 대여·리뷰 기능의 접근 제어에서 별도로 판단한다.
3. `RENTAL_BAN`, `REVIEW_BAN`은 계정 정지의 해제/만료와 무관하게 유효 기간까지 유지된다. 계정 정지 만료 배치는 두 제재를 해제·변경·삭제하지 않는다.
4. 성공한 상태/제재 변경, 제재 이력, 감사 로그는 하나의 transaction으로 커밋한다. 어느 하나라도 실패하면 모두 rollback한다.
5. 기존 신고 처리 등 다른 경로가 `SANCTIONED`를 만들거나 해제할 수 있다면, 해당 경로도 `currentSanctionId`를 일관되게 갱신/해제하도록 함께 점검한다. 이 연결값이 없는 상태는 배치에서 복구하지 않는다.

### 1.5 계정 정지 만료 배치: 원인 검증과 멱등성

`member.current_sanction_id`(nullable FK)를 “현재 `SANCTIONED` 상태를 만든 계정 정지 제재”의 연결값으로 사용한다.

1. 계정 정지 생성과 동시에 `SANCTIONED`로 전이할 때 그 제재 ID를 `currentSanctionId`에 저장한다.
2. 배치 후보는 `ACCOUNT_SUSPENSION`이며 `endedAt < 현재시각`인 이력으로 한정한다. ADMIN 대상은 후보 단계에서 제외한다.
3. 배치는 회원 행과 관련 제재 행을 `PESSIMISTIC_WRITE`로 잠그거나 동등한 조건부 갱신을 사용한다.
4. 아래를 **모두** 만족할 때에만 `SANCTIONED → JOINED`를 수행한다.
   - 회원 상태가 아직 `SANCTIONED`이다.
   - `currentSanctionId`가 만료 후보 제재 ID와 같다.
   - 후보가 실제 만료된 `ACCOUNT_SUSPENSION`이다.
   - 같은 회원에 다른 활성 `ACCOUNT_SUSPENSION`이 없다.
5. 원인 연결을 확인할 수 없거나, 상태가 달라졌거나, 대상이 ADMIN이면 무조건 no-op 처리한다. 이 경우 상태·이력·감사 로그를 남기지 않는다.
6. 다른 활성 계정 정지가 있으면 상태를 복구하지 않는다. `currentSanctionId`는 활성 제재 중 `startedAt`이 가장 최근인 제재(동률은 ID가 큰 제재)로 재지정한다. 이 재지정만으로는 복구 이력·감사 로그를 만들지 않는다.
7. 실제 복구에 성공한 경우에만 `currentSanctionId`를 비우고, 복구 이력과 성공 감사 로그를 같은 transaction에 기록한다. 재실행 시 조건을 통과하지 못하므로 멱등적이다.
8. 잠금 대기 초과·deadlock은 자동 재시도하지 않는다. transaction rollback 후 새 additive ErrorCode `CONCURRENT_UPDATE`(HTTP 409)로 응답하며, 운영자는 재요청한다.

### 1.6 004 포인트 조정: 원자성·멱등성

#### 요청·응답 계약 보강

- 요청 본문에 UUID 형식의 필수 `requestId`를 추가한다. 기존 `pointAmount(+/-)`, `description`은 유지한다.
- `requestId`는 **대상 회원별 멱등 키**다. 같은 `memberId + requestId`로 재요청하면 기존 성공 결과를 반환한다.
- 같은 키에 `pointAmount` 또는 공백 정규화 후 `description`이 다르면 HTTP 409 `IDEMPOTENCY_KEY_CONFLICT`로 거부한다.
- 멱등 재응답은 잔액, `POINT_HISTORY`, `ADMIN_AUDIT_LOG`를 다시 만들거나 변경하지 않는다.

#### 처리 규칙

1. 새 요청이면 대상 회원 행을 `PESSIMISTIC_WRITE`로 읽고 ADMIN 대상 보호 및 잔액 규칙을 검사한다.
2. `pointAmount=0`은 400으로 거부한다. 차감 후 잔액이 음수면 기존 `POINT_BALANCE_INSUFFICIENT`(400)로 거부한다.
3. 잔액 갱신, `pointType=ADMIN_ADJUST` 이력 생성, 성공 감사 로그 생성은 **하나의 transaction**에서 처리한다. 실패 시 셋 모두 rollback되어야 한다.
4. `point_history`의 `(member_id, request_id)` 유니크 제약 위반은 기존 이력을 다시 읽는다. payload가 같으면 기존 응답을 반환하고, 다르면 `IDEMPOTENCY_KEY_CONFLICT`로 거부한다. 차감을 재실행하지 않는다.
5. 잠금 실패는 003과 동일하게 재시도 없이 rollback하고 `CONCURRENT_UPDATE`(409)를 반환한다.

## 2. DB·공통 코드 변경 원칙

### 2.1 런타임 스키마 변경 계획

실제 DB 기준인 `src/main/resources/schema.sql`에 아래 변경을 구현 단계에 반영한다. 설계용 `docs/데이터베이스` 문서는 참고만 하며, 실제 스키마보다 우선하지 않는다.

| 대상 | 변경 | 이유·호환성 |
|---|---|---|
| `member` | nullable `current_sanction_id` 추가 및 `sanction_history(sanction_history_id)` FK 추가 | 현재 SANCTIONED 상태의 원인을 신뢰성 있게 판별한다. 기존 회원은 null로 시작하며, null은 배치 복구 대상이 아니다. |
| `point_history` | nullable `request_id CHAR(36)` 추가 | 기존 이력 backfill 없이 유지한다. 신규 `ADMIN_ADJUST`만 non-null requestId를 서비스 검증으로 강제한다. |
| `point_history` | `UNIQUE(member_id, request_id)` 추가 | MySQL의 nullable unique 특성으로 기존 null 이력은 공존하고, 새 관리자 조정만 회원별 멱등성을 보장한다. |
| 관련 인덱스 | 만료 계정 정지 조회·회원별 활성 제재 조회에 필요한 인덱스를 EXPLAIN으로 검증 후 최소 추가 | 배치 전체 스캔과 잠금 범위를 줄인다. |

- FK 생성 순서와 초기화 재실행 시의 동작을 검증한다. `schema.sql`의 기존 FK 추가 방식과 충돌하지 않게 배치한다.
- `data.sql`, 테스트 fixture, 수동 테스트 SQL은 새 컬럼과 unique 제약을 만족하도록 최소 수정한다.
- 데이터 변경을 수반하는 수동 검증은 현 상태 확인 → 백업 → 임시 조작 → API/배치 검증 → 원복 순서로 기록한다.

### 2.2 공통 코드 영향 통제

- 기존 `ErrorCode`의 의미·HTTP 상태·사용처는 바꾸지 않는다. 새 코드만 additive하게 추가한다.
- 새 코드 후보는 `CONCURRENT_UPDATE(409)`, `IDEMPOTENCY_KEY_CONFLICT(409)` 두 개다. 구현 전에 필요성과 메시지·사용 위치·기존 도메인 영향(기존 사용처 없음)을 확정하고, **`docs/작업현황/ErrorCode_신규추가_완료.md`에 추가 기록**한 뒤 `ErrorCode.java`에 enum 항목을 추가한다.
- `PointService`의 일반 포인트 지급/사용 흐름은 유지한다. 관리자 전용 잠금·requestId·ADMIN 보호는 관리자 조정 전용 메서드/서비스로 좁혀 다른 포인트 도메인의 동작을 바꾸지 않는다.
- 공통 인증 로직과 `SecurityConfig`는 변경하지 않는다. 계정 정지 해제는 검증된 만료 배치가 상태를 복구하는 방식으로만 처리한다.
- 기존 감사 로그 writer의 성공 로그 계약은 유지한다. 신규 action type이 필요하면 additive enum으로 추가하고, 기존 action type의 이름이나 의미는 변경하지 않는다.

## 3. 구현 순서

1. **설계·명세 선반영**
   - `docs/작업현황/설계문서/2026-07-16_관리자-회원API_설계문서.md`에 네 endpoint, 002 탭 응답 DTO 분리, 004의 `requestId`, 정렬/페이징, PII 범위를 기록한다.
   - 기준 API 명세에 002 탭 query 계약, 004 `requestId`, 목록/상세 PII 노출 범위를 반영한다. 명세 변경 PR을 분리하면 해당 PR의 선행 병합을 구현 완료 조건으로 명시한다.
   - ErrorCode 신규 항목은 별도 신규 파일이 아니라 `docs/작업현황/ErrorCode_신규추가_완료.md`에 기록한다.
2. **DB와 엔티티 준비**
   - runtime schema, Entity, repository를 `currentSanctionId`와 `requestId`에 맞게 추가한다.
   - member 잠금 조회, 활성/만료 계정 정지 조회, idempotency 이력 조회를 전용 repository 메서드로 만든다.
3. **조회 API 구현**
   - 001 projection/DTO에서 원문 PII를 원천적으로 제외하고 마스킹만 조립한다.
   - 002 DEFAULT DTO와 5개 탭 전용 DTO·query validation·tab별 paging/sort를 구현한다.
4. **상태·제재 및 만료 배치 구현**
   - ADMIN/탈퇴/비활성 보호를 Controller와 Service에 적용한다.
   - 제재 유형별 상태 전이, `currentSanctionId` 갱신, 성공 감사 로그를 transaction으로 묶는다.
   - 인과 연결값 검증과 잠금 조건을 갖춘 만료 배치를 구현한다. 다른 상태 변경 경로의 `currentSanctionId` 일관성도 점검·보완한다.
5. **포인트 조정 구현**
   - 004 request/response, idempotency 조회, 잠금, 잔액 검사, unique 충돌 복구를 구현한다.
   - 잔액·이력·감사 로그의 단일 transaction과 rollback을 검증한다.
6. **테스트·수동 검증 문서 작성**
   - 자동 테스트 후 Swagger/Postman 체크리스트와 테스트 데이터 준비·원복 SQL을 작성하고 실행 결과를 남긴다.

## 4. 자동 테스트 계획

### 4.1 001·002 조회 계약

- 001 응답에 원문 이메일·전화번호, `birthDate`, `gender`가 절대 포함되지 않는지 확인한다.
- 002 `DEFAULT`에는 원문 이메일·전화번호·생년월일·성별이 포함되는지 확인한다.
- 002 모든 탭 응답에 `profile` 필드와 원문 PII가 존재하지 않는지 JSON 직렬화 기준으로 검증한다.
- `DEFAULT`, `RENTALS`, `PAYMENTS`, `REPORTS`, `POINTS`, `SANCTIONS` 허용값, 기본값, 정렬, 0-based page, size 최대 100, 잘못된 tab/page/size의 400을 검증한다.
- 미인증 401, 일반 회원 403, 존재하지 않는 회원 404도 검증한다.

### 4.2 003 상태·제재와 배치

- ADMIN 대상의 상태·제재 변경은 Controller 경로와 Service 직접 호출 모두 거부되는지 확인한다.
- `WITHDRAWN`·`DEACTIVATED` 대상의 상태/제재 변경이 거부되는지 확인한다.
- `ACCOUNT_SUSPENSION`만 `SANCTIONED` 전이와 `currentSanctionId` 설정을 하는지, `RENTAL_BAN`·`REVIEW_BAN`은 상태를 바꾸지 않는지 검증한다.
- 성공 시 상태·제재 이력·감사 로그가 함께 저장되고, 실패 시 셋 모두 남지 않는지 검증한다.
- 만료 배치가 정확히 현재 상태 원인인 만료 계정 정지만 복구하는지 검증한다.
- 연결값이 null/불일치이거나 다른 활성 계정 정지가 있거나 ADMIN 대상이면 복구하지 않는지 검증한다.
- 중첩 계정 정지에서 먼저 만료된 이력이 JOINED 복구를 유발하지 않는지, 활성 제재로 `currentSanctionId`만 재지정되는지 검증한다.
- 배치를 재실행해도 실제 복구 이력과 감사 로그가 한 번만 생성되는지 검증한다.

### 4.3 004 포인트 원자성·멱등성

- 동시 차감 요청 후 잔액이 음수가 될 수 없는지 검증한다.
- 같은 `memberId + requestId`와 같은 payload의 재시도는 잔액·이력·감사 로그가 한 번만 생성되고 동일 결과를 반환하는지 검증한다.
- 같은 키와 다른 금액 또는 정규화한 사유가 다르면 `IDEMPOTENCY_KEY_CONFLICT`(409)인지 검증한다.
- ADMIN 대상 변경, 잔액 부족, 잠금 실패에서 잔액·이력·감사 로그가 모두 남지 않는지 검증한다.
- unique 충돌 경합에서 차감이 중복되지 않는지 검증한다.
