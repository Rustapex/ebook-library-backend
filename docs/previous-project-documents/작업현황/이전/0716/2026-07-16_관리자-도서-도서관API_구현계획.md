# 2026-07-16 관리자 도서 API 구현 계획

## 0. 문서 목적과 현재 작업 범위

- `docs/작업현황/2026-07-15_API-ID별_백엔드구현_프론트연결_현황.md` §3.8에서 백엔드 구현 `X`로 판정된 관리자 도서 4개 API와 신규 관리자 도서 단건 조회 1개, **총 5개 endpoint**의 구현 순서와 검증 기준을 정한다.
- 프론트 화면 A-004, A-005, A-006 연결에 필요한 관리자 도서 단건 조회 계약의 공백을 함께 정리한다.
- 관리자 도서관 API, 지도 API, 외부 도서관 정보 조회, 관련 API Key 발급·설정은 담당 팀원이 구현한다. 이 문서는 해당 기능의 설계·구현·테스트·수동 검증을 포함하지 않는다.
- **작업 주체의 담당 범위는 백엔드 개발뿐이다.** 프론트 문서는 요청·응답 계약과 화면 필요 필드를 확인하는 참고 근거로만 사용하며, 프론트 소스·타입·wrapper·화면은 수정하지 않는다.
- 이 문서는 구현, 자동 테스트, Swagger/Postman 수동 테스트 자료, 초경량 이해 메모, 설계문서 작성을 만드는 순서와 기준을 확정하기 위한 계획 문서다.
- **현재 단계에서 실제로 생성하는 파일은 이 계획 문서 1개뿐이다.**
- 현재 단계에서는 Java 소스, 테스트 소스, 스키마, API 명세, 프론트 소스, 테스트 SQL을 생성하거나 수정하지 않는다.

### 2.1 확인된 문서 불일치

1. 런타임 스키마는 `book.title/isbn/status`를 사용하지만 설계 DDL은 `book_title/book_isbn/book_status`를 사용한다. 현재 Entity는 런타임 스키마와 일치하므로 구현 기준은 런타임 스키마다.
2. API 명세의 도서 등록 request에는 `file`이 있고 참조 테이블 목록에도 `BOOK_FILE`이 있으나 런타임 스키마, 설계 DDL, Entity에는 해당 테이블이 없다.
3. 비즈니스 정책 문서에는 `publisher_review` 삭제 의견이 있으나 API 명세, 프론트 A-005/A-006, 런타임 `book_detail.publisher_review`는 여전히 해당 필드를 사용한다.
4. API 명세는 `defaultRentalDays`를 request에 포함하지만 비즈니스 정책과 현재 `BookApprovalService`는 무료 7일, 유료 14일을 고정한다.
5. A-006은 기존 값을 채워야 하지만 final API 명세에는 관리자 도서 단건 조회 API가 없다. 공개 상세 API는 `AVAILABLE` 노출 정책 때문에 `HIDDEN/INACTIVE` 수정 화면의 근거로 사용할 수 없다.
8. 프론트 공통 문서는 final spec의 `page=1` 가능성과 backend의 `page=0` 관례가 충돌한다고 기록한다. 현재 `PageResponse`와 관리자 Controller들은 0-based를 사용한다.

## 4. 확정 API 계약

### 4.1 API-ADMIN-BOOK-001 — 관리자 도서 목록

- `GET /api/v1/admin/books`
- Query: `q?`, `categoryId?`, `rentalType?`, `status?`, `page=0`, `size=20`
- `q`는 제목, 저자, 출판사, ISBN을 검색한다.
- `rentalType`은 `FREE/PAID`, `status`는 `AVAILABLE/HIDDEN/INACTIVE`만 허용한다.
- 응답은 `ApiResponse<PageResponse<AdminBookSummaryResponse>>`다.
- 목록 항목은 A-004가 요구하는 `bookId`, 표지/제목, 저자, 출판사, ISBN, 카테고리, 대여 유형/가격, 상태와 수정 진입에 필요한 최소 필드를 포함한다.
- 공개 `BookRepository.search()`의 `AVAILABLE` 고정 조건을 제거하지 않고 관리자 전용 query를 별도로 둔다.

### 4.2 API-ADMIN-BOOK-002 — 도서 등록

- `POST /api/v1/admin/books`, 성공 `201 Created`
- Request: `title`, `isbn?`, `publisherName`, `authors[]`, `categoryIds[]`, D-05의 `keywords[]`, `rentalType`, `rentalPrice`, `defaultRentalDays`, `coverImageUrl?`, `status`, `detail`, `pages[]`
- 제목·출판사·저자 1명 이상은 필수다. 저자명은 trim 후 빈 값·중복을 거부한다.
- ISBN은 있을 때 숫자 13자리이며 기존 `BOOK.isbn UNIQUE`와 `BOOK_ISBN_ALREADY_EXISTS`로 중복을 차단한다.
- FREE는 가격 0/7일, PAID는 가격 양수/14일만 허용한다.
- `pages[]`의 `pageNo`는 1 이상·중복 금지, `pageContent`는 필수다. `totalPages`는 최대 `pageNo`, 빈 목록이면 0이다.
- category는 기존 `ACTIVE` 항목만 허용한다. keyword는 `keywordName + keywordType`이 일치하는 기존 `ACTIVE` 항목만 허용하며, 존재하지 않거나 비활성인 keyword는 `400 Bad Request`로 거절한다. 도서 등록·수정 요청으로는 `BOOK_KEYWORD`를 신규 생성하지 않는다.
- 출판사는 이름 기준 재사용/생성, 저자는 현재 `findFirstByAuthorNameOrderByAuthorIdAsc` 패턴으로 재사용/생성한다.
- 도서 aggregate 저장과 `BOOK_CREATE` 감사 로그를 하나의 transaction으로 처리한다.
- 응답: `bookId`, `status`, `createdAt`.

### 4.3 API-ADMIN-BOOK-003 — 도서 수정

- `PUT /api/v1/admin/books/{bookId}`, 성공 `200 OK`
- D-12 기준 전체 aggregate 수정이며 요청 검증은 등록과 동일하다.
- 대상 도서를 write lock으로 조회하고, ISBN 중복은 자기 자신을 제외한다.
- `Book` 기본 필드와 출판사를 변경하고 저자·카테고리·키워드·페이지 mapping을 최종 request와 동기화한다.
- `rentalCount`, `averageRating`, `reviewCount`, `createdAt`은 수정 request로 덮어쓰지 않는다.
- `BookDetail`은 기존 row를 update하고, child mapping 교체 시 UNIQUE 충돌을 피하도록 delete/flush/save 순서를 검증한다.
- 수정 전후 핵심 값과 변경된 ID/페이지 수를 `BOOK_UPDATE`, target `BOOK`으로 기록한다.
- write lock 대기 초과 또는 DB 교착 상태는 `CONCURRENT_UPDATE`와 `409 Conflict`로 응답한다. 서버 자동 재시도는 하지 않으며, 클라이언트는 최신 값을 다시 조회한 뒤 사용자가 재시도한다.
- 응답: `bookId`, `updatedAt`.

### 4.4 API-ADMIN-BOOK-004 — 도서 상태 변경

- `PATCH /api/v1/admin/books/{bookId}/status`
- Body: `status(AVAILABLE/HIDDEN/INACTIVE)`, `reason?`
- 대상 도서를 write lock으로 조회해 상태 변경과 감사 로그를 직렬화한다.
- 물리 삭제하지 않는다. `reason`은 별도 도서 컬럼에 저장하지 않고 감사 로그 after summary에 포함한다.
- 같은 상태 요청의 멱등 처리는 성공 200으로 유지하고, 실제 변경이 없으면 감사 로그를 추가하지 않는다.
- write lock 대기 초과 또는 DB 교착 상태는 `CONCURRENT_UPDATE`와 `409 Conflict`로 응답하며 자동 재시도하지 않는다.
- 공개 목록/검색/상세는 `HIDDEN/INACTIVE`를 계속 제외해야 한다.

### 4.5 API-ADMIN-BOOK-005 — 관리자 도서 단건 조회(D-01 확정)

- `GET /api/v1/admin/books/{bookId}`
- A-006의 기존 값 채움에 필요한 기본 정보, publisher, 순서가 있는 authors, categories, keywords, detail, pages, status를 반환한다.
- `HIDDEN/INACTIVE`도 조회할 수 있다.
- 공개 상세 DTO/Service를 재사용해 관리자 노출을 제한하지 말고 관리자 전용 Response 조립을 사용한다.

### 5.7 공통 코드 보호 원칙

이번 구현의 기본 방침은 **기존 공통 동작을 수정하지 않고 도메인별 새 코드를 추가하는 것**이다.

| 공통/공유 영역 | 허용 변경 | 금지 또는 별도 승인 필요 | 보호 검증 |
|---|---|---|---|
| `ApiResponse`, `PageResponse`, `ErrorResponse` | 기존 factory/record 재사용 | 필드·page 의미·JSON 구조 변경 | 기존 관리자 Controller 테스트와 신규 응답 contract test |
| `GlobalExceptionHandler` | 기존 `BusinessException` → ErrorCode 응답 경로 재사용 | 예외 매핑 순서·공통 status 변경 | `CONCURRENT_UPDATE` 409과 400/401/403/404 공통 응답 회귀 테스트 |
| `SecurityConfig` | 기존 `/api/v1/admin/**` 규칙 재사용 | 공개 matcher 확대, ADMIN 규칙 변경 | 기존 관리자 API와 신규 Controller 401/403/ADMIN 통합 테스트 |
| `ErrorCode` | `CONCURRENT_UPDATE` 상수만 additive하게 추가 | 기존 code/status/message·상수명·사용 도메인 변경 | 기존 예외 code 회귀와 신규 409 contract test |
| 감사 로그 enum | 기존 `BOOK_*` 상수 재사용 | 기존 상수 삭제·이름 변경·의미 재사용 | 기존 action/target 회귀 테스트 |
| `AdminAuditLogWriter` | 그대로 재사용 | transaction 전파·직렬화·실패 정책 변경 | 로그 실패 시 본 transaction rollback 테스트 |
| 공통/기존 Entity | 관리자용 factory/update 메서드 추가 | 기존 factory/getter/집계 메서드 동작 변경 | 공개 도서, 대여, 리뷰, 외부 ISBN 승인 회귀 테스트 |
| 기존 Repository | 신규 관리자 query/method 추가 | 공개 query 조건을 관리자 요구에 맞춰 변경 | 공개 검색·추천 Repository/Service 테스트 |

- 기존 공통 코드의 수정이 불가피해지면 바로 구현하지 않고 영향 호출부를 `rg`로 조사한 뒤 별도 `_수정계획.md` 또는 `_승인요청.md`에 이유, 대안, 영향 도메인, 회귀 테스트를 기록한다.
- 공통 코드 수정과 관리자 도서 기능 구현을 같은 diff에 섞지 않는 것을 원칙으로 한다.
- 단순 신규 enum 상수나 신규 Repository method처럼 additive한 변경도 기존 값과 method의 의미를 바꾸지 않는다.

| 영향 도메인 | 예상 영향 | 방어 계획 |
|---|---|---|
| 공개 도서 | 관리자 상태 변경과 상세 수정 결과가 공개 목록/검색/상세에 반영됨 | `AVAILABLE`만 노출되는 기존 조건을 유지하고 공개 `BookServiceTest` 회귀 실행 |

프론트는 영향 분석 대상이 아니라 **외부 소비자 계약 참고 대상**이다. 백엔드 응답이 확정되면 설계문서에 차이만 기록하고 프론트 저장소는 수정하지 않는다.

## 6. 자동 테스트 계획

### 6.1 관리자 도서 Controller

- API-001 query 기본값, 모든 filter, 잘못된 enum/page/size 400, 공통 `ApiResponse<PageResponse<...>>`.

### 6.2 관리자 도서 Service

- 관리자 목록에 `AVAILABLE/HIDDEN/INACTIVE`가 모두 조건대로 포함되고 공개 조회에는 회귀가 없는지 확인.

- PUT이 child mapping을 최종 상태로 바꾸되 집계 컬럼을 보존하는지 확인.
- 상태 변경의 public 노출 반영, reason 감사 로그, 동일 상태 멱등 계약 확인.
- 동시 수정 lock query와 aggregate 단위 원자성을 Repository/실DB 테스트로 확인한다. 잠금 대기 초과·교착 상태는 `CONCURRENT_UPDATE` 409이고, 실패 요청은 도서·mapping·감사 로그를 남기지 않으며 서버 자동 재시도가 없는지 확인한다.

### 7.1 공통 작성 원칙

- Markdown과 SQL 각각 하나만 보고도 준비 → 호출 → DB 확인 → 원복을 독립 실행할 수 있게 작성한다.
- 테스트 번호, 전체 URL, Method, ADMIN 인증, request, 예상 HTTP/JSON, 실행 전후 SQL, 감사 로그 확인, 원복 순서를 일치시킨다.
- 기존 DB row를 임의 수정하기 전에 대상 ID와 현재 값을 SELECT로 확인하고 필요한 값을 기록한다.
- 생성 데이터는 FK 역순으로 정확한 ID만 정리한다. 광범위 DELETE나 전체 table 정리는 금지한다.
- 변경 API는 본 row와 mapping, `admin_audit_log`가 함께 commit/rollback되는지 확인한다.
- rollback 시나리오마다 실패 호출 직후 아래처럼 대상 row·mapping·감사 로그를 조회하는 SQL을 체크리스트에 포함한다. `:bookId`, `:startedAt`은 해당 테스트에서 기록한 값으로 치환한다.

```sql
SELECT * FROM book WHERE book_id = :bookId;
SELECT * FROM book_detail WHERE book_id = :bookId;
SELECT * FROM book_author WHERE book_id = :bookId ORDER BY author_id;
SELECT * FROM book_category WHERE book_id = :bookId ORDER BY category_id;
SELECT * FROM book_keyword_map WHERE book_id = :bookId ORDER BY display_order, keyword_id;
SELECT * FROM book_page WHERE book_id = :bookId ORDER BY page_no;
SELECT * FROM admin_audit_log
WHERE target_type = 'BOOK' AND target_id = :bookId
  AND created_at >= :startedAt
ORDER BY audit_log_id;
```

- 수동 검증 실행자는 테스트 데이터 생성·원복과 결과 캡처의 책임자이며, 완료 증거는 요청·응답 캡처, 위 SQL 결과, 원복 SQL 실행 결과를 같은 테스트 번호로 보관한다.

### 7.2 관리자 도서 필수 시나리오

- 목록 기본/검색어/카테고리/대여 유형/상태/복합 filter와 0-based pagination.
- 무료·유료 정상 등록, nullable ISBN, ISBN 중복, invalid 가격/기간, 저자·페이지 중복, 없는 category/keyword.
- 상세 조회의 `HIDDEN/INACTIVE` 포함과 모든 child 순서.
- 전체 수정 후 child mapping 교체와 집계 컬럼 보존.
- 상태 `AVAILABLE → HIDDEN → INACTIVE → AVAILABLE`, public API 노출 변화, reason 감사 로그.
- 변경 중 오류를 유발해 도서·mapping·감사 로그가 모두 rollback되는 케이스.
- 같은 도서를 동시에 수정해 첫 요청만 완결되고, 잠금 대기 초과·교착 상태가 발생한 요청은 `CONCURRENT_UPDATE` 409, 부분 저장 없음, 감사 로그 없음, 서버 자동 재시도 없음으로 종료되는 케이스.
- 미인증 401, USER 403, ADMIN 성공.

## 11. 범위 제외와 주의사항

- 현재 계획 작성 단계에서는 소스 구현, 테스트 실행, 실제 DB 조작, 프론트 연결을 하지 않는다.
- 이후 구현 단계에서도 담당 범위는 백엔드 Controller/Service/DTO/Domain/Repository, 백엔드 테스트, Swagger/Postman·DB 검증, 백엔드 저장소 문서로 한정한다.
- `C:/Github/abc-proj-win-FRONT`의 React/TypeScript/API wrapper/화면/프론트 문서는 수정하지 않는다.
- `BOOK_FILE` 신규 도입, 실제 PDF/EPUB/IMAGE 업로드·저장·다운로드는 D-02 확정 기준 범위 제외다.
- 관리자 카테고리 API 구현은 별도 도메인이다. A-004/A-005의 category option 실연결에는 `API-ADMIN-CATEGORY-001`이 선행 의존성으로 남는다.
- 희망도서 승인/반려 API 자체는 구현하지 않는다. A-005 등록 성공 후 `approvedBookId`를 넘기는 연결은 `API-ADMIN-REQUEST-002` 완료 후 가능하다.
- ISBN 외부 preview/temp 수집 API의 외부 네트워크·credential 설정은 이번 CRUD 구현의 완료 조건이 아니다.
- 도서 검색의 출판사 index 추가는 실제 실행 계획/성능 측정 없이 스키마에 선반영하지 않는다.
- 관리자 도서관 API 전체, 지도 API, 외부 도서관 정보 조회, 관련 API Key 발급·보관·설정은 담당 팀원 범위다. 이 문서의 구현·테스트·Swagger/Postman·설계문서 산출물에서 모두 제외한다.
- 공개 도서 API의 기존 응답 계약을 관리자 편의를 위해 넓히지 않는다.
- `docs/데이터베이스/ddl/schema.sql`을 실제 런타임 DB 기준으로 사용하라는 별도 결정이 있다면, 현재 Entity/런타임 스키마와 컬럼명이 충돌하므로 구현 전에 스키마 정합성 작업을 먼저 계획해야 한다.

### 13.2 최종 확정 백엔드 안전 구현 방식

- D-12 A: 도서 PUT은 aggregate 전체 교체로 처리하되 기존 집계·ID를 보존한다.
- D-13 A: 기존 query를 고치지 않고 write-lock 전용 Repository method를 추가한다. 잠금 대기 초과·교착 상태는 `CONCURRENT_UPDATE` 409으로 응답하고 서버 자동 재시도는 지원하지 않는다.

### 13.3 확정안 변경 요청 시 재검토 기준

- 확정안과 다른 선택이 스키마, 공통 응답, 공통 예외, 공통 보안, 기존 Entity/Repository 동작을 바꾸면 즉시 구현하지 않는다.
- 먼저 다른 도메인 호출부와 테스트를 조사하고 별도 수정계획 또는 승인요청 문서를 작성한다.
- 프론트 계약 변경이 필요하더라도 백엔드 문서에 후속 필요사항만 남기며 프론트 소스는 수정하지 않는다.
- 확정안에 따라 `schema.sql`, 공통 응답, 공통 보안, `AdminAuditLogWriter`, 기존 `ErrorCode`의 code/status/message·상수명을 변경하지 않고 구현한다. `CONCURRENT_UPDATE`는 기존 값을 건드리지 않는 신규 상수 추가로만 반영한다.
