# PR #50 코드리뷰 보완 계획

작성일: 2026-07-16  
대상 PR: [#50 관리자 컬렉션 API 6종 추가](https://github.com/shangpa/AcornProject/pull/50)

## 1. 목적과 범위

PR #50의 병합 차단 HIGH 2건과 추가 권고 MEDIUM 1건을 해소한다. 이번 후속 구현의 범위는 관리자 컬렉션 API의 쓰기 트랜잭션 보장, 공개 API 계약 문서 동기화, PATCH 요청의 `removeBookIds` 원소 검증 및 그 검증 증거 보완이다.

실제 런타임 DDL의 기준은 `src/main/resources/schema.sql`이며, 이번 지적은 테이블·컬럼 변경을 요구하지 않는다. ERD와 멘토링 기획 문서는 설계 의도 확인용으로만 참조하고, SQL/ERD 구조를 변경하지 않는다.

### 포함 범위

1. 생성·수정·도서 매핑·PATCH의 단일 트랜잭션 경계 보장
2. 감사 로그 기록 실패 시 컬렉션 및 매핑 변경의 롤백을 증명하는 Spring 통합 테스트
3. `removeBookIds`의 null·0·음수 원소를 요청 검증 단계에서 400으로 차단
4. API-ADMIN-COLLECTION-002·005·006 계약을 기준 API 명세와 관련 화면/프론트 참고 문서에 동기화
5. 기존 Swagger/Postman/DB 체크리스트에 트랜잭션·감사 로그·입력 경계 재검증 항목 추가

### 제외 범위

- `collection`, `collection_book` 스키마 및 초기 데이터 변경
- 신규 ErrorCode, GlobalExceptionHandler, 공통 응답 형식 변경
- 공개 컬렉션 API의 URL·동작 변경
- API-ADMIN-BOOK-001 또는 프론트엔드 실제 구현

## 3. 리뷰 항목별 보완 계획

### 3.1 HIGH — 쓰기 트랜잭션과 감사 로그 원자성

#### 수정 파일

| 파일 | 변경 계획 |
|---|---|
| `src/main/java/com/acorn/abc/collection/service/AdminCollectionService.java` | `createAdminCollection`, `updateAdminCollection`, `upsertCollectionBooks`, `patchCollection` 각각에 `@Transactional`을 추가한다. 조회 메서드의 기존 `@Transactional(readOnly = true)`는 유지한다. |
| `src/test/java/com/acorn/abc/collection/service/AdminCollectionTransactionIntegrationTest.java` (신규) | 실제 Spring 프록시와 MySQL을 사용하는 통합 테스트를 추가한다. 테스트 메서드 자체에는 트랜잭션을 붙이지 않아 서비스의 선언 누락을 가리지 않는다. |
| `src/test/java/com/acorn/abc/collection/service/AdminCollectionServiceTest.java` | Mockito 단위 테스트는 현재 비즈니스 규칙 검증을 유지하고, 트랜잭션 보장은 통합 테스트 책임임을 분리한다. 필요한 경우 감사 로그 호출 인자 검증만 보강한다. |

#### 구현 방식

1. 서비스 클래스 전체에 기본 쓰기 트랜잭션을 부여하는 대신, 변경 의도를 명확히 하기 위해 네 공개 쓰기 메서드에만 `@Transactional`을 붙인다.
2. 생성 API는 컬렉션 저장과 `COLLECTION_CREATE` 감사 로그 저장을 하나의 트랜잭션으로 처리한다.
3. 수정·도서 매핑·PATCH API는 `findByIdForUpdate()` 잠금 조회부터 엔티티 변경, `collection_book` 변경, 감사 로그 저장까지 하나의 트랜잭션으로 묶는다.
4. `AdminAuditLogWriter`의 전파 정책, `ErrorCode`, 예외 처리기는 변경하지 않는다. 기록 중 예외가 발생하면 예외를 삼키지 않고 상위 트랜잭션을 롤백시킨다.

#### 통합 테스트 설계

`BookApprovalServiceRequiresNewIntegrationTest`의 실제 Spring 프록시 테스트 방식을 따른다. 테스트 데이터는 고유 접두어/식별자로 생성하고 `@AfterEach`에서 `admin_audit_log` → `collection_book` → `collection` 순으로 정확한 테스트 ID만 정리한다.

| 시나리오 | 방법 | 기대 결과 |
|---|---|---|
| 수정 경로의 잠금 조회 | 실제 `AdminCollectionService.updateAdminCollection()`을 트랜잭션 없이 호출한다. | `PESSIMISTIC_WRITE` 조회가 `TransactionRequiredException` 없이 완료된다. |
| 도서 매핑 경로의 잠금 조회 | 실제 `upsertCollectionBooks()`을 호출한다. | 매핑 저장과 감사 로그가 함께 완료된다. |
| PATCH 경로의 잠금 조회 | 실제 `patchCollection()`으로 상태 및 매핑 삭제를 호출한다. | 잠금·상태 변경·삭제·감사 로그가 하나의 서비스 호출로 완료된다. |
| 감사 로그 실패 롤백 | 통합 테스트 컨텍스트에서 `AdminAuditLogWriter`를 예외를 던지는 테스트 대역으로 교체하고, 생성·수정·매핑·PATCH를 각각 호출한다. 호출 후 새 트랜잭션에서 DB를 재조회한다. | 생성 row가 남지 않고, 수정 전 상태·설명·매핑 수가 복구되며, 감사 로그도 남지 않는다. |
| 성공 경로 원자성 | 실제 writer를 사용해 각 쓰기 API를 호출한다. | 도메인 변경과 action/target이 맞는 감사 로그가 모두 commit된다. |

동시 요청의 실제 대기 시간·직렬화는 자동 테스트에서 불안정할 수 있으므로, 기존 Postman 동시 요청 시나리오도 유지한다. 자동 테스트는 “트랜잭션이 있어 잠금 API가 정상 호출됨”과 “감사 로그 실패 시 롤백됨”을 증명하고, 수동 테스트는 두 요청의 순서와 최종 상태를 확인한다.

### 3.3 MEDIUM — `removeBookIds` 원소 검증

#### 수정 파일

| 파일 | 변경 계획 |
|---|---|
| `src/main/java/com/acorn/abc/admin/collection/dto/AdminCollectionPatchRequest.java` | `removeBookIds`를 `List<@NotNull @Positive Long>`으로 선언한다. `status`와 목록 중 하나 이상 필요하다는 교차 규칙은 기존처럼 Service에서 유지한다. |
| `src/test/java/com/acorn/abc/admin/collection/controller/AdminCollectionControllerTest.java` | `[null]`, `[0]`, `[-1]` 요청이 `400 Bad Request`, `VALIDATION_ERROR`이고 service를 호출하지 않는지 검증한다. |
| `src/test/java/com/acorn/abc/collection/service/AdminCollectionServiceTest.java` | Controller를 우회한 호출도 방어하도록 `null` 원소·0·음수 목록이 `VALIDATION_ERROR`가 되는 방어 검증을 추가한다. Bean Validation을 우회할 수 있는 내부 호출에도 일관성을 유지한다. |

#### 구현 방식

1. DTO에는 컨테이너 원소 검증을 추가해 요청 단계에서 잘못된 ID를 차단한다.
2. Service의 중복·빈 요청 검사와 별개로 `removeBookIds`의 각 ID가 null이 아니고 양수인지 다시 확인한다. 이 방어 검증은 Controller 외 호출이나 테스트용 직접 호출에서의 비정상 쿼리 실행을 막는다.
3. 정상적인 “존재하지 않는 양수 ID”는 기존 idempotent 삭제 정책을 유지한다. 즉 `[999999]`는 200이지만 `[null]`, `[0]`, `[-1]`은 400이다.
4. 신규 ErrorCode를 만들지 않고 기존 `VALIDATION_ERROR` 및 GlobalExceptionHandler 응답 형식을 그대로 사용한다.

## 4. Swagger·Postman·DB 재검증 계획

기존 산출물 경로 `api-test-results/관리자 컬렉션 API/0717 전체 보완`의 체크리스트와 SQL을 보완한다. 실행 전 DB 상태 확인, 테스트용 접두어 seed, 테스트, 증거 기록, 정확한 ID 기반 cleanup 순서를 유지한다.

| 구분 | 추가 시나리오 | 확인 증거 |
|---|---|---|
| Swagger | PATCH body의 `removeBookIds: [null]`, `[0]`, `[-1]` | 400 / `VALIDATION_ERROR`, DB·감사 로그 무변경 |
| Swagger | 005 생성, 006 상세, 002 수정 역할 분리 | 201/200, 문서의 request·response와 실제 응답 일치 |
| Postman | 동일 컬렉션 대상 매핑 PUT과 PATCH를 거의 동시에 전송 | 두 요청의 응답 순서, 최종 `collection_book`·상태·감사 로그 정합성 |
| DB SQL | 성공 호출 전후 `collection`, `collection_book`, `admin_audit_log` 조회 | action/target/targetId 및 매핑 수·상태 일치 |
| 자동 통합 테스트 | 감사 로그 writer 실패를 강제 | 서비스 호출 실패 후 도메인 row와 매핑이 원복되고 audit row가 없음 |

테스트 SQL은 실제 스키마인 `src/main/resources/schema.sql`의 컬럼·FK·제약을 기준으로 작성한다. 테스트가 만든 row만 삭제하며 기존 운영/공유 데이터는 수정하지 않는다.

## 5. 구현 순서

1. 본 계획 문서를 기준으로 테스트 fixture와 cleanup 대상 FK 순서를 먼저 확인한다.
2. `AdminCollectionService` 네 쓰기 메서드에 `@Transactional`을 추가한다.
3. `AdminCollectionPatchRequest`와 Service의 원소 단위 방어 검증을 추가한다.
4. Controller·Service 단위 테스트에 null/0/음수 요청 케이스를 추가한다.
5. Spring 프록시 기반 통합 테스트에서 잠금 경로, 감사 로그 성공, 감사 로그 실패 롤백을 구현한다.
6. 기준 API 명세, A-018 화면 문서, 프론트 참고 문서, 설계문서 반영예정 기록을 계약표 기준으로 함께 갱신한다.
7. Swagger/Postman/DB 체크리스트와 SQL에 추가 시나리오를 기록하고 수동 실행한다.
8. 관련 단일 테스트 → 전체 `./gradlew.bat build` → 수동 검증·cleanup 순으로 확인한다.


### 완료 기준

1. 네 쓰기 API가 실제 Spring 트랜잭션 안에서 동작하고, `PESSIMISTIC_WRITE` 경로가 정상 실행된다.
2. 감사 로그 저장 실패 시 생성·수정·매핑·PATCH의 데이터 변경이 각각 rollback됨을 통합 테스트로 확인한다.
3. `removeBookIds`의 null·0·음수 원소는 service 호출 전 400으로 반환하고, 직접 서비스 호출도 방어한다.
4. API 명세·A-018 화면 문서·프론트 참고 문서가 002 수정, 005 생성, 006 상세의 동일 계약을 표현한다.
5. Swagger/Postman/DB 결과에 성공·실패·동시 요청·cleanup 증거가 남는다.
6. 신규 ErrorCode, Handler, schema.sql 변경 없이 관련 테스트와 전체 build가 성공한다.
