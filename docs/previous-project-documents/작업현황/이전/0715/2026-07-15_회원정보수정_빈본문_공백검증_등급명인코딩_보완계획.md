# 회원정보 수정 빈 본문·공백 검증 및 등급명 인코딩 보완 계획

## 1. 문서 목적

- 회원가입 및 회원정보 조회·수정 Swagger/Postman/프론트 연동 결과를 실제 저장 증거 기준으로 판정한다.
- `PATCH /api/v1/me`의 빈 본문, 빈 JSON, 공백 문자열 처리 규칙을 확정한다.
- `GET /api/v1/me`와 `PATCH /api/v1/me` 응답의 등급명이 깨지는 원인을 확인하고 수정하는 순서를 정한다.
- 수정 후 다시 작성할 Swagger/Postman 체크리스트와 테스트 데이터 SQL의 개선 형식을 정한다.

이 문서는 수정 계획만 다룬다. 이 문서 작성 단계에서는 Java 소스, 설정, SQL을 수정하거나 새로운 테스트 SQL·체크리스트를 만들지 않는다.

## 2. 기준 API 및 범위

| API ID | Method | URL | 이번 점검 범위 |
|---|---|---|---|
| API-AUTH-001 | POST | `/api/v1/auth/signup` | 회원가입, 아이디·이메일 중복 검증 |
| API-ME-001 | GET | `/api/v1/me` | 회원정보 사전 조회, 등급명 인코딩 |
| API-ME-002 | PATCH | `/api/v1/me` | 수정, 빈 본문·공백·초기화 정책, 등급명 인코딩 |

### 2.1 범위 제외

- 프론트 화면 디자인 변경
- 마이페이지 요약 카운트 확장
- 신규 `ErrorCode` 추가
- API URL 또는 HTTP Method 변경
- 이 계획 단계에서의 실제 코드 구현과 자동 테스트 실행
- 새로운 Swagger/Postman 체크리스트 및 테스트 SQL 파일 생성

## 3. 현재 테스트 결과 판정

기존 체크리스트와 저장된 JSON·화면 캡처를 대조한 결과 전체 판정은 **부분 실패**다.

| 구분 | 판정 | 근거 |
|---|---|---|
| 정상 회원가입 | 통과 | 201 응답 증거 확인 |
| 로그인 아이디 중복 가입 | 통과 | 409 응답 증거 확인 |
| 이메일 중복 가입 | 통과 | 409 응답 증거 확인 |
| 회원정보 정상 수정 | 부분 실패 | 수정값은 반영되지만 응답 등급명이 깨짐 |
| 수정 시 이메일 중복 | 통과 | 409 응답 증거 확인 |
| JWT 없이 회원 API 호출 | 통과 | 401 응답 증거 확인 |
| 회원정보 조회 | 부분 실패 | `gradeName`, `nextGradeName`이 정상 한글이 아님 |
| Swagger 빈 본문 | 재시험 필요 | Swagger UI가 필수 본문 전송을 클라이언트에서 차단하므로 백엔드 응답 증거가 아님 |
| 프론트 이름 공백 | 프론트 검증 통과 | 화면에서 `이름을 입력하세요.`로 전송을 차단함. 백엔드 검증 증거는 아님 |
| Postman 빈 본문·공백 | 실패/미확인 | 기대하는 400 JSON 응답 증거가 완성되지 않음 |

### 3.1 빈 본문에서 응답이 보이지 않는 이유

- `@RequestBody`가 필수이므로 Swagger UI는 본문 입력란이 완전히 비면 요청 자체를 보내지 않는다.
- 프론트는 이름이 공백이면 화면 검증에서 요청을 보내지 않는다.
- 두 경우 모두 네트워크 요청이 발생하지 않으므로 백엔드 JSON 응답이 없는 것이 정상이다.
- 백엔드의 빈 본문 처리 결과는 Swagger UI가 아니라 Postman 또는 동등한 HTTP 클라이언트로 실제 요청을 전송하여 확인해야 한다.
- Swagger 테스트 편의를 위해 요청 본문을 선택 사항으로 바꾸지는 않는다.

### 3.2 등급명 손상 판정

- 저장된 JSON을 UTF-8로 해석해도 `씨앗`, `새싹`이 아니라 손상된 문자열이 들어 있다.
- 따라서 PowerShell 출력 또는 Markdown 표시만의 문제가 아니라 실제 응답 데이터 문제로 본다.
- `data.sql`의 등급명 원문은 정상 한글이므로 현재 DB 저장값과 초기화·연결 문자셋을 순서대로 확인해야 한다.

## 4. 확정 처리 정책

### 4.1 PATCH 요청 필드 정책

| 요청 형태 | 확정 동작 |
|---|---|
| 요청 본문 없음 | 400 `VALIDATION_ERROR` JSON 응답 |
| `{}` 또는 모든 수정 필드가 `null` | 변경할 값이 없으므로 400 `VALIDATION_ERROR` |
| `name` 누락 또는 `null` | 다른 필드가 유효하게 수정되는 경우 기존 이름 유지 |
| `name`이 `""` 또는 공백만 존재 | 400, `errors[].field`에 `name` 표시 |
| `email` 누락 또는 `null` | 다른 필드가 유효하게 수정되는 경우 기존 이메일 유지 |
| `email`이 `""` 또는 공백만 존재 | 400, `errors[].field`에 `email` 표시 |
| `phone` 누락 또는 `null` | 기존 전화번호 유지 |
| `phone`이 `""` 또는 공백만 존재 | 사용자가 삭제를 요청한 것으로 보고 DB `null` 저장 |
| `gender` 누락 또는 `null` | 기존 성별 유지 |
| `gender="NONE"` | 선택 안 함으로 보고 DB `null` 저장 |
| `gender=""` 또는 허용되지 않은 값 | 400, `errors[].field`에 `gender` 표시 |

`phone` 공백은 유효한 삭제 명령이므로, `phone`만 공백으로 보낸 요청은 “변경할 값 없음”으로 판단하지 않는다.

### 4.2 오류 응답 정책

- 공통 `ErrorResponse` 형식을 유지한다.
- 빈 본문과 빈 JSON은 기존 `VALIDATION_ERROR`를 사용한다.
- 필드 공백·형식 오류는 가능한 한 `MethodArgumentNotValidException` 흐름으로 처리해 `errors[].field`와 거절 사유를 제공한다.
- 신규 `ErrorCode`는 만들지 않는다.

### 4.3 등급명 정책

- API-ME-001과 API-ME-002 응답은 등급명을 정확한 한글로 반환해야 한다.
- 테스트 대상 회원 기준 예상값은 `gradeName="씨앗"`, `nextGradeName="새싹"`이다.
- 손상된 DB 문자열이 확인되면 설정만 고치고 종료하지 않고 기존 행도 정상 한글로 복구한다.

## 5. 코드 수정 계획

### 5.1 빈 본문 예외를 400 JSON으로 변환

대상: `src/main/java/com/acorn/abc/common/exception/GlobalExceptionHandler.java`

1. `HttpMessageNotReadableException` 전용 처리기를 추가한다.
2. 본문 누락 또는 읽을 수 없는 JSON을 400 `VALIDATION_ERROR` 공통 JSON으로 변환한다.
3. 범용 예외 처리기로 빠져 500이 되지 않도록 한다.
4. 잘못된 JSON 문법과 본문 누락의 외부 응답 형식은 동일하게 유지하되 로그 원인은 구분한다.

### 5.2 DTO 공백 및 무변경 요청 검증

대상: `src/main/java/com/acorn/abc/member/dto/MemberUpdateRequest.java`

1. `name`과 `email`은 `null`을 허용하면서 값이 존재할 때 빈 문자열·공백만 있는 문자열을 거부한다.
2. `email`은 공백 검증을 통과한 뒤 이메일 형식과 최대 길이를 검증한다.
3. 클래스 단위 검증 또는 동등한 DTO 검증으로 `{}`와 모든 필드 `null`을 거부한다.
4. `phone=""` 또는 공백은 유효한 명시적 삭제 요청으로 인정한다.
5. `gender="NONE"`은 허용하고 빈 문자열은 거부한다.
6. DTO 검증 실패가 필드 오류 배열에 반영되도록 메시지와 필드 연결 방식을 정한다.

### 5.3 서비스 방어 검증 유지

대상: `src/main/java/com/acorn/abc/member/service/MemberService.java`

1. DTO 검증이 기본 진입점이더라도 서비스의 이름·이메일 공백 방어 검증은 유지한다.
2. 전화번호 공백을 `null`로, `gender="NONE"`을 `null`로 정규화하는 기존 정책을 유지한다.
3. 중복 이메일 검사와 기존값 유지 로직이 새 DTO 검증으로 회귀하지 않는지 확인한다.

### 5.4 등급명 인코딩 원인 확인 및 수정

대상 후보:

- `src/main/resources/data.sql`
- `src/main/resources/application.properties`
- 실제 MySQL `member_grade` 데이터

수정 전에 다음 쿼리로 DB 저장 바이트를 확인한다.

```sql
SELECT grade_id, grade_name, HEX(grade_name)
FROM member_grade
ORDER BY grade_id;
```

정상 UTF-8 바이트 예상값:

| 등급명 | 예상 HEX |
|---|---|
| 씨앗 | `EC94A8EC9597` |
| 새싹 | `EC8388EC8BB9` |
| 나무 | `EB8298EBACB4` |
| 도토리 | `EB8F84ED86A0EBA6AC` |

원인별 처리 순서:

1. DB 바이트가 이미 손상된 경우 초기 데이터 입력 경로와 DB/연결 문자셋을 먼저 수정한다.
2. `spring.sql.init.encoding=UTF-8`을 명시해 SQL 초기화 파일 해석 기준을 고정한다.
3. 기존 손상 행은 정상 한글 값으로 복구한 뒤 HEX와 API 응답을 다시 확인한다.
4. DB 바이트가 정상인데 응답만 깨지면 JDBC URL의 Unicode·문자 인코딩 설정과 HTTP `Content-Type` 응답 바이트를 점검한다.
5. 설정 변경은 원인 확인 후 필요한 최소 항목만 적용한다.

## 7. Swagger/Postman 재시험 계획

### 7.1 필수 재시험

- Postman에서 요청 본문을 완전히 제거한 API-ME-002 요청: 400 JSON 확인
- Postman과 Swagger에서 `{}` 요청: 400 확인
- Postman과 Swagger에서 이름·이메일의 빈 문자열 및 공백 문자열: 400 필드 오류 확인
- 전화번호 빈 문자열: 200 및 DB `null` 확인
- `gender="NONE"`: 200 및 DB `null` 확인
- 정상 GET·PATCH: `씨앗`, `새싹` 정확한 응답 확인
- 수정 후 GET 재조회: 변경값과 등급명 유지 확인

Swagger UI는 필수 본문을 완전히 비운 요청을 전송하지 않으므로 “본문 없음” 케이스는 Postman 증거를 기준으로 한다. Swagger에서는 `{}`와 필드별 공백 요청을 확인한다.

## 8. 후속 테스트 산출물 작성 계획

코드 수정과 자동 테스트가 끝난 뒤 다음 두 파일을 새로 작성한다. **현재 단계에서는 생성하지 않는다.**

- 회원가입·회원정보 수정 테스트 데이터 준비/검증/원복 SQL
- 회원가입·회원정보 수정 Swagger/Postman 재시험 체크리스트 Markdown

기존 산출물이 불편했던 문제를 반복하지 않도록 두 파일은 각각 단독으로 테스트를 끝낼 수 있게 작성한다.

### 8.1 테스트 계정 사용 기준

- 테스트에 사용하는 회원·관리자·OAuth 계정은 `api-test-results/전체 회원 정보.txt`에 기재된 계정으로만 제한한다.
- 위 파일의 계정은 회원가입이 필요 없는 기존 가입 완료 계정이며, 테스트 시작 시 이미 DB에 존재하는 것을 전제로 한다.
- API-ME-001·API-ME-002 테스트를 위해 회원가입 API를 호출하거나 회원 레코드를 `INSERT`하지 않는다. 지정 계정으로 로그인 또는 OAuth 인증하여 JWT를 발급받는 단계부터 시작한다.
- 문서 작성자가 임의의 로그인 아이디, 이메일, 회원 ID 또는 OAuth 계정을 새로 만들지 않는다.
- API-AUTH-001을 다시 확인해야 한다면 기존 계정은 아이디·이메일 중복 검증에만 사용하며, 정상 신규 가입을 위해 기존 계정을 삭제하거나 새로운 계정을 임의 생성하지 않는다.
- SQL 파일과 체크리스트에는 동일한 계정 별칭, 로그인 아이디, 이메일, 권한, 인증 방식을 일관되게 적는다.
- JWT 문자열을 문서에 고정하지 않고, 지정 계정의 로그인 또는 OAuth 인증으로 현재 JWT를 발급받는 단계를 해당 시나리오 앞에 포함한다.
- 계정 파일에 없는 테스트 계정이 필요해지는 경우 임의로 추가하지 않고 `범위확인필요`로 남긴다.

### 8.2 두 파일 공통 진행 순서

SQL과 Markdown 중 어느 파일을 열더라도 다른 파일을 참조하지 않고 다음 작업과 남은 작업을 알 수 있어야 한다. 두 파일에 같은 시나리오 번호와 같은 단계 번호를 사용하며, 각 시나리오는 다음 순서를 생략하지 않는다.

1. 사용할 계정, 인증 방식, 테스트 목적을 확인한다.
2. 변경 전 DB 상태를 전체 `SELECT` 문으로 확인하고 예상 조회 결과를 적는다.
3. 필요한 보조 데이터 `INSERT`, `UPDATE` 또는 사전 원복 SQL을 전체 문장으로 실행하고 예상 반영 건수를 적는다. 지정 회원 계정 자체는 `INSERT`하거나 삭제하지 않는다.
4. 호출할 API ID, Method, 전체 URL, 헤더, JWT 사용 계정, JSON body를 확인한다.
5. Swagger 또는 Postman에서 API를 호출하고 예상 HTTP 상태와 예상 JSON을 확인한다.
6. API 호출 후 DB 상태를 전체 `SELECT` 문으로 확인하고 예상값과 비교한다.
7. 같은 시나리오의 다음 API 호출이 있으면 전체 URL·body·예상 응답을 다시 적고 호출한다.
8. 다음 호출 후 DB 검증도 전체 `SELECT` 문과 예상 결과를 다시 적는다.
9. 시나리오 완료 후 원복 SQL을 실행한다.
10. 원복 확인용 전체 `SELECT` 문을 실행하고 예상 최종 상태를 확인한다.
11. 실제 응답 증거 경로와 `통과/실패/재시험 필요` 판정을 기록한 뒤 다음 시나리오 번호를 안내한다.

각 단계는 `다음 단계: 시나리오 02의 1단계`처럼 이후 진행 위치를 명시한다. 공통 SQL 절이나 다른 문서의 번호만 참조하지 않고, 현재 단계에서 필요한 명령·URL·body·예상 결과를 그대로 반복해서 적는다.

예시 구조:

```text
[시나리오 01 - 1단계] 변경 전 DB 확인
SELECT ...;
예상 결과: ...

[시나리오 01 - 2단계] 테스트 데이터 준비
INSERT INTO ...;
예상 결과: 1행 반영

[시나리오 01 - 3단계] API 호출
API ID: API-ME-002
Method/URL: PATCH /api/v1/me
인증 계정: 전체 회원 정보.txt의 회원 A
Body: {}
예상 응답: HTTP 400, VALIDATION_ERROR

[시나리오 01 - 4단계] 호출 후 DB 확인
SELECT ...;
예상 결과: 변경 없음

[시나리오 01 - 5단계] 원복 및 원복 확인
UPDATE ...;
SELECT ...;
예상 결과: 테스트 시작 전 상태

다음 단계: 시나리오 02의 1단계
```

### 8.3 SQL 파일 작성 원칙

- 각 시나리오 주석에 API ID, Method, 전체 URL을 적는다.
- `전체 회원 정보.txt`에서 선택한 계정 별칭과 JWT 필요 여부를 적는다.
- 테스트 전 상태 확인 쿼리와 예상 결과를 적는다.
- 데이터 준비 쿼리 직후 “이제 어느 도구에서 어떤 URL·본문으로 요청할지”를 그대로 적는다.
- 요청 후 실행할 DB 검증 쿼리와 예상 결과를 적는다.
- 각 시나리오 종료 위치에 원복 쿼리를 배치한다.
- 다른 Markdown 절 번호를 찾아보라고 안내하지 않고 필요한 JSON body를 SQL 주석에 전부 포함한다.
- `SELECT`, `INSERT`, `UPDATE`, 원복 쿼리는 일부 조건이나 생략 기호 없이 실행 가능한 전체 SQL로 적는다.
- SQL 주석만 따라가도 Swagger/Postman 호출 시점, 예상 응답, 호출 이후 검증 쿼리, 다음 시나리오를 알 수 있게 한다.
- 각 단계 시작 주석에 완료 표시란(`[ ]`)과 실제 결과 기록 위치를 둔다.
- 등급명은 값과 `HEX(grade_name)`을 함께 확인한다.

### 8.4 체크리스트 Markdown 작성 원칙

- 모든 테스트 행에 API ID, Method, 전체 URL을 반복해서 적는다.
- `전체 회원 정보.txt`에서 선택한 계정 별칭, JWT 필요 여부, 헤더, 정확한 JSON body를 각 시나리오에 포함한다.
- 예상 HTTP 상태와 예상 JSON 핵심 필드를 적는다.
- 테스트 전 준비 SQL, 응답 후 검증 SQL, 예상 DB 결과, 원복 SQL을 각 시나리오 안에 직접 포함한다.
- 모든 DB 쿼리는 실행 가능한 전체 문장으로 코드 블록에 적고 `SQL 파일의 몇 번 쿼리 참조` 같은 지시를 사용하지 않는다.
- 체크박스를 단계마다 배치하고 마지막 완료 단계 아래에 다음 시나리오 번호와 시작 작업을 적는다.
- 본문 없음과 `{}`를 서로 다른 시나리오로 분리한다.
- Swagger에서 실행할 수 없는 본문 없음 케이스는 Postman 전용이라고 명시한다.
- 실제 응답 파일·화면 캡처 경로와 `통과/실패/재시험 필요` 판정 칸을 둔다.
- 인증 성공 증거와 JWT 없음 증거가 같은 폴더 의미로 섞이지 않도록 증거 경로를 단순하게 정리한다.

## 9. 완료 조건

다음 항목이 모두 충족되어야 이 후속 작업을 완료로 판단한다.

- 빈 본문이 400 공통 JSON을 반환한다.
- `{}`와 모든 필드 `null` 요청이 400을 반환한다.
- 이름·이메일 공백은 필드가 표시된 400 응답을 반환한다.
- 전화번호 공백과 `gender="NONE"`은 각각 DB `null`로 저장된다.
- API-ME-001과 API-ME-002가 정상 한글 등급명을 반환한다.
- 실제 DB 등급명 바이트와 문자열 검증이 통과한다.
- 관련 자동 테스트와 전체 build가 통과한다.
- 개선된 SQL과 체크리스트를 각각 하나만 보고도 수동 테스트·DB 검증·원복까지 수행할 수 있다.
- Swagger/Postman 재시험 증거가 저장되고 기존 체크리스트의 실패·미확인 항목이 통과로 갱신된다.
