## 1. 문서 목적과 범위

이 문서는 다음 두 결과를 하나로 정리한다.

1. 도서·카테고리·컬렉션 사용자 공개 API의 코드리뷰 결과
2. 부족한 Swagger·Postman·DB 검증을 위한 **후속 테스트 문서 생성 계획**

이번 작업에서는 후속 Swagger 체크리스트나 Postman Collection, 테스트 SQL, `api-test-results` 증거 파일을 실제로 만들지 않는다. 기존 자동 테스트만 실행해 현재 기준선을 확인하고, 수동·통합 재검증은 어떤 문서와 시나리오로 수행할지 계획까지만 확정한다.

관리자 도서·카테고리·컬렉션 CRUD와 외부 도서 수집 API는 이번 코드리뷰 범위에서 제외한다.

## 4. 코드리뷰 발견사항

### 4.1 HIGH — 수정 후 재검증 필요

#### H-01. 로그인 회원의 컬렉션 도서 카드가 항상 `favoriteYn=false`를 반환한다

- 근거
  - `src/main/java/com/acorn/abc/collection/controller/CollectionController.java:28-47`에는 `@AuthenticationPrincipal`이 없다.
  - `src/main/java/com/acorn/abc/collection/service/CollectionService.java:69`, `83-85`는 회원 식별자 없이 카드 변환을 호출한다.
  - `src/main/java/com/acorn/abc/book/service/BookService.java:202-205`는 `toCardResponses(books, null)`을 호출한다.
  - `CollectionSummaryResponse`와 `CollectionDetailResponse`는 `favoriteYn`을 포함한 공통 `BookCardResponse`를 사용한다.
- 영향
  - 같은 도서가 `API-BOOK-001/002/005`에서는 즐겨찾기 `true`, `API-COLLECTION-001/002`에서는 `false`가 될 수 있다.
  - 홈 컬렉션·이벤트 화면의 즐겨찾기 UI가 잘못 표시된다.
- 권고
  - 두 컬렉션 Controller에서 선택적 회원 정보를 받고 Service와 `findCardsByCollectionId`까지 `memberId`를 전달한다.
  - 비회원과 로그인 회원의 동일 도서 응답을 교차 검증하는 Controller·Service 테스트를 추가한다.

#### H-02. `previewSize<=0` 요청이 `500 INTERNAL_SERVER_ERROR`로 이어질 수 있다

- 근거
  - `CollectionService.java:117-124`는 0 이하를 0으로 정규화한다.
  - `CollectionService.java:82-85`는 `null`만 빈 미리보기로 처리하고 0은 Repository 호출로 넘긴다.
  - `BookService.java:202-204`는 `PageRequest.of(0, limit)`을 호출하며 page size 0은 허용되지 않는다.
  - 처리되지 않은 `IllegalArgumentException`은 `GlobalExceptionHandler.java:61-65`의 일반 500 처리로 갈 수 있다.
- 영향
  - 잘못된 공개 입력이 서버 장애 응답처럼 보이고 공통 Validation 규칙을 위반한다.
- 권고
  - `previewSize<1`을 `400 VALIDATION_ERROR`로 거절하는 방식을 우선 권고한다.
  - 0을 “미리보기 없음”으로 허용하려면 `PageRequest` 생성 전에 빈 목록을 반환하도록 계약과 코드를 함께 명시한다.
  - `-1`, `0`, `1`, `6`, `12`, `13` 경계값을 자동·수동 테스트에 모두 넣는다.

#### H-03. 공개 카드 조회와 컬렉션 미리보기에 N+1·쿼리 fan-out 위험이 있다

- 근거
  - `Book.java:32-34`의 출판사 연관은 LAZY이다.
  - `BookService.java:234-246`은 각 카드에서 출판사명을 읽는다.
  - 목록·추천·컬렉션 쿼리는 출판사를 fetch join/entity graph로 가져오지 않는다.
  - `CollectionService.java:58-60`, `82-85`는 컬렉션 한 건마다 도서 카드 조회를 다시 실행한다.
- 영향
  - `size=100` 및 다수 미리보기 요청은 익명 공개 API에서도 많은 DB round trip과 큰 지연을 만들 수 있다.
- 권고
  - 도서 카드 조회에서 출판사를 entity graph 또는 fetch join으로 묶는다.
  - 현재 페이지의 컬렉션 ID 전체에 대해 미리보기 도서·저자·출판사를 일괄 조회한다.
  - Hibernate query count와 MySQL `EXPLAIN`을 후속 검증에 포함한다.

### 4.2 MEDIUM — 계약·정합성 또는 테스트 보완 필요

#### M-01. 기본 `size`가 공통 규칙과 계획의 10이 아니라 20이다

- 공통 규칙은 `size=10`을 정의하고, 카탈로그 수정계획도 20→10 변경을 지시한다.
- `BookService.java:53-55`, `CollectionService.java:28-30`은 여전히 `DEFAULT_SIZE=20`이다.
- `BookServiceTest` 일부는 20을 기대해 오래된 동작을 고정한다.
- 권고: 기본값을 10으로 통일하거나 공통 규칙과 계획을 공식적으로 개정한 뒤, 생략·명시 파라미터 테스트를 추가한다.

#### M-02. `collectionId`는 구현·프론트에는 있지만 최종 API 명세에는 없다

- `BookController.java:35-42`, `BookListCriteria`, `BookSpecifications.java:64-79`에는 구현되어 있다.
- 최신 프론트 문서 `ABC_front_화면.md:402`는 U-006에서 `collectionId` 전달을 요구한다.
- `api-spec(final).md:269`의 API-BOOK-001 요청에는 `collectionId`가 없다.
- 권고: 최신 프론트와 현재 구현을 유지하는 방향으로 명세에 `collectionId` 및 다른 필터와의 조합 규칙을 추가한다.

#### M-03. 추천의 KEYWORD 사용 여부가 기준 문서끼리 충돌한다

- API 명세와 `BookRepository.java:55-69`는 AUTHOR/CATEGORY/KEYWORD 추천을 지원한다.
- 비즈니스 정책 문서의 같은 절 안에서도 “장르 키워드 기준”과 “장르 키워드/해시태그 제외”가 충돌한다.
- 권고: KEYWORD 유지 또는 제외를 먼저 결정하고, 결정 전에는 Swagger/Postman 기대값을 확정하지 않는다.

#### M-04. 잘못된 추천 `type`과 없는 `baseBookId`가 조용히 fallback된다

- `BookService.java:287-299`는 지원하지 않는 `type`을 `MAIN`으로 바꾼다.
- `BookService.java:195-199`는 `baseBookId`의 존재·AVAILABLE 상태를 검증하지 않는다.
- 권고: 잘못된 `type`은 400으로 처리하고, 없는/비공개 기준 도서는 404 또는 빈 결과 중 하나를 명세로 결정한다.

#### M-05. 검색어의 `%`, `_`가 SQL LIKE wildcard로 동작하고 길이 제한이 없다

- 바인딩 파라미터를 사용하므로 SQL Injection은 확인되지 않았다.
- 다만 `q=%`, `q=_`가 문자 검색이 아니라 광범위 매칭·leading wildcard scan으로 동작한다.
- 권고: wildcard literal 처리 정책과 최대 검색어 길이를 정하고 escape 및 경계 테스트를 추가한다.

#### M-06. 잘못된 page/size/limit 값이 400이 아니라 기본값·상한값으로 바뀐다

- `BookService.java:302-320`, `CollectionService.java:127-139`는 음수 page, 0 이하 size, 상한 초과 값을 조용히 보정한다.
- 공통 규칙은 Validation 실패를 `400 VALIDATION_ERROR`로 처리하도록 한다.
- 권고: Request Criteria 또는 Controller 파라미터 제약으로 명시적으로 검증하고 모든 공개 목록 API에 같은 정책을 적용한다.

#### M-07. 실제 MySQL Repository 테스트의 ID 회수 방식이 동시 실행에 취약하다

- `BookRepositoryTest.java:212-216` 등은 INSERT 뒤 `SELECT MAX(id)`로 방금 생성한 ID를 찾는다.
- 공유 DB에서 다른 세션이 사이에 INSERT하면 다른 행을 선택할 수 있다.
- 권고: connection-scoped generated ID 또는 JPA persist 결과를 사용하고 테스트 데이터 이름을 매 실행 고유하게 만든다.

### 4.3 LOW — 테스트 자체의 정합성 수정 필요

#### L-01. `BookServiceTest`가 DB에서 불가능한 대여 상태 `RENTED`를 사용한다

## 5. 아키텍처 BLOCK 및 범위 확인 필요 항목

다음 항목은 코드만 보고 기대 결과를 임의로 정하면 안 된다. 후속 테스트 체크리스트를 작성하기 전에 문서 소유자가 계약을 확정해야 한다.

| 항목 | 현재 충돌 또는 공백 | 권고 결정 |
|---|---|---|
| API-BOOK-001 `collectionId` | 프론트·코드에는 있고 final API spec에는 없음 | 명세에 정식 추가하고 조합 우선순위 정의 |
| `section` 허용값 | 코드는 `event`만 특별 처리하고 다른 값은 일반 목록으로 처리. 프론트 내비게이션은 `section=recommend`도 사용 | `event`, `recommend` 등 enum과 각각의 동작 정의. 추천은 API-BOOK-005로 redirect/호출할지도 결정 |
| 추천 KEYWORD | API spec·코드와 비즈니스 정책 문구가 충돌 | AUTHOR/CATEGORY/KEYWORD 최종 집합 확정 |
| EVENT 정렬 | API spec은 “운영 정렬”, 코드는 SERIES와 같은 `displayOrder` 기반 정렬 | EVENT의 운영 정렬 키를 명시하거나 같은 정렬임을 명세에 기록 |
| EVENT 데이터 모델 | 정책 문서는 `EVENT/EVENT_BOOK`, runtime schema와 final API는 `COLLECTION/COLLECTION_BOOK + collectionType=EVENT` | 정책 문서를 현행 모델로 개정하거나 별도 EVENT 모델 필요 여부 재결정 |
| 이벤트 날짜 | `startDate/endDate`가 있지만 공개 조회는 ACTIVE만 확인 | 날짜 자동 노출 제어인지 관리자 status가 단일 기준인지 결정 |
| 컬렉션 상세 크기 | 현재 unpaged 전체 목록 | pagination 또는 컬렉션 최대 도서 수 계약 정의 |
| 카테고리 이상 데이터 | cycle 방어가 없고, ACTIVE 자식의 부모가 INACTIVE면 응답 트리의 parent 관계가 불완전해질 수 있음 | write/import cycle 방지, read visited set, orphan 노출 정책 결정 |
| 직접 `categoryId` 필터 | parentCategoryId는 ACTIVE 트리만, 직접 categoryId/search는 카테고리 ACTIVE를 확인하지 않음 | 비활성 카테고리 직접 접근 허용 여부 통일 |

아키텍처 판정은 `BLOCK`이다. 위 계약이 미확정인 상태에서 테스트를 먼저 작성하면 우연한 현재 동작을 정답으로 고정할 위험이 있다.

## 6. 확인된 정상 구현

- 공개 7개 GET 경로는 `SecurityConfig.java:60-69`에서 비회원 접근을 허용하며 명세와 일치한다.
- JPQL과 Specification은 바인딩 파라미터를 사용하며 SQL Injection 경로는 발견되지 않았다.
- 주요 도서 목록·검색·상세·추천은 `BOOK.status=AVAILABLE`을 기준으로 결과 도서를 제한한다.
- 컬렉션 도서 조회는 비공개 도서를 제외한다.
- 카테고리 API는 ACTIVE만 조회하고 `displayOrder`, ID 순서를 사용한다.
- 도서 카드의 저자와 로그인 회원 즐겨찾기 조회는 목록 단위 bulk query를 사용한다.
- 도서 상세의 최신 대여 상태 조회는 `createdAt`, `rentalId` 역순으로 tie-break한다.
- 공통 `ApiResponse`와 `PageResponse` DTO를 반환하고 Entity를 직접 노출하지 않는다.

### 7.3 기존 Swagger·Postman·DB 증거 상태

### 8.4 Postman 역할

대상 API는 모두 GET이므로 POST/PUT의 중복 생성 같은 동시성 테스트는 하지 않는다. 대신 Postman은 Swagger와 다른 다음 역할을 맡는다.

- 파라미터 data set으로 조합을 반복 실행한다.
- `status`, `success`, `code`, PageResponse 필드, 정렬, 최대 개수를 자동 assertion한다.
- 비회원과 로그인 회원 결과에서 같은 `bookId`의 `favoriteYn`만 달라지는지 비교한다.
- 두 번 연속 실행해 응답과 DB가 멱등·무변경인지 확인한다.
- invalid 값이 500이 아닌 400/404로 끝나는지 일괄 확인한다.

### 8.5 DB 검증 설계

DB 검증은 단순 화면 캡처가 아니라 “왜 그 응답이어야 하는가”를 증명하도록 작성한다.

- API 호출 전 대상 도서·카테고리·컬렉션·매핑 row를 SELECT로 저장한다.
- AVAILABLE/ACTIVE/HIDDEN/ENDED 조합별 포함·제외를 SQL 결과와 API JSON으로 대조한다.
- SERIES의 `display_order`, EVENT의 확정된 운영 정렬을 DB와 응답 순서로 대조한다.
- 최신 대여 상태는 `created_at DESC, rental_id DESC` 결과와 상세 응답을 비교한다.
- GET 실행 전후 row count와 핵심 값이 같음을 확인한다.
- 성능 검증은 실제 페이지 크기와 previewSize에서 query count, 실행 시간, `EXPLAIN`을 기록한다.
- 테스트 종료 후 prefix row와 매핑 row가 0건인지 확인한다.

### 8.6 문서 작성·실행 순서

1. 아키텍처 BLOCK 계약을 결정한다.
2. H-01, H-02를 수정하고 자동 회귀 테스트를 먼저 추가한다.
3. 기본 size·validation 정책과 추천 정책을 코드·명세에 동기화한다.
4. 체크리스트 문서를 작성하고 시나리오 ID를 확정한다.
5. 테스트 DB 상태 확인·백업·seed를 수행한다.
6. Swagger 정상/오류/회원 상태를 실행한다.
7. Postman data-driven 회귀를 실행한다.
8. DB 전후·정렬·필터·성능을 확인한다.
