## 2. 확정 API 계약

### 2.1 기본 계약

| 항목 | 확정값 |
|---|---|
| API ID | `API-AUTH-006`(최초 배정 `API-AUTH-004`에서 변경, PR49 후속수정계획 §3) |
| Method | `GET` |
| URL | `/api/v1/auth/check-login-id?loginId={값}` |
| 인증 | 불필요, JWT 없이 호출 가능 |
| Request Body | 없음 |
| Query Parameter | `loginId`, 필수 |
| 성공 상태 | HTTP 200 |
| 검증 실패 상태 | HTTP 400 |
| DB 변경 | 없음, 조회 전용 |

### 2.2 요청 검증

형식 검증은 선택 사항이 아니라 이번 구현 범위에 포함한다. 회원가입과 중복 확인의 판정 차이를 막기 위해 `SignupRequest.loginId`와 아래 규칙을 완전히 동일하게 유지한다.

1. 값은 필수이며 `null`, 누락, 빈 문자열, 공백 문자열을 허용하지 않는다.
2. 길이는 5자 이상 20자 이하이다.
3. 영문 대소문자와 숫자만 허용한다: `^[a-zA-Z0-9]+$`.
4. 공백 제거 또는 대소문자 변환을 서버가 임의로 수행하지 않는다.
5. 형식이 잘못되면 Repository를 조회하지 않고 HTTP 400 `VALIDATION_ERROR`를 반환한다.

직접 `@RequestParam`에 제약을 붙이지 않고 신규 `CheckLoginIdRequest` DTO에 검증을 둔다. Controller는 `@Valid @ModelAttribute CheckLoginIdRequest`로 받아 기존 `MethodArgumentNotValidException` 기반의 필드 오류 JSON 형식을 유지한다.

### 2.3 성공 응답 의미

사용 가능한 아이디와 이미 사용 중인 아이디 모두 정상 조회 결과이므로 HTTP 200을 반환한다.

```json
{
  "success": true,
  "code": "OK",
  "data": {
    "loginId": "abc123",
    "available": true
  }
}
```

- `available=true`: 현재 DB에 동일한 로그인 아이디가 없다.
- `available=false`: 현재 DB에 동일한 로그인 아이디가 있다.
- 이미 사용 중인 아이디를 확인하는 요청에는 HTTP 409를 사용하지 않는다.
- HTTP 409 중복 오류는 실제 회원가입 요청에서 동시 요청 등으로 충돌했을 때 기존 정책대로 유지한다.

## 3. 구현 계획

### 3.1 요청 DTO 신규 작성

대상 파일:

`src/main/java/com/acorn/abc/auth/dto/CheckLoginIdRequest.java`

계획:

```java
public record CheckLoginIdRequest(
        @NotBlank(message = "아이디는 필수입니다.")
        @Size(min = 5, max = 20, message = "아이디는 5~20자로 입력해주세요.")
        @Pattern(regexp = "^[a-zA-Z0-9]+$", message = "아이디는 영문과 숫자만 사용할 수 있습니다.")
        String loginId
) {
}
```

- 실제 구현 시 메시지와 Annotation 순서를 `SignupRequest.loginId`와 다시 대조한다.
- 동일한 규칙을 별도 상수나 공통 Annotation으로 추출하는 리팩터링은 이번 범위에서 제외한다.

### 3.2 응답 DTO 신규 작성

대상 파일:

`src/main/java/com/acorn/abc/auth/dto/CheckLoginIdResponse.java`

계획:

```java
public record CheckLoginIdResponse(String loginId, boolean available) {
}
```

### 3.3 Service 조회 로직 추가

대상 파일:

`src/main/java/com/acorn/abc/auth/service/AuthService.java`

계획:

```java
@Transactional(readOnly = true)
public CheckLoginIdResponse checkLoginId(String loginId) {
    boolean exists = memberRepository.existsByLoginId(loginId);
    return new CheckLoginIdResponse(loginId, !exists);
}
```

- 조회 전용 트랜잭션으로 명시한다.
- 기존 `existsByLoginId`를 그대로 사용하며 Repository와 Entity는 수정하지 않는다.
- 아이디가 존재해도 예외를 던지지 않고 `available=false`를 반환한다.

### 3.4 Controller 엔드포인트 추가

대상 파일:

`src/main/java/com/acorn/abc/auth/controller/AuthController.java`

계획:

```java
@GetMapping("/check-login-id")
@Operation(summary = "로그인 아이디 중복 확인")
public ResponseEntity<ApiResponse<CheckLoginIdResponse>> checkLoginId(
        @Valid @ModelAttribute CheckLoginIdRequest request) {
    CheckLoginIdResponse response = authService.checkLoginId(request.loginId());
    return ResponseEntity.ok(ApiResponse.ok(response));
}
```

- 실제 반환 코드는 현재 `AuthController`의 `ApiResponse` 조립 방식과 동일하게 맞춘다.
- 요청 본문을 받지 않으며 Query Parameter만 사용한다.
- Swagger에서 `loginId` 필수 여부와 검증 조건이 드러나도록 Request DTO에 Schema 설명이 필요하면 기존 DTO 문서화 패턴에 맞춰 추가한다.

### 3.5 익명 접근 허용

대상 파일:

`src/main/java/com/acorn/abc/common/config/SecurityConfig.java`

계획:

- GET 공개 경로 목록에 `/api/v1/auth/check-login-id`를 추가한다.
- POST 인증 공개 목록이나 `/api/v1/auth/**` 전체를 넓게 공개하지 않는다.
- JWT 없이 호출했을 때 401이 아니라 입력값에 따른 200 또는 400이 반환되는지 보안 설정 통합 테스트와 수동 테스트로 확인한다.

### 3.6 스키마와 예외 코드

- `member.login_id`의 기존 `UNIQUE` 제약을 사용하므로 `schema.sql` 변경은 없다.
- 기존 검증 실패 코드 `VALIDATION_ERROR`를 사용하므로 신규 `ErrorCode`는 만들지 않는다.
- 조회 API는 데이터를 생성하거나 갱신하지 않으므로 별도 마이그레이션 SQL은 없다.

### 5.1 두 파일의 공통 작성 원칙

- 두 파일을 번갈아 보지 않아도 각각 하나만으로 처음부터 끝까지 테스트할 수 있게 작성한다.
- 두 파일의 테스트 번호와 실행 순서를 완전히 동일하게 유지한다.
- 각 테스트마다 `API-AUTH-006`, `GET`, 전체 URL, 인증 여부, Query Parameter, 예상 HTTP 상태, 예상 JSON 핵심 필드, 실행 전 DB 확인 SQL, 실행 후 DB 확인 SQL, 예상 DB 결과, 다음 단계와 원복 여부를 모두 적는다.
- SQL 파일에도 주석으로 Swagger/Postman 호출 위치, 정확한 URL, 예상 응답, 다음 순서를 적는다.
- Markdown 체크리스트에도 생략 없는 전체 SQL을 코드 블록으로 적는다.
- 이 API는 익명 공개 API이므로 로그인 계정, JWT, OAuth 토큰은 사용하지 않는다.
- Swagger/Postman 및 DB 수동 테스트의 기존 회원 기준 자료는 `C:/Github/abc-proj-win/api-test-results/전체 회원 정보.txt`만 사용한다.
- 위 TXT에 기록된 **이미 가입되어 있는 계정의 loginId만** 중복 아이디 확인값으로 사용한다. 비밀번호, 토큰 등 인증정보는 이 API에 필요하지 않으므로 체크리스트나 SQL에 옮기지 않는다.
- 수동 테스트를 위해 회원가입 API를 호출하거나 `member` 테이블에 INSERT하지 않으며, 신규 테스트 계정을 생성하지 않는다.
- 사용 가능 아이디는 실행 전 `member` 조회 결과가 0건인 테스트 전용 문자열을 선택한다. 해당 아이디로 회원가입하거나 DB에 INSERT하지 않는다.
- GET 조회 API이므로 정상 동작 시 DB 변경과 원복 DML이 없어야 한다. 각 파일에 `원복 대상 없음`과 그 근거를 명시한다.

### 5.2 파일별 독립 실행 순서

각 테스트 케이스는 아래 순서로 작성한다.

1. 실행 전 DB 상태를 확인하는 전체 `SELECT`를 실행한다.
2. Swagger 또는 Postman에서 정확한 GET URL을 JWT 없이 호출한다.
3. HTTP 상태와 공통 응답 JSON의 필드를 예상값과 비교한다.
4. 같은 전체 `SELECT`를 다시 실행해 DB가 변경되지 않았음을 확인한다.
5. 체크 결과를 기록하고 다음 번호의 테스트로 이동한다.
6. 전체 종료 후 변경 데이터와 원복 대상이 없음을 최종 `SELECT`로 확인한다.

### 5.3 필수 수동 테스트 목록

| 번호 | 요청 | 예상 결과 |
|---|---|---|
| 1 | DB에 존재하지 않는 5~20자 영문·숫자 아이디 | 200, `available=true`, 전후 DB 0건 |
| 2 | `전체 회원 정보.txt`의 기존 회원 아이디 | 200, `available=false`, 전후 DB 1건 |
| 3 | 기존 아이디의 대소문자만 바꾼 값 | 현재 `utf8mb4_0900_ai_ci` 기준 200, `available=false` |
| 4 | `loginId` Query Parameter 누락 | 400, `VALIDATION_ERROR`, `errors.field=loginId` |
| 5 | `loginId=` 빈 값 | 400, `VALIDATION_ERROR` |
| 6 | 공백 문자열 | 400, `VALIDATION_ERROR` |
| 7 | 4자 아이디 | 400, `VALIDATION_ERROR` |
| 8 | 정확히 5자 아이디 | 200, DB 존재 여부에 맞는 `available` |
| 9 | 정확히 20자 아이디 | 200, DB 존재 여부에 맞는 `available` |
| 10 | 21자 아이디 | 400, `VALIDATION_ERROR` |
| 11 | 한글 포함 아이디 | 400, `VALIDATION_ERROR` |
| 12 | 밑줄 또는 특수문자 포함 아이디 | 400, `VALIDATION_ERROR` |
| 13 | Authorization 헤더 없이 유효 아이디 호출 | 200이며 401이 아님 |

- Swagger와 Postman에서 동일한 번호를 각각 수행하고 결과 파일이나 응답 저장 위치를 체크리스트에 기록한다.
- 8번과 9번 경계값은 실행 전 DB 조회로 사용 가능 여부를 확정한 뒤 그 값에 맞는 `available`을 예상값으로 적는다.

기록할 내용:

1. `docs/API 명세/api-spec(final).md` 인증 API 목록에 `API-AUTH-006`이 없다는 현재 차이.
2. 추가할 Method, URL, 익명 인증 정책, Query 검증 규칙, 200/400 응답 계약.
3. 중복된 유효 아이디는 오류가 아니라 `available=false`인 정상 응답이라는 이유.
4. 회원가입 화면에서 중복 확인 결과를 표시하되 실제 회원가입 409 처리는 계속 필요하다는 이유.
5. `SecurityConfig` 공개 GET 경로가 추가되었다는 보안 설계 변경점.
6. 기존 `member.login_id UNIQUE`를 그대로 사용하므로 ERD, 런타임 스키마, 데이터 마이그레이션 변경은 없다는 판단.
7. 실제 API 명세와 화면흐름도는 나중에 일괄 최신화하고 이번 작업에서는 수정하지 않는다는 범위.

## 8. 구현 순서

1. `CheckLoginIdRequest`, `CheckLoginIdResponse`를 추가한다.
2. `AuthService.checkLoginId` 조회 로직과 단위 테스트를 추가한다.
3. `AuthController`에 `API-AUTH-006`을 추가하고 Controller 검증 테스트를 작성한다.
4. `SecurityConfig` 공개 GET 경로를 추가하고 보안 설정 통합 테스트를 작성한다.
5. 관련 단위 테스트와 전체 build를 실행한다.
6. Swagger/Postman 체크리스트와 독립 실행 가능한 SQL 파일을 작성한다.
7. Swagger와 Postman에서 전체 수동 테스트를 수행하고 DB 무변경을 확인한다.
8. 초경량 이해 메모와 설계문서 반영예정 기록을 작성한다.
9. `git diff`, 테스트 결과, 수동 응답 결과를 대조한 뒤 PR 준비 상태를 판단한다.

## 9. 완료 조건

- `API-AUTH-006`이 JWT 없이 호출된다.
- 회원가입과 동일한 아이디 검증 규칙이 적용된다.
- 유효한 미사용 아이디는 200 `available=true`이다.
- 유효한 기존 아이디와 대소문자 변형은 현재 DB 중복 기준에 따라 200 `available=false`이다.
- 잘못된 입력은 400 공통 `VALIDATION_ERROR` JSON이다.
- 실제 회원가입의 기존 중복 검사와 DB `UNIQUE` 제약은 유지된다.
- 관련 자동 테스트와 전체 build가 통과한다.
- Swagger/Postman 전체 항목이 예상 응답과 일치하고 DB 변경이 없다.
- 수동 테스트는 `전체 회원 정보.txt`의 기존 계정만 참고했고 신규 회원 계정, 회원가입 요청, `member` INSERT가 발생하지 않았다.
- 테스트용 `.sql`과 체크리스트 `.md` 각각 하나만 보고도 전체 테스트를 독립적으로 수행할 수 있다.
- 이해 메모와 설계문서 반영예정 기록이 지정 경로에 작성된다.

## 10. 범위 제외와 주의사항

- 프론트의 확인 버튼, 안내 문구, debounce 구현은 백엔드 작업 범위에서 제외한다.
- 중복 확인 API 호출은 아이디를 예약하지 않는다. 확인 직후 다른 요청이 같은 아이디로 먼저 가입할 수 있으므로 프론트는 실제 회원가입의 409 응답을 반드시 처리해야 한다.
- 공개 조회 API에 대한 rate limit, CAPTCHA, 아이디 존재 여부 노출 완화 정책은 현재 공통 인프라에 없는 별도 보안 과제이며 이번 범위에서 추가하지 않는다.
- 공통 검증 Annotation 추출, 전체 인증 DTO 리팩터링, API 명세 원문 수정, 화면흐름도 원문 수정은 이번 구현 PR에서 제외한다.
