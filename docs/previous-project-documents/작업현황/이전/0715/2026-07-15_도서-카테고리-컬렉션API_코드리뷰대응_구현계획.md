# 도서·카테고리·컬렉션 API 코드리뷰 대응 구현계획

## 1. 목적

선행 코드리뷰의 `REQUEST CHANGES`와 아키텍처 `BLOCK`에 대응하기 위해 다음 작업을 한 실행계획으로 정리한다.

1. 도서·카테고리·컬렉션 공개 API의 실제 소스 수정
2. Controller·Service·Repository 자동 테스트 보강
3. 실제 설계 문서를 직접 수정하지 않고, 설계 문서 수정계획과 이해메모 작성
4. 지정된 API 테스트 결과 경로에 Swagger·Postman·DB 재검증 체크리스트 Markdown 작성
5. 같은 경로에 재현·검증·원복용 MySQL SQL 파일 작성

이번 단계에서는 **이 구현계획 문서만 수정**한다. Java·SQL·API 명세·정책 문서·프론트 문서는 수정하지 않고, 설계 문서 수정계획·이해메모·테스트 체크리스트·SQL도 아직 생성하지 않으며, Swagger/Postman/DB 수동 테스트도 실행하지 않는다.

## 2. 작업 원칙과 범위

### 2.1 작업 원칙

- 런타임 DB 기준은 `src/main/resources/schema.sql`로 고정한다.
- API URL·요청·응답·상태코드는 `docs/API 명세/api-spec(final).md`를 기준으로 대조하되, 충돌·누락은 실제 문서를 직접 고치지 않고 별도 설계 문서 수정계획에 기록한다.
- 문서 충돌 항목은 아래 결정 게이트를 먼저 승인받은 뒤 구현한다.
- 신규 `ErrorCode`는 만들지 않는다. 필요성이 새로 확인되면 별도 승인요청 문서를 먼저 작성한다.
- `GlobalExceptionHandler`, `ErrorCode`, `SecurityConfig`처럼 전역으로 적용되는 공통 코드는 기본 변경 대상에서 제외한다. 변경이 불가피하면 호출 도메인·응답 계약·회귀 범위를 먼저 문서화하고 별도 승인을 받는다.
- `BookRepository`와 `BookService`는 타 도메인이 공유하므로 기존 공용 메서드의 의미를 바꾸지 않고 카탈로그 전용 조회 경로를 우선한다.
- 새 의존성이나 `build.gradle` 변경 없이 현재 Spring/JPA/Mockito/MockMvc 구성으로 구현한다.
- 테스트 데이터는 고유 prefix와 생성된 ID로만 정리하며 기존 업무 데이터를 수정·삭제하지 않는다.
- 실제 MySQL 테스트는 현재 상태 확인 → 테스트 데이터 생성 → 실행 → 검증 → FK 역순 원복 순서로 수행한다.

## 3. 구현 전 결정 게이트

다음 항목은 기준 문서가 충돌하거나 동작이 명확하지 않다. 아래 권고안으로 승인된 이후 Java 구현·테스트 기대값·설계 문서 수정계획을 함께 고정한다. 실제 API 명세·정책·프론트 문서는 이번 작업에서 직접 수정하지 않는다.

| ID | 결정 항목 | 확인된 충돌 | 권고안 |
|---|---|---|---|
| D-01 | API-BOOK-001 `collectionId` | 최신 프론트와 코드는 사용하지만 final API spec에는 없음 | 기존 구현을 유지하고 API-BOOK-001 정식 query parameter로 명세화 |
| D-02 | `section` 허용값 | 코드는 `event`만 처리하고 프론트 라우트에는 `section=recommend`도 있음 | API-BOOK-001은 `EVENT`만 허용. 추천 화면은 API-BOOK-005 호출로 분리하고 그 관계를 프론트/API 문서에 명시 |
| D-03 | 추천 KEYWORD | API spec·코드는 KEYWORD 포함, 비즈니스 정책의 뒤쪽 확정 문구는 제외 | 정책 문서 560행을 최종 결정으로 보고 KEYWORD 추천을 제거, AUTHOR/CATEGORY/MAIN만 유지 |
| D-04 | EVENT 정렬 | API spec은 “운영 정렬”, 코드는 SERIES와 같은 displayOrder 정렬 | EVENT도 `displayOrder ASC NULLS LAST → collectionBook.createdAt ASC → book.createdAt DESC`로 명세화 |
| D-05 | EVENT 데이터 모델 | 정책 문서는 `EVENT/EVENT_BOOK`, runtime은 `COLLECTION/COLLECTION_BOOK + EVENT type` | 런타임·final API 모델을 유지하고 정책 문서의 별도 EVENT 테이블 문구를 현행 컬렉션 모델로 개정 |
| D-06 | EVENT 날짜 노출 | start/end가 있지만 공개 조회는 ACTIVE만 확인 | 이번 범위는 관리자 `status=ACTIVE`를 단일 노출 기준으로 유지. 날짜는 응답 정보이며 자동 필터에 사용하지 않음을 명시 |
| D-07 | 잘못된 paging/limit | 현재 조용히 보정, 공통 규칙은 400 | `page>=0`, `1<=size<=100`, `1<=limit<=50`, `1<=previewSize<=12`를 벗어나면 400 |
| D-08 | 없는 추천 기준 도서 | 현재 MAIN/빈 결과로 조용히 진행 | `baseBookId`가 없거나 AVAILABLE이 아니면 기존 `BOOK_NOT_FOUND` 404 |
| D-09 | 비활성 카테고리 직접 필터 | parentCategoryId는 ACTIVE만, categoryId/search는 상태 미확인 | 공개 API의 직접 categoryId도 ACTIVE만 허용하고 비활성 ID는 빈 결과 처리 |
| D-10 | 검색 wildcard | `%`, `_`가 LIKE 연산자로 동작 | 사용자 입력을 literal로 escape하고 검색어 최대 길이를 100자로 제한 |
| D-11 | 컬렉션 없음 오류 코드 | 현재 `COMMON_NOT_FOUND`, 도메인 전용 코드는 없음 | 기존 `COMMON_NOT_FOUND`를 유지해 전역 `ErrorCode`와 클라이언트 계약 변경을 피함 |
| D-12 | 컬렉션 미리보기 생략값 | `previewSize` 생략 시 빈 배열, 0은 내부에서 500 가능 | 생략은 빈 배열 유지, 명시적 0은 `VALIDATION_ERROR` 400으로 구분 |
| D-13 | N+1 개선 범위 | `BookRepository`는 대여·결제·통계·배치·외부도서도 공유 | 상속 `findAll`의 전역 동작을 바꾸지 않고 공개 카탈로그 전용 조회/배치 메서드를 추가 |
| D-14 | 기본 페이지 크기 | API 계약 목표는 10, 일부 구현·테스트는 20 | 도서·검색·컬렉션 공개 목록의 기본 `size=10`으로 통일 |
| D-15 | ACTIVE 자식·비활성 부모 | 현재 ACTIVE 자식이 루트처럼 보이면서 비활성 `parentCategoryId`를 응답할 수 있음 | 공개 트리와 상위 카테고리 탐색에서는 비활성 조상을 가진 하위 트리도 노출하지 않음 |

승인되지 않은 결정은 `범위확인필요`로 남기고 해당 분기의 코드·테스트·Swagger 기대값을 작성하지 않는다.

### 3.1 설계 문서 산출물 계획

구현 착수 시 실제 기준 문서를 직접 수정하지 않고 다음 두 문서만 새로 만든다.

```text
docs/작업현황/설계문서/2026-07-15_도서-카테고리-컬렉션API_설계문서_수정계획.md
docs/작업현황/설계문서/이해 메모/이해메모.md
```

- 설계 문서 수정계획에는 대상 원문 경로, 현재 문구·누락, 권장 변경안, 결정 ID, 프론트 영향, 실제 반영 보류 사유를 적는다.
- 이해메모에는 API별 `API/목적/흐름/DB/주의`를 5줄 이하로 기록하고, 확정 결정과 미확정 결정을 분리한다.
- 대상 원문은 API 명세, 비즈니스 정책 문서, 최신 프론트 문서이며 모두 참조만 하고 이번 작업에서는 수정하지 않는다.
- 이후 실제 설계 문서 반영은 이 계획과 사용자 승인을 기준으로 별도 작업에서 수행한다.

### 3.2 전역·타 도메인 영향 통제

- `GlobalExceptionHandler`: 기존 `ConstraintViolationException`, 타입 불일치, `BusinessException` 처리로 요구 응답을 충족하므로 수정하지 않는다.
- `ErrorCode`: paging·limit·section·검색 입력은 기존 `VALIDATION_ERROR`, 없는 추천 기준 도서는 `BOOK_NOT_FOUND`, 없는 컬렉션은 `COMMON_NOT_FOUND`를 사용한다. 신규 코드가 필요해지면 구현 전에 별도 승인요청 문서를 만든다.
- `SecurityConfig`: 공개 GET 경로가 이미 허용되어 있고 선택적 로그인도 동작하므로 수정하지 않는다. 현재 작업트리의 인증 관련 변경과도 겹치지 않는다.
- `BookRepository`: 대여·결제·통계·배치·외부도서에서 공유하므로 inherited `findAll` override나 공용 조회 의미 변경을 피한다. 공개 목록·검색·추천·컬렉션 카드에만 적용되는 명시적 메서드로 최적화한다.
- `BookService`: `getAvailableBookOrThrow`는 서재·즐겨찾기·리뷰가, `toCardResponses`는 즐겨찾기가 호출한다. 이 두 공용 메서드의 시그니처·AVAILABLE 규칙은 유지하고 컬렉션용 overload 또는 별도 내부 메서드를 추가한다.
- 다른 도메인 파일 변경이 꼭 필요하면 변경 전 호출자 목록, 변경 이유, 기존 계약, 예상 회귀, 검증 방법을 설계 문서 수정계획에 적고 범위를 확정한다.
- 단위 테스트 수정은 별도 비즈니스 결정 게이트로 두지 않되, 공유 메서드나 공통 코드가 바뀌면 관련 타 도메인 회귀 테스트를 검증 범위에 포함한다.

## 4. 리뷰 항목별 실제 소스 구현 계획

### 4.1 H-01 — 컬렉션 BookCard의 회원 `favoriteYn` 전달

#### 수정 파일

- `src/main/java/com/acorn/abc/collection/controller/CollectionController.java`
- `src/main/java/com/acorn/abc/collection/service/CollectionService.java`
- `src/main/java/com/acorn/abc/book/service/BookService.java`
- `src/test/java/com/acorn/abc/collection/controller/CollectionControllerTest.java` 신규
- `src/test/java/com/acorn/abc/collection/service/CollectionServiceTest.java` 신규
- `src/test/java/com/acorn/abc/book/service/BookServiceTest.java`

#### 구현 방식

1. `CollectionController`에 `BookController`와 같은 선택적 `@AuthenticationPrincipal` 표현식을 사용한다.
2. `getCollections`와 `getCollectionDetail`이 `memberId`를 `CollectionService`에 전달하도록 signature를 확장한다.
3. `CollectionService`가 미리보기·상세 카드 조회 시 `memberId`를 `BookService`에 전달한다.
4. `BookService.findCardsByCollectionId`에 `memberId`를 추가하고 `toCardResponses(books, memberId)`를 호출한다.
5. 비회원은 모두 `favoriteYn=false`, 회원은 `favorite_book` 존재 여부가 정확히 반영되도록 기존 bulk favorite 조회를 재사용한다.

#### 검증

- 같은 도서를 API-BOOK과 API-COLLECTION으로 조회했을 때 회원 `favoriteYn`이 일치한다.
- 비회원 요청에서 인증 객체가 없어도 200이며 `favoriteYn=false`이다.
- 즐겨찾기 조회는 카드당 1회가 아니라 book ID 목록 단위 1회로 유지한다.

### 4.2 H-02 — `previewSize<=0` 500 제거

#### 수정 파일

- `src/main/java/com/acorn/abc/collection/controller/CollectionController.java`
- `src/main/java/com/acorn/abc/collection/service/CollectionService.java`
- `src/test/java/com/acorn/abc/collection/controller/CollectionControllerTest.java`
- `src/test/java/com/acorn/abc/collection/service/CollectionServiceTest.java`

#### 구현 방식

1. Controller에 `@Validated`를 추가한다.
2. `previewSize`에 `@Min(1)`, `@Max(12)`를 적용한다.
3. Service의 `normalizePreviewSize`는 null만 “미리보기 미요청”으로 허용하고, 범위 밖 값은 `BusinessException(ErrorCode.VALIDATION_ERROR)`로 방어한다.
4. 어떤 경로에서도 `PageRequest.of(0, 0)`이 만들어지지 않게 한다.
5. `GlobalExceptionHandler`의 기존 `ConstraintViolationException → 400 VALIDATION_ERROR` 경로를 사용하며 새 ErrorCode를 추가하지 않는다.

#### 검증

- `previewSize=-1`, `0`, `13`은 400이다.
- `previewSize=1`, `6`, `12`는 200이고 최대 반환 개수를 지킨다.
- 파라미터 생략은 200이며 현재 계약대로 빈 `previewBooks`를 반환한다.

### 4.3 H-03 — 출판사 N+1 및 컬렉션 preview fan-out 축소

#### 수정·신규 파일

- `src/main/java/com/acorn/abc/book/repository/BookRepository.java`
- `src/main/java/com/acorn/abc/book/service/BookService.java`
- `src/main/java/com/acorn/abc/collection/repository/CollectionBookRepository.java` 신규
- `src/main/java/com/acorn/abc/collection/repository/CollectionBookPreviewProjection.java` 신규
- `src/main/java/com/acorn/abc/collection/service/CollectionService.java`
- 관련 Repository·Service 통합 테스트

#### 구현 방식

1. `BookRepository`의 공개 카탈로그 전용 목록·검색·추천·컬렉션 조회에 `@EntityGraph(attributePaths = "publisher")` 또는 동등한 fetch join을 적용한다.
2. 공유 inherited `findAll(Specification, Pageable)`을 전역 override하지 않고, 공개 목록용 명시적 Repository 메서드 또는 custom repository fragment를 사용한다. 단순 JPQL join은 fetch가 아니므로 쿼리 수로 검증한다.
3. `CollectionBookRepository`에 MySQL 8 `ROW_NUMBER() OVER (PARTITION BY collection_id ORDER BY ...)` 기반 preview projection 조회를 추가한다.
4. 현재 페이지의 collection ID 전체를 한 번에 전달하고 컬렉션별 `previewSize`개 mapping만 가져온다.
5. projection에서 얻은 전체 book ID를 한 번에 조회한 뒤 저자·출판사·회원 favorite를 bulk로 조립한다.
6. `BookService`에 book ID 목록을 카드 맵으로 변환하는 내부 공통 경로를 만들고, 원래 mapping 순서를 보존해 컬렉션별로 재그룹한다.
7. 상세 API는 단일 컬렉션 조회를 유지하되 publisher·author·favorite가 bulk로 처리되게 한다.

#### 성능 검증

- 컬렉션 1건과 10건에서 preview query 수가 컬렉션 수에 비례해 증가하지 않아야 한다.

### 8.2 SQL 안전 규칙

- 광범위한 `DELETE WHERE name LIKE '%TEST%'`를 사용하지 않는다.
- ID 변수와 정확한 prefix를 함께 조건으로 사용한다.
- seed는 테스트에 필요한 신규 row만 INSERT하고 기존 row를 수정하지 않는다.
- cleanup 구간은 문서에서 명확히 분리하고 실행 전 ID 목록을 다시 출력한다.
- SQL 파일에는 credential, token, password hash 원문을 넣지 않는다.

## 11. 완료 기준

- 결정 게이트가 설계 문서 수정계획과 이해메모에 반영되어 있고, 실제 API 명세·정책·프론트 문서는 변경되지 않았다.
- HIGH 3건과 MEDIUM·LOW 회귀 항목이 코드와 자동 테스트로 해결되어 있다.
- API-BOOK/CATEGORY/COLLECTION Controller 테스트와 `CollectionServiceTest`가 존재한다.
- 관련 테스트와 전체 build가 통과한다.
- 지정된 `api-test-results/도서 카테고리 컬렉션 API/0715 전체 보완` 경로에 체크리스트 `.md`와 재검증 `.sql`이 작성되어 있다.
- Swagger·Postman·DB 검증 결과가 체크리스트에 PASS/FAIL로 기록되어 있다.
- GET 호출 전후 DB 무변경과 cleanup 0건 증거가 있다.
- 컬렉션 preview query가 컬렉션 수에 비례해 증가하지 않는다.
- 실행하지 못한 항목과 남은 위험이 명확히 분리되어 있다.

## 12. 예상 위험과 대응

| 위험 | 대응 |
|---|---|
| 문서 결정을 하지 않고 코드부터 수정 | D-01~D-15 승인 전 관련 branch 구현 금지 |
| native window query의 JPA projection 호환 문제 | Repository 단일 테스트를 먼저 작성하고 실패 시 두 단계 bulk 조회 대안 사용 |
| query 최적화로 순서가 바뀜 | projection order와 DTO order를 별도 assertion |
| Method Validation이 standalone MockMvc에서 동작하지 않음 | 기존 Controller 테스트처럼 `MethodValidationPostProcessor` proxy 사용 |
| 실제 DB fixture 충돌 | UUID suffix, `LAST_INSERT_ID()`, transaction rollback 사용 |
| cleanup이 기존 데이터에 영향 | 신규 row만 생성하고 정확한 ID+prefix 조건으로 FK 역순 삭제 |
| 추천 KEYWORD 제거로 프론트 탭 영향 | API·프론트 문서 확인 후 탭 노출과 요청 type을 함께 조정 |
| 컬렉션 상세 대용량 응답 잔존 | 이번 범위 위험으로 기록하고 별도 pagination 계약 작업으로 분리 |

현재 계획의 소스 구현 착수 조건은 **D-01~D-15 결정 승인**이다.
