## 1. 코드리뷰 결과 요약

### 1.1 병합 차단 항목

현재 중복 확인 API에 배정한 `API-AUTH-004`는 최종 API 명세에서 이미 **제외된 비밀번호 재설정 API ID**로 사용되고 있다.

- `docs/API 명세/api-spec(final).md:166-168`: 사용 중인 인증 API는 `API-AUTH-001`~`003`이다.
- `docs/API 명세/api-spec(final).md:385`: `API-AUTH-004`, `API-AUTH-005`는 제외된 비밀번호 재설정 API로 기록되어 있다.
- 기존 구현계획은 중복 확인 API에 `API-AUTH-004`를 재사용하도록 정했다.
- URL과 런타임 동작은 정상이지만 API ID 하나가 두 의미를 가지므로 문서, 테스트 결과, 화면 연계 추적이 깨진다.

### 1.2 정상 반영된 항목

- `GET /api/v1/auth/check-login-id` URL과 `permitAll` 범위는 요구사항대로다.
- `CheckLoginIdRequest` 검증은 회원가입 아이디 규칙과 동일하다.
- 잘못된 Query는 400 `VALIDATION_ERROR`로 처리된다.
- 사용 가능/중복 아이디 모두 200이며 `available=true/false`로 구분된다.
- 기존 `MemberRepository.existsByLoginId()`를 재사용하며 DB를 변경하지 않는다.
- 실제 회원가입의 409와 DB `UNIQUE`가 최종 중복 방어선으로 유지된다.
- 리뷰어 재실행 기준 관련 19개 테스트와 전체 빌드가 통과했다.

### 1.3 비차단 후속 권고

1. 공개 API의 아이디 존재 여부 노출과 자동화된 반복 조회를 운영 공개 전 통제해야 한다.
2. `SignupRequest`와 `CheckLoginIdRequest`에 중복된 로그인 아이디 검증 애노테이션을 공통화해야 한다.
3. MySQL Collation에 따른 대소문자 중복을 Repository 통합 테스트로 고정해야 한다.
4. Swagger/Postman 실제 완료 상태를 PR 본문에 반영해야 한다.
5. 기존 계획에서 예정한 체크리스트, SQL, 이해 메모, 설계문서 반영예정 기록을 만들어야 한다.

수정 대상:

3. 구현 전에 만들 테스트 SQL의 API ID와 파일명/주석
4. 구현 후 만들 초경량 이해 메모의 API ID와 파일명
5. 구현 후 만들 설계문서 반영예정 기록의 API ID와 파일명
6. Java 테스트 주석이나 PR 본문에 API ID가 추가되어 있다면 해당 표기

현재 추적된 Java 코드에는 `API-AUTH-004` 문자열이 없으므로 URL, Controller 메서드, Service 로직, SecurityConfig의 경로를 ID 변경 때문에 수정하지 않는다.

- 신규 `API-AUTH-006`의 목록/상세 명세에 나중에 반영할 정확한 위치와 내용을 `docs/작업현황/설계문서` 하위 반영예정 문서에 기록한다.

## 4. 로그인 아이디 검증 공통화 계획

### 4.1 선택지 비교

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 현재 애노테이션 복제 유지 | 코드 변경이 없다. | 한 DTO만 수정되어 회원가입과 중복 확인의 판정이 갈릴 수 있다. | 제외 |
| B. 길이·정규식 상수만 공통화 | 정규식과 길이 숫자 중복은 줄어든다. | `@NotBlank`, 메시지, 애노테이션 구성은 계속 중복된다. | 제외 |
| C. 조합 애노테이션 `@ValidLoginId` | 두 DTO가 하나의 검증 계약을 사용하고 기존 Bean Validation 흐름을 유지한다. | 애노테이션 파일과 전용 테스트가 추가된다. | **채택** |
| D. 별도 `ConstraintValidator` 구현 | 복잡한 조건이나 DB 검증까지 확장할 수 있다. | 현재는 선언형 제약 세 개면 충분하며 불필요한 코드가 늘어난다. | 제외 |

### 4.2 신규 조합 애노테이션

신규 대상:

`src/main/java/com/acorn/abc/auth/validation/ValidLoginId.java`

구현 원칙:

```java
@Documented
@Constraint(validatedBy = {})
@Target({FIELD, METHOD, PARAMETER, ANNOTATION_TYPE, TYPE_USE, RECORD_COMPONENT})
@Retention(RUNTIME)
@NotBlank(message = "아이디는 필수입니다.")
@Size(min = 5, max = 20, message = "아이디는 5~20자로 입력해주세요.")
@Pattern(regexp = "^[a-zA-Z0-9]+$", message = "아이디는 영문과 숫자만 사용할 수 있습니다.")
public @interface ValidLoginId {
    String message() default "아이디 형식이 올바르지 않습니다.";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

- `@ReportAsSingleViolation`은 사용하지 않는다. 기존 필드별 검증 메시지를 유지하기 위해서다.
- 별도 `ConstraintValidator`는 만들지 않는다.
- 프로젝트에 새 의존성을 추가하지 않는다.

### 4.3 DTO 적용 범위

수정 대상:

1. `src/main/java/com/acorn/abc/auth/dto/SignupRequest.java`
2. `src/main/java/com/acorn/abc/auth/dto/CheckLoginIdRequest.java`

수정 방식:

- 각 `loginId` 구성요소의 `@NotBlank`, `@Size`, `@Pattern` 세 개를 `@ValidLoginId` 하나로 교체한다.
- 검증 메시지, 최소/최대 길이, 정규식, HTTP 400 응답 구조는 변경하지 않는다.
- `LoginRequest.loginId`에는 적용하지 않는다. 로그인은 이미 생성된 기존 계정 식별자를 받는 흐름이고, 이번 공통화 범위는 신규 아이디 생성 및 사용 가능 여부 판정 계약이다.

## 5. 운영 공개 전 보안 선택지

### 5.1 전제

`available=true/false`를 익명 사용자에게 돌려주는 기능은 아이디 존재 여부를 의도적으로 공개한다. 따라서 동일 응답 계약을 유지하면서 계정 열거 가능성을 완전히 제거할 수는 없다. 보안 목표는 정상 사용자의 확인 기능을 유지하면서 자동화된 대량 조회의 속도와 경제성을 제한하고 이상 징후를 탐지하는 것이다.

### 5.2 선택지 비교

| 선택지 | 원래 프론트 계약 유지 | 운영 확장성 | 장점 | 단점 | 판단 |
|---|---:|---:|---|---|---|
| A. `available`을 제거하고 항상 일반 응답 | 아니오 | 높음 | 계정 존재 여부 노출을 가장 강하게 줄인다. | 프론트의 중복 확인 기능 자체가 사라진다. | 제외 |
| B. 애플리케이션 메모리 기반 속도 제한 | 예 | 낮음 | 구현이 빠르고 별도 인프라가 없다. | 다중 인스턴스·재시작·우회에 약하고 직접 보안 로직을 유지해야 한다. | 제외 |
| C. Redis 기반 애플리케이션 속도 제한 | 예 | 높음 | 모든 인스턴스가 같은 카운터를 사용하고 `ApiResponse` 형식의 429를 만들기 쉽다. | 현재 프로젝트에 Redis/관련 의존성이 없어 운영 범위가 커진다. | Edge가 없을 때 대안 |
| D. CDN/WAF/API Gateway의 경로별 속도 제한 + 반복 초과 시 관리형 Challenge | 예 | 높음 | 애플리케이션 앞단에서 자동화 요청을 줄이고 다중 인스턴스에도 일관된다. | 배포 인프라 설정과 관측 체계가 필요하다. | **권장** |
| E. 첫 요청부터 CAPTCHA 필수 | 조건부 | 높음 | 자동화 비용을 높인다. | 정상 회원가입 UX와 접근성을 크게 해치며 CAPTCHA도 단독 방어가 아니다. | 제외 |

### 5.3 권장 보안안

정상 요청의 Method, URL, Query Parameter, 200 응답 DTO는 그대로 유지하고 아래를 운영 공개 전 배포 조건으로 둔다.

1. Edge/CDN/WAF/API Gateway에서 `GET /api/v1/auth/check-login-id` 경로에만 Token Bucket 또는 Sliding Window 속도 제한을 적용한다.
2. 초기 운영 후보값은 IP당 `10회/분`, 순간 Burst `5회`로 두고 실제 정상 트래픽을 관측한 뒤 조정한다. 임계값은 소스에 하드코딩하지 않고 운영 설정으로 관리한다.
3. IP 기준만으로 완전한 방어가 되지 않으므로 경로 전체의 비정상 급증 한도와 IP/ASN 평판을 함께 사용한다.
4. 처음부터 CAPTCHA를 요구하지 않는다. 반복 초과 또는 봇 의심 점수가 높을 때만 Edge의 관리형 Challenge를 적용한다.
5. 제한된 요청은 HTTP 429와 `Retry-After`를 반환한다. 정상 200/400 계약은 바꾸지 않는다.
6. 애플리케이션과 접근 로그에 Query의 원문 `loginId`를 별도 기록하지 않는다. 보안 통계가 필요하면 아이디 원문 대신 단방향 해시 또는 요청 횟수 집계만 사용한다.
7. `Cache-Control: no-store`가 실제 응답에 포함되는지 테스트한다. 현재 Spring Security 기본 헤더로 충족되지 않으면 Controller 또는 공통 보안 설정에서 해당 경로에만 추가한다.
8. 200/400/429 횟수, IP별 급증, 짧은 시간 동안 서로 다른 아이디를 연속 조회하는 패턴을 모니터링하되 원문 아이디를 경보에 남기지 않는다.
9. CORS는 브라우저 출처 제어일 뿐 자동화 도구의 직접 호출을 막지 못하므로 보안 대책으로 간주하지 않는다.

### 5.4 프로젝트 적용 경계

- PR #49의 병합 차단 해소에는 Edge 제품이나 Redis 도입을 포함하지 않는다.
- 현재 저장소에는 rate limit/Redis 관련 의존성이 없으므로 임시 메모리 Map으로 보안 기능을 직접 구현하지 않는다.
- 운영 인프라에 Edge/Gateway가 있으면 권장안 D를 적용한다.
- Edge/Gateway를 사용할 수 없다면 별도 보안 PR에서 Redis 기반 선택지 C를 검토한다. 이때 의존성 추가, 신규 429 `ErrorCode`, `Retry-After`, 분산 카운터 키 정책은 사용자 승인 후 진행한다.
- 운영 보안 정책이 적용되지 않은 상태는 로컬/개발 검증에는 사용할 수 있지만 **운영 공개 완료 상태로 판단하지 않는다.**

### 5.5 보안 근거

- OWASP는 계정 존재 여부 차이가 사용자 열거에 이용될 수 있으며, 일반 응답을 사용할 수 없는 UX에서는 자동화 방어와 CAPTCHA를 방어 계층으로 사용할 수 있다고 설명한다.
- OWASP의 Bot Management 지침은 단일 통제가 아니라 Edge·Application·Business 계층을 조합하고, IP 하나가 아닌 여러 키와 엔드포인트별 Token Bucket/Sliding Window 제한을 권고한다.
- OWASP Logging 지침에 따라 과도한 사용과 검증 실패는 관측하되 개인 식별 가능 데이터는 제거·마스킹·해시 처리한다.

### 6.2 기능 테스트 순서

1. 기존 계정 아이디: 200, `available=false`.
2. DB에 없는 아이디: 200, `available=true`.
3. 기존 아이디의 대소문자 변형: 현재 MySQL Collation 기준 200, `available=false`.
4. Query 누락, 빈 값, 공백: 400, `VALIDATION_ERROR`.
5. 4자/21자: 400, `VALIDATION_ERROR`.
6. 정확히 5자/20자: 200, DB 존재 여부에 맞는 `available`.
7. 한글/밑줄/특수문자: 400, `VALIDATION_ERROR`.
8. JWT 없이 호출: 정상값은 200이고 401이 아님.
9. 정상·실패 응답에 `Cache-Control: no-store` 포함 여부 확인.
10. 모든 호출 전후 DB 조회 결과가 동일한지 확인.

### 6.3 운영 보안 인수 테스트 항목

운영 Edge 정책이 준비된 스테이징 환경에서만 아래를 수행하며 로컬 Swagger/Postman 기능 테스트와 구분한다.

1. 임계값 미만 요청은 기존 200/400 응답 계약을 유지한다.
2. 임계값 초과 요청은 429와 `Retry-After`를 반환한다.
3. 제한 시간이 지나면 정상 요청이 다시 성공한다.
4. 반복 초과 시 관리형 Challenge가 설정대로 동작한다.
5. 접근 로그와 애플리케이션 로그에 원문 `loginId`가 남지 않는다.
