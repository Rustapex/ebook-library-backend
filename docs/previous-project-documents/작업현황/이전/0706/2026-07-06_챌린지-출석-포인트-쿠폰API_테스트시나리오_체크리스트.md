근거: `2026-07-06_챌린지-출석-포인트-쿠폰API_구현계획.md`, `api-test-results/2026-07-07_db_schema_testdata_change_plan.sql`

이 문서는 챌린지/출석/포인트/쿠폰 API(회원용 6개 + 관리자용 6개)를 Swagger로 검증하기 위한 진행표다. 자동화 테스트는 Repository 계층 중심이라, API 레벨 동작은 이 문서와 `api-test-results/챌린지출석포인트쿠폰 API/swagger` 결과 파일로 증명한다.

## 0. 현재 결정 사항

- **schema.sql 유지**: DB CHECK 제약은 `src/main/resources/schema.sql`을 기준으로 유지한다. 로컬 DB가 다르면 DB를 schema 기준으로 맞춘다.
- **테스트 재개 기준**: DB를 초기화하지 않고 `2026-07-07_db_schema_testdata_change_plan.sql`의 정합성 보정만 했다면, Swagger 테스트는 처음부터 다시 하지 않고 남은 항목부터 이어서 진행한다.
- **처음부터 다시 해야 하는 경우**: 새 DB 생성, `DROP`/`TRUNCATE`, 테스트 회원/챌린지/쿠폰/출석 데이터 삭제, `memberId`/`challengeId`/`couponId` 변경이 있으면 기존 Swagger 증거를 폐기하고 처음부터 다시 한다.
- **챌린지 신규 생성 API**: 이번 범위에서 만들지 않는다. `PUT /api/v1/admin/challenges/{challengeId}` 수정 API만 검증한다.
- **관리자 쿠폰 목록 집계**: `GET /api/v1/admin/coupons` 응답에 `issuedCount`/`usedCount`/`expiredCount` 포함.
- **보류 기능**: 출석 7일/30일 연속 쿠폰 자동 지급, 챌린지 보상 중 쿠폰 지급은 이번 검증 범위 밖이다.
- **주의할 계약 불일치**: schema 유지 정책에서는 `point_history.point_type='challenge_reward'`, `challenge_reward.reward_type='coupon'`이 기준이다. 코드가 `CHALLENGE_REWARD` 또는 `COUPON`을 쓰면 해당 API는 실패할 수 있고, 이 경우 DB 문제가 아니라 코드/스키마 계약 불일치로 기록한다.

### 2-4. 재개용 DB 변수 확인

**안전 참고**: 아래 블록은 `SET @변수` 세션 변수 할당과 `SELECT` 조회뿐이라 테이블 데이터를 전혀 변경하지 않는다. 2-1(DB 정합성 보정)보다 먼저 실행했더라도 **되돌릴 필요는 없다** — 롤백 대상 자체가 없다.

다만 **순서상 2-1을 먼저 마친 뒤에 이 블록을 실행(또는 재실행)하는 걸 권장**한다. 2-1을 건너뛰고 먼저 실행하면 `@coupon_id`/`@daily_challenge_id`/`@total_challenge_id` 같은 변수가 아직 정리되지 않은 데이터(예: `coupon.status='UNACTIVE'` 오타, 정합성 안 맞는 챌린지 보상)를 가리킬 수 있어 **변수 값 자체가 부정확**할 위험이 있다. 이 경우 데이터가 잘못된 게 아니라 변수가 잘못된 것이므로, 2-1을 마친 뒤 이 블록만 다시 실행해서 변수를 최신화하면 된다(재실행도 안전 — `SET`/`SELECT`는 몇 번을 실행해도 부작용 없음).

Workbench 새 탭을 열 때마다 아래 변수를 먼저 잡는다. 실제 `login_id`는 현재 테스트 계정에 맞게 바꾼다.

```sql
SET @login_id_a = 'sys1009';
SET @login_id_b = 'wes6027';
SET @login_id_admin = 'adminuser';

SET @member_id_a = (SELECT member_id FROM member WHERE login_id = @login_id_a LIMIT 1);
SET @member_id_b = (SELECT member_id FROM member WHERE login_id = @login_id_b LIMIT 1);
SET @admin_member_id = (SELECT member_id FROM member WHERE login_id = @login_id_admin LIMIT 1);

SET @daily_challenge_id = (
    SELECT challenge_id FROM challenge
    WHERE challenge_name LIKE '%일일%' AND challenge_type = 'DAILY'
    ORDER BY challenge_id DESC LIMIT 1
);

SET @total_challenge_id = (
    SELECT challenge_id FROM challenge
    WHERE challenge_type = 'TOTAL'
    ORDER BY challenge_id DESC LIMIT 1
);

SET @coupon_id = (
    SELECT coupon_id FROM coupon
    WHERE status = 'ACTIVE'
    ORDER BY coupon_id DESC LIMIT 1
);

SELECT
    @member_id_a AS memberId_A,
    @member_id_b AS memberId_B,
    @admin_member_id AS adminMemberId,
    @daily_challenge_id AS dailyChallengeId,
    @total_challenge_id AS totalChallengeId,
    @coupon_id AS couponId;
```

### 3-2. API-COUPON-001 — 내 쿠폰 목록 조회

현재 DB 상태: 테스트용 `member_coupon`에 회원 A의 `ISSUED`/`USED`/`EXPIRED`가 있어야 한다. 없다면 먼저 테스트 데이터를 다시 넣고 진행한다.

시딩 SQL(없을 때만 실행, `@member_id_a`/`@coupon_id`는 2-4절 변수 사용):

```sql
-- 1) ISSUED (만료 임박 2일 후 — #4 만료 임박 플래그 테스트도 겸함)
INSERT INTO member_coupon (member_id, coupon_id, coupon_status, issued_at, expires_at)
VALUES (@member_id_a, @coupon_id, 'ISSUED', NOW(), DATE_ADD(NOW(), INTERVAL 2 DAY));

-- 2) USED (20일 전 발급, 10일 전 사용, 유효기간은 6일 전 만료)
INSERT INTO member_coupon (member_id, coupon_id, coupon_status, issued_at, expires_at, used_at)
VALUES (@member_id_a, @coupon_id, 'USED', DATE_SUB(NOW(), INTERVAL 20 DAY), DATE_SUB(NOW(), INTERVAL 6 DAY), DATE_SUB(NOW(), INTERVAL 10 DAY));

-- 3) EXPIRED (30일 전 발급, 16일 전 만료, 미사용)
INSERT INTO member_coupon (member_id, coupon_id, coupon_status, issued_at, expires_at)
VALUES (@member_id_a, @coupon_id, 'EXPIRED', DATE_SUB(NOW(), INTERVAL 30 DAY), DATE_SUB(NOW(), INTERVAL 16 DAY));
```

**주의**: 이 3개는 한 번씩만 실행한다(중복 실행 시 행이 겹쳐 늘어남 — 실수로 두 번 넣었던 사례 있음). 잘못 중복 삽입했을 때 초기화하는 방법:

```sql
SET SQL_SAFE_UPDATES = 0;
DELETE FROM member_coupon WHERE member_id = @member_id_a;
SET SQL_SAFE_UPDATES = 1;
SELECT COUNT(*) FROM member_coupon WHERE member_id = @member_id_a; -- 0건 확인 후 위 3개 INSERT 재실행
```

사전 DB 확인:

```sql
SELECT mc.member_coupon_id, mc.coupon_id, mc.coupon_status, mc.issued_at, mc.expires_at, mc.used_at
FROM member_coupon mc
WHERE mc.member_id = @member_id_a
ORDER BY mc.member_coupon_id;
```

### 3-3. API-CHALLENGE-002 #1 — 달성+미수령 보상 수령

이 항목은 mutation이다. 반드시 사전/사후 DB를 비교한다.

사전 DB 확인:

```sql
SELECT cp.challenge_progress_id, cp.current_count, cp.achieved_yn, cp.reward_claimed_at
FROM challenge_progress cp
WHERE cp.member_id = @member_id_a
  AND cp.challenge_id = @daily_challenge_id;

SELECT point_balance
FROM member
WHERE member_id = @member_id_a;

SELECT point_history_id, point_type, point_amount, description, created_at
FROM point_history
WHERE member_id = @member_id_a
ORDER BY point_history_id DESC
LIMIT 5;
```

진행 조건:

- `achieved_yn=1`
- `reward_claimed_at IS NULL`

만약 이미 `reward_claimed_at` 값이 있으면, 이 시나리오용 새 DAILY 챌린지와 progress를 만들거나 DB를 초기화해야 한다. 이미 수령된 row로는 #1 정상 수령을 검증할 수 없다.

**`challenge_progress`에 행 자체가 없을 때(사전 DB 확인 결과가 0건인 경우)**: 출석 체크(`API-ATTEND-001`)는 그 시점에 `status='ACTIVE'`인 챌린지만 갱신하므로, DAILY 챌린지를 오늘 출석 이후에 등록했거나 `target_action`이 정확히 `ATTENDANCE`가 아니면 행이 안 생긴다. 오늘 출석은 이미 완료되어 재체크인이 불가능하므로(`ATTENDANCE_ALREADY_EXISTS`), 아래처럼 "달성+미수령" 상태를 직접 시딩한다(`target_count`를 challenge 테이블에서 그대로 가져와 `current_count`와 맞춰서 달성 조건을 만족시킴):

```sql
INSERT INTO challenge_progress (member_id, challenge_id, progress_date, current_count, achieved_yn, achieved_at)
SELECT @member_id_a, @daily_challenge_id, CURDATE(), c.target_count, 1, NOW()
FROM challenge c
WHERE c.challenge_id = @daily_challenge_id;

-- 확인
SELECT challenge_progress_id, current_count, achieved_yn, reward_claimed_at
FROM challenge_progress
WHERE member_id = @member_id_a AND challenge_id = @daily_challenge_id;
```

**Swagger 경로에 넣을 `dailyChallengeId`를 못 찾겠으면**: 챌린지 이름이 같은 DAILY 챌린지가 여러 개(테스트 중 반복 시딩으로 중복 생성) 있을 수 있어 헷갈릴 수 있다. `@daily_challenge_id` 변수 값을 직접 확인하거나, 방금 시딩한 `challenge_progress` 행이 실제로 물려 있는 `challenge_id`를 그대로 쓰면 된다(변수보다 이쪽이 확실함):

```sql
-- 방법 1: 세션 변수 값 확인
SELECT @daily_challenge_id;

-- 방법 2(권장): 방금 시딩한 progress 행이 물린 challenge_id를 직접 확인 — 이 값이 dailyChallengeId
SELECT cp.challenge_progress_id, cp.challenge_id AS dailyChallengeId, c.challenge_name, c.created_at
FROM challenge_progress cp
JOIN challenge c ON c.challenge_id = cp.challenge_id
WHERE cp.member_id = @member_id_a
ORDER BY cp.challenge_progress_id DESC
LIMIT 1;
```

`challenge` 테이블에 이름이 같은 DAILY 챌린지가 여러 건 보인다면(예: 반복 시딩으로 `challenge_id` 5, 7, 9처럼 여러 개 쌓인 경우), 실제로 테스트에 쓰는 건 위 방법 2로 확인된 하나뿐이다. 나머지 중복 row는 지금 당장 안 지워도 테스트엔 지장 없지만, 헷갈림을 막으려면 사용하지 않는 challenge_id는 `challenge_reward`/`challenge_progress`에 연결이 없는지 확인 후 정리해도 된다.

Swagger 요청:

```text
POST /api/v1/challenges/{dailyChallengeId}/reward
인증: 회원 A
```

기대:

- 코드와 schema 계약이 맞으면 `200 OK`, `grantedPoint=100`
- 현재 schema 유지 정책에서 코드가 `CHALLENGE_REWARD`를 insert한다면 `500 INTERNAL_SERVER_ERROR` 가능
- 500이면 실패를 통과로 간주하지 말고, 계약 불일치 재현 증거로 저장

사후 DB 확인:

```sql
SELECT cp.challenge_progress_id, cp.current_count, cp.achieved_yn, cp.reward_claimed_at
FROM challenge_progress cp
WHERE cp.member_id = @member_id_a
  AND cp.challenge_id = @daily_challenge_id;

SELECT point_balance
FROM member
WHERE member_id = @member_id_a;

SELECT point_history_id, point_type, point_amount, description, created_at
FROM point_history
WHERE member_id = @member_id_a
ORDER BY point_history_id DESC
LIMIT 5;
```

판단:

- `200`이면 포인트 증가, `point_history` 추가, `reward_claimed_at` 입력 확인
- `500`이면 트랜잭션 rollback으로 포인트/이력/수령시각이 변하지 않았는지 확인

### 3-4. API-ADMIN-COUPON-001 #2 — 관리자 쿠폰 목록 필터

FROM member_coupon
WHERE coupon_id = @coupon_id
  AND member_id IN (@member_id_a, @member_id_b)
GROUP BY member_id, coupon_id, coupon_status
ORDER BY member_id, coupon_status;
