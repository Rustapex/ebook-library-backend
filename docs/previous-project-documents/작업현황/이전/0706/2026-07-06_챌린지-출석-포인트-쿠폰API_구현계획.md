## 3. 발견한 이슈 (구현 판단 사항 — 사용자 결정 불필요)

아래 3개는 문서 충돌/애매함이 아니라 제가 조사해서 그대로 적용하면 되는 사항입니다. 문서끼리 충돌하거나 애매해서 사용자 확인이 필요한 항목은 4절로 분리했습니다.

### 3-1. `point_history` CHECK 제약 오타 (버그, 정보 기록용)

- `src/main/resources/schema.sql`의 `point_history` 테이블 CHECK 제약:
  ```sql
  CONSTRAINT chk_point_history_point_type CHECK (point_type IN ('challenge_reward', 'REVIEW_REWARD', 'PAYBACK', 'EVENT_REWARD', 'PAYMENT_USE', 'ADMIN_ADJUST'))
  ```
- `challenge_reward`만 소문자이고 나머지 5개는 전부 대문자. api-spec(`:94`, `:315` 등)은 전부 `CHALLENGE_REWARD`(대문자)로 일관되게 표기 — 문서(api-spec)와 실제 코드(schema.sql)가 불일치하는 사례.
- 지금 시점엔 이 사실만 기록해두고 별도 문서 작업은 하지 않는다. 실제 구현 단계에서 고칠 때 "무엇을 수정했는지"만 기록하면 충분하고, 굳이 별도 문서가 필요하면 새 markdown 파일 1개로 남기는 정도면 됨(기존 문서를 손댈 필요 없음).

### 3-2. 패키지 구조 (규칙.md 9절 그대로 적용 — 별도 결정 아님)

`docs/공통문서/백엔드_공통_개발_규칙.md` 9절이 이미 "기능별 controller/service/dto/domain/repository로 분리"를 규정하고 있어, 아래는 새로운 결정이 아니라 이 규칙을 이번 4개 기능에 그대로 적용한 결과다.

| 기능 | 패키지 | 근거 |
|---|---|---|
| 챌린지 (Repository/Service/Controller/DTO) | 기존 `challenge` 패키지 | 도메인이 이미 여기 있음 |
| 출석/포인트 (Repository/Service/Controller/DTO) | 기존 `member` 패키지 | `Attendance`/`PointHistory` 도메인이 이미 `member.domain`에 있음 |

### 3-3. 포인트 지급/차감 공통 로직

- 챌린지 보상 지급(`API-CHALLENGE-002`, `pointType=CHALLENGE_REWARD`)과 관리자 포인트 조정(`API-ADMIN-MEMBER-004`, `pointType=ADMIN_ADJUST`)이 전부 "포인트 이력 저장 + `member.point_balance` 갱신"을 같은 트랜잭션으로 해야 하는 동일 패턴(api-spec 4절 실행순서 공통 규칙과 일치).

### 4-2. 관리자 쿠폰/챌린지 목록 응답에 집계 포함 범위 — 결정 완료(2026-07-06)

**문서 간 충돌 내용 (원문 대조)**

| 문서 | 원문 | 해석 |
|---|---|---|
| api-spec `API-ADMIN-COUPON-001` | Response data: "쿠폰 정의와 발급/사용/만료 현황" | 목록 한 화면에서 "쿠폰 정의"뿐 아니라 "발급/사용/만료 현황"(=숫자 집계 또는 이력)까지 같이 보여줘야 한다는 뜻으로 읽힘 |
| 화면흐름도 A-013 (쿠폰 탭) | "이력: 보유 상태, 발급일, 만료일, 사용일, 사용 결제" | "이력"이라는 단어와 "보유 상태/발급일/사용일" 같은 필드는 **쿠폰 1건 정의에 대한 숫자 집계가 아니라, 발급된 회원쿠폰 개별 건(row)의 목록**처럼 읽힘 |

두 문서 다 "발급/사용/만료 관련 정보를 보여준다"는 데는 동의하지만, **그 정보가 "쿠폰 정의 목록에 곁들이는 집계 숫자"인지 "회원쿠폰 개별 발급 이력 목록"인지가 다르게 읽혀서 충돌**한다.

**"(a) 방법"이 실제로 의미하는 것 — DB 컬럼 추가 아님**

(a)는 `coupon` 테이블에 새 컬럼을 추가하는 게 **아니다**. `GET /api/v1/admin/coupons` 목록 조회 시점에 기존 `member_coupon` 테이블을 `coupon_id` 기준으로 집계 쿼리(`COUNT ... GROUP BY coupon_status`)를 돌려서, 응답 DTO에만 `issuedCount`(발급 총수)/`usedCount`(`coupon_status='USED'` 건수)/`expiredCount`(`coupon_status='EXPIRED'` 건수) 필드를 계산해서 얹는 방식이다. DB 스키마 변경도, 새 테이블도 필요 없다 — 순수하게 조회 쿼리와 응답 DTO 필드만 추가되는 것.

**"(b) 방법"이 의미하는 것**

(b)는 `GET /api/v1/admin/coupons` 응답엔 `coupon` 정의 필드(이름/유형/혜택/유효기간/상태)만 담고, 개별 회원쿠폰 발급 이력(누가 언제 받았고 언제 썼는지)은 아예 다른 화면/엔드포인트로 분리하는 것이다. 문제는 **그 "다른 엔드포인트"가 api-spec URL 요약표에 정의돼 있지 않다** — 즉 (b)를 선택하면 api-spec에 없는 엔드포인트를 하나 더 만들어야 해서, 4-1(챌린지 생성 API)과 비슷한 성격의 "명세에 없는 엔드포인트 신설" 문제가 하나 더 생긴다.

**결정: (a) 채택.** `GET /api/v1/admin/coupons` 응답에 쿠폰 정의 필드 + `issuedCount`/`usedCount`/`expiredCount` 집계값을 포함한다. `member_coupon`을 `coupon_id` 기준으로 집계하는 조회 쿼리만 추가하며, DB 스키마 변경이나 신규 엔드포인트는 없음. (b)(별도 엔드포인트 신설)는 채택하지 않음.

## 9. Swagger 수기 테스트 문서 계획

이 절은 실제 테스트 체크리스트 문서 자체가 아니라, **구현이 끝난 뒤 어떻게 만들지에 대한 계획**이다. `2026-07-03_PR22_테스트시나리오_체크리스트.md`와 같은 구조를 따르되, 이번 범위(회원 API + 관리자 API)에 맞게 준비물이 늘어난다.

### 언제, 왜 지금 안 만드는지

코드가 확정되기 전에 시나리오를 먼저 못박으면 구현 중 세부사항(에러코드, 필드명 등)이 바뀔 때마다 문서를 다시 고쳐야 한다. PR22 때도 실제 구현 완료 후에 코드 동작을 보면서 체크리스트를 작성했던 방식을 그대로 따른다.

### 사전 준비 — 무엇을 미리 갖춰둬야 하는지

**앱 실행**: `.\gradlew.bat bootRun --console=plain`, Swagger UI(`http://localhost:8080/swagger-ui/index.html`) 접속.

**테스트 계정** — PR22 때는 회원 2개(본인 A / 타인 접근 차단용 B)만 있으면 됐지만, 이번엔 관리자 API가 섞여 있어 계정이 하나 더 필요하다.

| 계정 | 용도 |
|---|---|
| 회원 A | 정상 케이스, 본인 리소스 검증 |
| 회원 B | 타인 접근 차단 검증용 |
| 관리자 1 | 관리자 API(`/api/v1/admin/**`) 검증용 |

각 계정 로그인 후 JWT 확보, Swagger `Authorize`에 등록.

**Workbench로 시딩할 테스트 데이터** — 현재 `data.sql`엔 `member_grade` 시드만 있어 아래는 전부 로컬에서 직접 INSERT 필요:
