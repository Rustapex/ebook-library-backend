## 3. Backend 수정 계획 — PR #56 fixture SQL

대상 파일: `src/main/resources/프론트API연결_확인용_테스트데이터.sql`

### 3.1 SERIES 컬렉션 규칙 정정

`§16. 컬렉션 2개`의 `API연결테스트 시리즈 컬렉션` INSERT에서 아래 세 값을 모두 `NULL`로 변경한다.

- `discount_rate`
- `start_date`
- `end_date`

EVENT 행은 검증 목적의 할인율 `20.00`과 기간을 유지한다. SERIES의 `collection_book.display_order`는 양수·고유값을 유지하고, EVENT의 `display_order = NULL`도 변경하지 않는다. `§17` 원복 DELETE의 자연키 조건은 변경하지 않는다.

### 3.2 Backend 완료 기준

| 확인 항목 | 완료 기준 |
|---|---|
| 정적 확인 | SERIES INSERT의 할인율·시작일·종료일이 모두 `NULL`이고 EVENT 행에만 기간·할인율이 존재한다. |
| 수동 SQL 적용 | 실행 전 `§0`으로 대상 DB와 기존 `apitest_%`·`99900000%` 데이터를 확인한 뒤 sidecar SQL을 적용한다. |
| 데이터 확인 | 생성된 SERIES와 EVENT 컬렉션, 각 `collection_book.display_order`가 위 규칙과 일치한다. |
| 원복 확인 | `§17`은 테스트 접두어를 가진 행만 삭제하며, 공유 DB에서는 대상 행을 다시 확인한 뒤 실행한다. |

SQL은 `schema.sql`·`data.sql`을 변경하지 않는 수동 적용 fixture다. 공유 RDS 적용과 원복은 실행 권한·DB 상태 확인이 필요한 별도 수동 검증으로 진행한다.

## 4. Front 수정 계획 — PR #100

### 4.1 A-013 목록의 미조회 잔액 표시 정정

대상 파일: `abc_front/src/pages/admin/A013CouponsPoints/AdminCouponsPointsPage.tsx`

1. `getAdminMembers()`로 만든 목록 상태에서 잔액 미조회 값을 `0`으로 만들지 않는다.
2. 목록용 `pointBalance`는 `number | undefined`(또는 같은 의미의 optional 값)로 유지한다.
3. 목록의 포인트 열은 잔액이 없으면 `-`로 표시한다. `0P`는 상세 조회 또는 포인트 조정 성공 응답으로 실제 `0`이 확인된 경우에만 표시한다.
4. `handleSelectMember()`가 `getAdminMember()`에 성공하면 `usageSummary.pointBalance`를 선택 회원과 해당 목록 항목에 반영한다.
5. 상세 조회나 포인트 조정이 실패하면 선택·목록 잔액 및 이력을 성공한 것처럼 갱신하지 않고 오류만 표시한다.
6. fallback 회원 데이터도 실제 잔액처럼 보이는 값을 넣지 않는다.

### 4.2 A-018 누적 JSX 변경 기록

관리자 컬렉션 A-018의 모달·폼 JSX 변경은 실제 API DTO의 요청·응답 필드에 맞춰 기존 화면 상태를 정렬한 작업임을 PR 본문과 이 문서에 기록한다. 신규 모달·탭·라우트·CSS·클래스명·시각 디자인 변경은 포함하지 않는다.

### 4.3 Front 완료 기준

| 확인 항목 | 완료 기준 |
|---|---|
| 선택 전 목록 | 잔액 미조회 회원은 `0P`가 아니라 `-`로 표시한다. |
| 회원 선택 | 상세 API 성공 뒤에만 실제 `pointBalance`를 선택 카드와 해당 목록 항목에 표시한다. |
| 포인트 조정 성공 | 응답의 `pointBalance`, `pointHistoryId`를 사용해 선택 회원·조회 완료 목록·최근 이력만 갱신한다. |
| 포인트 조정 실패 | 성공 메시지, 가짜 이력, 로컬 잔액 변경이 발생하지 않는다. |
| 컬렉션 상세 | 유효한 `collectionId`로 상세 API를 호출하고, 누락·형식 오류·실패 시 다른 도서 목록을 컬렉션 결과로 표시하지 않는다. |
| A-018 | 실제 API DTO 계약 정렬 목적과 변경 범위가 PR 설명에 기록된다. |

## 5. 실제 HTTP 연동 검증 계획

1. Backend fixture를 로컬 DB에 적용한다. 공유 RDS에는 `§0` 확인과 팀 데이터 충돌 확인 전 적용하지 않는다.
2. 관리자 권한이 있는 별도 계정으로 A-013 화면을 연다. fixture 회원의 `password_hash`는 로그인용 값이 아니므로 관리자 로그인 검증 계정으로 사용하지 않는다.
3. U-001에서 컬렉션을 선택해 U-006으로 이동하고, 상세 API의 도서 목록·오류 경로를 각각 확인한다.
4. A-013에서 fixture 회원을 선택해 실제 잔액 표시를 확인하고, 정상 조정 1회와 서버 오류 또는 유효성 실패 1회를 확인한다.
5. 실행 SQL, 요청 결과, 화면 결과, 원복 여부를 별도 검증 기록에 남긴다.

`npm run build`는 기존 `epubjs` 모듈 누락 상태가 해소된 환경에서만 실행 결과를 완료 근거로 사용한다. 이 보완 계획은 의존성 추가·빌드 설정 변경을 포함하지 않는다.
