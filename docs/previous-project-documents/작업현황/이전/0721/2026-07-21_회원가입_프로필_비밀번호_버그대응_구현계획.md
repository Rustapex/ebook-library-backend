# 2026-07-21 회원가입·프로필·비밀번호 버그 대응 구현계획

작성일: 2026-07-21  
대상: `API-AUTH-001`, `API-ME-002`, `API-ME-003`  
상태: 구현 전 계획

## 0. 목적·범위·제외 범위

- 회원가입에서 성별의 `선택 안 함(NONE)`을 제거하고, 이메일 형식을 서버에서도 확실히 검증한다.
- 프로필 수정 API에서 성별 변경을 차단한다.
- 비밀번호 변경 API에서 현재 비밀번호와 같은 비밀번호를 새 비밀번호로 설정하지 못하게 한다.
- 소장(`OWNED`) 표시 및 소장 처리 로직은 다른 팀원 구현 범위이므로 이번 작업에서 제외한다.
- 프런트 화면·API 호출 코드, 런타임 DB 스키마, 신규 ErrorCode 추가는 이번 작업에서 수정하지 않는다.

| API ID | Method / URL | 이번 변경 |
|---|---|---|
| `API-AUTH-001` | `POST /api/v1/auth/signup` | 성별 필수값·허용값 검증, 잘못된 이메일 검증 회귀 테스트 |
| `API-ME-002` | `PATCH /api/v1/me` | 성별 요청값 거부 및 기존 성별 보존 |
| `API-ME-003` | `PATCH /api/v1/me/password` | 새 비밀번호가 현재 비밀번호와 동일한 경우 거부 |

## 2. 확정 계약

### 2.1 회원가입 성별·이메일

- `gender`는 필수이며 `MALE`, `FEMALE`만 허용한다.
- `NONE`, 빈 문자열, 누락, 그 밖의 문자열은 `400 Bad Request`와 `VALIDATION_ERROR`로 응답한다.
- `email`은 필수이고 완성된 이메일 형식이 아니면 `400 Bad Request`와 `VALIDATION_ERROR`로 응답한다.
- 이메일 중복은 기존과 동일하게 `409 Conflict`, `MEMBER_EMAIL_DUPLICATED`로 응답한다.

### 2.2 프로필 수정 성별 불변

- `PATCH /api/v1/me`의 수정 가능 필드는 `name`, `email`, `phone`만 유지한다.
- 요청 본문에 `gender`가 포함되면 값이 `MALE`, `FEMALE`, `NONE`, 빈 문자열 중 무엇이든 `400 Bad Request`, `VALIDATION_ERROR`로 거부한다.
- 거부된 요청은 이메일·이름·전화번호를 포함해 어떠한 회원정보도 변경하지 않는다.
- 요청 본문에서 성별을 생략한 정상 수정은 기존 `MEMBER.gender` 값을 그대로 유지한다.

### 2.3 동일 비밀번호 변경 차단

- 현재 비밀번호 검증이 성공한 뒤 `newPassword`가 현재 저장된 해시와 일치하면 `400 Bad Request`, `VALIDATION_ERROR`로 거부한다.
- 현재 비밀번호 불일치는 기존 계약대로 `AUTH_INVALID_PASSWORD`를 우선 응답한다.
- 거부된 요청에서는 `password_hash`를 갱신하지 않는다.
- 별도 ErrorCode는 만들지 않는다. 기존 `VALIDATION_ERROR`를 사용한다.

## 3. DB·공통 코드 변경 원칙

- `member` 테이블, `password_hash` 컬럼, 이메일 `UNIQUE` 제약은 변경하지 않는다.
- BCrypt 해시는 동일 평문이라도 매번 달라질 수 있으므로 SQL `CHECK`나 해시 문자열 비교로 동일 비밀번호를 판별하지 않는다.
- 신규 ErrorCode가 없으므로 ErrorCode 승인 요청 문서는 만들지 않는다.
- 기존 회원의 `gender` 값은 데이터 마이그레이션 없이 보존한다.

## 4. 상세 구현 순서

1. **회원가입 요청 검증 보강**
   - `src/main/java/com/acorn/abc/auth/dto/SignupRequest.java`의 `gender`에 필수·허용값 검증을 추가한다.
   - `NONE` 또는 누락 성별이 서비스와 DB까지 도달하지 않음을 컨트롤러 테스트로 확인한다.

2. **프로필 성별 변경 경로 차단**
   - `src/main/java/com/acorn/abc/member/dto/MemberUpdateRequest.java`에서 `gender` 입력을 변경 불가 값으로 검증한다.
   - `src/main/java/com/acorn/abc/member/dto/MemberUpdateRequestValidator.java`에서 성별만 포함된 요청을 유효한 수정 요청으로 보지 않도록 조정한다.
   - `src/main/java/com/acorn/abc/member/service/MemberService.java`에서 성별 해석·갱신 경로를 제거하고, `Member.updateProfile` 호출 시 기존 성별을 유지한다.
   - `src/main/java/com/acorn/abc/member/controller/MeController.java`의 Swagger 설명을 이름·이메일·전화번호 수정으로 정정한다.

3. **동일 비밀번호 변경 차단**
   - `MemberService.changePassword`에서 현재 비밀번호 확인 뒤 `passwordEncoder.matches(request.newPassword(), member.getPasswordHash())`를 검사한다.
   - 일치하면 인코딩·엔티티 변경 전에 `BusinessException(ErrorCode.VALIDATION_ERROR)`를 던진다.

4. **테스트 보강 및 수동 검증 문서 작성**
   - 컨트롤러 테스트에는 요청 검증과 HTTP 응답 계약을, 서비스 테스트에는 엔티티 변경 방지와 인코더 호출 방지를 검증한다.
   - Swagger/Postman 체크리스트와 테스트 데이터 준비·원복 SQL은 `api-test-results/0721 추가 버그 대응`에 유지한다.

## 7. 완료 조건과 범위 제외

### 완료 조건

1. 회원가입에서 완성되지 않은 이메일, 성별 누락, `NONE`이 모두 400으로 차단된다.
2. 프로필 수정 요청의 성별은 변경되지 않으며, 성별 포함 요청은 400으로 거부된다.
3. 현재 비밀번호와 같은 새 비밀번호는 400으로 거부되고 해시가 변경되지 않는다.
4. 관련 자동 테스트와 `./gradlew.bat build`가 통과한다.
5. Swagger/Postman 정상·실패·DB 원복 체크리스트가 작성되고 실행 결과가 기록된다.

### 범위 제외

- 소장(`OWNED`) 상태 생성, 대여 가능 일수 표시, 내 서재·도서 상세 응답 변경
- 프런트 성별 선택 UI 및 에러 메시지 구현
- 실제 API 명세·화면설계 원본 수정
- DB 스키마 변경, 데이터 마이그레이션, 신규 ErrorCode 추가
