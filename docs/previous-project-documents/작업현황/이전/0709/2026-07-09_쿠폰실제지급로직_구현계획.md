## 0. 재조사 결과 — 5차 문서 §5 대비 달라진 점

5차 문서 작성 시점엔 "막고 있는 지점은 `AdminChallengeRewardItemRequest.rewardType`의 `@Pattern(regexp = "POINT")` 한 곳뿐"이라고 정리했는데, 이번에 코드를 다시 직접 읽어보니 **막고 있는 지점이 3곳**이었다(코드가 그 사이 바뀐 게 아니라, 그때 덜 자세히 봤던 것).

| 위치 | 현재 코드 | 문제 |
|---|---|---|
| `AdminChallengeRewardItemRequest.java:9` | `@Pattern(regexp = "POINT", ...)` | `rewardType="coupon"` 자체가 DTO 검증에서 막힘 |
| `ChallengeService.validateRewardItems()` (191~201행) | `... \|\| item.couponId() != null` 이면 무조건 `VALIDATION_ERROR` | `couponId`가 있기만 해도 거부 — coupon 타입을 등록하려면 couponId가 필수인데, 있으면 오히려 막힘(모순) |
| `ChallengeService.updateChallenge()` (184~187행) | `ChallengeReward.create(challenge, item.rewardType(), item.rewardPoint(), null, item.rewardQuantity())` | `coupon` 파라미터 자리에 **`item.couponId()`를 아예 안 쓰고 `null`을 하드코딩** — 위 두 개를 다 풀어도 이 줄까지 고치지 않으면 저장된 `ChallengeReward`의 `coupon`이 항상 `null`이 됨 |

세 곳을 전부 고쳐야 실제로 동작한다.

## 1. 이미 준비돼 있어서 새로 안 만들어도 되는 것 (재확인)

- `ChallengeReward` 엔티티: `coupon`(FK) 필드 이미 있음(`ChallengeReward.java:39-40`), `create()` 팩토리 메서드도 `Coupon coupon` 파라미터를 이미 받음(45~46행) — 위 표의 3번째 문제만 고치면 그대로 씀.
- `MemberCoupon.create(member, coupon)`(`MemberCoupon.java:52-61`): 상태(`ISSUED`)·발급시각·유효기간(`coupon.getValidDays()`)까지 이미 다 처리. 관리자 쿠폰 발급(`CouponService.issueCoupon()`)에서 이미 쓰이는 검증된 코드라 그대로 재사용.
- schema: `challenge_reward.coupon_id` FK, `chk_challenge_reward_reward_type CHECK (reward_type IN ('POINT', 'coupon'))` — 스키마 변경 불필요.
- `ErrorCode.COUPON_NOT_FOUND`(404) 이미 있음 — coupon 존재 확인용으로 재사용, 신규 ErrorCode 불필요.

## 2. 수정 방안

### 2-1. `AdminChallengeRewardItemRequest.java`

```java
@Pattern(regexp = "POINT|coupon", message = "보상 유형은 POINT 또는 coupon만 허용됩니다.")
String rewardType,
```

### 2-2. `ChallengeService.validateRewardItems()` — 타입별로 분기해서 검증

현재는 "무조건 POINT여야 하고 couponId는 없어야 함" 하나의 조건이라, `POINT`/`coupon` 두 갈래로 나눠야 한다.

```java
private void validateRewardItems(List<AdminChallengeRewardItemRequest> rewards) {
    for (AdminChallengeRewardItemRequest item : rewards) {
        if (item == null) {
            throw new BusinessException(ErrorCode.VALIDATION_ERROR);
        }
        if ("POINT".equals(item.rewardType())) {
            if (item.rewardPoint() == null || item.rewardPoint() <= 0 || item.couponId() != null) {
                throw new BusinessException(ErrorCode.VALIDATION_ERROR);
            }
        } else if ("coupon".equals(item.rewardType())) {
            if (item.couponId() == null || item.rewardPoint() != null) {
                throw new BusinessException(ErrorCode.VALIDATION_ERROR);
            }
            if (!couponRepository.existsById(item.couponId())) {
                throw new BusinessException(ErrorCode.COUPON_NOT_FOUND);
            }
        } else {
            throw new BusinessException(ErrorCode.VALIDATION_ERROR);
        }
    }
}
```

- `POINT`와 `coupon`이 서로 반대 조건(포인트 있으면 안 되고, 쿠폰ID 있으면 안 되는 식)으로 섞이지 않게 상호 배타적으로 검증.
- `couponRepository.existsById(...)`로 실존 여부 확인 — 없으면 `COUPON_NOT_FOUND`(404)로 구분해서 응답(단순 `VALIDATION_ERROR`보다 명확).

### 2-3. `ChallengeService.updateChallenge()` — 실제 `Coupon` 엔티티를 조회해서 넘기기

```java
for (AdminChallengeRewardItemRequest item : request.rewards()) {
    Coupon coupon = item.couponId() != null
            ? couponRepository.findById(item.couponId())
                    .orElseThrow(() -> new BusinessException(ErrorCode.COUPON_NOT_FOUND))
            : null;
    challengeRewardRepository.save(ChallengeReward.create(
            challenge, item.rewardType(), item.rewardPoint(), coupon, item.rewardQuantity()));
}
```

`validateRewardItems()`에서 이미 존재 확인을 했지만, 실제 저장에 쓸 엔티티 레퍼런스는 별도로 한 번 더 조회해야 한다(기존 코드 스타일과 동일한 패턴 — 검증과 빌드를 분리).

### 2-4. `ChallengeService.claimReward()` — coupon 타입 실제 지급

```java
Member member = memberRepository.findById(memberId)
        .orElseThrow(() -> new BusinessException(ErrorCode.MEMBER_NOT_FOUND));

int grantedPoint = 0;
List<ChallengeReward> rewards = challengeRewardRepository.findByChallenge_ChallengeId(challengeId);
for (ChallengeReward reward : rewards) {
    if ("POINT".equals(reward.getRewardType()) && reward.getRewardPoint() != null) {
        int amount = reward.getRewardPoint() * reward.getRewardQuantity();
        pointService.grantOrAdjustPoint(memberId, amount, "challenge_reward",
                challenge.getChallengeName() + " 챌린지 보상");
        grantedPoint += amount;
    } else if ("coupon".equals(reward.getRewardType()) && reward.getCoupon() != null) {
        for (int i = 0; i < reward.getRewardQuantity(); i++) {
            memberCouponRepository.save(MemberCoupon.create(member, reward.getCoupon()));
        }
    } else {
        // schema CHECK 제약상 POINT/coupon 외 값은 DB에 못 들어가므로 사실상 도달 불가능한 방어 코드.
        // "안 터지게만 최소 방어"(4차 계획 문서 §1-2와 같은 맥락)로 유지.
        throw new BusinessException(ErrorCode.CHALLENGE_REWARD_TYPE_NOT_SUPPORTED);
    }
}
```

- `Member` 엔티티가 `MemberCoupon.create(member, coupon)`에 필요해서 메서드 시작 부분에 한 번 조회. `memberId`는 이미 호출부에서 검증된 값(인증된 사용자)이라 실무상 `MEMBER_NOT_FOUND`가 발생할 일은 거의 없지만, 다른 메서드들(`updateProgressOnAttendance()` 등)과 동일하게 방어적으로 조회.
- **중요**: `ChallengeServiceTest.claimReward_POINT가_아닌_보상은_fail_fast로_막는다()`(PR #35에서 추가)는 `rewardType="coupon"`이 fail-fast로 막힌다는 걸 검증하는데, 이 작업 이후엔 **coupon이 더 이상 fail-fast 대상이 아니게 되므로 이 테스트가 깨진다.** 아래 §3에서 이 테스트를 어떻게 바꿀지 정리.

### 2-5. `ChallengeRewardClaimResponse` — 응답에 쿠폰 지급 결과 반영 여부

api-spec(`api-spec(final).md:322`)은 `API-CHALLENGE-002` 응답에 "보상 수령 시각, **지급 포인트/쿠폰**"이 포함돼야 한다고 명시한다. 그런데 현재 `ChallengeRewardClaimResponse`는 `rewardClaimedAt`, `grantedPoint`만 있고 쿠폰 지급 결과를 담을 필드가 없다.

- **안 A(최소)**: `int grantedCouponQuantity` 필드 추가 — `grantedPoint`와 대칭되는 단순한 수량 정보.
- **안 B(상세)**: `List<Long> grantedMemberCouponIds` 필드 추가 — 프론트가 "내 쿠폰함"으로 바로 연결할 수 있게 발급된 `MemberCoupon` ID 목록 제공.
- **현재 진행 방향**: 안 A(`grantedCouponQuantity`) 우선. 응답에 "몇 장 지급됐는지"만 추가하고, 발급된 `member_coupon_id` 목록 노출은 이번 범위에서 제외한다.

의존성 주입 필요: `CouponRepository couponRepository`, `MemberCouponRepository memberCouponRepository`를 `ChallengeService`에 신규 필드로 추가(`@RequiredArgsConstructor`라 필드만 추가하면 생성자는 자동 반영).

## 4. Swagger/Postman 필요 여부

이번엔 **필요하다** — 4차/PR #35 때와 다른 점: 이번 변경은 응답 스키마(§2-5)와 실제 DB 부수효과(`MEMBER_COUPON` row 생성)가 새로 생기는 진짜 기능 추가라서, 이전처럼 "동작이 안 바뀌니 단위테스트로 충분"이라는 논리가 적용되지 않는다.

## 5. 결정 사항

1. **§2-5 응답 필드**: 안 A(`grantedCouponQuantity`) 우선 진행. `grantedMemberCouponIds`는 이번 범위에서 제외.
2. **§3의 기존 fail-fast 테스트 처리**: PR #35 테스트 완료 사실은 유지(테스트 자체가 틀렸던 게 아니라, 검증 대상이던 `coupon`이라는 값의 의미가 이번 작업으로 바뀌는 것). 삭제하지 않고 재작성 + 신규 테스트 분리 방식으로 처리한다. 근거: `ChallengeService.claimReward()`의 방어용 `else` 분기에 이미 "schema CHECK 제약상 POINT/coupon 외 값은 DB에 못 들어가므로 사실상 도달 불가능한 방어 코드"라는 주석이 있고, 이는 4차 계획 문서 §1-2에서 확립된 팀 컨벤션("도달 불가능해도 방어 코드는 남기고 mock으로 회귀 검증한다")과 동일한 패턴이라 새로 만드는 방식이 아님.
   - **기존 테스트 재작성**: 메서드명 `claimReward_POINT가_아닌_보상은_fail_fast로_막는다()` → `claimReward_스키마상_존재할_수_없는_보상타입은_방어코드로_막는다()`로 변경. mock `ChallengeReward.getRewardType()` 반환값을 `"coupon"`에서 실제로 등장할 수 없는 임의 값(예: `"UNKNOWN"`)으로 교체. 테스트 안에 "실제로는 DTO `@Pattern` + schema `CHECK`로 도달 불가능하지만, `claimReward()`의 방어 분기 자체를 회귀 검증하기 위한 테스트"라는 주석 추가(향후 제3의 보상 타입이 추가됐는데 `claimReward()` 분기 처리를 빠뜨리는 회귀를 잡기 위함).
   - **신규 테스트 추가**: `claimReward_coupon_보상은_MemberCoupon을_실제로_생성한다()` — `rewardType="coupon"`인 `ChallengeReward`를 mock해서 `claimReward()` 호출 시 `memberCouponRepository.save(...)`가 `rewardQuantity`만큼 호출되는지 검증. 기존 테스트를 뒤집어 재활용하지 않고 별도 테스트로 분리(하나의 테스트가 "이전엔 실패, 이제는 성공"으로 assertion만 바뀌면 git blame/히스토리 추적이 어려워지므로, 각 테스트의 책임을 명확히 분리).
3. **coupon 재고/유효기간 관련 추가 검증 여부**: 이번 범위에서 추가하지 않음. 기존 `CouponService.issueCoupon()`도 쿠폰 `status=ACTIVE`나 별도 재고 검증을 하지 않으므로, 이번 구현도 기존 발급 패턴과 동일하게 `couponId` 존재 여부와 `MemberCoupon.create()`의 유효기간 계산 재사용까지만 검증한다.

## 6. "이것만 하면 100% 완성인가?" — 솔직한 답변

**아니요, 100%라고 단정하긴 어렵습니다.** 정확히는:

- **기능적으로는 이게 마지막으로 알려진 큰 갭입니다.** BaseEntity(별도 진행 확정)를 빼면, 5차 문서에서 파악된 항목(§1 BaseEntity, §2 PR본문, §3 fail-fast, §4 usableForBookId, §5 쿠폰 지급) 중 §2/§4는 이미 "액션 불필요"로 종결됐고 §3은 merge 완료라, 이 §5까지 끝내면 **이번 세션에서 파악된 갭은 다 메워집니다.**
- 다만 **"100%"라고 부르기 조심스러운 이유**:
  1. 이 작업도 완료 후 코드 리뷰를 받을 텐데, 이전 4번의 라운드에서 매번 새로운 지적이 나왔던 걸 보면 6차 리뷰에서 또 뭔가 나올 가능성을 배제할 수 없습니다.
  2. 애초에 "100% 완성"의 기준(구현율 체크 때 말씀드린 기준)이 명세 대비 기능 구현이었는데, 이 프로젝트 전체(다른 팀원 도메인 포함)가 아니라 **본인 담당 범위(챌린지/출석/포인트/쿠폰) 기준**으로는 이걸로 사실상 다 되는 게 맞습니다.

**요약**: "담당 범위 기능 구현" 기준으로는 이게 마지막 조각이 맞지만, 리뷰 라운드가 또 돌아올 가능성까지 고려하면 "100%"보다는 "알려진 갭은 다 처리"라는 표현이 더 정확합니다.
