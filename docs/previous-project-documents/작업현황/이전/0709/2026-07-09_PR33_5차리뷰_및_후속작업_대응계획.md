## 1. MEDIUM — BaseEntity 미상속 (5차 리뷰, 신규 지적)

### 1-1. 리뷰 원문 요약

### 1-3. 왜 단순 치환이 아닌지 (중요 리스크)

`PointHistory.createPaymentUse(Member, Payment, int, LocalDateTime createdAt)`은 `createdAt`을 **외부에서 주입받아** 다른 레코드와 타임스탬프를 공유시키는 용도로 쓰인다(결제 시점 관련 포인트 이력들을 같은 시각으로 묶기 위한 의도로 추정). `BaseEntity`의 `@CreatedDate`는 JPA Auditing이 엔티티 최초 저장 시점에 **자동으로** 채우는 방식이라, 외부에서 값을 주입하는 이 패턴과 충돌한다. 그냥 `extends BaseEntity`로 바꾸고 `createdAt` 필드를 지우면 `createPaymentUse()`의 타임스탬프 공유 불변식이 깨진다.

### 1-4. 수정 방안 (안 A/B, 결정 필요 — §6 참고)

**안 A — 전부 BaseEntity로 전환**
- `Challenge`, `Attendance`: 별다른 특수 로직 없이 `createdAt` 직접 선언만 걷어내면 되므로 비교적 단순.
- `PointHistory`: `createPaymentUse()`의 외부 주입 패턴을 `BaseEntity`와 공존시키기 어려움 → 이 메서드만 별도 설계 필요(예: `updatedAt`을 대신 쓰거나, `BaseEntity`에 `@CreatedDate`를 `updatable=true`로 바꾸는 등 공통 클래스 자체를 건드려야 할 수 있음 — **이 경우 다른 모든 엔티티에 영향**을 주므로 신중해야 함).
- `ChallengeProgress`, `ChallengeReward`: `createdAt` 필드 자체가 없어서 `extends BaseEntity`만 추가하면 새로 `createdAt`/`updatedAt` 컬럼이 생기는데, DB 테이블(`challenge_progress`, `challenge_reward`)에 해당 컬럼이 없으면 `ddl-auto=validate` 기동 실패 위험(이전 세션에서 이미 분석된 리스크, 스키마 변경 필요).

**안 B — 이번 PR 예외 범위로 명시하고 후속 이슈로 분리**
- 리뷰 Fix 제안에 포함된 대안: "바로 수정하지 않는다면 이번 PR의 명시적 예외 범위와 후속 처리 계획을 PR 본문에 남기는 편이 안전". PR #33은 이미 merge됐으니, 이 안을 택하면 **별도 이슈/문서로만 기록**하고 코드는 안 건드림.

### 1-5. 권장

**안 B(후속 이슈로 분리)를 권장.** 이유: `PointHistory` 하나만 해도 `BaseEntity` 공통 클래스 자체를 건드릴 수 있는 리스크가 있고, `ChallengeProgress`/`ChallengeReward`는 스키마 변경(컬럼 추가)까지 필요해서 "리뷰 코멘트 대응"치고는 범위가 너무 커진다. 5개 엔티티 전체를 한 번에 바꾸기보다, **엔티티별로 나눠서 별도 작업으로 진행하는 게 안전**하다고 판단.

## 3. WATCHLIST(신규) — `claimReward()`가 coupon reward를 만나면 silent 처리됨

### 3-1. 리뷰 원문 요약

챌린지 coupon reward는 관리자 등록에서 막고 있지만 schema/ERD는 coupon reward를 허용한다. 수동/기존 데이터로 coupon reward row가 있으면 `claimReward()`가 POINT만 지급하고 claimed 처리할 수 있다는 지적. 후속으로 fail-fast 또는 데이터 가드 정책 필요.

### 3-2. 코드 확인 (기억 기반, 이전 세션에 이미 읽은 부분)

`ChallengeService.claimReward()`(약 87~97행)의 보상 지급 루프:

```java
for (ChallengeReward reward : rewards) {
    if ("POINT".equals(reward.getRewardType()) && reward.getRewardPoint() != null) {
        // ... 포인트 지급 ...
    }
    // TODO: rewardType=coupon 지급 연동은 이번 범위에서 보류
}
```

- `markRewardClaimedIfUnclaimed()`는 이 루프보다 **먼저** 호출돼서 "수령 완료" 상태로 원자적으로 선점한다.
- 즉 `reward.getRewardType()`이 `"coupon"`이면 이 루프에서 아무 것도 안 하고 넘어가는데, **progress는 이미 "수령됨"으로 마킹된 뒤**라 회원 입장에서는 "보상을 받았다고 하는데 아무것도 안 온" 상태가 될 수 있음.
- 정상 경로(관리자 등록 API)로는 `rewardType=coupon`이 DTO 검증에서 막히지만, **DB에 직접 데이터가 들어가거나(수동 SQL, 마이그레이션, 과거 데이터) 검증 우회 경로가 생기면** 이 문제가 실제로 발생할 수 있음.

### 3-2-1. (추가 확인) 애초에 쿠폰 보상은 스펙에 있던 기능

`docs/API 명세/api-spec(final).md` 확인 결과:
- 366행 `API-ADMIN-CHALLENGE-002`: "보상은 `POINT` 또는 `COUPON`과 지급 수량" — 관리자가 COUPON 타입 보상을 등록할 수 있어야 한다고 명시.
- 210행 `API-CHALLENGE-002`(보상 수령) 영향 테이블에 `MEMBER_COUPON` 포함 — 보상 수령 시 실제 쿠폰 지급(= `MEMBER_COUPON` row 생성)이 스펙상 기대되는 동작.

즉 "관리자가 쿠폰 보상을 등록 못 하게 막아둔 것"은 **설계에 없던 게 새로 생긴 게 아니라, 스펙에 있던 기능을 미구현 상태로 막아둔 것**이다(1~2차 리뷰 때 "쿠폰 발급 로직 미구현이라 우선 차단"으로 결정 — 그 결정 자체는 합리적이었으나 근본적으로는 스펙 대비 미완성 상태라는 점을 명확히 해둔다).

### 3-3. 수정 방안 (안전성 확인 완료, 변경 지점 정확히 구분)

**안 A — Fail-fast**: 루프에서 `POINT`가 아닌(`coupon` 등) reward를 만나면 `BusinessException`을 던져서 수령 자체를 막는다.

**변경 지점을 "순수 추가"와 "기존 코드 수정"으로 정확히 구분하면:**

| 변경 | 성격 | 상세 |
|---|---|---|
| `ErrorCode`에 신규 상수 1개 | **순수 추가** | 새 줄 하나 추가, 기존 상수는 안 건드림(예: `CHALLENGE_REWARD_TYPE_NOT_SUPPORTED`) |
| `ChallengeService.claimReward()`의 기존 `if` 블록(116~124행) | **기존 코드 수정** | 현재는 `POINT`가 아니면 그냥 넘어감(TODO 주석만 있음). 이걸 "예외를 던지게" 바꾸려면 기존 `if`에 `else` 분기를 추가해야 함 — 완전히 새 메서드/파일이 아니라 **기존 메서드의 기존 조건문에 else 한 줄을 더하는 수정**. "기존 코드 완전 무수정 + ErrorCode만 추가"로는 불가능함(동작 자체를 바꾸는 거라서).

- **트랜잭션 안전성 확인 완료(더 이상 리스크 아님)**: `ChallengeService`는 클래스 레벨 `@Transactional`이라 `claimReward()` 전체가 하나의 트랜잭션이다. `BusinessException`이 `RuntimeException`을 상속하는 것도 확인했다(`BusinessException.java:19`). 즉 `markRewardClaimedIfUnclaimed()`로 먼저 선점한 뒤 `BusinessException`을 던져도 **트랜잭션 전체가 롤백**되어 선점 자체가 취소된다.
- **전역 영향 검토 완료**: `rg -n "switch\s*\(.*[Ee]rrorCode"`로 전체 코드베이스를 확인한 결과 `ErrorCode`를 `switch`로 분기하는 코드가 없음 — 새 `ErrorCode` enum 상수를 추가해도 기존 코드에 컴파일/런타임 영향 없음. `GlobalExceptionHandler`는 `BusinessException.class`용 핸들러가 이미 있어(`GlobalExceptionHandler.java:26`) **수정할 필요가 없다.**

**안 B — 데이터 가드**: 애초에 `coupon` 타입 reward row가 DB에 존재하지 못하게 막는 게 근본적. 하지만 이건 이미 있는 데이터를 어떻게 처리할지가 별개 문제로 남음.

### 3-4. 권장

**안 A(fail-fast)를 권장.** 영향 범위는 "`ErrorCode` 신규 상수 1개(순수 추가) + `claimReward()` 기존 `if` 블록에 `else` 1줄 추가(기존 코드 최소 수정)"로 정리됨 — 트랜잭션/전역 영향 리스크는 해소 확인, 남은 건 이 정도 수정을 진행할지 여부.

## 5. 구현 갭 — `rewardType=coupon` 실제 지급 로직 미구현 (근본 원인, **보류: 이번 작업 범위 아님**)

§3이 전부 이 갭에서 파생된 문제다. 관리자가 쿠폰 보상을 등록하지 못하게 막아둔 것(1~2차 리뷰에서 이미 결정된 사항)과, `claimReward()`가 coupon 타입을 처리 못하는 것(§3)은 같은 미구현 기능의 양면이다.

**§3-2-1에서 확인했듯, 이건 스펙에 없던 걸 새로 만드는 게 아니라 스펙(api-spec(final).md 210행, 366행)에 있던 기능이 미구현 상태로 남아있는 것이다.**

**결정(수정, 2026-07-08): 이번 작업(§7)에는 포함하지 않는다.** §3 작업이 끝난 뒤, 또는 완전히 별도 세션에서 진행하기로 함. 아래 §5-1/§5-2의 재조사 내용은 **나중에 바로 착수할 수 있도록 참고용으로 남겨둔다** — 실제 구현 시점이 오면 이 섹션부터 다시 읽으면 됨.

### 5-1. 재조사 결과 — 예상보다 범위가 작음(스키마 변경 불필요)

처음엔 "쿠폰 발급 API 연동, 재고/유효기간 처리 등"으로 범위를 크게 예상했으나, 코드를 직접 확인한 결과 필요한 조각 대부분이 이미 존재한다:

- `ChallengeReward` 엔티티에 이미 `coupon` 필드(FK, `ChallengeReward.java:39-40`)가 있음 — 데이터 모델은 이미 준비됨.
- `AdminChallengeRewardItemRequest` DTO에도 이미 `couponId` 필드(15행)가 있음 — 애초에 쿠폰 보상을 염두에 두고 설계됨.
- 회원에게 쿠폰을 발급하는 로직(`MemberCoupon.create(member, coupon)`, `MemberCoupon.java:52-61`)이 이미 관리자 쿠폰 발급(`CouponService.issueCoupon()`)에서 쓰이고 있고, **유효기간(`coupon.getValidDays()`)까지 이미 처리됨** — 새로 설계할 필요 없이 그대로 재사용 가능.
- 실제로 막고 있는 지점은 `AdminChallengeRewardItemRequest.rewardType`의 `@Pattern(regexp = "POINT")` 한 곳뿐(9행) — schema의 `chk_challenge_reward_reward_type CHECK (reward_type IN ('POINT', 'coupon'))`(`schema.sql:452`)는 이미 `coupon`을 허용하고 있어서 스키마 변경도 불필요.

### 5-2. 실제 구현 시 손대야 할 지점

1. **`AdminChallengeRewardItemRequest.java`**: `@Pattern` 값을 `"POINT|coupon"`으로 완화. `rewardType=coupon`일 때 `couponId`가 필수가 되도록 조건부 검증 추가 필요(Bean Validation 단독으로는 어려워서 커스텀 검증 애노테이션 또는 서비스단 체크 중 택1 — 구현 시 결정).
2. **`ChallengeService.updateChallenge()` / `validateRewardItems()`**: `rewardType=coupon`일 때 `couponId`가 실제 존재하는 쿠폰인지 확인(`couponRepository.findById(...)` + 기존 `ErrorCode.COUPON_NOT_FOUND` 재사용 — 새 ErrorCode 불필요).
3. **`ChallengeService.claimReward()`**: coupon 타입 reward를 만나면 `rewardQuantity`만큼 `memberCouponRepository.save(MemberCoupon.create(member, reward.getCoupon()))` 반복 호출(관리자 쿠폰 발급과 동일 패턴 재사용).
4. **테스트**: `AdminChallengeRewardItemRequestTest`(coupon 등록 성공/couponId 누락 실패), `ChallengeServiceTest`(coupon 등록 검증 + claimReward 시 실제 `MemberCoupon` 생성 확인).

### 5-3. §3(fail-fast)과의 관계 (나중에 §5 착수 시 반드시 참고)

이 기능이 나중에 구현되면 §3의 fail-fast 대상은 "`POINT`도 `coupon`도 아닌 미지의 타입"으로 좁아진다(현재 schema CHECK 제약상 이 두 값만 가능하므로 사실상 도달 불가능한 방어 코드가 되지만, "안 터지게만 최소 방어"라는 이전 결정(§1-2, 4차 계획 문서 참고)과 같은 맥락에서 유지 권장). **§5를 나중에 시작할 때는 §3의 fail-fast 조건문(`"coupon".equals(...)` 등)을 "그 외 전부"로 조정해야 한다는 걸 잊지 말 것** — §3이 먼저 merge되고 §5가 한참 뒤에 진행되므로, §5 착수 시점에 이 조정을 빠뜨리기 쉬움.
