## 1. 확정 사항

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| DB 적용 방식 | `schema.sql`과 `application.properties`의 자동 초기화 목록은 변경하지 않는다. DB 구조 변경은 별도 sidecar SQL로 만들고, 대상 DB에 순서대로 수동 적용한다. | 서버 기동 때마다 모든 변경 SQL이 실행되어 개발자 DB가 예고 없이 바뀌는 것을 막는다. |
| 공유 DB/RDS 적용 | 팀 공유 DB와 이후 RDS에는 애플리케이션 기동 전에 누적 sidecar SQL을 한 번 적용하고 `information_schema`로 결과를 확인한다. | 현재 `ddl-auto=validate`이므로 엔티티가 요구하는 컬럼·제약이 없으면 기동할 수 없다. 공유 DB에 적용을 끝냈다면 해당 DB를 사용하는 실행 환경은 정상 동작한다. |
| 신규 DB 준비 | 새 개발자 DB·새 테스트 DB·새 RDS는 `schema.sql`/`data.sql`만으로 끝내지 않고, 별도 변경 SQL을 생성 순서대로 적용한다. | 기준 스키마 보존 정책에서는 신규 컬럼과 제약이 sidecar SQL에만 존재하기 때문이다. |
| 포인트 조정 대상 | `ADMIN`, `WITHDRAWN`, `DEACTIVATED` 회원의 포인트 조정을 모두 거부한다. | 상태·제재 변경 API의 보호 기준과 맞추고, 종료·비활성 계정의 잔액 변경을 막는다. |
| 계정 정지 만료 | 이번 범위에서는 스케줄러를 구현하지 않는다. 관리자가 상태 변경 API에서 `status=JOINED`, 사유 입력, `sanctionType` 생략으로 수동 복구한다. | 현재 과제에서는 자동 시각 복구보다 관리자 재량의 수동 복구가 충분하며, 기존 상태 변경·감사 로그 흐름을 그대로 사용한다. |
| 포인트 멱등 재응답 | 같은 `(memberId, requestId)` 재시도는 최초 조정 직후의 `pointBalance`를 반환하도록 보완한다. | 이후 다른 포인트 변경이 발생했을 때 현재 잔액을 반환하면 최초 성공 응답과 달라져 재시도 응답 계약이 흔들린다. |
| API 명세 | `API-ADMIN-MEMBER-004` 요청 본문에 UUID `requestId`를 필수로 명시한다. | 구현의 멱등 키를 제거하지 않고 명세를 구현 계약에 맞춘다. |

## 2. 코드리뷰 반영 구현 계획

### 2.1 DB sidecar 적용 절차 보완

1. 기존 `src/main/resources/관리자회원_계정정지연결및포인트멱등키.sql`은 `member.current_sanction_id`, FK, `point_history.request_id`, `(member_id, request_id)` UNIQUE를 적용하는 수동 SQL로 유지한다.
2. 멱등 재응답의 잔액 스냅샷은 기존 SQL을 수정하지 않고, 새 sidecar SQL `src/main/resources/관리자회원_포인트멱등응답스냅샷.sql`로 분리한다.
3. 새 SQL은 `point_history.balance_after INT NULL`을 추가한다. 기존 이력은 `NULL`로 유지하고, 신규 `ADMIN_ADJUST` 이력만 서비스에서 값 저장을 강제한다.
4. 각 SQL은 현재 DB·대상 테이블·컬럼/제약 존재 여부를 확인한 뒤 적용하며, 적용 후 `information_schema.columns`, `information_schema.table_constraints` 조회 결과를 남긴다.
5. `spring.sql.init.schema-locations`에 sidecar 파일을 추가하지 않는다. `spring.sql.init.continue-on-error=true`가 DDL 오류를 가릴 수 있으므로, SQL 실행 성공 여부를 애플리케이션 기동 여부만으로 판단하지 않는다.

### 2.2 관리자 포인트 조정 보호 및 멱등 응답

1. `AdminPointAdjustExecutor`의 `member.isAdmin()` 단독 검사를 `member.isProtectedFromAdminChanges()`로 교체한다.
2. 새 포인트 조정은 회원 행 잠금 후 보호 대상 검사, 음수 잔액 검사, 포인트 이력 생성, 감사 로그 기록을 하나의 transaction으로 유지한다.
3. `PointHistory`에 `balanceAfter` 필드를 추가하고, `createAdminAdjust`에서 조정 직후 잔액을 저장한다.
4. 신규 성공과 같은 `requestId` 재시도 모두 `PointHistory.balanceAfter`로 `AdminPointAdjustResponse.pointBalance`를 만든다.
5. 같은 키에 금액 또는 공백 정규화 후 사유가 다르면 기존처럼 멱등 키 충돌 오류를 반환한다.

### 2.3 API 계약·조회 품질 보완

1. `API-ADMIN-MEMBER-004` 명세와 Swagger에 `pointAmount`, `description`, UUID `requestId`를 모두 필수 요청값으로 적는다.
2. `API-ADMIN-MEMBER-002`의 탭별 응답은 `ApiResponse<?>`/`Object` 노출을 제거하고, 탭별 Response DTO 또는 명시된 oneOf 응답 스키마로 Swagger 계약을 보강한다.
3. `REPORTS` 탭은 책 신고·리뷰 신고 전체 목록을 메모리에서 합쳐 정렬·페이징하지 않고, DB 수준 정렬·페이지 조회가 가능한 조회 방식으로 변경한다. 두 테이블을 통합 조회할 수 없는 경우에도 전체 건수를 제한 없이 적재하지 않는 별도 페이지 조회 전략을 사용한다.

### 2.4 계정 정지 만료 처리 범위

- `AccountSuspensionExpiryBatchService`의 만료 후보 복구 서비스는 재사용 가능한 도메인 로직으로 유지한다.
- `@EnableScheduling`, `@Scheduled`, cron/fixed-rate 설정, 운영 배치 모니터링은 이번 PR 범위에서 제외한다.
- 수동 복구는 `PATCH /api/v1/admin/members/{memberId}/status`에서 `status=JOINED`, `reason`을 사용하고 `sanctionType`을 보내지 않는 기존 흐름으로 수행한다. 이 경우 이전 `currentSanctionId`는 해제되고 감사 로그가 남아야 한다.

## 3. 구현 순서

1. 설계 변경 예정 문서와 초경량 이해 메모를 기준으로 API·DB 계약을 고정한다.
2. 기존 계정 정지/멱등 키 sidecar SQL의 적용 전·후 확인 절차를 검토하고, 잔액 스냅샷용 새 sidecar SQL을 별도로 작성한다.
3. `PointHistory`/관리자 포인트 조정 서비스·응답 DTO를 스냅샷 계약에 맞게 수정한다.
4. 포인트 조정 보호 대상을 `ADMIN`, `WITHDRAWN`, `DEACTIVATED`로 통일한다.
5. 002 탭 Swagger 응답 타입과 REPORTS 조회·페이징을 보완한다.
6. API 명세 원문, Swagger/Postman 체크리스트, DB 준비·검증·원복 SQL을 작성한다.
7. 단위/통합 테스트, 실제 MySQL 적용 확인, Swagger/Postman 수동 테스트를 차례로 수행한다.

## 4. 검증 계획

| 구분 | 확인 항목 | 기대 결과 |
|---|---|---|
| DB 사전조건 | 기존 sidecar와 잔액 스냅샷 sidecar를 순서대로 적용 | 컬럼·FK·UNIQUE가 존재하고 SQL 재실행 시 중복 오류 없이 확인 단계로 끝난다. |
| 서버 기동 | DB 변경 SQL 적용 후 `ddl-auto=validate` 기동 | 엔티티-테이블 불일치 없이 기동한다. |
| 포인트 보호 | ADMIN, WITHDRAWN, DEACTIVATED 대상의 004 호출 | 모두 거부되고 잔액·이력·감사 로그가 변하지 않는다. |
| 멱등 재시도 | 동일 `memberId + requestId + payload`를 재호출하고, 중간에 별도 포인트 변동도 발생시킴 | 이력과 감사 로그는 한 번만 생성되며, 재시도 응답은 최초 조정 직후 `balanceAfter`를 반환한다. |
| 멱등 충돌 | 동일 키에 금액 또는 정규화 사유를 달리해 호출 | 멱등 키 충돌 오류를 반환하고 DB 변경이 없다. |
| 수동 복구 | SANCTIONED 회원을 003으로 JOINED 전환 | `currentSanctionId`가 해제되고 상태 변경 감사 로그가 남는다. |
| 조회 | 002 각 탭과 REPORTS 대량 데이터 | Swagger 응답 스키마가 구체적이며 전체 목록 메모리 적재 없이 정렬·페이지 계약을 지킨다. |

## 6. 완료 조건과 범위 제외

### 완료 조건

1. 공유 DB 또는 RDS 적용 전 필요한 sidecar SQL과 검증 순서가 문서화되고 실제 적용 결과가 확인된다.
2. 004가 보호 대상의 잔액·이력·감사 로그를 변경하지 않는다.
3. 동일 멱등 키 재시도 응답이 최초 성공의 `balanceAfter`를 재현한다.
4. 002 Swagger 응답 계약과 REPORTS 페이지 조회가 대량 데이터에서도 유지된다.
5. 상태 003의 수동 JOINED 복구가 감사 로그까지 포함해 검증된다.

### 범위 제외

- `schema.sql` 원본 병합 및 `application.properties`의 자동 SQL 실행 목록 변경
- 계정 정지 만료 자동 복구 스케줄러, 다중 인스턴스 분산 잠금, 운영 배치 모니터링
- 일반 포인트 지급·사용 도메인의 정책 변경
- 실제 설계 원문·API 명세 원문·테스트 산출물의 이번 문서 작성 단계 수정
