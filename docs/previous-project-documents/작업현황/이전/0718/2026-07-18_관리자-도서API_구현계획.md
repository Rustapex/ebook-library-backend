# 2026-07-18 관리자 도서 API 구현 계획

## 0. 목적과 범위

- 관리자 도서 API `API-ADMIN-BOOK-001`~`004`, 총 4개 endpoint만 백엔드로 구현한다.
- 이 문서는 구현 전 계약 정리, 구현 순서, 테스트와 후속 산출물 작성 기준을 정한다. 현재 생성하는 파일은 이 계획 문서 1개뿐이다.
- 프런트엔드 코드, 관리자 도서관·지도 API, 외부 연동 키 발급·보관·설정, 관리자 카테고리 API는 범위에서 제외한다.
- 신규 `API-ADMIN-BOOK-005`는 만들지 않는다. A-006 수정 화면의 최초 데이터 확보는 프런트가 보유한 목록/화면 상태를 이용하는 범위로 두며, 백엔드는 상세 조회 endpoint나 목록 응답의 임의 확장을 추가하지 않는다.

> **정정(2026-07-20, PR #52 코드리뷰 대응계획)**: 위 "005 미추가" 방침은 PR #52 리뷰에서 A-006 초기 데이터 확보 계약 부재가 지적되어 뒤집혔다. `API-ADMIN-BOOK-005`(관리자 도서 상세 조회, `GET /api/v1/admin/books/{bookId}`)를 추가했다. 상세 내용은 `docs/작업현황/2026-07-20_PR52_관리자-도서API_코드리뷰_대응계획.md` §2.1 참고. 이 문서의 이후 절(§0/§2.1 확정 API 계약 표/§7 완료 조건)은 "001~004만"이라는 원래 범위 기준으로 읽되, 실제 구현 범위는 대응계획 기준이 최신이다.

## 1. 기준과 선행 문서 정리

### 1.1 확인 기준

| 우선순위 | 기준 | 적용 내용 |
|---:|---|---|
| 1 | `src/main/resources/schema.sql` | `publisher`, `author`, `category`, `book`, `book_detail`, `book_page`, 매핑 테이블과 실제 제약조건 |
| 2 | `docs/API 명세/api-spec(final).md` | `API-ADMIN-BOOK-001`~`004`의 URL, HTTP Method, 인증, 상태코드 |
| 3 | `docs/작업현황/0715/2026-07-15_API-ID별_백엔드구현_프론트연결_현황.md` | 관리자 도서 001~004와 관리자 카테고리 001~002의 분리된 범위 |

### 1.2 구현 전 반드시 갱신할 계약 문서

현재 API 명세의 등록 요청에는 `keywords[]`, `file`, `pages[]`, 상태값이 남아 있다. 구현 전에 아래를 설계 문서와 기준 API 명세에 반영한다.

- 등록·수정 요청과 응답에서 `keywords[]`, `file`, `pages[]`를 제거한다.
- `BookPage`와 페이지 원문은 이 API가 생성·수정·삭제·반환하지 않는다고 명시한다.
- `detail`은 `description`, `tableOfContents`, `publisherReview` 같은 안내성 정보만 허용한다. `detailContent` 및 실제 열람용 원문은 허용하지 않는다.
- 등록 요청에서 `status`를 받지 않으며, 신규 도서는 항상 `INACTIVE`로 생성한다.
- `AVAILABLE` 전환은 `API-ADMIN-BOOK-004`만 사용한다. 이번 팀 프로젝트에서는 별도 콘텐츠 완료 표식을 DB에 추가하지 않고, 시연·테스트용 콘텐츠가 준비된 경우에 관리자 수동 판단으로 전환한다.
- `API-ADMIN-BOOK-005`는 API 명세나 설계 문서에 추가하지 않는다.

## 2. 확정 API 계약

| API ID | Method / URL | 구현 계약 |
|---|---|---|
| `API-ADMIN-BOOK-001` | `GET /api/v1/admin/books` | `q`, `categoryId`, `rentalType`, `status`, `page`, `size`로 관리자 목록을 조회한다. `HIDDEN`, `INACTIVE`도 조회한다. page는 0-based이며 정렬은 `createdAt DESC, bookId DESC`이다. |
| `API-ADMIN-BOOK-002` | `POST /api/v1/admin/books` | 도서 메타정보, 출판사·작가명, 기존 활성 카테고리, 대여 정보, 표지 URL, 안내성 상세 정보만 등록한다. 성공 응답 상태는 항상 `INACTIVE`이다. |
| `API-ADMIN-BOOK-003` | `PUT /api/v1/admin/books/{bookId}` | 등록 API와 같은 허용 메타정보만 전체 교체한다. 실제 열람 원문, 페이지, 키워드, 파일은 어떤 경우에도 건드리지 않는다. |
| `API-ADMIN-BOOK-004` | `PATCH /api/v1/admin/books/{bookId}/status` | `AVAILABLE`, `HIDDEN`, `INACTIVE`로 상태만 변경하고 삭제하지 않는다. 사유는 감사 로그에 남긴다. |

### 2.1 수정 가능한 데이터와 보호 데이터

- 허용: 제목, ISBN, 출판사, 작가, 기존 활성 카테고리 연결, 대여 유형·가격·기간, 표지 URL, 안내성 상세 정보, 상태.
- 보호: `BookPage.pageContent`를 포함한 실제 도서 원문, `pages[]`, 키워드·키워드 매핑, 파일 업로드/다운로드, 누적 대여·평점·리뷰 집계값.
- 기존 `BookPage`·키워드 데이터와 공개 도서 API의 동작은 변경하지 않는다.
- 관리자 카테고리 CRUD·상태·트리·순서 API는 만들지 않는다. 도서 API는 기존 `ACTIVE` 카테고리 ID의 존재 검증과 매핑만 수행한다.

## 3. 비즈니스 및 저장 규칙

### 3.1 입력 검증

- 제목·출판사명·작가명은 trim과 공백 정규화 후 빈 값이면 거부한다.
- 작가명과 `categoryIds`의 중복을 거부한다. 카테고리는 존재하며 `ACTIVE`여야 한다.
- ISBN은 기존 `uk_book_isbn` 기준으로 중복을 거부하고 `BOOK_ISBN_ALREADY_EXISTS(409)`를 사용한다.
- `FREE`는 가격 0원, `PAID`는 가격 1원 이상을 강제한다. 문자열 길이와 컬렉션 최대 개수는 구현 전에 `schema.sql`의 저장 가능 범위와 맞춰 DTO Validation 값으로 확정한다.

### 3.2 출판사·작가 처리

- 출판사·작가 master는 이미 저장된 기준 행을 뜻한다. 예를 들어 기존의 “민음사”, “홍길동” 행이 이에 해당한다.
- 이번 팀 프로젝트에서는 관리자 동시 등록이 발생하지 않는다고 가정한다. 이름을 정규화해 먼저 조회하고, 없을 때만 새 행을 만들어 도서에 연결한다.
- 기존 master의 이름·상태·생성 시각 등은 수정하지 않는다. 동시 등록용 DB upsert, 재시도, 별도 잠금 정책은 이번 범위에 넣지 않는다.

### 3.3 목록 조회와 수정 transaction

- 목록은 작가·카테고리 조건으로 한 도서가 중복 행이 되지 않도록, 동일 predicate로 `bookId` 페이지와 `count(distinct book.id)`를 먼저 구한다. 이후 연관 데이터를 bulk 조회하고 최초 ID 페이지 순서대로 재조립한다. collection fetch join으로 페이지를 만들지 않는다.
- 등록은 입력·참조 검증 → master 조회/필요 시 생성 → book·detail·author/category 매핑 저장 → 감사 로그 저장 순서의 하나의 transaction으로 처리한다.
- 수정은 입력·참조 검증 → 도서 write lock → 허용 scalar/detail 갱신 → 기존 author/category 매핑 삭제 → 필요한 flush → 새 매핑 저장 → 감사 로그 저장 순서로 처리한다.
- 같은 도서의 동시 수정은 pessimistic write lock으로 보호한다. 잠금 대기는 transaction-bound 동일 JDBC connection에서만 5초로 설정하고, 기존 값을 읽어 `try/finally`로 commit·rollback·예외 모두에서 복원한 뒤 pool에 반환한다. facade는 예외 변환만 하며 session 값을 바꾸지 않는다.

  > **정정(2026-07-20, PR #52 코드리뷰 대응계획 §2.3)**: 위 5초 session timeout 설정/복원 로직(`BookLockTimeoutSupport`)은 PR #52 리뷰에서 "복원 실패 시 JDBC connection의 session 값이 pool에 남을 위험"이 지적되어 제거했다. `findByIdForUpdate`(PESSIMISTIC_WRITE) 행 잠금 자체는 유지하되, 잠금 대기 시간은 DB 기본 `innodb_lock_wait_timeout`을 그대로 쓴다.
- MySQL lock timeout/deadlock만 `CONCURRENT_UPDATE(409)`로 변환하고 자동 재시도하지 않는다. ISBN 외 제약 오류를 ISBN 또는 동시수정 오류로 바꾸지 않는다.

### 3.4 감사 로그와 rollback

- 등록은 `BOOK_CREATE`, 수정·상태 변경은 기존 `BOOK_UPDATE`와 target `BOOK`을 사용한다. 공통 enum이나 기존 감사 규칙은 수정하지 않는다.
- 본문 변경과 성공 감사 로그는 같은 transaction이다. 감사 writer 예외는 잡아 무시하지 않고 전파하는 fail-closed 정책으로, 본문도 함께 rollback한다. 조회 API는 감사 writer를 호출하지 않는다.
- 등록 실패 시 새 도서·상세·매핑·감사 로그와 이번 요청에서 새로 만든 master가 남지 않아야 한다.
- 수정·상태 변경 실패 시 허용 메타정보, 상세, author/category 매핑, 상태, 감사 로그가 요청 전과 완전히 같아야 한다. 페이지·키워드 데이터도 변함없어야 한다.

## 4. 구현 구조와 공통 코드 보호

- `admin.book` 영역에 Controller, request/response DTO, Service, validator, 관리자 전용 조회 Repository를 새로 추가한다.
- 기존 공개 도서 조회의 `AVAILABLE` 조건, `BookApprovalService`, 키워드·페이지 Repository와 로직은 수정하거나 재사용 대상으로 끌어들이지 않는다.
- 필요한 도메인 메서드는 `Book`, `BookDetail`, `BookAuthor`, `BookCategory`의 허용 메타정보 변경에 한정한다. `BookPage`, 키워드, 공통 `ApiResponse`·`PageResponse`·보안 코드는 변경하지 않는다.
- `CONCURRENT_UPDATE`가 아직 없다면 기존 ErrorCode를 수정하지 않고 additive 상수로만 추가하고, 사유·영향·코드 목록은 `docs/작업현황/ErrorCode_신규추가_완료.md`에 기록한다.

## 5. 테스트 계획

### 5.1 자동 테스트

- 단위 테스트는 DB에 연결하지 않는다. mock/fake로 validation, 상태 전환, transaction 경계의 호출 규칙을 검증한다.
- Repository·통합 테스트는 개발자 개인 로컬 DB의 기존 데이터·ID를 절대 사용하지 않는다. `src/main/resources/schema.sql`과 `src/main/resources/data.sql`만 반영된 독립 테스트 DB를 전제로, 다른 백엔드 개발자도 같은 결과를 얻어야 한다.
- Controller/보안 테스트: 관리자 성공, 비관리자 403, 미인증 401, 잘못된 query/body, 존재하지 않는 도서·카테고리, ISBN 중복을 검증한다.
- 목록 테스트: 복수 작가·카테고리 조건에서도 중복 root·틀린 total·순서 흔들림이 없음을 검증한다.
- 저장 테스트: 신규 도서는 항상 `INACTIVE`, 키워드·페이지 요청 필드가 없고 기존 `BookPage`·키워드가 변경되지 않음, `ACTIVE` 카테고리만 연결됨을 검증한다.
- rollback 테스트: child 저장 실패 및 마지막 감사 로그 저장 실패 때 등록은 신규 데이터가 없고, 수정은 이전 aggregate가 완전히 복구됨을 검증한다.
- 동시 수정 테스트는 sleep 대신 latch/barrier로 첫 transaction이 lock을 획득한 후 두 번째 요청을 시작해 409을 확인한다. 관리자 동시 등록/master 생성 동시성은 범위에서 제외한다.

## 7. 구현 순서와 완료 조건

1. 설계 문서와 API 명세에서 001~004 계약을 확정하고, 기존 명세의 키워드·파일·페이지·등록 상태 항목을 정정한다.
2. 관리자 전용 DTO·validation·조회 Repository와 목록 2단계 pagination을 구현한다.
3. 등록 API를 `INACTIVE` 생성과 허용 메타정보 저장만으로 구현하고 감사 로그를 연결한다.
4. 수정 API를 author/category 전체 교체와 원문·키워드 보호 규칙으로 구현한다.
5. 상태 변경 API와 동시 수정 lock/409 변환을 구현한다.
6. 단위·통합·보안 테스트를 작성하고, 독립 테스트 DB에서 검증한다.
7. Swagger 체크리스트와 테스트 SQL을 위 경로에 작성하고 생성 데이터 정리까지 확인한다.

완료 조건은 다음과 같다.

- 001~004만 구현되며 `005`, 관리자 카테고리, 도서관/지도/외부 키 관련 코드가 추가되지 않는다.

  > **정정(2026-07-20, PR #52 코드리뷰 대응계획)**: `005`는 위 §0 정정과 동일하게 추가됐다. 관리자 카테고리, 도서관/지도/외부 키는 이번 대응 범위에서도 그대로 제외된다.
- 새 도서는 항상 `INACTIVE`이고, 허용 메타정보 외의 페이지 원문·키워드·파일·집계값이 변경되지 않는다.
- API 명세와 설계 문서의 요청/응답 계약이 구현과 일치한다.
- 자동 테스트가 개인 로컬 DB 데이터에 의존하지 않고, 수동 검증 자료가 준비부터 Swagger 요청·검증·정리까지 독립적으로 실행 가능하다.

## 8. 권장 브랜치명

```text
feature/admin-book-api
```

문서 작성만으로는 브랜치를 생성하거나 전환하지 않는다.
