## 0. 결정 사항 기록

**결정: 테스트 DB 전략 — A안(현행 유지) 채택**

- 3차 리뷰(HIGH)에서 "테스트가 실DB에 의존해 재현성/안전성이 약하다"고 지적받았고, H2 복원 또는 Testcontainers 도입을 대안으로 제시받음.
- 채택한 결론: **현행 유지(로컬 `ABC` MySQL을 테스트에도 그대로 사용)**.
- 이유: 지금은 개발 초기 단계이고 협업이 더 진행되면 공통 DB로 전환할 계획이 있어, 그 전환 시점에 테스트 DB 전략도 같이 정리할 예정. 지금 단계에서 Testcontainers 등을 도입하는 건 과함.
- 후속 조치: 공통 DB 전환 시점에 테스트 DB 격리 전략(Testcontainers 또는 전용 test profile)을 재검토한다.

## 1. 사전 준비

### 1-1. 앱 실행

```powershell
.\gradlew.bat bootRun --console=plain
```
Swagger UI: `http://localhost:8080/swagger-ui/index.html`

### 1-2. 테스트 회원 확보 + JWT 발급

1. Swagger `Auth` 태그 → `POST /api/v1/auth/signup`으로 신규 회원 생성 (또는 기존 계정 사용).
2. `POST /api/v1/auth/login` → 응답의 `accessToken` 확보.
3. Swagger 우측 상단 `Authorize` → `Bearer {accessToken}` 입력.
4. `memberId` 확인 (로그인 응답 또는 회원 조회 API로).
5. **비교용으로 회원 계정 2개 준비** (본인 계정 A, 타인 접근 차단 테스트용 계정 B). 각각 로그인해서 토큰 2개를 따로 보관.

### 1-3. 테스트 데이터 준비 (Workbench)

기존 도서/페이지 확인:
```sql
SELECT book_id, total_pages FROM book LIMIT 5;
SELECT book_id, page_no FROM book_page WHERE book_id = <book_id> ORDER BY page_no;
```
`<book_id>`는 `book_page`가 최소 2페이지 이상 있는 걸 고른다 (마지막 페이지 완독 테스트 때문).

아래 표대로 `book_rental`을 시드한다 (전부 회원 A 소유, `<memberId_A>`/`<bookId>`는 위에서 확인한 값으로 치환):

| 시드 ID | rental_status | rental_end_at | 용도 |
|---|---|---|---|
| R1 | `READY` | `DATE_ADD(NOW(), INTERVAL 7 DAY)` | 정상 케이스(만료 전) |
| R2 | `READY` | `DATE_SUB(NOW(), INTERVAL 1 DAY)` | 만료 케이스 |
| R3 | `OWNED` | `DATE_SUB(NOW(), INTERVAL 30 DAY)` | OWNED는 만료 무시 확인 |

```sql
INSERT INTO book_rental (member_id, book_id, rental_end_at, rental_status, created_at)
VALUES (<memberId_A>, <bookId>, DATE_ADD(NOW(), INTERVAL 7 DAY), 'READY', NOW());
-- SELECT LAST_INSERT_ID(); 결과를 R1로 기록

INSERT INTO book_rental (member_id, book_id, rental_end_at, rental_status, created_at)
VALUES (<memberId_A>, <bookId>, DATE_SUB(NOW(), INTERVAL 1 DAY), 'READY', NOW());
-- R2로 기록

INSERT INTO book_rental (member_id, book_id, rental_end_at, rental_status, created_at)
VALUES (<memberId_A>, <bookId>, DATE_SUB(NOW(), INTERVAL 30 DAY), 'OWNED', NOW());
-- R3로 기록
```

## 2. API별 시나리오 (Swagger)

응답 포맷은 공통 규칙 문서 기준 `{success, code, message, data}`이며, 아래 표의 "응답"은 `data` 필드와 최상위 `code`만 표기한다.

### API-VIEWER-001 — `GET /api/v1/rentals/{rentalId}/pages/{pageNo}` (뷰어 페이지 조회)

| # | 시나리오 | 요청 | 인증 | 기대 응답 |
|---|---|---|---|---|
| 1 | 정상 조회 | `GET /api/v1/rentals/{R1}/pages/1` | 회원 A | `200`, `code: OK`, `data: {title, pageContent, totalPages, progressRate, bookmarkYn}` |
| 2 | 최초 진입 시 상태 전환 | 시나리오 1 실행 직후 DB 확인 | - | `book_rental.rental_status`가 `READY`→`READING`, `rental_start_at`에 값 채워짐 (`SELECT rental_status, rental_start_at FROM book_rental WHERE rental_id={R1}`) |
| 3 | 재진입 시 진행상태 갱신 (MEDIUM #2 이슈 확인) | 다른 `pageNo`(예: 2)로 다시 GET 호출 후 DB 확인 | 회원 A | `reading_progress.current_page`가 방금 조회한 페이지 번호로, `last_read_at`이 갱신됨 (`SELECT current_page, last_read_at FROM reading_progress WHERE rental_id={R1}`) — GET만으로 상태가 바뀌는 게 의도된 설계인지 재확인하는 케이스 |
| 4 | 만료 대여 접근 차단 | `GET /api/v1/rentals/{R2}/pages/1` | 회원 A | `403`, `code: RENTAL_EXPIRED` |
| 5 | OWNED는 만료 무시 (제일 중요) | `GET /api/v1/rentals/{R3}/pages/1` | 회원 A | `200` (403 나오면 버그) |
| 6 | 타 회원 접근 차단 | `GET /api/v1/rentals/{R1}/pages/1` | 회원 B | `403`, `code: AUTH_ACCESS_DENIED` |
| 7 | 존재하지 않는 rentalId | `GET /api/v1/rentals/999999/pages/1` | 회원 A | `404`, `code: RENTAL_NOT_FOUND` |
| 8 | 존재하지 않는 페이지 | `GET /api/v1/rentals/{R1}/pages/9999` | 회원 A | `404`, `code: BOOK_PAGE_NOT_FOUND` |
| 9 | 북마크된 페이지 조회 시 플래그 | 3번 API로 먼저 북마크 추가 후 같은 페이지 조회 | 회원 A | `data.bookmarkYn: true` |

## 3. Postman 시나리오 (동시 요청 등 Swagger로 어려운 것)

Swagger는 순차 실행만 가능해서, 아래는 Postman이 필요한 케이스다. 나머지 단건 요청은 위 2장 표와 동일하게 Postman으로도 그대로 재현 가능하다(Header에 `Authorization: Bearer {token}` 추가).

### 3-1. Postman 기본 설정

1. Collection 생성 (예: `ABC-PR22-검증`)
2. Collection 변수로 `baseUrl = http://localhost:8080`, `tokenA`, `tokenB`, `rentalR1`, `rentalR2`, `rentalR3` 등록 (1장에서 확보한 값)
3. 각 요청의 Header에 `Authorization: Bearer {{tokenA}}` (또는 `tokenB`) 형태로 변수 사용

### 3-2. 동시 중복 북마크 요청 (API-VIEWER-003 #6)

1. `POST {{baseUrl}}/api/v1/rentals/{{rentalR1}}/bookmarks`, Body `{"pageNo": 5}` (아직 북마크 안 한 페이지) 요청 저장
2. 이 요청 하나만 담은 Collection 또는 Folder를 Runner에 등록
3. Runner에서 **Iterations: 2, Delay: 0ms**로 실행
4. 결과 확인: `Run Results`에서 2개 응답 중 하나는 `201`, 하나는 `409`(`code: BOOKMARK_ALREADY_EXISTS`)여야 함
   - 둘 다 `201`이면: unique 제약 자체가 안 걸려있거나 검증 누락 (심각)
   - 하나가 `500`이면: `saveAndFlush()` + `DataIntegrityViolationException` catch가 의도대로 동작 안 하는 것

### 3-3. 타 회원 접근 차단 일괄 확인 (API-VIEWER-001/002/003/004/005 #6 등)

1. 같은 Collection에 회원 A의 `rentalR1`을 대상으로 한 5개 API 요청을 폴더로 묶기
2. Header만 `Authorization: Bearer {{tokenB}}`로 바꿔서 Runner로 5개 한 번에 실행
3. 전부 `403 AUTH_ACCESS_DENIED`인지 Run Results에서 한 번에 확인

### 3-4. 만료 대여 접근 차단 일괄 확인

1. 같은 5개 API를 `rentalR2`(만료) 대상으로 폴더 구성, 인증은 `tokenA`
2. Runner로 실행 후 전부 `403 RENTAL_EXPIRED`인지 확인 (단, 2-4/2-5에서 언급한 "북마크 삭제/목록 조회도 막히는 게 맞는지"는 별도 판단 필요)

## 5. 확인하면서 판단이 필요할 수 있는 지점

- API-VIEWER-004/005의 "만료 대여에서도 삭제/목록조회는 허용해야 하지 않나" — 지금 코드는 `getOwnedRentalOrThrow()`를 공유해서 전부 막힘. 테스트하다가 이게 어색하게 느껴지면 알려주면 좋음(정책 결정 필요).
- API-VIEWER-004 #3 (타 회원 북마크 삭제 시도) 응답이 `BOOKMARK_NOT_FOUND`인지 `AUTH_ACCESS_DENIED`인지는 `getOwnedRentalOrThrow` 호출 순서에 달려있어 실제 응답 보고 기록해두면 좋음.
