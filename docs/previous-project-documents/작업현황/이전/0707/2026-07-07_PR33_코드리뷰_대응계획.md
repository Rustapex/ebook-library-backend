### HIGH-2. `PointService` 포인트 잔액 동시성 (`PointService.java:31-39`)

**리뷰 지적**: `grantOrAdjustPoint()`가 `member` 조회 → 메모리에서 잔액 변경 → 저장 방식이라, 동시에 여러 요청(챌린지 보상 수령/관리자 포인트 조정)이 겹치면 lost update가 발생할 수 있다.

**코드 확인 결과** (`PointService.java:31-39`):
```java
public PointHistory grantOrAdjustPoint(Long memberId, int amount, String pointType, String description) {
    Member member = memberRepository.findById(memberId)
            .orElseThrow(() -> new BusinessException(ErrorCode.MEMBER_NOT_FOUND));
    if (member.getPointBalance() + amount < 0) {
        throw new BusinessException(ErrorCode.POINT_BALANCE_INSUFFICIENT);
    }
    member.applyPointChange(amount);
    PointHistory pointHistory = PointHistory.create(member, null, pointType, amount, description);
    return pointHistoryRepository.save(pointHistory);
}
```
지적이 정확하다. `findById` → JVM 메모리에서 `+= amount` → JPA dirty checking으로 flush 시점에 UPDATE가 나가는 구조라, 두 트랜잭션이 동시에 같은 `member` row를 읽으면 한쪽 변경이 유실될 수 있다(`chk_member_point_balance >= 0` 제약이 있어도 잔액 자체가 틀어지는 건 막지 못함). 오늘 챌린지/출석에서 고친 "원자적 UPDATE" 패턴과 동일한 근본 원인이다.

**대응 확정(권장 방향 적용)**: `MemberRepository`에 `UPDATE member SET point_balance = point_balance + :amount WHERE member_id = :memberId AND point_balance + :amount >= 0` 형태의 조건부 원자적 업데이트를 추가하고, 영향받은 row가 0건이면 `POINT_BALANCE_INSUFFICIENT`를 던지는 방식으로 변경. (오늘 `ChallengeProgressRepository.markRewardClaimedIfUnclaimed()`에 적용한 패턴과 동일한 접근.)

**영향/컴파일 검토**:
- `MemberRepository`에 `@Modifying @Query` 메서드를 추가하는 방식이라 기존 `findById`/`existsBy...` 호출부 시그니처는 깨지지 않는다.
- `PointService.grantOrAdjustPoint()` 내부 구현만 바꾸면 기존 호출부(`ChallengeService.claimReward()`, `AdminMemberPointController`)의 컴파일 영향은 없다.
- 결제 포인트 차감(`PaymentService`)은 이번 담당 범위가 아니다. 이번 라운드는 챌린지/출석/포인트/쿠폰 API 범위 안에서 `PointService.grantOrAdjustPoint()`를 사용하는 챌린지 보상 수령과 관리자 포인트 조정만 원자적 UPDATE 전환 대상으로 본다.
- 원자적 UPDATE 후 응답에 최신 잔액이 필요하므로, `PointHistory` 저장 전후에 `memberRepository.findById()`로 최신 `Member`를 다시 조회하는 단계가 필요하다. 이 재조회는 컴파일 문제는 없지만 쿼리 1회가 추가된다.

### MEDIUM-3. DTO에 CHECK 제약과 일치하는 허용값 검증 부재

**리뷰 지적**: `coupon.status`, `benefit_unit`, `challenge_reward.reward_type` 등 DB에 CHECK 제약이 있는 값들이 DTO에는 `@NotBlank`/`@Min`만 있고 허용값(enum/`@Pattern`) 검증이 없어서, 잘못된 문자열이 들어오면 서비스 계층이 아니라 DB 제약에서 터진다. 게다가 `GlobalExceptionHandler`가 `DataIntegrityViolationException`을 400으로 변환하지 않아 500으로 노출될 수 있다.

**코드 확인 결과**:
- `AdminCouponCreateRequest.java` (`benefitUnit`, `status`) — `@NotBlank`만 있고 `@Pattern`/enum 없음. schema.sql 102-103행: `chk_coupon_benefit_unit CHECK (benefit_unit IN ('AMOUNT','PERCENT'))`, `chk_coupon_status CHECK (status IN ('ACTIVE','INACTIVE'))`.
- `couponType`은 현재 schema.sql에 CHECK 제약이 없다. 별도 API 명세에서 허용값을 확정하지 않는 한 이번 MEDIUM-3의 "schema CHECK와 일치하는 검증" 대상으로 보지 않는다.
- `AdminChallengeRewardItemRequest.java` (rewardType) — `@NotBlank`만 있음. schema.sql 452행: `chk_challenge_reward_reward_type CHECK (reward_type IN ('POINT','coupon'))`.
- `GlobalExceptionHandler.java` — 오늘 추가한 핸들러는 `MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException`만 처리하고, `DataIntegrityViolationException`은 여전히 catch-all(`Exception.class`)로 떨어져 500이 된다.

**대응 확정(권장 방향 적용, 2차 리뷰 반영 — 전역 매핑 범위 축소)**:
1. **1순위**: `AdminCouponCreateRequest.benefitUnit/status`, `AdminChallengeRewardItemRequest.rewardType`에 `@Pattern(regexp = "...")`으로 schema CHECK와 동일한 허용값 검증 추가 — 이걸로 대부분의 잘못된 값은 DB까지 내려가기 전에 400으로 걸러진다.
2. **`DataIntegrityViolationException` 전역 매핑은 무조건 400/409로 뭉뚱그리지 않는다.** 2차 리뷰 지적대로, 이렇게 하면 예상된 CHECK/UNIQUE 위반뿐 아니라 진짜 DB 버그(예: FK 무결성 깨짐, NOT NULL 위반 등 코드 버그성 오류)까지 400/409로 숨겨버릴 수 있다. 기준을 아래처럼 명확히 정한다:
   - 이미 위 1번 `@Pattern` 검증으로 걸러지는 CHECK 제약은 애초에 `DataIntegrityViolationException`까지 갈 일이 거의 없어야 정상.
   - 그래도 남는 `DataIntegrityViolationException`(예: 동시성으로 인한 UNIQUE 제약 위반처럼 애플리케이션 레벨에서 사전 검증이 불가능한 경우)만 선별적으로 400/409 매핑.
   - 그 외의 예기치 못한 `DataIntegrityViolationException`은 지금처럼 500 + `log.error`로 스택트레이스를 남긴다(전부 400으로 숨기지 않는다).

**영향/컴파일 검토**:
- `@Pattern`은 DTO 필드 애너테이션 추가와 import 추가만 필요하므로 기존 서비스/컨트롤러 메서드 시그니처를 깨지 않는다.
- 올바른 기존 요청값(`AMOUNT`, `PERCENT`, `ACTIVE`, `INACTIVE`, `POINT`)은 그대로 통과한다.
- HIGH-1 옵션 A와 같이 적용하면 `rewardType=coupon`은 더 이상 허용하지 않는다. 따라서 schema에는 `coupon`이 허용되어 있어도 이번 API 계약상 관리자 챌린지 수정 요청에서만 400으로 차단된다.
- `couponType`은 schema CHECK가 없으므로 이번 수정에서 `@Pattern`을 추가하지 않는다. 임의로 추가하면 기존 데이터/요청의 컴파일 문제가 아니라 런타임 검증 실패가 생길 수 있다.

### MEDIUM-4. 목록 조회 N+1 쿼리

**리뷰 지적**: 쿠폰 목록/챌린지 목록 조회 시 row마다 추가 쿼리가 발생한다.

**코드 확인 결과** — 모두 사실:
- `CouponService.toAdminSummary()` (`CouponService.java:99-107`): coupon row마다 `countByCoupon_CouponId`, `countByCoupon_CouponIdAndCouponStatus`(USED), 같은 메서드(EXPIRED) — **row당 count 쿼리 3개**.
- `ChallengeService.toRewardItems()`/`toResponse()`(`ChallengeService.java:130-135`, `169-173`): challenge row마다 `challengeRewardRepository.findByChallenge_ChallengeId()` 호출 — **row당 조회 쿼리 1개**.

**대응 확정(권장 방향 적용)**: 페이지 크기가 큰 관리자 목록 API부터 우선 개선한다.
- `AdminCouponController` 목록: 현재 `CouponService.toAdminSummary()`가 coupon row마다 count 쿼리 3개를 호출하므로, `member_coupon`을 `coupon_id IN (...) GROUP BY coupon_id, coupon_status` 형태로 한 번에 집계하고 메모리에서 `issued/used/expired` 값을 매핑한다.
- `AdminChallengeController` 목록: 현재 challenge row마다 reward 조회가 발생하므로, `challenge_reward`를 `challenge_id IN (...)`으로 한 번에 조회하고 `challengeId` 기준으로 그룹핑해 매핑한다.
- 사용자 챌린지 목록(`ChallengeController`)도 같은 helper를 재사용할 수 있으면 함께 개선하되, 이번 라운드의 필수 완료 기준은 관리자 목록 N+1 제거로 둔다.

**영향/컴파일 검토**:
- 기존 repository 메서드는 삭제하지 않고 배치 조회/집계 메서드를 추가하는 방식으로 진행하면 기존 호출부 컴파일은 깨지지 않는다.
- JPQL projection/interface 또는 `Object[]` 집계를 사용할 수 있는데, 컴파일 안정성은 projection/record DTO가 더 낫다. 단, JPQL 생성자 표현식을 쓰면 패키지명/생성자 타입이 정확히 맞아야 한다.
- 응답 DTO(`AdminCouponSummaryResponse`, `AdminChallengeSummaryResponse`) 필드 구조는 유지하므로 프론트/Swagger 응답 형태는 바뀌지 않는다.

**단, 이미 검토·결정된 사항이다.** `2026-07-06_챌린지-출석-포인트-쿠폰API_구현계획.md` 3-4절에서 이 8개 Entity(`Challenge`/`ChallengeProgress`/`ChallengeReward`/`Attendance`/`PointHistory`/`Coupon`/`MemberCoupon`/`CouponUsage`)를 전수 점검했고, "이전에 만들어진 Entity라 이번 계획에서 손대지 않는다(사용자 지시)"로 이미 범위 밖 결론을 냈다. 이번 PR #33은 이 Entity들을 새로 만들거나 구조를 바꾸지 않았으므로 **새로운 위반이 아니라 기존 결정의 재확인**이다.

## 3. 남은 결정 필요 사항

1. HIGH-1은 옵션 A로 확정: `rewardType=coupon` 등록 차단.
2. HIGH-2는 권장 방향으로 확정: `MemberRepository` 조건부 원자적 UPDATE 추가 후 `PointService`에서 사용.
3. MEDIUM-3은 권장 방향으로 확정: schema CHECK와 일치하는 DTO `@Pattern` 검증을 먼저 추가하고, `DataIntegrityViolationException` 전역 일괄 매핑은 하지 않는다.
4. MEDIUM-4는 권장 방향으로 확정: 관리자 쿠폰/챌린지 목록의 N+1을 배치 조회/집계로 제거한다.
5. 범위 제외로 확정: 결제 포인트 차감(`PaymentService.member.usePoint()`)은 이번 담당 범위가 아니므로 수정하지 않는다.

### 4-1. 이번 점검에서 새로 추가된 항목

- 나머지(1~9, 12절)는 전부 준수 확인, 10절은 기존에 이미 파악·결정된 사항의 재확인이라 **이번 점검으로 새로 추가되는 대응 항목은 없다**. 위 1절/2절에 정리된 HIGH-1, HIGH-2, MEDIUM-3, MEDIUM-4, MEDIUM-5가 이 문서의 유일한 대응 대상이다.
- **(2차 리뷰 반영, 액션 아이템 추가)** `GlobalExceptionHandler`는 `@RestControllerAdvice`로 전역 적용되므로, 오늘 추가한 핸들러(`MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException`)가 이 기능과 무관한 다른 팀원의 `@RequestParam` API 응답 계약까지 바꾼다. 이 회귀 범위를 검증 없이 "영향 없음"으로만 적어두는 건 부족하다는 지적을 반영해, §5(테스트 계획)에 "타입 불일치/필수 파라미터 누락/validation 실패" 최소 1개씩의 회귀 테스트를 필수 항목으로 추가한다.

### 4-2. BaseEntity 상속 전환 시 영향 분석 (지금 바로 하지는 않되, 실행 가능성 검토)

10절 위반 Entity 6개(`Challenge`/`ChallengeProgress`/`Attendance`/`PointHistory`/`Coupon`/`MemberCoupon`)를 실제로 `BaseEntity` 상속으로 바꾸면 어떤 일이 생기는지 코드/스키마 기준으로 확인했다.

**결론부터: 단순 리팩터링이 아니라 DB 스키마 변경이 선행돼야 하고, 컴파일 에러 3곳 + 조용한 동작 변경 위험 1곳이 있다.**

**1) 스키마 검증 실패로 앱 기동 자체가 막힌다 (`ddl-auto=validate`)**
- `BaseEntity`(`common/domain/BaseEntity.java`)는 `createdAt`(컬럼 `created_at`)과 `updatedAt`(컬럼 `updated_at`) **두 컬럼을 항상 요구**한다(`@CreatedDate`/`@LastModifiedDate`).
- 실제 테이블 컬럼(schema.sql 확인 결과):
  - `coupon`(92-104행), `challenge`(106-117행), `attendance`(187-194행), `point_history`(196-206행): `created_at`만 있고 **`updated_at` 컬럼이 아예 없음**.
  - `member_coupon`(406-416행), `challenge_progress`(431-442행): **`created_at`/`updated_at` 둘 다 없음**.
- `application.properties`의 `spring.jpa.hibernate.ddl-auto=validate` 설정상, Hibernate가 기동 시점에 엔티티 매핑 컬럼과 실제 테이블 컬럼을 대조하다가 매핑된 컬럼이 테이블에 없으면 `SchemaManagementException`을 던지고 **애플리케이션이 아예 기동되지 않는다**(컴파일 에러가 아니라 런타임 기동 실패라 테스트도 전부 막힘).
- 해결하려면 `schema.sql`에 컬럼을 추가해야 하는데, `schema.sql`은 `CREATE TABLE IF NOT EXISTS`(신규 생성 전용)라 **이미 만들어진 테이블에는 컬럼이 자동 반영되지 않는다**. 즉 `schema.sql` 수정만으로는 안 되고, 이미 존재하는 로컬/공유 DB마다 `ALTER TABLE ... ADD COLUMN`을 수동 실행해야 한다(Flyway/Liquibase 같은 마이그레이션 도구가 없어 팀원 전원이 개별 반영해야 함).

**2) 컴파일 에러 발생 지점 (3개 파일, 4개 메서드)**
- `PointHistory.create()`(57행) — `pointHistory.createdAt = LocalDateTime.now();`
- `PointHistory.createPaymentUse()`(67행) — `history.createdAt = createdAt;`
- `Attendance.create()`(44행) — `attendance.createdAt = LocalDateTime.now();`
- `Coupon.create()`(56행) — `coupon.createdAt = LocalDateTime.now();`

`BaseEntity.createdAt`은 `private` 필드고 setter가 없다(`@CreatedDate`가 영속화 시점에 자동으로 채우는 구조라 직접 대입을 애초에 허용하지 않음). 현재처럼 필드를 직접 선언하지 않고 상속만 받으면 위 4곳은 `createdAt` 심볼을 찾지 못해 컴파일이 깨진다.

**3) 참고 — `PointHistory.createPaymentUse()`는 이번 담당 범위 밖이지만 BaseEntity 전환 시 영향이 있다**
- 호출부 `PaymentService.java:85-105`를 확인한 결과, 결제 처리 트랜잭션 안에서 `LocalDateTime now = LocalDateTime.now();`를 **딱 한 번만** 캡처해서 `Payment.create(..., now)` / `memberCoupon.use(now)` / `CouponUsage.create(..., now)` / `PointHistory.createPaymentUse(..., now)`에 전부 동일하게 넘긴다. 즉 "한 결제 트랜잭션에서 만들어지는 여러 row가 정확히 같은 타임스탬프를 공유해야 한다"는 게 원래 설계 의도다.
- `@CreatedDate`로 바꾸면 `createdAt`을 파라미터로 지정할 수 없고, 실제 flush 시점에 JPA Auditing이 자체적으로 캡처하는 별도의 `now()`가 들어간다. 이 값은 `Payment`/`CouponUsage`가 쓰는 `now`와 밀리초 단위로 어긋날 수 있어 "같은 결제 트랜잭션 = 같은 시각"이라는 기존 불변식이 깨진다.
- 이건 컴파일 에러로 잡히지 않고, 밀리초 단위 오차라 테스트에서도 눈에 잘 안 띄는 **조용한 회귀**다. 다만 결제 API는 이번 담당 범위가 아니므로, 이 문서에서는 BaseEntity 전환을 지금 하지 않는 근거로만 기록하고 실제 수정 대상으로 보지 않는다.

**4) `ChallengeProgress`/`MemberCoupon`은 현재 `createdAt` 필드가 아예 없음**
- 대입 코드가 없어 컴파일 에러는 없지만, 1)의 스키마 문제(두 테이블 모두 `created_at`+`updated_at` 컬럼 신설 필요)는 동일하게 적용된다.

**5) 참고(BaseEntity와 무관, 점검 중 추가로 발견) — 죽은 코드**
- `ChallengeProgress.markRewardClaimed()`(75-77행)는 오늘 `claimReward()`를 원자적 UPDATE(`ChallengeProgressRepository.markRewardClaimedIfUnclaimed()`) 방식으로 바꾸면서 더 이상 호출하는 곳이 없다(프로젝트 전체 검색 결과 선언부 1곳뿐). BaseEntity와는 별개 사안이라 이번 대응 우선순위에는 넣지 않되, 다음 코드 정리 때 제거 대상으로 기록.

**종합 판단**: 이 6개 Entity의 BaseEntity 전환은 "필드 몇 줄 바꾸는" 리팩터링이 아니라 (a) 최소 4개 테이블에 컬럼 1개, 2개 테이블에 컬럼 2개를 추가하는 실제 DB 스키마 변경(마이그레이션 도구 없이 각 DB에 수동 반영 필요)과 (b) `PointHistory.createPaymentUse()`의 "동일 트랜잭션 내 동일 타임스탬프 공유" 설계를 어떻게 유지할지에 대한 별도 결정이 선행돼야 하는 작업이다. 지금 당장 진행하기보다는, 스키마 마이그레이션 계획과 `createPaymentUse()` 타임스탬프 정책을 먼저 정한 뒤 별도 작업으로 분리하는 것을 권장한다.

## 5. 필수 회귀 테스트 계획 (2차 코드 리뷰 반영 — "구현 방향"만으로는 부족, 테스트로 고정)

2차 리뷰(REQUEST CHANGES)는 "포인트 잔액/중복 보상/출석 중복 같은 금전성·동시성 버그가 재발해도 테스트로 막지 못한다"는 점을 아키텍처 BLOCK 사유로 지적했다. 아래 테스트를 **실제 코드 수정과 같은 라운드에 필수로 추가**한다(위 §2 우선순위와 1:1 대응).

| 대상 | 필수 테스트 케이스 |
|---|---|
| `PointService`(HIGH-2 원자적 UPDATE 전환 후) | ① 챌린지 보상 지급/관리자 포인트 조정 후 잔액 검증, ② 관리자 차감 요청에서 잔액 부족 시 `POINT_BALANCE_INSUFFICIENT` 발생, ③ 동시 요청 2개 이상이 같은 회원 잔액을 동시에 변경할 때 lost update 없이 순차 반영되는지(동시성 테스트). 결제 포인트 차감은 이번 담당 범위가 아니므로 제외 |
| `ChallengeService.claimReward()`(오늘 이미 수정한 원자적 UPDATE) | ④ 동시 요청 2개 중 1개만 성공하고 나머지는 `CHALLENGE_REWARD_NOT_CLAIMABLE`인지(동시성 테스트, 회귀 방지용으로 지금 라운드에 추가) |
| `AttendanceService.checkIn()`(오늘 이미 수정) | ⑤ 동시 출석 요청 시 1건만 성공하고 나머지는 409 `ATTENDANCE_ALREADY_EXISTS`인지 |
| HIGH-1 옵션 A | ⑥ `rewardType=coupon`으로 `updateChallenge()` 호출 시 검증 오류로 차단되는지 |
| MEDIUM-3 DTO 검증 | ⑦ `AdminCouponCreateRequest.benefitUnit/status`, `AdminChallengeRewardItemRequest.rewardType`에 CHECK 제약 밖 값을 넣었을 때 400 `VALIDATION_ERROR`로 걸러지는지(DB까지 내려가지 않는지) |
| MEDIUM-4 N+1 개선 | ⑪ 관리자 쿠폰 목록/관리자 챌린지 목록 조회 결과가 기존과 동일한 응답 필드를 유지하는지, 쿼리 수가 row 수에 비례해 증가하지 않는지 |
| `GlobalExceptionHandler` 신규 핸들러(오늘 이미 수정) | ⑧ 타입 불일치(`MethodArgumentTypeMismatchException`) 400, ⑨ 필수 파라미터 누락(`MissingServletRequestParameterException`) 400, ⑩ 기존 `@Valid` 검증 실패가 여전히 400으로 유지되는지(회귀 확인) |

이 표의 ①~⑩ 전부를 이번 대응 라운드의 완료 조건에 포함한다. 코드만 고치고 테스트 없이 "빌드 통과"만으로 완료 보고하지 않는다.
