## 1. 원인 분석

### 1-1. 구조적 원인 (커밋 `ddf0742` 내용 확인)

- `ddf0742`("H2 인메모리 테스트 DB 제거하고 .env 매핑 실DB로 전환")에서 `@DataJpaTest` 8개 클래스가 H2 대신 `@AutoConfigureTestDatabase(replace = NONE)`로 바뀌어, **테스트가 각 개발자의 로컬 실 MySQL(`ABC` DB)을 그대로 사용**하게 됨.
- `README.md`(로컬 확인): "백엔드는 로컬 MySQL 8.x의 `ABC` 데이터베이스를 사용합니다" — 즉 **팀원 각자 자신의 로컬 `ABC` DB**를 개발+테스트에 동시에 사용하는 구조. H2 시절엔 테스트마다 완전히 빈 DB에서 시작했지만, 실DB 전환 후에는 그 개발자가 실제로 개발/수동테스트하며 쌓아온 데이터가 항상 같이 존재하는 상태에서 테스트가 실행됨.
- `application.properties` 확인 결과 `spring.jpa.hibernate.ddl-auto=validate` + `spring.sql.init.schema-locations=classpath:schema.sql`(`CREATE TABLE IF NOT EXISTS`)를 쓰고 있어, **스키마 마이그레이션 도구가 없음**. `schema.sql`이 바뀌어도 이미 존재하는 테이블에는 컬럼이 자동으로 추가되지 않아서, PR #23의 ALTER(`aladin_category_id`/`aladin_category_name`)가 반영 안 된 로컬 DB에서는 Hibernate `validate` 단계부터 실패한다(`ddf0742` 커밋 메시지에 동일 증상 기록됨).

### 1-2. 실제 로컬 DB 조사 결과 (mysql CLI, `.env`의 `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` 사용)

| 확인 항목 | 결과 |
|---|---|
| `category` 테이블 컬럼 | `aladin_category_id`, `aladin_category_name` **존재함**(이 로컬 DB는 스키마 최신) |
| `category` 테이블 행 수 | 0건 (현재 이 로컬 DB에서는 비어 있음) |
| `book.isbn`에 `1111111111111`/`2222222222222`/`3333333333333` 존재 여부 | 0건 (현재 이 로컬 DB에서는 충돌 없음) |

**중요**: 이 로컬 DB(이 세션 실행 환경)에서는 현재 3건이 재현되지 않는다. 즉 보고된 실패는 **다른 팀원의 로컬 DB 상태**(스키마 drift 또는 기존 데이터 존재)에 의존적이며, 이 저장소의 테스트 코드 자체가 "실DB에 뭐가 들어있든 항상 통과"하도록 설계돼 있지 않다는 게 근본 문제다. 개별 DB 상태를 손대는 방식으로는 재발을 막을 수 없고, **테스트 코드/설정을 고쳐야** 한다.

### 1-3. 코드 레벨 원인 (실제 테스트 파일 확인)

| 파일 | 문제 패턴 |
|---|---|
| `category/repository/CategoryRepositoryTest.java:39` | `findByStatusOrderBy...("ACTIVE")`로 **전역** 조회 후 `containsExactly("Essay", "Novel")`(정확히 이 2건만) 단정 → 실DB에 이미 다른 `ACTIVE` 카테고리(예: 알라딘 배치로 들어온 실데이터)가 있으면 실패 |
| `book/repository/BookRepositoryTest.java:44-46` | `1111111111111`/`2222222222222`/`3333333333333` **고정 리터럴 ISBN** 사용(`book.isbn`엔 `UNIQUE` 제약) → 다른 테스트나 수동 Swagger 테스트에서 동일 플레이스홀더 ISBN을 이미 넣어놨다면 `INSERT` 시점에 제약 위반 |
| (보고되지 않았지만 동일 위험 발견) `collection/repository/CollectionRepositoryTest.java:38-42` | `findByStatus("ACTIVE", ...)`로 **전역** 조회 후 `containsExactlyInAnyOrder("Spring Series", "Summer Event")` 단정 — `CategoryRepositoryTest`와 완전히 같은 패턴. 지금 당장 실패로 보고되진 않았지만 실DB에 다른 `ACTIVE` 컬렉션이 생기는 순간 똑같이 깨짐 |

반면 같은 파일 안에서도 `LibraryBookRepositoryTest.findActiveByBookId(bookId)`처럼 **테스트가 만든 특정 ID로 스코프를 좁힌 조회**는 실DB에 다른 데이터가 있어도 영향을 안 받는다(`bookId`로 필터링되므로). 즉 **"전역 상태값 조회 + 정확 일치 단정"** 조합이 근본 문제이지, 실DB 자체나 `@DataJpaTest` 방식이 문제가 아니다.

## 2. `resources/` vs `api-test-results/` 비교 (요청하신 대로 확인)

- `src/main/resources/schema.sql`, `data.sql`: 앱 부팅/테스트 실행 시 실제로 적용되는 파일(`spring.sql.init.*` 설정 대상). **이번 문제와 직접 관련된 기준 파일 — 우선순위 1순위**(사용자 지시와 일치).
- `api-test-results/swagger/pr22-test-seed.sql`: PR #22 뷰어/북마크 API를 **Swagger로 수기 테스트**할 때 쓰는 시드 데이터일 뿐, 자동화 테스트(`@DataJpaTest` 등)에서는 전혀 참조되지 않음(`api-test-results/swagger/README.md`에 "This is manual verification evidence. It does not replace `.\\gradlew.bat test`"라고 명시). `schema.sql`과 충돌하는 내용도 없음(단순 `INSERT` 시드).
- 사용자가 언급한 `"api-test-results\swagger 테스트용.sql"`은 실제로 **존재하지 않는 파일명**이다 — 해당 디렉터리에는 `pr22-test-seed.sql` 하나만 있음(확인: `ls api-test-results/swagger/`). 오타이거나 다른 경로를 의도하신 것 같으니 확인 부탁드린다.
- 결론: 이번 이슈는 `resources/schema.sql`·`data.sql`과 로컬 실DB 간의 정합성 문제이고, `api-test-results/`는 무관하다.

## 3. 해결 방안 옵션

### 옵션 A. 테스트 전용 DB(스키마) 분리

- 로컬에 개발용 `ABC`와 별도로 `ABC_TEST` 스키마를 만들고, 테스트 실행 시에만 그쪽을 바라보도록 `application-test.properties`(H2 관련 내용 없이, `DB_URL`만 `ABC_TEST`로) 부활 + `@DataJpaTest` 클래스에 `@ActiveProfiles("test")` 재적용.
- 장점: 실제 개발 중 쌓인 데이터와 완전히 분리되어 "내 DB에 뭐가 있는지" 신경 쓸 필요가 없어짐.
- 단점: 각 팀원이 `ABC_TEST` 스키마를 로컬에 추가로 만들어야 하는 1회성 설정 작업 발생(`README.md` 안내 추가 필요). `CREATE TABLE IF NOT EXISTS` 한계(1-1)는 테스트 DB에도 동일하게 남음 — 스키마 바뀌면 `ABC_TEST`도 드롭 후 재생성 필요.

### 옵션 B. 테스트 코드 자체의 격리 패턴 통일

- `CategoryRepositoryTest`/`CollectionRepositoryTest`처럼 **전역 조회 + 정확 일치(`containsExactly`)** 패턴을, 이미 프로젝트에 있는 안전한 패턴(`BookRepositoryTest.availableSpecificationExcludesHiddenBooks`가 쓰는 `contains(내가 넣은 것)` + `doesNotContain(내가 숨긴 것)`)으로 바꿈.
- `BookRepositoryTest`의 고정 ISBN 리터럴은 `@BeforeEach`마다 유일한 값(예: 타임스탬프/UUID 일부를 13자리로 가공)으로 생성해 실DB의 기존 데이터와 절대 충돌하지 않게 함.
- 장점: 설정 변경이나 팀원 추가 작업 없이 테스트 코드만 고치면 됨.
- 단점: "실DB에 스키마 자체가 안 맞는" 문제(컬럼 없음 등, 1-1 후반부)는 이 방법으로 못 잡음 — 이건 애초에 테스트가 잡아야 할 문제라기보다 팀원이 `schema.sql` 최신화를 놓친 것이라, 별도로 "로컬 DB 스키마 최신화 안내"가 필요.

### 옵션 C. 팀 공유 MySQL DB로 전환 (`2026-07-07_mysql-shared-db-test-guide.md`, 신규 확정 방향)

- 내용: 팀원 각자 로컬 `ABC` DB 대신, 한 명(DB 제공 노트북)이 MySQL을 계속 켜두고 나머지 팀원이 같은 LAN에서 원격 접속해서 **하나의 물리적 DB를 공유**한다. 가이드 9절("DB 통합 전 권장 순서")에 최종 기준 `schema.sql`/`data.sql`을 먼저 정하고 그걸 공유 DB에 한 번만 적용하는 절차가 이미 정리돼 있음.
- **이게 실제로 해결하는 것 — 1-1의 "스키마 drift" 문제**: 지금까지는 팀원마다 로컬 DB에 `schema.sql` 반영 시점이 달라서 PR #23의 ALTER(`aladin_category_id` 등)가 누락된 사람이 생겼다(`ddf0742` 커밋 메시지에 기록된 증상). DB가 하나로 합쳐지면 **스키마는 항상 전원 동일**해지므로, "말로 전달하거나 SQL 파일을 git으로 공유할 필요 없이" 이 문제는 구조적으로 사라진다. 이 부분은 사용자가 의도한 대로 정확히 맞다.
- **이게 해결 못 하는 것, 오히려 악화되는 것 — 1-2/1-3의 "테스트 데이터 격리" 문제**: PR #29에서 보고된 3건은 애초에 "내 로컬 DB에 남아있는 다른 데이터가 테스트 assertion을 오염시킨다"는 문제였다. DB를 공유로 바꾸면 그 "오염 가능성이 있는 데이터"의 출처가 **나 혼자**에서 **팀원 전체**로 늘어난다 — 예를 들어 팀원 B가 Swagger로 카테고리를 만들어보는 순간, 팀원 A가 `CategoryRepositoryTest`를 돌리다가 실패할 수 있다. 즉 **옵션 C는 1-1을 고치지만 1-3(코드 패턴 문제)은 그대로 남고, 오히려 발생 빈도가 늘어날 수 있다.**
- 추가로 가이드 11절("주의사항")에 이미 나온 리스크: DB 제공 노트북이 꺼지면 전원 테스트 불가, 동시 접속 시 부하/락 경합 가능성. 여러 명이 같은 시각에 `@DataJpaTest`를 돌리면(트랜잭션은 각자 롤백되지만) `UNIQUE` 제약이 있는 고정 리터럴 값(예: 지금의 ISBN 3개)에서 **동시 실행 시 일시적 충돌**이 날 수 있음.

### 권장: 옵션 C(팀 결정) + 옵션 B 병행, 옵션 A는 보류

- 사용자가 이미 옵션 C(공유 DB)로 방향을 정했으므로 그대로 채택한다. 다만 **옵션 C는 스키마 동기화 문제만 해결할 뿐 PR #29가 보고한 테스트 격리 문제는 그대로 남거나 악화되므로, 옵션 B(테스트 코드의 전역조회+정확일치 assertion 수정, 고정 리터럴 제거)는 선택이 아니라 필수**로 격상한다.
- 옵션 A(팀원 각자 로컬에 `ABC_TEST` 스키마 분리)는 "각자 로컬 DB"라는 전제 자체가 옵션 C로 대체되므로 원래 형태로는 보류한다. 대신 공유 DB 제공 노트북에 `ABC_TEST`라는 **공유 테스트 전용 스키마**를 하나 더 만드는 변형은 가능하나(운영용 `ABC`와 분리), 여러 명이 동시에 테스트를 실행하면 여전히 경합 위험이 남아 "팀 컨벤션(테스트는 한 번에 한 사람만 실행)"이 필요 — 이건 5장 결정 필요 사항으로 분리.

## 6. 실행 순서(안) — 승인 후 진행

옵션 B(코드 수정)를 먼저 끝내고, 그 다음 공유 DB로 전환하는 순서를 권장한다 — 지금 상태에서 바로 공유 DB로 옮기면 테스트 취약점을 그대로(오히려 더 위험하게) 옮기는 셈이기 때문.
