## 완료 후 추가로 발견/해결한 문제 (병합 계획에 없었던 것)

- **문제**: 빌드 시 전체 테스트 42건이 전부 `BeanDefinitionOverrideException`으로 실패. 원인은 `payment.repository.MemberCouponRepository`(main 쪽에서 신규 추가)와 `coupon.repository.MemberCouponRepository`(제가 reward-api에서 신규 추가)가 **서로 다른 패키지인데 클래스 simple name이 같아서** Spring이 둘 다 빈 이름 `memberCouponRepository`로 등록하려다 충돌한 것. git이 서로 다른 경로라 충돌로 표시하지 않아 이번 병합 충돌 목록(5개)엔 없었지만, 실제로는 병합의 직접적인 부작용.
- **해결(사용자 승인 후 진행)**: `payment.repository.MemberCouponRepository`로 통합(엔티티 `MemberCoupon`이 `payment.domain`에 있어 그쪽이 정본) — 양쪽 메서드(`findByMemberCouponIdAndMember_MemberId` + `findByMember_MemberId`/`findByMember_MemberIdAndCouponStatus`/`countByCoupon_CouponId`/`countByCoupon_CouponIdAndCouponStatus`) 전부 병합. `coupon.repository.MemberCouponRepository`는 삭제. 유일한 호출부였던 `coupon/service/CouponService.java`의 import 수정. 관련 테스트(`MemberCouponRepositoryTest`)도 `payment.repository` 패키지로 이동.
- **빌드 결과**: 86개 테스트 중 85개 통과. 남은 1건(`CategoryRepositoryTest.findsOnlyActiveCategoriesOrderedByDisplayOrder`)은 이번 병합과 무관 — `2026-07-07_실DB테스트격리이슈_수정계획.md`에 이미 문서화된 기존 이슈(전역 조회 + `containsExactly` 취약점)가 그대로 재현된 것.

## 0. 핵심 결론 (사용자 확정 완료)

5개 충돌 중 **4개는 "내 것 vs 상대 것" 양자택일이 아니라, 서로 다른 기능이라 둘 다 살려야 하는 충돌**입니다(같은 클래스 끝부분에 각자 메서드를 추가하다 보니 git이 충돌로 표시한 것뿐) — **둘 다 유지로 확정**.

진짜 "하나를 골라야 하는" 중복은 `ErrorCode` 딱 1건이고, 그마저도 **제 이름이 아니라 상대방(main) 이름이 이겨야 합니다** — 이미 병합 완료된 `PaymentServiceTest.java`가 상대방 이름에 의존하고 있어서, 제 이름을 남기면 그 테스트가 컴파일부터 깨집니다(1-1절 근거 참고). **사용자 확정 원칙**: "main과 내 쪽이 겹치거나 같은 의미인 항목은 main 이름으로 유지하고, main에 없는 내 `ErrorCode`는 그대로 추가한다."

## 1. 파일별 분석

### 1-1. `common/exception/ErrorCode.java` — **유일한 진짜 중복, main 이름으로 통일 (확정)**

| 내 쪽(HEAD) | 상대 쪽(main) |
|---|---|
| `ATTENDANCE_ALREADY_EXISTS`, `COUPON_NOT_FOUND`, `MEMBER_COUPON_NOT_FOUND`, `CHALLENGE_NOT_FOUND`, `CHALLENGE_REWARD_NOT_CLAIMABLE` | `BOOK_RENTAL_TYPE_MISMATCH`, `MEMBER_COUPON_NOT_USABLE` |
| `POINT_BALANCE_INVALID` (400, "포인트 잔액이 부족합니다.") | `POINT_BALANCE_INSUFFICIENT` (400, "포인트 잔액이 부족합니다.") |

- 위 표 첫 줄 5개+2개는 서로 겹치지 않는 별개 코드라 **전부 유지**(양쪽 다 살림).
- 둘째 줄만 문제: `POINT_BALANCE_INVALID`와 `POINT_BALANCE_INSUFFICIENT`는 HTTP 상태·메시지가 완전히 동일한 사실상 중복.
- **근거(`grep` 확인 결과)**:
  - `POINT_BALANCE_INVALID` 사용처: 제가 만든 `member/service/PointService.java:35` **1곳뿐**.
  - `POINT_BALANCE_INSUFFICIENT` 사용처: `member/domain/Member.java:113`(충돌 중인 `usePoint()` 안, main 쪽) + **이미 충돌 없이 병합 완료된** `payment/service/PaymentServiceTest.java` 2곳(`.isEqualTo(ErrorCode.POINT_BALANCE_INSUFFICIENT)` 등).
  - `PaymentServiceTest.java`는 이미 "both modified/added" 목록이 아니라 그냥 "new file"로 조용히 병합 완료된 상태라, 여기서 참조하는 상수명을 제가 지우면 그 테스트가 컴파일 에러로 깨집니다.
- **결론(확정): `POINT_BALANCE_INSUFFICIENT`(main 이름)로 통일하고, `POINT_BALANCE_INVALID`는 삭제한다.**
- **`PointService.java`를 같이 고쳐야 하는 이유**: `POINT_BALANCE_INVALID`를 지우면, 이 상수를 참조하는 코드는 전부 `cannot find symbol` 컴파일 에러가 난다. `grep` 결과 이 상수를 쓰는 곳은 전체 코드베이스에서 `member/service/PointService.java:35` **딱 한 곳**이다. `PointService.java` 자체는 상대편이 손댄 적 없는 파일이라 git이 충돌(`UU`/`AA`)로 표시하지 않지만, `ErrorCode`를 합치기로 한 이상 이 한 줄(`ErrorCode.POINT_BALANCE_INVALID` → `ErrorCode.POINT_BALANCE_INSUFFICIENT`)은 반드시 같이 고쳐야 하는 **기계적 연쇄 수정**이다(선택 사항 아님).

**병합 후 최종 형태(제안)**:

### 1-2. `member/domain/Member.java` — 중복 아님, 둘 다 유지 (확정)

| 내 쪽(HEAD) | 상대 쪽(main) |
|---|---|
| `applyPointChange(int amount)`: 검증 없이 `pointBalance += amount`(양/음 둘 다 허용, 호출자인 `PointService.grantOrAdjustPoint`가 미리 잔액 검증) | `usePoint(int amount)`: `amount > pointBalance`면 `POINT_BALANCE_INSUFFICIENT` 던지고 `pointBalance -= amount`(결제 시 포인트 차감 전용, 자체 검증 포함) |

- 용도가 다름: `applyPointChange`는 챌린지 보상/관리자 조정처럼 **+/- 임의 금액**을 다루는 제 범용 메서드이고, `usePoint`는 **결제 시 포인트 사용**이라는 특정 시나리오 전용(상대방 `PaymentService`가 호출).
- **결론: 두 메서드 다 유지**(하나를 지우면 안 됨).

### 1-3. `member/domain/PointHistory.java` — 중복 아님, 둘 다 유지 (확정)

| 내 쪽(HEAD) | 상대 쪽(main) |
|---|---|
| `create(member, payment, pointType, pointAmount, description)`: 범용 팩토리(챌린지 보상/관리자 조정 등에서 사용, 제 `PointService`가 호출) | `createPaymentUse(member, payment, pointUsed, createdAt)`: `pointType="PAYMENT_USE"` 고정, 결제 시각과 동일한 `createdAt`을 명시적으로 받는 결제 전용 팩토리 |

- **결론: 두 팩토리 메서드 다 유지.**

### 1-4. `member/repository/PointHistoryRepository.java` — 중복 아님, 메서드 합치기 (확정)

| 내 쪽(HEAD) | 상대 쪽(main) |
|---|---|
| `findByMember_MemberId(...)`, `findByMember_MemberIdAndPointType(...)` — 내 포인트 이력 조회(`API-POINT-001`)용 | `findFirstByPayment_PaymentId(...)` — 특정 결제 건에 연결된 포인트 이력 조회용(결제 상세/내역 조회 쪽에서 사용 추정) |

- **결론: 인터페이스 하나에 메서드 3개 다 선언**(서로 다른 조회 축이라 충돌 아님).

### 1-5. `payment/domain/MemberCoupon.java` — 중복 아님, 둘 다 유지 (확정)

| 내 쪽(HEAD) | 상대 쪽(main) |
|---|---|
| `create(member, coupon)`: 신규 회원 쿠폰 **발급**용 정적 팩토리(관리자 쿠폰 발급 API에서 사용) | `use(now)`: 기존 회원 쿠폰을 **사용 처리**하는 인스턴스 메서드, `ISSUED`가 아니거나 만료면 `MEMBER_COUPON_NOT_USABLE` 던짐(결제 시 쿠폰 적용에서 사용) |

- 발급(`create`)과 사용(`use`)은 생명주기의 다른 단계라 겹치지 않음.
- **결론: 두 메서드 다 유지.**

### 1-6. `member/service/PointService.java` — git 충돌 파일은 아니지만 같이 수정 (확정)

- git 상태: 상대편(main)이 손댄 적 없는 파일이라 `git status`에는 충돌(`UU`)로 뜨지 않는다. 하지만 1-1에서 `ErrorCode.POINT_BALANCE_INVALID`를 삭제하기로 확정했으므로, 이 상수를 참조하는 유일한 곳인 이 파일도 **같은 작업 단위로 반드시 같이 고쳐야** 한다.
- 위치: `grantOrAdjustPoint(...)` 메서드 내부, 잔액 검증 실패 시 예외를 던지는 줄(`PointService.java:35`).
- 수정 내용: `throw new BusinessException(ErrorCode.POINT_BALANCE_INVALID);` → `throw new BusinessException(ErrorCode.POINT_BALANCE_INSUFFICIENT);` (한 줄, 상수명만 교체 — 로직 변경 없음).
- **결론: 5개 충돌 파일과 동일한 우선순위로, 같은 커밋에 포함해서 수정.** (`git add` 대상에도 이 파일을 포함시킨다.)

## 2. 사용자 가정("ErrorCode는 내가 만든 게 우선")에 대한 정정 — 확정된 절충안

- 사용자 확정 원칙: **main과 내 쪽이 겹치거나 같은 의미인 항목은 main 이름으로 유지하고, main에 없는 내 `ErrorCode`는 그대로 추가한다.**
- 대부분의 `ErrorCode` 값은 겹치지 않아 이 원칙이 그대로 "둘 다 유지"로 귀결된다.
- 유일하게 겹치는 `POINT_BALANCE_INVALID` vs `POINT_BALANCE_INSUFFICIENT`는 위 원칙에 따라 **main 이름(`POINT_BALANCE_INSUFFICIENT`)으로 통일** — 이미 병합 완료된 테스트 코드(`PaymentServiceTest.java`)가 상대방 이름에 의존하고 있다는 근거(1-1절)와도 정확히 일치한다.
