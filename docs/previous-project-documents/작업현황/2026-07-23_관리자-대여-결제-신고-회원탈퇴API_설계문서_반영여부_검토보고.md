## 1. 결론 요약

**누락 있음.** `API-ADMIN-RENTAL-001`(관리자 대여 조회), `API-ADMIN-PAYMENT-001`(관리자 결제 조회)의 고정 정렬 기준과 응답 구성 정책이 구현계획 문서에는 있으나, 두 설계문서 어디에도 기록되지 않았고 `api-spec(final).md` 정책 칸에도 반영되지 않았다.

그 외 `API-ME-004`, `API-ADMIN-REPORT-001`, `API-ADMIN-REPORT-002` 관련 정책은 설계문서에 기록돼 있고 `api-spec(final).md`에도 실제 반영이 확인된다.

## 2. 확인된 누락: `API-ADMIN-RENTAL-001` / `API-ADMIN-PAYMENT-001` 고정 정렬·응답 구성

**근거 (계획 문서 원문):** `docs/작업현황/2026-07-22_관리자-대여-결제-신고-회원탈퇴API_구현계획.md:60-67` `### 2.3 관리자 대여·결제 조회`

- 대여 목록: `READY`, `READING`, `OWNED` 상태만 허용, 고정 정렬은 `createdAt DESC, rentalId DESC`.
- 대여 응답: 대여 ID, 회원 ID·이름, 도서 ID·제목, 상태, 대여·최초 열람·종료 시각, 진행률, 결제 요약(nullable).
- 결제 목록: `PAID`만 반환, 고정 정렬은 `paidAt DESC, paymentId DESC`.
- 결제 응답: 결제 ID, 회원·도서·대여 식별 정보, 결제수단, 정가·쿠폰·포인트 차감·최종 결제금액, 결제 시각.
- 목록/count query는 같은 predicate 사용, 페이징은 0-based `PageResponse`, N+1 방지를 위해 bulk 조회·조립.

**확인한 것 — 이 내용이 설계문서에 없음:**

- `docs/작업현황/설계문서/2026-07-22_관리자-대여-결제-신고-회원탈퇴API_설계차이.md` §2(확정 구현 정책)는 `2.1 회원 탈퇴와 대여`, `2.2 기존 토큰 차단`, `2.3 신고의 수동 처리` 세 개 하위 절만 있다. 문서 상단 "대상"에는 `API-ADMIN-RENTAL-001`, `API-ADMIN-PAYMENT-001`이 명시돼 있지만, 본문에는 두 API 전용 정책 하위 절이 없다. §3(프런트 데이터 계약 조율 기록)에 쿼리 파라미터(`q`, `memberId`, `status` / `q`, `from`, `to`)만 표로 언급될 뿐, 고정 정렬·응답 필드 구성은 없다.
- `docs/작업현황/설계문서/2026-07-22_PR64_관리자-대여-결제-신고-회원탈퇴API_설계문서_반영예정.md` §1(확정 계약표)은 `API-ME-004`, `API-ADMIN-REPORT-001`, `API-ADMIN-REPORT-002` 세 행만 있다. `API-ADMIN-RENTAL-001`, `API-ADMIN-PAYMENT-001` 행 자체가 없다.

**확인한 것 — 현재 `api-spec(final).md` 상태:**

- `docs/API 명세/api-spec(final).md:347` (`API-ADMIN-RENTAL-001`): "대여 관리는 조회 전용. `READY`, `READING`, `OWNED`만 제공." — 상태 필터는 있으나 고정 정렬 문구 없음.

## 4. 모호 항목 소스 확인 결과 (2026-07-23 추가 확인, 해소됨)

**확인 방법:** `src/main/java/com/acorn/abc/common/security/JwtAuthenticationFilter.java`를 이번 PR 커밋(`c6dbdda`)과 그 직전 인증/회원 API 구현 커밋(`7d18338`)의 두 시점으로 비교했다(`git show 7d18338:...` vs 현재 워킹트리, 전체 통독 아님 — `doFilterInternal`/`memberRepository`/`SecurityContext` 키워드로 필요한 줄만 확인).

- **`7d18338`(PR 이전) 시점**: `JwtAuthenticationFilter`에 `memberRepository` 관련 코드가 전혀 없다. `doFilterInternal`은 `jwtTokenProvider.validateToken(token)`으로 서명·만료만 검사하고, 통과하면 즉시 `SecurityContextHolder`에 인증 정보를 설정했다 — **요청마다 회원 상태를 DB에서 다시 조회하는 로직 자체가 없었다.**
- **현재(`c6dbdda`, 이번 PR) 시점**: `JwtAuthenticationFilter.java:28-44`에서 토큰 검증 통과 후 `isActiveMember(memberId)`(`:48-52`)를 호출해 **매 요청마다** `memberRepository.findById(memberId)`로 최신 상태를 조회하고, `JOINED`일 때만 `SecurityContext`를 설정한다. `common/security`, `common` 전체를 검색해도 이 파일 외에 회원 상태를 조회하는 다른 공통 로직은 없다(`isActiveMember`가 유일한 지점).

**결론:** §4에서 모호하다고 남겼던 부분은 실제로는 모호하지 않다 — 기존 `api-spec(final).md §1.2`의 "주요 활동 요청을 거부한다" 문구는 이 PR 이전 코드에는 대응하는 필터 단계 구현이 없었으므로, 이번 PR에서 추가된 "매 요청마다 JWT 필터에서 회원 상태를 재조회해 즉시 차단"하는 동작은 기존 문구가 이미 포괄하고 있었다고 보기 어렵고, **새로 생긴 전역 동작이 맞다.** 따라서 이 내용은 §2와 마찬가지로 설계문서·API 명세에 아직 명시적으로 기록되지 않은 누락으로 재분류한다(기존 §1.2 문구와 모순되지는 않지만, "이미 발급된 토큰도 다음 요청부터 즉시 무효화된다"는 구체적 보장이 빠져 있다).
