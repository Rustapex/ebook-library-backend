팀 저장소 브랜치 PR 협업 기준

Git 브랜치 PR 협업 가이드

Fork 없이 팀 저장소에서 개인 작업 브랜치를 만들고, PR로 팀장에게 merge 요청하는 협업 방식

핵심 원칙
main에는 직접 작업하지 않습니다. 모든 작업은 개인 작업 브랜치에서 진행하고, PR을 올린 뒤 팀장이 검토 후 main에 merge합니다. merge 이후 작업자는 다시 main을 pull하고, 계속 작업 중인 브랜치가 있으면 최신 main을 병합한 뒤 push합니다.

1. 협업 원칙

원칙내용이유
main 직접 작업 금지기능 개발, 버그 수정, 문서 수정은 모두 작업 브랜치에서 진행합니다.main은 팀 기준 코드이므로 승인된 변경만 들어가야 합니다.
작업 브랜치 사용작업마다 feature/..., fix/... 같은 브랜치를 만듭니다.GitHub Docs는 브랜치를 다른 작업에 영향 주지 않는 격리 공간으로 설명합니다.
PR로 merge 요청작업 브랜치를 push한 뒤 GitHub에서 PR을 생성합니다.팀장이 변경 내용을 검토하고 main에 반영할 수 있습니다.
merge 후 다시 최신화팀장이 merge하면 작업자는 main을 pull합니다.로컬 코드가 팀 저장소의 최신 상태를 따라가야 다음 충돌을 줄일 수 있습니다.
설치 문서 제외Sourcetree 설치, GitHub 계정 연결, Fork 생성 설명은 이 문서에서 다루지 않습니다.이 문서는 설치가 아니라 반복 협업 절차를 설명합니다.

2. 역할 구분

팀장 / Git 관리자

  • 팀 저장소와 main 브랜치 관리
  • PR 검토, 리뷰 요청, merge 수행
  • 충돌 또는 규칙 위반 PR에 대한 수정 요청
  • 팀원이 어느 브랜치에서 작업해야 하는지 안내

작업자 / 팀원

  • main 최신화 후 작업 브랜치 생성
  • 작업 브랜치에서 코드/문서 수정, 검증, commit
  • 자기 작업 브랜치만 push
  • PR 제목/본문을 규칙에 맞게 작성
  • 팀장 merge 후 main pull 및 진행 중 브랜치 최신화

3. 용어 정리

용어의미예시
origin내 로컬 저장소가 연결된 팀 GitHub 저장소입니다.팀계정/프로젝트저장소
main팀 기준 브랜치입니다. 승인된 코드만 들어갑니다.origin/main, local main
작업 브랜치개별 작업을 진행하는 브랜치입니다.feature/member-login
head branchPR에서 변경 내용을 담은 브랜치입니다.feature/member-login
base branchPR 변경이 들어갈 대상 브랜치입니다.main
merge한 브랜치의 변경을 다른 브랜치에 합치는 작업입니다.작업 브랜치 -> main
stash아직 commit하지 않은 변경을 임시 보관하고 작업 폴더를 깨끗하게 만드는 기능입니다.git stash push -m "작업명"

5. 작업 시작 전 상태 확인

Sourcetree GUI

  1. 왼쪽 사이드바의 브랜치 목록을 봅니다.
  2. 굵게 표시되거나 선택된 브랜치가 현재 작업 중인 브랜치입니다. 작업 시작 전에는 보통 main이어야 합니다.
  3. 왼쪽 파일 상태 화면을 열어 아직 commit하지 않은 변경 파일이 있는지 확인합니다.
  4. 변경 파일이 있으면 먼저 내 작업인지 확인합니다. 내 작업이면 commit 또는 stash를 결정하고, 작업과 무관한 파일이면 commit하지 않습니다.
  5. History 화면에서는 main, origin/main, 내 작업 브랜치 위치가 어디인지 확인합니다.
  6. 로컬 설정 파일, secret 파일, 개인 PC 경로가 들어간 파일이 보이면 절대 commit하지 않습니다.

Sourcetree 버전에 따라 메뉴명은 조금 다를 수 있습니다. 핵심은 현재 브랜치와 변경 파일 목록 확인입니다.

터미널

git branch --show-current
git status --short

출력이 있으면 변경 파일을 확인하고, 작업과 무관한 파일은 commit 대상에서 제외합니다.

6. main 최신화

작업 브랜치를 만들기 전에는 항상 main을 최신화합니다. 오래된 main에서 브랜치를 만들면 PR 시점에 충돌 가능성이 커집니다.

Sourcetree GUI

  1. 왼쪽 브랜치 목록에서 main을 더블클릭해 이동합니다.
  2. 화면 상단의 패치(Fetch) 버튼을 누릅니다. Fetch는 원격 저장소의 최신 상태를 먼저 화면에 가져오는 작업입니다.
  3. 패치 창에서 모든 원격 저장소에서 가져오기를 체크합니다.
  4. 리모트에서 제거된 브랜치 정리하기를 체크합니다. 이미 GitHub에서 삭제된 원격 브랜치 표시를 정리하기 위한 옵션입니다.
  5. 확인을 눌러 Fetch를 실행합니다.
  6. Fetch가 끝나면 History 그래프에서 origin/main 위치가 갱신되었는지 확인합니다.
  7. 상단의 Pull 버튼을 누릅니다.
  8. Pull 창에서 원격 저장소가 origin인지 확인합니다.
  9. 가져오기 위한 원격 브랜치가 main인지 확인합니다.
  10. 가져온 뒤 병합될 현재 브랜치가 로컬 main인지 확인합니다.
  11. 충돌이 없으면 묶어서 바로 커밋 옵션이 보이면 체크합니다.
  12. Pull을 눌러 원격 main 내용을 로컬 main에 반영합니다.

터미널

git status --short
git switch main
git fetch --prune origin
git pull origin main

git pull은 내부적으로 fetch 후 병합을 수행하지만, 초보자 문서에서는 Sourcetree 흐름과 맞추기 위해 git fetch --prune origin으로 원격 상태를 먼저 갱신하는 방식을 함께 안내합니다.

main 이동 전에 변경 파일이 있으면 먼저 commit하거나 stash 처리합니다.

7. 브랜치 규칙

브랜치는 type/작업-내용 형식을 사용합니다. 영문 소문자와 하이픈을 사용하고, 한글과 공백은 피합니다.

작업 내용branch type예시사용 기준
새 기능featurefeature/member-login회원가입, 로그인, 검색 등 기능 추가
버그 수정fixfix/reservation-seat-duplicate오류, 검증 실패, 잘못된 응답 수정
문서 수정docsdocs/git-guideREADME, API 문서, ERD, 가이드 수정
구조 개선refactorrefactor/movie-service동작 유지, 중복 제거, 서비스 분리
테스트testtest/member-validation테스트 코드 추가/수정
설정/환경chorechore/gitignore-cleanup빌드, 설정, 폴더 정리
화면 스타일stylestyle/reservation-page기능 변화 없는 CSS, 정렬, 포맷 수정

여러 작업이 있을 때 브랜치 분리 기준

상황권장이유
로그인 기능 추가 + 로그인 테스트 추가한 브랜치 허용같은 목적의 기능과 검증이므로 하나의 PR로 리뷰하기 쉽습니다.
로그인 기능 추가 + Git 가이드 문서 수정브랜치 분리기능과 문서는 목적이 다르므로 리뷰 기준이 다릅니다.
버그 수정 + 해당 버그 재발 방지 테스트한 브랜치 허용수정의 타당성을 테스트가 설명합니다.
회원 기능 + 예매 기능 동시 수정브랜치 분리변경 범위가 커지면 리뷰와 rollback이 어려워집니다.
리팩터링 + 기능 추가가능하면 분리동작 변화와 구조 변경을 섞으면 리뷰어가 실제 변경 의도를 파악하기 어렵습니다.
판단 기준: “하나의 PR 제목으로 변경 목적을 정확히 설명할 수 있는가?”에 답하기 어렵다면 브랜치를 분리합니다. Git 공식 문서의 topic branch 설명처럼, 단일 기능 또는 관련 작업 단위로 짧게 유지하는 것이 좋습니다.

8. 브랜치 생성

Sourcetree GUI

  1. 먼저 main으로 이동하고 Fetch/Pull까지 끝났는지 확인합니다.
  2. 상단 브랜치(Branch) 버튼을 누릅니다.
  3. 새 브랜치 이름에 feature/member-login처럼 입력합니다.
  4. 기준 브랜치가 최신 main인지 확인합니다.
  5. 생성 후 새 브랜치로 바로 이동하는 옵션이 보이면 체크합니다.
  6. 생성 후 왼쪽 브랜치 목록에서 새 브랜치가 굵게 표시되거나 선택되어 있는지 확인합니다.

터미널

git switch main
git fetch --prune origin
git pull origin main
git switch -c feature/member-login

브랜치 생성 후 git branch --show-current로 현재 브랜치를 확인합니다.

9. 작업과 검증

확인 항목기준
로컬 실행수정한 화면 또는 API가 로컬에서 정상 동작하는지 확인합니다.
테스트관련 단위 테스트 또는 통합 테스트를 실행합니다.
빌드백엔드 변경이면 프로젝트 기준 빌드를 실행합니다.
변경 파일작업과 무관한 파일이 섞이지 않았는지 확인합니다.
보안.env, token, auth 파일 원문, 개인 설정 파일을 올리지 않습니다.

10. 커밋 규칙

커밋 메시지는 Conventional Commits 형식을 팀 규칙에 맞게 한국어 summary로 사용합니다.

type(scope): 한국어 요약

scope가 애매하면 생략합니다.

type: 한국어 요약
type의미사용 상황예시
feat새 기능회원가입, 로그인, 검색 등 기능 추가feat(member): 로그인 검증 로직 추가
fix버그 수정오류, 검증 실패, 잘못된 응답 수정fix(reservation): 좌석 중복 예매 검증 오류 수정
docs문서 수정README, API 문서, 가이드 수정docs(git): 브랜치 PR 협업 가이드 추가

규칙좋은 예나쁜 예
summary는 한국어fix: 예매 좌석 중복 확인 오류 수정fix: correct reservation error
마침표 생략docs: Git 협업 가이드 보완docs: Git 협업 가이드 보완.
모호한 표현 금지feat: 회원가입 입력값 검증 추가feat: 작업함
여러 목적이면 commit 분리feat(member): 로그인 추가 + docs(git): 가이드 보완feat: 이것저것 수정

Sourcetree GUI

  1. 왼쪽 파일 상태 화면을 엽니다.
  2. 변경 파일 목록에서 이번 commit에 포함할 파일만 체크합니다.
  3. 오른쪽 diff 영역에서 각 파일의 변경 내용이 의도한 작업인지 확인합니다.
  4. commit 메시지 입력칸에 type(scope): 한국어 요약을 작성합니다.
  5. 작업과 무관한 파일, 개인 설정 파일, secret 파일이 섞이지 않았는지 다시 확인합니다.
  6. Commit을 누릅니다.

터미널

git status --short
git add src/main/java/...
git commit -m "feat(member): 로그인 검증 로직 추가"

git add .는 불필요한 파일까지 포함할 수 있으므로 변경 파일을 먼저 확인합니다.

11. push 규칙

push는 자기 작업 브랜치에만 합니다. main에 직접 push하지 않습니다.

Sourcetree GUI

  1. 왼쪽 브랜치 목록에서 현재 브랜치가 main이 아니라 내 작업 브랜치인지 확인합니다.
  2. 상단 Push 버튼을 누릅니다.
  3. Push 창에서 원격 저장소가 origin인지 확인합니다.
  4. 로컬 브랜치와 원격 브랜치 이름이 내 작업 브랜치 이름과 같은지 확인합니다.
  5. main이 체크되어 있으면 체크를 해제하고, 내 작업 브랜치만 push합니다.

터미널

git branch --show-current
git push -u origin feature/member-login

두 번째 push부터는 보통 git push만으로 충분합니다.

PR 본문

GitHub Docs는 PR 본문에 목적, 변경 개요, 관련 이슈나 대화 링크 등 리뷰어가 이해할 수 있는 맥락을 제공하라고 안내합니다. 팀 문서에서는 아래 형식을 기본으로 사용합니다.

13. PR 올리기 전 최신 main 병합

PR 생성 전 또는 리뷰 반영 전, 내 작업 브랜치가 최신 main 기준인지 확인합니다.

Sourcetree GUI

  1. 먼저 작업 브랜치의 변경 파일을 확인합니다. 아직 commit하지 않은 변경이 있으면 commit하거나 stash로 임시 보관합니다.
  2. 왼쪽 브랜치 목록에서 main을 더블클릭해 이동합니다.
  3. 상단 패치(Fetch) 버튼을 누릅니다.
  4. 패치 창에서 모든 원격 저장소에서 가져오기와 리모트에서 제거된 브랜치 정리하기를 체크하고 확인을 누릅니다.
  5. 상단 Pull 버튼을 누릅니다.
  6. Pull 창에서 원격 저장소가 origin, 원격 브랜치가 main, 현재 브랜치가 로컬 main인지 확인합니다.
  7. 충돌이 없으면 묶어서 바로 커밋 옵션이 보이면 체크하고 Pull을 실행합니다.
  8. 왼쪽 브랜치 목록에서 내 작업 브랜치를 더블클릭해 다시 이동합니다.
  9. 왼쪽 main 브랜치를 우클릭하고 Merge main into current branch 또는 유사한 merge 메뉴를 선택합니다.
  10. 충돌이 없으면 테스트/빌드를 다시 실행합니다.
  11. 병합 결과 commit이 생겼거나 브랜치가 갱신되면 상단 Push로 작업 브랜치를 push합니다.

터미널

git switch main
git fetch --prune origin
git pull origin main
git switch feature/member-login
git merge main
# 테스트/빌드 후
git push

14. 다른 팀원 PR merge 전달을 받았을 때

내가 아직 작업 중인데 다른 팀원의 PR이 main에 merge되었다는 전달을 받으면, 내 변경 상태를 먼저 정리한 뒤 최신 main을 받아야 합니다.

현재 내 상태권장 처리이유
작업 파일이 아직 commit할 수준이 아님stash미완료 변경을 임시 보관하고 깨끗한 상태에서 최신 main을 받을 수 있습니다.
작업 단위가 의미 있고 테스트 전이라도 보존해야 함WIP commit 검토작업 이력을 브랜치에 남길 수 있지만, PR 전에는 메시지 정리나 추가 commit 정리가 필요할 수 있습니다.
이미 commit 완료바로 main 최신화 후 작업 브랜치에 병합내 변경이 브랜치 이력에 있으므로 merge 충돌만 확인하면 됩니다.
commit은 충돌을 없애는 기능이 아닙니다. 충돌은 최신 main을 내 작업 브랜치에 병합할 때 발생할 수 있습니다. commit은 내 변경을 이력으로 고정하는 것이고, stash는 아직 commit하지 않을 변경을 임시 보관하는 것입니다.

Sourcetree에서 stash에 넣기

stash는 아직 commit하기 애매한 작업을 잠깐 치워 두는 기능입니다. Atlassian Git Tutorial 기준으로 stash는 staged/unstaged 변경을 저장한 뒤 작업 폴더를 깨끗한 상태로 되돌립니다. 단, 새로 만든 파일은 옵션을 켜지 않으면 stash에 포함되지 않을 수 있습니다.

순서Sourcetree GUI 작업확인할 것
1왼쪽 파일 상태를 클릭합니다.아직 commit하지 않은 변경 파일이 있는지 확인합니다.
2변경 파일 목록을 봅니다.내가 임시 보관할 파일인지, 실수로 생긴 파일인지 구분합니다.
3새 파일이 있다면 파일명이 회색/물음표/추적 안 됨 상태로 보이는지 확인합니다.새 파일은 stash 옵션에 따라 포함되지 않을 수 있으므로 별도로 확인합니다.
4상단의 스태시(Stash) 버튼을 누릅니다.상단 버튼이 보이지 않으면 메뉴의 액션 또는 왼쪽 스태시 영역을 확인합니다.
5stash 이름을 입력합니다.WIP: member-login, WIP: reservation-ui처럼 나중에 알아볼 수 있게 씁니다.
6새 파일 포함 옵션이 보이면 필요한 경우 체크합니다.새로 만든 파일까지 임시 보관해야 하면 untracked/new file 포함 옵션을 켭니다.
7확인 또는 Stash를 눌러 실행합니다.실행 후 파일 상태가 깨끗해졌는지 확인합니다.
8왼쪽 스태시 목록을 확인합니다.방금 입력한 stash 이름이 목록에 보이면 정상입니다.
초보자 기준 권장: stash 이름을 비워 두지 마세요. stash가 여러 개 쌓이면 기본 이름만 보고는 어떤 작업인지 구분하기 어렵습니다.

Sourcetree에서 stash 다시 꺼내기

stash를 다시 꺼낼 때는 현재 브랜치가 맞는지 먼저 확인합니다. 다른 브랜치에서 꺼내면 예상하지 못한 파일 변경이나 충돌이 생길 수 있습니다.

순서Sourcetree GUI 작업확인할 것
1왼쪽 브랜치 목록에서 내 작업 브랜치로 이동합니다.stash를 적용할 브랜치가 맞는지 확인합니다.
2왼쪽 스태시 목록을 펼칩니다.적용할 stash 이름과 생성 시점을 확인합니다.
3적용할 stash를 선택합니다.가능하면 diff 또는 변경 파일 목록을 보고 맞는 stash인지 확인합니다.
4적용(Apply) 또는 적용 후 삭제(Pop)에 해당하는 메뉴를 선택합니다.처음에는 적용 후 목록에 남는 방식이 더 안전합니다.
5파일 상태 화면으로 이동합니다.stash에 있던 변경 파일이 다시 나타났는지 확인합니다.
6충돌 표시가 있는지 확인합니다.충돌이 있으면 바로 commit하지 말고 충돌 파일을 먼저 해결합니다.
7로컬 실행, 테스트, 빌드를 확인합니다.복원된 변경이 최신 main 위에서도 정상인지 확인합니다.
8문제가 없으면 commit합니다.복원한 변경을 작업 브랜치 이력으로 저장합니다.
9적용 후 남아 있는 stash가 더 이상 필요 없으면 삭제합니다.삭제 전 변경 내용이 commit되었는지 확인합니다.

Apply와 Pop 선택 기준

방식의미권장 상황
Applystash 내용을 작업 폴더에 적용하지만 stash 목록에는 남깁니다.초보자에게 우선 권장. 복원 중 문제가 생겨도 stash가 남아 있어 다시 시도할 수 있습니다.
Popstash 내용을 적용하고 성공하면 stash 목록에서 제거합니다.stash 내용이 확실하고 바로 정리해도 되는 경우에 사용합니다.
충돌 발생적용 중 충돌이 나면 파일을 수동으로 해결해야 합니다.Git 공식 문서 기준으로 pop 적용이 충돌로 실패하면 stash가 목록에 남을 수 있으므로, 상태를 확인한 뒤 직접 삭제합니다.

Sourcetree GUI

  1. 왼쪽 브랜치 목록에서 현재 브랜치가 내 작업 브랜치인지 확인합니다.
  2. 파일 상태 화면에서 아직 commit하지 않은 변경 파일이 있는지 확인합니다.
  3. 미완료 변경이면 상단 또는 메뉴의 스태시(Stash) 기능으로 임시 보관합니다. stash 이름에는 작업 내용을 짧게 적습니다.
  4. 새로 만든 파일까지 보관해야 하면 새 파일 포함 옵션이 있는지 확인합니다.
  5. main으로 이동합니다.
  6. 패치(Fetch)를 실행하고 모든 원격 저장소에서 가져오기, 리모트에서 제거된 브랜치 정리하기를 체크합니다.
  7. Pull을 실행합니다. 원격 저장소가 origin, 원격 브랜치가 main인지 확인합니다.
  8. 다시 내 작업 브랜치로 이동합니다.
  9. 최신 main을 현재 작업 브랜치에 merge합니다.
  10. stash한 변경이 있으면 왼쪽 스태시 목록에서 해당 stash를 선택하고 먼저 적용(Apply) 방식으로 다시 적용합니다.
  11. 충돌 여부를 확인하고, 해결 후 테스트/빌드를 실행합니다.
  12. 검증 후 commit하고 작업 브랜치를 push합니다.
  13. stash가 목록에 남아 있고 더 이상 필요 없으면 삭제합니다.

터미널

git status --short
git stash push -u -m "WIP: member-login"
git switch main
git fetch --prune origin
git pull origin main
git switch feature/member-login
git merge main
git stash apply
# 충돌 확인, 테스트/빌드 후
git add 수정한파일
git commit -m "feat(member): 작업 내용 정리"
git push

-u는 새로 만든 파일까지 stash에 포함하는 옵션입니다. git stash apply는 stash를 목록에 남깁니다. 복원과 검증이 끝난 뒤 더 이상 필요 없을 때 git stash drop을 사용합니다.

15. 내 PR merge 이후 작업자 동기화

순서작업목적
1PR이 merge되었는지 확인팀 저장소 main 반영 여부 확인
2main으로 이동최신 기준 브랜치로 이동
3main pull팀장이 merge한 내용 받기
4완료된 작업 브랜치 정리더 이상 필요 없는 브랜치 삭제
5계속 작업 중인 브랜치로 이동다음 작업 또는 이어지는 작업 진행
6작업 브랜치에 최신 main 병합다음 PR 충돌 가능성 감소
7작업 브랜치 push원격 작업 브랜치도 최신화

Sourcetree GUI

  1. GitHub에서 내 PR이 merge되었는지 먼저 확인합니다.
  2. Sourcetree에서 main 브랜치로 이동합니다.
  3. 패치(Fetch)를 실행하고 원격 상태를 갱신합니다.
  4. Pull을 실행해 팀장이 merge한 내용을 로컬 main에 반영합니다.
  5. 완료된 작업 브랜치가 필요 없으면 삭제합니다. 삭제 전 main에 merge된 PR인지 확인합니다.
  6. 계속 작업 중인 브랜치가 있으면 그 브랜치로 이동합니다.
  7. 최신 main을 현재 작업 브랜치에 merge합니다.
  8. 충돌 해결과 검증 후 작업 브랜치를 push합니다.

터미널

git switch main
git fetch --prune origin
git pull origin main
git switch feature/next-work
git merge main
# 충돌 해결과 검증 후
git push

16. 충돌 처리

상황처리 기준
같은 파일의 같은 부분 수정두 변경 중 무엇이 맞는지 확인하고 하나로 정리합니다.
내 변경과 팀 변경 모두 필요둘 다 유지되도록 코드를 수동 병합합니다.
어느 쪽이 맞는지 불명확작성자 또는 팀장에게 확인합니다.
stash 적용 중 충돌파일을 수동 해결하고 검증합니다. stash pop 실패 시 stash는 보통 목록에 남으므로 상태를 확인합니다.

Sourcetree GUI

  1. 파일 상태 화면에서 충돌 표시가 붙은 파일 목록을 확인합니다.
  2. 충돌 파일을 더블클릭하거나 외부 편집기로 열어 <<<<<<<, =======, >>>>>>> 표시를 찾습니다.
  3. 내 변경과 팀원의 변경 중 무엇을 남길지 결정하고 최종 코드만 남깁니다.
  4. 어느 쪽이 맞는지 모르겠으면 임의로 고르지 말고 팀장 또는 해당 파일 작성자에게 확인합니다.
  5. 수정한 파일을 저장한 뒤 Sourcetree로 돌아와 해결한 파일을 stage합니다.
  6. merge commit 또는 충돌 해결 commit을 완료합니다.
  7. 테스트/빌드를 다시 실행하고 문제가 없으면 push합니다.

터미널

git status --short
# 충돌 파일 수정
git add 충돌파일
git commit

merge 중인 상태라면 git commit이 merge commit을 완료합니다.

17. 브랜치 정리

PR이 merge된 작업 브랜치는 더 이상 필요 없으면 정리합니다. 단, 삭제 전 main에 merge된 것을 확인합니다.

Sourcetree GUI

  1. main으로 이동합니다.
  2. 완료된 작업 브랜치를 우클릭합니다.
  3. Delete 또는 유사한 삭제 메뉴를 선택합니다.
  4. 원격 브랜치 삭제는 팀 규칙에 따라 GitHub 또는 Sourcetree에서 처리합니다.

터미널

git switch main
git branch -d feature/member-login
# 원격 브랜치 삭제가 필요하고 팀 규칙상 허용된 경우
git push origin --delete feature/member-login

원격 브랜치 삭제는 팀 규칙에 맞게 진행합니다.

18. 자주 하는 실수

실수문제예방
main에서 직접 commit승인되지 않은 변경이 기준 브랜치에 섞입니다.작업 전 현재 브랜치를 확인합니다.
관련 없는 작업을 한 PR에 포함리뷰가 느려지고 merge 판단이 어려워집니다.단일 목적 브랜치와 PR을 사용합니다.
PR 본문 없이 제목만 작성리뷰어가 변경 이유와 검증 여부를 알기 어렵습니다.본문 템플릿을 채웁니다.
팀장 merge 후 pull 누락다음 작업이 오래된 코드 기준으로 진행됩니다.merge 알림을 받으면 main pull부터 합니다.
stash 후 복원 누락내 작업이 사라진 것처럼 보일 수 있습니다.git stash list 또는 Sourcetree stash 목록을 확인합니다.

19. 근거 자료

이 문서는 아래 자료를 조사해 팀 협업 문서용으로 재구성했습니다.

  • GitHub Docs: About branches - 브랜치를 작업 격리와 PR 병합 단위로 설명
  • GitHub Docs: Creating a pull request - base branch, compare/head branch, PR 제목/본문 입력 흐름 확인
  • GitHub Docs: Helping others review your changes - 작고 단일 목적의 PR, 명확한 제목과 설명, 자체 리뷰/테스트 권장 기준 확인
  • Conventional Commits 1.0.0 - type(scope): description, feat, fix, optional scope 구조 확인
  • Pro Git: Branching Workflows - topic branch를 단일 기능 또는 관련 작업 단위로 사용하는 기준 확인
  • Atlassian Git Tutorial: Git stash - stash가 staged/unstaged 변경을 임시 저장하고 작업 폴더를 깨끗하게 만드는 동작, untracked 파일 포함 옵션 확인
  • Git documentation: git-stash - stash push/apply/pop 동작과 충돌 가능성 확인
