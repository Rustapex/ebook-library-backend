## 발표 전 확인 사항

이 대본은 화면의 문구를 순서대로 읽기보다, 해당 내용을 넣은 이유와 구현 방법, 실제 이용자와 운영자에게 생기는 결과를 설명하도록 작성했다.

같은 사실을 여러 번 설명하지 않도록 역할을 분리했다. 서비스 정의는 5번, 검증 방법은 11번, 전체 기능 범위는 17번에서만 설명한다. 18·19번은 사용자 또는 관리자 흐름 중 한 장만 선택하고, 20~25번에서는 17번에 나온 기능을 다시 나열하지 않고 각 화면의 대표 처리 방식만 설명한다. 26번에서는 시연 순서를 미리 읽지 않고 바로 시연을 시작한다.

발표에서 다음 사항을 과장하지 않는다.

- 모든 API를 같은 수준으로 Swagger·Postman 검증했다고 말하지 않는다. 자동 테스트는 공통적으로 사용했지만, 수동 검증 완료 범위는 도메인마다 다르다.
- 추천 기능은 같은 저자·카테고리·키워드 중 요청한 한 가지 기준으로 후보를 찾고, 대여 수·평점·등록일로 정렬한다. 세 유사도를 합산하거나 AI로 개인화한 추천이라고 표현하지 않는다.
- 출석 일수만으로 특정 쿠폰이 자동 발급된다고 단정하지 않는다. 쿠폰은 보상 조건이 정의된 챌린지를 중심으로 설명한다.
- 관리자 카테고리 API처럼 최종 구현 범위에서 제외한 기능도 있으므로, 화면의 모든 메뉴가 동일한 수준으로 구현됐다고 말하지 않는다.

현재 Canva에는 개인 자체 평가 및 소감의 별도 표지가 없다. 26번 시연 다음에 27번 두 명의 회고, 28번 세 명의 회고, 29번 감사 인사가 이어진다. 27번 김재민 항목에는 ABC와 무관한 식재료·레시피·거래·채팅 기능이 섞여 있어 대본에 반영하지 않았고, 로컬 소스에서 확인한 결제 처리 사례를 기준으로 작성했다.

## 슬라이드 17. 핵심 사용자 여정과 전체 기능

**권장 시간: 1분 40초**

회원 영역에서는 일반 회원가입과 로그인을 제공하고, Google 인증은 백엔드 처리 흐름까지 구현했습니다. 도서 탐색 영역에는 컬렉션, 카테고리 검색, 조건별 정렬, 상세 정보, 찜과 관련 도서가 있습니다. 여기서 컬렉션은 사용자가 만드는 개인 책장이 아니라 운영자가 여러 도서를 하나의 주제로 묶어 보여주는 단위입니다. 읽는 순서가 있는 시리즈와 기간이나 할인 정보를 함께 설정할 수 있는 이벤트 기획전으로 구분하고, 현재 공개 상태인 묶음과 그 안의 도서만 사용자에게 제공합니다.

대여 영역에서는 무료 도서를 바로 대여하고, 유료 도서는 쿠폰과 포인트를 적용해 서비스 내부 결제 내역과 대여를 하나의 트랜잭션으로 생성합니다. 열람 영역에서는 EPUB 파일과 읽던 위치, 진행률, 북마크를 관리합니다. 지역별 종이책 소장 도서관 조회는 ISBN과 지역 코드를 정보나루에 전달하는 백엔드 API까지 구현했으며, 지도 화면 연결까지 완료한 기능으로 설명하지는 않겠습니다.

알림과 공지는 전달 대상과 저장 목적이 달라서 분리했습니다. 알림은 대여 시작, 결제 완료, 희망도서와 신고 처리 결과처럼 특정 회원에게 생긴 일을 알려주는 기록입니다. 따라서 알림 유형과 이동할 대상, 회원별 읽음 여부와 읽은 시각을 저장합니다. 공지는 모든 사용자가 같은 제목과 본문을 읽는 게시물이므로 공개 여부와 작성·수정 시각을 중심으로 관리합니다. 관리자가 공지를 등록할 때 알림 발송을 선택하면 공지 본문을 회원마다 복사하는 대신, 각 회원에게 해당 공지로 이동하는 `NOTICE` 알림만 생성합니다.

이 밖에도 리뷰, 출석, 챌린지 보상, 포인트·쿠폰, 희망도서 신청과 개인 통계를 제공하며, 관리자는 회원·도서·컬렉션·희망도서·공지·쿠폰·챌린지와 통계·감사 로그를 관리합니다. 대여·결제 조회와 신고 처리는 백엔드 API까지 구현했지만, 사용자 신고 접수와 해당 관리자 화면의 프런트 호출은 최종 연동 범위에 포함되지 않았습니다.

## 슬라이드 23. 뷰어 페이지

**권장 시간: 1분**

그래서 CFI에는 EPUB 본문 안에서 마지막으로 읽던 문장이나 글자의 위치를 가리키는 주소를 저장합니다. 장 정보에는 어떤 파일을 읽고 있었는지를, 스파인 위치에는 그 장이 책의 읽기 순서에서 몇 번째인지를 저장합니다. 진행률은 책 전체에서 어느 정도 읽었는지를 0부터 100퍼센트에 해당하는 값으로 기록합니다. 이 정보를 함께 사용하면 화면 크기가 달라져도 마지막으로 읽던 부분을 더 정확하게 복원할 수 있습니다.

여러 창에서 저장 요청이 겹칠 때는 오래된 위치가 최신 진도를 덮지 않도록 수정 버전을 비교하고, 충돌한 요청은 최신 정보를 다시 조회하게 했습니다. 북마크도 EPUB 파일의 버전과 함께 관리해 파일이 교체된 뒤 이전 파일의 잘못된 위치를 그대로 열지 않도록 했습니다.

## 발표자용 최종 점검표

- 18번 사용자 흐름과 19번 관리자 흐름 중 실제 발표에서는 한 장과 해당 대본 하나만 사용한다.
- 27번 김재민의 Canva 내용에서 ABC와 무관한 식재료·레시피·거래·채팅 문구를 실제 담당 내용으로 교체했는지 확인한다.
- 모든 API를 Swagger·Postman으로 검증했다는 표현을 사용하지 않는다. 자동 테스트, 수동 검증, 정적 연동 확인의 범위를 구분한다.
- Google 로그인은 백엔드 인증 흐름까지, 주변 도서관 조회는 백엔드 조회까지 구현했다고 범위를 구분한다.
- 사용자 신고 접수와 관리자 대여·결제·신고 화면을 최종 연동 기능으로 소개하지 않는다.
- 결제는 외부 결제사 연동이 아니라 서비스 내부 금액 계산과 결제 내역 저장이라고 설명한다.
- GitHub Actions 배포는 백엔드 범위라고 설명한다.
- 시연 순서를 26번에서 다시 읽지 않는다. 로그인과 데이터 준비, 쿠폰·포인트·대여·진도 초기 상태는 발표 전에만 점검한다.
- 챌린지는 당일 데이터 상태가 불안정하면 라이브 시연에서 제외하고 구현 설명만 진행한다.
- 화면 전환 중 같은 기능을 다시 설명하지 않는다. 17번은 기능 범위, 18·19번은 선택한 전체 흐름, 20~25번은 대표 처리 방식, 26번은 시연 시작이라는 역할을 유지한다.
