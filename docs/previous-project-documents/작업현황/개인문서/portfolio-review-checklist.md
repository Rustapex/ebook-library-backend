# 프로젝트 포트폴리오 리뷰 기준표

## 1. 문서 목적

이 문서는 회사 제출용 프로젝트 포트폴리오가 충분히 설득력 있는지 평가하기 위한 기준표다.

평가 기준은 디자인이나 보기 좋은 구성보다 아래 항목에 둔다.

- 프로젝트가 무엇인지 빠르게 이해되는가
- 본인이 맡은 역할이 명확한가
- 단순 기능 나열이 아니라 문제 해결 과정이 보이는가
- 기술 선택 이유와 구현 근거가 있는가
- API, DB, 테스트, 문서화, 협업 경험이 확인되는가
- 면접에서 본인이 설명할 수 있는 내용인가
- 팀 전체 성과와 본인 성과가 구분되어 있는가

---

## 2. 평가 방식

각 항목은 0점부터 5점까지 평가한다.

| 점수 | 기준 |
|---:|---|
| 0점 | 내용이 없음 |
| 1점 | 언급은 있으나 매우 부족함 |
| 2점 | 기본 내용은 있으나 구체성이 부족함 |
| 3점 | 일반적인 포트폴리오 수준 |
| 4점 | 구체적이고 면접 질문으로 이어질 수 있음 |
| 5점 | 근거, 맥락, 본인 기여, 검증까지 명확함 |

총 10개 항목을 평가한다.

```text
총점 = 각 항목 점수 합계
만점 = 50점
100점 환산 = 총점 × 2
```

# 4. 세부 평가 기준

---

## 1. 프로젝트 개요와 한 줄 설명

### 확인할 내용

- 프로젝트 이름이 있는가?
- 한 줄 소개가 있는가?
- 어떤 사용자를 위한 서비스인지 보이는가?
- 핵심 기능이 짧게 설명되어 있는가?
- 사용 기술이 프로젝트 목적과 연결되어 있는가?
- 첫 문단만 읽어도 프로젝트 성격을 이해할 수 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 프로젝트 개요가 없거나 제목만 있다. |
| 1점 | 설명은 있지만 “웹 서비스”, “관리자 페이지”처럼 너무 모호하다. |
| 2점 | 서비스 종류는 알 수 있지만 사용자, 목적, 핵심 기능이 부족하다. |
| 3점 | 프로젝트 목적과 주요 기능이 일반적인 수준으로 설명되어 있다. |
| 4점 | 서비스 대상, 핵심 기능, 기술 방향이 짧고 명확하다. |
| 5점 | 한 줄 소개만으로 도메인, 사용자, 핵심 문제, 본인 역할 방향이 이해된다. |

---

## 2. 문제 정의와 서비스 맥락

### 확인할 내용

- 왜 이 프로젝트가 필요한지 설명되어 있는가?
- 사용자 기능과 관리자 기능의 목적이 구분되어 있는가?
- 기능을 만든 배경이나 요구사항이 있는가?
- 서비스 운영 정책이나 제약 조건이 드러나는가?
- 단순 CRUD가 아니라 실제 서비스 흐름을 고려했는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 문제 정의가 전혀 없다. |
| 1점 | “전자책을 빌릴 수 있게 만들었다”처럼 기능 설명만 있다. |
| 2점 | 주요 기능은 보이지만 왜 필요한지 설명이 약하다. |
| 3점 | 주요 요구사항과 기능 목적이 설명되어 있다. |
| 4점 | 사용자, 관리자, 운영 정책, DB 제약이 어느 정도 연결되어 있다. |
| 5점 | 기능별 문제, 제약, 해결 방향이 명확해 요구사항을 해석한 개발자로 보인다. |

---

## 3. 본인 담당 범위와 기여도

### 확인할 내용

- 팀 규모와 역할 분담이 적혀 있는가?
- 본인이 맡은 도메인이 명확한가?
- 직접 구현한 API, 화면, DB, 테스트 범위가 구분되어 있는가?
- 팀원이 한 작업과 본인이 한 작업이 섞이지 않았는가?
- “참여”, “담당”, “구현”, “검증”, “리뷰 대응”이 구분되어 있는가?
- 본인이 설명 가능한 범위만 적었는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 본인 담당 부분이 전혀 없다. |
| 1점 | “백엔드 담당”, “관리자 기능 담당”처럼 두루뭉술하다. |
| 2점 | 담당 도메인은 있으나 어떤 API, DB, 예외, 테스트를 맡았는지 불명확하다. |
| 3점 | 맡은 기능 목록은 있고 어느 정도 구체적이다. |
| 4점 | 담당 도메인, 구현 API, 관련 DB, 검증 방식, 문서 작업이 구분되어 있다. |
| 5점 | 팀 전체 구조 속에서 본인 책임, 직접 구현 범위, 수정 범위, 검증 범위가 근거와 함께 명확하다. |

---

## 4. 핵심 구현 사례의 기술적 깊이

### 확인할 내용

- 핵심 구현 사례가 3~5개로 압축되어 있는가?
- 각 사례에 문제, 원인, 해결, 검증 흐름이 있는가?
- 단순 기능 설명이 아니라 기술적 고민이 보이는가?
- 상태 관리, 예외 처리, 정렬, 페이징, 멱등성, 동시성 같은 구현 포인트가 있는가?
- 코드, DB, API, 비즈니스 규칙이 연결되어 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 구현 사례가 없다. |
| 1점 | “회원 API 구현”, “도서 API 구현”처럼 기능명만 나열되어 있다. |
| 2점 | 기능 설명은 있지만 기술적으로 무엇을 고민했는지 부족하다. |
| 3점 | 대표 기능의 구현 방식이 설명되어 있다. |
| 4점 | 상태 관리, 예외 처리, DB 조회 방식, 트랜잭션, 테스트 등 기술 포인트가 드러난다. |
| 5점 | 문제의 원인, 선택한 해결책, 대안 대비 이유, 검증 방법까지 설명되어 면접 질문에 바로 연결된다. |

---

## 5. 설계 선택 이유와 트레이드오프

### 확인할 내용

- 기술이나 구현 방식을 선택한 이유가 있는가?
- 다른 대안과 비교한 내용이 있는가?
- 선택한 방식의 장점과 한계를 설명하는가?
- 비즈니스 요구사항과 설계가 연결되어 있는가?
- “사용했다”가 아니라 “이 문제 때문에 선택했다”로 설명되어 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 설계 선택 이유가 없다. |
| 1점 | 사용 기술만 나열되어 있다. |
| 2점 | 기술을 사용한 이유가 있지만 “편해서”, “많이 써서” 수준이다. |
| 3점 | 특정 기능에서 왜 해당 방식을 택했는지 설명한다. |
| 4점 | 대안, 제약, 장단점이 함께 설명된다. |
| 5점 | 설계 선택이 요구사항, 운영 정책, DB 구조, 검증 방식과 연결되어 있고 한계도 정직하게 설명한다. |

---

## 6. API, DB, 테스트 검증 근거

### 확인할 내용

- API 명세 링크 또는 요약이 있는가?
- Swagger 또는 Postman 검증 내용이 있는가?
- DB 변경 확인 결과가 있는가?
- 정상 케이스와 실패 케이스가 모두 검증되어 있는가?
- 테스트 코드 또는 테스트 문서가 있는가?
- 시연 화면, 스크린샷, GIF, 영상, 배포 링크 중 하나 이상이 있는가?
- “테스트했다”가 아니라 “무엇을 어떻게 확인했다”로 설명되어 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 검증 자료가 없다. |
| 1점 | “테스트했습니다”라고만 되어 있다. |
| 2점 | Swagger, Postman, DB 확인 중 일부만 언급되어 있고 구체적 결과가 없다. |
| 3점 | 주요 API의 정상 동작 검증이 설명되어 있다. |
| 4점 | 정상/실패 케이스, DB 상태 확인, API 응답 예시가 연결되어 있다. |
| 5점 | 기능별 검증 근거가 명확하고, 시연/문서/테스트/PR 리뷰 대응까지 추적 가능하다. |

---

## 7. 결과, 개선 효과, 한계

### 확인할 내용

- 구현 결과가 있는가?
- 개선 전/후가 설명되어 있는가?
- 구체적 근거가 있는가?
- 한계가 정직하게 적혀 있는가?
- 다음 개선 방향이 현실적인가?
- 배운 점이 단순 감상이 아니라 기술, 협업, 검증과 연결되어 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 결과나 회고가 없다. |
| 1점 | “많이 배웠습니다”, “성장했습니다” 수준의 감상만 있다. |
| 2점 | 결과는 있지만 구체적 근거가 부족하다. |
| 3점 | 구현 결과와 배운 점이 설명되어 있다. |
| 4점 | 개선 전/후, 한계, 다음 개선 계획이 구체적이다. |
| 5점 | 결과가 문제 정의와 연결되고, 검증 근거와 회고까지 이어진다. 과장 없이 설득력 있다. |

## 8. GitHub, README, 문서화 품질

### 확인할 내용

- README가 있는가?
- 프로젝트 설명, 기술스택, 실행 방법, 주요 기능이 정리되어 있는가?
- API 명세나 ERD 문서 링크가 있는가?
- 스크린샷, 시연 이미지, 영상 링크가 있는가?
- 이미지 경로가 깨지지 않는가?
- GitHub repository description이나 topics가 정리되어 있는가?
- 민감정보가 올라가 있지 않은가?
- 다른 사람이 프로젝트 구조를 이해할 수 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | GitHub 링크나 README가 없다. |
| 1점 | README가 있지만 거의 비어 있거나 자동 생성 수준이다. |
| 2점 | 프로젝트 설명은 있으나 실행 방법, 주요 기능, 스크린샷, 문서 링크가 부족하다. |
| 3점 | README와 기본 문서가 있고 프로젝트 이해가 가능하다. |
| 4점 | README, API 문서, ERD, 실행 방법, 스크린샷/시연 자료가 연결되어 있다. |
| 5점 | GitHub만 봐도 프로젝트 목적, 실행, 구조, 주요 기능, 검증 근거, 문서 링크를 따라갈 수 있다. |

## 9. 이력서/ATS 관점의 표현 품질

### 확인할 내용

- 문장이 너무 길지 않은가?
- “담당했습니다”, “구현했습니다”만 반복하지 않는가?
- 기술 키워드가 자연스럽게 포함되어 있는가?
- 기술 키워드가 단순 나열이 아니라 기능 설명과 연결되어 있는가?
- 표, 목록, 문단 구분이 읽기 쉬운가?
- 불필요한 감상문이 없는가?
- 맞춤법과 용어가 일관적인가?
- 이력서에 옮겨도 어색하지 않은 문장이 있는가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 읽기 어렵고 문서 구조가 없다. |
| 1점 | 문장은 있으나 너무 장황하거나 감상문에 가깝다. |
| 2점 | 기본 구조는 있지만 핵심 키워드와 역할 표현이 약하다. |
| 3점 | 읽을 수 있는 수준이며 주요 기술과 역할이 보인다. |
| 4점 | 문장이 간결하고 기술 키워드가 기능과 잘 연결되어 있다. |
| 5점 | 채용 담당자와 기술 면접관 모두 빠르게 이해할 수 있고, 문장 단위로 이력서에 옮기기 좋다. |

## 10. 정직성, 면접 방어 가능성

### 확인할 내용

- 본인이 직접 설명할 수 있는 내용만 적었는가?
- 팀 전체 성과와 본인 성과를 구분했는가?
- 수치를 지어내지 않았는가?
- 모르는 기술을 깊게 아는 것처럼 쓰지 않았는가?
- 한계와 미완성 부분을 숨기지 않았는가?
- 질문이 들어왔을 때 코드, 문서, 테스트 결과로 설명 가능한가?

### 점수 기준

| 점수 | 기준 |
|---:|---|
| 0점 | 과장, 모호한 표현, 본인 기여 불명확성이 심하다. |
| 1점 | 본인 작업과 팀 작업이 섞여 있어 신뢰하기 어렵다. |
| 2점 | 대체로 사실 기반이지만 설명 가능한 범위가 불명확하다. |
| 3점 | 본인 담당 범위는 구분되어 있고 면접 대응이 가능하다. |
| 4점 | 구현 이유, 한계, 검증 방식까지 설명 가능해 보인다. |
| 5점 | 문서 자체가 면접 질문 흐름을 만들고, 질문이 들어와도 근거를 들어 설명할 수 있다. |
