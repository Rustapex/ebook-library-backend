# K05. 설계·구현 차이와 미구현

## 도메인 1. 현재 차이 요약

### 질문 유형 1. 현재 상태표

#### [기본][현재 상태] Q. 설계와 현재 구현이 다른 항목을 한눈에 정리하면 무엇인가요?

**짧은 답변:** 사용자 신고와 일부 관리자 기능은 미구현 또는 부분 구현이고, 뷰어는 초기 API 명세와 다른 계약으로 구현됐습니다. Google 로그인과 외부 도서 수집은 코드 구현과 운영 활성화를 구분해야 합니다.

**상세 답변:** 아래 표는 `구현되지 않음`, `부분 구현`, `최종 범위 제외`, `설계와 다르게 구현`, `설정상 비활성 가능`을 구분한 현재 기준표입니다. 화면이나 문서가 존재한다는 이유만으로 완료 처리하지 않고, 현재 Backend 처리 경로와 Front 호출을 기준으로 분류했습니다.

| 영역 | 현재 로컬 상태 | 분류 | 발표·답변 표현 |
|---|---|---|---|
| 사용자 책·리뷰 신고, 내 신고 조회 | Backend endpoint 없음 | 구현되지 않음 | 관리자 신고 처리와 사용자 신고 제출을 분리해 설명 |
| 기존 `API-VIEWER-001` | 명세 URL과 현재 EPUB 구현이 다름 | 설계와 다르게 구현 | 뷰어 기능은 `/viewer`, `/epub`, 진행·북마크 경로로 구현됐다고 설명 |
| 관리자 카테고리 API | 구현하지 않기로 확정 | 최종 범위 제외 | 화면이 있어도 운영 가능 기능으로 말하지 않음 |
| 관리자 도서관 관리 | Front A-015 UI는 있으나 Backend Admin Controller 없음 | 부분 구현 | 사용자 도서관 조회와 관리자 도서관 CRUD를 구분 |
| 7일·30일 출석 쿠폰 자동 지급 | TODO로 보류 | 부분 구현 | 출석·연속일수·챌린지 갱신까지만 구현 |
| 외부 PG 승인·취소·환불 | 없음 | 최종 범위 밖 | 서비스 내부 유료 대여 결제 기록으로 설명 |
| Google 로그인 | Backend·Front 코드 연결, Backend 기본 비활성 | 설정상 비활성 가능 | 코드 구현과 배포 활성화를 구분 |
| 외부 도서 메타데이터 | 구현됐으나 기본 비활성 | 설정상 비활성 가능 | 활성화·키가 있는 환경에서만 실제 호출 |
| 모니터링 | CI/CD·smoke는 있으나 애플리케이션 관측 체계는 추가 확인 필요 | 운영 보완 | 장애·성능 모니터링을 개선 과제로 설명 |

## 도메인 2. 설계에는 있으나 구현되지 않은 기능

### 질문 유형 1. 사용자 신고

#### [압박][구현되지 않음] Q. 신고 관리 화면이 있는데 사용자는 어떻게 신고를 생성하나요?

**짧은 답변:** 현재 Backend에는 관리자 신고 조회·처리 경로는 있지만 사용자 책 신고, 리뷰 신고, 내 신고 조회 endpoint가 없습니다. 따라서 사용자 신고 기능 전체가 완성됐다고 말할 수 없습니다.

**상세 답변:** Front에 신고 모달이나 내 신고 화면이 있어도 실제 Backend 저장 경로가 없으면 운영 기능이 아닙니다. 현재는 관리자 처리 구조와 DB 테이블·테스트를 설명할 수 있고, 사용자 생성 API는 후속 구현 대상입니다.

**근거:** 프로젝트현황의 `API-REPORT-001`, `002`, `004`, 현재 Controller 목록

### 질문 유형 2. 관리자 도서관

#### [압박][부분 구현] Q. 관리자 도서관 위치 관리도 구현됐나요?

**짧은 답변:** Front A-015 화면과 API wrapper 계획은 있지만 현재 Backend에는 `/api/v1/admin/libraries` Controller가 없습니다. 실제 등록·수정·보유 도서 저장은 운영 가능 상태가 아닙니다.

**상세 답변:** 사용자용 `/api/v1/books/{bookId}/libraries` 조회는 구현·연동돼 있지만 관리자 CRUD와는 다른 기능입니다. 둘을 합쳐 “도서관 관리 완료”라고 표현하지 않습니다.

**근거:** Front A-015, Backend `library` 패키지와 Controller 목록

## 도메인 3. 최종 범위 제외

### 질문 유형 1. 관리자 카테고리

#### [심화][최종 범위 제외] Q. 관리자 카테고리 화면은 있는데 왜 API가 없나요?

**짧은 답변:** `API-ADMIN-CATEGORY-001`, `002`는 최종 구현 범위에서 제외하기로 확정했습니다. 화면 존재와 실제 저장 기능을 구분해야 합니다.

**상세 답변:** 사용자 카테고리 조회는 동작하지만 관리자 카테고리 목록·수정은 별도 API입니다. 일정 안에서 핵심 대여·열람과 운영 우선순위를 맞추기 위해 제외됐으며, 이후 구현하려면 계층 변경이 기존 도서 분류와 검색에 미치는 영향도 설계해야 합니다.

**근거:** 프로젝트현황 1장·4.4·6장

### 질문 유형 2. 반납·연체

#### [심화][최종 범위 제외] Q. 전자책 대여인데 반납과 연체가 없는 이유는 무엇인가요?

**짧은 답변:** 최종 서비스 정책에서 반납·연체·연체료를 제외하고 대여 종료 시각과 `READY`, `READING`, `OWNED` 상태로 범위를 단순화했습니다.

**상세 답변:** 기간제 전자책은 종료 시각 이후 열람을 막을 수 있어 물리적 반납 흐름을 필수로 두지 않았습니다. 대신 대여 권한 검증이 실제 종료 시각을 확인해야 합니다.

**근거:** `api-spec(final).md` 제외 API, `RentalService`

### 질문 유형 3. 결제 취소·환불

#### [심화][최종 범위 제외] Q. 결제 취소와 환불은 왜 구현하지 않았나요?

**짧은 답변:** 외부 PG와 결제 상태 전이·환불 이력까지 포함하면 별도의 핵심 도메인이 되므로 이번 범위에서는 완료 결제 저장과 조회에 집중했습니다.

**상세 답변:** 실제 확장 시에는 승인 전·후, 실패, 취소 요청, 부분 환불, 포인트·쿠폰 복구, 중복 웹훅을 설계해야 합니다. 현재 `PAYMENT`를 실제 PG 결제로 과장하지 않습니다.

## 도메인 4. 설계와 다른 구현

### 질문 유형 1. 뷰어 API

#### [압박][설계와 다르게 구현] Q. `API-VIEWER-001`이 미구현이면 뷰어도 없는 것 아닌가요?

**짧은 답변:** 뷰어 기능이 없는 것이 아니라 기존 명세 URL 대신 EPUB 중심 endpoint로 전환됐습니다. 세션 조회, EPUB binary 제공, 진도와 북마크 API는 현재 구현돼 있습니다.

**상세 답변:** 현황표에서 `API-VIEWER-001`을 X로 둔 이유는 특정 API ID와 URL의 불일치입니다. 기능 구현률과 명세 일치율을 구분해야 합니다. 명세 개정이나 새 API ID 부여가 필요합니다.

**근거:** `ViewerController`, `BookmarkController`, 프로젝트현황 3.4·6장

### 질문 유형 2. 페이지 기준

#### [심화][설계와 다르게 구현] Q. 명세 예시와 실제 페이지 번호가 다른 이유는 무엇인가요?

**짧은 답변:** 일부 명세 예시는 1 기반이지만 실제 Spring Controller·PageRequest는 0 기반입니다. 현재 Front는 UI 페이지와 API 페이지를 변환하는 방식이 안전합니다.

**개선:** 최종 API 명세의 paging 기본값과 예시를 현재 구현에 맞게 통일해야 합니다.

## 도메인 5. 부분 구현과 정책 미완성

### 질문 유형 1. 출석 보상

#### [압박][부분 구현] Q. 출석 응답에 발급 쿠폰이 있는데 실제 쿠폰은 왜 없나요?

**짧은 답변:** 응답 구조는 발급 결과를 담을 수 있지만 현재 7일·30일 쿠폰 자동 발급은 구현하지 않았습니다. 출석 기록·연속 일수와 챌린지 진행 갱신까지만 동작합니다.

**상세 답변:** 출석 전용 쿠폰을 안정적으로 식별할 컬럼·정책과 중복 지급 기준이 없어 보류했습니다. 빈 목록을 반환할 수 있는 응답이 있다고 기능이 구현된 것은 아닙니다.

**근거:** `AttendanceService`

### 질문 유형 2. Google 배포 상태

#### [압박][설정상 비활성 가능] Q. Google 로그인 버튼과 코드가 있으면 실제 서비스에서도 되나요?

**짧은 답변:** 코드 연결은 확인됐지만 Backend 기본값은 `GOOGLE_AUTH_ENABLED=false`입니다. 배포 환경 변수와 Front Google Client ID가 올바르게 주입돼야 실제로 사용할 수 있습니다.

**상세 답변:** Front 최신 커밋은 Google Client ID build 주입을 보완했습니다. 이번 조사에서는 배포 로그인 시나리오를 실행하지 않았으므로 현재 운영 성공까지 단정하지 않습니다.

**근거:** Backend `application*.properties`, Front 최신 커밋과 LoginPage

### 질문 유형 3. 외부 도서 API

#### [심화][설정상 비활성 가능] Q. 외부 도서 API를 사용했다고 발표해도 되나요?

**짧은 답변:** 연동 코드와 관리자 수집·승인 흐름을 구현했다고 말할 수 있습니다. 하지만 기본 비활성이고 이번 조사에서 배포 호출을 확인하지 않았으므로 “현재 운영에서 항상 외부 데이터를 가져온다”고 말하면 안 됩니다.

**근거:** `external.book.enabled=false`, external book 패키지

## 도메인 6. 과거 차이에서 현재 해결된 항목

### 질문 유형 1. 도서관 Front 계약

#### [최신 소스 확인] Q. 도서관 조회는 아직 Front와 계약이 다른가요?

**짧은 답변:** 과거 현황 문서에는 불일치로 남아 있지만 현재 로컬 Front는 `region`을 필수로 전달하고 Backend의 객체형 페이지 응답을 사용합니다.

**근거:** Front `libraryApi.ts`, `U024Libraries/BookLibrariesPage.tsx`, `types/api.ts`

### 질문 유형 2. 관리자 대여·결제·신고 Front 연결

#### [최신 소스 확인] Q. 관리자 대여·결제·신고는 Backend만 구현된 상태인가요?

**짧은 답변:** 과거 프로젝트현황에는 Front 미연동으로 기록돼 있지만 현재 로컬 Front의 A-008·A-009·A-010 페이지는 실제 API wrapper를 호출합니다.

**상세 답변:** 정적 소스상 연결은 확인됐습니다. 이번 조사에서 실제 관리자 로그인·HTTP 응답까지 실행하지 않았으므로 `구현·연동 확인`, `실행 확인 필요`로 표현합니다.

**근거:** Front `adminRentalApi.ts`, `adminPaymentApi.ts`, `adminReportApi.ts`와 각 페이지 호출부

### 질문 유형 3. Front CI/CD

#### [최신 소스 확인] Q. Front는 아직 수동으로 파일을 올려 배포하나요?

**짧은 답변:** 아닙니다. 현재 Front에는 CI와 Production CD workflow가 있습니다. PR·main push에서 CI를 수행하고 Production 변경은 승인 성격의 수동 workflow dispatch로 실행합니다.

**근거:** Front `.github/workflows/frontend-ci.yml`, `frontend-cd.yml`, `docs/배포/CI-CD_운영.md`

## 도메인 7. 문서 충돌 대응

### 질문 유형 1. 어떤 문서를 믿을 것인가

#### [압박][문서 원칙] Q. 문서마다 구현 여부가 다른데 어느 것이 맞나요?

**짧은 답변:** 시점과 용도를 확인합니다. 실제 동작은 현재 소스와 런타임 스키마를 우선하고, 프로젝트현황은 작성 당시의 정적 스냅샷, 화면 문서는 설계 의도와 과거 상태로 사용합니다.

**상세 답변:** 충돌을 조용히 하나로 합치지 않고 `과거 상태`, `현재 소스`, `실행 확인 여부`를 나눕니다. 이 매뉴얼도 기준 커밋을 기록해 이후 변경 시 판단 기준을 남깁니다.

### 질문 유형 2. 발표 표현

#### [기본][문서 원칙] Q. 구현 상태가 애매할 때 발표에서 어떻게 말해야 하나요?

**짧은 답변:** “구현했습니다” 하나로 합치지 말고 “Backend와 Front 호출부는 구현돼 있고 실제 배포 실행은 추가 확인이 필요합니다”처럼 확인 수준을 그대로 말합니다.

**금지 표현 예시:**

- 화면만 있는데 “기능 완성”
- 내부 결제 기록을 “PG 결제 구현”
- 규칙 기반 추천을 “AI 추천”
- 반복 요청 검증을 “동시 부하 테스트 완료”
- 기본 비활성 외부 연동을 “운영 중 사용”
