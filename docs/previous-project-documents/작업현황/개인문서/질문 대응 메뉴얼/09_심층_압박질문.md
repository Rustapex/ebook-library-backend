## 도메인 1. 독서 보상

### 질문 유형 1. 전체 실행 경로

#### [심층][구현 확인] Q. 보상 수령 요청이 들어오면 Controller부터 DB까지 어떤 순서로 동작하나요?

**짧은 답변:** 로그인 회원과 보상 대상을 확인하고, 수령 시점의 최신 독서 기록으로 조건을 다시 계산한 뒤, 미수령 조건을 만족하는 행만 갱신하고 보상을 지급합니다.

**상세 답변:** 화면에서 달성으로 보였다는 사실을 신뢰하지 않고 서버가 현재 조건을 계산합니다. 이후 `reward_claimed_at IS NULL` 조건의 갱신 결과로 중복 수령을 차단하며, 수령 상태와 보상 지급을 같은 트랜잭션에 둡니다. 구체 클래스와 SQL은 질문 시 현재 Challenge reward Service·Repository를 열어 설명합니다.

**근거:** Challenge reward Controller·Service·Repository·test, 독서보상 포트폴리오 초안

### 질문 유형 2. 동시 요청

#### [압박][구현 확인] Q. 같은 보상을 동시에 두 번 요청하면 왜 한 번만 지급되나요?

**짧은 답변:** 먼저 조회했다는 사실이 아니라 DB의 조건부 갱신 성공 여부를 지급 권한으로 사용하기 때문입니다.

**상세 답변:** 두 요청이 모두 수령 전 상태를 읽을 가능성은 있습니다. 그러나 `reward_claimed_at`이 비어 있을 때만 바꾸는 갱신은 한 요청만 성공할 수 있고, 실패한 요청은 이미 처리된 요청으로 판단합니다. 지급까지 같은 트랜잭션이므로 상태만 바뀌거나 보상만 지급되는 중간 결과를 줄입니다.

### 질문 유형 3. 조건 변경

#### [압박][정책 확인] Q. 달성 후 기준이 바뀌면 과거 달성자는 어떤 기준으로 보상을 받나요?

**짧은 답변:** 현재 구현은 수령 시점의 최신 조건을 적용합니다.

**상세 답변:** 이 정책은 단순하지만 달성 당시 기준을 보존하지 않으므로 기준이 강화되면 사용자가 불리해질 수 있습니다. 운영 요구가 과거 기준 보장이라면 challenge version이나 달성 snapshot을 저장하는 설계가 필요합니다.

### 질문 유형 4. 출석 보상

#### [압박][현재 한계] Q. 7일·30일 출석 쿠폰도 완성됐나요?

**짧은 답변:** 출석과 포인트 관련 기능은 있지만, 7일·30일 쿠폰 발급은 현재 TODO가 남아 있어 완료됐다고 말하지 않습니다.

**근거:** Attendance Service의 TODO, `05_설계구현차이_미구현.md`

## 도메인 2. 대여·결제

### 질문 유형 1. 유료 대여 트랜잭션

#### [심층][구현 확인] Q. 유료 도서를 대여할 때 어떤 데이터가 함께 변경되나요?

**짧은 답변:** 대여와 결제 기록을 만들고, 사용한 쿠폰과 포인트 내역을 반영하며, 결과 알림까지 같은 업무 흐름에서 처리합니다.

**상세 답변:** 금액과 할인 조건을 서버에서 다시 확인한 후 대여를 생성합니다. 쿠폰을 사용했다면 사용 상태를, 포인트를 사용했다면 잔액과 이력을 반영하고 결제 기록과 알림을 남깁니다. 각 단계가 분리 저장되면 부분 성공이 생길 수 있어 Service 트랜잭션 경계를 사용합니다.

**근거:** Rental·Payment·Coupon·Point·Notification 관련 Service와 schema

### 질문 유형 2. 0원 결제

#### [압박][정책 확인] Q. 쿠폰과 포인트로 최종 금액이 0원이면 결제 행을 만들 필요가 있나요?

**짧은 답변:** 현재 구현은 0원이어도 결제 행을 남깁니다.

**상세 답변:** 현금 승인은 없더라도 원래 가격, 할인과 포인트 사용, 최종 금액을 한 거래 단위로 추적하기 위해서입니다. 이 기록은 사용자 결제 내역과 관리자 통계·감사에서 같은 거래를 설명하는 근거가 됩니다.

### 질문 유형 3. 중복 대여

#### [압박][구현 확인] Q. 같은 책을 동시에 두 번 대여하면 어떻게 막나요?

**짧은 답변:** 무료·유료 대여 모두 먼저 회원 행을 비관적 잠금으로 가져온 뒤, 같은 회원과 도서의 최신 대여가 `READY` 또는 `READING`인지 확인해 중복 생성을 막습니다.

**상세 답변:** 같은 회원의 두 요청은 회원 행 잠금에서 직렬화되므로 뒤 요청은 앞 요청이 만든 대여를 본 뒤 `RENTAL_ALREADY_EXISTS`로 거절됩니다. `book_rental`에는 회원·도서 조합의 UNIQUE 제약을 두지 않았는데, 완독 후 같은 책을 다시 대여한 이력을 별도 행으로 남길 수 있어야 하기 때문입니다. 중복 금지는 모든 과거 행이 아니라 최신 행의 활성 상태를 기준으로 합니다.

**근거:** `RentalService.createFreeRental`, `PaymentService.createPaidRentalAndPayment`, `RentalService.validateNoActiveRental`, `MemberRepository.findByIdForUpdate`, `BookRentalRepository`

### 질문 유형 4. 외부 결제

#### [압박][현재 한계] Q. 왜 실제 PG 연동을 하지 않았나요?

**짧은 답변:** 이번 범위는 전자책 대여 정책과 내부 거래 일관성을 구현하는 데 두었고, 외부 PG 승인·취소·정산은 포함하지 않았습니다.

**상세 답변:** 외부 결제는 API 한 번을 추가하는 문제가 아니라 webhook, 멱등성, timeout, 취소·환불, 정산과 장애 복구까지 필요합니다. 현재 결제를 실제 카드 결제로 표현하지 않고, 확장 시 필요한 상태 전이를 설명합니다.

## 도메인 3. EPUB 뷰어·진행률

### 질문 유형 1. 열람 권한

#### [심층][구현 확인] Q. EPUB URL만 알면 다른 사용자의 책도 읽을 수 있나요?

**짧은 답변:** 뷰어 요청에서 로그인 회원의 유효한 대여와 사용할 EPUB 버전을 확인하므로 URL 문자열만으로 권한을 대신하지 않습니다.

**상세 답변:** 소유·대여 상태를 확인한 뒤 읽을 수 있는 자원을 제공하고, 진행 저장도 해당 회원과 대여의 관계를 확인합니다. 실제 storage URL의 노출 방식과 만료 정책은 배포 설정 범위까지 구분해 답합니다.

**근거:** Viewer·Rental Service, EPUB storage 설정

### 질문 유형 2. 진행률 저장

#### [심층][구현 확인] Q. 독서 위치는 무엇을 저장하고 왜 페이지 번호만 쓰지 않았나요?

**짧은 답변:** EPUB의 CFI, chapter·spine 위치, progression, revision과 EPUB 버전을 함께 관리합니다.

**상세 답변:** EPUB은 화면 크기와 글꼴에 따라 페이지가 달라질 수 있어 고정 페이지 번호만으로 위치를 복원하기 어렵습니다. CFI와 구조 위치를 사용하고, 콘텐츠 버전이 바뀐 경우 오래된 위치를 그대로 적용하지 않도록 버전 정보도 확인합니다.

### 질문 유형 3. 동시 저장

#### [압박][구현 확인] Q. 두 기기에서 진행률을 동시에 저장하면 마지막 요청이 무조건 덮어쓰나요?

**짧은 답변:** reading progress 행의 잠금과 revision 검증으로 충돌을 감지하도록 구현했습니다.

**상세 답변:** 클라이언트가 알고 있는 revision과 현재 값을 비교하고, 오래된 요청이면 충돌로 처리합니다. 따라서 단순히 도착 순서만으로 조용히 덮어쓰는 방식은 아닙니다.

**근거:** ReadingProgress Repository·Service·DTO

### 질문 유형 4. 완독 판정

#### [압박][정책 확인] Q. 완독은 어떤 기준으로 판정하나요?

**짧은 답변:** 명시적인 끝 도달 정보와 progression이 약 98% 이상인지 등을 현재 구현 기준으로 사용합니다.

**상세 답변:** 렌더링 오차와 마지막 여백 때문에 정확히 100%만 요구하지 않습니다. 다만 이 기준이 독서 내용을 실제로 이해했다는 뜻은 아니며, 보상 정책에서 필요한 기술적 완료 신호입니다.

## 도메인 4. Google 로그인

### 질문 유형 1. 세 가지 결과

#### [심층][구현 확인] Q. Google 로그인은 왜 로그인·가입·기존 계정 연동으로 나뉘나요?

**짧은 답변:** Google 식별자에 연결된 가입 회원이면 로그인하고, 연결 정보가 없으면 신규 가입 또는 기존 계정 연동 중 사용자가 선택해야 하기 때문입니다.

**상세 답변:** Backend가 Google token을 검증하고 공급자의 안정적인 `sub`를 확인합니다. 이미 연결된 정상 회원이면 token을 발급하고, 그렇지 않으면 제한된 transition token으로 가입이나 연동 경로를 이어갑니다. Front는 이 결과에 따라 화면을 분기합니다.

**근거:** Google Auth Controller·Service·DTO, Front login page와 auth API

### 질문 유형 2. 이메일 신뢰

#### [압박][보안 확인] Q. Google 이메일만 같으면 기존 계정에 자동 연동하나요?

**짧은 답변:** 이메일 문자열만으로 자동 연동하는 방식은 계정 탈취 위험이 있어, 현재 연동 경로의 사용자 확인과 transition token 조건을 따릅니다.

**상세 답변:** 공급자 token의 서명·audience·issuer·만료와 식별자를 검증하고, 연동 대상 계정에 대한 별도 인증을 요구해야 합니다. 정확한 입력 조건은 현재 link endpoint와 DTO를 기준으로 답합니다.

### 질문 유형 3. 운영 활성화

#### [압박][현재 상태] Q. 지금 배포 환경에서 Google 로그인이 반드시 동작하나요?

**짧은 답변:** 코드 경로는 구현됐지만 기본 기능 flag가 비활성화돼 있어 운영 설정과 client 정보가 주입된 환경에서만 동작합니다.

**근거:** Google Auth 설정, Backend·Front 배포 workflow의 환경 변수 주입

## 도메인 5. 도서관 외부 API

### 질문 유형 1. 장애 대응 순서

#### [심층][구현 확인] Q. 외부 도서관 API가 느리거나 실패하면 사용자에게 무엇을 보여주나요?

**짧은 답변:** fresh cache, 외부 조회, stale cache, 수동 데이터 순서로 가능한 결과를 찾고 모두 없으면 503으로 구분합니다.

**상세 답변:** 정상 데이터가 없는데 빈 목록을 성공으로 반환하면 사용자는 주변 도서관이 없다고 오해할 수 있습니다. 그래서 stale 여부와 warning을 응답에 담고, 사용할 데이터가 전혀 없는 장애는 서비스 불가로 처리합니다.

**근거:** Library Service·Response DTO, Front library API·page

### 질문 유형 2. 요청 폭주

#### [압박][구현 확인] Q. 같은 ISBN을 여러 사용자가 동시에 검색하면 외부 API를 모두 호출하나요?

**짧은 답변:** 동일 요청을 합치는 coalescing과 동시 호출 제한을 사용해 불필요한 외부 호출을 줄입니다.

**상세 답변:** 캐시 miss가 동시에 발생할 때 동일한 작업을 공유하고 외부 공급자 호출 수를 제한합니다. 다만 실제 최대 처리량 수치는 부하 시험 결과가 확인되지 않으면 말하지 않습니다.

### 질문 유형 3. Front 계약

#### [압박][현재 구현] Q. 지역과 세부지역, 경고 정보가 실제 화면까지 전달되나요?

**짧은 답변:** 현재 Front는 지역·세부지역 파라미터와 좌표·페이지 정보를 보내고, `stale`, `warnings`, `libraries`가 포함된 응답을 소비합니다.

**상세 답변:** 과거 현황 문서에는 연결이 부족하다고 적혀 있지만 최신 로컬 Front source에서 보완된 것을 확인했습니다. 답변 기준은 과거 snapshot이 아니라 현재 source입니다.

**근거:** Front `src/api/libraryApi.ts`, `BookLibrariesPage.tsx`, `src/types/api.ts`

## 도메인 6. 관리자 포인트 조정

### 질문 유형 1. 멱등성

**상세 답변:** 네트워크 timeout 뒤 재시도처럼 결과를 모르는 상황에서 endpoint만 다시 호출하면 포인트가 두 번 바뀔 수 있습니다. 요청 식별자와 이력을 확인해 같은 업무 요청은 한 번만 반영되도록 합니다.

### 질문 유형 2. 잔액과 이력

#### [압박][구현 확인] Q. 회원 잔액만 바꾸고 포인트 이력을 남기지 않으면 안 되나요?

**짧은 답변:** 운영 조정은 사후 설명과 감사가 필요하므로 잔액과 변동 이력을 함께 남겨야 합니다.

**상세 답변:** 누가, 어떤 요청으로, 얼마를, 왜 바꿨는지 추적할 수 있어야 통계와 장애 조사에서 잔액을 재구성할 수 있습니다. 관리자 권한과 대상 회원 잠금, 중복 requestId까지 함께 확인합니다.

## 도메인 7. 데이터 접근·성능

### 질문 유형 1. N+1

#### [압박][구현 확인] Q. JPA를 사용하면서 N+1 문제는 어떻게 줄였나요?

**짧은 답변:** 조회 목적에 따라 fetch join, `EntityGraph`, ID 일괄 조회와 집계 query를 사용한 구간이 있습니다.

**상세 답변:** 모든 연관을 EAGER로 바꾸지 않고 목록 응답에 필요한 관계만 명시적으로 가져옵니다. 구체 질문에는 해당 Repository query와 실행 SQL을 보여주고, 전체 시스템에서 N+1이 전혀 없다고 단정하지 않습니다.

**근거:** 관련 Repository의 fetch join·EntityGraph·batch query

### 질문 유형 2. 인덱스

#### [압박][설계 확인] Q. 인덱스는 어떤 조회를 기준으로 만들었나요?

**짧은 답변:** 회원별 상태·시간 조회, 도서 검색과 정렬, 대여·진행·알림·감사 기록처럼 실제 where·join·order 조건을 기준으로 runtime schema에서 확인합니다.

**상세 답변:** 인덱스 이름만 나열하지 않고 질문받은 query의 선두 컬럼과 정렬, 선택도를 함께 설명해야 합니다. 성능 개선 수치는 실행 계획과 측정 결과가 있을 때만 제시합니다.

**근거:** `src/main/resources/schema.sql`, 해당 Repository query

### 질문 유형 3. 비관적 잠금

#### [압박][설계 확인] Q. 모든 변경에 비관적 잠금을 사용하면 성능이 나빠지지 않나요?

**짧은 답변:** 모든 조회에 쓰는 것이 아니라 같은 행을 동시에 갱신할 가능성이 있고 정합성이 중요한 경로에 제한해 사용합니다.

**상세 답변:** 회원 포인트, 진행률, 신고 처리, 도서·컬렉션·대여 등 현재 잠금이 있는 경로도 각 경쟁 조건을 확인해야 합니다. 처리량이 중요한 구간에서는 조건부 update나 낙관적 revision처럼 충돌 범위에 맞는 방법을 선택합니다.

## 도메인 8. 검증 증거

### 질문 유형 1. Swagger·Postman

#### [압박][검증 범위] Q. Swagger와 Postman에서 성공했으면 기능이 완성된 것 아닌가요?

**짧은 답변:** API의 한 요청을 확인하는 데는 유용하지만 동시성, rollback, 권한 조합, Front 상태와 회귀까지 모두 보장하지는 않습니다.

**상세 답변:** Swagger·Postman은 입력과 응답을 빠르게 확인하고 Front 연결 전 계약 오류를 찾는 데 사용합니다. 정책 경계와 예외는 자동 테스트, 실제 Front 경로는 통합 확인, schema와 배포는 별도 검증이 필요합니다.

**근거:** `04_검증_품질.md`

### 질문 유형 2. 테스트 실행 여부

#### [압박][증거 기준] Q. 지금 이 자리에서 모든 테스트가 통과한다고 말할 수 있나요?

**짧은 답변:** 마지막으로 확인한 CI 또는 로컬 실행 기록의 범위와 시점을 제시하고, 이번 문서 작성 중 다시 실행하지 않은 테스트는 통과했다고 새로 주장하지 않겠습니다.

**상세 답변:** 테스트 코드가 존재하는 것과 현재 commit에서 실행해 성공한 것은 구분합니다. 답변할 때 command, commit SHA, DB 조건과 결과를 함께 제시합니다.
