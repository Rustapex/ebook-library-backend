# K01. 프로젝트·기획

## 도메인 1. 프로젝트 개요

### 질문 유형 1. 짧은 프로젝트 설명

#### [기본][구현 확인] Q. ABC 프로젝트를 1분 안에 설명해 주세요.

**짧은 답변:** ABC는 사용자가 전자책을 검색하고 무료 또는 유료로 대여한 뒤 웹 EPUB 뷰어에서 읽을 수 있는 서비스입니다. 도서 탐색·대여·결제·독서 기록·리뷰·보상 기능과 이를 운영하는 관리자 기능을 함께 구현했습니다. 핵심은 화면 수가 아니라 대여 권한, 결제와 포인트·쿠폰의 정합성, 독서 진도 충돌처럼 서비스 상태를 서버와 DB에서 일관되게 관리한 것입니다.

**상세 답변:** 사용자 영역은 회원가입·로그인, 도서 탐색, 대여·결제, 뷰어, 리뷰·찜, 출석·챌린지, 희망도서·알림·통계로 이어집니다. 관리자 영역은 회원·도서·컬렉션·공지·쿠폰·챌린지와 운영 통계·감사 로그를 관리합니다. 모든 화면이 같은 완성도인 것은 아니므로 현재 구현과 미구현 범위는 별도 차이 문서에서 구분합니다.

**근거:** `AGENTS.md`, 발표 대본 슬라이드 5~10·17~23, Backend·Frontend 도메인 소스

**예상 꼬리질문:** “가장 핵심적인 기술 문제 하나만 고르면 무엇인가요?”

### 질문 유형 2. 핵심 차별점

#### [심화][구현 확인] Q. 단순 도서 게시판과 무엇이 다른가요?

**짧은 답변:** 도서 정보를 보여주는 데서 끝나지 않고 대여 가능 여부, 무료·유료 대여, 결제·포인트·쿠폰, EPUB 열람 권한, 독서 진도와 북마크, 사용자 보상과 관리자 운영까지 하나의 상태 흐름으로 연결했다는 점이 다릅니다.

**상세 답변:** 화면에서 대여 가능으로 보인다는 이유만으로 요청을 허용하지 않고, 실제 대여와 열람 요청에서 회원·도서·대여 상태를 다시 확인합니다. 유료 대여는 결제 내역과 대여, 쿠폰 사용, 포인트 이력을 한 트랜잭션에서 변경합니다. 뷰어는 EPUB 버전과 진도 revision을 확인합니다. 이런 데이터 일관성이 단순 CRUD와 가장 다른 부분입니다.

**근거:** `PaymentService.createPaidRentalAndPayment`, `ViewerService`, `ChallengeService.claimReward`

## 도메인 2. 개발 배경과 목적

### 질문 유형 1. 개발 이유

#### [기본][팀 설명] Q. 왜 전자책 대여 서비스를 만들었나요?

**짧은 답변:** 사용자가 원하는 책을 발견한 뒤 장소에 제약받지 않고 대여와 열람까지 이어갈 수 있는 온라인 독서 흐름을 구현하기 위해 선택했습니다. 동시에 운영자가 도서와 혜택, 회원 상태를 관리할 수 있게 해 사용자 화면만 있는 데모가 아니라 운영 구조까지 다루려 했습니다.

**상세 답변:** 발표에서는 “접근성” 같은 단어를 읽기보다 탐색에서 열람까지 단절되지 않는 이용 경험을 설명합니다. 개발 관점에서는 도서 검색, 유료 대여, EPUB 열람, 독서 보상과 관리자 운영이 서로 다른 데이터와 상태를 연결하기 때문에 팀 프로젝트에서 API·DB·프런트 통합을 경험하기 적합했습니다.

**근거:** 발표 대본 슬라이드 6~10

### 질문 유형 2. 기대 효과

#### [기본][팀 설명] Q. 이 서비스를 이용하면 사용자에게 어떤 경험을 제공할 수 있나요?

**짧은 답변:** 사용자는 컬렉션·카테고리·검색으로 책을 찾고, 조건에 따라 무료 또는 유료로 대여한 다음 웹에서 읽고 마지막 위치부터 이어볼 수 있습니다. 출석과 챌린지 보상, 리뷰와 찜, 희망도서 신청을 통해 한 번의 대여 이후에도 서비스를 계속 이용할 이유를 제공합니다.

**근거:** Front User route·화면, Backend `book`, `rental`, `challenge`, `request`, `notification` 패키지

## 도메인 3. 사용자·관리자 여정

### 질문 유형 1. 사용자 흐름

#### [기본][구현·연동 확인] Q. 사용자의 핵심 이용 흐름을 설명해 주세요.

**짧은 답변:** 로그인 후 도서를 탐색하고 상세에서 대여 조건을 확인합니다. 무료 도서는 바로 대여하고 유료 도서는 쿠폰과 포인트를 적용해 대여와 결제 내역을 생성합니다. 대여가 유효하면 EPUB 뷰어에서 읽고 진도·북마크를 저장하며, 이후 마이페이지에서 이어 읽을 수 있습니다.

**상세 답변:** 검색과 상세는 공개 도서를 기준으로 합니다. 대여 생성 후 상태는 `READY`이고 뷰어에 처음 들어갈 때 `READING`으로 전환됩니다. 진도는 CFI·chapter href·spine index·progression·revision으로 저장합니다. 대여·결제·독서 기록이 각자 다른 테이블인 이유는 발생 시점과 변경 주기가 다르기 때문입니다.

**근거:** `BookController`, `RentalController`, `ViewerController`, `ReadingController`

### 질문 유형 2. 관리자 흐름

#### [기본][부분별 구현·연동 확인] Q. 관리자는 이 서비스를 어떻게 운영하나요?

**짧은 답변:** 관리자는 대시보드와 통계로 상태를 확인하고 회원·도서·컬렉션·공지·쿠폰·챌린지 등을 관리합니다. 주요 변경은 감사 로그로 추적합니다. 대여와 결제는 현재 조회 중심이며, 카테고리와 관리자 도서관 관리는 최종 범위 또는 백엔드 구현 상태가 다르므로 별도로 구분합니다.

**근거:** `src/main/java/com/acorn/abc/admin`, Front Admin pages, `AdminAuditLogService`

### 질문 유형 3. 사용자와 관리자의 연결

#### [심화][구현 확인] Q. 사용자 기능과 관리자 기능은 어떻게 연결되나요?

**짧은 답변:** 둘은 별도 서비스가 아니라 같은 데이터를 다른 목적으로 사용합니다. 관리자가 도서 공개 상태나 컬렉션·공지·쿠폰·챌린지를 바꾸면 사용자 탐색과 혜택에 반영되고, 사용자의 대여·결제·희망도서·신고 결과는 관리자 조회·처리 대상이 됩니다.

**근거:** 발표 대본 슬라이드 8, 관리자·사용자 Controller와 공통 테이블

## 도메인 4. 범위와 우선순위

### 질문 유형 1. 핵심 범위 선정

#### [심화][팀 진행 사실] Q. 왜 탐색·대여·결제·뷰어를 우선했나요?

**짧은 답변:** 전자책 서비스의 핵심 가치가 “책을 찾고 실제로 대여해 읽는 것”이기 때문입니다. 이 흐름이 완성되지 않으면 출석·통계·관리자 부가 기능이 많아도 서비스 핵심을 증명하기 어렵다고 판단했습니다.

**상세 답변:** 핵심 사용자 여정을 먼저 연결한 뒤 이를 운영하는 관리자 도서·회원·컬렉션과 배포 환경을 보강했습니다. 출석·챌린지·통계는 핵심 흐름 이후 확장했습니다.

**근거:** 발표 대본 슬라이드 9, WBS 사용 사실

### 질문 유형 2. 제외 이유

#### [심화][최종 범위 제외] Q. 구현하지 않은 기능은 왜 제외했나요?

**짧은 답변:** 모든 메뉴를 얕게 구현하기보다 핵심 대여·열람 흐름의 정합성과 연동을 우선했습니다. 비회원 비밀번호 재설정, 미리보기, 반납·연체, 결제 취소·환불, 관리자 카테고리 API 등은 최종 정책과 화면 범위에서 제외했습니다.

**상세 답변:** 제외 기능은 “실패한 구현”과 “최종 범위에서 의도적으로 뺀 기능”을 구분해 설명합니다. 예를 들어 반납과 연체를 제외하면서 대여 상태를 `READY`, `READING`, `OWNED`로 단순화했습니다. 반면 사용자 신고 API처럼 설계에 있으나 미구현된 항목은 범위 제외로 바꾸어 말하지 않습니다.

**근거:** `api-spec(final).md` 5장, 프로젝트현황 문서, `05_설계구현차이_미구현.md`

## 도메인 5. 담당과 책임

### 질문 유형 1. 개인 기여 설명

#### [기본][개인별 확인 필요] Q. 본인이 직접 구현한 부분은 어디까지인가요?

**짧은 답변 작성 원칙:** 기능 이름만 나열하지 않고 `직접 설계`, `직접 구현`, `공동 구현`, `후속 정합화`, `검증·문서화`로 나누어 답합니다. 본인 커밋·PR·소스 경로로 확인할 수 있는 부분만 “직접 구현”이라고 표현합니다.

**답변 템플릿:** “저는 `[도메인]`에서 `[설계/구현/검증]`을 담당했습니다. 대표적으로 `[문제]`를 발견해 `[판단]`을 내렸고, `[소스·테스트]`로 구현과 결과를 확인했습니다. `[공동 영역]`은 팀원이 핵심 구현을 맡고 저는 `[구체적 후속 기여]`를 담당했습니다.”

**근거:** 발표 대본 개인 회고, 포트폴리오 독서보상 API 초안, Front `김건희_작업이력_정리.md`

### 질문 유형 2. 팀원 구현 설명

#### [압박][팀 확인 필요] Q. 팀원이 만든 기능도 본인이 구현한 것처럼 설명하는 것 아닌가요?

**짧은 답변:** 아닙니다. 프로젝트 전체 흐름을 설명하는 것과 개인 구현을 구분합니다. 전체 서비스 질문에는 팀 구현을 포함해 동작을 설명하되, 개인 기여 질문에는 PR과 소스 근거가 있는 범위만 답합니다.

**상세 답변:** 공동 구현에서는 최초 구현자, 현행 핵심 로직 구현자, 후속 오류 수정자를 나누어 설명합니다. 예를 들어 Front 뷰어는 초기 화면과 라우팅, EPUB/CFI 렌더러 고도화, 후속 실행 오류·UX 보완을 한 사람의 단독 구현으로 합치지 않습니다.

**근거:** Front `김건희_작업이력_정리.md` 5장
