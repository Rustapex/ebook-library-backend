# K07. 협업·개인 기여

> 이 문서는 팀 전체 성과와 개인 기여를 섞어 말하지 않기 위한 답변 기준이다. 개인 답변에서는 반드시 `내가 맡은 범위`, `팀과 합의한 경계`, `내가 직접 확인한 결과`를 구분한다.

## 도메인 1. 일정·업무 분배

### 질문 유형 1. WBS 활용

#### [기본][팀 진행 사실] Q. WBS는 문서만 만들고 끝난 것이 아니라 실제로 어떻게 사용했나요?

**짧은 답변:** 기능을 사용자·관리자 영역과 Backend·Frontend 작업으로 나눈 뒤 담당자와 선후 관계를 정했고, 진행 중에는 남은 작업의 우선순위를 다시 정하는 기준으로 사용했습니다.

**상세 답변:** 인증이나 API 계약처럼 다른 작업의 시작 조건이 되는 항목을 먼저 배치하고, 화면과 API를 병렬로 개발할 수 있는 항목은 나누어 진행했습니다. 일정이 바뀌었을 때는 단순히 마감일만 옮기지 않고 시연에 필요한 핵심 경로와 다른 작업을 막는 항목을 먼저 처리했습니다. 이 내용은 팀의 실제 진행 사실을 전제로 한 답변이며, 저장소 코드만으로 증명되는 사실은 아닙니다.

**근거:** 발표자료 WBS, 팀 진행 사실

### 질문 유형 2. 우선순위

#### [심화][팀 진행 사실] Q. 시간이 부족할 때 어떤 기능부터 완성했나요?

**짧은 답변:** 회원이 도서를 찾고 대여한 뒤 뷰어로 읽는 핵심 경로와, 이를 운영자가 관리하는 데 필요한 기능을 우선했습니다.

**상세 답변:** 기능 수가 많아도 핵심 사용자 경로가 끊기면 서비스로 설명하기 어렵습니다. 따라서 인증, 도서 조회, 대여·결제 기록, 내 서재, 뷰어를 우선 연결했고 이후 리뷰·보상·알림·통계 같은 확장 기능을 붙였습니다. 다만 사용자 신고처럼 현재 미구현인 기능과 운영 설정이 필요한 기능은 완료된 것처럼 포함하지 않습니다.

**근거:** 발표자료 기능 범위, 현재 Controller·Service·Front route

## 도메인 2. 화면·API 사전 합의

### 질문 유형 1. Figma·화면설계

#### [기본][팀 진행 사실] Q. 화면설계도는 구현 과정에서 어떤 역할을 했나요?

**짧은 답변:** 완성 화면을 꾸미기 위한 자료라기보다, 구현 전에 각 화면의 역할과 이동 경로를 합의하는 기준으로 사용했습니다.

**상세 답변:** 사용자와 관리자의 메뉴, 한 화면에서 필요한 데이터, 다음 화면으로 이동하는 조건을 먼저 맞추면 Front가 임의로 API를 가정하거나 Backend가 사용되지 않는 응답을 만드는 일을 줄일 수 있습니다. 실제 구현 중 정책과 API가 바뀐 부분은 현재 소스가 최종 기준이며, 화면설계도와 다른 이유를 질문받으면 변경된 계약과 현재 동작을 함께 설명합니다.

**근거:** Figma·스토리보드·화면설계 문서, 팀 진행 사실, 현재 route와 API wrapper

### 질문 유형 2. API 명세

#### [기본][구현 확인] Q. Front와 Backend는 어떤 기준으로 기능을 나눠 개발했나요?

**짧은 답변:** API ID, URL, 요청·응답 DTO와 오류 형식을 계약으로 두고 각 영역을 병렬로 구현했습니다.

**상세 답변:** Front는 화면 상태와 요청 형식을, Backend는 검증·정책·데이터 처리를 맡았습니다. 병합 전에 Swagger나 Postman으로 Backend endpoint를 확인하고 Front에서도 실제 wrapper와 화면 연결을 점검했지만, 이 검증이 모든 통합 시나리오를 자동으로 보장한다고 말하지는 않습니다.

**근거:** `docs/API 명세/api-spec(final).md`, 공통 Backend 개발 규칙, Front `src/api`

### 질문 유형 3. 계약 변경

#### [심화][현재 상태] Q. API 명세와 구현이 달라진 경우에는 어떻게 처리하나요?

**짧은 답변:** 현재 실행되는 Controller·DTO·Front 호출을 먼저 확인하고, 명세 불일치를 별도 문서에 남겨 수정 대상을 정합니다.

**상세 답변:** 대표적으로 뷰어 진행 저장은 초기 명세와 현재 구현 계약에 차이가 있습니다. 이런 경우 문서에 맞추려고 동작을 추측하지 않고 현재 계약을 기준으로 Front와 Backend를 함께 확인한 다음 명세를 갱신해야 합니다.

**근거:** `05_설계구현차이_미구현.md`, 뷰어 Controller·DTO·Front viewer API

## 도메인 3. Git·PR·리뷰

### 질문 유형 1. 협업 단위

#### [기본][팀 진행 사실] Q. Git 작업은 어떤 단위로 나눴나요?

**짧은 답변:** 담당 기능을 branch와 PR 단위로 나누고, 병합 전에는 변경 목적·영향 범위·검증 결과를 확인하는 방식으로 진행했습니다.

**상세 답변:** 기능별 PR을 사용하면 누가 어떤 계약과 파일을 바꿨는지 추적하기 쉽고, Front와 Backend에서 동시에 바뀌어야 하는 항목도 확인할 수 있습니다. 다만 모든 PR이 동일한 수준의 테스트를 거쳤다고 일반화하지 않고, 개별 질문에는 해당 PR과 실행 기록을 확인한 범위만 답합니다.

**근거:** 로컬 Git 이력, PR 문서, 작업현황 문서

### 질문 유형 2. 리뷰 대응

#### [심화][구현 확인] Q. 코드 리뷰를 통해 실제로 개선한 사례는 무엇인가요?

**짧은 답변:** 기능마다 사례가 다르므로 질문받은 담당 영역의 PR과 후속 문서를 기준으로 답해야 합니다. 예를 들어 감사 로그 DB 제약과 리뷰 조회 구조처럼 리뷰 뒤에 후속 수정 계획과 구현을 분리해 관리한 기록이 있습니다.

**상세 답변:** “리뷰를 많이 받았다”보다 지적 내용, 위험, 수정한 코드, 재검증 결과를 순서대로 설명합니다. 자신의 담당 PR이 아닌 사례를 개인 성과처럼 말하지 않습니다.

**근거:** `docs/작업현황/2026-07-14_PR46_코드리뷰_대응계획.md`, 관련 후속 계획과 Git diff

## 도메인 4. 팀 전체 역할

| 김재민 | 외부 도서 정보, 대여·결제, 리뷰·즐겨찾기, 도서 요청·알림, EPUB 저장·배포 관련 영역 | 팀 공통 설계와 개인 구현을 구분 |

### 질문 유형 2. 공동 작업

#### [심화][답변 기준] Q. 여러 사람이 함께 수정한 기능은 누구의 성과인가요?

### 질문 유형 2. 손영석 개인 기여

#### [심화][개인문서 근거] Q. 독서 보상 API에서 본인이 해결한 핵심 문제는 무엇인가요?

**짧은 답변:** 보상 수령 시점에 조건을 다시 계산하고, 이미 수령한 행은 조건부 갱신으로 막으며, 보상 지급과 수령 처리를 같은 트랜잭션에 묶은 점입니다.

**상세 답변:** 화면에 보이는 달성 상태만 믿으면 동시에 두 요청이 들어왔을 때 중복 보상이 발생할 수 있습니다. 그래서 수령 요청 시 최신 독서 기록으로 달성 여부를 다시 판단하고 `reward_claimed_at IS NULL` 조건을 만족할 때만 상태를 바꾼 뒤 지급 내역을 함께 저장합니다. 이 답변은 설계 의도뿐 아니라 포트폴리오 초안과 현재 구현을 함께 근거로 말할 수 있습니다.

**근거:** `2026-07-22_포트폴리오_독서보상API_초안` 계열 문서, Challenge reward Service·Repository·test

**짧은 답변:** 초기 route와 인증 guard, 공통 API client·오류 처리, 공통 layout·UI 구조를 만들고 여러 사용자·관리자 화면을 실제 Backend API와 연결했습니다.

**근거:** Front `docs/김건희_작업이력_정리.md`, Front `src/router`, `src/api`, 관련 page

### 질문 유형 4. 기여도 수치

#### [압박][답변 기준] Q. 본인의 기여도를 퍼센트로 말할 수 있나요?

**짧은 답변:** commit 수나 파일 수만으로 기여도를 환산하지 않고, 담당한 사용자 경로·핵심 정책·통합 책임과 검증 결과로 설명하겠습니다.

**상세 답변:** 공통 기반 한 번의 변경이 많은 화면에 영향을 줄 수 있고, 작은 오류 수정도 핵심 경로를 복구할 수 있어 단순 수치가 실제 기여와 같지 않습니다. 수치가 반드시 필요하면 팀이 합의한 산정 기준이 있는 경우에만 사용합니다.

**답변 주의:** 일반적인 협업 모범답안을 프로젝트 경험처럼 말하지 않습니다.
