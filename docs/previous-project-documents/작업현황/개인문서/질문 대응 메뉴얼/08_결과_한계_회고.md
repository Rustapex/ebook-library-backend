



# K08. 결과·한계·회고

## 도메인 1. 프로젝트 결과

### 질문 유형 1. 핵심 성과

#### [기본][현재 구현] Q. 이 프로젝트에서 실제로 완성한 핵심 결과는 무엇인가요?

**짧은 답변:** 회원이 도서를 검색하고 대여·결제 기록을 만든 뒤 EPUB을 읽고 진행 상태를 저장하는 경로와, 리뷰·보상·알림·마이페이지 및 관리자 운영 기능을 하나의 서비스로 연결했습니다.

**상세 답변:** 단순 CRUD 수보다 사용자 경로가 실제 데이터와 정책으로 이어지는지가 중요했습니다. 대여에서는 쿠폰·포인트·결제·알림을 함께 처리하고, 뷰어에서는 대여 권한과 EPUB 버전을 확인하며, 보상에서는 수령 시점 재검증과 중복 지급 방지를 적용했습니다. 관리자는 회원·도서·대여·결제·요청·쿠폰·포인트·챌린지·통계·감사 로그 등을 조회하거나 처리할 수 있습니다. 다만 사용자 신고 API와 일부 관리자 기능처럼 미구현인 항목은 성과에 포함하지 않습니다.

**근거:** 현재 Backend Controller·Service·schema, 현재 Front route·API wrapper, `05_설계구현차이_미구현.md`

### 질문 유형 2. 기술적 성과

#### [심화][현재 구현] Q. 기능 구현 외에 기술적으로 남긴 것은 무엇인가요?

**짧은 답변:** API 오류 규격, 권한 검사, 트랜잭션, 동시성 제어, 멱등 처리, 감사 로그, CI/CD처럼 기능을 안전하게 운영하기 위한 공통 기준을 적용했습니다.

**상세 답변:** 예를 들어 보상과 포인트 조정은 중복 처리를 막고, 뷰어 진행 저장은 revision 충돌을 확인하며, 관리자 경로는 역할을 검사합니다. 배포도 commit SHA와 immutable artifact를 기준으로 어떤 코드를 실행하는지 추적할 수 있게 구성했습니다.

**근거:** 공통 Backend 개발 규칙, SecurityConfig, 관련 Service·Repository, CI/CD workflow와 가이드

### 질문 유형 3. 수치 설명

#### [압박][검증 범위] Q. API나 화면을 몇 개 구현했나요?

**짧은 답변:** 특정 시점의 연동 현황 문서에는 전체 83개 API와 Backend·Front 연결 수가 정리돼 있지만, 현재 소스가 그 뒤에 바뀌었으므로 숫자를 최신 완료율처럼 단정하지 않겠습니다.

**상세 답변:** 발표에서 숫자가 필요하면 기준일과 계산 규칙을 함께 제시하고 현재 Controller와 Front 호출을 다시 집계해야 합니다. 기능이 존재하는 것, Front에서 호출하는 것, 시나리오가 검증된 것은 서로 다른 상태입니다.

**근거:** `docs/프로젝트현황/API-ID별_백엔드구현_프론트연결_현황.md`, 현재 소스

## 도메인 2. 현재 한계

### 질문 유형 1. 미구현 기능

#### [기본][현재 상태] Q. 아직 구현하지 못한 기능은 무엇인가요?

**짧은 답변:** 대표적으로 사용자 신고 생성·내 신고 조회·철회 API, 관리자 도서관 관리 Backend, 관리자 카테고리 관리가 현재 범위에서 완성되지 않았습니다.

**상세 답변:** 관리자 신고 조회·처리와 관련 화면은 존재하지만 사용자 신고 생성 경로는 별개입니다. 관리자 도서관 화면은 있어도 이를 지원하는 관리자 Backend 계약은 확인되지 않았고, 카테고리 관리는 scope 제외로 관리됐습니다. 따라서 화면이나 Entity가 있다는 이유만으로 전체 기능이 완성됐다고 말하지 않습니다.

**근거:** `05_설계구현차이_미구현.md`

### 질문 유형 2. 운영 설정

#### [기본][현재 상태] Q. 코드가 있어도 바로 사용할 수 없는 기능이 있나요?

**짧은 답변:** Google 로그인과 외부 도서 정보 수집은 기본 비활성화돼 있어 운영 환경의 설정과 자격 정보가 있어야 활성화됩니다.

**상세 답변:** 구현 완료와 운영 활성화는 다른 상태입니다. Google 로그인은 token 검증과 가입·연동 경로가 구현돼 있지만 client 설정과 기능 flag가 필요하고, 외부 도서 API도 공급자별 설정과 장애 대응 조건이 필요합니다.

**근거:** `application*.yml`의 기능 flag 키, Google Auth·external book 설정과 Service

### 질문 유형 3. 결제 범위

#### [압박][현재 한계] Q. 결제 기능은 실제 PG사 결제까지 되나요?

**짧은 답변:** 아닙니다. 현재 결제는 프로젝트 내부의 대여 금액, 쿠폰, 포인트, 결제 상태와 이력을 관리하는 범위이며 외부 PG 승인·취소 연동은 포함하지 않았습니다.

**상세 답변:** 지금 구조는 최종 금액을 계산하고 대여·결제·쿠폰 사용·포인트 내역을 같은 업무 흐름에서 남깁니다. 실제 서비스로 확장하려면 PG의 승인 식별자, webhook 검증, 멱등 키, 취소·환불·부분 실패·정산과 장애 복구를 별도로 설계해야 합니다.

**근거:** Rental·Payment Service와 schema

### 질문 유형 4. 테스트 한계

#### [압박][검증 범위] Q. 모든 기능을 자동 테스트로 보장하나요?

**짧은 답변:** 아닙니다. Backend 테스트와 CI 검증은 있지만 모든 사용자·관리자 시나리오와 실제 운영 외부 연동을 완전히 보장한다고 말할 수 없습니다.

**상세 답변:** Controller·Service·Repository 테스트와 schema 검증이 존재하고 CI에서 실제 MySQL 계열 환경을 사용하지만, Front에는 별도 테스트 runner가 없고 일부 문서는 수동 검증 재실행 여부를 명시하지 않습니다. 따라서 테스트 종류와 실제 실행 증거를 구분해 답합니다.

**근거:** `04_검증_품질.md`, Backend test source, Front `package.json`, workflow

### 질문 유형 5. 모니터링 한계

#### [심화][현재 한계] Q. 운영 장애를 자동으로 탐지하는 체계가 충분한가요?

**짧은 답변:** 배포 health check와 로그·감사 기록은 있지만, 별도의 완성된 관측 플랫폼과 자동 경보 체계까지 갖춘 상태로 보기는 어렵습니다.

**상세 답변:** 현재는 배포 직후 container와 API 상태를 확인하고 애플리케이션 로그, 감사 로그, 배포 metadata로 원인을 추적할 수 있습니다. 운영 수준으로 확장하려면 지표·중앙 로그·trace·SLO와 경보 기준을 추가해야 합니다.

**근거:** CI/CD workflow와 가이드, 감사 로그 구현

## 도메인 3. 설계와 구현의 차이

### 질문 유형 1. 차이가 생긴 이유

#### [기본][설명 원칙] Q. 처음 설계와 실제 구현이 달라진 이유는 무엇인가요?

**짧은 답변:** 구현 중에 실제 데이터 구조, 권한, 오류 처리와 Front 사용 방식이 구체화되면서 계약이 바뀐 부분이 있기 때문입니다.

**상세 답변:** 설계 변경 자체보다 변경 뒤 문서와 구현의 기준을 일치시키지 못한 점이 문제입니다. 현재는 runtime schema와 실행 소스를 우선하고, 뷰어 계약처럼 명세와 다른 항목은 불일치로 표시했습니다. 이후에는 API 계약 변경과 문서 갱신을 같은 PR의 완료 조건으로 두는 것이 필요합니다.

**근거:** `AGENTS.md`의 source-of-truth 우선순위, `05_설계구현차이_미구현.md`

### 질문 유형 2. 과거 현황 문서

#### [심화][문서 기준] Q. 현황 문서에는 미연동인데 현재 화면에서는 동작하는 이유는 무엇인가요?

**짧은 답변:** 현황 문서는 작성 시점의 snapshot이고 이후 로컬 소스에서 연결된 기능이 있기 때문입니다.

**상세 답변:** 도서관 검색의 지역·세부지역 파라미터와 관리자 대여·결제·신고 화면 연결은 과거 snapshot 뒤에 반영된 항목입니다. 그래서 질문 대응 문서는 날짜가 오래된 완료율보다 현재 route, API wrapper, Controller, DTO를 우선했습니다.

**근거:** 과거 프로젝트현황 문서와 현재 Front source 비교

## 도메인 4. 개선 우선순위

### 질문 유형 1. 가장 먼저 보완할 기능

#### [기본][개선안] Q. 시간이 더 있다면 무엇부터 개선하겠나요?

**짧은 답변:** 첫째로 미구현 경로와 문서 불일치를 정리하고, 둘째로 핵심 통합 시나리오 자동화, 셋째로 운영 관측과 복구 절차를 강화하겠습니다.

**상세 답변:** 새로운 기능을 늘리기 전에 사용자 신고 경로, 관리자 도서관 관리, 뷰어 명세처럼 현재 경계가 불분명한 부분을 해결하겠습니다. 이후 가입부터 대여·결제·뷰어·보상까지의 통합 테스트와 Front 자동 테스트를 추가하고, 배포 자동 rollback 여부보다 안전한 판단 기준과 관측 정보를 먼저 보강하겠습니다.

### 질문 유형 2. 결제 확장

#### [심화][개선안] Q. 실제 결제 서비스로 확장한다면 무엇이 달라져야 하나요?

**짧은 답변:** PG 승인과 내부 대여를 한 번에 성공했다고 가정하지 않고, 외부 거래 상태와 내부 상태를 멱등하게 동기화해야 합니다.

**상세 답변:** 결제 요청 식별자, 승인·실패·취소·환불 상태, webhook 서명 검증, 재시도, 중복 callback, timeout 후 조회, 대여 생성 보상 트랜잭션을 설계해야 합니다. DB 트랜잭션만으로 외부 시스템까지 원자적으로 묶을 수 없으므로 상태 전이와 복구 작업이 필요합니다.

### 질문 유형 3. 검색·추천 확장

#### [심화][개선안] Q. 추천 기능을 더 발전시킨다면 어떻게 하겠나요?

**짧은 답변:** 현재의 저자·카테고리·키워드 기준 관련 도서를 기반선으로 두고, 사용자의 대여·완독·평점 신호를 검증 가능한 방식으로 추가하겠습니다.

**상세 답변:** 먼저 추천 이유를 설명할 수 있는 규칙 기반 점수와 offline 평가 기준을 만들고, 데이터가 충분해진 뒤 개인화를 적용하겠습니다. 현재 구현을 AI 추천이라고 과장하지 않습니다.

**근거:** 관련 도서 Service의 현재 criterion과 sort

## 도메인 5. 회고

### 질문 유형 1. 가장 큰 교훈

#### [기본][회고] Q. 프로젝트에서 가장 크게 배운 점은 무엇인가요?

**짧은 답변:** 기능을 각각 만드는 것보다 계약, 상태 전이, 실패 처리와 검증 기준을 팀이 같은 의미로 사용하는 일이 더 중요하다는 점입니다.

**상세 답변:** 도서관 검색처럼 Backend 응답이 풍부해도 Front가 일부 파라미터만 보내면 사용자 기능은 완성되지 않습니다. 반대로 화면이 있어도 이를 받는 관리자 API가 없으면 운영 기능으로 볼 수 없습니다. 이후에는 기능 완료를 Backend 구현, Front 연결, 통합 검증, 문서 갱신으로 나누어 확인하겠습니다.

### 질문 유형 2. 다시 설계한다면

#### [심화][회고] Q. 처음부터 다시 만든다면 어떤 순서로 진행하겠나요?

**짧은 답변:** 핵심 사용자 경로와 상태 전이를 먼저 고정하고, API 계약 테스트와 작은 vertical slice를 완성한 다음 기능을 넓히겠습니다.

**상세 답변:** 회원 가입부터 도서 검색·대여·읽기까지 한 경로를 Backend, Front, DB, 배포 환경에서 먼저 통과시키고 공통 오류·권한·관측 기준을 확정하겠습니다. 그다음 리뷰·보상·관리자 기능을 같은 기준으로 확장하면 뒤늦은 계약 불일치와 통합 비용을 줄일 수 있습니다.

### 질문 유형 3. 아쉬운 선택

#### [상황형][개인 확인 필요] Q. 본인이 내린 결정 중 아쉬웠던 것은 무엇인가요?

**짧은 답변:** 실제 본인 결정 하나를 선택해 당시 근거, 드러난 한계, 지금의 수정안을 설명해야 합니다.

**답변 주의:** 팀 전체의 미구현 항목을 본인의 실패처럼 가져오거나, 반대로 본인이 결정하지 않은 설계를 개인 회고로 꾸미지 않습니다.

## 도메인 6. 발표 종료 답변

### 질문 유형 1. 프로젝트 요약

#### [마무리][현재 구현] Q. 이 프로젝트를 한 문장으로 정리하면 무엇인가요?

**짧은 답변:** 전자책을 찾고 대여해 읽는 사용자 경험과, 그 과정의 결제·보상·운영 기록을 관리하는 기능을 하나의 웹 서비스로 구현한 팀 프로젝트입니다.

### 질문 유형 2. 가장 보여주고 싶은 점

#### [마무리][현재 구현] Q. 한 가지만 강조한다면 무엇인가요?

**짧은 답변:** 화면 수보다 대여·결제·읽기·보상처럼 여러 도메인이 만나는 경로에서 권한, 상태, 중복 요청과 실패를 어떻게 처리했는지를 보여드리고 싶습니다.
