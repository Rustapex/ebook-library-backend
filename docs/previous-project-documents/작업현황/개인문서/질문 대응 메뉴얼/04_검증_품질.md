# K04. 검증·품질

## 도메인 1. 자동 테스트

### 질문 유형 1. Backend 테스트 범위

#### [기본][자동 테스트 근거 있음] Q. Backend는 어떤 방식으로 테스트했나요?

**짧은 답변:** Controller 요청·권한·응답, Service 비즈니스 규칙, Repository 쿼리와 일부 실제 DB 통합 경로를 테스트했습니다. 기능별 `*Test.java`를 두고 회귀 가능성이 큰 상태·정합성 문제를 테스트로 고정했습니다.

**상세 답변:** 예를 들어 유료 대여·결제는 금액과 포인트·쿠폰 처리, 챌린지 보상은 최신 보상·중복 수령·지급 결과, 뷰어는 EPUB 버전·revision 충돌, Google 인증은 token 검증과 계정 연결·DB 제약을 테스트합니다. 단순 성공 응답뿐 아니라 최종 데이터 상태가 중요한 기능은 Service·Repository 검증을 함께 봅니다.

**근거:** `src/test/java/com/acorn/abc`

### 질문 유형 2. 테스트 DB

#### [압박][프로젝트 규칙 확인] Q. H2나 Testcontainers를 사용했나요?

**짧은 답변:** 현재 프로젝트 기본 테스트는 H2나 Testcontainers가 아니라 로컬 또는 팀 공유 MySQL DB를 사용합니다.

**상세 답변:** 실제 MySQL 문법과 제약을 확인할 수 있지만 테스트 데이터 간 간섭과 환경 의존성이 생기는 단점이 있습니다. 다음에는 Testcontainers로 격리된 MySQL을 띄워 재현성과 실제 DB 호환성을 함께 확보하는 것이 개선 방향입니다.

**근거:** `AGENTS.md` 검증 규칙

### 질문 유형 3. Front 테스트

#### [압박][현재 구성 확인] Q. Front 자동 테스트도 있나요?

**짧은 답변:** 현재 별도 Front 테스트 러너는 설정되어 있지 않습니다. TypeScript/Vite build, ESLint와 CI, 정적 API 호출 대조, 브라우저 smoke를 중심으로 검증합니다.

**상세 답변:** 따라서 Front 품질을 “자동 테스트 완료”라고 포괄적으로 말하지 않습니다. 컴포넌트·E2E 회귀 테스트가 부족한 점은 현재 한계이며, 핵심 대여·로그인·뷰어 흐름부터 테스트를 추가하는 것이 우선입니다.

**근거:** Backend `AGENTS.md`의 Front 규칙, Front workflow

## 도메인 2. Swagger·Postman·DB 검증

### 질문 유형 1. 도구별 역할

#### [기본][검증 기준] Q. Swagger·Postman 테스트와 JUnit은 무엇이 다른가요?

**짧은 답변:** JUnit은 규칙을 반복 가능한 자동 검증으로 고정하고, Swagger는 실제 endpoint와 인증·요청 형식을 수동 확인하며, Postman은 여러 요청과 재시도·환경 변수를 조합한 시나리오 확인에 적합합니다.

**상세 답변:** 셋 중 하나가 나머지를 완전히 대체하지 않습니다. 자동 테스트가 통과해도 배포 환경의 인증·CORS·seed 데이터 문제는 남을 수 있고, Swagger 한 번 성공했다고 예외와 회귀가 보장되지는 않습니다.

**근거:** 발표 대본 슬라이드 11, `AGENTS.md` 검증 규칙

### 질문 유형 2. DB 결과 확인

#### [심화][검증 기록 있음] Q. 응답이 200이면 기능이 성공했다고 볼 수 있나요?

**짧은 답변:** 정합성이 중요한 기능은 그렇지 않습니다. 응답뿐 아니라 잔액, 이력, 쿠폰 발급 수량, 수령 상태 같은 최종 DB 결과를 확인해야 합니다.

**상세 답변:** 보상 수령은 포인트 잔액과 `point_history`, 또는 실제 `member_coupon` 생성까지 확인합니다. 유료 대여는 `book_rental`, `payment`, `coupon_usage`, `point_history`가 요청 내용과 일치하는지 봐야 합니다.

**근거:** 독서보상 포트폴리오 E-01~E-04, `PaymentService`

### 질문 유형 3. 모든 API 검증 여부

#### [압박][제한사항] Q. 모든 API를 Swagger와 Postman으로 검증했나요?

**짧은 답변:** 아닙니다. 자동 테스트, Swagger·Postman 수동 검증, DB 검증, Front 정적 연결 확인의 수준이 API마다 다릅니다.

**상세 답변:** 발표에서도 모든 API가 같은 수준의 검증을 거쳤다고 말하지 않습니다. 관리자 도서처럼 Swagger와 DB 전후 기록이 있는 기능, 단위 테스트와 build 기록만 있는 기능, Front 호출만 정적으로 확인한 기능을 구분합니다.

**근거:** 발표 대본 슬라이드 11, 프로젝트현황 6장 제한사항

## 도메인 3. 동시성·멱등성 검증

### 질문 유형 1. 보상 중복 수령 검증

#### [압박][부분 검증] Q. 보상 중복 방지는 실제 동시 부하 테스트까지 했나요?

**짧은 답변:** 조건부 UPDATE와 빠른 반복 요청의 중복 방지 결과는 확인했지만, 포트폴리오에 있는 검증은 실제 다중 스레드·다중 프로세스 부하 테스트와 같지 않습니다.

**상세 답변:** 첫 요청 성공, 반복 요청 충돌과 DB 중복 미발생은 근거가 있습니다. 하지만 같은 시점에 여러 연결을 발생시키는 Testcontainers 기반 통합 테스트나 부하 도구 검증은 남은 과제입니다.

**근거:** 독서보상 포트폴리오 `현재 한계와 개선 방향`

### 질문 유형 2. DB 잠금 검증

#### [압박][소스·단위 테스트 근거][통합 검증 제한] Q. `PESSIMISTIC_WRITE`를 사용했으니 동시성 안전이 증명된 것 아닌가요?

**짧은 답변:** 아닙니다. 잠금 코드는 경쟁을 직렬화하도록 설계됐다는 근거이고, 실제 DB 격리 수준·교착·대기 시간까지 증명하려면 동시 통합 테스트가 필요합니다.

**상세 답변:** 회원 탈퇴와 결제, 관리자 포인트 조정, 신고 처리처럼 같은 회원 행을 잠그는 경로는 잠금 순서와 트랜잭션 범위를 확인해야 합니다. 기능 성공뿐 아니라 deadlock·timeout·처리량도 별도 검증 대상입니다.

**근거:** `MemberRepository.findByIdForUpdate`, PR #64 검토 제한사항

### 질문 유형 3. 멱등 키 검증

#### [심화][자동 테스트 근거 있음] Q. 관리자 포인트 조정의 같은 요청을 다시 보내면 무엇을 확인해야 하나요?

**짧은 답변:** 같은 회원·requestId·내용이면 기존 결과를 반환하고 이력을 추가하지 않아야 합니다. 동일 키에 다른 금액이나 설명이면 충돌해야 합니다.

**근거:** `AdminPointAdjustService`, 관련 Controller·Service 테스트

## 도메인 4. Front·Backend 통합

### 질문 유형 1. 정적 연결과 실행 연결

#### [심화][검증 기준] Q. Front에서 함수를 호출하면 연동 완료인가요?

**짧은 답변:** 정적 연결은 확인할 수 있지만 실행 성공까지 의미하지는 않습니다. endpoint·method·parameter·DTO·인증·환경 설정과 실제 HTTP 응답을 확인해야 연동 완료를 말할 수 있습니다.

**상세 답변:** 현재 매뉴얼의 `구현·연동 확인`은 소스상 Backend endpoint와 Front 호출부가 맞는다는 뜻입니다. 이번 문서 작성 과정에서 실제 로그인·외부 API·브라우저 시나리오를 실행하지 않은 항목은 `실행 확인 필요`를 함께 붙입니다.

### 질문 유형 2. 실패 fallback

#### [심화][Front 개선 근거] Q. API가 실패하면 샘플 데이터를 보여주는 것이 사용자 경험에 더 좋지 않나요?

**짧은 답변:** 개발용 mock은 필요할 수 있지만 실제 기능처럼 보이는 fallback은 장애와 미구현을 숨깁니다. 운영 화면에서는 로딩·빈 상태·오류 상태를 구분하고 실패를 성공으로 표시하지 않는 것이 우선입니다.

**상세 답변:** Front에서는 도서 목록, 관리자 대여·결제·도서관, 신고 처리에서 가짜 성공·목록 fallback을 제거한 기록이 있습니다. Mock이 필요하면 API wrapper 안에 섞지 않고 개발 전용 경계를 둡니다.

**근거:** Front `김건희_작업이력_정리.md` 7.1, Admin 화면 문서 38장

### 질문 유형 3. 통합 시점

#### [회고][팀 진행 사실] Q. 통합 과정에서 가장 아쉬웠던 점은 무엇인가요?

**짧은 답변:** Front와 Backend가 병렬 개발됐지만 핵심 시나리오의 실제 통합 확인이 후반에 집중돼 응답 필드·parameter 차이를 늦게 발견한 점입니다.

**상세 답변:** 다음에는 로그인→검색→대여→뷰어 같은 핵심 세로 흐름을 초기부터 얇게 연결하고, API 계약 테스트와 격리된 E2E 환경을 준비해야 합니다.

**근거:** 발표 대본 슬라이드 25

## 도메인 5. 성능·품질 위험

### 질문 유형 1. 성능 측정

#### [압박][실행 확인 필요] Q. 성능 개선 효과를 수치로 측정했나요?

**짧은 답변:** 일부 반복 조회를 일괄 조회·GROUP BY·캐시로 개선한 소스 근거는 있지만, 전체 서비스의 부하 테스트와 전후 성능 수치는 이번 자료에서 확인되지 않았습니다.

**상세 답변:** 수치가 없는 상태에서 “성능을 크게 개선했다”고 말하지 않습니다. 구현 의도와 쿼리 구조를 설명하고, 다음 단계로 응답 시간·쿼리 수·처리량·락 대기 시간을 측정하겠다고 답합니다.

### 질문 유형 2. 외부 API 품질

#### [심화][구현 확인][실행 확인 필요] Q. 외부 API가 느리면 요청이 계속 쌓이지 않나요?

**짧은 답변:** 도서관 조회는 동시 호출 수를 제한하고 동일 cache key 요청을 하나의 in-flight 호출로 합칩니다. fresh·stale cache와 수동 데이터를 fallback으로 사용합니다.

**근거:** `InfoNaruLibraryConcurrencyLimiter`, `PhysicalLibrarySearchService`

## 도메인 6. 현재 검증 기준 요약

### 질문 유형 1. 자신 있게 말할 수 있는 범위

#### [기본][문서 기준] Q. 현재 무엇까지 검증됐다고 말하는 것이 안전한가요?

**짧은 답변:** 현재 소스에서 구현 경로와 관련 테스트 파일은 확인했습니다. 과거 build·Swagger·DB 검증 기록도 구분해 인용할 수 있습니다. 다만 이번 매뉴얼 작성에서는 Backend build, Front build, 실제 배포 로그인·외부 API·E2E를 재실행하지 않았습니다.

**상세 답변:** 질문에 따라 `코드 확인`, `자동 테스트 근거`, `과거 수동 검증 기록`, `현재 실행 확인`을 나누어 답합니다. 실행하지 않은 검증을 완료했다고 표현하지 않습니다.
