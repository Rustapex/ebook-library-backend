# K03. 기술 설계·구현

## 도메인 1. 전체 구조

### 질문 유형 1. 기술 선택

#### [기본][구현 확인] Q. 어떤 기술로 구성했고 왜 선택했나요?

**짧은 답변:** Backend는 Java 17, Spring Boot, Spring Data JPA, Spring Security와 MySQL을 사용하고 Front는 React, TypeScript, Vite, React Router와 Axios를 사용했습니다. 기능별 도메인 분리와 REST API 계약을 기준으로 Front와 Backend를 병렬 개발하기 위한 구성이었습니다.

**상세 답변:** Spring Boot는 웹·검증·보안·데이터 접근과 테스트 생태계를 함께 사용할 수 있고, JPA는 도메인 객체와 관계 중심으로 구현하기에 적합했습니다. React와 TypeScript는 많은 사용자·관리자 화면을 컴포넌트와 타입으로 나누고 API 계약 오류를 줄이는 데 사용했습니다. 기술 이름보다 실제로 DTO, 예외, 권한, 트랜잭션, 화면 상태를 어떻게 통일했는지가 핵심입니다.

**근거:** Backend `build.gradle`, Front `package.json`, `AGENTS.md`

### 질문 유형 2. 도메인 패키지

#### [심화][구현 확인] Q. 계층형 패키지 대신 기능별 패키지를 사용한 이유는 무엇인가요?

**짧은 답변:** 인증·도서·대여·결제·보상처럼 변경 이유가 다른 기능을 한 영역에 모아 담당 범위와 의존성을 찾기 쉽게 하기 위해서입니다.

**상세 답변:** 최상위에는 `auth`, `member`, `book`, `rental`, `payment`, `challenge`, `notification`, `admin` 등이 있고 각 기능 안에서 Controller·Service·DTO·Domain·Repository를 나눕니다. 다만 Entity가 있다고 모든 계층이 구현됐다고 가정하지 않으며 실제 endpoint와 서비스 경로를 확인합니다.

**근거:** `src/main/java/com/acorn/abc`, `AGENTS.md`

## 도메인 2. REST API·DTO

### 질문 유형 1. URL과 버전

#### [기본][구현 확인] Q. API URL 규칙은 어떻게 정했나요?

**짧은 답변:** `/api/v1` prefix를 사용하고 리소스는 복수형 명사로 표현합니다. 로그인한 본인 데이터는 `/me`, 관리자 기능은 `/admin` 영역으로 구분합니다.

**근거:** `api-spec(final).md`, 백엔드 공통 개발 규칙, Controller 매핑

### 질문 유형 2. Entity 직접 반환 금지

#### [심화][구현 확인] Q. 왜 Entity를 직접 반환하지 않고 DTO를 사용했나요?

**짧은 답변:** DB 구조와 외부 API 계약을 분리하고 필요한 필드만 공개하며 지연 로딩·순환 참조·민감정보 노출 문제를 막기 위해서입니다.

**상세 답변:** Request DTO에는 `@Valid` 검증을 적용하고 Response는 화면과 API 목적에 맞춘 `*Response`, `*SummaryResponse`를 사용합니다. Entity가 바뀌어도 API 계약 전체가 의도 없이 바뀌지 않게 하는 경계입니다.

**근거:** 백엔드 공통 개발 규칙 7~9장, Controller·DTO 패키지

### 질문 유형 3. 공통 응답

#### [심화][구현·연동 확인] Q. 공통 응답 형식이 왜 필요한가요?

**짧은 답변:** 성공 여부, 코드, 메시지, 데이터를 같은 구조로 제공해 Front가 endpoint마다 다른 방식으로 파싱하지 않게 합니다.

**상세 답변:** 단건은 `ApiResponse<T>`, 페이지는 그 안에 `PageResponse<T>`를 넣습니다. 실패는 공통 ErrorResponse와 ErrorCode를 사용합니다. Front도 같은 envelope 타입을 정의해 `response.data.data`처럼 중앙에서 처리합니다.

**근거:** `common/response`, Front `types/api.ts`, `apiClient.ts`

### 질문 유형 4. 페이지 번호

#### [압박][설계와 다르게 구현] Q. 페이지는 0부터 시작하나요, 1부터 시작하나요?

**짧은 답변:** 현재 Backend Controller와 Spring `PageRequest` 기준은 0부터 시작합니다. Front에서 사용자에게 1부터 보여주면 API 호출 전에 0 기반으로 변환합니다.

**상세 답변:** 일부 문서 예시는 1 기반으로 남아 있어 혼동 가능성이 있습니다. 실제 계약을 말할 때는 현재 Controller와 Front wrapper를 우선하고, 명세 예시는 정정 대상이라고 설명합니다.

**근거:** Controller의 `page=0`, `PageRequest.of`, Front Admin 화면 문서 35장

### 질문 유형 5. Validation과 비즈니스 검증

#### [심화][구현 확인] Q. 입력 검증과 비즈니스 검증은 어떻게 나눴나요?

**짧은 답변:** 형식·필수값·범위는 Request DTO의 Bean Validation으로 검사하고, 존재 여부·소유권·상태 전이·잔액 같은 규칙은 Service에서 검사합니다.

**상세 답변:** 예를 들어 진행률이 0~1인지, EPUB 버전이 양수인지 같은 값 형식은 DTO에서 거릅니다. 해당 대여가 본인 것인지, 현재 EPUB 버전과 일치하는지, revision이 최신인지는 DB 상태가 필요하므로 Service에서 판단합니다.

**근거:** `ProgressUpdateRequest`, `ViewerService`, 백엔드 공통 개발 규칙

## 도메인 3. DB·ERD

### 질문 유형 1. 46개 테이블

#### [기본][구현 확인] Q. 테이블이 46개로 많은 이유는 무엇인가요?

**짧은 답변:** 화면 수를 따라 기계적으로 나눈 것이 아니라 회원·보상, 도서·콘텐츠, 대여·결제·독서 기록, 운영 데이터의 생명주기와 관계가 다르기 때문입니다.

**상세 답변:** 예를 들어 대여와 결제는 발생 의미가 다르고, 진도와 북마크는 읽는 동안 반복 변경됩니다. 포인트는 잔액과 이력이 필요하고, 쿠폰 정의·회원 발급·실제 사용도 구분됩니다. 외부 도서 후보와 정식 도서도 승인 전후 생명주기가 달라 분리했습니다.

**근거:** `src/main/resources/schema.sql`의 46개 `CREATE TABLE`

### 질문 유형 2. 런타임 스키마와 ERD

#### [압박][구현 확인] Q. ERD와 실제 DB가 다르면 무엇을 기준으로 하나요?

**짧은 답변:** 실제 동작은 `src/main/resources/schema.sql`을 기준으로 합니다. 설계 ERD는 의도를 설명하는 자료이고 차이가 있으면 숨기지 않고 변경 이유와 영향을 기록합니다.

**근거:** `AGENTS.md` 문서 우선순위

### 질문 유형 3. 현재값과 이력

#### [심화][구현 확인] Q. 현재 상태만 저장하지 않고 이력을 따로 둔 이유는 무엇인가요?

**짧은 답변:** 빠른 현재 조회와 변화 원인 추적이 모두 필요하기 때문입니다. 회원 포인트 잔액은 현재값이고 `point_history`는 지급·사용·조정 원인을 남깁니다.

**상세 답변:** 결제·쿠폰 사용·제재·감사 로그도 같은 이유로 현재 상태와 사건 이력을 구분합니다. 대신 중복 데이터의 정합성 위험이 있으므로 변경을 같은 트랜잭션과 서비스 경로로 묶습니다.

**근거:** `member`, `point_history`, `payment`, `coupon_usage`, `sanction_history`, `admin_audit_log`

### 질문 유형 4. DB 제약

#### [심화][구현 확인] Q. 애플리케이션에서 검사하면 DB 제약은 필요 없지 않나요?

**짧은 답변:** 필요합니다. 동시 요청이나 다른 변경 경로에서 애플리케이션 검사를 우회해도 잘못된 중복·상태 조합이 저장되지 않도록 마지막 방어선이 됩니다.

**상세 답변:** 외래 키는 참조 무결성을, UNIQUE는 한 회원의 동일 관계·멱등 키 중복을, CHECK는 Enum과 상태 범위를 방어합니다. 다만 DB 제약 오류만 사용자에게 그대로 노출하지 않고 비즈니스 오류로 변환합니다.

**근거:** 런타임 `schema.sql`, Entity·Repository

## 도메인 4. JPA·조회 설계

### 질문 유형 1. N+1

#### [압박][정적 구현 확인][성능 실행 확인 필요] Q. N+1 문제가 생길 수 있는 곳은 어디이고 어떻게 대응했나요?

**짧은 답변:** 도서의 출판사·저자·카테고리, 대여의 회원·도서·진도·결제, 관리자 목록의 연관 요약처럼 목록에서 연관 데이터를 반복 조회하는 곳이 후보입니다. 현재 코드는 Join Fetch, EntityGraph, ID 목록 일괄 조회와 집계 쿼리를 사용한 부분이 있습니다.

**상세 답변:** 모든 화면에 N+1이 없다고 단정하지 않습니다. 예를 들어 결제·대여 관리자 목록은 현재 페이지 ID를 모아 쿠폰·포인트·진도를 한 번에 조회하고, OAuth 계정과 쿠폰은 EntityGraph 또는 Join Fetch를 사용합니다. 실제 쿼리 수와 성능은 SQL 로그·프로파일링으로 추가 검증해야 합니다.

**근거:** `AdminPaymentService`, `AdminRentalService`, `PaymentRepository`, `OauthAccountRepository`, `MemberCouponRepository`

### 질문 유형 2. 읽기 전용 트랜잭션

#### [심화][구현 확인] Q. 조회 메서드에도 트랜잭션을 붙인 이유가 있나요?

**짧은 답변:** `open-in-view=false` 환경에서 필요한 지연 로딩을 서비스 조회 범위 안에서 끝내고, 읽기 의도를 명확히 하기 위해 `@Transactional(readOnly = true)`를 사용합니다.

**근거:** `BookService`, `ReadingService`, 관리자 조회 Service 주석

### 질문 유형 3. 통계 집계

#### [심화][구현 확인] Q. 통계 그래프를 날짜마다 반복 조회하나요?

**짧은 답변:** 완독·대여 추이는 기간 전체를 한 번에 `GROUP BY`하는 쿼리를 사용해 bucket마다 반복 조회하지 않게 보완했습니다.

**근거:** `ReadingProgressRepository`, `BookRentalRepository` 통계 추이 쿼리

## 도메인 5. 트랜잭션·동시성·멱등성

### 질문 유형 1. 트랜잭션 범위

#### [기본][구현 확인] Q. 트랜잭션은 어디까지 묶었나요?

**짧은 답변:** 하나의 사용자 요청이 성공했을 때 함께 성립해야 하는 데이터 변경을 묶었습니다. 유료 대여는 대여·결제·쿠폰·포인트·알림, 보상 수령은 수령 표시·포인트 또는 쿠폰 지급을 한 트랜잭션으로 처리합니다.

**근거:** `PaymentService`, `ChallengeService`

### 질문 유형 2. 비관적 락

#### [압박][구현 확인] Q. 비관적 락을 실제로 사용했나요?

**짧은 답변:** 네. 회원 상태·잔액 변경, 대여 시작, 진도 저장, 관리자 신고 처리, 도서·컬렉션 변경처럼 같은 행의 경쟁 변경을 직렬화해야 하는 경로에 `PESSIMISTIC_WRITE` 조회가 있습니다.

**상세 답변:** 모든 곳에 락을 거는 것은 아닙니다. 보상 수령은 조건부 UPDATE의 영향 행 수로 선점하고, 관리자 포인트 재요청은 멱등 키와 UNIQUE 제약을 함께 사용합니다. 문제 특성에 따라 락·조건부 갱신·멱등 키를 구분했습니다.

**근거:** `MemberRepository.findByIdForUpdate`, `ReadingProgressRepository.findByRentalIdForUpdate`, `BookReportRepository`, `ReviewReportRepository`, `CollectionRepository`

### 질문 유형 3. 낙관적 방식

#### [심화][구현 확인] Q. 뷰어 진도는 비관적 락인가요, 낙관적 락인가요?

**짧은 답변:** 저장 시 DB 행을 비관적으로 잠근 뒤 애플리케이션 revision을 비교하는 혼합 방식입니다. JPA `@Version`만 사용하는 전형적인 낙관적 락은 아닙니다.

**상세 답변:** 잠금은 동시에 수정되는 짧은 구간을 직렬화하고 revision은 오래된 탭의 요청인지 판단합니다. 현재 revision이 요청의 `expectedRevision`과 다르면 충돌로 반환합니다.

**근거:** `ViewerService.updateProgress`, `ReadingProgress.revision`

### 질문 유형 4. 조건부 갱신

#### [심화][구현 확인] Q. 보상 수령에는 왜 조회 후 락 대신 조건부 UPDATE를 사용했나요?

**짧은 답변:** `reward_claimed_at IS NULL`이라는 수령 가능 조건과 상태 변경을 한 SQL에 묶어, 영향 행이 1인 요청만 지급하도록 하기 위해서입니다.

**상세 답변:** 조회와 갱신을 분리하면 두 요청이 모두 미수령을 읽을 수 있습니다. 조건부 갱신은 DB가 한 요청만 성공시키므로 선점 결과가 명확합니다.

**근거:** `ChallengeProgressRepository.markRewardClaimedIfUnclaimed`

### 질문 유형 5. 멱등 키

#### [압박][구현 확인] Q. 모든 변경 API에 멱등 키가 있나요?

**짧은 답변:** 아닙니다. 현재 명시적 요청 멱등 키는 관리자 포인트 조정처럼 재전송 위험과 동일 요청 판정이 중요한 경로에 적용했습니다. 다른 경로는 UNIQUE, 상태 조건, 잠금, 이미 처리된 상태 반환을 사용합니다.

**근거:** `AdminPointAdjustService`, `PointHistory.requestId`

## 도메인 6. 보안

### 질문 유형 1. Google token 검증

#### [압박][구현·자동 테스트 근거 있음] Q. Front가 보낸 Google 사용자 정보를 그대로 신뢰하나요?

**짧은 답변:** 아닙니다. Front는 Google ID token을 보내고 Backend가 서명·시간·issuer·audience와 `email_verified`를 확인한 뒤 `sub`와 이메일을 추출합니다.

**상세 답변:** 신규 가입과 기존 계정 연결에 사용하는 신원도 검증된 token에서 가져옵니다. transition token은 access token과 목적을 분리해 일반 API 인증에 사용할 수 없게 합니다.

**근거:** `GoogleIdTokenValidators`, `GoogleIdTokenVerifier`, `TransitionTokenProvider`, Google 인증 테스트

### 질문 유형 2. 서버 재검증

#### [기본][구현 확인] Q. 화면에서 버튼을 숨기면 권한 검증이 끝난 것 아닌가요?

**짧은 답변:** 아닙니다. Front 제어는 사용자 경험이고 실제 요청에서는 서버가 회원 상태, 관리자 역할, 자원 소유권, 대여 권한을 다시 확인합니다.

**근거:** `SecurityConfig`, 각 Service의 memberId·상태 검증

## 도메인 7. Front·Backend 계약

### 질문 유형 1. API wrapper

#### [심화][구현·연동 확인] Q. 페이지에서 URL을 직접 호출하지 않은 이유는 무엇인가요?

**짧은 답변:** API endpoint·parameter·응답 envelope 처리를 `src/api` wrapper로 분리해 화면은 로딩·성공·빈 상태·오류 상태에 집중하도록 했습니다.

**근거:** Front `src/api`, `apiClient.ts`, User/Admin 화면 문서

### 질문 유형 2. 계약 불일치

#### [압박][구현 확인] Q. Front와 Backend 응답이 다를 때 어떻게 찾았나요?

**짧은 답변:** 화면 증상만 수정하지 않고 Front wrapper·TypeScript 타입·Backend DTO와 Controller parameter를 함께 대조했습니다. 실패를 가짜 데이터로 숨기는 fallback도 제거해 실제 계약 오류가 드러나게 했습니다.

**상세 답변:** 도서관 API는 과거 `region` 누락과 배열 응답 기대 차이가 있었지만 현재 Front가 필수 지역과 새 응답 구조를 사용합니다. 추천 응답 envelope, 통계 필드, 관리자 대여·결제 DTO도 같은 방식으로 정합화했습니다.

**근거:** Front `김건희_작업이력_정리.md` 7장과 현재 관련 소스

### 질문 유형 3. 화면 존재와 연동

#### [압박][문서 원칙] Q. 화면이 있으면 기능이 구현된 것 아닌가요?

**짧은 답변:** 아닙니다. route·화면·API wrapper·Backend endpoint·현재 계약 일치·실행 성공을 각각 구분합니다.

**상세 답변:** 화면이 mock이나 빈 상태만 보여줄 수 있고 wrapper가 있어도 Backend Controller가 없을 수 있습니다. 반대로 Backend API는 구현됐지만 화면이 없을 수 있습니다. 매뉴얼에서는 `구현`, `연동`, `실행 확인` 상태를 따로 표시합니다.

**근거:** 프로젝트현황 판정 기준, Front 화면 문서
