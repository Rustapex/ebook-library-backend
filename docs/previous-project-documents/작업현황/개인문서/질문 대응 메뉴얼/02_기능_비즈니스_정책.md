# K02. 기능·비즈니스 정책

## 도메인 1. 인증·회원

### 질문 유형 1. 일반 로그인 정책

#### [기본][구현 확인] Q. 어떤 회원이 로그인할 수 있나요?

**짧은 답변:** 일반 로그인은 아이디와 비밀번호가 일치하고 회원 상태가 `JOINED`인 경우에만 성공합니다. `SANCTIONED`, `WITHDRAWN`, `DEACTIVATED` 상태는 로그인할 수 없습니다.

**상세 답변:** 비밀번호는 평문으로 비교하지 않고 `PasswordEncoder.matches`를 사용합니다. 상태별 상세 원인을 로그인 응답으로 구분하면 계정 존재 여부가 노출될 수 있어 인증 실패로 수렴합니다. Google 로그인도 연결 회원의 상태가 `JOINED`가 아니면 거부합니다.

**근거:** `AuthService.login`, `GoogleAuthService.requireActive`

### 질문 유형 2. 관리자 권한

#### [심화][구현 확인] Q. JWT만 있으면 관리자 API를 호출할 수 있나요?

**짧은 답변:** 아닙니다. 인증 토큰이 유효해야 하고, Spring Security에서 `/api/v1/admin/**` 요청에 `ADMIN` 역할을 추가로 요구합니다.

**상세 답변:** Front의 Admin Guard는 잘못된 화면 이동을 막기 위한 사용자 경험 장치이고 최종 권한 판단은 서버가 합니다. 따라서 URL을 직접 입력하거나 Front 코드를 우회해도 일반 회원은 관리자 API를 사용할 수 없습니다.

**근거:** `SecurityConfig`의 `requestMatchers("/api/v1/admin/**").hasRole("ADMIN")`

### 질문 유형 3. Google 로그인

#### [심화][구현·연동 확인][설정상 비활성 가능] Q. Google 로그인은 어디까지 구현됐나요?

**짧은 답변:** Backend에는 ID token 검증, 신규 가입, 기존 계정 연결 흐름이 있고 Front 로그인 화면도 세 endpoint를 호출합니다. 다만 Backend 기본 설정은 비활성이므로 실제 배포 환경에서는 `GOOGLE_AUTH_ENABLED`와 Client ID 주입 여부를 별도로 확인해야 합니다.

**상세 답변:** Backend는 Google `sub`를 외부 계정 식별자로 사용하고 이메일만으로 자동 연결하지 않습니다. 동일 이메일의 기존 회원은 비밀번호 재인증 후 연결하며, 신규 회원은 단기 transition token으로 추가 가입 정보를 받습니다. access token과 transition token의 용도를 분리합니다.

**근거:** `GoogleAuthController`, `GoogleAuthService`, `GoogleIdTokenValidators`, Front `authApi.ts`, `U003Login/LoginPage.tsx`, `application.properties`

**예상 꼬리질문:** “코드는 있는데 배포에서 비활성이라면 구현 완료라고 할 수 있나요?”

### 질문 유형 4. 회원 탈퇴

#### [심화][구현·연동 확인] Q. 회원 탈퇴는 물리 삭제인가요?

**짧은 답변:** 물리 삭제하지 않고 상태를 `WITHDRAWN`으로 변경합니다. 결제·대여·포인트·신고 같은 기존 기록의 참조를 보존해야 하기 때문입니다.

**상세 답변:** 회원 행을 잠근 뒤 관리자 계정인지, 현재 상태가 `JOINED`인지, 비밀번호가 맞는지, 진행 중인 `READY`·`READING` 대여가 있는지 확인합니다. 조건을 통과하면 탈퇴 사유와 상태를 변경합니다.

**근거:** `MemberService.withdraw`, `BookRentalRepository.existsByMember_MemberIdAndRentalStatusIn`

## 도메인 2. 도서·검색·카테고리·컬렉션

### 질문 유형 1. 검색 대상

#### [기본][구현 확인] Q. ISBN으로도 검색할 수 있나요?

**짧은 답변:** 네. 현재 사용자 도서 검색은 제목뿐 아니라 ISBN, 출판사, 저자, 활성 키워드를 부분 일치 대상으로 사용합니다.

**상세 답변:** `BookController`가 검색어를 `BookService.searchBooks`에 전달하고, `BookRepository` 쿼리가 도서 제목·ISBN·출판사명과 저자·키워드 관계를 함께 검사합니다. 발표에서 ISBN 검색을 말할 수 있지만 Front 검색 UI가 어떤 입력을 제공하는지와는 구분합니다.

**근거:** `BookController.searchBooks`, `BookService.searchBooks`, `BookRepository.searchAvailableBooks`

### 질문 유형 2. 카테고리 범위

#### [심화][구현 확인] Q. 상위 카테고리를 선택하면 하위 카테고리도 모두 조회하나요?

**짧은 답변:** 카테고리 탐색과 키워드 검색의 동작이 다릅니다. 카테고리 목록 탐색은 선택한 상위 분류의 하위 ID를 포함할 수 있지만, 키워드 검색에서 지정한 `categoryId`는 현재 검색 조건의 정확한 카테고리 기준으로 처리합니다.

**상세 답변:** 두 화면의 목적이 다르기 때문에 발표 대본에서도 “항상 하위 카테고리를 포함한다”고 일반화하지 않습니다. 카테고리 탐색은 분류를 넓게 보는 기능이고 검색 조건의 카테고리는 결과를 좁히는 필터입니다.

**근거:** `CategoryService`, `BookService.searchBooks`, 관련 Repository 조건

### 질문 유형 3. 정렬과 필터

#### [기본][구현 확인] Q. 검색 결과를 어떤 기준으로 줄일 수 있나요?

**짧은 답변:** 검색어와 카테고리, 무료·유료 대여 유형을 적용하고 제목·최신·인기 기준으로 정렬합니다. 페이지와 크기도 query parameter로 받습니다.

**근거:** `BookController.searchBooks`, `BookSearchCriteria`, `BookService.resolveSort`

### 질문 유형 4. 관련 도서

#### [심화][구현 확인] Q. 관련 도서는 AI 추천인가요?

**짧은 답변:** 아닙니다. 현재는 규칙 기반 추천입니다. 같은 저자·카테고리·키워드 중 요청한 한 가지 기준으로 후보를 찾고 대여 수, 평균 평점, 등록일 순으로 정렬합니다.

**상세 답변:** 여러 기준을 AI 모델로 결합하거나 개인 행동을 학습하는 구조는 아닙니다. 구현 수준을 과장하지 않고 “설명 가능한 규칙 기반 관련 도서 조회”라고 답합니다.

**근거:** `BookService.getRecommendations`, `BookRepository.findRecommendations`

### 질문 유형 5. 컬렉션

#### [기본][구현·연동 확인] Q. 컬렉션은 무엇이고 카테고리와 무엇이 다른가요?

**짧은 답변:** 카테고리는 도서의 분류이고, 컬렉션은 운영자가 특정 주제나 노출 목적에 맞춰 도서를 묶고 순서를 정하는 전시 단위입니다.

**상세 답변:** 컬렉션은 사용자 목록·상세 조회와 관리자 목록·상세·생성·기본정보·도서 구성·상태 변경 API가 있습니다. 카테고리처럼 고정 분류 체계를 표현하기보다 홈과 이벤트성 탐색을 운영하는 데 사용합니다.

**근거:** `CollectionController`, `AdminCollectionController`, `collection`, `collection_book`

## 도메인 3. 대여·결제

### 질문 유형 1. 무료·유료 흐름

#### [기본][구현·연동 확인] Q. 무료 대여와 유료 대여는 어떻게 다르나요?

**짧은 답변:** 무료 대여는 도서와 회원 조건을 확인한 뒤 대여만 생성합니다. 유료 대여는 쿠폰·포인트를 검증하고 대여와 서비스 내부 결제 내역, 사용 이력과 알림까지 하나의 트랜잭션에서 처리합니다.

**근거:** `RentalService.createFreeRental`, `PaymentService.createPaidRentalAndPayment`

### 질문 유형 2. 대여 상태

#### [심화][구현 확인] Q. `READY`, `READING`, `OWNED`는 무엇인가요?

**짧은 답변:** `READY`는 대여 후 아직 읽기 시작하지 않은 상태, `READING`은 뷰어에 진입해 읽기 시작한 상태, `OWNED`는 만료 없이 소장하는 상태입니다.

**상세 답변:** 대여는 항상 `READY`로 생성되고 뷰어 최초 진입 시 `READING`으로 전환됩니다. `READY`와 `READING`은 대여 종료 시각을 검사하지만 `OWNED`는 만료 검사를 하지 않습니다.

**근거:** `BookRental.create`, `BookRental.startReading`, `RentalService.validateRental`

### 질문 유형 3. 0원 결제

#### [압박][구현 확인] Q. 할인 후 결제금액이 0원이어도 `PAYMENT`를 저장하나요?

**짧은 답변:** 네. 유료 도서를 쿠폰과 포인트로 전액 차감해도 유료 대여가 어떤 가격과 할인으로 완료됐는지 남기기 위해 결제 행을 저장합니다.

**상세 답변:** `originalAmount`와 최종 `amount`, 결제 상태·시각을 남겨 대여 결과와 할인 이력을 연결합니다. 결제 행을 생략하면 무료 도서 대여와 유료 도서의 전액 할인 대여를 이력에서 구분하기 어렵습니다.

**근거:** `PaymentService.createPaidRentalAndPayment`, `Payment.create`

### 질문 유형 4. 쿠폰·포인트 성격

#### [심화][구현 확인] Q. 쿠폰과 포인트는 결제수단인가요?

**짧은 답변:** 현재 구현에서는 독립 외부 결제수단이 아니라 원래 대여 가격에서 차감하는 할인 수단입니다. 최종 금액과 사용 이력은 별도로 남깁니다.

**근거:** `PaymentService`의 `couponDiscount`, `pointUsed`, `amount` 계산

### 질문 유형 5. 외부 결제

#### [압박][부분 구현] Q. 실제 카드 결제까지 구현했나요?

**짧은 답변:** 아닙니다. 현재 `PAYMENT`는 서비스 내부 결제 완료 기록이며 외부 PG 승인·취소·환불 연동은 구현 범위에 없습니다.

**상세 답변:** 따라서 “카드 결제를 구현했다”고 말하지 않고 “유료 대여의 금액·할인·결제 이력과 데이터 정합성을 구현했다”고 답합니다. 실제 서비스로 확장하려면 PG 승인 전후 상태, 결제 키, 웹훅, 중복 승인 방지, 취소·환불 이력이 필요합니다.

**근거:** `PaymentService`, `Payment`, 최종 API 제외 목록

### 질문 유형 6. 실패와 롤백

#### [압박][구현 확인] Q. 대여 생성 후 포인트 차감이 실패하면 어떻게 되나요?

**짧은 답변:** 유료 대여 메서드 전체가 하나의 DB 트랜잭션이므로 대여·결제·쿠폰 사용·포인트 차감·알림 중 하나가 실패하면 전체가 롤백됩니다.

**근거:** `PaymentService.createPaidRentalAndPayment`의 `@Transactional`

## 도메인 4. EPUB 뷰어·독서 기록

### 질문 유형 1. 열람 권한

#### [기본][구현·연동 확인] Q. URL만 알면 다른 사람의 EPUB을 볼 수 있나요?

**짧은 답변:** 볼 수 없습니다. 뷰어 세션과 EPUB 요청에서 현재 회원의 대여인지, 대여가 열람 가능한 상태와 기간인지 확인합니다.

**근거:** `ViewerService.requireReadableRental`, `ViewerController`

### 질문 유형 2. 진도 저장

#### [심화][구현 확인] Q. 독서 위치는 무엇을 저장하나요?

**짧은 답변:** EPUB 버전, CFI, chapter href, spine index, 전체 진행률, 마지막 읽은 시각과 revision을 저장합니다.

**상세 답변:** EPUB은 인쇄 페이지 번호처럼 고정된 위치만으로 복원하기 어렵기 때문에 CFI와 spine 정보를 함께 사용합니다. 진행률은 목록과 통계에 사용하고 revision은 충돌 판단에 사용합니다.

**근거:** `ReadingProgress`, `ProgressUpdateRequest`, `ViewerService.updateProgress`

### 질문 유형 3. 여러 창의 충돌

#### [압박][구현 확인] Q. 여러 창에서 진도를 저장하면 오래된 값이 덮어쓰지 않나요?

**짧은 답변:** 저장 요청의 `expectedRevision`과 현재 revision을 비교합니다. 일치하지 않으면 충돌 응답을 주고 최신 상태를 다시 조회하게 합니다.

**상세 답변:** 저장 대상 진도 행을 잠금 조회한 뒤 EPUB 버전과 revision을 확인합니다. 단순 마지막 쓰기 우선 방식보다 오래된 탭이 최신 위치를 덮는 문제를 명시적으로 드러냅니다.

**근거:** `ViewerService.updateProgress`, `ReadingProgressRepository.findByRentalIdForUpdate`, `ProgressRevisionConflictException`

### 질문 유형 4. EPUB 교체

#### [심화][구현 확인] Q. EPUB 파일이 교체되면 기존 진도와 북마크는 어떻게 되나요?

**짧은 답변:** 진도와 북마크에 EPUB 버전을 저장합니다. 현재 파일 버전과 다른 위치를 그대로 사용하지 않고 진도는 새 버전에 맞춰 초기화하며, 북마크 조회도 현재 버전을 기준으로 합니다.

**근거:** `ReadingProgressRepository.resetForEpubVersion`, `BookmarkService`

### 질문 유형 5. 완독 처리

#### [심화][구현 확인] Q. 진행률만 높으면 완독으로 처리하나요?

**짧은 답변:** EPUB 끝에 도달했다는 값과 진행률 98% 이상을 함께 확인하고 이미 완독이면 다시 처리하지 않습니다.

**근거:** `ReadingProgress.completeIfEpubEnd`

## 도메인 5. 리뷰·찜·신고

### 질문 유형 1. 리뷰 작성 조건

#### [기본][구현 확인] Q. 아무 사용자나 리뷰를 작성할 수 있나요?

**짧은 답변:** 아닙니다. 해당 회원이 그 책을 대여했고 실제 읽기 시작 시각이 있어야 리뷰를 작성할 수 있습니다.

**근거:** `ReviewService.validateStartedRental`

### 질문 유형 2. 리뷰와 별점

#### [심화][구현 확인] Q. 리뷰와 별점을 왜 별도 테이블로 관리하나요?

**짧은 답변:** 리뷰 내용의 상태 변경과 별점 집계를 분리하기 위해서입니다. API에서는 작성 흐름상 함께 받지만 DB에서는 리뷰와 별점을 별도 행으로 관리합니다.

**상세 답변:** 리뷰를 사용자가 삭제해도 기존 별점을 유지하는 현재 정책이 있고, 삭제된 리뷰를 다시 작성할 때는 기존 별점을 재사용합니다. 따라서 리뷰 내용과 별점의 생명주기가 완전히 같지 않습니다.

**근거:** `review`, `rating` 테이블, `ReviewService.createReview`

### 질문 유형 3. 삭제·숨김

#### [심화][구현 확인] Q. 사용자 삭제와 관리자 숨김은 무엇이 다른가요?

**짧은 답변:** 수령 표시와 포인트·쿠폰 지급을 같은 트랜잭션에서 처리하므로 지급이 실패하면 수령 시각도 롤백됩니다.

### 질문 유형 4. 포인트 잔액과 이력

#### [압박][구현 확인] Q. 포인트를 `MEMBER`와 `POINT_HISTORY`에 모두 저장하면 정합성 문제가 없나요?

**짧은 답변:** 현재 잔액은 빠른 조회와 검증에 사용하고 이력은 변화 원인과 감사에 사용합니다. 두 값을 변경하는 서비스 로직을 같은 트랜잭션에 두고 관리자 조정은 조정 후 잔액 스냅샷도 남깁니다.

**상세 답변:** 중복 저장이므로 정합성 위험이 없다고 말할 수는 없습니다. 모든 변경 경로를 서비스로 통일하고 DB 제약·트랜잭션·회귀 테스트로 관리합니다. 장기적으로는 잔액 재계산 검증이나 정기 대조가 필요합니다.

**근거:** `Member.pointBalance`, `PointHistory`, `PointService`, `AdminPointAdjustExecutor`

**짧은 답변:** 회원별 `requestId`로 기존 이력을 먼저 확인합니다. 같은 요청이면 이전 결과를 재사용하고, 동일 키에 다른 금액이나 설명이 오면 충돌로 처리합니다.
