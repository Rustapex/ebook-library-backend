# K06. 배포·운영

## 도메인 1. Backend CI/CD

### 질문 유형 1. 전체 배포 흐름

#### [기본][배포 코드 확인] Q. Backend는 어떻게 배포하나요?

**짧은 답변:** feature branch에서 PR을 만들면 Backend CI가 실행되고, main 병합 후 운영자가 Production CD를 수동 실행합니다. CD는 GitHub OIDC로 AWS 임시 권한을 얻어 immutable ECR image를 만들고 SSM Run Command로 EC2에 배포한 뒤 container health와 API를 검증합니다.

**상세 답변:** main push만으로 production이 자동 변경되지는 않습니다. 배포할 main의 full SHA와 확인 값을 입력하고, 해당 SHA의 CI 성공과 현재 production metadata를 대조한 뒤 진행합니다.

**근거:** `.github/workflows/backend-ci.yml`, `backend-cd.yml`, `docs/배포/CI-CD_개발자_사용가이드.md`

### 질문 유형 2. Backend CI

#### [심화][배포 코드 확인] Q. Backend CI는 무엇을 검사하나요?

**짧은 답변:** MySQL 8.0.40과 8.0.42에서 schema·runtime contract와 Gradle test를 실행하고, Docker build·Compose 검증과 credential pattern 검사를 수행합니다.

**상세 답변:** CI DB는 production과 timezone·charset·collation·sql mode를 맞추고 PR base와 head schema를 독립 비교합니다. CI가 실패하면 merge와 Production CD를 진행하지 않는 것이 원칙입니다.

**근거:** Backend CI/CD 개발자 가이드 3장

### 질문 유형 3. immutable release

#### [압박][배포 코드 확인] Q. 왜 `latest` 대신 full SHA와 digest를 사용하나요?

**짧은 답변:** 어떤 코드를 배포했는지 재현하고 같은 tag가 다른 image를 가리키는 일을 막기 위해서입니다.

**상세 답변:** CD는 GitHub Deployment, SSM metadata, EC2 설정과 실제 running container digest가 일치하는지 확인합니다. production tag를 다른 commit으로 이동하거나 재사용하지 않습니다.

**근거:** Backend 배포 가이드 7·10장

### 질문 유형 4. Backend rollback

#### [압박][현재 제한] Q. Backend 배포 실패 시 자동 롤백하나요?

**짧은 답변:** 현재 자동 롤백은 구현하지 않았습니다. 이전 image와 현재 DB schema·EPUB storage 계약의 호환성을 확인한 뒤 별도 승인된 수동 SSM 절차로 처리합니다.

**상세 답변:** 단일 EC2이고 staging 검증 환경이 없으며 schema가 바뀌면 단순 image rollback이 더 큰 장애를 만들 수 있습니다. RDS snapshot 복구는 일반 롤백이 아니라 재해 복구로 구분합니다.

**근거:** Backend 배포 가이드 9장

## 도메인 2. Frontend CI/CD

### 질문 유형 1. Front CI

#### [기본][배포 코드 확인] Q. Front도 CI가 있나요?

**짧은 답변:** 네. PR과 main push에서 `npm ci`, production dependency audit, ESLint, TypeScript·Vite build를 수행합니다.

**근거:** Front `.github/workflows/frontend-ci.yml`, `docs/배포/CI-CD_운영.md`

### 질문 유형 2. Production CD

#### [심화][배포 코드 확인] Q. Front는 main에 push하면 바로 배포되나요?

**짧은 답변:** 아닙니다. CI는 자동이지만 Production CD는 운영자가 full SHA와 production 확인 값을 입력해 수동 실행합니다.

**상세 답변:** build 결과는 S3의 SHA별 release prefix에 올리고 검증 후 `current`로 승격합니다. asset을 먼저 반영하고 `index.html`을 마지막에 반영한 뒤 CloudFront invalidation과 deep-link·cache·CORS smoke를 수행합니다.

**근거:** Front `frontend-cd.yml`, CI/CD 운영 문서

### 질문 유형 3. Front rollback

#### [심화][배포 코드 확인] Q. Front는 어떻게 롤백하나요?

**짧은 답변:** 기존 `releases/<release-id>`의 `index.html` 존재를 확인한 뒤 rollback operation과 full SHA를 입력합니다. 승격·CloudFront invalidation·smoke는 일반 배포와 동일하게 수행합니다.

**상세 답변:** 기존 브라우저가 참조하는 hashed asset을 보호하기 위해 `current/assets`의 이전 asset을 첫 단계에서 바로 삭제하지 않습니다.

**근거:** Front CI/CD 운영 문서

### 질문 유형 4. dependency 위험

#### [압박][현재 제한] Q. Front 의존성 취약점은 없나요?

**짧은 답변:** 현재 production audit에 `epubjs` 계열 high와 `react-router-dom` moderate 항목이 문서화돼 있습니다. CI는 critical 이상을 차단하며 major 호환성이 필요한 업그레이드는 별도 작업으로 남아 있습니다.

**근거:** Front CI/CD 운영 문서 `알려진 non-blocking 항목`

## 도메인 3. Backend·Frontend 동시 변경

### 질문 유형 1. 배포 순서

#### [심화][운영 설계 확인] Q. Backend와 Front가 함께 바뀌면 무엇을 먼저 배포하나요?

**짧은 답변:** DB migration 필요 여부를 먼저 확인하고, 필요하면 migration을 적용한 뒤 Backend를 배포·검증하고 Front를 배포한 다음 E2E 기능을 확인합니다.

**상세 답변:** Front가 아직 없는 endpoint를 먼저 호출하지 않도록 backend-first를 기본으로 합니다. 다만 호환 가능한 API 변경이나 feature flag를 사용하면 두 버전이 겹치는 시간도 안전하게 만들 수 있습니다.

**근거:** Backend 배포 가이드 11장

### 질문 유형 2. DB migration

#### [압박][운영 제한] Q. 애플리케이션 배포와 DB 변경을 자동으로 동시에 적용하나요?

**짧은 답변:** schema 변경은 별도 계약과 증거를 확인하는 gate로 다룹니다. 단순 애플리케이션 rollback으로 DB를 되돌릴 수 없기 때문에 배포 전 호환성을 먼저 판단합니다.

**근거:** `CI-CD_구축계획.md` 6~8·12장, Backend 배포 가이드

## 도메인 4. 환경 설정과 보안

### 질문 유형 1. 비밀정보

#### [기본][배포 설계 확인] Q. AWS Key나 `.env`를 GitHub에 올리나요?

**짧은 답변:** 올리지 않습니다. AWS는 GitHub OIDC 임시 자격증명을 사용하고 Backend `.env.prod`는 EC2에만 둡니다. Docker image와 Action log에 비밀값을 포함하지 않습니다.

**근거:** Backend 배포 가이드 10장

### 질문 유형 2. Front 환경변수

#### [심화][배포 설계 확인] Q. `VITE_*` 환경변수는 비밀값인가요?

**짧은 답변:** browser bundle에 포함되므로 비밀값으로 취급할 수 없습니다. API base URL과 browser용 지도 Client ID 같은 공개 설정만 넣고 Client secret이나 AWS access key는 넣지 않습니다.

**근거:** Front CI/CD 운영 문서

### 질문 유형 3. 기능 flag

#### [심화][설정상 비활성 가능] Q. 구현된 외부 연동이 환경마다 다른 이유는 무엇인가요?

**짧은 답변:** Google 인증과 외부 도서 API는 환경 변수로 활성화합니다. 설정과 키가 없는 환경에서도 서비스의 나머지 기능이 기동하도록 기본값을 비활성으로 두었습니다.

**상세 답변:** Google은 활성화됐는데 Client ID가 없으면 audience 검증을 할 수 없으므로 fail-fast합니다. 외부 연동 코드 존재와 운영 활성 상태를 따로 확인해야 합니다.

**근거:** `GoogleAuthConfig`, `application*.properties`, `BookApiProperties`

## 도메인 5. 외부 장애 대응

### 질문 유형 1. 도서관 API

#### [압박][구현 확인] Q. 외부 도서관 API 장애가 전체 서비스 장애로 이어지지 않나요?

**짧은 답변:** 도서관 검색 안에서 fresh cache, 외부 호출, stale cache, 관리자 수동 정보 순으로 fallback하고 모두 없을 때 해당 요청만 503으로 처리합니다.

**상세 답변:** 같은 검색의 동시 외부 호출을 합치고 호출 수를 제한합니다. 예상한 외부 실패는 fallback하지만 내부 버그까지 숨기지 않도록 예외 종류를 구분합니다.

**근거:** `PhysicalLibrarySearchService`, `InfoNaruLibraryConcurrencyLimiter`

### 질문 유형 2. 외부 데이터 표시

#### [심화][구현 확인] Q. 오래된 cache를 사용자에게 숨기나요?

**짧은 답변:** 숨기지 않습니다. 응답의 `stale`과 `warnings`로 이전 결과 또는 수동 정보임을 알리고 Front가 안내 문구를 표시합니다.

**근거:** `LibrarySearchResponse`, U-024 화면

## 도메인 6. 로그·감사·모니터링

### 질문 유형 1. 일반 로그와 감사 로그

#### [심화][구현 확인] Q. 애플리케이션 로그가 있는데 감사 로그를 DB에 따로 둔 이유는 무엇인가요?

**짧은 답변:** 애플리케이션 로그는 장애 분석 중심이고 감사 로그는 관리자 행위의 대상·시점·변경 전후를 업무 데이터로 조회하기 위한 것입니다.

**근거:** `AdminAuditLogService`, `admin_audit_log`

### 질문 유형 2. 모니터링

#### [압박][운영 보완] Q. 배포 후 오류와 성능을 어떻게 모니터링하나요?

**짧은 답변:** 현재 CI/CD health·API smoke와 애플리케이션 로그·감사 로그 근거는 있지만, 지표·분산 추적·알림을 포함한 관측 체계는 보완 과제입니다.

**상세 답변:** 다음 단계는 요청 실패율·응답 시간·DB connection·락 대기·외부 API 지연을 수집하고 임계치 알림과 대시보드를 구성하는 것입니다. 현재 없는 체계를 운영 중이라고 말하지 않습니다.

**근거:** 발표 대본 슬라이드 25, 배포 문서

## 도메인 7. 현재 배포 확인 범위

### 질문 유형 1. 이번 문서 조사에서 확인한 것

#### [기본][배포 코드 확인][실행 확인 필요] Q. 이 매뉴얼을 만들면서 실제 production 배포도 다시 확인했나요?

**짧은 답변:** workflow와 운영 문서, 로컬 소스는 확인했지만 production workflow를 실행하거나 실제 URL의 로그인·대여·외부 API를 재검증하지는 않았습니다.

**상세 답변:** 따라서 배포 구조는 설명할 수 있지만 특정 기능의 현재 운영 성공 여부는 별도 smoke·E2E 결과가 필요합니다.
