# 1. 프로젝트 개요

ABC(Acorn Book Cloud)는 사용자가 전자책을 탐색·대여·열람하고, 독서 활동을 챌린지와 보상으로 이어 갈 수 있는 전자책 대여 플랫폼이다. 운영자는 관리자 기능을 통해 서비스 현황을 확인하고, 도서와 컬렉션을 관리하며, 변경 이력을 추적한다.

이 프로젝트의 백엔드는 화면이 요청할 수 있는 API를 제공하는 역할에 그치지 않는다. 공개할 수 있는 도서만 보여 주는 정책, 읽던 위치를 복원하는 기준, 중복되지 않는 보상 지급, 운영 이력의 추적 가능성처럼 서비스의 신뢰를 만드는 규칙을 함께 처리한다.

# 2. 개인 역할과 기여 방향

## 2.1 개인 역할

나는 사용자 경험의 시작인 도서 탐색과 전자책 열람, 독서 보상 흐름, 운영자용 대시보드·통계·감사 로그 및 도서 관리 영역의 API 설계·구현·검증을 담당했다.

한 문장으로 정리하면 다음과 같다.

> **사용자가 책을 발견해 읽고 보상을 받는 흐름과, 운영자가 그 흐름을 관리·점검하는 API를 연결하는 역할을 맡았다.**

## 2.2 업무 방식

기능 구현 전에는 API 명세, 화면 흐름, 실제 데이터베이스 구조가 서로 맞는지 먼저 확인했다. 구현 후에는 정상 응답만 보지 않고 입력 오류, 권한, 중복 처리, 데이터베이스 반영 여부를 나누어 확인하려 했다. 코드리뷰에서 발견된 사항은 단순 수정으로 끝내지 않고 API 계약과 수동 검증 계획까지 함께 보완했다.

# 4. 개발 기준과 설계 기준

## 4.1 실제 데이터 구조를 최우선 기준으로 삼기

기획·API 명세·설계 문서가 항상 실제 실행 구조와 일치하는 것은 아니다. 그래서 구현 전에 실제 스키마와 제약조건을 확인하고, 문서에만 존재하는 테이블이나 상태값을 그대로 전제하지 않았다. 불일치가 있으면 조용히 우회하기보다 구현 근거와 범위 제외를 작업 문서에 남겼다.

## 4.2 화면에 필요한 데이터만, 안전한 형태로 제공하기

API는 데이터베이스 객체를 그대로 내보내지 않고 화면에 필요한 응답 형식으로 변환한다. 일반 사용자에게는 공개 가능한 도서만 보여 주고, 관리자 상세 조회에서도 전자책 본문·파일·페이지처럼 보호해야 할 데이터는 응답에서 제외하는 기준을 적용했다.

## 4.3 한 번만 일어나야 하는 일을 중복 처리하지 않기

출석, 보상 수령, 쿠폰 지급, 완독, 도서 상태 변경은 중복되면 사용자 신뢰와 데이터 정합성을 해칠 수 있다. 따라서 고유 제약, 수령 상태, 사유 기록, 잠금 및 예외 응답을 함께 고려했다.

## 4.4 검증 결과를 과장하지 않기

자동 테스트 성공, Swagger 수동 호출, Postman 동시 요청, DB 반영 확인은 서로 다른 수준의 증거다. 이 문서에서는 실행된 결과만 ‘검증 완료’로 쓰고, 계획이나 체크리스트만 존재하는 항목은 ‘검증 예정’ 또는 ‘증거 보완 필요’로 구분한다.

# 5. 대표 구현 사례 1 — 실제 데이터 기준으로 API 설계를 바로잡기

## 기능 카드

| 구분 | 내용 |
|---|---|
| 기능명 | 전자책 뷰어·읽기 진행 API의 데이터 기준 정리 |

| 담당 범위 | 페이지 조회, 진행도 저장, 북마크, 최근 읽은 책의 API 경계와 데이터 처리 기준 |
| 증거 | `2026-07-02_뷰어-북마크-진행API_구현계획.md` |

## 요구사항과 문제

사용자는 전자책을 읽다가 나가도 다음 방문에서 마지막 위치부터 이어 읽을 수 있어야 한다. 페이지를 열고, 읽은 위치를 저장하고, 필요한 곳에 북마크를 남기며, 마지막 페이지에 도달했을 때만 완독으로 처리해야 한다.

초기 명세에는 뷰어 관련 데이터로 별도의 파일 테이블이 언급되어 있었지만, 실제 데이터베이스에는 해당 테이블이 존재하지 않았다. 명세만 믿고 구현하면 존재하지 않는 데이터를 조회하는 API가 만들어질 위험이 있었다.

## 설계 결정

- 실제 데이터베이스에 있는 페이지 본문 데이터를 기준으로 뷰어 내용을 제공한다.
- 대여 생성·대여 목록은 별도 기능으로 두고, 뷰어는 유효한 대여가 이미 존재한다는 경계 안에서 처리한다.
- 페이지 조회, 진행도 저장, 북마크 추가·삭제·목록, 최근 읽은 책을 역할별 API로 구분한다.
- 마지막 페이지에 **처음** 도달했을 때만 완독 상태를 기록한다.
- 같은 대여의 같은 페이지에 북마크가 중복 저장되지 않도록 고유성 기준을 둔다.
- 최근 읽은 책 응답에는 표지와 현재/전체 페이지 정보를 포함해 이어 읽기 판단을 돕는다.

## 구현·검증 관점

이 사례의 핵심은 특정 코드가 아니라 “문서에 적힌 구조”가 아니라 “실제로 동작하는 데이터 구조”를 기준으로 설계를 수정했다는 점이다. 현재 작업현황 문서는 설계·구현 계획 중심이므로, 최종 제출 전에는 다음 증거를 추가한다.

- [ ] 페이지 조회, 진행 저장, 북마크 추가·삭제·목록의 실제 응답 캡처
- [ ] 마지막 페이지 도달 후 한 번만 완독 처리되는 DB 확인
- [ ] 같은 페이지 북마크 중복 요청의 오류 응답 확인
- [ ] 최근 읽은 책에서 마지막 위치와 표지가 표시되는 화면 또는 Swagger 결과

## 결과

명세와 실제 데이터 구조가 달라도 무리하게 기능을 만들지 않고, 서비스가 보유한 데이터로 설명 가능한 API 경계를 세웠다. 이는 이후 통계·완독·대여 도메인과 연동할 때도 불필요한 데이터 의존을 줄이는 기반이 된다.

# 6. 대표 구현 사례 2 — 도서 탐색 API를 공개 정책과 성능까지 고려해 구성하기

## 기능 카드

| 구분 | 내용 |
|---|---|
| 기능명 | 도서·카테고리·컬렉션 탐색 API |
| 관련 화면/API | 도서 목록·검색·상세, 카테고리, 컬렉션 / `API-BOOK-*`, `API-CATEGORY-001`, `API-COLLECTION-*` |
| 담당 범위 | 공개 목록, 도서 상세, 카테고리·컬렉션 조회와 응답 규칙 검토 |
| 증거 | `2026-07-15_도서-카테고리-컬렉션API_코드리뷰_및_재검증계획.md` |

## 요구사항과 문제

도서 탐색은 단순히 제목을 목록으로 보여 주는 기능이 아니다. 일반 사용자에게는 대여 가능한 도서만 보여야 하고, 카테고리는 활성 상태와 정해진 순서를 지켜야 하며, 컬렉션에도 비공개 또는 이용 불가 도서가 섞여서는 안 된다. 로그인 사용자의 찜 여부와 최근 대여 상태도 화면에 맞게 일관되게 보여야 한다.

또한 목록의 카드마다 찜 여부를 한 번씩 조회하면, 목록이 길어질수록 불필요한 데이터 조회가 늘어난다.

## 설계 결정과 구현 내용

- 주요 도서 목록과 검색은 이용 가능한 도서 상태를 기준으로 제한했다.
- 카테고리는 활성 상태만 제공하고, 표시 순서와 식별자를 기준으로 안정적인 정렬을 적용했다.
- 컬렉션 상세에서는 이용 불가 도서를 제외하도록 했다.
- 도서 카드의 찜 여부는 목록 단위로 조회해 반복 조회를 줄이는 방향을 적용했다.
- 도서 상세의 최근 대여 상태는 생성 시각만으로 판단하지 않고 식별자를 추가 기준으로 사용해 순서가 같을 때도 결과가 흔들리지 않게 했다.
- 공통 응답과 페이지 응답 형식을 사용하고, 데이터베이스 객체를 직접 노출하지 않았다.

## 검증 방법과 결과

관련 자동 테스트는 도서 서비스·저장소, 페이지 저장소, 카테고리 서비스·저장소, 컬렉션 저장소를 대상으로 실행되었고 **21건 성공, 실패 0건**으로 기록되어 있다.

다만 이 수치는 현재 존재하는 테스트 범위의 성공을 의미한다. 공개 Controller 계약, 컬렉션 Service, Swagger 응답, 페이지 파라미터 조합까지 모두 검증됐다는 의미는 아니다. 따라서 최종 문서에는 자동 테스트 결과와 함께 대표 API의 수동 호출 증거를 추가한다.

## 결과

사용자에게 무엇을 보여 줄지라는 정책, 목록 응답의 성능, 화면 응답의 일관성을 함께 다뤘다. ‘조회 API’도 서비스 정책과 데이터 접근 방식을 함께 설계해야 한다는 점을 확인한 사례다.

| 담당 범위 | 출석 처리, 챌린지 진행·수령, 포인트 이력, 쿠폰 조회·발급, 관리자 보상 관리 |
| 증거 | `2026-07-06_챌린지-출석-포인트-쿠폰API_구현계획.md`, `2026-07-09_쿠폰실제지급_Swagger검증_체크리스트.md` |

## 요구사항과 문제

챌린지 보상은 화면에서 “수령 완료”라고만 표시해서는 부족하다. 포인트 보상은 회원 잔액과 이력이 함께 바뀌어야 하며, 쿠폰 보상은 회원에게 실제 쿠폰이 발급되어야 한다. 출석과 보상 수령은 중복 요청이 발생해도 같은 보상이 여러 번 지급되면 안 된다.

## 설계 결정

- 같은 회원이 같은 날 다시 출석하지 못하도록 출석 날짜 기준의 중복을 오류로 처리한다.
- 챌린지 진행도는 이번 범위에서 출석 행동과 연동하고, 대여·리뷰·완독 연동은 후속 범위로 분리한다.
- 포인트 지급 또는 관리자 조정은 포인트 이력 저장과 회원 잔액 갱신이 함께 성공하도록 같은 처리 단위로 다룬다.
- 잔액보다 큰 포인트 차감은 허용하지 않는다.
- 챌린지 쿠폰 보상은 쿠폰 식별자와 수량을 검증한 뒤, 수령 시 실제 회원 쿠폰을 수량만큼 생성한다.
- 이미 수령한 보상은 수령 시각을 기준으로 다시 지급하지 않는다.
- 관리자 쿠폰 목록은 쿠폰 정의에 발급·사용·만료 수를 함께 보여 주되, 새로운 테이블을 만들기보다 기존 회원 쿠폰 데이터를 집계한다.

## 구현 흐름

```text
출석 요청
  → 중복 출석 여부 확인
  → 챌린지 진행도 갱신
  → 달성·미수령 여부 확인
  → 보상 수령 요청
  → 포인트 이력·잔액 반영 또는 회원 쿠폰 실제 발급
  → 수령 시각 기록으로 재수령 차단
```

## 검증 방법

- 저장소 테스트와 빌드 성공 기록을 확인했다.
- 쿠폰 보상은 쿠폰 식별자 누락, 존재하지 않는 쿠폰, 수량 지정, 실제 수령의 성공·실패 시나리오를 Swagger 체크리스트로 만들었다.
- 실제 수령 후에는 보상 수령 시각, 생성된 회원 쿠폰 수량, 쿠폰 상태와 만료일, 포인트 이력 생성 여부를 DB에서 확인하도록 설계했다.

## 검증 상태와 결과

구현·빌드 성공 및 검증 시나리오가 기록되어 있다. 다만 최종 보고서에서는 체크리스트에 실제로 실행한 항목만 성공으로 표기한다. 아직 비어 있는 수동 실행·정리 항목은 추후 캡처와 DB 결과를 채운 뒤 반영한다.

이 사례는 사용자 경험의 한 번의 클릭을 **이력·잔액·쿠폰 데이터가 일관되게 바뀌는 비즈니스 처리**로 완성하려 한 사례다.

## 요구사항과 문제

관리자는 일반 사용자와 달리 비공개·비활성 상태의 도서도 관리 목적으로 확인해야 한다. 그러나 관리자에게도 전자책 본문, 파일, 페이지처럼 보호해야 할 정보까지 모두 노출할 필요는 없다. 또 여러 관리자가 같은 도서를 수정할 수 있으며, 같은 상태로 반복 요청했을 때마다 변경 시각과 감사 로그가 계속 쌓이면 실제 변경 이력을 신뢰하기 어렵다.

## 설계 결정

- 관리자 상세 조회는 수정에 필요한 메타데이터, 출판사·저자·카테고리·상태·시각을 제공한다.
- 전자책 본문, 파일, 페이지와 같이 보호해야 할 정보는 관리자 상세 응답에서도 제외한다.
- 도서 상태가 실제로 바뀌는 경우에만 변경 사유와 이전·이후 상태를 감사 로그에 남긴다.
- 현재 상태와 동일한 요청은 불필요한 수정 시각·감사 로그 변화 없이 처리한다.
- 실제 상태 변경에는 빈 문자열이 아닌 사유를 요구한다.
- 동시 수정은 잠금 실패를 명확한 동시 수정 오류로 변환하는 방향으로 다룬다.
- 컬렉션은 생성·기본 정보 수정·도서 편성·상태 변경을 분리하여 운영자가 의도를 분명히 표현할 수 있게 한다.

## 리뷰 대응과 검증 계획

이 사례는 코드리뷰에서 발견한 API 계약 공백과 동시성 처리 문제를 보완하는 과정이다. 관리자 도서 상세 조회 API를 별도로 두고, 세션 단위 시간 제한 조작 대신 데이터베이스 기본 잠금 정책을 따르며, 잠금 실패를 의미 있는 오류로 처리하는 방향을 정리했다.

현재 최신 기록에서는 수동 Swagger/Postman 검증이 아직 실행되지 않은 것으로 남아 있다. 그러므로 최종 문서에는 다음을 완료 증거로 추가한 뒤 ‘구현 완료’로 표현한다.

- [ ] 관리자 상세 조회에서 보호 데이터가 제외되는 응답 캡처
- [ ] 실제 상태 변경과 같은 상태 재요청의 감사 로그 차이
- [ ] 사유 누락 요청의 입력 오류 응답
- [ ] 동시 수정 요청의 성공/충돌 결과
- [ ] 컬렉션 생성·도서 편성·상태 변경의 화면 또는 API 호출 결과

## 결과

관리자 기능은 ‘수정할 수 있다’보다 **안전하게 수정하고, 나중에 이유를 설명할 수 있다**가 중요하다는 점을 반영했다. 리뷰에서 나온 문제를 API 계약·예외·수동 검증 계획까지 확장해 보완한 사례다.

# 10. API 검증 및 테스트 방식

## 10.1 검증 원칙

API 구현 후에는 정상 요청만 확인하지 않는다. 공통 응답 형식, 입력 검증, 권한, 중복·상태 충돌, 데이터베이스 반영 여부를 나누어 확인한다.

| 검증 대상 | 검증 도구 | 확인 내용 | 보고서 작성 원칙 |
|---|---|---|---|
| 정상 요청 | 자동 테스트, Swagger | 200/201 응답과 응답 DTO | 실제 성공 결과만 표기 |
| 입력값 오류 | Swagger, Postman | 400 및 검증 오류 응답 | 잘못된 요청 예시를 한 건 이상 제시 |
| 권한 오류 | Swagger, Postman | 인증 없음·권한 없음의 401/403 | 관리자 API 사례에 반드시 포함 |
| 중복·상태 충돌 | Postman, DB | 중복 출석·보상 재수령·상태 충돌 등의 오류 | 비즈니스 오류와 DB 제약을 구분 |
| DB 반영 | MySQL | 상태값, 이력 행, 관계 연결 | 테스트 데이터와 정리 여부를 함께 기록 |
| 동시성 | Postman 등 동시 요청 도구 | 잠금·중복 처리·충돌 응답 | 실행 전에는 계획으로만 표기 |

## 10.2 현재 확인 가능한 결과

- 도서·카테고리·컬렉션: 관련 자동 테스트 21건 성공 기록
- 관리자 대시보드·통계·감사 로그: 단위 테스트 158건 성공 및 빌드 통과 기록
- 챌린지·출석·포인트·쿠폰: 구현·빌드 성공 기록과 Swagger 검증 시나리오

이 결과는 기능 전체의 완전성을 의미하지 않는다. 특히 뷰어, 사용자 통계, 관리자 도서·컬렉션의 일부 수동 검증은 최종 제출 전 별도로 실행하고 증거를 채운다.

# 11. 협업 방식과 코드리뷰 대응

## 11.1 문서로 먼저 합의하기

구현 전에 API ID, URL, 응답, 데이터 구조, 오류 코드, 범위 제외를 작업현황 문서에 정리했다. 이를 통해 명세와 실제 구조가 충돌하거나, 팀이 아직 결정하지 않은 기능을 임의로 넓히는 일을 줄이려 했다.

## 11.2 코드리뷰를 계약 보완으로 확장하기

도서·카테고리·컬렉션 및 관리자 도서 API는 코드리뷰를 통해 테스트 공백, 응답 계약, 성능, 상태 변경, 동시 수정 같은 보완 지점을 발견했다. 발견 사항은 단순히 코드 한 줄을 수정하는 데 그치지 않고 다음으로 이어졌다.

```text
코드리뷰 발견
  → 원인과 영향 정리
  → API 계약 또는 처리 규칙 보완
  → 테스트·Swagger·DB 확인 항목 추가
  → 실제 실행 결과를 근거로 완료 판정
```

## 11.3 프론트 연동 증거를 추가하는 방법

이 문서에서는 확인되지 않은 프론트 연동을 실제 기여로 주장하지 않는다. 프론트 연동에 참여한 내용이 있다면, 최종본 부록에 다음만 추가한다.

- API wrapper 또는 타입 변경 파일
- 임시 데이터(fallback) 제거 전후
- 실데이터가 화면에 표시되는 캡처
- 백엔드 응답 변경이 화면에 반영된 사례

# 12. 주요 문제 해결 사례

| 문제 | 원인 판단 | 해결 방향 | 배운 점 |
|---|---|---|---|
| 뷰어 명세의 파일 테이블과 실제 스키마 불일치 | 문서가 실제 실행 구조보다 앞서 있거나 오래된 상태 | 실제 페이지 본문 데이터를 기준으로 API를 설계 | 명세보다 실제 스키마를 먼저 확인해야 한다 |
| 포인트·쿠폰 보상의 중복 지급 위험 | 화면 상태만으로는 재요청을 막을 수 없음 | 수령 상태, 고유성, 이력·잔액을 함께 관리 | 보상은 화면 기능이 아니라 데이터 정합성 문제다 |
| 통계 데이터가 없는 기간의 오류 처리 | 입력 오류와 데이터 미집계를 같은 오류로 취급할 수 있음 | 잘못된 요청과 미집계 데이터를 서로 다른 응답으로 구분 | 오류 메시지도 API 사용 경험의 일부다 |
| 같은 도서 상태 요청의 감사 로그 오염 | 실제 변경 여부를 구분하지 않음 | 실제 변경일 때만 사유·감사 로그 기록 | 이력은 많이 남기는 것보다 믿을 수 있게 남기는 것이 중요하다 |
| 도서 탐색 목록의 반복 조회 위험 | 카드 단위로 관계 데이터를 조회할 수 있음 | 목록 단위 조회 기준으로 개선 | 목록 API는 응답 내용과 조회 횟수를 함께 봐야 한다 |

# 13. 결과, 한계, 향후 개선 방향

## 13.1 결과

사용자 영역에서는 도서 탐색, 전자책 이어 읽기, 독서 보상이라는 흐름을 설계했고, 관리자 영역에서는 운영 수치, 통계, 감사 로그, 콘텐츠 변경 안전성을 다뤘다. 특히 상태값·중복·이력·권한처럼 화면에 바로 보이지 않는 문제를 API의 처리 기준으로 명확히 하려 했다.

## 13.2 한계

- 일부 뷰어·사용자 통계·관리자 콘텐츠 기능은 작업현황에 계획 또는 리뷰 대응 단계가 포함되어 있다.
- 모든 API에 대해 동일한 수준의 Swagger/Postman/DB 증거가 확보된 것은 아니다.
- 자동 테스트 성공은 해당 테스트 범위의 통과를 뜻하며, 전체 화면 계약과 수동 시나리오를 대체하지 않는다.

## 13.3 향후 개선 방향

1. 계획·구현·수동 검증 상태를 API별로 최종 대조한다.
2. 보상·상태 변경·동시 수정 기능의 실제 DB 전후 상태를 캡처로 남긴다.
3. 뷰어의 완독, 북마크 중복, 이어 읽기를 화면 단위 시나리오로 검증한다.
4. 관리자 통계는 기간별 추세와 데이터 생성 시점을 더 명확히 보여 주도록 보완한다.
5. 대표 사례마다 코드 캡처 대신 요청·응답, 데이터 변화, 화면 결과를 한 장씩 연결한다.

# 14. 회고

처음에는 기능 단위로 API를 구현하는 데 집중하기 쉬웠다. 그러나 전자책 서비스에서는 기능 하나가 다른 도메인의 상태와 맞물린다. 읽기 진행은 완독·통계·챌린지와 연결되고, 보상은 이력·잔액·쿠폰과 연결되며, 관리자 변경은 권한·감사 로그·동시 수정 문제와 연결된다.

이번 작업을 통해 API 구현은 Controller와 Service를 만드는 일만이 아니라, **어떤 데이터를 기준으로 할지, 어떤 상태를 한 번만 바꿀지, 실패했을 때 무엇을 알려 줄지, 운영자가 나중에 어떻게 설명할지를 결정하는 일**이라는 점을 배웠다.

앞으로는 구현 시작 전에 화면·API·스키마의 차이를 더 빠르게 표로 정리하고, 기능 완료 기준에 수동 검증 증거까지 포함해 계획과 완료 상태의 간격을 줄이겠다.
