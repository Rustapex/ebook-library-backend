## 종합 판정

이 초안은 기능 나열형 문서에서 벗어나 **보상 확정 정책 → 중복 수령 방어 → 트랜잭션 일관성 → API·DB 검증**으로 이어지는 강한 기술 사례를 만들었다. 특히 정책 대안, 조건부 갱신, 롤백 범위, 구현 한계를 숨기지 않은 점은 면접용 소재로 충분히 경쟁력이 있다.

다만 현재 상태는 완성된 입사지원용 포트폴리오라기보다 **근거가 풍부한 기술 사례 보고서**에 더 가깝다. 본인과 팀의 경계, Spring/JPA/MySQL/REST의 구체적인 사용 이유, ERD·API 명세에서 검증까지 이어지는 추적 관계, Git·PR·코드리뷰 대응 근거가 첫눈에 잡히지 않는다. 검증 자료와 화면도 본문에서 차지하는 비중이 커 핵심 판단이 뒤로 갈수록 희석된다.

이 리뷰는 PDF 포트폴리오 제작을 전제로 했다. GitHub README와 별도 1장 요약은 제작 범위에서 제외된 것으로 보고, 체크리스트의 README 항목은 **PDF 자체의 문서 연결성·검증 가능성**으로 대체해 평가했다.

## 잘한 점

### 1. 첫 페이지에서 대표 사례의 방향이 보인다

- 제목인 “운영 중 변경되는 보상을 안전하게 지급한 독서 보상 API”는 기능명이 아니라 해결한 문제를 드러낸다(초안 1행).
- ABC가 어떤 서비스인지 한 문장으로 설명하고, 기간·팀·역할·기술·대표 사례를 표로 정리했다(10~20행).
- “수령권 선점과 실제 지급을 하나의 트랜잭션으로 묶었다”는 한 줄 성과가 백엔드 개발자의 책임을 보여 준다(24~26행).
- 기준 문서가 권장한 첫 페이지의 프로젝트·역할·핵심 문제·기술·검증 구성을 대부분 반영했다.

### 2. 문제 정의가 데이터 위험으로 연결된다

- “달성”과 “지급”을 분리하고, 운영 중 보상 변경·반복 요청·부분 지급·잔액과 이력 불일치라는 문제를 구체적인 데이터 위험으로 바꿨다(30~46행).
- 단순히 챌린지 API를 만들었다고 쓰지 않고, 왜 신뢰할 수 있는 최종 상태가 필요한지를 설명한다.
- 사용자와 관리자의 행동이 충돌할 수 있는 실제 운영 상황을 다뤄 CRUD 이상의 사고가 보인다.

### 3. 정책 선택과 트레이드오프가 명확하다

- 달성 시점 스냅샷과 수령 시점 최신값을 장점·비용·위험으로 비교했다(112~126행).
- 선택한 정책이 항상 옳다고 주장하지 않고, 일정과 데이터 구조를 고려한 결정임을 밝혔다.
- 실제 서비스 확장 시 보상 버전이나 변경 알림이 필요하다는 후속 방향까지 제시해 면접 방어력이 높다.

### 4. 동시성·트랜잭션 설명이 구체적이다

- 조회 후 지급 구조에서 두 요청이 동시에 미수령 상태를 볼 수 있다는 원인을 먼저 설명한다(130~140행).
- `reward_claimed_at IS NULL` 조건부 갱신과 영향 행 수 `1/0`으로 수령권을 판정하는 흐름이 구체적이다(140~150행).
- 선점 뒤 지급이 실패할 수 있다는 2차 문제를 찾아, 선점·포인트·쿠폰 지급을 하나의 트랜잭션으로 묶었다(160~174행).
- DB 트랜잭션이 HTTP 전달이나 화면 렌더링까지 보장하지 않는다고 범위를 제한한 점도 정확하다(176행).

### 5. 응답이 아니라 실제 데이터까지 검증했다

- 포인트 응답 `100`, 잔액 `300 → 400`, 이력 `1건`을 연결했다(283~307행).
- 쿠폰 응답 수량 `2`와 실제 `member_coupon` 두 행을 대조했다(311~334행).
- 반복 수령의 `200/409`, 지급 실패 후 `reward_claimed_at=NULL`과 신규 이력 미생성을 정상·실패 경로로 나눴다(338~370행).
- 로컬 이미지 링크 6개는 모두 실제 파일이 존재해 현재 Markdown 기준으로 경로가 끊어지지 않는다. 단, PDF 변환 엔진에서의 크기·페이지 분할은 별도 렌더링 검수가 필요하다.

### 6. 과장을 피하고 현재 한계를 공개했다

- Postman Runner의 빠른 반복이 엄밀한 동시 부하 테스트가 아니라고 명시했다(152~156행, 349행).
- 비활성 쿠폰 발급 차단과 만료 상태 자동 전환이 미구현임을 숨기지 않았다(206~213행).
- 배포 화면을 직접 증거가 아닌 보조 증거로 한정했다(376~389행).
- 남은 개선을 보상 스냅샷, 동시 요청 통합 테스트, 쿠폰 상태 정책 등 현실적인 후속 과제로 정리했다(427~436행).

### 7. 면접 질문으로 이어질 주제가 충분하다

다음 질문은 문서만으로도 자연스럽게 이어진다.

- 왜 달성 시점 스냅샷 대신 수령 시점 최신값을 선택했는가?
- 비관적 락이나 별도 멱등키 대신 조건부 갱신을 사용한 이유는 무엇인가?
- 수령권을 먼저 선점하면서도 지급 실패 시 재수령 가능성을 어떻게 보장했는가?
- 포인트 잔액과 이력, 여러 쿠폰 행 중 일부만 반영되는 문제를 어떻게 막았는가?
- 빠른 반복 요청과 실제 동시성 테스트의 차이는 무엇인가?

## 부족한 점

### 1. “내가 직접 한 일”이 첫 페이지에서 충분히 증명되지 않는다

- `개인 역할 | 부팀장, DB 설계, 백엔드 개발, 발표`는 범위가 넓고 일반적이다(16행).
- `전체 담당 범위`에는 많은 도메인이 한 줄로 나열되어 깊이를 판단하기 어렵다(17행).
- 관리자 기능을 “제공했다”고 표현해 설계·구현·수정·검증 중 어디까지 직접 했는지 알기 어렵다(72~82행).
- “일부 기능은 프런트 화면 연동까지 직접 구현·확인했다”에서 `일부`가 어떤 화면인지 특정되지 않는다(22행).

첫 페이지에는 전체 도메인 수보다 대표 사례에서 직접 맡은 책임을 먼저 보여 줘야 한다.

### 2. 기술 스택이 구현과 완전히 결합되지 않았다

- Spring Boot, Spring Data JPA, MySQL, REST API는 19행에 나열되어 있으나 각 기술이 어떤 문제를 해결했는지 한눈에 연결되지 않는다.
- 계층 구조와 조건부 갱신은 설명하지만 JPA Repository에서 조건부 갱신을 어떻게 수행하고 영향 행 수를 어떻게 판정했는지가 기술명과 직접 이어지지 않는다(236~263행).
- REST 엔드포인트는 부록에 있으나 리소스 URL, `200/409`, 오류 코드 설계가 하나의 API 계약으로 묶여 있지 않다(217~230행, 448~463행).

### 3. ERD와 기준 API 명세가 문서에서 사라져 있다

- `challenge`, `challenge_progress`, `challenge_reward`, `member`, `point_history`, `coupon`, `member_coupon` 목록은 있지만 관계·FK·카디널리티를 보여 주지 않는다(249~253행).
- API ID와 URL만 있고 어떤 기준 문서에서 요청·응답·오류를 정의했는지 연결되지 않는다.
- Swagger와 Postman은 검증 도구로 언급되지만 API 명세 → 구현 → Swagger/Postman → DB 확인의 개발 절차가 보이지 않는다.
- 검증 원본 경로가 HTML 주석 안에 있어 PDF에서는 독자가 볼 수 없다(309, 336, 351, 372행).

### 4. Git·PR·코드리뷰 경험이 한 문장에 머문다

- “코드리뷰에서 문제가 제기됐다”는 설명은 좋지만 PR 번호, 리뷰 요지, 변경 전 문제, 본인이 수정한 영역, 추가한 테스트, 재검증 결과가 없다(95~126행).
- 저장소에는 PR #33 관련 대응 기록이 존재하지만, 현재 초안에서는 이를 협업 경험으로 추적할 수 없다.
- GitHub Actions CI/CD와 AWS 배포 스택은 첫 표에만 등장해 본인이 구축한 것인지 팀 환경을 사용한 것인지 구분되지 않는다(20행).

### 5. 일부 검증 문장이 현재 증거보다 강하다

- 155행은 Postman의 `200/409`와 포인트 이력 1건을 하나의 실행 결과처럼 연결한다. 캡처와 DB 자료가 같은 실행이라는 추적 근거가 없다면 별도 시나리오로 표현하는 편이 안전하다.
- 363~370행은 실패 후 상태만 보여 준다. 회원 포인트 `300`이 유지됐다고 롤백을 주장하려면 동일 시나리오의 실패 전 잔액도 함께 제시해야 한다.
- 26행의 “여러 요청이 들어와도 한 요청만”은 실제 고부하 동시성 검증까지 완료한 것으로 먼저 읽힐 수 있다. 본문에서 한계를 설명하더라도 첫 페이지 문장을 현재 증거 수준에 맞춰야 한다.

### 6. 입사지원용 문서로는 근거가 본문을 너무 오래 점유한다

- 전체 463행 중 검증과 배포 화면이 266~415행으로 약 150행이다.
- 같은 Postman 검증 한계가 152~156행과 338~349행에서 반복된다.
- 포인트·쿠폰의 설계 설명과 검증 설명이 각각 5절과 8절에서 중복된다.
- 관리자 쿠폰·포인트 화면은 전체 담당 범위의 보조 자료이지만 독서 보상 핵심 사례의 직접 증거는 아니다.
- 결과와 회고가 앞 절의 정책·한계를 다시 요약한다(417~444행).

## 반드시 수정할 부분

### 1순위. 본인 책임과 팀 결과를 분리한다

첫 페이지에 다음 구조의 표를 추가하고, 확인된 사실만 기재한다.

| 구분 | 내용 |
|---|---|
| 대표 사례에서 직접 담당 | 보상 정책 정리, API 계약, 조건부 수령 처리, 포인트·쿠폰 지급, 트랜잭션, 테스트·DB 검증 |
| 프런트 연동 | `[직접 구현한 화면 ID/Route]` / `[API 제공 후 연동만 확인한 화면]` |
| 팀 결과 | 전체 서비스 배포, 팀원이 구현한 화면·기능 |
| 구현 제외 | 출석 7일·30일 쿠폰 직접 지급, 보상 스냅샷, 고부하 동시성 검증 |

`전체 담당 범위`는 `본인 담당 도메인`으로 바꾸고, 배포 환경은 `팀 배포 구성`으로 표시해야 한다.

### 2순위. 코드리뷰를 Git 협업 사례로 완성한다

본문에 다음 한 개의 표만 추가해도 협업 경험이 크게 개선된다.

| 리뷰 문제 | 내가 내린 판단 | 수정·검증 | 근거 |
|---|---|---|---|
| 달성 후 미수령 상태에서 보상이 바뀌면 지급 기준이 불명확 | 수령 시점 최신값 정책 선택 | 서비스 주석과 `ChallengeServiceTest` 회귀 시나리오 추가 | PR #33 및 [`2차 코드리뷰 대응계획`](../../이전/0708/2026-07-08_PR33_2차코드리뷰_대응계획.md) |
| 조회 후 갱신 구조의 중복 수령 위험 | 조건부 갱신으로 수령권 선점 | Repository `1 → 0` 검증과 반복 요청 `200/409` 확인 | PR #33 대응 기록 |

실제 PR 링크를 공개할 수 없다면 PR 번호와 로컬 대응 문서만으로도 충분하다. 리뷰를 많이 받았다는 사실보다 **지적 → 판단 → 수정 → 재검증** 흐름이 중요하다.

### 3순위. ERD·API 명세·구현·검증 추적표를 추가한다

전체 ERD를 넣기보다 대표 사례에 필요한 테이블만 표시한다.

```text
challenge ── challenge_reward
    │
    └── challenge_progress ── member
                                  ├── point_history
                                  └── member_coupon ── coupon
```

그 아래에는 다음 추적표를 둔다.

| 설계 근거 | 구현 | 검증 |
|---|---|---|
| `API-CHALLENGE-002` 성공·중복·실패 계약 | REST 보상 수령 API와 오류 코드 | Swagger·Postman `200/409` |
| 보상 관련 ERD·런타임 스키마 | JPA Entity/Repository와 MySQL 제약 | DB 전후 행 비교 |
| 중복 수령 규칙 | `reward_claimed_at IS NULL` 조건부 갱신 | Repository `1 → 0`, 빠른 반복 요청 |
| 부분 반영 방지 규칙 | 선점·잔액·이력·쿠폰을 같은 트랜잭션으로 처리 | 실패 응답, 수령 시각·이력 미반영 |

연결할 기준 파일은 [`API 명세`](<../../../API 명세/api-spec(final).md>), [`ERD`](../../../데이터베이스/erd/ebook-rental-erd.md), [`런타임 스키마`](../../../../src/main/resources/schema.sql)다.

### 4순위. 기술을 문제 해결 방식과 직접 연결한다

긴 기술 설명 대신 한 표로 정리한다.

| 기술 | 이 사례에서 사용한 이유 | 확인된 결과 |
|---|---|---|
| Spring Boot 트랜잭션 | 수령 선점과 지급을 하나의 작업 단위로 처리 | 지급 예외 시 수령 시각과 지급 데이터 함께 롤백 |
| Spring Data JPA | 조건부 갱신과 포인트·쿠폰 데이터 저장 | 영향 행 수로 선점 성공 여부 판정 |
| MySQL | 원자적 갱신과 제약조건으로 최종 상태 보호 | 중복 수령·음수 잔액·상태 불일치 방어 |
| REST API | 정상·중복·실패를 명시적 계약으로 구분 | `200`, `409`, 도메인 오류 코드 반환 |

`@Transactional`, `@Modifying`, JPQL 또는 native query 같은 구체 명칭은 실제 소스와 일치하는 경우에만 넣는다.

### 5순위. 검증 근거의 범위와 추적성을 바로잡는다

- Postman `200/409`와 DB 이력 1건이 별도 실행 자료라면 한 시나리오처럼 합치지 않는다.
- 실패 전 포인트 값이 없다면 “포인트 잔액도 롤백됐다”는 주장은 제거하고, 확인 가능한 `reward_claimed_at=NULL`과 신규 이력 미생성으로 범위를 좁힌다.
- HTML 주석에 숨긴 원본 경로는 PDF에서 보이는 `검증 자료` 각주나 부록으로 옮긴다.
- 자동 테스트 표에는 실제 실행한 명령, 실행 시점, 통과 결과 또는 검증 문서 경로 중 하나를 추가한다.

## 추가하면 좋은 부분

### 1. 30초 소개 문장

> ABC는 전자책 대여·열람과 독서 보상을 제공한 5인 팀 프로젝트다. 나는 부팀장으로 DB 설계와 백엔드 API 개발을 맡았으며, 대표적으로 운영 중 변경되는 챌린지 보상의 중복·부분 지급 문제를 해결했다. Spring Data JPA 조건부 갱신과 트랜잭션으로 한 요청만 지급되도록 설계하고, 반복 수령 `200/409`, 포인트 `300 → 400`, 쿠폰 2건 생성, 지급 실패 시 수령 상태 미반영을 API와 DB 자료로 검증했다.

이 문장은 첫 페이지의 서비스 소개, 개인 역할, 핵심 문제, 기술, 검증 결과를 하나로 연결한다. “한 요청만 지급” 뒤에는 실제 고부하 동시성 검증이 아닌 빠른 반복 검증이라는 한계를 본문에서 유지해야 한다.

### 2. 개발 절차 한 줄

```text
API 명세·ERD 확인 → 구현 계획 → Spring Boot/JPA 구현 → PR 리뷰 대응 → Swagger/Postman → MySQL 전후 검증
```

현재 문서에는 각 요소가 흩어져 있다. 이 한 줄을 넣으면 설계·구현·협업·검증 경험이 하나의 개발 방식으로 보인다.

### 3. 검증 가능한 결과 카드

- 수령 시점 최신 보상 회귀 시나리오
- 조건부 갱신 결과 `1 → 0`
- 빠른 반복 수령 결과 `200 → 409`
- 포인트 `300 → 400`, 이력 1건
- 쿠폰 응답 2개, `member_coupon` 2건
- 지급 실패 후 `reward_claimed_at=NULL`, 신규 이력 미생성

새로운 성능 수치를 만들 필요는 없다. 이미 증명 가능한 상태 변화가 충분히 강한 정량 결과다.

### 4. PDF용 증거 색인

각 사례 아래에 원본 경로를 숨은 주석 대신 짧게 표시한다.

```text
검증 근거: API-CHALLENGE-002 / Postman 반복 수령 / DB 사전·사후 조회 / ChallengeServiceTest
```

백엔드 저장소가 비공개일 수 있으므로 PDF 안에서 API 명세, ERD, 테스트 이름, DB 결과를 스스로 이해할 수 있게 해야 한다.

### 5. 면접 중심축 표시

면접 질문 포인트가 많으므로 다음 세 가지에만 `핵심 판단` 표시를 사용한다.

1. 달성 시점과 수령 시점 중 보상을 언제 확정할 것인가
2. 중복 수령 요청에서 한 요청만 어떻게 선점할 것인가
3. 선점 후 지급 실패를 어떻게 하나의 롤백으로 만들 것인가

포인트·쿠폰 세부 구현과 입력 검증은 이 세 판단을 뒷받침하는 하위 근거로 배치하는 편이 좋다.

수정:

> 트랜잭션은 DB 변경까지만 보장하며, HTTP 응답 전달과 화면 렌더링 실패는 롤백 범위가 아니다.
