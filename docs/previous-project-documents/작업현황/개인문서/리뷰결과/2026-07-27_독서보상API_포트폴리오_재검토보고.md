## 잘한 점

### 1. 프로젝트 개요와 대표 문제가 30초 안에 이해된다

첫 페이지에서 다음 정보가 바로 연결된다.

- 전자책 대여·열람과 독서 보상 서비스
- 5인 팀 프로젝트
- 부팀장, DB 설계, 백엔드 API 개발
- 운영 중 보상 변경, 중복 수령, 부분 반영 문제
- 조건부 갱신과 트랜잭션
- 포인트 `300 → 400`, 쿠폰 2건, 반복 요청 `200/409`

서비스 종류만 소개하지 않고 “어떤 문제를 어떤 기술로 해결했는지”까지 첫 두 문단에 포함했다. 비전공 채용 담당자는 서비스와 역할을 이해할 수 있고, 기술 면접관은 조건부 갱신·트랜잭션·DB 검증이라는 질문 지점을 바로 찾을 수 있다.

### 2. 개인 역할과 팀 결과의 경계가 명확해졌다

첫 페이지 표와 2장, 9장에서 다음 항목을 분리했다.

- 본인: DB 설계, 백엔드 API, 보상 정책, 조건부 갱신, 트랜잭션, 테스트·DB 검증
- 본인 프런트 기여: 기존 A-013 관리자 포인트 화면의 API 연동
- 팀원: 프런트 화면 디자인·페이지 구현, 전체 서비스 배포
- 제외 범위: 출석 쿠폰 직접 지급, 보상 스냅샷, 소급 재계산, 고부하 동시성 검증

특히 화면 캡션마다 “팀원이 구현한 화면”과 “내가 개발한 API”를 구분한 점이 좋다. 배포 구성에도 참여하지 않았다고 명시해 팀 성과를 개인 성과처럼 보이게 하지 않았다.

### 3. 기능 나열보다 문제-판단-구현-검증 구조가 중심이다

본문의 중심을 다음 세 판단으로 제한한 구성이 효과적이다.

1. 보상을 달성 시점과 수령 시점 중 언제 확정할 것인가
2. 반복 요청에서 한 요청만 어떻게 수령권을 선점할 것인가
3. 선점 후 지급 실패를 어떻게 함께 롤백할 것인가

각 판단에는 문제 상황, 대안, 선택 이유, 구현 방식, 검증 한계가 들어 있다. 도메인별로 “무엇을 구현했다”를 나열하던 문서에서 면접형 사례 문서로 방향이 바뀌었다.

### 4. Spring Boot·JPA·MySQL·REST API 역량이 실제 문제와 연결된다

기술을 단순 나열하지 않고 다음과 같이 역할을 부여했다.

- Spring 트랜잭션: 선점과 지급을 하나의 작업 단위로 처리
- Spring Data JPA: 조건부 갱신과 영향 행 수 판정
- MySQL: 원자적 갱신과 최종 상태 보호
- REST API: 정상·중복·실패를 `200`, `409`, 도메인 오류로 구분
- Swagger·Postman: 정상·실패·반복 요청 재현

조건부 `UPDATE`, `reward_claimed_at IS NULL`, 영향 행 `1/0`까지 설명해 JPA 사용 경험이 CRUD 수준에 머물지 않는다. 트랜잭션이 HTTP 응답 전달이나 화면 렌더링까지 롤백하지 않는다고 경계를 설명한 것도 기술적으로 정직하다.

### 5. ERD·API 명세·Swagger·Postman·DB 검증이 하나의 개발 과정으로 보인다

6장의 핵심 데이터 관계와 추적표가 다음 흐름을 만든다.

```text
API 명세·ERD
  → Spring Boot·JPA 구현
  → PR 코드리뷰
  → Swagger·Postman
  → MySQL 전후 상태 확인
```

7장과 부록 B에서는 정상 포인트 지급, 쿠폰 지급, 반복 수령, 지급 실패를 각각 다른 증거 범위로 구분했다. Postman `200/409`와 별도 DB 이력 검증을 한 시나리오처럼 합치지 않은 점도 이전 리뷰보다 정확해졌다.

### 6. Git 협업과 코드리뷰 대응이 구체적이다

8장은 PR 번호를 나열하는 데서 끝나지 않고 다음 흐름을 보여 준다.

```text
리뷰에서 발견한 위험
  → 내가 내린 정책·기술 판단
  → 구현과 테스트 수정
  → 결과 확인
```

보상 확정 시점, 조건부 선점, 미지원 유형 fail-fast, 쿠폰 실제 지급, A-013 서버 응답 기반 상태 갱신이 서로 다른 협업 사례로 구분된다. 코드리뷰를 수동 수정 작업이 아니라 정책과 회귀 테스트를 보완한 과정으로 설명했다.

### 7. 과장 방지와 면접 방어 가능성이 좋다

다음 한계를 문서 안에서 직접 밝혔다.

- 빠른 반복 요청은 실제 동시 부하 테스트가 아님
- 달성 조건 변경 후 소급 재계산은 해결 범위가 아님
- 트랜잭션은 DB 작업까지만 보장
- 쿠폰 상태·만료 자동 전환은 미완성
- 프런트 PR #100 당시 전체 빌드와 브라우저 검증을 완료하지 못함

이러한 표현 덕분에 면접 질문이 들어와도 “검증한 범위”와 “추가로 필요한 검증”을 구분해 답할 수 있다.

### 8. 면접 질문으로 이어질 구현 포인트가 충분하다

면접관이 질문할 가능성이 높은 지점이 명확하다.

- 왜 달성 시점 스냅샷 대신 수령 시점 최신값을 선택했는가
- 조건부 UPDATE와 비관적 락 중 왜 이 방식을 선택했는가
- 영향 행이 0일 때 어떤 오류 계약을 반환하는가
- 선점 후 예외가 발생하면 어떤 데이터가 롤백되는가
- 포인트 잔액과 이력을 왜 함께 처리해야 하는가
- 쿠폰 수량과 `member_coupon` 행 수를 어떻게 맞췄는가
- 실제 동시성 테스트를 추가한다면 어떻게 구성할 것인가

대표 사례로서 기술적 깊이와 질문 유도력이 충분하다.

## 부족한 점

### 1. PDF에서 저장소·PR·문서 링크와 로컬 경로를 사용할 수 없다

다음 항목은 Markdown에서는 편리하지만, 링크를 열 수 없는 PDF에서는 증거가 되지 않는다.

- 첫 페이지의 Backend·Frontend 저장소 링크
- `Backend PR #33·#35·#36`, `Frontend PR #99·#100` 링크
- API 명세·ERD·런타임 스키마 상대 경로
- `api-test-results/...` 로컬 검증 경로
- 서비스·Backend API·Frontend Repository 링크

현재 문서에는 링크 없이도 핵심 설명이 어느 정도 남지만, “근거” 열이 실제로는 클릭 가능한 링크에 의존한다. 특히 Backend 저장소가 비공개라면 URL을 그대로 표시해도 외부 면접관은 접근할 수 없다.

PDF에서는 다음 원칙을 적용해야 한다.

```text
링크 = 선택적 참고 정보
문서 안의 표·캡처·요약 = 실제 증거
```

### 2. 첫 페이지 표가 다시 담당 기능 목록처럼 보일 수 있다

`본인 담당 도메인` 행에 도서·카테고리·컬렉션부터 관리자 통계·감사 로그까지 한 줄로 들어가 있어 범위가 매우 넓어 보인다. 구현 계획상 일부 구현·보완 작업도 포함돼 있으므로, 면접관이 “이 모든 기능을 처음부터 끝까지 혼자 만들었는가”라고 오해할 수 있다.

첫 페이지에서는 다음 정도만 남기는 편이 낫다.

- 대표 담당: 챌린지·출석·포인트·쿠폰 백엔드
- 추가 기여: 도서·컬렉션·전자책·관리자 API 일부 구현·보완

세부 도메인은 부록이나 별도 담당 범위 표로 이동하면 된다.

### 3. 30초 요약의 두 번째 문단이 기술과 수치로 과밀하다

첫 두 문단에 조건부 갱신, 트랜잭션, `200/409`, `300 → 400`, 쿠폰 2건, `reward_claimed_at=NULL`이 모두 들어 있다. 기술 면접관에게는 강하지만, 비전공 채용 담당자가 한 번에 읽기에는 밀도가 높다.

첫 페이지에서는 “해결한 문제와 핵심 결과”를 먼저 말하고, 세부 수치는 바로 아래 결과 카드로 분리하는 편이 읽기 쉽다.

### 4. 기술 표의 MySQL 설명이 서로 다른 방어 수단을 한 문장에 합친다

현재 문장은 MySQL의 “원자적 갱신과 제약조건”이 중복 수령·음수 잔액·상태 불일치를 모두 막은 것처럼 보인다.

실제로는 다음을 구분해야 한다.

- 중복 수령: `reward_claimed_at IS NULL` 조건부 UPDATE와 영향 행 수
- 음수 잔액: 잔액 조건이 포함된 조건부 UPDATE
- 잘못된 상태·값: CHECK·UNIQUE 등 DB 제약

조건부 갱신과 스키마 제약의 책임을 분리해야 기술 설명이 정확해진다.

### 5. API 명세 경험이 “링크와 API ID” 수준에 머문다

`API-CHALLENGE-002`와 `200/409`는 보이지만, PDF 자체에는 대표 API의 다음 계약이 한 번에 정리되어 있지 않다.

- Method·Path
- 인증 주체
- 요청 입력
- 성공 응답 핵심 필드
- 중복 수령 오류
- 미지원 유형 오류

부록 A는 API 목록이고 부록 B는 결과 자료이므로, 두 정보 사이를 연결하는 “대표 API 계약 카드”가 필요하다.

### 6. 자동 테스트의 실행 사실이 PDF 안에서 완전히 증명되지 않는다

테스트 클래스와 확인 내용은 명확하지만, “PR 본문에 관련 테스트와 빌드 결과를 기록했다”는 문장은 PR에 접근할 수 없는 면접관에게는 확인할 수 없는 주장이다.

PDF 안에 최소한 다음 중 하나가 필요하다.

- 실제 실행 명령과 결과 요약
- Gradle 테스트 성공 화면
- 테스트 클래스·메서드와 실행 날짜가 보이는 캡처
- PR 테스트 섹션 캡처

전체 테스트 건수를 새로 만들 필요는 없지만, 관련 테스트를 실제 실행했다는 자체 완결형 근거는 필요하다.

### 7. 본문과 결과 장에서 같은 성과가 반복된다

다음 내용이 첫 페이지, 7장, 10장에서 반복된다.

- 조건부 갱신으로 수령권 선점
- 트랜잭션으로 부분 반영 방지
- 포인트 `300 → 400`
- 쿠폰 2건
- 반복 요청 `200/409`
- 실패 후 수령 상태 미반영

강조 자체는 필요하지만 세 번 반복할 필요는 없다. 첫 페이지에는 핵심 성과 3개, 7장에는 증거, 10장에는 개선 전후와 회고만 남기는 편이 낫다.

### 8. 일부 검증 한계 설명이 포트폴리오보다 내부 보고서처럼 보인다

다음 내용은 정직하지만 본문 흐름을 늦춘다.

- 공유 DB 상태에 영향을 받는 기존 테스트 이력
- DB 초기화 후 당시 행이 현재 DB에 남아 있지 않다는 설명
- 프런트 PR #100의 `epubjs` 누락과 브라우저 미검증 상세

핵심 사실은 남기되, 상세 사유는 “검증 한계” 부록으로 이동하는 편이 좋다.

## 반드시 수정할 부분

### 1순위. PDF에서 열 수 없는 링크를 증거 구조에서 제거한다

첫 페이지의 `저장소` 행은 삭제하거나 다음처럼 바꾼다.

| 구분 | 수정 방향 |
|---|---|
| Backend·Frontend 링크 | PDF 본문에서는 제거. 공개 가능한 경우 마지막 페이지에 전체 URL 또는 QR을 선택적으로 배치 |
| PR 링크 | PR 번호·제목·지적·수정·검증 결과를 본문 표에 직접 표시 |
| API 명세·ERD 링크 | 대표 API 계약표와 핵심 데이터 관계도를 PDF 안에 직접 수록 |
| 로컬 검증 경로 | `E-01`, `E-02`와 같은 증거 ID로 바꾸고 실제 캡처·표와 연결 |
| 배포 URL | 화면 캡처를 주 근거로 사용하고 URL은 선택 정보로 취급 |

Backend가 비공개라면 QR이나 전체 URL을 추가해도 해결되지 않는다. 이 경우 PR 화면 캡처에서 저장소명·작성자·PR 번호·리뷰 내용·테스트 결과가 보이도록 하거나, 현재 8장 표를 더 구체화해야 한다.

### 2순위. 첫 페이지의 담당 범위를 대표 사례 중심으로 축소한다

`본인 담당 도메인`은 “전부 완성했다”는 인상을 줄 수 있으므로 다음과 같이 나눈다.

| 구분 | 내용 |
|---|---|
| 대표 담당 | 챌린지·출석·포인트·쿠폰 백엔드 API와 관련 DB·검증 |
| 추가 구현·보완 | 도서·카테고리·컬렉션, 전자책 뷰어·북마크·진행도, 관리자 API 일부 |

### 5순위. MySQL과 조건부 UPDATE의 책임을 정확히 분리한다

### 5. 프런트 PR #99의 전체 작업 설명

독서 보상 대표 사례에서는 A-013만 중요하다. 컬렉션·관리자 도서·회원 화면의 세부 연결은 전체 경력 부록으로 이동한다.

### 6. 프런트 PR #100 빌드 실패 상세

`epubjs` 누락 원인은 이번 대표 사례의 핵심이 아니다. 본문에서는 “수정 파일 정적 검증 완료, 당시 브라우저 수동 검증 미실행” 정도만 남기고 상세 사유는 부록으로 이동한다.

### 4. 조건부 UPDATE 대안 비교 한 줄

면접 질문에 대비해 다음 정도의 비교를 추가하면 좋다.

| 대안 | 이번 프로젝트에서 선택하지 않은 이유 |
|---|---|
| 비관적 락 | 단일 상태 선점에는 조건부 UPDATE와 영향 행 판정이 더 단순 |
| 낙관적 락 | 버전 충돌 처리보다 `NULL → 수령 시각` 상태 전이가 명확 |
| 멱등성 키 | 클라이언트 요청 단위가 아니라 챌린지 진행도 자체가 유일한 수령권 |

이는 실제 설계 당시 판단과 소스가 일치하는 경우에만 넣어야 한다.
