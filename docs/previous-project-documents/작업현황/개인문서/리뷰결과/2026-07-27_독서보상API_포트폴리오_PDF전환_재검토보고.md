### 외부 URL을 제거한 판단

현재 문서에서 GitHub 저장소, PR, 배포 주소와 같은 외부 URL을 제거한 것은 의도된 수정이며 PDF 제출본 기준으로 적절하다.

PDF 자체는 클릭 가능한 링크를 포함할 수 있지만 다음 문제가 남는다.

- 비공개 Backend 저장소는 주소가 있어도 평가자가 접근할 수 없다.
- PDF 뷰어나 회사 보안 정책에 따라 외부 링크가 비활성화될 수 있다.
- 네트워크가 없는 상태에서는 링크가 검증 근거 역할을 하지 못한다.
- 링크가 만료되거나 배포 서버가 종료되면 문서의 설득력이 함께 사라진다.

따라서 외부 URL을 핵심 근거로 사용하지 않고 PR 번호·문제·수정·테스트, API 계약, 응답과 DB 결과를 문서 안에 직접 수록한 현재 방향이 맞다. 외부 URL은 나중에 공개 저장소가 준비됐을 때 마지막 페이지의 선택 정보로 추가할 수 있지만 필수 수정 사항은 아니다.

## 잘한 점

### 1. 프로젝트 개요가 30초 안에 이해된다

제목과 30초 요약만 읽어도 다음 내용이 보인다.

- 전자책 대여·열람과 독서 보상을 제공하는 서비스
- 5인 팀 프로젝트
- 부팀장, DB 설계 참여, 백엔드 개발, 발표
- 대표 사례가 챌린지·포인트·쿠폰 보상 API
- 해결한 문제가 지급 기준, 중복 수령, 부분 반영

특히 10~12줄의 요약은 “무엇을 많이 만들었는가”보다 “어떤 데이터 문제를 해결했는가”를 먼저 보여 준다. 이전의 도메인 나열형 문서보다 입사지원용 포트폴리오에 훨씬 가깝다.

### 2. 개인 기여와 팀 기여가 명확하게 구분된다

17~23줄과 78~84줄에서 다음 경계를 분리했다.

- 본인: 보상 API, 관련 DB 흐름, 정책, 트랜잭션, 검증
- 본인 프런트 기여: 기존 화면과 API 연결
- 팀원: 화면 디자인, 페이지·라우팅 구현, 배포

또한 “신규 화면이나 신규 라우트를 개발한 것으로 표현하지 않는다”는 문장이 있어 프런트 기여를 과장하지 않는다. 배포 역시 본인이 담당하지 않았음을 21줄과 286줄에서 일관되게 구분했다.

### 3. 기능 나열이 아니라 문제-판단-구현-검증 구조다

문서의 중심이 세 가지 판단으로 정리돼 있다.

1. 보상을 달성 시점과 수령 시점 중 언제 확정할 것인가
2. 같은 보상은 어떤 요청이 지급받도록 할 것인가
3. 수령 상태와 실제 지급의 불일치를 어떻게 막을 것인가

각 사례가 문제 제기, 선택지, 결정, 구현, 검증, 한계로 이어진다. 특히 수령 시점 최신값과 달성 시점 스냅샷을 비교한 105~116줄은 기술이 아니라 운영 정책을 해석한 경험을 보여 준다.

### 4. Spring Boot, JPA, MySQL, REST API 역량이 역할별로 드러난다

194~204줄의 기술 표와 설명은 기술 이름을 나열하는 데 그치지 않는다.

- Spring Boot: 서비스 흐름과 트랜잭션 경계
- Spring Data JPA: 조건부 UPDATE와 영향 행 수 반환
- MySQL: 조건부 UPDATE의 원자적 실행과 스키마 제약
- REST API: 정상·중복·실패 계약 구분
- Swagger·Postman: 요청 재현과 결과 확인

중복 수령 방어의 직접 기준이 MySQL 제약조건이 아니라 조건부 UPDATE와 영향 행 수라는 점도 정확하게 구분했다.

### 5. API, ERD, JPA, DB 검증 흐름이 연결된다

182~228줄에서 데이터 관계, 기술 책임, 대표 API 계약, 설계부터 검증까지의 추적성이 연결된다.

대표 API는 다음 항목을 문서 안에서 확인할 수 있다.

- Method와 Path
- 인증
- 요청 값
- 성공 응답
- 중복 수령 오류
- 미지원 유형 오류
- 최종 DB 결과

별도 API 명세 파일이나 Swagger 페이지를 열 수 없는 PDF 환경에서도 REST API 설계 의도를 이해할 수 있다.

### 6. 코드리뷰 대응이 구체적이다

273~280줄에서 PR 번호만 제시하지 않고 다음 내용을 직접 기록했다.

- 리뷰 또는 연동 과정에서 발견한 문제
- 본인이 선택한 정책과 수정
- 연결된 테스트·검증 범위

PR #33의 정책 결정, #35의 실패 처리와 롤백, #36의 쿠폰 실지급으로 개선 과정이 이어져 Git 협업을 단순 커밋 횟수가 아니라 코드 품질 개선 경험으로 보여 준다.

### 7. 과장 방지 문장이 잘 들어가 있다

다음 항목을 완료했다고 과장하지 않는다.

- 관리자 달성 조건 변경 후 과거 진행도 재계산
- 실제 동시 부하 테스트
- 커밋 후 HTTP 전달과 화면 렌더링까지의 트랜잭션 보장
- 전체 DB 테이블의 단독 설계
- 전체 테스트의 고정된 성공 건수
- 테스트 파일 전체의 단독 소유

한계가 분명해 면접에서 질문을 받아도 설명 가능한 범위가 명확하다.

### 8. 면접 질문을 만들 만한 구현 포인트가 충분하다

면접관은 문서만 보고도 다음 질문을 이어갈 수 있다.

- 수령 시점 최신값을 선택한 이유는 무엇인가?
- 달성 시점 스냅샷 방식과 비교하면 어떤 차이가 있는가?
- 조건부 UPDATE는 왜 중복 지급을 방어할 수 있는가?
- 영향 행 수가 0일 때 왜 409를 반환했는가?
- 선점 이후 지급 실패는 어떻게 롤백되는가?
- 실제 동시 부하 테스트와 빠른 반복 요청은 어떻게 다른가?
- 쿠폰 여러 장을 지급할 때 일부만 저장되는 문제는 어떻게 처리했는가?

포트폴리오가 면접 질문의 흐름을 직접 만들어 준다는 점이 강점이다.

## 부족한 점

### 1. 첫 페이지가 여전히 조밀하다

30초 요약 자체는 명확하지만 첫 페이지에 다음 내용이 한꺼번에 배치될 가능성이 높다.

- 요약 문단 2개
- 프로젝트 정보 8개 행
- 핵심 결과 4개 행

Markdown 화면에서는 읽을 수 있지만 A4 PDF 한 페이지에 맞추면 글자가 작아지거나 표가 다음 페이지로 넘어갈 가능성이 있다. 30초 이해도는 높지만 시각적 첫인상은 실제 PDF 레이아웃을 확인해야 한다.

### 2. 같은 검증 결과가 여러 번 반복된다

포인트 `300 → 400`, 쿠폰 2건, 반복 요청 `200/409`, 실패 후 롤백이 다음 위치에서 반복된다.

- 첫 페이지 핵심 결과
- 6장의 추적성 표
- 7장의 증거 색인
- 7장의 검증 결과 표
- 10장의 개선 전후
- 부록 B의 상세 근거

핵심 결과를 반복해서 강조하는 효과보다 문서가 길어지는 영향이 더 커지기 시작했다.

### 3. E-05는 실제 실행 증거보다 요약에 가깝다

248~254줄과 427~435줄은 테스트 클래스와 확인 항목을 잘 정리했지만 실제 실행 명령, 통과 결과, 테스트 화면 중 하나가 문서에 직접 들어 있지는 않다.

현재 상태에서는 “PR 본문에 실행 기록이 있었다”는 설명은 가능하지만 PDF를 받은 사람이 그 기록을 독립적으로 확인할 수 없다. E-01~E-04보다 E-05의 증거 강도가 약하다.

### 4. 핵심 데이터 관계가 정식 ERD로 보이기에는 부족하다

184~190줄의 텍스트 관계도는 전체 흐름을 빠르게 이해하는 데는 좋다. 그러나 다음 항목은 보이지 않는다.

- PK와 FK
- 각 관계의 정확한 카디널리티
- 중복·상태 제약이 어느 테이블에 있는지
- 보상 지급 시 변경되는 핵심 컬럼

“ERD를 활용해 설계했다”는 경험은 전달되지만 DB 설계 역량을 시각적으로 강하게 보여 주지는 못한다.

### 5. 일부 화면 캡처가 핵심 주장을 직접 증명하지 않는다

관리자 포인트 모달은 실제 연동 대상 화면임을 보여 주지만 저장 성공 결과나 변경 후 잔액은 화면에 보이지 않는다. 그런데 현재 캡션은 서버 성공 응답을 기준으로 결과를 반영했다고 설명한다.

사용자 포인트·쿠폰 화면도 서비스 결과를 보여 주지만 챌린지 보상 지급 건과 직접 연결된 데이터는 아니다. 본문의 캡션이 이를 정직하게 구분하고 있으므로 과장은 아니지만, PDF에서 화면이 설명보다 먼저 눈에 들어오면 대표 사례의 직접 증거로 오해될 수 있다.

### 6. 방어 문장이 여러 장에 분산돼 있다

달성 조건 변경 미해결, 실제 동시 부하 테스트 미실행, 트랜잭션 범위 제한, 전체 DB 단독 설계 아님, 전체 테스트 건수 미주장 등이 각각 다른 장에 반복된다.

정직성은 높지만 문서가 지나치게 방어적으로 읽힐 수 있다. 핵심 판단 근처에는 필요한 한 줄만 남기고 나머지는 “검증 범위와 한계”로 모으는 편이 더 간결하다.

## 반드시 수정할 부분

### 1. PDF 변환 도구와 레이아웃 규칙을 먼저 확정한다

현재 Markdown은 내용 문서이고 페이지 문서가 아니다. 변환 도구를 정하지 않은 상태에서 바로 PDF로 만들면 표와 이미지의 페이지 분할 결과를 예측할 수 없다.

PDF 제작 전 다음을 확정해야 한다.

- A4 세로 또는 가로 사용 구간
- 본문 글꼴과 코드용 고정폭 글꼴
- 제목·본문·표·캡션 글자 크기
- 표와 코드 블록의 페이지 분할 방지
- 이미지와 캡션을 같은 페이지에 유지
- 장 시작 전 명시적 페이지 나누기
- 페이지 번호와 문서 제목을 표시할 머리말·꼬리말

한글과 `→`, `├─`, `└─` 문자를 모두 지원하는 글꼴을 지정하지 않으면 관계도와 흐름도가 네모 또는 빈칸으로 표시될 수 있다.

### 2. 상대 이미지 경로를 PDF 변환 환경에서 검증한다

현재 이미지 6개는 모두 실제 파일이 존재한다. 다만 파일명이 한글과 공백을 포함하고 Markdown에서 상대경로를 사용하므로 변환 명령의 실행 위치나 도구에 따라 누락될 수 있다.

반드시 다음 중 하나로 변환해야 한다.

- Markdown 파일이 있는 `개인문서` 폴더에서 변환 실행
- 변환 도구의 이미지 검색 경로에 `개인문서`와 `화면 캡처` 폴더 지정

첫 변환 후 PDF의 모든 이미지가 보이는지 페이지별로 확인해야 한다. Markdown 미리보기에서 보인다는 사실만으로 PDF 포함을 보장할 수 없다.

### 3. E-03 반복 수령 캡처를 교체하거나 재편집한다

현재 E-03 이미지는 1567×506의 매우 넓은 어두운 화면이다. A4 세로 폭에 맞추면 글자가 작아지고 흑백 인쇄에서 가독성이 크게 떨어진다.

또한 화면에 `All tests 0`, `No tests found`가 표시된다. 이 화면은 요청 응답 `200/409`를 보여 주지만 자동 테스트 통과 화면으로 오해되거나 반대로 “테스트가 없었다”는 인상을 줄 수 있다.

권장 수정:

- 첫 요청 `200`과 두 번째 요청 `409` 부분만 밝은 배경의 두 패널로 잘라 배치
- 또는 현재 이미지를 제거하고 응답 두 개를 표와 짧은 JSON으로 표시
- 캡션을 “Postman 반복 요청 결과이며 assertion 테스트 개수를 의미하지 않음”으로 명확화

### 4. E-05에 실제 자동 테스트 실행 증거를 최소 1개 추가한다

새로운 전체 테스트를 다시 수행할 필요는 없다. 기존 PR 본문에 남아 있는 자료 중 다음 하나를 PDF에 포함하면 된다.

- 테스트 명령과 성공 결과가 함께 보이는 캡처
- PR 본문의 테스트 실행 결과 캡처
- 테스트 클래스·시나리오·성공 여부를 보여 주는 기존 기록

캡처를 추가할 수 없다면 “실행 근거”라는 표현을 “작성 당시 PR 본문에 남긴 테스트 범위 요약”으로 낮추는 것이 정확하다.

### 5. PDF에서 폭이 넓은 표를 분리한다

다음 표는 A4 세로에서 열이 지나치게 많아질 가능성이 높다.

- 258~263줄 검증 결과 4열 표
- 273~278줄 PR 4열 표
- 429~433줄 E-05 4열 표

특히 PR 표는 각 셀의 문장이 길어 한 행이 페이지를 넘어갈 수 있다.

권장 형식:

```text
Backend PR #33
문제: 달성 후 미수령 보상의 변경 기준이 불명확했다.
판단·수정: 수령 시점 최신값 정책과 조건부 갱신을 적용했다.
검증: ChallengeServiceTest, PointServiceTest, 반복 요청 200/409.
```

PR별 2열 카드 또는 짧은 블록으로 바꾸면 PDF와 면접용 화면 모두에서 읽기 쉽다.

### 6. 첫 페이지를 실제 한 페이지로 고정한다

첫 페이지에는 다음만 남기는 것이 적절하다.

- 제목과 한 줄 소개
- 프로젝트 기간·5인 팀·개인 역할
- 대표 문제 3개
- 핵심 결과 4개
- 핵심 기술 4~5개

“추가 구현·보완”, 프런트 연동 상세, PR 번호는 2장 또는 기여 범위 장으로 이동할 수 있다. 첫 페이지를 작게 축소해서 한 페이지에 맞추면 30초 요약의 목적이 약해진다.

### 7. 이미지와 캡션의 증명 범위를 맞춘다

관리자 포인트 모달 이미지는 입력 화면이므로 “직접 연동한 화면”의 근거로는 충분하지만 성공 응답과 잔액 반영을 시각적으로 증명하지는 않는다.

다음 중 하나를 선택해야 한다.

- 캡션을 “API 연동 대상 모달” 수준으로 조정
- 저장 성공 메시지 또는 변경 후 잔액이 보이는 화면을 추가

현재 자료만 사용한다면 캡션을 낮추는 편이 안전하다.

## 추가하면 좋은 부분

### 1. 핵심 데이터 관계를 작은 SVG로 교체

스크린샷은 PNG가 적합하며 SVG로 바꿔도 선명도가 좋아지지 않는다. 반면 데이터 관계도는 벡터 SVG로 만들면 PDF에서 확대해도 깨지지 않는다.

관계도에는 다음만 표시하면 충분하다.

- `challenge`
- `challenge_reward`
- `challenge_progress`
- `member`
- `point_history`
- `member_coupon`
- `coupon`
- 지급 흐름에서 변경되는 `reward_claimed_at`, `point_balance`

전체 ERD를 넣기보다 대표 사례와 직접 관련된 관계만 표시하는 것이 좋다.

### 2. 페이지별 구성 계획

권장 PDF 구성은 다음과 같다.

1. 프로젝트·역할·문제·핵심 결과
2. 서비스 흐름과 개인 기여 범위
3. 핵심 판단 1 — 보상 확정 시점
4. 핵심 판단 2 — 조건부 갱신
5. 핵심 판단 3 — 트랜잭션과 롤백
6. 데이터 관계·대표 API 계약
7. 검증 E-01~E-05와 코드리뷰
8. 서비스 화면·개선 전후·한계
9쪽 이후. 필요한 증거 부록

### 3. 내부 참조에 페이지 번호 추가

현재 “7장”, “부록 B”, “E-01” 같은 참조는 좋다. PDF 레이아웃이 확정되면 다음처럼 페이지 번호를 함께 표시하면 찾기 쉽다.

```text
E-01 포인트 보상 검증 — 부록 B-1, p.9
```

페이지 번호는 최종 변환 뒤에 확정해야 한다.

### 4. 비전공자를 위한 용어 한 줄 설명

조건부 UPDATE와 트랜잭션은 본문에서 충분히 설명했지만 첫 등장에 다음 정도의 짧은 풀이를 넣으면 비전공자도 이해하기 쉽다.

- 조건부 UPDATE: 아직 수령하지 않은 행만 한 번 변경하는 DB 명령
- 트랜잭션: 관련된 저장 작업이 모두 성공하거나 모두 취소되도록 묶는 단위

### 5. PDF 품질 확인 목록

최종 변환 후 다음을 사람이 직접 확인해야 한다.

- 한글과 특수문자가 깨지지 않는가
- 이미지 6개가 모두 보이는가
- 표의 행이 페이지 사이에서 잘리지 않는가
- 코드 블록이 오른쪽에서 잘리지 않는가
- 이미지와 캡션이 서로 다른 페이지로 갈라지지 않는가
- 본문 글자가 인쇄 상태에서도 읽히는가
- 흑백으로 봐도 성공·실패와 표의 구분이 가능한가
- 빈 페이지나 고아 제목이 생기지 않는가
- 페이지 번호와 목차의 페이지가 일치하는가

## 문장 단위 수정 예시

### 예시 1 — 첫 페이지 요약 압축

현재:

> ABC는 전자책 대여·열람과 독서 활동 보상을 제공한 5인 팀 프로젝트다. 나는 부팀장으로 DB 설계와 백엔드 API 개발, 발표를 맡았으며, 대표 사례로 챌린지 달성 후 실제 보상이 지급되기까지 발생하는 지급 기준 변경, 중복 수령, 부분 반영 문제를 해결했다.

수정 예시:

> 5인 팀 전자책 플랫폼에서 부팀장과 백엔드 개발을 맡았다. 대표적으로 보상 정책 변경, 중복 수령, 지급 중 실패로 발생할 수 있는 데이터 불일치를 해결했다.

### 예시 2 — 조건부 UPDATE의 비전공자 설명

현재:

> 이를 막기 위해 Spring Data JPA 조건부 UPDATE에 reward_claimed_at IS NULL을 포함하고, 영향받은 행이 1일 때만 지급하도록 했다.

수정 예시:

> 아직 수령하지 않은 행만 변경하는 조건부 UPDATE를 실행하고, 실제로 한 행이 변경된 요청만 지급 단계로 넘겼다. 이미 다른 요청이 처리한 경우 변경 행이 0이므로 409를 반환했다.

### 예시 3 — 관리자 포인트 화면 캡션

현재:

> 팀원이 구현한 화면에서 회원의 실제 잔액을 API로 조회하고, 서버 성공 응답을 기준으로 포인트 지급·차감 결과를 반영하도록 직접 연동했다.

현재 이미지에 맞춘 수정 예시:

> 팀원이 구현한 A-013 포인트 조정 모달에 실제 잔액 조회와 지급·차감 API를 연결했다. 이 화면은 연동 대상을 보여 주며, 지급 결과의 직접 근거는 API 응답과 DB 이력이다.

### 예시 4 — E-05 증거 수준 조정

실제 실행 캡처가 없을 때:

> E-05는 PR #33·#35·#36 작성 당시 본문에 남긴 테스트 대상과 확인 결과를 문서 안에 요약한 기록이다.

실제 실행 캡처를 넣었을 때:

> E-05는 PR #33·#35·#36의 리뷰 지적, 관련 테스트 실행 결과, 수정 후 확인 내용을 한 화면에 정리한 증거다.

### 예시 5 — 배포와 개인 기여

현재:

> 팀 배포 환경에서 내가 구현한 API의 연동 결과를 확인했다. 배포 구성은 팀원이 담당했으며, 아래 화면은 API·DB 검증을 보완하는 서비스 결과 자료다.

권장:

> 배포는 팀원이 담당했다. 아래 화면은 팀 배포 환경에서 내가 구현한 API가 기존 화면과 연결된 결과이며, 백엔드 동작의 직접 근거는 E-01~E-05다.

### 예시 6 — 반복 수령 캡처의 오해 방지

> E-03은 Postman Runner로 같은 요청을 빠르게 두 번 실행해 `200 → 409` 응답을 확인한 자료다. 화면의 테스트 개수는 assertion 작성 여부를 나타내며, 이 자료를 자동 테스트나 동시 부하 테스트 결과로 사용하지 않는다.

### 예시 7 — 외부 URL을 넣지 않은 이유

문서 본문에는 별도 설명을 길게 넣지 않고 다음 한 줄이면 충분하다.

> 외부 접근이 필요한 저장소·배포 주소 대신 PR 변경 내용, API 계약, 테스트와 DB 결과를 문서 안에 직접 수록했다.
