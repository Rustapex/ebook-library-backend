# 2026-07-23 설계문서 전체 vs api-spec(final).md 반영 여부 검토보고

작성일: 2026-07-23
목적: `docs/작업현황/2026-07-23_관리자-대여-결제-신고-회원탈퇴API_설계문서_반영여부_검토보고.md`에서 PR64 범위만 확인한 데 이어, `docs/작업현황/설계문서`에 있는 **나머지 전체 파일**(PR64/추가분 2건 제외, 19개)을 `docs/API 명세/api-spec(final).md` 현재 내용과 대조했다. 이번 문서는 확인·보고만 하며, `api-spec(final).md`/설계문서 원문은 수정하지 않았다.

## 0. 확인 대상과 방법

- `docs/작업현황/설계문서` 최상위 19개 파일(이해 메모 하위 폴더, `ErrorCode_신규추가_완료.md`, PR64 관련 2건 제외) 전체를 읽었다.
- 각 파일이 "반영 예정"으로 남긴 API ID를 `rg`로 `api-spec(final).md`에서 찾아 현재 서술과 대조했다.
- 문서 대조만으로 판단이 어려운 3건(RENTAL/PAYMENT 정렬은 이미 §1 문서에서 처리 완료, `AdminPointAdjustRequest.requestId`, `SignupRequest.gender`, `MemberService` gender/password 처리)은 실제 소스(`rg`로 필요한 줄만) 대조로 검증했다. 전체 통독·빌드는 하지 않았다.

## 1. 결론 요약

19개 파일 중 **실제 반영이 필요한 항목이 있는 파일은 11개**다. 심각도가 다른 세 종류로 나뉜다.

| 심각도 | 의미 | 해당 항목 수 |
|---|---|---|
| A. API 자체가 명세에 없음 | 클라이언트가 명세만 보면 해당 endpoint 존재를 모름 | 3건(API-AUTH-006, API-ADMIN-COLLECTION-005/006, API-ADMIN-BOOK-005) |
| B. 명세의 Request/Response 필드가 실제 구현과 다름(구식) | 명세대로 호출하면 실패하거나 요청이 거부됨 | 4건(API-ADMIN-BOOK-002/003, API-ADMIN-MEMBER-004, API-AUTH-001 gender) |
| C. 정책 설명 누락(필드는 맞지만 세부 규칙 설명 없음) | 동작은 되지만 문서만 보고는 알 수 없음 | 나머지 |

**추가로, 문서 대조 중 코드 자체가 설계 의도와도 다른 사례를 1건 발견했다(§9 API-ME-002).** 이건 "명세 vs 설계문서" 문제가 아니라 "설계문서(의도) vs 실제 구현" 불일치라 별도로 표시한다.

## 3. B등급 — 명세 필드가 실제 구현과 달라 그대로 호출하면 실패함

### 3.1 `API-ADMIN-MEMBER-004`(회원 포인트 조정) — 필수 필드 `requestId` 누락 (소스로 확인)

- 근거: `2026-07-18_PR51_관리자-회원API_설계문서_반영예정.md` §4, `2026-07-16_관리자-회원API_설계문서.md` §5.
- **소스 확인**: `src/main/java/com/acorn/abc/admin/member/dto/AdminPointAdjustRequest.java:19-24` — `requestId`가 `@NotBlank` + UUID `@Pattern`으로 **필수**다.
- `api-spec(final).md:347`: `Body: pointAmount(+/-), description` — `requestId` 언급 자체가 없다. 이 명세만 보고 호출하면 필수 필드 누락으로 400을 받는다.
- 추가로 누락: `(memberId, requestId)` 멱등 재시도 시 기존 응답 재반환, 다른 금액/사유로 같은 키 재요청 시 409 `IDEMPOTENCY_KEY_CONFLICT`, `ADMIN`/`WITHDRAWN`/`DEACTIVATED` 대상 거부 — 셋 다 정책 칸에 없음.

### 3.2 `API-ADMIN-BOOK-002`(도서 등록) — Request body가 구버전 그대로 남아 있음

- 근거: `2026-07-18_관리자-도서API_설계문서.md` §2.2, `2026-07-20_PR52..._반영예정.md` 확정 계약표.
- `api-spec(final).md:216, 334`: Body가 `title, isbn?, publisherName, authors[], categoryIds[], keywords[], rentalType, rentalPrice, defaultRentalDays, coverImageUrl?, status, detail, file, pages[]`로 돼 있다.
- 실제 계약(두 설계문서 일치): `keywords[]`, `status`, `file`, `pages[]`는 요청 필드가 **아니다**(이 API가 원문·페이지·키워드·파일을 다루지 않음). `status`는 요청으로 받지 않고 항상 `INACTIVE` 생성. `detail`도 `{description?, tableOfContents?, publisherReview?}`로 범위가 좁다.
- Entity 목록(216행)에도 `BOOK_FILE, BOOK_PAGE, BOOK_KEYWORD, BOOK_KEYWORD_MAP`이 남아 있어 실제 미사용 Entity가 명세에 표시돼 있다.

### 3.3 `API-ADMIN-BOOK-003`(도서 수정) — 동일 문제 + Response 필드 누락

- `api-spec(final).md:217, 335`: Body가 "도서 수정 필드"로 뭉뚱그려져 있고, Entity 목록에 `BOOK_FILE, BOOK_PAGE, BOOK_KEYWORD_MAP`이 그대로 남아 있다.
- 실제 계약: Body는 002와 동일한 허용 메타정보 집합(`status` 제외) 전체 교체이며, 실 열람 원문·페이지·키워드·파일·누적 집계값은 어떤 경우에도 변경하지 않는다. Response에는 `status`가 포함돼야 하는데(PR52 반영예정) 현재 335행 Response는 `bookId, updatedAt`만 있다.

### 3.4 `API-AUTH-001`(회원가입) — `gender` 필수 전환이 반영 안 됨 (소스로 확인)

- 근거: `2026-07-21_회원가입_프로필_비밀번호_설계문서_반영예정.md` §2.
- **소스 확인**: `src/main/java/com/acorn/abc/auth/dto/SignupRequest.java:43-45` — `gender`는 이미 `@NotBlank` + `@Pattern(^(MALE|FEMALE)$)`로 **필수**로 바뀌어 있다.
- `api-spec(final).md:258`: Body에 `gender?`로 여전히 **선택**으로 표기돼 있다. 실제로는 생략하거나 `NONE`을 보내면 400이 난다.

## 5. 설계문서 자체가 "아직 코드/사이드카 SQL만 반영, 문서 미반영"이라고 명시한 항목(위 표에 없는 나머지)

아래는 각 설계문서가 스스로 "문서 원문 미수정"이라고 밝힌 항목 중, 위 A/B/C에 포함되지 않는 나머지다. api-spec 자체보다 ERD/DDL/화면흐름도/공통규칙 문서가 주 대상이라 이번 api-spec 최신화와는 결이 다르지만, 참고로 남긴다.

- `2026-07-13_ERD정책문서_읽은페이지지표_반영예정.md`: 대상은 `docs/기획문서들/...ERD-정책-확정-필요사항...md`(기획팀 소관, 이 저장소 밖 아님이지만 백엔드 담당자가 직접 수정하지 않기로 확정). api-spec 쪽은 이미 `API-STAT-001`에 "읽은 페이지" 필드명만 있고(321행) 계산 근사치 설명은 없음 — 우선순위 낮은 선택 사항으로 남긴다.
- `2026-07-13_관리자통계_성능인덱스_적용현황.md`: DB 인덱스 적용 여부 추적 문서, api-spec 대상 아님.
- `2026-07-13_프론트설계문서_수정요청.md`: `abc-proj-win-FRONT` 저장소 문서 대상, 이 저장소의 api-spec과 무관.
- `2026-07-14_PR46_감사로그_DB_CHECK제약_분리SQL_근거.md`: DB CHECK 제약 sidecar SQL 문서, api-spec 대상 아님(§1의 enum 허용값 문서화만 위 4.의 `API-ADMIN-AUDIT-001` 항목과 겹침).
- `2026-07-16_PR50_관리자-컬렉션API_updatedAt_설계문서_변경반영예정.md`: "Mockito 단위 테스트 확인 + Swagger·DB 수동 재검증 후"로 반영 조건이 걸려 있어, 검증 완료 여부부터 확인해야 한다(이번 문서 대조 범위 밖).

## 6. 별도 표시 — 설계 의도(문서)와 실제 코드가 서로 다른 사례 (api-spec 문제가 아님)

### `API-ME-002`(회원정보 수정)의 `gender` 처리

- 설계 의도(`2026-07-21_회원가입_프로필_비밀번호_설계문서_반영예정.md` §2): "`gender`가 요청에 포함되면 `400 VALIDATION_ERROR`로 거부. 수정 가능 필드는 `name`/`email`/`phone`만."
- **소스 확인 결과**: `MemberUpdateRequest.java:25`에 `gender` 필드가 여전히 존재하고, `ValidMemberUpdateRequest`의 "전부 null이면 거부" 판정에도 여전히 `gender`가 포함된다(`ValidMemberUpdateRequest.java:12` 주석). 그런데 `MemberService.java:94` `member.updateProfile(name, email, phone, member.getGender())` — 요청의 `gender` 값을 아예 쓰지 않고 **기존 값을 그대로 재대입**한다.
- 즉 실제 동작은 "요청에 `gender`를 넣어도 400이 나지 않고, 조용히 무시되며 기존 성별이 유지"된다 — **설계문서가 요구한 "400 거부"도 아니고, api-spec의 구버전 "gender 수정 가능"도 아닌 제3의 동작**이다.
- 이건 문서 반영 여부 이전에 코드 동작 자체를 어떻게 할지(안 A: 요청에 `gender` 있으면 400으로 명시적 거부 / 안 B: 현재처럼 조용히 무시 + 문서에 "무시됨"으로 명시) 결정이 필요해 보인다. **이번 검토보고 범위를 벗어나므로 코드는 건드리지 않았고, 사실만 보고한다.**
