# 2026-07-22 관리자 대여·결제·신고·회원 탈퇴 API 구현 계획

## 0. 목적과 범위

- 백엔드 API `API-ME-004`, `API-ADMIN-RENTAL-001`, `API-ADMIN-PAYMENT-001`, `API-ADMIN-REPORT-001`, `API-ADMIN-REPORT-002` 총 5개 endpoint를 구현한다.
- 기준 현황 문서에서 위 5개는 백엔드 구현·프런트 연결이 `X`, 화면은 `O`이다. 이번 작업은 화면을 새로 만들지 않고 백엔드 구현을 완료하는 범위다.
- 프런트의 API 파라미터·응답 매핑 수정은 이후 별도 작업/PR로 관리한다. JSX·CSS·화면 배치 변경은 이번 범위에서 제외한다.
- 기존 `docs/API 명세/api-spec(final).md`, ERD·DDL 문서는 **수정하지 않는다**. 현재 기준 명세와 프런트 호출 간 차이는 후속 설계 기록 문서에만 남긴다.

### 범위 제외

- 관리자 도서, 관리자 도서관, 관리자 카테고리 API의 생성·수정
- 대여 취소·강제 종료·탈퇴 전용 대여 상태 추가, `BOOK_RENTAL` 물리 삭제
- 5회/10회 누적 제재, 자동 리뷰 숨김, 자동 계정 제재·자동 탈퇴 등 자동 조치
- 신고 상세 조회 신규 API
- 프런트 화면 디자인·JSX·CSS·배치 변경

## 2. 확정 API 계약과 비즈니스 규칙

| API ID | Method / URL | 구현 계약 |
|---|---|---|
| `API-ME-004` | `DELETE /api/v1/me` | 현재 비밀번호 확인 후 본인 계정을 `WITHDRAWN`으로 전환하고 `withdrawnAt`, 선택 사유를 저장한다. 물리 삭제하지 않는다. |
| `API-ADMIN-RENTAL-001` | `GET /api/v1/admin/rentals` | `q`, `memberId`, `status`, `page`, `size`로 대여 현황과 진행률을 관리자 전용으로 조회한다. 조회 전용이다. |
| `API-ADMIN-PAYMENT-001` | `GET /api/v1/admin/payments` | 기준 명세의 `q`, `from`, `to`, `page`, `size`로 `PAID` 결제만 조회한다. 취소·환불·복구 기능은 만들지 않는다. |
| `API-ADMIN-REPORT-001` | `GET /api/v1/admin/reports` | `targetType`, `status`, `page`, `size`로 책·리뷰 신고 목록을 조회한다. 목록 행에 모달 표시용 신고자·대상·신고 내용 정보를 포함하며 별도 상세 API는 만들지 않는다. |
| `API-ADMIN-REPORT-002` | `PATCH /api/v1/admin/reports/{targetType}/{reportId}/status` | 관리자 수동 신고 처리 API다. 처리 상태·결과, 리뷰 숨김, 계정 정지를 조건부로 처리한다. |

### 2.1 회원 탈퇴

- 대상은 본인 계정이며 `ADMIN` 역할 계정의 탈퇴는 Service에서도 거부한다.
- 현재 비밀번호가 일치해야 한다.
- 회원에게 `READY` 또는 `READING` 상태의 `BOOK_RENTAL`이 하나라도 있으면 탈퇴를 거부한다. `OWNED`는 소장 상태이므로 탈퇴를 막지 않는다.
- 대여 행의 상태를 강제로 끝내거나 바꾸지 않는다. 취소/탈퇴 상태를 새로 만들지 않는다.
- 성공 시 회원 상태만 `WITHDRAWN`으로 전환하고, 탈퇴 일시와 선택 사유를 저장한다. 관계 데이터 및 이력은 보존한다.
- 탈퇴 회원의 개인정보 비식별화·별도 보존 기간 처리는 이번 API 구현에서 수행하지 않는다. 물리 삭제하지 않고 접근을 차단하는 현재 정책을 유지하며, 향후 정책 확정 시 별도 설계·DB 작업으로 분리한다.

### 2.2 탈퇴 후 인증 차단

- 새 로그인은 기존 로그인 흐름의 회원 상태 검증을 유지한다.
- 이미 발급된 토큰도 다음 요청부터 차단하도록 JWT 인증 단계에서 회원을 조회하고 `JOINED` 상태일 때만 SecurityContext를 만든다.
- `WITHDRAWN`, `DEACTIVATED`, `SANCTIONED` 회원의 토큰은 인증되지 않은 요청으로 처리되어 보호 API에서 401을 반환한다.
- 특정 Controller마다 상태 검사를 중복 추가하지 않는다. JWT 필터와 회원 상태 조회 경계를 한 곳으로 두어 공통 보안 동작으로 관리한다.

### 2.3 관리자 대여·결제 조회

- 두 API는 관리자 권한만 허용하고, 변경·감사 로그·상태 전이를 수행하지 않는다.
- 대여 목록은 `READY`, `READING`, `OWNED` 상태만 허용하고, 고정 정렬은 `createdAt DESC, rentalId DESC`로 한다.
- 대여 응답은 대여 ID, 회원 ID·이름, 도서 ID·제목, 상태, 대여·최초 열람·종료 시각, 진행률 및 결제 요약을 포함한다. 결제 정보가 없는 경우 결제 요약은 nullable로 반환한다.
- 결제 목록은 `PAID`만 반환하고, 고정 정렬은 `paidAt DESC, paymentId DESC`로 한다. 결제 ID, 회원·도서·대여 식별 정보, 결제수단, 정가·쿠폰·포인트 차감·최종 결제금액, 결제 시각을 반환한다.
- 목록과 count query는 같은 predicate를 사용하며, 페이징은 0-based `PageResponse`로 반환한다. 필요 연관 데이터는 목록 page 후 bulk 조회·조립하여 N+1과 중복 root row를 방지한다.

### 2.4 관리자 신고의 수동 처리

- 신고 대상은 `BOOK`, `REVIEW`만 허용하며 회원 대상 신고 API는 만들지 않는다.
- 상태값은 `WAITING`, `PROCESSING`, `DONE`, `REJECTED`만 허용한다. `WAITING`은 `PROCESSING`/`DONE`/`REJECTED`로, `PROCESSING`은 `DONE`/`REJECTED`로만 전환한다. `DONE`, `REJECTED`는 이번 범위에서 재개하지 않는 최종 상태다.
- `processResult`는 최종 처리(`DONE`, `REJECTED`)일 때 trim 후 빈 값이 아니어야 한다.
- `hideReviewYn=true`는 `REVIEW` 신고를 `DONE`으로 처리할 때만 허용하며, 해당 리뷰 상태만 `HIDDEN`으로 바꾼다. 자동 숨김은 하지 않는다.
- 제재는 `REVIEW` 신고를 `DONE`으로 처리하는 관리자 수동 요청에서만 허용한다. 이번 신고 API의 허용 제재 유형은 `ACCOUNT_SUSPENSION` 하나이며, 제재 사유·시작일은 필수, 종료일은 선택이다. 종료일이 없으면 별도 관리자 수동 해제 전까지 유지한다.
- `BOOK` 신고에는 리뷰 숨김·회원 제재를 허용하지 않는다. `RENTAL_BAN`, `REVIEW_BAN`은 이번 신고 API 범위에서 제외한다.
- 누적 횟수·금칙어·신고 수에 따른 자동 제재/자동 숨김/자동 탈퇴는 구현하지 않는다. 모든 처리 결과는 관리자 요청에 의해서만 발생한다.
- 처리 변경, 리뷰 숨김, 계정 정지·제재 이력, 신고 알림, 성공 감사 로그는 하나의 transaction으로 처리한다. 어느 하나라도 실패하면 모두 rollback한다.

## 3. 구현 구조와 공통 코드 보호

### 3.1 추가·수정 영역

- `member`: 탈퇴 Request/Response DTO, `DELETE /me`, 현재 비밀번호·관리자 계정·진행 중 대여 검증, 회원 상태 변경 메서드
- `rental`: 관리자 대여 목록 전용 Controller/Service/DTO/Repository query와 탈퇴용 `exists` query
- `payment`: 관리자 결제 목록 전용 Controller/Service/DTO/Repository query
- `admin.report`(또는 기존 패키지 구조에 맞춘 관리자 신고 패키지): 목록·처리 Controller/Service/DTO, BOOK/REVIEW 분기 Repository query
- `common.security`: JWT에 연결된 회원 상태 조회 경계. 역할 판정 규칙과 JWT 형식·발급 규칙은 바꾸지 않는다.

### 3.2 공통 코드 영향 제한

- 공통 `ApiResponse`, `PageResponse`, 기존 공개 대여·결제·리뷰 API의 응답 계약은 수정하지 않는다.
- 상태 차단은 JWT 필터 한 곳에서 수행한다. 각 API Service에 동일한 `WITHDRAWN` 검사 코드를 중복하지 않는다.
- 기존 ErrorCode로 표현 가능한 오류는 재사용한다. 진행 중 대여 탈퇴 거부·관리자 탈퇴 거부처럼 정확한 코드가 없을 때만 기존 코드를 변경하지 않고 additive 방식으로 새 코드를 추가한다. 그 경우 별도 ErrorCode 기록 문서에 이유·영향·코드를 남긴다.
- 관리자 신고의 성공 감사 로그는 기존 `AdminAuditLogWriter` 패턴을 재사용한다. 감사 로그 저장 실패를 catch 후 무시하지 않으며 본문 transaction도 rollback하는 fail-closed 정책을 유지한다.
- 신규 `ADMIN_AUDIT_LOG` action/target enum이 필요하면 기존 enum 값을 바꾸지 않고 상수만 추가하며, 기존 감사 로그 회귀 테스트를 수행한다.

## 4. 프런트 연계 원칙과 후속 조율 사항

- 프런트는 데이터 요청·응답 매핑을 후속 작업에서 수정할 수 있다. 그러나 이 백엔드 작업은 기준 API 명세를 우선하며, 프런트의 현재 파라미터에 맞추기 위해 비공개 alias나 별도 endpoint를 만들지 않는다.
- `API-ME-004`는 프런트가 이미 `DELETE /me` 성공 후 로컬 토큰을 제거하고 홈으로 이동하는 흐름을 사용한다. 백엔드의 요청 시 상태 검증은 오래 열린 탭·외부 클라이언트의 기존 토큰도 차단한다.
- 결제 화면의 `startDate`/`endDate`는 후속 프런트 작업에서 기준 계약인 `from`/`to`로 맞춘다. 관리자 회원 상세의 결제 이동도 기준 결제 목록 계약의 `q`를 사용하거나 화면 동작을 조정하며, 명세에 없는 `memberId` query를 이번 백엔드에 추가하지 않는다.
- 신고 화면의 `q` 및 제재 UI는 후속 프런트 작업에서 기준 계약과 수동 처리 정책에 맞춘다. 제재 입력은 `REVIEW` 신고일 때만 전송하고, `BOOK` 신고에는 보내지 않는다.
- 위 차이와 프런트 수정 범위는 구현 전·후 별도 설계 기록으로 남긴다. 이번 문서와 구현은 프런트 JSX·CSS·디자인 파일을 수정하지 않는다.

## 5. 테스트·검증 계획

### 5.1 자동 테스트

- 단위 테스트는 개인 로컬 DB나 팀 공유 DB에 연결하지 않는다. mock/fake로 비밀번호 검증, 상태 전이, 권한, request 검증, transaction 호출 규칙을 검증한다.
- DB가 필요한 repository/integration 테스트는 다른 개발자도 동일하게 실행할 수 있는 독립 테스트 DB를 사용한다. 개인 DB의 기존 데이터는 전제하지 않으며, `src/main/resources/schema.sql` 및 프로젝트에서 필수로 관리하는 `src/main/resources` SQL을 적용한 빈 DB에서 seed를 명시적으로 만든다.
- 탈퇴: 비밀번호 불일치, `ADMIN` 계정 거부, `READY`/`READING` 존재 거부, `OWNED`만 존재 성공, 성공 후 상태·탈퇴 일시·사유, 대여 행 불변을 검증한다.
- 인증: `JOINED` 토큰은 통과하고 `WITHDRAWN`·`DEACTIVATED`·`SANCTIONED` 토큰은 보호 API에서 차단되는지 검증한다.
- 관리자 조회: ADMIN 성공, 비관리자 403, 미인증 401, 잘못된 enum/query 400, 정렬·페이징·count 정확성, 결제 `PAID` 한정 및 nullable 결제 요약을 검증한다.
- 신고: BOOK/REVIEW 목록 조립, 허용 상태 전이, 최종 처리 사유 검증, BOOK 신고의 숨김·제재 거부, REVIEW `DONE` 수동 숨김·계정 정지 성공, 자동 처리 미발생을 검증한다.
- rollback: 리뷰 상태·회원 상태·제재 이력·알림·감사 로그 중 마지막 저장이 실패하는 경우 앞선 변경도 남지 않는지 검증한다.

### 5.2 수동 Swagger/Postman 검증

- 수동 검증은 자동 테스트와 별개다. 개인 로컬 DB의 기존 데이터를 신뢰하지 않고 시작 상태 확인 → 명시적 test seed INSERT → Swagger/Postman 요청 → 결과 SELECT → 정확한 ID 기반 정리 순서로 수행한다.
- 각 시나리오에 API ID, Method/URL, 인증 주체, query/path/body, 예상 응답, 직후 확인 SQL, 다음 요청 또는 정리 단계가 한 흐름으로 이어지도록 작성한다.
- 진행 중 대여 탈퇴 거부, `OWNED` 탈퇴 성공, 기존 토큰 차단, 관리자 대여/결제 필터, BOOK/REVIEW 신고 처리, 수동 숨김·제재, 잘못된 조합 거부, rollback 검증을 포함한다.

## 7. 구현 순서와 완료 조건

1. 후속 설계 차이 기록과 이해 메모에서 5개 API의 요청·응답·상태값 및 프런트 조율 범위를 고정한다.
2. 기존 ErrorCode, 감사 로그 enum, 알림·제재·회원 상태·필수 sidecar SQL을 인벤토리하고 additive 변경 필요 여부만 결정한다.
3. `API-ME-004`와 JWT 상태 검증을 구현하고, 진행 중 대여 확인 query와 회원 탈퇴 테스트를 작성한다.
4. 관리자 대여·결제 조회 API를 전용 DTO·Repository query로 구현하고 권한·페이징·필터 테스트를 작성한다.
5. 관리자 신고 목록·수동 처리 API를 구현하고, 리뷰 숨김·계정 정지·알림·감사 로그 transaction 및 rollback 테스트를 작성한다.
6. 프런트 데이터 매핑 보완은 별도 작업으로 분리해 PR 또는 작업 기록을 남긴다. 이번 백엔드 PR에는 포함하지 않는다.
7. 자동 테스트와 build를 수행한 뒤, 요청이 있을 때만 Swagger/Postman 체크리스트·SQL을 작성하여 seed부터 정리까지 수동 검증한다.

완료 조건은 다음과 같다.

- 5개 API가 기준 URL·권한·응답 계약으로 동작하고, 범위 제외 API나 자동 제재 기능이 추가되지 않는다.
- 탈퇴는 진행 중 대여를 안전하게 거부하며 대여 데이터를 변경하지 않는다.
- 탈퇴·비활성·계정 정지 회원의 기존 JWT는 다음 보호 요청부터 차단된다.
- 관리자 신고의 실제 변경은 관리자 수동 요청으로만 발생하고, 관련 저장과 감사 로그는 원자적으로 처리된다.
- 자동 테스트는 개인 DB 데이터에 의존하지 않으며, 수동 테스트 자료는 별도 요청 후 지정 경로에 작성한다.
