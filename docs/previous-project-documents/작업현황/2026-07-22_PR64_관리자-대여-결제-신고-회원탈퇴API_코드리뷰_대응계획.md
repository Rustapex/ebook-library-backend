# 2026-07-22 PR #64 관리자 대여·결제·신고·회원 탈퇴 API 코드리뷰 대응 계획

## 0. 목적과 범위

- PR #64의 동시성·보호 회원·탈퇴 검증 순서 리뷰를 반영해 다음 5개 API의 구현·검증 완료 기준을 닫는다.
  - `API-ME-004`
  - `API-ADMIN-RENTAL-001`
  - `API-ADMIN-PAYMENT-001`
  - `API-ADMIN-REPORT-001`
  - `API-ADMIN-REPORT-002`
- 최초 작성 단계에서는 대응 계획과 후속 문서만 준비했고, 이후 PR에서 소스·자동 단위 테스트와 `API-ME-004`, `API-ADMIN-REPORT-002` API 명세 문구가 실제로 수정됐다. 재코드리뷰 후속 기준은 `2026-07-22_PR64_재코드리뷰_후속수정계획.md`에서 관리한다.
- 일반 사용자 신고 API, 관리자 도서관 API, 프런트 코드, 신규 API, 신규 ErrorCode는 범위에서 제외한다.

## 1. 리뷰 결론과 확정 정책

| 리뷰 항목 | 확정 대응 |
|---|---|
| 탈퇴·대여 경합 | 세 경로가 같은 회원 행을 먼저 `PESSIMISTIC_WRITE`로 잠그고, 잠금 안에서 상태·진행 중 대여를 검증한다. |
| ADMIN 탈퇴 | 잠금 후 ADMIN 역할을 먼저 거부한다. ADMIN은 `JOINED` 상태여도 탈퇴할 수 없다. |
| 동일 신고 중복 처리 | BOOK/REVIEW 신고 행을 잠가 한 요청만 상태 전이를 완료한다. |
| 서로 다른 REVIEW 신고의 같은 회원 제재 | 신고 행 잠금 뒤 대상 회원 행을 잠가 직렬 처리하며, 중첩 `ACCOUNT_SUSPENSION`을 허용한다. |
| 보호 회원 제재 | 제재 요청이 있는 경우 ADMIN/WITHDRAWN/DEACTIVATED 대상은 403 `AUTH_ACCESS_DENIED`로 요청 전체를 거부한다. |
| lock timeout/deadlock | transaction 내부에서 복구하지 않고 rollback 후 공통 예외 처리에서 MySQL 원인일 때만 409 `CONCURRENT_UPDATE`로 변환한다. |

## 2. 구현 변경 계획

### 2.1 회원 탈퇴·무료 대여·유료 대여/결제

- `MemberService.withdraw()`의 첫 DB 조회를 `MemberRepository.findByIdForUpdate(memberId)`로 교체한다.
- `RentalService.createFreeRental()`과 `PaymentService.createPaidRentalAndPayment()`의 일반 회원 조회도 동일 잠금 조회로 교체하고, 도서 조회보다 먼저 수행한다.
- 탈퇴 순서는 `회원 잠금 → ADMIN 역할 거부 → JOINED 검증 → 비밀번호 검증 → READY/READING 존재 검증 → WITHDRAWN 변경`으로 고정한다.
- 무료·유료 대여 순서는 `회원 잠금 → JOINED 검증 → 진행 중 대여 검증 → 도서·콘텐츠·쿠폰·결제 검증 및 저장`으로 고정한다.
- 대여가 먼저 커밋되면 탈퇴는 409 `MEMBER_WITHDRAWAL_RENTAL_IN_PROGRESS`으로 거부한다. 탈퇴가 먼저 커밋되면 대여는 403 `AUTH_ACCESS_DENIED`로 거부한다.
- 승리한 요청의 대여·결제 데이터는 유지하고, 실패한 요청의 변경만 rollback한다.

### 2.2 관리자 신고 처리와 제재

- BOOK/REVIEW 신고 Repository에 `findByIdForUpdate()`를 추가하고, 신고 상태 전이는 잠금 뒤 최신 상태 기준으로 검증한다.
- REVIEW 신고에서 `ACCOUNT_SUSPENSION`이 요청되면 리뷰 작성자 회원을 `MemberRepository.findByIdForUpdate()`로 추가 잠금한다.
- 보호 대상 제재 요청은 상태·리뷰·제재 이력·알림·감사 로그를 만들기 전에 403으로 거부한다.
- 이미 `SANCTIONED`인 일반 회원의 추가 계정 정지는 허용한다. 서로 다른 유효 신고 두 건이 제재되면 제재 이력은 2건, 알림·감사 로그는 신고별 각 1건을 남기고 회원은 계속 `SANCTIONED`로 유지한다.
- 직렬 처리상 마지막 유효 제재를 `currentSanction`으로 연결한다. 만료 배치가 다른 활성 제재를 발견하면 최신 활성 제재로만 재지정하고, 유효 제재가 없을 때만 `JOINED`로 복구한다.

### 2.3 잠금 예외 경계

- 별도 5초 세션 lock timeout 조작은 추가하지 않고 DB 기본 대기 정책을 사용한다.
- write Service는 lock timeout/deadlock을 catch해 같은 transaction을 계속 진행하지 않는다.
- `GlobalExceptionHandler`에서 예외 원인 체인을 확인해 MySQL lock wait timeout 또는 deadlock일 때만 409 `CONCURRENT_UPDATE`로 변환한다.
- 첫 요청이 커밋된 뒤 두 번째 요청이 변경된 신고 상태를 읽은 경우는 409 `REPORT_INVALID_STATUS_TRANSITION`으로 처리한다.
- UNIQUE/FK·검증·기타 무결성 오류는 `CONCURRENT_UPDATE`로 변환하지 않는다.
- 만료 배치는 HTTP 응답이 없으므로 잠금 충돌 후보를 no-op으로 두고 다음 배치에서 다시 검토한다.

## 3. 테스트·검증 계획

### 3.1 자동 테스트

- 단위 테스트는 개인·공유 DB에 연결하지 않고 mock/fake로 Service의 잠금 조회 호출 순서, 역할·상태 검증, 예외 변환 경계를 검증한다.
- DB 통합 테스트는 `test` profile의 전용 MySQL DB `ABC_TEST`만 사용한다. 설정은 향후 `src/test/resources/application-test.yml`에 두고 연결 정보는 환경 변수로 주입한다.
- 테스트 실행 전 전용 DB를 초기화한 뒤 `schema.sql` 및 프로젝트 관리 SQL을 적용한다. 각 테스트는 고유 `testRunId` seed를 만들고 자신이 만든 데이터만 정리한다.
- `sleep` 대신 latch/barrier를 사용해 다음 경합을 검증한다.
  - 같은 BOOK/REVIEW 신고: 한 건만 성공하고 나머지는 최신 상태 충돌 또는 실제 잠금 충돌로 거부되는지
  - 서로 다른 REVIEW 신고가 같은 회원을 제재: 제재 이력 2건, `SANCTIONED` 유지, 마지막 유효 제재 연결, 신고별 알림·감사 로그 1건씩인지
  - 만료 배치와 신규 계정 정지: 새 제재 직후 잘못 `JOINED`로 복구되거나 `currentSanction`이 이전 값으로 돌아가지 않는지
  - 무료 대여/탈퇴 및 유료 대여·결제/탈퇴: 대여 승리·탈퇴 승리 결과와 부수 데이터가 각각 정확한지

### 3.2 Swagger/Postman 수동 검증

- 기존 `api-test-results/0722 API 개발/0722 API 개발 SWAGGER ,POSTMAN 테스트.md`와 `.sql`을 이번 계획에 맞게 최신화한다.
- 완료된 신고를 같은 요청으로 다시 처리하면 409 `REPORT_INVALID_STATUS_TRANSITION`이고 제재·알림·감사 로그 수가 증가하지 않는지 확인한다.
- ADMIN 탈퇴 403, 진행 중 대여 탈퇴 409, OWNED만 남은 탈퇴 성공은 기존 시나리오를 유지한다.
- 실제 동시 요청·timeout/deadlock은 Swagger/Postman 수동 요청의 재현 기준으로 삼지 않고 자동 경합 테스트에서만 판정한다.

## 5. 구현 순서와 완료 조건

1. 기존 ErrorCode·공통 예외 처리·회원/신고 Repository 잠금 메서드의 실제 사용처를 확인한다.
2. 회원 탈퇴·무료 대여·유료 대여/결제의 회원 선잠금과 검증 순서를 수정한다.
3. 신고 행·제재 대상 회원 잠금, 보호 회원 거부, 중첩 제재 처리를 수정한다.
4. 만료 배치와 신규 제재의 직렬화 조건을 확인하고 회귀 테스트를 추가한다.
5. 단위·통합·동시성 테스트와 Swagger/Postman 수동 테스트 자료를 최신화한다.
6. 자동 검증과 수동 검증을 구분해 기록하고, 모두 통과한 뒤에만 5개 API를 백엔드 완료로 갱신한다.

완료 기준은 `WITHDRAWN + READY/READING` 조합이 남지 않고, 동일 신고의 중복 부수 데이터·보호 회원 제재·만료 배치의 잘못된 복구가 발생하지 않는 것이다. 일반 사용자 신고 도메인 전체 또는 관리자 도서관 API의 완료를 이번 결과에 포함하지 않는다.
