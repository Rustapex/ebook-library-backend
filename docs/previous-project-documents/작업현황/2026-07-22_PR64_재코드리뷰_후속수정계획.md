## 2. 코드 수정 계획

### 2.1 관리자 신고 통합 목록 고정 정렬

- 대상: `AdminReportRepository.search()`의 native query.
- `ORDER BY created_at DESC, report_id DESC`를 `ORDER BY created_at DESC, report_id DESC, target_type ASC`로 변경한다.
- `book_report_id`와 `review_report_id`가 같은 값이고 `created_at`까지 같은 BOOK/REVIEW 행도 `BOOK -> REVIEW` 순서로 고정한다.
- 검색 predicate와 count query는 변경하지 않는다. API 요청·응답 DTO와 URL도 변경하지 않는다.
- `target_type`은 결과 행을 유일하게 정렬하기 위한 마지막 tie-breaker일 뿐, 별도 비즈니스 우선순위를 추가하는 용도로 사용하지 않는다.

### 2.2 잠금 예외 원인 판별

- 대상: `GlobalExceptionHandler.handlePessimisticLockingFailureException()`.
- 예외와 `cause` 체인을 순회해 `SQLException`의 MySQL vendor error 및 SQLState를 확인한다. 예외 메시지 문자열 비교는 사용하지 않는다.
- 다음 실제 DB 잠금 충돌만 기존 `CONCURRENT_UPDATE(409)`로 변환한다.
  - lock wait timeout: vendor error `1205`, SQLState `HY000`
  - deadlock: vendor error `1213`, SQLState `40001`
- 위 조합이 확인되지 않는 `PessimisticLockingFailureException`은 동시성 오류로 오분류하지 않고 기존 공통 미처리 예외 응답인 `INTERNAL_SERVER_ERROR(500)` 경로로 보낸다.
- Service transaction 내부에서 예외를 잡아 계속 처리하지 않는다. transaction rollback이 끝난 뒤 전역 예외 처리에서 HTTP 응답만 변환한다.
- 이 변경은 Java 예외 처리와 테스트만 수정한다. DB 제약조건, 스키마, session lock timeout은 변경하지 않는다.

## 3. 자동 테스트 계획

### 3.1 빠른 단위·Repository 검증

- `GlobalExceptionHandler` 테스트에 다음 경우를 추가한다.
  - cause 체인에 MySQL `1205/HY000`이 있으면 409 `CONCURRENT_UPDATE`.
  - cause 체인에 MySQL `1213/40001`이 있으면 409 `CONCURRENT_UPDATE`.
  - 다른 vendor error, UNIQUE/FK 및 일반 `PessimisticLockingFailureException`은 409로 변환하지 않고 500 공통 오류.
  - 중첩 wrapper 안의 `SQLException`도 판별하며 cause 순회가 무한 반복되지 않는다.
- 관리자 신고 Repository 통합 테스트에 BOOK/REVIEW 행의 `created_at`과 각 테이블 PK를 같게 만든 fixture를 추가한다.
- page size를 1로 조회했을 때 첫 페이지는 BOOK, 다음 페이지는 REVIEW이며 `totalElements=2`, 중복·누락이 없음을 검증한다. 같은 조회를 반복해도 순서가 바뀌지 않아야 한다.

### 3.2 MySQL 동시성 통합 테스트

- `src/test/resources/application-test.yml`을 만들고 `@ActiveProfiles("test")`로 명시한 테스트만 전용 MySQL `ABC_TEST`를 사용하도록 한다.
- 연결 비밀값은 파일에 기록하지 않고 환경 변수로 주입한다. 기본 개발 DB `abc`와 팀원의 개인 DB를 자동 테스트 대상으로 사용하지 않는다.
- `ABC_TEST`는 매 실행 전 `schema.sql`과 현재 runtime에 필요한 관리자 회원 sidecar SQL을 적용한 상태로 준비한다. 테스트는 고유 `testRunId` seed를 만들고 자신이 생성한 데이터만 정리한다.
- 단위 테스트는 DB에 연결하지 않는다. 실제 잠금 검증이 필요한 통합 테스트만 `ABC_TEST`를 사용한다.
- `sleep`에 의존하지 않고 latch/barrier로 transaction 시작·잠금 획득·두 번째 요청 진입 순서를 통제한다.
- 기존 대응계획의 다음 경합을 실제 MySQL에서 검증한다.
  - 탈퇴 vs 무료 대여
  - 탈퇴 vs 유료 대여·결제
  - 동일 BOOK 신고 동시 처리
  - 동일 REVIEW 신고 동시 처리
  - 서로 다른 REVIEW 신고가 같은 회원에게 중첩 계정 정지
  - 만료 배치 vs 신규 `ACCOUNT_SUSPENSION`
- 승리한 transaction의 데이터만 남고 실패 요청의 대여·결제·쿠폰 사용·포인트 이력·제재·알림·감사 로그가 남지 않는지 시나리오별로 구분해 검증한다.
- 테스트 전용 schema 준비 외에 개발 DB `abc`에는 DDL이나 seed를 적용하지 않는다.

## 4. 수동 검증 계획

- Swagger/Postman 수동 테스트는 후속 코드 수정과 전체 자동 테스트가 끝난 뒤 마지막 단계에서 수행한다. 중간 코드 상태에서 성공 기록을 만들지 않는다.
- 다음 기존 자료를 최종 코드 계약에 맞게 먼저 최신화한다.
  - `api-test-results/0722 API 개발/0722 API 개발 SWAGGER ,POSTMAN 테스트.md`
  - `api-test-results/0722 API 개발/0722 API 개발 SWAGGER ,POSTMAN 테스트.sql`
- 체크리스트에는 API ID, URL, method, parameter/body, 선행 seed SQL 실행 시점, 요청 순서, 기대 상태코드, 요청 후 확인 SQL, 최종 정리 순서를 한 흐름으로 유지한다.
- 신고 목록은 동일 시각·동일 ID BOOK/REVIEW fixture를 준비해 page 0/1에서 중복·누락과 순서 변동이 없는지 확인한다.
- 잠금 timeout/deadlock 자체는 Swagger/Postman으로 억지 재현하지 않고 자동 통합 테스트 결과를 근거로 삼는다.
- 수동 검증 결과는 실제 수행 후 성공·실패와 확인 SQL 결과를 기록한다. 수행 전에는 완료로 표시하지 않는다.

## 6. 구현 순서

1. `AdminReportRepository.search()`에 `target_type ASC` tie-breaker를 추가한다.
2. 동일 시각·동일 ID BOOK/REVIEW pagination Repository 통합 테스트를 추가한다.
3. `GlobalExceptionHandler`에 MySQL `1205/HY000`, `1213/40001` 원인 판별을 추가한다.
4. 잠금 예외 409/500 분기 단위 테스트를 추가한다.
5. `ABC_TEST` 전용 test profile과 seed·cleanup 경계를 구성한다.
6. 기존 대응계획에 적힌 여섯 가지 MySQL 동시성 통합 테스트를 추가·실행한다.
7. 관련 단위/Repository/통합 테스트를 실행하고 전체 `./gradlew.bat build`를 수행한다.
8. 기존 대응계획·설계 반영 기록·필요한 이해 메모를 실제 PR 내용과 맞춘다.
9. Swagger/Postman `.md`·`.sql`을 최종 코드에 맞게 최신화한 뒤 실제 수동 검증을 수행하고 결과를 기록한다.
10. 모든 검증이 통과한 경우에만 프로젝트 현황 문서의 이번 5개 API를 백엔드 완료로 갱신한다.

## 7. 완료 조건

- 같은 `created_at`, 같은 숫자 ID의 BOOK/REVIEW 신고가 페이지 경계에서 중복·누락 없이 항상 같은 순서로 조회된다.
- MySQL lock wait timeout/deadlock만 409 `CONCURRENT_UPDATE`이며 다른 잠금·무결성 오류는 409로 오분류되지 않는다.
- 자동 테스트가 개발 DB `abc`에 연결되지 않고 독립된 `ABC_TEST`에서 재현 가능하게 통과한다.
- 기존 여섯 가지 경합에서 잘못된 상태 조합이나 실패 transaction의 side effect가 남지 않는다.
- 전체 build가 통과한다.
- Swagger/Postman/DB 수동 테스트는 최종 코드 기준으로 실제 수행됐고 자료에 결과와 정리 증거가 남아 있다.
- 기존 대응계획, 설계 반영 기록, API 명세의 실제 변경 이력 및 프로젝트 현황이 서로 모순되지 않는다.
