## 1. 감사 로그 actionType/targetType 허용값 문서화

- 관련 API: `API-ADMIN-AUDIT-001 GET /api/v1/admin/audit-logs`
- 현재 코드 기준 source of truth: `AdminAuditLogActionType`, `AdminAuditLogTargetType` enum
- 변경 필요 이유: Swagger `@Schema(allowableValues)`는 문자열 배열이라 enum과 수동 동기화된다. API 명세에도 허용값 목록과 “enum 값과 동기화 필요”를 명확히 남겨야 한다.
- 나중에 반영할 문서 후보:
  - `docs/API 명세/api-spec(final).md`의 관리자 감사 로그 조회 절
  - 관리자 API Swagger/Postman 체크리스트
- 반영할 내용:
  - `actionType` 허용값은 `AdminAuditLogActionType` 기준
  - `targetType` 허용값은 `AdminAuditLogTargetType` 기준
  - 목록에 없는 값은 `400 VALIDATION_ERROR`
  - Swagger 허용값과 enum이 불일치하면 테스트 실패로 잡는다는 구현 정책

## 2. `reading_progress.last_read_at` 인덱스 적용 경로

- 관련 기능: 사용자 통계 `API-STAT-001 GET /api/v1/me/statistics`의 읽은 페이지 지표
- 확정 내용: `idx_reading_progress_last_read_at`는 `schema.sql`에 넣지 않고, 기존처럼 별도 수동 SQL 적용 경로로 관리한다.
- 나중에 반영할 문서 후보:
  - DB/ERD 정책 문서의 `reading_progress` 인덱스 설명
  - 운영/공유 DB 적용 노트
  - Swagger/Postman 테스트 SQL 또는 수동 DB 확인 체크리스트
- 반영할 내용:
  - `last_read_at` 기간 필터를 쓰는 사용자 통계 경로가 있음
  - `idx_reading_progress_last_read_at` 적용 여부 확인 SQL
  - `schema.sql`과 분리 유지한다는 결정과, 기존/공유 DB에는 별도 SQL로 수동 적용해야 한다는 절차를 구분

## 3. `user_reading_statistic` dormant 상태

- 관련 API: `API-STAT-001 GET /api/v1/me/statistics`
- 현재 확정 내용: 사용자 통계는 실시간 집계이며 `user_reading_statistic` 테이블/배치를 사용하지 않는다.
- 변경 필요 이유: 테이블과 엔티티가 존재하므로, 다음 유지보수자가 이 테이블을 현재 API의 저장소로 오해할 수 있다.
- 나중에 반영할 문서 후보:
  - ERD/DDL 설명 문서의 `user_reading_statistic` 테이블 설명
  - 사용자 통계 API 명세 또는 화면/정책 문서
  - 도메인 이해노트
- 반영할 내용:
  - 현재 API-STAT-001은 `book_rental`, `reading_progress`, `review`, `favorite_book` 실시간 조회 기준
  - `user_reading_statistic`는 현재 미사용(dormant/legacy 후보)
  - 배치/스냅샷 통계가 필요해질 때 재활성화 또는 제거 여부를 별도 검토

## 7. 마지막 Swagger/Postman 테스트 산출물 생성 계획

PR #46 코드리뷰 대응 구현이 끝난 뒤, 아래 경로에 최종 수동 테스트 산출물을 만든다.

- 대상 경로: `api-test-results/관리자 API (대시보드통계감사로그 등)/마지막 관리자 API 0714`
- SQL 파일명 예시: `마지막_관리자API0714_테스트데이터_준비및원복.sql`
- 체크리스트 파일명 예시: `마지막_관리자API0714_Swagger_Postman_체크리스트.md`

### 7.1 공통 작성 원칙

두 파일은 서로 교차 확인하지 않아도 테스트를 이어갈 수 있게 작성한다.

- `.sql` 파일만 봐도 테스트 데이터 준비, Swagger/Postman 호출 지점, 사후 DB 확인, 원복 위치를 순서대로 알 수 있어야 한다.
- 체크리스트 `.md` 파일만 봐도 어떤 API를 어떤 Method/URL/Query/Body로 호출하고, 어떤 응답을 확인해야 하는지 알 수 있어야 한다.
- 두 파일은 같은 절 번호를 공유한다. 예: SQL `§2`와 체크리스트 `§2`는 같은 테스트를 의미한다.
- 각 테스트는 “사전 SQL 또는 조건 확인 → API 호출 → 응답 확인 → 사후 SQL 확인 → 원복” 순서로 작성한다.
- Swagger UI에서 클라이언트 검증 때문에 서버 응답을 확인하지 못하는 invalid 값 테스트는 Postman 테스트로 명시한다.
- 실제 테스트 실행 전에는 서버가 PR #46 코드리뷰 대응 구현이 반영된 최신 코드로 재기동되어 있어야 한다.

### 7.2 `.sql` 파일 작성 계획

SQL 파일은 단순 insert 모음이 아니라 테스트 진행 안내서 역할까지 한다.

필수 포함 내용:

- `§0` 테스트 전제와 사용법: 관리자 JWT/회원 JWT 필요, Swagger UI 주소, Postman 사용 케이스, 대상 체크리스트 파일명
- `§1` 현재 DB 상태 확인: 관리자 계정, 회원 계정, 통계 관련 데이터 존재 여부, `idx_reading_progress_last_read_at` 인덱스 존재 여부 확인 SQL
- `§2` 관리자 대시보드 회귀 확인 전 DB 조회: `GET /api/v1/admin/dashboard` 호출 전에 기대값 또는 확인 대상 데이터 조회
- `§3` 관리자 통계 정상 응답 확인 전 DB 조회: `TOTAL/WEEKLY/MONTHLY/YEARLY`와 `baseDate`, `ageBand` 기대값 확인 SQL
- `§4` 사용자 통계 정상 응답 확인 전 DB 조회: 로그인 회원 기준 대여/완독/읽은 페이지/리뷰/즐겨찾기 기대값 확인 SQL
- `§5` 감사 로그 조회/필터 확인 전 DB 조회: actionType/targetType별 감사 로그 존재 여부 확인 SQL
- `§6` Postman invalid 값 테스트 안내: SQL 준비는 필요 없지만 `periodType=DAILY`, `actionType=INVALID`, `targetType=INVALID` 호출 위치를 주석으로 명시
- `§7` 사후 확인: Swagger/Postman 호출 뒤 응답과 DB가 맞는지 확인하는 SELECT
- `§8` 원복: 테스트 목적으로 추가한 데이터만 되돌리는 SQL. 운영/공유 DB 수동 인덱스는 원복 대상이 아니라 적용 여부 확인 대상으로 둔다.

`idx_reading_progress_last_read_at`는 `schema.sql`에 넣지 않는 것으로 확정했으므로, SQL 파일에는 다음 관점을 명시한다.

- 이 인덱스는 별도 수동 적용 인덱스다.
- 테스트 DB에 없으면 수동 인덱스 SQL을 실행한 뒤 다시 확인한다.
- fresh schema 자동 생성 기대값으로 검증하지 않는다.

### 7.3 체크리스트 `.md` 파일 작성 계획

체크리스트는 모든 테스트 행에 API 번호, Method, 실제 URL을 각각 적는다. 같은 API라도 Query 조합이 다르면 별도 행으로 둔다.

필수 컬럼:

| 컬럼 | 작성 기준 |
|---|---|
| 번호 | `§1-1`, `§1-2`처럼 SQL 절 번호와 맞춘다. |
| 도구 | Swagger 또는 Postman |
| API 번호 | API 명세의 API ID를 적는다. |
| Method | `GET`, `POST`, `PUT` 등 실제 HTTP Method를 적는다. |
| 실제 URL | Query string까지 포함해 그대로 호출할 URL을 적는다. |
| Body | GET은 `없음`, Body가 필요한 요청은 JSON 예시를 그대로 적는다. |
| 사전 SQL | SQL 파일의 실행 절 번호를 적는다. |
| 기대 응답 | HTTP status, `success`, `code`, 핵심 `data` 필드를 적는다. |
| 사후 확인/원복 | SQL 파일의 확인/원복 절 번호를 적는다. |

최소 포함 테스트:

| API 번호 | Method | 실제 URL | 도구 | Body | 확인 목적 |
|---|---|---|---|---|---|
| API-ADMIN-DASHBOARD-001 | GET | `/api/v1/admin/dashboard` | Swagger | 없음 | 관리자 대시보드 회귀 확인 |
| API-ADMIN-STAT-001 | GET | `/api/v1/admin/statistics?periodType=TOTAL&baseDate={baseDate}&ageBand=ALL` | Swagger | 없음 | TOTAL 정상 응답과 최근 12개월 bucket 확인 |
| API-ADMIN-STAT-001 | GET | `/api/v1/admin/statistics?periodType=WEEKLY&baseDate={baseDate}&ageBand=ALL` | Swagger | 없음 | WEEKLY 7일 bucket 확인 |
| API-ADMIN-STAT-001 | GET | `/api/v1/admin/statistics?periodType=MONTHLY&baseDate={baseDate}&ageBand=20S` | Swagger | 없음 | MONTHLY + ageBand 만 나이 필터 확인 |
| API-ADMIN-STAT-001 | GET | `/api/v1/admin/statistics?periodType=YEARLY&baseDate={baseDate}&ageBand=ALL` | Swagger | 없음 | YEARLY 12개월 bucket 확인 |
| API-ADMIN-STAT-001 | GET | `/api/v1/admin/statistics?periodType=DAILY&baseDate={baseDate}` | Postman | 없음 | invalid periodType 서버 응답 `400 VALIDATION_ERROR` 확인 |
| API-STAT-001 | GET | `/api/v1/me/statistics?periodType=TOTAL&baseDate={baseDate}` | Swagger | 없음 | 사용자 통계 TOTAL 정상 응답 확인 |
| API-STAT-001 | GET | `/api/v1/me/statistics?periodType=WEEKLY&baseDate={baseDate}` | Swagger | 없음 | 사용자 통계 WEEKLY bucket 확인 |
| API-STAT-001 | GET | `/api/v1/me/statistics?periodType=DAILY&baseDate={baseDate}` | Postman | 없음 | invalid periodType 서버 응답 `400 VALIDATION_ERROR` 확인 |
| API-ADMIN-AUDIT-001 | GET | `/api/v1/admin/audit-logs?page=0&size=10` | Swagger | 없음 | 감사 로그 기본 조회 확인 |
| API-ADMIN-AUDIT-001 | GET | `/api/v1/admin/audit-logs?actionType=BOOK_CREATE&page=0&size=10` | Swagger | 없음 | actionType enum 정상 필터 확인 |
| API-ADMIN-AUDIT-001 | GET | `/api/v1/admin/audit-logs?targetType=BOOK&page=0&size=10` | Swagger | 없음 | targetType enum 정상 필터 확인 |
| API-ADMIN-AUDIT-001 | GET | `/api/v1/admin/audit-logs?actionType=INVALID&page=0&size=10` | Postman | 없음 | invalid actionType `400 VALIDATION_ERROR` 확인 |
| API-ADMIN-AUDIT-001 | GET | `/api/v1/admin/audit-logs?targetType=INVALID&page=0&size=10` | Postman | 없음 | invalid targetType `400 VALIDATION_ERROR` 확인 |

이번 PR #46 대응 범위의 API 호출은 모두 GET이므로 Body는 `없음`으로 명시한다. 이후 다른 관리자 write API까지 같은 체크리스트에 합치게 되면, 해당 행마다 JSON Body 예시를 반드시 포함한다.
