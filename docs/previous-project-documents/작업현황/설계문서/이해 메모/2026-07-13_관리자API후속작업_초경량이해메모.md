## 항목 1 — 감사 로그 actionType/targetType 검증 (§7, 안 B)

- API: GET /api/v1/admin/audit-logs
- 목적: 잘못된 actionType/targetType이 조용히 빈 목록(200)으로 처리되지 않고 fail-fast하게 한다.
- 흐름: AdminAuditLogController -> AdminAuditLogService.getAuditLogs() -> AdminAuditLogActionType/TargetType.isValid() 대조 -> 실패 시 BusinessException(VALIDATION_ERROR)
- DB: 스키마 변경 없음. AdminAuditLog.actionType/targetType은 여전히 순수 String 컬럼.
- 주의: 컨트롤러 `@Pattern`이 아니라 서비스단 상수 대조 방식(안 B) — 상수 클래스에 값이 추가돼도 정규식을 따로 안 고쳐도 된다.

## 항목 2 — ReadingProgressRepository grouped 쿼리 테스트 (§6)

- API: (직접 API 아님) AdminStatisticService의 completedReadTrend 내부 의존 쿼리
- 목적: groupByDayCompletedStatisticConditions/groupByMonthCompletedStatisticConditions의 GROUP BY 결과가 정확한지 repository 단위로 직접 검증.
- 흐름: ReadingProgressRepositoryTest에서 baseline bucket count 캡처 -> 완독 데이터 1건 삽입 -> delta가 정확히 +1인지 확인.
- DB: 실제 공유 MySQL 기준, 절대 건수 대신 baseline-delta로 검증(격리 문제 회피).
- 주의: 완독 "률"이 아니라 "수"(건수) 집계다. 완독률 필드는 현재 응답에 없음.

## 항목 3 — TOTAL 기준일 차이 (§4, 안 A)

- API: GET /api/v1/admin/statistics?periodType=TOTAL
- 목적: periodEndDate(항상 오늘)와 추이/ageBand(baseDate 기준) 계산 기준일이 다르다는 사실을 문서화.
- 흐름: 코드 변경 없음 — AdminStatisticService.resolvePeriodRange()의 TOTAL 분기는 기존 그대로.
- DB: 해당 없음.
- 주의: 코드 결함이 아니라 문서 누락이었음. 실제 반영은 `docs/작업현황/설계문서/2026-07-13_관리자API후속작업_설계문서_반영예정.md` 참고.

## 항목 4 — trend label 포맷 규칙 문서화 (§5)

- API: (직접 API 아님) 관리자 통계 추이 필드 전반
- 목적: native SQL alias 포맷과 서비스 bucket label 포맷이 항상 같아야 한다는 제약을 문서로 고정.
- 흐름: 코드 변경 없음 — 문서만 신규 작성.
- DB: 해당 없음.
- 주의: 포맷을 바꾸는 다음 작업자가 repository/service/test 3곳을 함께 고쳐야 함을 반영예정 문서에 명시.

## 항목 5 — 성능 인덱스 적용현황 추적 (§3)

- API: (직접 API 아님) 운영 DB 성능 관련
- 목적: `관리자통계_성능인덱스.sql`이 각 DB에 실제 적용됐는지 추적할 표를 마련.
- 흐름: 문서만 생성, 코드/스키마 변경 없음.
- DB: `book_rental.created_at`, `reading_progress.completed_at`, `review(status, created_at)` 인덱스 대상.
- 주의: 실제 인덱스 적용(로컬/공유 DB)은 이번 작업 범위 밖 — 표는 비어 있는 상태로 시작.
