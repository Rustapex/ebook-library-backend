# PR49 API-AUTH-006 설계문서 반영 예정 기록

## 1. API ID를 API-AUTH-006으로 배정한 이유

- 최초 구현계획(`docs/작업현황/2026-07-15_로그인아이디_중복확인_API_구현계획.md`)은 신규 중복확인 API에 `API-AUTH-004`를 배정했다.
- PR #49 코드리뷰에서 `docs/API 명세/api-spec(final).md:385`에 `API-AUTH-004`, `API-AUTH-005`가 이미 **제외된 비밀번호 재설정 API**로 기록돼 있음이 확인됐다(병합 차단 사유).
- `API-AUTH-004`, `005`의 제외 이력은 그대로 보존하고, 충돌하지 않는 다음 번호인 `API-AUTH-006`을 신규 중복확인 API에 배정한다.

## 2. API 목록 요약에 추가할 내용

- Method: `GET`
- URL: `/api/v1/auth/check-login-id`
- 권한: 익명(비로그인) — `permitAll`
- 화면: 회원가입 화면의 아이디 입력란 실시간 확인
- Entity: `member`(조회 전용, 변경 없음)

## 3. Auth 상세 명세에 추가할 내용

- Query Parameter: `loginId`(필수, 5~20자, 영문·숫자만, `SignupRequest.loginId`와 동일 규칙)
- Response: `{ "loginId": string, "available": boolean }`
- 상태 코드: 형식 유효 + 사용 가능/중복 모두 `200`, 형식 오류는 `400 VALIDATION_ERROR`

## 4. 중복된 유효 아이디도 409가 아닌 200인 이유

- 이 API는 "확인" 목적의 조회이며 리소스를 생성하지 않는다. 중복 여부 자체가 정상적인 조회 결과이므로 오류(409)가 아니라 `available=false`로 표현한다.
- 409는 실제 리소스 생성(회원가입) 시점에 발생하는 충돌에만 사용한다는 프로젝트 공통 규칙을 그대로 따른다.

## 5. 회원가입 409와 DB UNIQUE가 최종 방어선인 이유

- 이 API는 아이디를 예약하지 않는다. 확인 직후 다른 요청이 동일 아이디로 먼저 가입할 수 있다(TOCTOU).
- 최종 방어선은 여전히 `AuthService.signup()`의 `existsByLoginId()` 사전 검사 + `409 MEMBER_LOGIN_ID_DUPLICATED`, 그리고 `member.login_id`의 DB `UNIQUE` 제약이다. 이 API 추가로 이 방어선의 우선순위나 동작은 바뀌지 않는다.

## 6. @ValidLoginId로 검증 계약을 공통화한 내용

- 기존에는 `SignupRequest.loginId`와 `CheckLoginIdRequest.loginId`가 각각 `@NotBlank`/`@Size(5,20)`/`@Pattern(^[a-zA-Z0-9]+$)`를 개별 선언해, 한쪽만 수정되면 회원가입과 중복확인의 판정이 갈릴 위험이 있었다(PR #49 코드리뷰 비차단 권고 2번).
- `src/main/java/com/acorn/abc/auth/validation/ValidLoginId.java`(조합 애노테이션, 별도 `ConstraintValidator` 없이 `@NotBlank`/`@Size`/`@Pattern`을 조합)를 신규 작성하고 두 DTO 모두 이 애노테이션 하나로 교체했다.
- `@ReportAsSingleViolation`을 쓰지 않아 기존처럼 필드별 개별 위반 메시지가 유지되고, `LoginRequest.loginId`(로그인 식별자 입력)에는 적용하지 않았다(신규 아이디 생성/판정 계약과는 다른 흐름이므로 공통화 범위에서 제외).

## 7. MySQL Collation에 따른 대소문자 중복 정책과 근거

- `member` 테이블(schema.sql 기준)은 `utf8mb4_0900_ai_ci` Collation을 사용하며 이는 대소문자를 구분하지 않는다(`ai_ci` = accent-insensitive, case-insensitive).
- 즉 `existsByLoginId()`는 대소문자만 다른 아이디도 이미 존재하는 것으로 판단하며, 이는 회원가입 시점의 `UNIQUE` 제약과 동일한 기준이다.
- `MemberRepositoryLoginIdIntegrationTest`(Mock이 아닌 실제 로컬 MySQL 대상)로 원본/전체대문자/전체소문자 3가지 케이스 모두 `existsByLoginId=true`임을 자동 검증했다(PR #49 코드리뷰 비차단 권고 3번 반영).

## 8. 공개 GET 경로와 운영 Edge 속도 제한/429/관리형 Challenge 계획

- `SecurityConfig`의 공개 GET 목록에 `/api/v1/auth/check-login-id` 1건만 추가했다. 다른 `/api/v1/auth/**` 경로나 POST 공개 목록은 변경하지 않았다.
- `available=true/false` 응답은 구조적으로 아이디 존재 여부를 노출한다. 정상 계약(200/400, `available` 필드)은 유지하되, 운영 공개 전에는 Edge/CDN/WAF/API Gateway에서 이 경로 전용 속도 제한(Token Bucket 또는 Sliding Window, 초기 후보 IP당 10회/분·Burst 5회)과, 반복 초과 시에만 관리형 Challenge를 적용하는 것을 권장안으로 확정했다(PR49 후속수정계획 §5).
- 제한 초과 응답은 `429` + `Retry-After`로 하고, 정상 200/400/응답 DTO 계약은 바꾸지 않는다. 접근/애플리케이션 로그에는 `loginId` 원문을 남기지 않는다.
- 이번 PR 범위에서는 Redis/속도 제한 의존성을 도입하지 않았다 — 운영 환경에 Edge/Gateway가 없다고 확인되는 경우에만 별도 승인 과제로 Redis 기반 대안을 검토한다.
- `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` 헤더는 Spring Security 기본 `HeaderWriterFilter`가 이미 모든 응답(permitAll 포함)에 적용하고 있음을 `AuthSecurityIntegrationTest`로 직접 확인했다 — 추가 코드 보완은 필요 없었다.

## 9. 스키마/데이터 마이그레이션 변경 없음 판단

- 기존 `member.login_id UNIQUE` 제약을 그대로 재사용하며 `schema.sql`을 수정하지 않았다.
- 신규 `ErrorCode`도 추가하지 않았다(기존 `VALIDATION_ERROR` 재사용).

## 10. 실제 설계 문서 반영 시 수정할 위치

- `docs/API 명세/api-spec(final).md:166-168`(인증 API 목록) — `API-AUTH-006` 행 추가.
- `docs/API 명세/api-spec(final).md:385` 인근(제외 API 이력) — `API-AUTH-004`/`005` 제외 이력은 그대로 두고, 바로 아래에 `API-AUTH-006` 신규 배정 사실만 덧붙인다.
- Auth 상세 명세 절 — Query/Response/상태 코드표에 위 §3 내용 반영.
- 화면흐름도(회원가입 화면 절) — 아이디 확인 버튼과 이 API 연동 관계 추가.
- 보안/운영 정책 문서(있다면) — §8의 Edge 속도 제한 계획을 배포 전 체크리스트 항목으로 추가.

이번 PR에서는 위 원문들을 직접 수정하지 않았다. 실제 반영은 별도 지시가 있을 때 이 문서를 기준으로 진행한다.
