## 1. `reviewCount`/`reportCount` 0 고정 정책 — 뒤집힘

- **기존 확정 내용**(`docs/작업현황/0710/2026-07-10_관리자-대시보드-통계-감사로그API_구현계획.md` §4-4, 2026-07-10 확정): "review 패키지에 Repository가 없어 `reviewCount`/`reportCount`는 항상 0으로 고정한다."
- **같은 취지로 남아있는 문서**: `docs/작업현황/2026-07-11_PR37코드리뷰반영_Swagger검증_체크리스트.md`(§ "review_count/report_count는 review 패키지 Repository 부재로 항상 0"), `docs/작업현황/0710/2026-07-10_관리자-대시보드-통계-감사로그API_Swagger검증_체크리스트.md`(§3-1 "reviewCount/reportCount는 항상 0이어야 한다").
- **새로 확정된 내용**(2026-07-12): PR #41에서 `BookReportRepository`/`ReviewReportRepository`/`ReviewRepository`가 실제로 추가되면서 위 전제가 깨졌다. `AdminStatisticService`가 이제 `reviewCount = ReviewRepository.countByStatus("ACTIVE")`, `reportCount = BookReportRepository.count() + ReviewReportRepository.count()`로 실제 집계한다.
- **반영 대상**: 위 3개 문서에 "이 결정은 PR #41(2026-07-12)에서 뒤집힘"이라는 주석을 추가(과거 이력은 삭제하지 않고 남긴다 — `CLAUDE.md` "PR 코드리뷰 대응은 ... 이전 차수에서 정정된 항목도 지우지 않고 이력을 남긴다" 원칙).

## 2. `reviewCount` 집계 기준 — 애매했던 부분이 확정됨

- **기존 상태**: `docs/API 명세/api-spec(final).md` 133행에 "`reviewCount` | number | 활성 리뷰 수"라고만 적혀 있고(이건 `BookCardResponse`용 설명이라 `AdminStatisticResponse.reviewCount`에 그대로 적용되는지는 명시돼 있지 않았음), `AdminStatisticService`에 review 집계 로직 자체가 없어 실제로 무엇을 셀지 정해진 바 없었다.
- **새로 확정된 내용**(2026-07-12): `AdminStatisticResponse.reviewCount`도 `BookCardResponse.reviewCount`와 동일하게 "활성(ACTIVE) 리뷰 수"로 통일 — `Review.STATUS_ACTIVE` 기준 `ReviewRepository.countByStatus(...)`. `HIDDEN`/`DELETED` 리뷰는 제외.
- **반영 대상**: `docs/API 명세/api-spec(final).md`의 관리자 통계 조회(API-ADMIN-STAT-001) 절에 `reviewCount` 필드 설명이 있다면 "활성 리뷰 수(status=ACTIVE) 기준"으로 명시. 없다면 이번에 필드 설명 자체를 새로 추가할지 검토.

## 3. `AdminAuditLogWriter` 감사 로그 summary 저장 계약 — 새 규칙 확정

- **기존 상태**: `docs/작업현황/0710/2026-07-10_관리자-대시보드-통계-감사로그API_구현계획.md` §6.6에는 "beforeSummary/afterSummary는 문자열로 저장한다"는 정도만 있고, 호출부가 문자열을 어떻게 만드는지(하드코딩 JSON 문자열 조립)까지는 규칙으로 못박혀 있지 않았다. 실제로 5개 호출부 중 상당수가 `"{\"key\":\"" + value + "\"}"` 식으로 직접 조립하고 있었다.
- **새로 확정된 내용**(2026-07-12, PR #41 리뷰 항목 1): `AdminAuditLogWriter.record(...)`는 `beforeSummary`/`afterSummary` 파라미터를 `Object`로 받아 내부에서 무조건 `ObjectMapper.writeValueAsString(...)`으로 직렬화한다. **호출부는 반드시 `Map`(또는 record 등 구조화된 객체)만 넘겨야 하며, 이미 완성된 JSON 문자열을 넘기면 안 된다** — 문자열을 넘기면 그 문자열 전체가 다시 JSON 문자열로 감싸져 이중 인코딩된다(실제로 `CouponService.issueCoupon()`/`PointService.adjustPointByAdmin()` 두 곳에서 이 실수로 회귀가 발생했다가 같은 날 수정됨, `audit_log_id=33, 35`가 이중 인코딩된 채로 DB에 남아 있었음).
- **추가로 확인된 환경 제약**: 이 프로젝트는 Spring Boot 4(Jackson 3, `tools.jackson`) 환경이라 `com.fasterxml.jackson.databind.ObjectMapper`가 자동 구성 빈으로 제공되지 않는다(`JacksonAutoConfiguration`이 `tools.jackson.databind.json.JsonMapper`만 등록함). 그래서 `AdminAuditLogWriter`도 `NaverBookClient`/`AladinBookClient`/`InfoNaruBookClient`와 동일하게 `ObjectMapper`를 DI 받지 않고 정적 인스턴스로 직접 생성한다.
- **반영 대상**:
  - `docs/공통문서/백엔드_공통_개발_규칙.md`에 "감사 로그(`AdminAuditLogWriter.record`) 호출부는 구조화된 값(Map 등)만 전달한다 — 완성된 JSON 문자열 금지" 규칙 추가.
  - 같은 문서 또는 별도 절에 "이 프로젝트(Spring Boot 4/Jackson 3)에서는 `com.fasterxml.jackson.databind.ObjectMapper`가 Spring 빈으로 자동 구성되지 않으므로 DI하지 말고 정적 인스턴스를 쓴다" 규칙 추가(향후 다른 서비스에서 같은 실수로 컨텍스트 로딩 실패를 겪는 것을 방지하기 위함 — 실제로 이번에 `AdminAuditLogWriterTest` 관련 컨텍스트 로딩이 이 이유로 한 번 실패했었음).

## 4. `recentReports[*].reportId` 유니크 보장 안 됨 — 제약사항 신규 확정

- **기존 상태**: 화면설계/API 명세 어디에도 `reportId`의 유니크 범위(전역 유니크인지, targetType별인지)가 명시돼 있지 않았다. `AdminRecentReportResponse.reportId`는 `book_report_id` 또는 `review_report_id`를 그대로 사용해서, BOOK 신고와 REVIEW 신고가 같은 `reportId` 값을 가질 수 있다.
- **새로 확정된 내용**(2026-07-12, PR #41 리뷰 항목 3): DTO 필드 타입은 바꾸지 않고, `reportId`는 **`targetType`과 조합해야만 유니크**하다는 제약을 문서화하기로 확정(코드 변경 없음, 설명 보강만). 실제 프론트 연동 시 유니크 식별이 필요해지면 `reportKey` 같은 별도 필드를 후속 검토.
- **반영 대상**: `docs/API 명세/api-spec(final).md`의 대시보드 API(API-ADMIN-DASHBOARD-001) 응답 스키마 설명에 `reportId`는 단독 유니크 값이 아니라는 문구 추가. `docs/화면흐름도/03-Admin-상세화면설계도.md`에 대시보드 신고 목록을 프론트가 어떻게 key로 쓸지 관련 내용이 있다면 함께 확인.

## 5. `AdminDashboardController` Swagger 설명이 실제 구현과 어긋나 있었던 점

- **기존 상태**: Swagger `@Operation description`에 "1차 구현으로 최근 결제만 포함하며, 최근 신고·최근 희망도서 위젯은 review/request 도메인 Repository 추가 후 후속 작업으로 제공될 예정"이라고 적혀 있었는데, 실제로는 이미 이전 커밋(`a661d67`)에서 두 위젯이 구현되어 있었다 — 문서(Swagger 설명)가 코드보다 뒤처져 있던 사례.
- **새로 확정된 내용**(2026-07-12): 설명을 실제 구현(대시보드가 KPI/최근 결제/최근 신고/최근 희망도서를 모두 반환)에 맞게 수정하고, `reportId` 식별 규칙(§4)도 같은 설명에 포함.
- **반영 대상**: 별도 설계문서 반영 항목은 없음(코드 내 Swagger 설명은 이미 수정 완료) — 다만 화면흐름도/구현계획 문서에 "최근 신고·희망도서는 후속 작업"이라고 적힌 부분이 남아 있다면 §1과 함께 정리 대상.
