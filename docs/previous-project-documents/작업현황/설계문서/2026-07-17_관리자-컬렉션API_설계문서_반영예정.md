# 관리자 컬렉션 API 설계문서 반영 예정 기록

작성일: 2026-07-17
근거: `docs/작업현황/2026-07-16_관리자-컬렉션API_구현계획.md`
성격: 실제 API 명세·ERD·정책·프론트 문서 원문을 지금 직접 수정하지 않고, 나중에 한 번에 반영할 변경 후보만 기록한다.

---

## 1. EVENT/EVENT_BOOK 문구를 통합 컬렉션 모델로 바꿀 예정인 근거

- 멘토링 전 정책 문서(566~599행)는 관리자 이벤트 CRUD 요구를 `EVENT`, `EVENT_BOOK` 신규 테이블로 전제하지만, 실제 런타임 DDL인 `src/main/resources/schema.sql`은 `collection`/`collection_book` + `collection_type IN ('SERIES','EVENT')` 통합 모델이다(D-01).
- 이번 구현은 기존 `Collection`/`CollectionBook` Entity·Repository를 그대로 재사용했고, 신규 테이블은 추가하지 않았다.
- 실제 정책 문서를 고칠 때는 "EVENT는 별도 테이블이 아니라 COLLECTION의 한 유형"으로 문구를 정정해야 한다.

## 2. 실제 SQL과 참고용 설계 ERD/DDL의 컬럼명 불일치

- 설계 ERD/DDL은 `collection_name`, `collection_description`, `collection_status`로 표기하지만, 실제 SQL은 `name`, `description`, `status`를 사용한다.
- 이번 구현(Entity, Repository, DTO)은 전부 실제 SQL 컬럼명 기준으로 작성했다.
- ERD/DDL 문서를 갱신할 때 위 3개 컬럼명 표기를 실제 SQL과 맞춰야 한다.

## 3. API-002를 수정 PUT, 신규 API-005를 생성 POST로 분리하는 확정 계약

- 기존 API 명세는 `PUT /api/v1/admin/collections/{collectionId}` 하나로 등록/수정을 모두 표현해 신규 생성 방법이 정의돼 있지 않았다(D-02).
- 확정: `POST /api/v1/admin/collections`(API-ADMIN-COLLECTION-005, 신규 생성, 201) / `PUT /api/v1/admin/collections/{collectionId}`(API-ADMIN-COLLECTION-002, 기존 수정 전용, 200).
- API 명세 갱신 시 API-002 설명에서 "등록" 표현을 제거하고 "수정 전용"으로 한정해야 한다.

## 4. 신규 API-006 관리자 상세 GET 확정 계약

- A-018(컬렉션 관리) 화면은 기존 컬렉션의 전체 정보와 등록 도서를 편집해야 하는데, 이를 위한 관리자 상세 조회 API가 명세에 없었다(D-03).
- 확정: `GET /api/v1/admin/collections/{collectionId}`(API-ADMIN-COLLECTION-006, 신규). HIDDEN/ENDED 컬렉션과 HIDDEN/INACTIVE 도서 mapping도 반환하며, 공개 상세(API-COLLECTION-002)와는 별도 조회 경로다(공개 상세를 재사용하면 HIDDEN/비공개 도서를 읽지 못하기 때문).
- API 명세에 API-ADMIN-COLLECTION-006 Method/URL/Response를 신규 항목으로 추가해야 한다.

## 5. API-003 partial upsert, API-004 atomic patch·idempotency

- API-003(`PUT .../books`)은 "전체 교체"가 아니라 "전달된 도서만 추가/순서 갱신, 미포함 기존 mapping은 유지"하는 partial upsert다(D-04). 도서 제외는 API-004의 책임으로 분리했다.
- API-004(`PATCH .../{collectionId}`)는 `status`와 `removeBookIds` 중 하나 이상이 있어야 하며, 둘 다 있으면 한 transaction으로 원자 처리한다(D-05). 이미 제거된 bookId 재요청이나 동일 status 재요청도 idempotent하게 200으로 성공 처리한다.
- API 명세의 API-003/004 설명에 이 저장 의미 차이를 명시해야 한다(현재 명세는 "저장"이라고만 돼 있어 전체 교체로 오해될 수 있음).

## 6. SERIES/EVENT 필드·정렬·유형 변경 규칙

- SERIES: `discountRate`/`startDate`/`endDate`는 항상 null이어야 하고, 도서 mapping은 양수·컬렉션 전체에서 중복되지 않는 `displayOrder`가 필수다.
- EVENT: `discountRate`(0~100, nullable), `startDate`/`endDate`(있으면 startDate<=endDate)만 사용하고, 도서 mapping의 `displayOrder`는 항상 null이어야 한다.
- mapping이 하나라도 있는 컬렉션은 `collectionType`(SERIES↔EVENT) 변경을 거부한다(D-08) — 임의 순서 생성/제거로 노출 순서가 깨지는 것을 막기 위함.

## 7. EVENT displayOrder 미사용·createdAt 순 조회, 7/15 계획 D-04 정정 예정

- 이번 계획 D-07은 "A-018 계약과 실제 SQL의 NULL 허용"에 따라 EVENT는 `displayOrder`를 사용하지 않고 `createdAt ASC` 순으로 조회하는 것으로 최종 확정했다.
- 기존 `docs/작업현황/2026-07-15_도서-카테고리-컬렉션API_코드리뷰대응_구현계획.md`의 D-04는 "EVENT에도 displayOrder 사용"을 권고했는데, 이번 결정과 상충한다.
- 해당 문서의 D-04 항목은 이번 결정으로 **정정 대상**이며, 실제 문서 반영 시 "EVENT는 displayOrder 미사용, createdAt 순"으로 고쳐야 한다. 이번 PR에서는 그 문서 원문을 직접 고치지 않았다.

## 8. 날짜는 정보, status가 공개 노출 기준이라는 결정

- 공개 컬렉션 노출 여부는 `status=ACTIVE` 하나만 기준으로 삼는다(D-09). `startDate`/`endDate`는 표시용 정보일 뿐 자동 필터링에 쓰이지 않는다(기존 공개 `CollectionService` 동작 그대로 유지, 변경 없음).
- 날짜 기반 자동 활성화/종료가 필요해지면 별도 배치나 스케줄러가 필요하며, 이번 범위에서는 다루지 않는다.

## 9. API-ADMIN-BOOK-001 의존성

- A-018 화면의 도서 검색은 관리자 도서 조회 API(API-ADMIN-BOOK-001)에 의존하지만, 이번 구현 범위에서는 만들지 않았다(D-14).
- API-003은 프론트가 이미 알고 있는 bookId를 받아 처리하는 것까지만 구현했다 — 실제 검색 UI 연결은 API-ADMIN-BOOK-001 완료 후 가능하다.

## 10. 감사 로그 enum 확장

- `AdminAuditLogActionType`에 `COLLECTION_CREATE`, `COLLECTION_UPDATE`, `COLLECTION_BOOKS_UPDATE`, `COLLECTION_PATCH` 4개를, `AdminAuditLogTargetType`에 `COLLECTION` 1개를 추가했다(D-11).
- 기존 값은 하나도 바꾸지 않았고, `AdminAuditLogController`의 `@Schema(allowableValues=...)`도 함께 갱신해 기존 Schema-enum 동기화 테스트(`AdminAuditLogControllerTest`)가 그대로 이 드리프트를 잡아냈다(실제로 구현 중 이 테스트가 실패해 즉시 수정함 — 아래 12번 참고).
- DB 컬럼(`admin_audit_log.action_type`/`target_type`)에는 CHECK 제약이 없어 schema 변경은 없다.

## 11. 스키마·데이터 마이그레이션 변경 없음 판단

- `src/main/resources/schema.sql`은 이번 구현에 필요한 테이블·FK·UNIQUE·CHECK·인덱스를 이미 전부 갖고 있어 변경하지 않았다.
- `GlobalExceptionHandler`, `SecurityConfig`, `ErrorCode`도 변경하지 않았다(기존 3개 ErrorCode와 기존 `/api/v1/admin/**` 보호 규칙 재사용).

## 12. 구현 중 확인된 사항(계획에 없던 추가 발견)

- `Collection`을 `BaseEntity`로 전환(D-15)하면서 `@CreatedDate`/`@LastModifiedDate` 자동 채움에 의존하게 됐다. `@DataJpaTest` 슬라이스는 `JpaAuditingConfig`를 자동으로 로드하지 않는다는 점은 이전 PR(회원정보수정)에서도 확인된 사항이라, 이번 신규 Repository 테스트(`CollectionBookRepositoryTest`)는 이 문제를 애초에 피하려고 native INSERT로 테스트 데이터를 준비했다(기존 `CollectionRepositoryTest`/`BookRepositoryTest`와 동일 패턴).
- `AdminCollectionServiceTest`에서 `Book` mock을 만드는 헬퍼(`bookOf()`)를 `given(...).willReturn(...)` 체인 내부에서 직접 호출했더니 Mockito의 `UnfinishedStubbingException`이 발생했다 — mock 생성/스텁을 별도 statement로 분리해서 해결했다(같은 실수를 반복하지 않도록 기록).
- 감사 로그 enum을 확장하면서 `AdminAuditLogController`의 Swagger `@Schema(allowableValues)`를 함께 갱신하는 것을 처음에 빠뜨렸는데, 기존에 만들어 둔 `AdminAuditLogControllerTest`의 Schema-enum 동기화 테스트가 전체 `./gradlew.bat build` 단계에서 즉시 실패로 잡아냈다. 이 안전장치가 실제로 유효하다는 것을 이번에 재확인했다.

## 13. 실제 미해결/한계로 남긴 사항

- API-003/004의 컬렉션 단위 `PESSIMISTIC_WRITE` lock(D-12)은 `findByIdForUpdate` 조회가 정상 동작하는 것만 자동 테스트로 확인했다 — 실제 동시 요청 직렬화(두 요청이 진짜로 순차 처리되는지)는 멀티스레드 테스트 없이는 증명되지 않는다. 이 부분은 Postman 동시 요청 시나리오로 별도 수동 검증한다(§10.3 체크리스트 참고).
- API-ADMIN-BOOK-001과 A-018 React 화면 연결은 이번 범위에서 다루지 않았다(9번 항목과 동일 사유).

## 14. 실제 문서 반영 범위

이번 PR에서는 위 1~13번 내용을 실제 API 명세(`docs/API 명세/api-spec(final).md`), ERD/DDL 문서, 화면흐름도, 7/15 공개 API 계획 문서 원문에 반영하지 않았다. 실제 반영은 별도 지시가 있을 때 이 문서를 기준으로 진행한다.
