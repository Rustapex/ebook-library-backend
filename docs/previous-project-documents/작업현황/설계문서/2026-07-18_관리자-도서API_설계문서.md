# 2026-07-18 관리자 도서 API 설계 문서

## 1. 적용 범위

- 기준 API 명세의 `API-ADMIN-BOOK-001`~`004`만 구현한다. 신규 `API-ADMIN-BOOK-005`는 만들지 않는다.
- 이 문서는 구현 전 계약 기록이다. `docs/API 명세/api-spec(final).md` 원문은 이번 세션에서 수정하지 않는다(사용자 지시) — 아래 §2가 실제 구현의 기준 계약이며, 명세 원문과의 차이는 §7에 별도로 남긴다.
- 프런트엔드 코드, 관리자 도서관·지도 API, 외부 연동 키 발급·보관·설정, 관리자 카테고리 API는 범위 밖이다.

| API ID | Method / URL | 확정 목적 |
|---|---|---|
| `API-ADMIN-BOOK-001` | `GET /api/v1/admin/books` | `HIDDEN`/`INACTIVE` 포함 관리자 도서 목록/검색/필터 |
| `API-ADMIN-BOOK-002` | `POST /api/v1/admin/books` | 허용 메타정보만 등록, 항상 `INACTIVE` 생성 |
| `API-ADMIN-BOOK-003` | `PUT /api/v1/admin/books/{bookId}` | 허용 메타정보 전체 교체(원문·페이지·키워드 보호) |
| `API-ADMIN-BOOK-004` | `PATCH /api/v1/admin/books/{bookId}/status` | `AVAILABLE`/`HIDDEN`/`INACTIVE` 상태만 변경 |

## 2. 확정 요청/응답 계약

### 2.1 목록(001)

- Query: `q?`, `categoryId?`, `rentalType?`, `status?`, `page?`(기본 0), `size?`(기본 20, 최대 100).
- `status`를 지정하지 않으면 `AVAILABLE`/`HIDDEN`/`INACTIVE` 전체를 조회한다(공개 목록과 달리 `AVAILABLE` 고정 조건 없음).
- 정렬은 `createdAt DESC, bookId DESC` 고정.
- `q`는 제목/ISBN/출판사명/저자명 부분일치(소문자 정규화 LIKE)를 OR로 검색한다.
- 응답은 `PageResponse<AdminBookSummaryResponse>`이며 각 항목은 `bookId, title, isbn, publisherName, authorNames[], categories[]{categoryId,categoryName}, rentalType, rentalPrice, defaultRentalDays, coverImageUrl, status, createdAt`을 포함한다.

### 2.2 등록(002)

- Request body: `title`, `isbn?`, `publisherName`, `authors[]`(저자명, 1~10개, 순서=배열 순서), `categoryIds[]?`(0~20개), `rentalType`(`FREE`/`PAID`), `rentalPrice`, `defaultRentalDays`, `coverImageUrl?`, `detail?{description?, tableOfContents?, publisherReview?}`.
- `status`는 요청으로 받지 않는다. 신규 도서는 항상 `INACTIVE`로 생성한다.
- `keywords[]`, `file`, `pages[]`, `detailContent`는 요청 필드로 두지 않는다 — 이 API는 실제 열람 원문·키워드·파일을 생성·수정·삭제하지 않는다.
- Response: `AdminBookSaveResponse(bookId, status, createdAt, updatedAt)`. 생성 시 `updatedAt`은 `null`.

### 2.3 수정(003)

- Path: `bookId`. Request body는 등록과 동일한 필드 집합(허용 메타정보 전체, `status` 제외)이며 PUT 전체 교체 의미로 처리한다 — 요청에 없는 선택 필드는 `null`로 교체된다(부분 patch 아님).
- 실 열람 원문(`BookPage`), 페이지, 키워드, 파일, 누적 집계값(`rentalCount`, `averageRating`, `reviewCount`, `totalPages`)은 어떤 경우에도 변경하지 않는다.
- Response: `AdminBookSaveResponse(bookId, status, createdAt, updatedAt)`(등록과 동일 타입 재사용 — `AdminCollectionSaveResponse`와 같은 기존 관례).

### 2.4 상태 변경(004)

- Path: `bookId`. Request body: `status`(`AVAILABLE`/`HIDDEN`/`INACTIVE` 중 하나, 필수), `reason?`(최대 500자, 감사 로그에만 기록되고 별도 컬럼에 저장하지 않음 — `book` 테이블에 사유 컬럼이 없음).
- 물리 삭제하지 않는다. Response: `AdminBookStatusChangeResponse(bookId, status)`.

### 2.5 보호 데이터

- 허용: 제목, ISBN, 출판사, 저자, 기존 `ACTIVE` 카테고리 연결, 대여 유형·가격·기간, 표지 URL, 안내성 상세(`description`/`tableOfContents`/`publisherReview`), 상태.
- 보호(이 API가 절대 건드리지 않음): `BookPage.pageContent`, `pages[]`, 키워드·키워드 매핑, 파일 업로드/다운로드, `book.rentalCount`/`averageRating`/`reviewCount`/`totalPages`, `book_detail.detailContent`.

## 3. 입력 검증 확정값

스키마 저장 가능 범위(`src/main/resources/schema.sql`)에 맞춰 아래를 DTO Validation 값으로 확정한다. 스키마가 명시적으로 제한하지 않는 항목(리스트 최대 개수, TEXT 컬럼 실질 상한)은 이번 구현에서 임의로 정한 값이며 향후 요구사항에 따라 조정 가능한 운영값으로 남긴다.

| 필드 | 제약 | 근거 |
|---|---|---|
| `title` | `@NotBlank`, 공백 정규화 후 length ≤ 255 | `book.title VARCHAR(255) NOT NULL` |
| `isbn` | 선택, 있으면 숫자 13자리(`^\d{13}$`) | `book.isbn CHAR(13)`, `uk_book_isbn` |
| `publisherName` | `@NotBlank`, 공백 정규화 후 length ≤ 100 | `publisher.publisher_name VARCHAR(100) NOT NULL` |
| `authors[]` | 1~10개, 각 항목 `@NotBlank` length ≤ 100, 중복 거부 | `author.author_name VARCHAR(100)`, 계획 §3.1 "작가명 중복 거부" |
| `categoryIds[]` | 0~20개, 중복 거부, 각 ID는 존재 + `status=ACTIVE` | 계획 §3.1, `category.status` CHECK |
| `rentalType` | `FREE` 또는 `PAID` | `chk_book_rental_type` |
| `rentalPrice` | `FREE`→0 고정, `PAID`→1 이상 | 계획 §3.1, `book.rental_price INT` |
| `defaultRentalDays` | 1 이상 정수 | `book.default_rental_days INT UNSIGNED NOT NULL`(기본값 없음 → 필수) |
| `coverImageUrl` | 선택, length ≤ 500 | `book.cover_image_url VARCHAR(500)` |
| `detail.description`/`tableOfContents`/`publisherReview` | 선택, 각 length ≤ 5000 | 컬럼은 `TEXT`(상한 없음) — 운영상 과도한 payload 방지용 임의 상한 |
| `status`(004) | `AVAILABLE`/`HIDDEN`/`INACTIVE` 중 하나 | `chk_book_status` |
| `reason`(004) | 선택, length ≤ 500 | 감사 로그 저장용 임의 상한(별도 컬럼 없음) |

- 카테고리가 존재하지 않거나 `ACTIVE`가 아니면 둘 다 `CATEGORY_NOT_FOUND`(404)로 응답한다(기존 코드베이스에 "존재하지만 비활성" 전용 에러코드가 없고, `BookApprovalService.resolveCategories`도 동일하게 `CATEGORY_NOT_FOUND` 하나로 처리하는 기존 관례를 따름). 신규 ErrorCode를 추가하지 않는다.

## 4. 출판사·작가 처리

- `PublisherRepository.findByPublisherName` / `AuthorRepository.findFirstByAuthorNameOrderByAuthorIdAsc`로 먼저 조회하고 없을 때만 `Publisher.create`/`Author.create`로 새로 저장한다(`BookApprovalService.approve()`와 동일한 find-or-create 패턴 재사용, 로직만 참고하고 클래스는 공유하지 않음).
- 관리자 동시 등록은 이번 범위에서 발생하지 않는다고 가정하며 별도 잠금·upsert·재시도를 추가하지 않는다(계획 §3.2).
- 기존 master의 이름·상태·생성 시각은 수정하지 않는다.

## 5. 목록 조회 구현 방식(계획 §3.3 대응)

계획 §3.3은 "동일 predicate로 bookId 페이지와 count(distinct book.id)를 먼저 구하고, 이후 연관 데이터를 bulk 조회해 재조립 — collection fetch join으로 페이지를 만들지 않는다"를 요구한다. 이번 구현은 아래와 같이 **기존 코드베이스에 이미 있는 `Specification`/`EXISTS` 서브쿼리 관례**로 이 요구를 만족시킨다(신규 `AdminBookSpecifications` 클래스 추가, 기존 `BookSpecifications`/`BookRepository.search()`는 수정하지 않음):

- `BookRepository`는 이미 `JpaSpecificationExecutor<Book>`을 구현하고 있고, 기존 `BookSpecifications.hasCategory`/`hasAnyCategory`도 `JOIN` 대신 `Subquery`+`EXISTS`로 카테고리 조건을 표현한다. 이 방식은 book 행을 절대 늘리지 않으므로 `collection fetch join` 페이지 버그(행 중복)가 원천적으로 발생하지 않는다.
- 신규 `AdminBookSpecifications`(작가/카테고리/상태/rentalType/q)도 동일하게 전부 `EXISTS` 서브쿼리 또는 단순 컬럼 비교로만 구성하고, `Author`/`Category`를 `JOIN`으로 root에 붙이지 않는다.
- `bookRepository.findAll(spec, pageable)`은 Spring Data JPA가 COUNT 쿼리와 content 쿼리를 자동으로 분리 실행하므로, 별도의 수동 `count(distinct ...)` 쿼리를 직접 작성하지 않아도 정확한 total과 안정적 정렬을 얻는다.
- 페이지에 포함된 `bookId` 목록으로 `BookAuthorRepository`/`BookCategoryRepository`에 신규 추가하는 관리자 전용 bulk 조회 메서드(`findAllByBookIdIn`, 상태 필터 없음 — 공개 `findActiveByBookId(s)`는 `status='ACTIVE'` 필터가 있어 관리자 화면에서 비활성 저자/카테고리를 숨기므로 재사용하지 않고 별도 메서드로 추가)를 호출해 `Map<Long, List<...>>`로 묶은 뒤 `AdminBookSummaryResponse`를 조립한다. 이 부분은 `AdminCollectionService.getAdminCollections()`의 "페이지 조회 후 ID로 매핑 데이터 bulk 조회" 패턴과 동일하다.

## 6. 동시 수정 잠금(계획 §3.3 대응)

- `BookRepository`에 `@Lock(PESSIMISTIC_WRITE)` `findByIdForUpdate(bookId)`를 신규 추가한다(`CollectionRepository`/`MemberRepository`/`SanctionHistoryRepository`와 동일한 기존 관례).
- 계획 §3.3은 잠금 대기를 "5초, transaction-bound 동일 JDBC connection에서만 설정, 기존 값을 읽어 try/finally로 복원"하도록 명시했고, 이 코드베이스에는 세션 타임아웃을 직접 조작하는 선례가 없었다. 계획 원문을 그대로 구현하기로 확정했다(사용자 결정, 2026-07-20).
- 구현: `book.service` 패키지에 `BookLockTimeoutSupport` 빈을 추가한다. `EntityManager.unwrap(Session.class).doWork(connection -> ...)`로 현재 트랜잭션과 동일한 JDBC connection 위에서 `SELECT @@SESSION.innodb_lock_wait_timeout`로 기존 값을 읽고 `SET SESSION innodb_lock_wait_timeout = 5`로 변경한 뒤, `try { 잠금 조회 + 본문 수정 } finally { 원래 값으로 SET SESSION 복원 }`한다. commit·rollback·예외 어느 경로든 finally가 실행되므로 값 복원이 보장된다.
- `AdminBookService.updateAdminBook()`, `changeAdminBookStatus()`(003/004의 write 경로) 모두 이 헬퍼로 `findByIdForUpdate` 이후 로직을 감싼다.
- MySQL lock wait timeout 초과·deadlock은 `PessimisticLockingFailureException`으로 전파되고, 기존 `GlobalExceptionHandler.handlePessimisticLockingFailureException()`이 이미 `CONCURRENT_UPDATE`(409)로 변환한다(추가 코드 불필요 — `CONCURRENT_UPDATE`는 이미 `ErrorCode.java`에 존재함, §8 참고). 자동 재시도는 하지 않는다.

## 7. 감사 로그·rollback

- 등록: `BOOK_CREATE` / `BOOK`, `beforeSummary=null`, `afterSummary`에 `bookId, title, isbn, status, rentalType, rentalPrice, defaultRentalDays, publisherName, authorNames, categoryIds` 기록.
- 수정·상태 변경: `BOOK_UPDATE` / `BOOK`, 같은 키 집합으로 `beforeSummary`/`afterSummary` 기록.
- `AdminAuditLogWriter.record()`는 호출자의 `@Transactional`에 그대로 참여하므로(기존 구현 그대로, 수정하지 않음) 본문 저장과 감사 로그가 항상 같은 transaction이다. 감사 writer 예외는 잡지 않고 전파해 본문도 함께 rollback된다(fail-closed, 기존 구현 자체가 이미 이 정책).
- 조회(001)는 감사 writer를 호출하지 않는다.

## 9. 검증 핵심

- 신규 도서는 항상 `INACTIVE`, `keywords[]`/`file`/`pages[]`/`detailContent`는 요청·응답 어디에도 없음.
- ISBN 중복(409), 존재하지 않거나 비활성인 카테고리(404), 저자/카테고리ID 중복(400).
- 수정 후에도 `BookPage`·키워드·`rentalCount`/`averageRating`/`reviewCount`/`totalPages`가 변경되지 않음.
- 동시 수정 시 두 번째 요청이 잠금 대기 후 409(`CONCURRENT_UPDATE`)로 응답하고, 세션 타임아웃 값이 원래대로 복원됨.
- 실패(child 저장 실패, 감사 로그 실패) 시 신규 book/detail/매핑/감사로그가 남지 않고, 수정 실패 시 이전 값이 완전히 복구됨.
