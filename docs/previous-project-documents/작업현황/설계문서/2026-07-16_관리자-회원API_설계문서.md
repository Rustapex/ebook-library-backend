# 2026-07-16 관리자 회원 API 설계 문서

## 1. 적용 범위

- 기준 API 명세의 `API-ADMIN-MEMBER-001`~`004`만 구현한다. 새 endpoint는 만들지 않는다.
- 이 문서는 구현 전 계약 기록이다. Java·런타임 스키마·기준 API 명세는 아직 수정하지 않았다.

| API ID | Method / URL | 확정 목적 |
|---|---|---|
| `API-ADMIN-MEMBER-001` | `GET /api/v1/admin/members` | 개인정보를 최소화한 회원 목록/검색/필터 |
| `API-ADMIN-MEMBER-002` | `GET /api/v1/admin/members/{memberId}` | 기본 상세와 이력 탭 조회 |
| `API-ADMIN-MEMBER-003` | `PATCH /api/v1/admin/members/{memberId}/status` | 상태 및 제재 변경 |
| `API-ADMIN-MEMBER-004` | `POST /api/v1/admin/members/{memberId}/points` | 멱등 포인트 조정 |

## 2. 조회·개인정보 계약

### 2.1 목록(001)

- query는 `q?`, `status?`, `role?`, `gradeId?`, `page?`, `size?`를 사용한다.
- page는 0-based(기본 0), size 기본 20·최대 100이며 기본 정렬은 `createdAt DESC, memberId DESC`다.
- 검색 대상은 이름·로그인 아이디·이메일이다.
- 응답 이메일·전화번호는 마스킹한다. `birthDate`, `gender`는 DTO에 선언하지 않는다.
- 목록에는 현재 유효 제재의 최소 요약만 포함한다. 만료 제재 사유와 원문 PII는 제외한다.

### 2.2 상세(002)

| `tab` | 응답 |
|---|---|
| 미지정 / `DEFAULT` | 프로필 및 이용 요약. 원문 이메일·전화번호·생년월일·성별 포함 가능 |
| `RENTALS`, `PAYMENTS`, `REPORTS`, `POINTS`, `SANCTIONS` | 해당 데이터만 담은 탭 전용 `PageResponse` |

- 탭 응답은 기본 상세 DTO를 재사용하지 않는다. `profile`은 null이 아니라 필드 자체를 포함하지 않는다.
- 탭은 `page=0`, `size=20`, 최대 100을 적용한다. 발생시각 내림차순 후 PK 내림차순을 고정 정렬로 사용하며 `SANCTIONS`는 `startedAt DESC, sanctionHistoryId DESC`다.
- 잘못된 tab, page, size는 `VALIDATION_ERROR`(400)다.

## 3. 상태·제재·ADMIN 대상 보호

- 대상 회원이 `ADMIN`이면 조회만 허용한다. 상태·제재·포인트 변경은 Controller와 Service 모두에서 거부하며 Service가 최종 방어선이다.
- `WITHDRAWN`, `DEACTIVATED` 대상은 조회만 허용하고 상태·제재 변경은 거부한다.
- `ACCOUNT_SUSPENSION`만 `SANCTIONED`로 전이하고 로그인 차단을 유발한다.
- `RENTAL_BAN`, `REVIEW_BAN`은 `SANCTION_HISTORY`만 생성한다. 회원 상태를 바꾸지 않고 계정 정지 복구와도 무관하게 각각의 기능 접근 제어에서 독립적으로 유지한다.
- 성공한 상태/제재 변경·제재 이력·관리자 감사 로그는 하나의 transaction으로 처리한다. 거부된 시도는 별도 보안 감사 로그를 만들지 않는다.

## 4. 계정 정지 만료 배치 설계

- `member.current_sanction_id` nullable FK는 현재 `SANCTIONED` 상태를 만든 `ACCOUNT_SUSPENSION` 이력의 ID다. 계정 정지 생성 시 설정하고, 다른 경로가 상태를 만들거나 해제하면 함께 갱신/해제한다.
- ADMIN이 아니고, 현재 `SANCTIONED`이며, `currentSanctionId`가 만료 후보와 같고, 후보가 만료된 `ACCOUNT_SUSPENSION`이며, 다른 활성 계정 정지가 없을 때만 JOINED로 복구한다.
- 회원·관련 제재 행은 `PESSIMISTIC_WRITE` 또는 동등한 조건부 갱신으로 보호한다. 원인 불일치·상태 변경·ADMIN 대상은 no-op이며 이력/감사 로그가 없다.
- 다른 활성 계정 정지가 있으면 상태를 복구하지 않고 `startedAt DESC, sanctionHistoryId DESC`의 최신 활성 제재로 연결값만 재지정한다. 실제 복구만 이력·감사 로그를 남기므로 배치 재실행은 멱등적이다.
- 잠금 대기 초과·deadlock은 자동 재시도하지 않으며 `CONCURRENT_UPDATE`(409)로 응답한다.

## 5. 포인트 조정(004) 설계

- request body는 기존 `pointAmount`, `description`에 필수 UUID `requestId`를 추가한다.
- `(memberId, requestId)`가 같고 금액·공백 정규화한 사유가 같으면 기존 성공 응답을 반환한다. 잔액·이력·감사 로그는 다시 만들지 않는다.
- 같은 키의 금액 또는 사유가 다르면 `IDEMPOTENCY_KEY_CONFLICT`(409)다.
- 새 요청은 대상 회원 행을 `PESSIMISTIC_WRITE`로 잠그고 ADMIN 대상 보호·0 금액·음수 잔액을 검사한다.
- 잔액 변경, `pointType=ADMIN_ADJUST` 이력, 성공 감사 로그는 하나의 transaction이다. 어느 하나라도 실패하면 모두 rollback한다.

## 6. 예정 DB·문서 변경

| 대상 | 변경 | 주의 |
|---|---|---|
| `member` | nullable `current_sanction_id` 및 `sanction_history` FK | 기존 null 회원은 자동 복구 후보가 아니다. |
| `point_history` | nullable `request_id CHAR(36)`, `UNIQUE(member_id, request_id)` | 기존 이력 null은 허용하고 신규 `ADMIN_ADJUST`만 requestId를 강제한다. |
| `docs/API 명세/api-spec(final).md` | 002 tab/page/size/정렬/PII, 004 requestId·멱등 규칙 보강 | 명세 반영 후 구현 계약으로 사용한다. |
| `docs/작업현황/ErrorCode_신규추가_완료.md` | `CONCURRENT_UPDATE`, `IDEMPOTENCY_KEY_CONFLICT` 기록 | 기존 ErrorCode는 변경하지 않고 enum 항목만 additive하게 추가한다. |

## 7. 검증 핵심

- 목록 PII 최소화, 상세 기본 PII 허용, 탭 응답 PII 미포함
- ADMIN·WITHDRAWN·DEACTIVATED 대상 변경 차단
- 계정 정지 원인 연결값 불일치/중첩 정지/ADMIN 대상에서 배치가 복구하지 않음
- 포인트 동시 차감의 음수 잔액 방지 및 requestId 재시도의 단일 반영
- 실패 시 잔액·이력·감사 로그·제재 이력이 남지 않음
