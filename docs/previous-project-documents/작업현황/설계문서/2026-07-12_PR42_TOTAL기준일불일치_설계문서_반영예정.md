# PR #42 Watchlist W1 — `TOTAL`의 기준일 불일치 설계문서 반영예정

성격: 이 문서는 기존 설계문서를 지금 바로 고치지 않는다는 세션 운영 규칙에 따라, 어디를 왜 어떻게 바꿀지만 추적하는 문서다. 실제 문서 반영과 코드 변경 여부 결정은 나중에 한 번에 진행한다.

## 무엇이 불일치하는가

`AdminStatisticService.resolvePeriodRange()`에서 `periodType=TOTAL`일 때 `periodEndDate`는 항상 `LocalDate.now()`(요청 시점의 오늘)다. 반면 같은 `TOTAL` 요청에서:

- 추이(`rentalTrend`/`paymentTrend`/`completedReadTrend`) bucket은 `resolvedBaseDate`(요청의 `baseDate` 파라미터, 없으면 `LocalDate.now()`) 기준 "최근 12개월"로 계산된다.
- `ageBand`(나이대) 만 나이 계산도 `resolvedBaseDate` 기준이다.

즉 `baseDate`를 명시적으로 넘긴 `TOTAL` 요청에서는 응답의 `periodEndDate`(항상 오늘)와 추이·나이대 계산 기준일(`baseDate`, 오늘과 다를 수 있음)이 서로 다른 날짜가 될 수 있다. 예를 들어 `GET /api/v1/admin/statistics?periodType=TOTAL&baseDate=2026-01-15&ageBand=20S`를 오늘(`2026-07-12`) 호출하면, `periodEndDate=2026-07-12`인데 추이는 `2025-02~2026-01`(2026-01-15 기준 최근 12개월), 나이대는 `2026-01-15` 기준 만 20세로 계산된다.

## 왜 문서화가 필요한가

- 리뷰에서 "소비자가 하나의 기준일 스냅샷으로 오해할 수 있다"고 지적했다 — API 응답만 보면 `periodEndDate`가 전체 응답의 "기준 시점"인 것처럼 보이지만, 실제로는 필드마다 기준일이 다르다.
- 현재 Swagger `@Parameter` 설명(`AdminStatisticController`)에 `baseDate`가 "TOTAL의 추이 bucket과 ageBand의 만 나이 계산 기준일로는 사용됩니다"라는 문구가 있어 코드 차원에서는 일부 안내가 되어 있지만, API 명세 문서에는 아직 반영되지 않았다.

## 코드 동작 변경이 필요한지 — 확정 필요 항목

이 문서 작성 시점에는 결정하지 않는다. 나중에 문서 반영 시점에 아래 중 하나를 택해야 한다.

- **안 A(현행 유지, 문서만 보강)**: `TOTAL`의 `periodEndDate`는 계속 "요청 시점의 오늘"로 두고(전체 기간 통계라는 의미와 맞음), 추이/나이대만 `baseDate` 기준이라는 차이를 API 명세에 명시한다.
- **안 B(동작 통일)**: `TOTAL`의 `periodEndDate`도 `resolvedBaseDate`로 통일해서, 하나의 요청 안에서는 모든 필드가 같은 기준일을 쓰도록 코드를 바꾼다.

## 반영 대상 문서(나중에 한 번에 반영)

- (안 B 채택 시) `AdminStatisticController`의 `@Operation`/`@Parameter` 설명도 실제 동작에 맞게 재수정.
- (안 B 채택 시) `AdminStatisticService`/`AdminStatisticServiceTest`의 `TOTAL` 기간 계산 로직·테스트 수정.
